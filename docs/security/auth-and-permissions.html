認證與資安

認證授權與權限機制

目的

本文件說明腳手架目前同時支援 Blazor UI Cookie 登入、Web API JWT Bearer 認證，以及 MCP Server 專用的 X-API-Key（McpApiKey）認證（1.0.5 起）。三者使用不同 authentication scheme，避免互相干擾。

Cookie 認證

Blazor UI 既有登入流程維持 Cookie authentication：

  • scheme 使用 MagicObjectHelper.CookieScheme。
  • Login path 為 /Auths/Login。
  • Logout path 為 /Auths/Logout。
  • Access denied path 為 /Auths/Login。

此機制主要服務 Razor/Blazor 頁面與既有後台使用者體驗。

Google OAuth2 第三方登入

網頁登入除了帳號密碼外，亦可選用 Google 單一登入（SSO）。Google 驗證完成後同樣以 MagicObjectHelper.CookieScheme 完成登入，並串接既有權控（RoleView）。首次登入會自動建立停用中的帳號，待管理者啟用；需呼叫 API 者可另行設定 API 密碼。完整設定與流程請見「Google OAuth2 第三方登入」一文。

UI 登入後檢查

Blazor 元件進入受保護頁面時，會透過 AuthenticationStateHelper.Check(...) 做 Cookie 認證後的二次檢查，並回傳 AuthenticationCheckResult 讓 Layout、NavMenu 或 Page 判斷是否繼續載入。

目前檢查項目：

  • 未登入或 Cookie 無效時，導向 /Auths/Logout，回傳 Unauthenticated。
  • ClaimTypes.Sid 缺失、格式錯誤或不是有效使用者 Id 時，導向 /Auths/Logout，回傳 InvalidUser。
  • 使用者不存在、帳號停用、缺少 RoleView 或角色權限 JSON 無法初始化時，導向 /Auths/Logout，回傳 InvalidUser。
  • 使用者仍使用需要強制更換的預設密碼時，導向 /ChangePassword，回傳 RequiresPasswordChange。
  • 檢查成功時，會把使用者、角色權限清單（RoleList）與角色的預設團隊清單（TeamList，來自 RoleView.DefaultTeamsJson）寫入 CurrentUserService.CurrentUser，回傳 Succeeded。

/ChangePassword 是強制改密碼流程允許進入的例外頁面；使用者在該頁完成密碼更新後，才會回到一般系統頁面。

JWT Bearer 認證

Web API 使用 JWT Bearer：

  • JWT 設定來源為 appsettings.json 的 JwtSettings。
  • JwtSettings 會綁定到強型別 KnowledgeExtraction.Web.Auth.JwtSettings。
  • Access token 用於 API 呼叫授權。
  • Refresh token 採 signed JWT，不落庫。

JwtSettings 欄位：

  • Issuer
  • Audience
  • SigningKey
  • AccessTokenMinutes
  • RefreshTokenDays
  • ClockSkewMinutes

Auth API

目前提供三個 API：

  • POST /api/Auth/login：使用帳號密碼登入，成功回傳 access token 與 refresh token。
  • POST /api/Auth/refresh：使用 refresh token 換發新 token。
  • GET /api/Auth/me：使用 Bearer access token 取得目前使用者 DTO。

API 授權規範

  • 各紀錄 CRUD API（Project/MyTask/Meeting/MediaTranscription/DocumentExtraction）與基礎資料 API（Category/Team）預設全部需要 Bearer token。
  • 紀錄類 API 另受「團隊資料權控」限制（見下節）；管理員不受限。
  • 登入與 refresh API 允許匿名。
  • API 未授權與禁止存取回應也會包成 ApiResult。

MCP Server 認證（1.0.5 起）

對外的 MCP 端點 /mcp 套具名授權 policy McpAccess，接受三種 scheme 任一通過：Bearer（JWT）、Cookie、McpApiKey。

  • JWT 方案：IJwtTokenService 簽發的 token 含 ClaimTypes.Sid（1.0.5 補上，修正非管理員原先只見公開內容的欠授權），RecordAccessScopeProvider 由 Sid 反查角色團隊。
  • MCP API Key 方案（1.0.9 起 DB 型）：client 帶專用標頭 X-API-Key；McpApiKeyAuthenticationHandler 經 McpAccessKeyService.FindEnabledMatchAsync（只載入啟用中金鑰、CryptographicOperations.FixedTimeEquals 常數時間比對）驗證後，發帶 ClaimTypes.Sid = McpAccessKey.UserId 的身分。金鑰存資料庫 McpAccessKey 表，由管理員於 /mcp-api-keys（adminOnly）網頁建立、對映使用者、即時啟用/停用（1.0.6 初版為 appsettings.json Mcp:ApiKeys 設定型，1.0.9 已移除）。
  • 權控一致：兩案皆經 McpIdentityResolver 填入 CurrentUserService，MCP 查詢沿用與 UI/API 完全相同的團隊資料權控。詳見 MCP Server 整合設計與使用指南。

頁面權限與選單對應

頁面層級授權以選單為基礎，三處須一致對應（以位置索引串接）：

  • 權限常數：KnowledgeExtraction.Share/Helpers/MagicObjectHelper.cs（角色_首頁、角色_專案協作…）。
  • 權限樹：RolePermissionService.GetRoleListPermissionAllName() 回傳二維清單，外層每組對應一個頂層選單。
  • 選單：KnowledgeExtraction.Web/Datas/Menu.json，頂層順序須與權限樹外層索引一致。

⚠️ 選單顯示名與權限名刻意分離（1.0.57 起）

Menu.json 的 name 是給使用者看的顯示名，可自由調整；權限名是 MagicObjectHelper.角色_xxx 的值，同時也是 RoleView.TabViewJson 內既存的字串。

權限常數的值永遠不可更動 —— 一旦更動，所有既有角色的已存權限字串會失配（RolePermissionService.SetPermissionInput 以 Ordinal 比對），非管理員角色瞬間掉權限，且沒有任何測試抓得到（測試皆透過常數引用，會跟著一起變綠）。

因此下表的「權限值」欄大多是舊選單名，這是正確的、不是待修的過期資料。兩者的對應關係集中維護於 MenuPermissionAlignmentTests.DisplayNameToPermissionName。

本群組現為 7 個頁面權限 ＋ 2 個動作權限，共 9 項（RolePermissionService 中另有群組標頭 角色_清洗與蒸餾 佔索引 0）。上表列出的順序就是 RolePermissionService 索引 3 群組與 Menu.json subMenu 的共同順序（1.0.106 依實際使用頻率重排：日常入口在前、品質與審核居中、瀏覽與圖譜在後）。兩處必須同步——SidebarMenuService.ApplyChildPermissionStructure 以陣列位置對應，只改一邊會讓選單項配到別人的權限名（靜默錯位，由 MenuPermissionAlignmentTests.EverySubMenuItem_PairsWith_ItsOwnPermissionName 把關）。

兩個動作權限必須留在群組末端——它們沒有對應選單頁，插到頁面型權限之間會占走選單子項的索引位。

Menu id 刻意非連號（41、45、42、44、46、47、48）且不重編號：id 在程式中完全沒有被使用（渲染 key 用陣列位置、選中狀態用 URL 前綴比對），重編號無益，反而會讓既有文件的 id 引用失效。

視覺分組欄是 Menu.json 的 group 欄位：相鄰兩項分組不同時，選單上會畫一條分隔線。它只影響外觀、不影響權限（不是陣列元素，故不佔位置索引）。分組邊界對「已過濾的可見清單」求值，因此某項因無權限被隱藏時，線仍落在正確的交界。

⚠️ 角色_知識圖譜審核 的權限值就是 知識圖譜審核，與選單顯示名完全相同。 這是本表少數兩者一致的一項（多數常數刻意保留 1.0.57 更名前的舊選單名），不是漏改，也不要「順手對齊」成別的字串——權限以名稱字串存於 RoleView.TabViewJson，改值等同清空所有既有角色的該權限，且沒有測試會攔到。

頁面內另有兩層不吃角色權限的細粒度判定（GraphReviewView.razor.cs）：核可／退回／編修三元組需管理員或 角色_蒸餾審核；「實體合併」分頁與「重建社群摘要」則寫死為僅管理員（CheckIsAdmin()），在角色管理頁勾 知識圖譜審核 也開不出來。

團隊資料權控（紀錄可見性）

除頁面授權外，五種紀錄（專案管理、工作任務、會議紀錄、影音轉逐字稿、文件轉文字）另以團隊控管「可見哪些資料」：

  • 角色可設定預設團隊（RoleView.DefaultTeamsJson），於角色管理頁以多選維護；登入時載入 CurrentUser.TeamList。
  • 可見性規則（非管理員）：紀錄的 Teams 為空（視為公開）或 與使用者角色團隊有交集，才可見。
  • 管理員（MyUser.IsAdmin）不受此限制，可見所有紀錄。
  • 規則為伺服器端強制，套用於：五種紀錄 Service 的清單／單筆查詢與下載/預覽；Project/MyTask/Meeting Repository 的清單／單筆／編輯／刪除（其 Web API Controller 走 Repository）；影音轉逐字稿／文件轉文字 Controller 走已權控的 Service。非授權者即使以 id 直接存取，也會被視為「找不到」。
  • 知識來源（KnowledgeSource）亦套用同規則：列表/檢視依其 Teams 標籤過濾；加入成員時並會檢查被參照素材（轉錄/萃取/圖片）是否為當前使用者可存取的團隊，避免以聚合繞過權控。
  • 團隊名稱採精確比對（不會「團隊」誤中「團隊2」）。

實作元件：

  • IRecordAccessScopeProvider / RecordAccessScopeProvider（Blazor 取自 CurrentUserService、Web API/下載取自 HttpContext claims 查角色團隊）→ 回傳 (IsAdmin, AllowedTeams)。
  • TagStringHelper.BuildTeamAccessPredicate（查詢述詞：公開 OR 團隊交集）、IsTeamAccessible（單筆判斷）。

詳細需求與測試矩陣見 紀錄分類、團隊標籤與團隊權限控管 PRD。

知識圖譜的權控延伸（Graph RAG，1.0.83～1.0.96）

圖譜把「關係」也當成受保護的知識。權控不是只在最後過濾一次，而是四層各自套用 BuildTeamAccessPredicate／IsTeamAccessible：

層說明
邊（GraphEdge、三元組邊）遍歷時每一條邊都檢查——而且每一跳都重新檢查。不能借道無權限的中間節點繞過去
節點（GraphNode）他人團隊的實體節點不納入；他隊節點的錨定 Wiki 頁不進跨來源實體合併
三元組（GraphTriple）只有 Status=已完成（已核可）且有權存取者參與檢索加分
鄰居內容片段擴展到的 Wiki 頁，其 chunk 仍須通過原本的內容層權控

三個容易誤解的地方：

  1. 他隊的三元組，即使兩端頁面都是公開的，也不會替你加分。 因為「這兩個東西之間有關係」本身就是一項知識，歸屬於抽出它的那個來源所在團隊。
  2. 社群摘要（GraphCommunity）的 ACL 比一般紀錄更嚴，採子集判定：社群的 Teams（成員來源的團隊聯集）必須是使用者團隊的子集，或該社群完全無團隊（公開），才可取用。理由是一份社群摘要混合了多筆來源的知識，只要其中任一筆使用者無權查看，整份摘要就不能給。這是本系統唯一採子集判定的地方，其餘紀錄都是交集判定。
  3. GraphEntityAlias 與 GraphJobState 沒有 Teams 欄位，屬全域管理員治理（別名維護與社群重建都寫死為僅管理員）。別名只改變「哪些名字算同一個實體」，不放寬任何人的可見範圍。

已知限制：非管理員的「團隊」下拉目前仍列出全部啟用團隊（伺服器端可見性已嚴格限制；指定到自身未授權團隊只會讓自己看不到該筆，非資料外洩），UI 下拉限縮列為後續強化。

Refresh Token 限制

目前 refresh token 不落庫，因此有以下限制：

  • 無法可靠撤銷單一 refresh token。
  • 使用者登出後，已發出的 refresh token 仍可能在有效期內換發 token。
  • 若要強制全部失效，只能輪替 SigningKey 或縮短有效期。
  • 未來若需要可撤銷、裝置管理或風險控管，應改成 refresh token 落庫並記錄 jti、使用者、過期時間、撤銷時間與裝置資訊。

安全待辦

  • ☐正式環境必須改用安全 secret 來源提供 JwtSettings:SigningKey（環境變數 JwtSettings__SigningKey、appsettings.Production.json 或部署平台 secret）。⚠️ 沒有任何程式會強制——原本的啟動守門因兩度擋住正式部署，已於 1.0.68 移除。沿用倉庫內的開發預設金鑰不會被擋，任何看得到原始碼的人都能偽造 token。1.0.72 起恢復了軟偵測：Production 啟動時記一筆 Error 日誌、/system-health「身分驗證」項轉黃燈（以 DevelopmentOnly- 前綴判定，故「在預設值後面接東西」也擋得住），但仍不會中止啟動，且只有在有人去看日誌或健康檢查頁時才會被發現——部署檢查清單的人工核對仍不可省。
  • ☐BootstrapSettings:SupportPassword 不會擋啟動：該守門原本比對字面值 support（而實際預設值是 1qaz@WSX，故從未觸發），後來連整支驗證器都在 1.0.68 移除。1.0.72 起併入上述軟偵測（已知不安全值集合 support／1qaz@WSX），會記 Error 日誌並讓「身分驗證」項轉黃，但仍不中止啟動。另注意 support 密碼每次啟動都會被設定值覆寫，在畫面上改密碼會在下次重啟被蓋回。
  • ☐圖譜全域問答 Web API（POST /api/v1/KnowledgeGraph/global-ask）缺 HTTP 層的 leak=0 端到端測試。服務層（GraphCommunityService.GetAccessibleSummariesAsync）已有權控測試覆蓋，但沒有一條測試是從 HTTP 進去、驗證非管理員拿不到他隊社群摘要的。上線前請人工以非管理員帳號驗一次。該端點也沒有 API 專用節流，成本只靠 Retrieval.GraphGlobalCommunityCap 控管。
  • ☐GraphTripleService.CancelExtractionAsync（取消三元組抽取）沒有另加團隊權控，沿用「唯一入口 /pipeline-jobs 為 adminOnly 頁面」的既有慣例把關。目前實際等效（只有管理員進得去），但若日後把取消動作開放到非管理員可及的頁面，這裡必須先補權控。
  • ☐評估正式環境是否停用或限制 Swagger UI；Swagger:EnabledInProduction 出貨範本為 false。⚠️ 原本「Production 必須明確設定、留空即中止啟動」的守門已隨 1.0.68 的驗證器移除一併失效——現在留空不會被擋，只會沿用基底的 false（安全側）。請以人工確認生效值。
  • ☑建立預設帳號強制改密碼基礎流程（AuthenticationStateHelper 偵測到密碼等於 MagicObjectHelper.NeedChangePassword 時導向 /ChangePassword）。
  • ☐若需要可靠登出與撤銷能力，將 refresh token 改為落庫版本。
