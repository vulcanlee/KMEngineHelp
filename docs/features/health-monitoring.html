功能機制

系統健康監控

文件目的

說明本專案的健康檢查端點與人工巡檢頁面，讓維運人員可以快速判斷網站、API、資料庫、日誌、身分驗證、檔案系統、主機資源與安全設定是否正常。

1. 部署探針

系統保留 ASP.NET Core Health Checks 端點：

路徑用途說明
/health/liveLiveness檢查應用程式處理程序是否仍存活。
/health/readyReadiness檢查資料庫連線是否可用，供部署平台判斷是否可接流量。

這兩個端點只提供簡短狀態，適合部署平台、反向代理或外部監控系統輪詢，不提供詳細診斷資料。

2. 人工巡檢頁

管理員可直接開啟：

/system-health

此頁位於左側選單「系統管理 → 系統監控 → 系統健康監控」（adminOnly），必須先以 Cookie 登入，且目前使用者必須是管理員（IsAdmin=true）才可查看。

頁面內容包含：

  • 整體健康百分比。
  • 整體紅 / 黃 / 綠燈號。
  • 每個檢查項目的紅 / 黃 / 綠燈號、權重、狀態、證據與失敗訊息。
  • 頁尾顯示目前 NLog 今日日誌檔案的最後 100 筆原始紀錄。

3. 燈號與分數

整體健康分數採加權計算：

狀態單項得分燈號
Healthy取得完整權重綠燈
Degraded取得一半權重黃燈
Unhealthy不得分紅燈

整體燈號門檻：

分數燈號說明
>= 90綠燈系統健康。
70-89黃燈系統可運作，但有項目需要關注。
< 70紅燈系統健康程度不足，應立即檢查失敗項目與日誌。

4. 檢查項目

基礎系統（Category: Application / API / Database / Logging / Authentication / FileSystem / Host / Security）

項目權重主要證據
網站 / 應用程式10環境、版本、啟動時間、運作時間。
API10Controller action 數量、Swagger 啟用狀態。
資料庫25Provider、連線狀態、待套用 migration 數量。
日誌15NLog 目錄、今日 log 檔、最後 100 筆讀取狀態。
身分驗證15Cookie scheme、JWT bearer、Issuer/Audience 是否設定、SigningKey 長度（≥32）。1.0.72 起另檢查金鑰／密碼內容：Production 下若 JwtSettings:SigningKey 仍以 DevelopmentOnly- 開頭，或 BootstrapSettings:SupportPassword 仍是 support／1qaz@WSX，本項轉警示（黃）並在證據列出原因。刻意用黃而非紅——接線本身沒壞，這是設定衛生問題（1.0.69 之所以整條移除，就是因為紅燈被誤判為身分驗證故障）。非 Production 不生效。
檔案系統10Database、Download、Upload、ProjectFile、TaskFile、MeetingFile 目錄存在與可寫入。
主機資源5Process working set、目前磁碟可用空間。
安全設定10Swagger in Production、CORS origins、Security.ReturnExceptionDetails。

語音轉文字工具（Category: TranscriptionTools）

項目權重主要證據設定來源
ffmpeg8工具路徑與版本字串。OpenAISettings:FfmpegPath
yt-dlp8工具路徑、版本字串、Cookies 設定狀態。OpenAISettings:YtDlpPath
markitdown6工具路徑與版本（若 --version 不支援則以 --help 確認存在）。MarkItDownSettings:MarkItDownPath
Node.js5工具路徑與版本（要求 major ≥ 20，建議最新 LTS）。OpenAISettings:NodePath
抖音助手腳本4腳本路徑與檔案存在狀態（選用功能，未設定為 Degraded）。OpenAISettings:DouyinHelperScript

語音轉文字設定（Category: TranscriptionSettings）

項目權重主要證據說明
OpenAI API 設定8ApiKey、BaseUrl、Model 是否設定。ApiKey 未設定一律為 Unhealthy（必要設定，缺它整個功能無法運作）；其餘問題缺 1 項為 Degraded、缺 2 項以上為 Unhealthy。證據僅顯示 ApiKey「已設定／未設定」，不顯示金鑰內容。OpenAISettings:{ApiKey,BaseUrl,Model}
轉錄儲存目錄6MediaUploadPath 與 TranscriptionFilePath 存在且可寫入。SystemSettings:ExternalFileSystem

向量索引（Category: EmbeddingIndex）

項目權重主要證據
向量索引涵蓋率15已清洗來源是否都已建立向量索引；嵌入未設定或索引為空時示警（直接影響AI 知識問答能否檢索）。

基礎設施與整合（1.0.11 新增 5 項）

項目權重主要證據紅/黃/綠判定
MCP Server8/mcp 端點是否註冊、McpAccess policy 與 McpApiKey scheme 是否就緒、啟用中金鑰數。綠＝基礎設施就緒且 ≥1 把啟用金鑰；黃＝0 把啟用金鑰（外部無狀態 Agent 無法用 X-API-Key，JWT/Cookie 仍可）；紅＝policy／scheme／端點缺失。
分散式快取8Provider（Memory/Redis）；Redis 時以 IDistributedCache 寫入/回讀一筆 ping 實測連線。Memory→綠；Redis 連線成功→綠、失敗→紅。
AI 生成/嵌入 Provider10依 Cloud/Local 分流的生成與嵌入端點設定是否齊備（模型、維度）。兩者皆就緒→綠；任一未就緒（Cloud 缺 ApiKey／Local 缺 BaseUrl+model）或 provider 值非法→紅。
RAG 檢索設定6向量/關鍵字權重、Reject/LowConfidence 門檻、TopK/CandidateTopK。全合理→綠；權重和非 1→黃；門檻越界或大小顛倒等→紅。（檢查 appsettings 值，DB override 可能覆蓋生效值）
背景管線8七條匯入/處理背景服務（預期清單由 PipelineNames 常數反射推導，慣例 {管線名}BackgroundService，新增管線自動納入），加上 1.0.72 納入的 2 支寫入服務（PipelineProgressWriter／TokenUsageWriter；它們沒有 PipelineNames 常數故無法推導，改為硬編維護）。全部就緒→綠；缺任一→紅。（僅檢查註冊/實例化，未偵測卡死或佇列積壓）<br>⚠️ 為何要檢查寫入服務：TokenUsageWriter 沒起來＝Token 用量默默不再記錄（成本治理與 5 份統計報表的資料基礎，且不會有錯誤訊息）；PipelineProgressWriter 沒起來＝進度不更新、完成 toast 消失。1.0.66–1.0.71 期間這兩支完全不在檢查範圍內。

註：PipelineProgressWriterBackgroundService 與 TokenUsageWriterBackgroundService 不是業務管線（無對應 PipelineNames 常數），刻意不在本項範圍；這兩支目前尚無健康檢查涵蓋，記於 優化建議清單。

分數計算採動態加權（earned / totalWeight × 100），新增項目不影響原有項目的相對比例。目前共 24 項檢查（基礎系統 9＋轉錄工具 5＋轉錄設定 2＋向量索引 1＋基礎設施與整合 7；1.0.13 新增「大語言模型可用性」「嵌入端點可用性」兩項實呼叫檢查與資訊型「資料庫大小與資料量」）。

5. 日誌顯示注意事項

/system-health 頁尾會顯示最後 100 筆原始日誌紀錄，不會額外遮罩內容。此設計是為了讓管理員快速追查失敗項目，但也代表頁面可能顯示路徑、帳號或例外訊息。

部署時請確認：

  • 只有可信任管理員可以登入此頁。
  • NLog 不應寫入密碼、token、完整連線字串等 secret。
  • 正式環境的日誌保存期限與存取權限符合組織政策。
