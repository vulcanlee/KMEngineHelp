一、背景與目的

本系統以「團隊管理」集中維護權控標籤，讓紀錄指定可存取團隊；團隊空白代表公開，非管理員只可讀取公開或與角色團隊有交集的資料。

本功能為一個標準 CRUD 頁面，需具備側邊選單項目、Menu.json 設定與角色權限控制。

設計範本

本功能與系統中剛完成的「知識庫分類」(Category) 功能高度同構，並以「專案管理」(ProjectPage / ProjectViewView) 為底層分層範本。實作時 以 Category 功能為主要範本，沿用其分層架構（Entity → Repository → Service → Controller → DTO → AdapterModel → Blazor View），差異僅在於團隊多一個「團隊代號」欄位。

可重用的現成模式：

  • 名稱唯一性檢查：CategoryRepository.ExistsByNameAsync 與 CategoryService.ValidateNameUniqueAsync（皆採 Trim + 忽略大小寫，編輯時排除自身）。
  • 分頁／搜尋／排序：CategoryRepository.GetPagedAsync、CategoryService.GetAsync，預設 OrderByDescending(UpdatedAt)。
  • Blazor UI：CategoryViewView 工具列 + Ant Design Table（遠端資料來源、分頁）+ 新增／編輯 Modal（EditForm + DataAnnotationsValidator）+ 啟用狀態欄位。
  • 選單與權限：以位置索引對應的 SidebarMenuService.ApplyPermissionStructure、MagicObjectHelper 權限常數、RolePermissionService.GetRoleListPermissionAllName()。

三、功能概述

新增「團隊管理」管理頁面，提供團隊項目的新增、查詢、編輯、刪除（CRUD）。每筆團隊包含名稱、團隊代號、描述與啟用狀態。團隊名稱在系統內為唯一值（忽略大小寫並去除頭尾空白後比對）；團隊代號為選填，但若有填寫，亦須為唯一值（相同比對規則）。列表預設依更新時間由新到舊呈現。

0.3.34 現況已把團隊標籤與權控套用至紀錄、下載、知識來源、Wiki、索引及問答；本 PRD 同時規範基礎資料與跨功能引用邊界。

四、使用者流程

  1. 進入「團隊管理」頁面（路由 /teams）；權限不足者不顯示選單、不可進入頁面。
  2. 列表預設依「更新時間」由新到舊排序，最近更新者在最上方；支援關鍵字搜尋（名稱／代號／描述）與分頁。
  3. 點「新增」，於 Modal 中輸入名稱（必填）、團隊代號（選填）、描述（選填），並設定是否啟用（預設啟用）。
  4. 送出時驗證唯一性（忽略大小寫 + 去頭尾空白）：
  5. 名稱重複：拒絕儲存，顯示「團隊名稱已存在」之類的友善訊息（API 回 409 Conflict）。
  6. 團隊代號有填且重複：拒絕儲存，顯示「團隊代號已存在」之類的友善訊息（API 回 409 Conflict）。
  7. 通過：建立紀錄，設定建立時間與更新時間，回到列表。
  8. 點「編輯」載入單筆資料，可修改名稱、代號、描述、啟用狀態；名稱與代號唯一性同樣須通過（比對時排除自身）。
  9. 點「刪除」出現確認對話框，確認後實體刪除該團隊。
  10. 任何新增或編輯成功皆更新 UpdatedAt，故該紀錄會回到列表最前方。

  • DbSet Team 註冊於 BackendDBContext，並新增對應 EF Core Migration（SqlServer 與 Sqlite 雙 provider，比照 AddCategory）。
  • 唯一性以應用層檢查為主：名稱 ExistsByNameAsync、代號 ExistsByCodeAsync；比對前先 Trim() 並以忽略大小寫方式比較。
  • 團隊代號為選填：當輸入為空白時不進行唯一性檢查（允許多筆團隊代號為空）。

七、架構與元件（比照 Category）

各層需新增的元件如下（命名與分層比照既有 Category*）：

  • Entity Team（KnowledgeExtraction.AccessDatas/Models/Team.cs）
  • Repository TeamRepository（KnowledgeExtraction.Business/Repositories/TeamRepository.cs）
  • GetPagedAsync(TeamSearchRequestDto request)：分頁／搜尋／排序，預設 OrderByDescending(t => t.UpdatedAt)；支援以名稱／代號／描述關鍵字搜尋。
  • GetByIdAsync(int id)、AddAsync、UpdateAsync（保留原 CreatedAt、更新 UpdatedAt）、DeleteAsync(int id)。
  • ExistsByNameAsync(string name, int? excludeId = null)：Trim + 忽略大小寫比對。
  • ExistsByCodeAsync(string code, int? excludeId = null)：Trim + 忽略大小寫比對；呼叫端於 code 非空白時才檢查。
  • Service TeamService（KnowledgeExtraction.Business/Services/DataAccess/TeamService.cs）：包裝 Repository，提供查詢／新增／編輯／刪除與前置檢查；BeforeAddCheckAsync／BeforeUpdateCheckAsync 驗證名稱唯一性與（代號非空白時的）代號唯一性。
  • DTO（KnowledgeExtraction.Dtos）：TeamDto、TeamCreateUpdateDto（名稱必填驗證、代號選填）、TeamSearchRequestDto（繼承 SearchRequestBaseDto，含關鍵字、分頁、排序、IsEnabled? 過濾）。
  • AdapterModel TeamAdapterModel（KnowledgeExtraction.Models/AdapterModel/TeamAdapterModel.cs）：前端綁定用，含 DataAnnotations 驗證。
  • Controller TeamController（KnowledgeExtraction.Web/Controllers/TeamController.cs）：比照 CategoryController。
  • AutoMapper：於 AutoMapping.cs 新增 Team ↔ TeamAdapterModel / TeamDto / TeamCreateUpdateDto 映射。
  • DI 註冊（ServiceCollectionExtensions.cs）：services.AddScoped<TeamService>();、services.AddScoped<TeamRepository>();

九、API 端點

新增 TeamController（比照 CategoryController，api/[controller] + api/v1/[controller]，沿用既有授權機制）：

  • POST {base}/team/search：接收 TeamSearchRequestDto，回傳分頁結果（預設依 UpdatedAt 降冪）。
  • GET {base}/team/{id}：取得單筆。
  • POST {base}/team：新增；名稱重複或代號（非空白）重複回 409 Conflict。
  • PUT {base}/team/{id}：編輯；驗證路由 id 與 payload id 一致；名稱／代號重複（排除自身）回 409 Conflict。
  • DELETE {base}/team/{id}：刪除。

十、選單與權限（需異動處）

本節為首次實作當時的選單結構，保留原貌。 現況為「基礎資料設定」(id 6)，子項共 5 項（知識庫分類 61、團隊管理 62、專案分類 63、AI 提示詞 64、清洗規則設定 65），權限群組為 6 個常數，登出為 id 8；一律以 Menu.json 與 RolePermissionService 為準。權限常數的「值」刻意保留舊選單名（角色_團隊清單 = "團隊清單"），不得變更——權限以名稱字串存於 RoleView.TabViewJson，改值等同清空所有既有角色的權限。

  1. KnowledgeExtraction.Share/Helpers/MagicObjectHelper.cs：新增權限常數 角色_團隊清單 = "團隊清單"。
  2. KnowledgeExtraction.Business/Services/Other/RolePermissionService.cs：

於 GetRoleListPermissionAllName() 既有「資料定義」群組 [角色_資料定義, 角色_分類清單] 末端加入 角色_團隊清單，成為 [角色_資料定義, 角色_分類清單, 角色_團隊清單]。

  1. KnowledgeExtraction.Web/Datas/Menu.json：於既有「資料定義」(id 4) 的 subMenu，在「分類清單」(id 41) 之後新增：
   {
     "id": 42,
     "name": "團隊清單",
     "icon": "groups",
     "url": "/teams"
   }
  1. 建立頁面與檢視元件（見第八節），於 View 加入權限檢查。

權限機制說明：本系統授權以選單為基礎，並以位置索引對應（SidebarMenuService.ApplyPermissionStructure）。 「資料定義」子項順序須與 RolePermissionService 中該群組（跳過第一個群組名後）的順序一致：分類清單、團隊清單。 角色實際勾選的權限存於資料庫 RoleView.TabViewJson，既有角色若要存取新頁面，須由角色管理頁重新勾選。

十一、編碼需求

  • 所有新增的程式碼檔以 UTF-8（繁體中文） 撰寫，不得有亂碼。
  • 本 PRD 與所有 docs/*.md 文件須為 UTF-8（含 BOM），以通過 scripts/Test-DocsEncoding.ps1 檢查。
  • Menu.json 等含中文之設定檔維持 UTF-8 編碼，確保選單名稱顯示正確。

十二、驗收條件

  1. 選單出現「資料定義 > 團隊清單」，且位於「分類清單」之後；無權限角色看不到、無法進入頁面。
  2. 列表預設依「更新時間」由新到舊排序，最近新增／編輯的團隊排在最前面。
  3. 新增團隊：名稱必填；名稱與既有團隊重複（忽略大小寫、去頭尾空白後）時被拒絕並顯示友善訊息。
  4. 團隊代號為選填；若有填且與既有團隊代號重複（同比對規則）時被拒絕；多筆代號為空白應可並存。
  5. 編輯團隊：可修改名稱、代號、描述、啟用狀態；名稱與代號唯一性比對排除自身；儲存後該筆回到列表最前方。
  6. 刪除團隊：確認後實體刪除。
  7. 啟用狀態可於新增／編輯切換，列表正確顯示啟用／停用。
  8. appsettings.json 版本號於實作建置時 +1（0.2.34 → 0.2.35），相關文件同步更新。
