對應代辦清單：專案協作模組強化開發代辦清單 相關 PRD：專案管理、工作任務、會議管理、知識庫分類、音訊影片轉錄服務、紀錄分類與團隊權控

一、背景與目的

1.1 企業真實需要

企業內「有一件事要完成」的作業型態，不只存在於公司層級，而是存在於每個部門，甚至臨時組成的虛擬團隊。這件事在系統中的自然對應是：

  • 專案管理＝一個要達成的需求或目標
  • 工作任務＝專案底下要做的事，且工作本身還能再拆成子工作任務
  • 會議管理＝推進這件事的過程中，人與人溝通所產生的決議與待辦

要回答「這個專案做完了沒／做到哪了」，答案應該來自底下所有工作與子工作的完成比例統計，而不是靠人手動維護一個數字。

1.2 三個待解問題

問題一：選單語意混雜。 現況「專案管理」子選單同時塞了六個功能——專案管理／工作任務／會議管理（人在協作、追進度）與影音轉逐字稿／文件轉文字／圖片解讀（把素材餵進知識庫）。兩類職能完全不同卻同居一組，使用者難以建立心智模型。

問題二：知識庫分類語意重疊。 專案、工作、會議的「分類」欄位目前共用 Category（知識庫分類），但那份清單的定位是知識庫主題標籤——知識來源、Wiki、問答篩選都吃它。兩種語意混在同一份清單，導致下拉選單越長越雜，且任一邊調整都會污染另一邊。

問題三：會議知識流失。 會議是企業內最高頻、也最容易流失的知識來源。現況「會議管理」是純手動 CRUD，而系統其實已具備完整的影音轉逐字稿管線（MediaTranscription）與 LLM 依提示詞產生內容能力（LlmGenerationService），兩者卻沒有接起來。使用者必須自己在兩個頁面之間搬運內容。

1.3 目標

  1. 讓「協作」與「匯入」在選單上分家，各自語意清楚。
  2. 給專案／工作／會議一份專屬的分類主檔，與知識庫分類脫鉤。
  3. 讓專案進度可依工作與子工作的完成比例自動彙總。
  4. 把「會議錄音／錄影 → 逐字稿 → AI 會議紀錄 → 待辦轉工作任務」串成一條可自動化的線。

1.4 非範圍

  • 甘特圖、任務相依性、看板、衝刺規劃、通知提醒
  • 多層巢狀子工作（維持既有的父→子一層）
  • 行事曆同步、會議排程
  • 線上會議連結（Teams／Zoom）自動抓取錄影（見 §6.2 決策說明）
  • 專案／工作／會議紀錄自動進入知識庫 RAG 索引（如需，仍循既有「知識來源聚合 → 清洗」流程）

二、需求決策摘要

項目決策理由
兩個新子選單名稱專案協作（專案管理／工作任務／會議管理）、資料匯入（影音轉逐字稿／文件轉文字／圖片解讀）與既有「知識庫」形成「匯入 → 清洗 → 蒸餾」的流水線語意
新知識庫分類名稱專案分類（Entity WorkCategory，路由 /work-categories）與知識庫的「知識庫分類」語意分離且不易混淆
新分類掛載位置「基礎資料設定」主選單下與知識庫分類／團隊管理／AI 提示詞同屬基礎資料
既有分類資料啟動時自動搬移：掃描三表既有 Categories 值，缺的自動建入 WorkCategory零資料遺失、使用者無感；既有紀錄字串完全不動
會議自動化入口會議管理頁一鍵走完使用者只在一個頁面操作；轉錄頁仍看得到該筆紀錄
錄音來源僅上傳檔案，上限 1GB → 2GB會議錄影實務上都是 Teams／Meet 匯出的本機檔；Teams／Zoom 連結需登入，yt-dlp 抓不到
AI 待辦 → 工作任務人工確認後建立LLM 會把閒聊當待辦；自動寫入會污染工作清單且難清理
會議新增欄位會議形式／地點／主持人／紀錄人／決議事項／AI 產生屬性欄位不加「會議狀態」——本次未確認有實務需求
AI 產出寫回檔案為主（Markdown 落地，DB 只存相對路徑）＋摘要／決議／出席者寫回欄位比照清洗結果、聊天紀錄的既有慣例：長內容不入 DB
欄位覆寫行為覆寫，但產生前跳確認對話窗明示行為可預測，使用者掌握主導權
進度統計即時計算不存檔（子工作→父工作→專案逐層平均）不新增欄位、不需 migration、永遠不會不同步
交付方式四階段，每階可建置，每階段版本 +1符合既有開發流程；風險最高的選單改動前置驗證

三、階段一：選單拆分（專案協作／資料匯入）

預計版本：1.0.16 → 1.0.17

3.1 選單結構

「專案管理」（現 Menu.json 索引 1）拆為兩個頂層群組：

新群組子項路由
專案協作（圖示 assignment）專案管理/projects
工作任務/Task
會議管理/meeting
資料匯入（圖示 cloud_upload）影音轉逐字稿/media-transcription
文件轉文字/document-extraction
圖片解讀/image-recognition

拆分後頂層順序為：首頁、專案協作、資料匯入、知識庫、系統管理、基礎資料設定、統計報表、登出（共 8 組，原 7 組）。

3.2 權限與相容性（本階段最關鍵）

側邊選單與權限樹以位置索引對應（SidebarMenuService.ApplyPermissionStructure），名稱從不參與比對。索引漂移是靜默失效——權限名會退化成選單項名稱，導致選單對非管理員直接消失。因此 Menu.json、RolePermissionService、MagicObjectHelper 三處必須同步。

相容性結論：AuthenticationStateHelper.CheckAccessPage(name) 只是對角色的 RoleView.TabViewJson 做平面字串 Contains。因此：

  • 只要六個葉節點權限字串（專案項目／工作項目／會議項目／音訊轉錄／文件萃取／圖片清單）逐字不變，既有角色不會失去任何頁面權限。
  • 選單也不會消失：FilterMenuItems 的規則是「父節點自身無權限但有 ≥1 個可見子項時仍保留」，故舊角色即使沒有新的群組權限字串，父節點照樣顯示。
  • 殘留的 "專案管理功能" 字串會被 SetPermissionInput 靜默忽略，無需資料遷移、無需改 SQL。
  • 預設角色 每次啟動由 Program.cs 重寫為全部權限，會自動修復。

唯一殘留：自訂角色在 /roleviews 會看到兩個未勾選的新群組標題。發行說明須帶一句：「既有角色的頁面權限不受影響；如需群組層級權限請至角色管理重新勾選。」

新增權限常數 角色_專案協作 = "專案協作功能"、角色_資料匯入 = "資料匯入功能"；刪除 角色_專案管理（由編譯器標出殘留引用）。

3.3 新增不變量守護測試

目前沒有任何測試守護 Menu.json ↔ RolePermissionService 的位置索引不變量，而這正是最容易壞的地方。新增 MenuPermissionAlignmentTests：

  1. Menu.json 頂層數 == GetRoleListPermissionAllName().Count
  2. 每組 subMenu.Count <= group.Count - 1（容許動作型權限尾隨）
  3. 走一次位置索引對應，斷言沒有任何葉節點退化成 item.Name

3.4 驗收條件

  1. 管理員登入，側邊選單為 首頁 / 專案協作(3) / 資料匯入(3) / 知識庫(7) / 系統管理(10) / 基礎資料設定(4) / 統計報表(5) / 登出，每個連結都導到正確頁面。
  2. 拿一個改動前建立、且不重新存檔的非管理員角色登入，六個頁面全部仍看得到、開得起來。
  3. 建一個只勾「影音轉逐字稿」的角色：資料匯入父節點顯示，專案協作不顯示。
  4. 「統計報表」與「登出」仍正常顯示（尾端對齊未被打壞）。
  5. dotnet build／dotnet test 綠燈。

四、階段二：專案分類（WorkCategory）

預計版本：1.0.17 → 1.0.18

4.1 資料模型

新增實體 WorkCategory（欄位與既有 Category 完全一致）：

欄位型別說明
Idint主鍵，自動遞增
Namestring分類名稱（必填、唯一）
Descriptionstring?描述（選填）
IsEnabledbool是否啟用（預設 true），停用者不供新資料選用
CreatedAtDateTime建立時間
UpdatedAtDateTime最後更新時間

名稱唯一性以應用層檢查：Trim() 後忽略大小寫比對，編輯時排除自身，重複回 409 Conflict。需產雙 provider migration（AddWorkCategory）。

4.2 影響範圍：只換下拉來源，不動儲存

專案、工作、會議的 Categories 欄位儲存格式完全不變——仍是 TagStringHelper 的 \n 包夾字串（如 "\nA\nB\n"），AutoMapper 的 ForMember 轉換不變，BuildContainsAnyPredicate 的精確成員比對不變。本階段只改「哪一張表填充下拉選單」。

全站共 12 處以 CategoryService.GetAllEnabledNamesAsync() 填充分類下拉，只換 5 處：

  • ProjectViewView（工具列篩選 ＋ 內嵌編輯表單）
  • MyTasViewView（工具列篩選）
  • MyTasEditModal（分類標籤）
  • MeetingViewView（工具列篩選）
  • MeetingEditModal（分類標籤）

ProjectRelatedRecordsModal（專案內的「工作與會議」對話窗）不需要改 — 它沒有注入 CategoryService，而是掛載 MyTasEditModal / MeetingEditModal，已被上述兩處涵蓋。

其餘 7 處維持吃「知識庫分類」：知識來源、Wiki 頁、知識百科、影音轉逐字稿、文件轉文字、圖片解讀、內容清點報表。

4.3 既有資料自動搬移

新增 WorkCategoryBootstrapSeeder，掛在既有的啟動 migration／seeding 區塊內：

掃 Project.Categories + MyTask.Categories + Meeting.Categories（AsNoTracking + Distinct）
→ TagStringHelper.ToList 攤平 → Trim → 濾掉空白 → Distinct（忽略大小寫）
→ 與 WorkCategory 既有名稱比對（忽略大小寫），缺的 AddRange（IsEnabled = true）
→ 記錄 ScannedCount / InsertedCount
→ try/catch + LogError，失敗不中斷啟動

設計取捨：每次啟動都執行（冪等），不使用一次性旗標。三個單欄 SELECT DISTINCT 成本可忽略，且能吸收「直接改 DB」或「還原備份」帶進來的新值。忽略大小寫的去重與服務層唯一性檢查一致，故 seeder 絕不會塞進 UI 會判為重複的列。

4.4 已知技術債（本次不處理）

MyTask.Category（單值、Required、自由輸入文字）是早期欄位，與新的多值 Categories 並存，目前供關鍵字搜尋、排序、以及對外 API 的精確過濾使用。

本次完全不動它。 它是非空欄位且有對外 API 過濾契約，改動＝migration ＋ API 破壞性變更 ＋ 回填每一列，且用途（單值標籤供排序過濾）與多值標籤本就不同。若要退場應另開 PRD。

4.5 驗收條件

  1. /work-categories 完整 CRUD；重複名稱（含 abc vs ABC ）被擋、API 回 409；可停用。
  2. 拿一份有真實資料的資料庫副本啟動：日誌出現回填筆數，/work-categories 列出既有分類值。
  3. 再重啟一次：新增筆數為 0（冪等）。
  4. /projects、/Task、/meeting 及專案內「工作與會議」對話窗的分類下拉顯示專案分類，且停用項不出現。
  5. 存一筆兩個分類的專案 → 資料庫值仍為 \nA\nB\n；用其中一個篩選，精確成員比對正確（「團隊」不誤中「團隊2」）。
  6. 知識來源、知識百科、三條匯入、內容清點報表的分類下拉仍讀舊的知識庫分類。

五、階段三：會議欄位擴充與進度統計

預計版本：1.0.18 → 1.0.19

5.1 會議新增欄位

Meeting 現有欄位為 Title／Description／Summary／Participants／StartDate／EndDate／Categories／Teams／ProjectId／Files。新增：

欄位型別用途
MeetingModestring?會議形式：實體／線上／混合
Locationstring?地點，或線上會議連結
Hoststring?主持人
Recorderstring?紀錄人
Decisionsstring?決議事項
SourceTranscriptionIdint?來源轉錄紀錄（FK → MediaTranscription，Restrict）
GeneratedContentRelativePathstring?AI 會議紀錄 Markdown 相對路徑
GeneratedAtDateTime?AI 產生時間
MinutesStatusstring?未產生／轉錄中／轉錄完成／排隊中／產生中／已產生／失敗／已取消（後兩者 1.0.78 新增）
PendingActionItemsJsonstring?AI 待辦草稿（JSON 陣列，階段四使用）

全部可空，既有資料不受影響。狀態常數放 MeetingAdapterModel（比照既有慣例）。需產雙 provider migration（AddMeetingFields）。

5.2 進度統計（純計算，零 migration）

  • 工作進度：有子工作 → 子工作 CompletionPercentage 平均；無子工作 → 自身值。
  • 專案進度：該專案下頂層工作（ParentTaskId == null）的工作進度平均；無工作 → 專案自身 CompletionPercentage。
  • 效能要求：清單頁比照既有 ChildCount 的單次 group-by 查詢做法，不可 N+1。
  • UI：專案清單與工作清單各加一欄進度條，tooltip 標示「依子項自動彙總」或「手動值」。

現有 CompletionPercentage 欄位保留為手動值，在無子項時作為進度來源。此設計不新增欄位、不需 migration，且永遠不會出現統計值與實際子項不同步的情況。

5.3 驗收條件

  1. 會議表單可填新欄位、存取正確；既有會議開啟編輯不報錯。
  2. 專案有 2 個工作（30%／70%）→ 專案進度顯示 50%；工作有 2 個子工作 → 父工作顯示子工作平均。
  3. 無工作的專案顯示自身手動值。
  4. 清單頁 SQL 查詢數不隨列數增長。
  5. 雙 migration 皆已產生，SQLite / SQL Server 皆可升級，且沒有誤產 MyTas rename。

六、階段四：會議 AI 自動化（核心）

預計版本：1.0.19 → 1.0.20

6.1 端到端流程

會議記錄頁「上傳會議錄音／錄影」
  → 建立 MediaTranscription（繼承會議的 Categories/Teams）
    寫回 Meeting.SourceTranscriptionId；MinutesStatus = 轉錄中
  → 既有轉錄管線：TranscriptionQueue → BackgroundService → Processor
    （OpenAI 語音轉文字，逐字稿落地為 .txt）
  → 轉錄成功後的「加值步驟」：若有會議掛此轉錄 → 入列會議紀錄產生佇列
  → MeetingMinutesQueue → BackgroundService → Processor
    （LlmPromptResolver 取「會議-紀錄生成」提示詞 → LLM）
  → 解析回傳 JSON：
      markdown       → 落地 .md，路徑寫入 GeneratedContentRelativePath
      summary        → Meeting.Summary       ┐
      decisions      → Meeting.Decisions     ├ 覆寫（產生前已跳確認）
      participants   → Meeting.Participants  ┘
      actionItems[]  → Meeting.PendingActionItemsJson（草稿，不建工作）
  → MinutesStatus = 已產生
  → 使用者開「待辦確認」對話窗 → 勾選／微調 → 批次建立工作項目

6.2 設計理由

  • 完全復用既有轉錄管線，不重造語音轉文字、分塊、重試、取消、重啟回復。
  • 轉錄完成後的觸發做成加值步驟（比照既有影片轉碼的慣例）：失敗只記警告、不影響轉錄本身成功。
  • 新的會議紀錄產生管線嚴格比照既有背景管線的四件套結構，與既有四條同構，維護心智負擔為零。
  • 待辦不自動建立：LLM 會把閒聊當待辦，自動寫入會污染工作清單且難以清理。人工確認是必要的品質閘門。
  • 不支援線上會議連結：Teams／Zoom 的錄影連結需要登入權杖，既有的 yt-dlp 下載器抓不到，實際可用性有限。使用者從會議平台匯出檔案再上傳，反而是最可靠的路徑。

6.3 提示詞契約

新增提示詞鍵 會議-紀錄生成，走既有四層解析（單次操作覆蓋 → 資料庫 → appsettings → 程式 fallback）。要求 LLM 回傳單一 JSON 物件：

{
  "markdown": "完整會議紀錄 Markdown",
  "summary": "三到五句摘要",
  "decisions": "決議事項條列",
  "participants": "出席者，逗號分隔",
  "actionItems": [{ "title": "", "owner": "", "dueDate": "YYYY-MM-DD", "description": "" }]
}

降級策略：JSON 解析失敗時，把整份回應當 markdown 落地、其餘欄位留空、狀態仍標為已產生，並記錄警告日誌（不得靜默）。這樣即使 LLM 不遵守格式，也不會整筆失敗。

6.4 權控與安全

  • 上傳與觸發都在 UI 執行緒完成團隊權控檢查（IsTeamAccessible），背景 scope 不做使用者權控（比照文件轉文字「依提示詞產生」的既有慣例）。
  • 新建的 MediaTranscription 繼承會議的 Teams，確保轉錄紀錄的可見範圍與會議一致。
  • 由待辦建立的工作任務繼承會議的 ProjectId／Teams／Categories。
  • 佇列載荷帶提交者身分（PipelineJob），token 用量正確歸屬。
  • 含檔案選擇的上傳對話窗必須設 MaskClosable="false"（否則選完檔案會誤關）。

6.5 容量

會議錄音／錄影上傳上限由 1GB 調整為 2GB。需實測 Kestrel 與 Blazor InputFile 串流是否需額外調整（InputFile 走分塊串流，理論上不受 SignalR 訊息上限影響，但需驗證）。

6.6 驗收條件

  1. 上傳一段 5 分鐘會議錄音 → 狀態依序走過 轉錄中 → 產生中 → 已產生。
  2. AI 會議紀錄可在頁內檢視／編修，存回原地覆寫同一檔案（不產生新檔、不動資料庫路徑欄位）。
  3. 摘要／決議／出席者確實寫回欄位；重新產生前有確認對話窗明示將覆寫。
  4. 待辦草稿可勾選建立為工作任務，且繼承專案／團隊／分類。
  5. 轉錄失敗 → 會議狀態為失敗並有錯誤訊息；LLM 回非 JSON → 降級成功且有警告日誌。
  6. 重啟後「轉錄中／產生中」的會議會被重新排程。
  7. 2GB 檔案可上傳。
  8. 非同團隊使用者看不到該會議與其轉錄紀錄。

七、跨階段共同規範

本專案既有的鐵則，四個階段全部適用（詳見 開發慣例與限制速查）：

  1. 雙 provider migration：每次模型變更要在 SQLite（AccessDatas）與 SQL Server（AccessDatas.SqlServerMigrations）各產生一次；產生後確認沒有誤產 MyTas／MyTasFile 的 rename。
  2. 團隊權控：任何新查詢／Controller／下載端點都要走 IRecordAccessScopeProvider ＋ TagStringHelper.BuildTeamAccessPredicate／IsTeamAccessible。
  3. 標籤欄位：以分隔字串儲存、TagStringHelper 轉換與精確比對；AutoMapper 以 ForMember 做 List ⇄ 字串。
  4. 選單三處同步：MagicObjectHelper 常數、RolePermissionService 群組、Menu.json，以位置索引對應。
  5. Blazor 慣例：建構式注入 Service／AntDesign 服務、[Inject] 注入框架類；編輯前 Clone()；Update／Delete 前 CleanTrackingHelper.Clean<T>()；多選 Select 用 Mode="SelectMode.Multiple" ＋ Values／OnSelectedItemsChanged。
  6. 動作鈕圖示：一律使用 CrudActionButton，新圖示名稱須加入允許清單測試；全站不可用 emoji 當圖示。
  7. 日誌：外部呼叫三點式（開始→成功→失敗）；catch 不得靜默；不記金鑰、不記請求／回應本文。
  8. 版本與文件：每個可建置階段 appsettings.json 的 SystemVersion +1 並於 commit message 說明；同步更新相關文件；docs/*.md 一律 UTF-8 含 BOM，提交前 scripts/Test-DocsEncoding.ps1 全綠。
  9. 不自動 commit：每階段完成後由使用者決定何時 commit／merge／push。
