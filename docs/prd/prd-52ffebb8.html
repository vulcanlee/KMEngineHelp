角色管理 PRD

一、目標與範圍

讓管理員建立與維護角色，決定使用者可見的頁面、可執行的動作，以及登入後套用的預設團隊。角色管理是頁面權限與團隊資料權控的交會點。

本 PRD 範圍包含 /roleviews 頁面、角色 CRUD、權限樹勾選、預設團隊多選、角色 JSON 儲存。非範圍包含欄位級權限、資料列級自訂規則、權限繼承。

二、使用者與入口

項目說明
路由/roleviews
選單系統管理 → 權限管理 → 角色管理（1.0.42 起「系統管理」下分三個子群組，本頁位於「權限管理」）
權限僅管理員 CheckIsAdmin()
主要使用者系統管理員

三、畫面與欄位

角色欄位為名稱、權限 JSON（TabViewJson）、預設團隊（DefaultTeamsJson）與建立／更新時間，無說明欄位、無啟用停用狀態。權限樹由 RolePermissionService.InitializePermissionSetting() 產生，預設團隊由啟用中的團隊管理提供多選。

四、內部系統運作

核心流程為 RoleViewView → RoleViewService → RolePermissionService → BackendDBContext。

  1. 進頁檢查登入與管理員身分。
  2. 載入啟用團隊名稱作為預設團隊選項。
  3. 權限樹由 RolePermissionService.GetRoleListPermissionAllName() 生成，外層順序需與 Menu.json 頂層一致。
  4. 儲存時將勾選權限序列化到 RoleView.TabViewJson。
  5. 預設團隊以 JSON 陣列儲存在 RoleView.DefaultTeamsJson，透過 TeamJsonHelper 轉換。
  6. 使用者登入時，AuthenticationStateHelper.Check 解析角色權限與預設團隊到 CurrentUser.RoleList / TeamList。

五、LLM / RAG 互動

本功能不呼叫 LLM、不使用 embedding，但會決定所有 LLM/RAG 功能的可見資料範圍。例如 AI 知識問答與檢索品質評測的團隊權控皆依登入者角色團隊或樣本模擬團隊運作。

六、權限與安全

  • 僅管理員可管理角色。
  • Menu.json、MagicObjectHelper、RolePermissionService 三處順序必須同步，因側邊選單以位置索引對應。
  • 動作型權限必須排在頁面型權限之後，避免占用選單索引。
  • 預設團隊名稱需與團隊管理精確相符，否則團隊權控會失效或看不到資料。

七、錯誤與邊界

  • 權限 JSON 無法解析時，登入檢查應拒絕該使用者。
  • 刪除角色前需評估是否仍有使用者指派（角色無停用機制，只能刪除）。
  • 新增頁面時若未同步三處，會造成選單顯示或授權錯亂。

八、驗收與測試

  • 管理員可新增、編輯、刪除與搜尋角色。
  • 權限勾選後，使用者登入可取得正確頁面權限。
  • 預設團隊可影響紀錄清單與 AI 知識問答可見範圍。
  • 選單順序與權限樹順序一致。

十、現況校正（1.0.63 核對）

  • 權限樹覆蓋所有非 adminOnly 的正式選單頁。adminOnly 群組（系統管理、統計報表）改以管理員身分把關、不進權限樹：SidebarMenuService.FilterMenuItems 對 adminOnly 項目直接以 AdminOnly 決定可見性、略過角色權限比對，頁面本身也只呼叫 CheckIsAdmin()。權限樹中「統計報表」與「系統管理」群組僅保留佔位常數以維持與 Menu.json 的位置索引對齊，MenuPermissionAlignmentTests 已將 adminOnly 項豁免於逐項對應的不變量。
  • 知識審核、蒸餾審核 等無選單動作型權限必須排在群組頁面權限之後，避免位置索引占用選單項。
  • 預設團隊為名稱 JSON 陣列，與團隊管理精確相符；管理員豁免與「角色剛好含所有現有團隊」不是同一語意。
