一、背景與目的

系統已具備「知識庫分類」(Category) 與「團隊管理」(Team) 兩項基礎資料管理功能。本需求要把這兩者實際套用到五種既有紀錄頁面，並加入以團隊為基礎的資料權限控管：

  1. 在五種紀錄（專案管理 Project、工作任務 MyTask、會議紀錄 Meeting、影音轉逐字稿 MediaTranscription、文件轉文字 DocumentExtraction）加入「分類」與「團隊」兩個標籤式多值字串欄位（可空、可多值、不做關聯），並提供標籤式輸入 UI 與清單過濾。
  2. 在使用者角色(RoleView) 加入「預設團隊」設定，使非管理員使用者瀏覽上述五種紀錄時，僅能看到自己角色團隊範圍內（或無團隊）的紀錄；管理員(IsAdmin) 不受限。

目的：讓使用者能快速依分類找到/過濾紀錄，並以團隊權控限制敏感資料的可見範圍。

設計範本與現況

  • 各類紀錄的清單查詢透過 Service.GetAsync(DataRequest) 或 Controller／Repository，支援關鍵字、分類／團隊篩選、排序與分頁；所有入口共用精確團隊權控規則。
  • 管理員以 MyUser.IsAdmin 判定，登入時複製到 CurrentUser.IsAdmin，可用 AuthenticationStateHelper.CheckIsAdmin() 檢查。
  • 角色 RoleView 以 TabViewJson（JSON 字串）儲存頁面權限；登入時 AuthenticationStateHelper.Check() 載入角色並寫入 CurrentUser。
  • AntDesign Blazor 1.6.0，支援 Select Mode="multiple"（目前尚無多選用例，將新增）。
  • CategoryService / TeamService 目前無「取得全部啟用清單」方法，需新增。

項目決策

三、安全模型（核心規則）

對某位非管理員使用者，一筆紀錄「可見」的條件為：

（紀錄的 Teams 為空） OR （紀錄的 Teams ∩ 使用者角色的「預設團隊」≠ ∅）

推論：

  • 管理員：略過上述過濾，可見所有紀錄。
  • 使用者角色無任何預設團隊：只看得到「無團隊（公開）」紀錄。
  • 此規則為伺服器端強制，套用於清單查詢、單筆讀取、編輯、刪除、下載/預覽。非授權者即使直接以 id 存取，亦回傳「找不到/無權限」（不可繞過 UI）。
  • 「分類」不參與可見性判斷。

團隊名稱精確比對

  • 紀錄 Teams／Categories 以分隔字元包夾的字串儲存，例如以換行字元 \n 為分隔："\n團隊A\n團隊B\n"。
  • 成員判斷一律以 Field.Contains("\n" + 名稱 + "\n") 進行，EF Core 轉為 LIKE，SQLite 與 SqlServer 皆可，並避免子字串誤判（例如「團隊」誤中「團隊2」）。
  • AdapterModel / DTO 對外以 List<string> 表示；存取層負責 List<string> ⇄ 分隔字串轉換（提供共用輔助方法）。

五、存取範圍解析（權控落點）

新增一個共用元件（建議命名 IRecordAccessScope / RecordAccessScopeProvider，置於 KnowledgeExtraction.Business）：

  • 由目前使用者情境取得 (bool IsAdmin, IReadOnlyList<string> AllowedTeams)。
  • Blazor 情境：取自 CurrentUserService.CurrentUser。
  • API（JWT）情境：由 JWT claims 解析使用者並載入其角色團隊（確保 API 路徑同樣受控）。
  • 提供方法產生 EF 述詞，封裝「公開 OR 團隊交集」邏輯，套用於：
  • 五個 Service.GetAsync(DataRequest)（清單）與 GetAsync(int id)（單筆）。
  • 五個 Controller 的 search / get-by-id / update / delete / 下載端點。
  • 管理員時回傳「不過濾」。

此元件是安全核心，必須有完整單元測試（見第九節）。

六、查詢與過濾（DataRequest 擴充）

  • 擴充 KnowledgeExtraction.Models/Systems/DataRequest.cs：新增
  • List<string> CategoryFilters（多選分類過濾）
  • List<string> TeamFilters（多選團隊過濾）
  • 各 Service.GetAsync(DataRequest) 內：
  • 既有關鍵字搜尋、排序、分頁維持不變。
  • 套用團隊權控述詞（第五節）。
  • 套用分類過濾：選取多個時以 OR（Categories.Contains("\n"+c+"\n") 任一成立）。
  • 套用團隊過濾：同上（在權控允許範圍內進一步縮小）。
  • 對外 API 的 *SearchRequestDto 亦對應新增 CategoryFilters、TeamFilters。

七、UI（Blazor Server + Ant Design）

7.1 新增/編輯 Modal — 標籤式多選

於五種紀錄的新增/編輯表單加入兩個欄位：

<FormItem Label="分類">
    <Select TItem="string" TItemValue="string"
            Mode="multiple" @bind-Values="CurrentRecord.Categories"
            AllowClear EnableSearch Placeholder="輸入關鍵字選擇分類" Style="width:100%">
        @foreach (var c in AvailableCategories)
        {
            <SelectOption TItem="string" TItemValue="string" Value="@c">@c</SelectOption>
        }
    </Select>
</FormItem>

<FormItem Label="團隊">
    <Select TItem="string" TItemValue="string"
            Mode="multiple" @bind-Values="CurrentRecord.Teams"
            AllowClear EnableSearch Placeholder="輸入關鍵字選擇團隊" Style="width:100%">
        @foreach (var t in AvailableTeams)
        {
            <SelectOption TItem="string" TItemValue="string" Value="@t">@t</SelectOption>
        }
    </Select>
</FormItem>
  • 已選項目以標籤（含 x 移除）呈現 —— 即 AntDesign Select Mode="multiple" 內建行為。
  • AvailableCategories：來自 CategoryService 的「所有啟用分類名稱」。
  • AvailableTeams：來自 TeamService 的「所有啟用團隊名稱」；非管理員只列出自己授權的團隊（與權控一致，避免指定到看不到的團隊）。

7.2 清單工具列 — 多選過濾下拉

於五種紀錄清單頁工具列，在既有搜尋框旁新增「分類」「團隊」多選過濾下拉（Select Mode="multiple"），變更時帶入 DataRequest.CategoryFilters / TeamFilters 並重新查詢。原搜尋/排序/分頁照常並與過濾、權控疊加。

7.3 清單欄位

五種紀錄清單表格新增「分類」「團隊」欄位，以標籤樣式顯示該紀錄的多個值。

7.4 角色管理頁 — 預設團隊

於角色維護 Modal（RoleViewView）新增「預設團隊」Select Mode="multiple"（來源為所有啟用團隊），儲存時序列化為 DefaultTeamsJson。

八、服務層支援方法

  • CategoryService 新增 GetAllEnabledNamesAsync()：回傳所有 IsEnabled 分類名稱（依名稱排序）。
  • TeamService 新增 GetAllEnabledNamesAsync()：回傳所有 IsEnabled 團隊名稱。
  • 共用名稱字串 ⇄ List<string> 轉換輔助（trim、去空、去重、以分隔字元組裝）。
  • 登入流程（AuthenticationStateHelper.Check()）：載入角色 DefaultTeamsJson → CurrentUser.TeamList。

九、測試 / 驗證策略（重點）

本需求涉及資安權控，必須具備可重複的自動化驗證。沿用既有測試模式（xUnit + SQLite in-memory fixture，參考 CategoryServiceTests / MyUserServicePasswordTests）。

9.1 存取範圍（權控）單元測試 — 核心

針對「存取範圍述詞」與各 Service.GetAsync，建立矩陣測試：

  1. 管理員 → 看得到所有紀錄（含有團隊、無團隊）。
  2. 非管理員（團隊 = {A}）→ 只看到 Teams 含 A 的紀錄 及 無團隊紀錄；看不到只屬 {B} 的紀錄。
  3. 非管理員無任何團隊 → 只看到無團隊（公開）紀錄。
  4. 空團隊紀錄 → 任何登入者皆可見。
  5. 團隊名稱精確比對：使用者團隊 {團隊} 不應看到只屬 {團隊2} 的紀錄（不可子字串誤判）。
  6. 每個紀錄型別（5 種）至少涵蓋一組權控測試。

9.2 防繞過測試

  • 非授權使用者對單筆 GET / 編輯 / 刪除 / 下載 → 回傳拒絕（找不到/無權限），不得成功。

9.3 過濾與相容性測試

  • 分類/團隊多選過濾以 OR 比對正確。
  • 過濾與既有關鍵字搜尋、排序、分頁疊加結果正確。
  • List<string> ⇄ 分隔字串轉換：空值、單值、多值、含前後空白、重複值的往返一致。

9.4 端到端驗證（手動）

  • 以管理員與非管理員（不同團隊）兩種帳號登入，於五個頁面驗證可見範圍、標籤新增/移除、過濾、儲存後回讀正確。

9.5 建置門檻

  • dotnet build 與 dotnet test 全綠；新增測試全部通過。

十二、驗收條件

  1. 五種紀錄可於新增/編輯時以標籤方式選取多個分類與團隊（只能選現有啟用清單、可逐一移除），儲存後回讀正確。

  4. 非管理員於五個頁面僅能看到「無團隊」或「與自己角色團隊交集」的紀錄；管理員可看到全部。

  7. 自動化測試（權控矩陣、防繞過、過濾、轉換）全數通過；dotnet build/dotnet test 綠燈。
  8. appsettings.json 版本號於實作建置時 +1（0.2.35 → 0.2.36），相關文件同步更新。
