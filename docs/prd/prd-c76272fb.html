產品需求（PRD）

知識圖譜（Graph RAG）PRD

定義「從蒸餾內容抽取實體關係、經人工治理後納入檢索與全域問答」之功能需求與設計

  • 文件用途：定義「從蒸餾內容抽取實體關係、經人工治理後納入檢索與全域問答」之功能需求與設計
  • 主要讀者：產品、開發團隊
  • 文件版本：1.0
  • 文件狀態：已實作
  • 現行系統版本：1.0.100
  • 首次實作版本：1.0.83
  • 最後核對日期：2026/07/29
  • 建立日期：2026/07/29
  • 對應版本：1.0.83–1.0.96（P1–P13，已實作）
  • 編碼：UTF-8（繁體中文，含 BOM）

導入前分析與分階段藍圖見 strategy/2026-07-27 Graph RAG 導入分析與實作藍圖；檢索設計細節見 architecture/知識庫 RAG 設計與執行 §4.2–§4.4；現況與缺口總表見 planning/2026-07-28 GraphRAG 待辦盤點；使用者操作見 guides/知識圖譜使用指南。

一、目標與範圍

補上一般 RAG（向量＋關鍵字混合檢索）結構上答不好的兩類問題：

  1. 多跳關聯：答案的推理鏈分散在多份文件，沒有任何單一片段同時涵蓋頭尾。
  2. 全域綜觀：問題需要「看過全部內容再歸納」（整體風險、系統性根因、趨勢），取 TopK 片段等於隨機抽樣。

對應兩條產品能力：多跳圖檢索（融合進混合檢索的第三路）與社群摘要全域問答（map-reduce）。

核心設計原則：LLM 提案、人工核可。 LLM 抽出的關係一律為「待審核」，只有經人工核可者才進入檢索加分。錯誤的關係若直接生效，會把錯的內容排到前面——比沒有圖譜更糟。

加分項而非取代品：SystemSettings.Retrieval.GraphWeight 設 0 即完全回到 1.0.82 之前的檢索行為，向量與關鍵字兩路不受影響。

非目標（刻意不做，理由見 待辦盤點 §4）：節點嵌入與圖神經網路、專用圖資料庫（Neo4j 等）、rerank、Agentic RAG 多輪規劃、寫入型 Web API、多執行個體共享的檢索快取。

二、流程

知識來源（已蒸餾、Wiki 頁已核可）
   │
   ├─按「抽取／重抽三元組」──► GraphExtraction 佇列 ──背景──► 讀現行 Wiki 頁 ──LLM──► 三元組（待審核）
   │                                                                                    │
   │                                                          人工核可 ──► 已完成 ──► 納入檢索加分
   │                                                          人工退回 ──► 已退回 ──► 永不生效
   │
   └─Wiki 頁核可／編修 ──► 解析 [[標題]] ──► GraphEdge（概念連結邊，無 LLM、冪等重建）

已核可三元組 ＋ 已核可別名 ──按「重建社群摘要」──► 建圖 → 社群偵測 → 每群 LLM 摘要 → 整批取代
                                                                                  │
                                                              全域問答 map-reduce ─┘
  • 兩種邊，來源不同：GraphEdge 由 Wiki 頁的 [[標題]] 連結具體化（純字串解析、無 LLM、無需審核）；三元組邊由 LLM 抽取（需審核）。
  • 抽取的輸入是「已完成且現行」的 Wiki 頁，因此 Wiki 頁未核可 ⇒ 抽取跑完但無產出。這是最常見的使用者踩雷點。
  • 重抽不覆蓋人工決策：以「主詞｜關係｜受詞」去重，已核可／已退回者原樣保留。
  • 社群重建是整批取代，不做版本化。

三、已實作需求

3.1 資料模型

新增 6 個實體（AccessDatas/Models/）：

實體要點
GraphNode實體節點：Name、Type、WikiPageId（軟錨，刻意無 FK）、Teams
GraphTriple三元組：主詞／受詞 NodeId、Relation、Confidence、Status（待審核／已完成／已退回）、ReviewedBy／ReviewedAt／ErrorMessage
GraphEdge頁↔頁概念連結邊：SourceWikiPageId／TargetWikiPageId 為純索引整數、刻意無 FK（避免 SQL Server 多重串聯路徑）
GraphCommunity社群摘要：Title、Summary、Teams（成員來源的團隊聯集）、MemberCount
GraphEntityAlias別名→標準名：Confidence、Status、ReviewedBy。無 Teams、無 FK（全域治理）
GraphJobState全域圖譜作業狀態：JobType、Status。無 Teams（1.0.95 起）

KnowledgeSource 新增抽取任務追蹤欄位：GraphStatus（待抽取／等待中／處理中／已抽取／失敗／已取消）、GraphProgressPercentage、GraphErrorMessage、GraphExtractedAt。

⚠️ 兩組狀態語意不同、不可混用：KnowledgeSource.GraphStatus 是管線狀態（跑到哪了），GraphTriple.Status 是審核狀態（待審核／已完成／已退回）。來源＝「已抽取」時，其三元組仍全為「待審核」。

雙資料庫 migration 各一套（Sqlite AccessDatas 與 AccessDatas.SqlServerMigrations）：AddGraphEdge(1.0.83)、AddGraphExtraction(1.0.84)、AddGraphCommunity(1.0.85)、AddGraphEntityAlias(1.0.87)、AddGraphEntityAliasConfidence(1.0.88)、AddGraphIndexes(1.0.89)、AddGraphHopParams(1.0.90)、AddRagEvalGraphFields(1.0.92)、AddGraphJobState(1.0.95)。

3.2 四條作業

作業範圍LLM觸發狀態持久化
三元組抽取per-record✅ 每來源一次蒸餾完成自動；或手動重抽KnowledgeSource.GraphStatus；進入 PipelineNames
概念連結邊重建per-record❌蒸餾完成、Wiki 頁核可／編修無（冪等、快速）
社群摘要重建全域單例✅ 每群一次管理員手動GraphJobState；刻意不進 PipelineNames
LLM 別名建議全域單例✅ 一次管理員手動同上
  • 抽取的前置守門順序：來源存在 → 團隊權控 → 蒸餾狀態＝已蒸餾 → Chat LLM 已設定 → 非進行中。任一不過即擋下，不浪費 LLM 費用。
  • 抽取背景服務重啟時，把殘留「處理中」改回「等待中」並重新排程。
  • 兩條全域作業重用既有的取消登記機制，並在重啟時撿回未完成作業。
  • ⚠️ 記憶體旗標只反映本機，GraphJobState 才是多執行個體下的全域真相。

3.3 審核頁與權限

頁面：/knowledge-graph-review（Menu.json id 48，「知識庫」群組），四個分頁：

  1. 三元組審核：狀態／團隊／關鍵字篩選、分頁表格；編修（主詞／型別／關係／受詞／型別）、核可、退回（可填理由）。
  2. 實體合併（僅管理員可見）：手動新增別名、「LLM 自動建議別名」、狀態篩選與審核。已核可別名以傳遞閉包收斂為同一實體。
  3. 圖譜瀏覽：實體名 + 跳數（1～3），inline SVG 放射狀圖 + 關係表格。節點上限 100，達上限回傳截斷旗標並在 UI 明示，不靜默截斷。
  4. 待抽取來源：已蒸餾但圖譜為空或抽取失敗者（進行中刻意排除），上限 50 筆。

頁頂：社群摘要狀態列（社群數／上次建立時間／上次錯誤）＋「重建社群摘要」（僅管理員）。

權限（三處已同步）：

  • MagicObjectHelper.角色_知識圖譜審核，值為 "知識圖譜審核"——這是少數「選單顯示名＝權限值」完全一致者，不是遺漏。
  • RolePermissionService 知識庫權限群組（該群組因此由 8 項變 9 項）。
  • Menu.json id 48。
  • 頁內細粒度：進頁需 角色_知識圖譜審核；核可／退回／編修需管理員或 角色_蒸餾審核；實體合併與社群重建寫死為僅管理員，不受角色授權影響。

3.4 檢索融合與參數

總分 = VectorWeight × 向量分 + KeywordWeight × 關鍵字分 + GraphWeight × 圖分

圖分：以向量∪關鍵字命中的 Wiki 頁為種子，沿 GraphEdge 與已核可三元組做 BFS，第 h 跳強度 = 種子強度 × GraphHopDecay^(h-1)（第 1 跳不衰減），鄰居頁的現行片段獲得加成，節點數達 GraphMaxNodes 即停止並記 log。

參數預設熱調
GraphWeight0.2✅ /rag-diagnostics（RetrievalParamOverride）
GraphMaxHops2（範圍 1～3）✅
GraphHopDecay0.5✅
GraphMaxNodes200❌ 需重啟
GraphGlobalCommunityCap20❌ 需重啟
GraphMaxCommunities50❌ 需重啟
GraphAliasNameCap300❌ 需重啟

後四項無資料庫覆寫路徑，讀取時以 Math.Max(1, 值) 夾住（填 0 退回 1，不靜默停擺）。

⚠️ GraphMaxHops 預設 2（1.0.90 起多跳生效）會使 1.0.89 之前的檢索評測基線位移；升級後應重跑評測。

提示詞槽位（5 個，DB Prompt.Name 為中文精確鍵）：GraphTripleExtract＝圖譜-三元組抽取、GraphCommunitySummary＝圖譜-社群摘要、GraphGlobalMap＝圖譜-全域map、GraphGlobalReduce＝圖譜-全域reduce、EntityAliasPropose＝圖譜-別名建議。皆走四層解析、可於 /prompts 覆蓋、免重啟。

3.5 全域問答

/knowledge-base-chat 設定區「查詢模式」：一般（精準檢索）／全域（社群摘要）。

  • map：逐一取用你有權存取的社群摘要，每個社群一次 LLM 取重點（上限 GraphGlobalCommunityCap）。
  • reduce：彙整成最終答案。只有 Blazor 聊天頁做完整 map-reduce；MCP 與 REST 只做 map。
  • 回答特性：無出處面板、無相似度（社群摘要無 chunk 層出處），改回傳取用社群數；不套用限定來源／分類／團隊篩選。
  • 從未重建過社群摘要時，回覆可行動的原因說明而非空白。

3.6 評測指標

/rag-evaluation 新增四個指標：圖召回增益（主指標，為保守下界——融合重排效應不計入）、圖參與率、圖獨有命中、平均取用社群數。基線記錄當時的 GraphWeight／GraphMaxHops／GraphHopDecay；未記錄時顯示「未記錄」而非 0（0 會謊稱當時圖是關閉的）。

支援「全域問答」評測模式：以關鍵詞涵蓋率計分，Precision／NDCG／MRR 顯示「—」。⚠️ 會呼叫 LLM 故非確定性；關鍵詞為子字串比對，不處理同義詞。

3.7 對外暴露面

MCP（1.0.91）：knowledge_graph_neighbors（純 DB 查詢、只回已核可三元組、節點上限 100 並回傳截斷旗標）；knowledge_ask 的 mode=global（sources 恆空、topScore 恆 0、改回 usedCommunities、只 map 不 reduce、無法辨識的 mode 明確拋錯）。

REST（1.0.96，KnowledgeGraphController，雙路由 api/[controller] 與 api/v1/[controller]，JWT 認證）：

  • POST .../global-ask：LLM 未設定回 503（服務依賴未備妥，刻意非 500）。
  • GET .../neighbors?entityName=&maxHops=：maxHops 超界回 400（刻意不靜默夾住，與 MCP 行為不同）；查無實體回 200 + found=false。
  • 身分解析重用 McpIdentityResolver，權控完全交給既有服務，與 MCP 走同一條把關程式碼。
  • Token 歸屬用專屬作業別與來源標記，刻意不重用 Blazor 常數，以便成本歸因可分辨管道。
  • DTO 刻意不含 sources／topScore（全域模式本來就沒有）。
  • 無寫入型端點（與 MCP 的既有非目標一致）。

四、資安不變量

越權洩漏＝0。 權控不是最後過濾一次，而是四層各自套用 TagStringHelper.BuildTeamAccessPredicate／IsTeamAccessible：

  1. 邊：遍歷時每一條邊都檢查——而且每一跳都重新檢查，不能借道無權限節點繞路。
  2. 節點：他隊實體節點不納入；他隊節點的錨頁不進跨來源合併。
  3. 三元組：只有已核可且有權存取者參與加分。他隊三元組即使兩端頁面都公開也不加分——「這兩者有關係」本身即知識，屬抽出它的來源所在團隊。
  4. 鄰居內容片段：仍須通過原本的內容層權控。

社群摘要 ACL 更嚴（子集判定）：社群涵蓋來源的 Teams 聯集必須是使用者團隊的子集，或該社群完全公開。理由是一份摘要混合多筆來源知識，其中任一筆無權即整份不可給。

別名表與作業狀態表無 Teams，屬全域管理員治理；別名只改變連通性，不放寬任何人的可見範圍。

已知安全待辦：

  • REST global-ask 缺 HTTP 層的越權洩漏端到端測試（服務層已覆蓋）。
  • 取消抽取的動作沿用頁面層級（僅管理員）把關，未另加團隊權控。

本節不重述細節，一律引用 planning/2026-07-28 GraphRAG 待辦盤點：

  • §4「選配未做」：節點嵌入、專用圖資料庫、rerank、Agentic RAG、寫入型 API 等，附每一項的不做理由與觸發條件。
  • §5「未達觸發」：規模或需求尚未到達門檻、暫不投入的項目。

⚠️ 這些項目不得視為現行能力。
