一、背景與目的

會議是企業內最高頻、也最容易流失的知識來源。系統早已具備完整的影音轉逐字稿管線與 LLM 產生內容能力，會議管理卻仍是純手動 CRUD——使用者必須自己在兩個頁面之間搬運內容。

本功能把「錄音 → 逐字稿 → AI 會議紀錄 → 待辦轉工作任務」串成一條自動化的線，讓使用者只需在會議管理頁上傳一次檔案。

二、端到端流程

階段執行者MinutesStatus
使用者於會議清單點「上傳錄音」MeetingService.AttachRecordingAsync（UI 執行緒）轉錄中
語音轉文字既有轉錄管線（第 1 條）轉錄中
轉錄成功後的加值步驟入列TranscriptionProcessor.TryEnqueueMeetingMinutesAsync排隊中（1.0.78 起；先前為「轉錄完成」）
請 LLM 產生會議紀錄會議紀錄產生管線（第 7 條）產生中 → 已產生／失敗
待辦勾選建立工作任務MeetingActionItemService（人工觸發）不變

上傳時建立的 MediaTranscription 繼承會議的 Categories／Teams，確保轉錄紀錄的可見範圍與會議一致。

三、管線設計

會議紀錄產生是系統的第 7 條背景管線（前 6 條：媒體轉錄、文件轉文字、圖片識別、資料清洗、知識頁審核、嵌入索引），嚴格比照既有四件套：

IMeetingMinutesQueue（Channel<PipelineJob> Singleton）→ MeetingMinutesBackgroundService（出列、OperationContext.Push、重啟回復）→ MeetingMinutesProcessor（Scoped、重試包裝）

三個必須維持的不變量：

  1. 加值步驟放在轉錄「已完成」寫入之後，且自帶總 try/catch。放之前若拋例外會被外層 catch 接到，把其實已成功的轉錄標成失敗。
  2. 重啟回復只撈「產生中」，不撈「轉錄中」——後者是轉錄管線的狀態，由它復原後再觸發本管線。
  3. 失敗狀態寫入用 CancellationToken.None，否則權杖已取消時狀態寫不進去。

背景 scope 無使用者情境，故 Processor 直接依相對路徑讀逐字稿檔，不走帶團隊權控的 GetTranscriptAsync。權控已在上傳當下於 UI 執行緒完成。

四、提示詞契約

提示詞鍵 會議-紀錄生成（LlmPromptKeys.MeetingMinutes），走既有四層解析：單次操作覆蓋 → DB Prompt 表 → appsettings LlmPrompts → 程式 fallback。

⚠️ LlmPromptsSettings.Get() 的 switch 用寫死的中文字面值而非常數。新增提示詞鍵要同步改三處（LlmPromptKeys 常數、LlmPromptsSettings 屬性、Get() switch）；漏掉 switch 會讓 appsettings 層靜默失效。

要求 LLM 回傳單一 JSON 物件：

{
  "markdown": "完整會議紀錄 Markdown",
  "summary": "三到五句摘要",
  "decisions": "決議事項條列",
  "participants": "出席者，以「、」分隔",
  "actionItems": [{ "title": "", "owner": "", "dueDate": "YYYY-MM-DD", "description": "" }]
}

提示詞明確要求「只列真正的待辦，不要把一般討論或閒聊當成待辦」與「dueDate 沒提到明確日期就給空字串，不要自行推測」。

五、降級策略

解析採「第一個 { 到最後一個 }」的括號掃描，可順帶越過 ``` `json ``` 圍欄與前後綴文字。

無法取得可用 JSON 時降級：整份回應當 Markdown 落檔、其餘欄位留空、狀態仍為「已產生」——不會整筆失敗。同時 LogWarning 並記下回應前 500 字（不記全文），讓模型不聽話時留得下線索。

被視為降級的情況：非 JSON、JSON 格式錯誤、JSON 合法但 markdown 欄位為空。

六、欄位寫回規則（重要）

自動產生時，摘要／決議／出席者只填原本空白的欄位，絕不覆寫使用者已寫的內容。

理由：觸發是自動的，當下沒有人能確認覆寫。若直接覆寫，使用者上傳錄音前手寫的摘要會在毫無提示的情況下被蓋掉。

使用者若想改用 AI 版本，到會議頁按「套用 AI 結果」——那是手動出口，會跳確認對話窗，確認後才覆寫三個欄位。

Markdown 全文一律落檔至 ExternalFileSystem.GeneratedContentPath（{yyyy}/{guid}.md），DB 只存相對路徑；重新產生即覆寫舊檔（只保留最新一筆）。可於頁內經 ContentEditDialog 檢視編修，原地覆寫同一檔案（不產生新檔、不動路徑欄位、不需 migration）。

七、待辦草稿與工作任務

AI 抽出的待辦不會自動建立工作任務——LLM 會把閒聊當待辦，自動寫入會污染工作清單且難以清理。

草稿存於 Meeting.PendingActionItemsJson（JSON 陣列），使用者在確認對話窗勾選（可就地微調標題／負責人／期限）後才批次建立。

建立規則：

  • 繼承會議的 ProjectId／Teams／Categories
  • Owner 空白時填「未指定」（該欄位為 Required）
  • Category（單值必填欄位）填「會議待辦」
  • EndDate 解析 DueDate；解析不出來就留空，不自行推測
  • Description 帶入草稿說明並附註來源會議

建立後草稿保留並標記 Created（置灰、不可再勾），供追溯「AI 建議了什麼、採納了哪些」，同時避免重複建立。

八、權控與容量

  • 權控落點：上傳與觸發時於 UI 執行緒檢查（IsTeamAccessible）；背景 scope 不做使用者權控（既有慣例）。待辦讀取與建立同樣套團隊權控。
  • token 用量歸屬：佇列載荷 PipelineJob 帶提交者身分，背景服務以 OperationContext.Push 推入情境（必須在建 DI scope 之前）。
  • 上傳上限 2GB（1.0.20 起，原 1GB）。
  • SourceTranscriptionId 為軟參照（見 會議管理 PRD）：轉錄被刪時會留下孤兒 Id，讀取端須容忍（ReadTranscriptAsync 找不到紀錄或檔案即回 null 並標記失敗）。又因 MediaTranscription 有版本鏈，此 Id 釘的是特定版本而非最新版。

九、驗收條件

  1. 上傳 5 分鐘錄音 → 狀態依序 轉錄中 → 排隊中 → 產生中 → 已產生。（1.0.78 起排隊階段寫「排隊中」；先前寫「轉錄完成」，與「入列失敗的孤兒」同值而分不出來，且重啟後不會被復原）
  2. 先手寫摘要再上傳：產生後摘要仍是手寫那份，決議／出席者（原為空）才被填入。
  3. 按「套用 AI 結果」跳確認，確認後摘要才被覆寫。
  4. 會議紀錄可檢視編修，存回原地覆寫同一檔案。
  5. 勾選待辦建立為工作任務，繼承專案／團隊／分類；建過的顯示「已建立」且不可再勾。
  6. 提示詞改成「請用純文字回答」→ 狀態仍為已產生、Markdown 為純文字、日誌有 warning 且含回應前 500 字。
  7. 一般轉錄（非會議掛載）完成後不會產生任何會議紀錄。
  8. 產生中時重啟 → 該筆重新排程；轉錄中的會議不被會議管線撈走。
  9. 非同團隊使用者看不到該會議、無法上傳與看待辦。
  10. >1GB 檔案可上傳。

十、規劃中需求（本次未實作）

  • 多語言會議的自動語言偵測與分段
  • 待辦事項的負責人自動對應到系統使用者帳號
