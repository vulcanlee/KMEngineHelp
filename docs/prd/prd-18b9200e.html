上層 PRD：專案協作模組強化 PRD（第二階段） 相關：知識庫分類（Category）管理 PRD、專案管理、工作任務、會議管理

一、背景與目的

專案、工作、會議的「分類」欄位原本共用 Category（知識庫分類），但那份清單的定位是知識庫主題標籤——知識來源、Wiki、三條匯入管線、問答篩選、內容清點報表共 7 處都吃它。兩種語意混在同一份清單，導致下拉選單越長越雜，且任一邊調整都會污染另一邊。

1.0.18 起新增獨立的 WorkCategory（專案分類） 主檔，專供「專案管理／工作任務／會議管理」使用，與知識庫分類徹底脫鉤。

二、分工邊界（最重要）

清單路由權限常數供哪些頁面的分類下拉使用
專案分類（本 PRD）/work-categories角色_專案分類專案管理、工作任務、會議管理（含專案內「工作與會議」對話窗）
知識庫分類/categories角色_分類清單知識來源加工、知識百科、Wiki 頁、影音轉逐字稿、文件轉文字、圖片解讀、內容清點統計報表

兩份清單資料完全獨立，同名項目彼此無關聯，各自維護。兩頁各有一行說明文字提醒使用者用途差異。

三、需求決策

項目決策
欄位與 Category 完全相同：名稱（唯一、必填）、描述（選填）、啟用狀態、建立時間、更新時間
名稱唯一性忽略大小寫 + 去頭尾空白（新增與編輯皆生效，編輯時排除自身）
預設排序依「更新時間」由新到舊
停用狀態停用者不供新資料選用（下拉不顯示），既有紀錄的字串標籤仍保留
刪除方式實體刪除
既有資料啟動時自動搬移（見第六節）
REST API完整提供（見第五節）

四、資料模型

新增實體 WorkCategory（KnowledgeExtraction.AccessDatas/Models/WorkCategory.cs）：

欄位型別說明
Idint主鍵，自動遞增
Namestring專案分類名稱（必填、唯一）
Descriptionstring?描述（選填）
IsEnabledbool是否啟用（預設 true）
CreatedAtDateTime建立時間
UpdatedAtDateTime最後更新時間
  • DbSet<WorkCategory> 註冊於 BackendDBContext，無 modelBuilder 特別設定（比照 Category 走慣例）。
  • 名稱唯一性以應用層檢查為主（服務層 ValidateNameUniqueAsync 與 Repository ExistsByNameAsync），資料庫層無唯一索引。
  • 雙 provider migration：AddWorkCategory（SQLite 20260720031350 / SQL Server 20260720031235），兩份皆僅 CreateTable，無任何 rename／drop。

4.1 三種協作紀錄的儲存格式未變更

Project／MyTask／Meeting 的 Categories 欄位儲存格式完全不變——仍是 TagStringHelper 產生的 \n 包夾字串（如 "\nA\nB\n"），AutoMapper 的 ForMember 轉換不動，BuildContainsAnyPredicate 的精確成員比對不動。本次只換了「哪一張表填充下拉選單」，沒有任何資料轉換。

五、API 端點

WorkCategoryController（api/[controller] + api/v1/[controller]，JWT 授權，比照 CategoryController）：

  • POST {base}/workcategory/search：接收 WorkCategorySearchRequestDto，回傳分頁結果（預設依 UpdatedAt 降冪）
  • GET {base}/workcategory/{id}：取得單筆
  • POST {base}/workcategory：新增；名稱重複回 409 Conflict
  • PUT {base}/workcategory/{id}：編輯；路由 id 與 payload id 不一致回 400；名稱重複（排除自身）回 409 Conflict
  • DELETE {base}/workcategory/{id}：刪除

排序參數字串（name／isenabled／createdat／updatedat）與知識庫分類 API 一致。

六、既有資料自動搬移

WorkCategoryBootstrapSeeder（Business/Services/Other/），掛在 Program.cs 既有的 migration／seeding 區塊內（Database.Migrate() 之後、與預設角色／預設帳號同一個 scope）。

流程：

掃 Project.Categories + MyTask.Categories + Meeting.Categories（AsNoTracking + Distinct）
→ TagStringHelper.ToList 攤平 → Trim → 濾掉空白 → 忽略大小寫去重
→ 與 WorkCategory 既有名稱（忽略大小寫）比對，缺的批次新增（IsEnabled = true）
→ 記錄 ScannedCount / InsertedCount

設計取捨與不變量：

  • 每次啟動都執行（冪等），不使用一次性旗標。三個單欄 SELECT DISTINCT 成本可忽略，而且能持續吸收「直接改資料庫」或「還原舊備份」帶進來的新分類值。
  • 以名稱（忽略大小寫）判斷是否已存在，與服務層唯一性檢查一致，故 seeder 絕不會塞進 UI 會判為重複的列。
  • 失敗不中斷啟動：整段以 try/catch 包住，例外時 LogError 後回傳 0（依日誌鐵則不得靜默吞掉）。
  • 採同步實作，以配合 Program.cs 該區塊全程同步（使用 SaveChanges）的既有風格，避免 sync-over-async。
  • 既有紀錄的 Categories 字串完全不動。

七、選單與權限

  • MagicObjectHelper.角色_專案分類 = "專案分類"
  • RolePermissionService：附加於「基礎資料設定」群組最末端（角色_清洗設定檔 之後）
  • Menu.json：「基礎資料設定」（id 6）subMenu 最末端，id 65、圖示 label、路由 /work-categories

三處以位置索引對應；本次僅在既有群組尾端追加，不動頂層結構。MenuPermissionAlignmentTests（1.0.17 新增）守護此不變量。

八、已知技術債

MyTask.Category（單值、Required、自由輸入文字）是早期欄位，與多值 Categories 並存，目前供關鍵字搜尋、排序，以及對外 API 的精確過濾使用（MyTaskRepository／MyTaskController 皆有契約）。

本階段完全不動它。 它是非空欄位且有對外 API 過濾契約，改動＝migration ＋ API 破壞性變更 ＋ 回填每一列，且用途（單值標籤供排序過濾）與多值標籤本就不同。若要退場應另開 PRD。

九、驗收條件

  1. 選單「基礎資料設定 → 專案分類」出現且位於「清洗規則設定」之後；無權限角色看不到、無法進入。
  2. /work-categories 可完整 CRUD；名稱重複（abc vs ABC ）被拒並顯示友善訊息；API 回 409。
  3. 列表預設依更新時間新到舊；可搜尋、分頁、排序；可切換啟用狀態。
  4. 以有真實資料的資料庫副本啟動：日誌出現回填筆數，/work-categories 列出既有紀錄用過的所有分類值。
  5. 再次啟動：新增筆數為 0（冪等）。全新空資料庫啟動不報錯。
  6. /projects、/Task、/meeting 及專案內「工作與會議」對話窗的分類下拉顯示專案分類，停用項不出現。
  7. 知識來源、知識百科、三條匯入、內容清點報表的分類下拉仍讀知識庫分類。
  8. 存一筆兩個分類的專案 → 資料庫該列 Categories 仍為 \nA\nB\n；篩選為精確成員比對（「團隊」不誤中「團隊2」）。
  9. SQLite 與 SQL Server 兩份 migration 皆可套用。
