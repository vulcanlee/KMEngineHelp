一、背景與目的

本系統以「知識庫分類」集中維護可重複使用的知識庫主題標籤，供匯入素材、知識來源、Wiki 及問答篩選使用。

1.0.18 起的分工邊界：專案管理／工作任務／會議管理的分類已改用獨立的 專案分類（WorkCategory） 主檔（/work-categories），不再取用本清單。本清單自 1.0.18 起僅供知識庫相關紀錄使用：知識來源加工、知識百科、Wiki 頁、影音轉逐字稿、文件轉文字、圖片解讀、內容清點統計報表（共 7 處）。兩份清單資料完全獨立、各自維護。

AI 知識問答頁的分類篩選是另一條路徑：其下拉選項由 KnowledgeBaseChatService.GetFilterCategoriesAsync() 從既有已索引資料 distinct 取值，並非讀取本主檔，因此停用或刪除分類不會立即改變該下拉的內容。

本功能為一個標準 CRUD 頁面，需具備側邊選單項目、Menu.json 設定與角色權限控制。

設計範本

程式碼庫已有結構單純、欄位精簡且非常適合做為範本的現成 CRUD 功能 「專案管理」(ProjectPage / ProjectViewView)。本功能 以 ProjectPage 為主要設計範本，沿用其分層架構（Entity → Repository → Service → Controller → DTO → AdapterModel → Blazor View），但欄位大幅精簡。

對應現成可重用模式：

  • 名稱唯一性檢查：ProjectRepository.ExistsByNameAsync(name, excludeId)（新增與編輯皆呼叫，編輯時排除自身）。
  • 分頁／搜尋／排序：ProjectRepository.GetPagedAsync(request)，預設排序為 OrderByDescending(p => p.UpdatedAt)。
  • 名稱重複回應：Controller 回傳 409 Conflict 與友善訊息。
  • Blazor UI：工具列 + Ant Design Table（遠端資料來源、分頁）+ 新增／編輯 Modal（EditForm + DataAnnotationsValidator）。

三、功能概述

新增「知識庫分類」管理頁面，提供分類項目的新增、查詢、編輯、刪除（CRUD）。每筆分類包含名稱、描述與啟用狀態。分類名稱在系統內為唯一值（忽略大小寫並去除頭尾空白後比對）。列表預設依更新時間由新到舊呈現，最近更新的紀錄排在最前面。

0.3.34 現況已將分類套用至各類紀錄與知識流程；本 PRD 同時規範基礎資料 CRUD 與跨功能引用邊界。

四、使用者流程

  1. 進入「知識庫分類」頁面（路由 /categories）；權限不足者不顯示選單、不可進入頁面。
  2. 列表預設依「更新時間」由新到舊排序，最近更新者在最上方；支援關鍵字搜尋與分頁。
  3. 點「新增」，於 Modal 中輸入名稱（必填）、描述（選填），並設定是否啟用（預設啟用）。
  4. 送出時驗證名稱唯一性（忽略大小寫 + 去頭尾空白）：
  5. 名稱重複：拒絕儲存，顯示「分類名稱已存在」之類的友善訊息（API 回 409 Conflict）。
  6. 通過：建立紀錄，設定建立時間與更新時間，回到列表。
  7. 點「編輯」載入單筆資料，可修改名稱、描述、啟用狀態；名稱唯一性同樣須通過（比對時排除自身）。
  8. 點「刪除」出現確認對話框，確認後實體刪除該分類。
  9. 任何新增或編輯成功皆更新 UpdatedAt，故該紀錄會回到列表最前方。

五、資料模型

新增實體 Category（KnowledgeExtraction.AccessDatas/Models/Category.cs）：

欄位型別說明
Idint主鍵，自動遞增
Namestring分類名稱（必填、唯一）
Descriptionstring?描述（選填）
IsEnabledbool是否啟用（預設 true）
CreatedAtDateTime建立時間（自動設定）
UpdatedAtDateTime最後更新時間（自動設定）
  • DbSet Category 註冊於 BackendDBContext，並新增對應 EF Core Migration（SqlServer 與 Sqlite）。
  • 名稱唯一性以應用層檢查為主（CategoryRepository.ExistsByNameAsync）；比對前先 Trim() 並以忽略大小寫方式比較。
  • 唯一性比對說明：以 Name.Trim() 後，採不分大小寫比較（例如 string.Equals(..., StringComparison.OrdinalIgnoreCase)，或於查詢端統一以 ToLower() 比對），確保「測試」與「測試 」、ABC 與 abc 視為重複。

七、架構與元件（比照 ProjectPage）

各層需新增的元件如下（命名與分層比照既有 Project*）：

  • Entity Category（KnowledgeExtraction.AccessDatas/Models/Category.cs）

  • AdapterModel CategoryAdapterModel（KnowledgeExtraction.Models/AdapterModel/CategoryAdapterModel.cs）：前端綁定用，含 DataAnnotations 驗證。
  • Controller CategoryController（KnowledgeExtraction.Web/Controllers/CategoryController.cs）：比照 ProjectController。

  • DI 註冊（KnowledgeExtraction.Web/Extensions/ServiceCollectionExtensions.cs）：

  • services.AddScoped<CategoryRepository>();

九、API 端點

新增 CategoryController（比照 ProjectController，api/[controller] + api/v1/[controller]，沿用既有授權機制）：

  • POST {base}/category/search：接收 CategorySearchRequestDto，回傳分頁結果（預設依 UpdatedAt 降冪）。
  • GET {base}/category/{id}：取得單筆。
  • POST {base}/category：新增；名稱重複回 409 Conflict。
  • PUT {base}/category/{id}：編輯；驗證路由 id 與 payload id 一致；名稱重複（排除自身）回 409 Conflict。
  • DELETE {base}/category/{id}：刪除。

十、選單與權限（需異動 4 處）

本節為首次實作當時的選單結構，保留原貌。 現況為「基礎資料設定」(id 6)，子項共 5 項（知識庫分類 61、團隊管理 62、專案分類 63、AI 提示詞 64、清洗規則設定 65），權限群組為 6 個常數，登出為 id 8，頂層共 8 組（首頁、專案協作、資料匯入、知識庫、系統管理、基礎資料設定、統計報表、登出）；一律以 Menu.json 與 RolePermissionService 為準。權限常數的「值」刻意保留舊選單名（角色_資料定義 = "資料定義功能"、角色_分類清單 = "分類清單"），不得變更——權限以名稱字串存於 RoleView.TabViewJson，改值等同清空所有既有角色的權限。

  1. KnowledgeExtraction.Share/Helpers/MagicObjectHelper.cs：新增權限常數
  2. 角色_資料定義 = "資料定義功能"
  3. 角色_分類清單 = "分類清單"
  4. KnowledgeExtraction.Business/Services/Other/RolePermissionService.cs：

於 GetRoleListPermissionAllName() 回傳的二維陣列中，在「系統管理」群組之後、「登出」之前 新增一個群組： [角色_資料定義, 角色_分類清單]。（外層索引順序須與 Menu.json 頂層順序一致。）

  1. KnowledgeExtraction.Web/Datas/Menu.json：在「系統管理」(id 3) 之後、「登出」之前插入新主選單，並調整「登出」id 以維持唯一：

  1. 建立頁面與檢視元件（見第八節）。

權限機制說明：本系統授權以選單為基礎。Menu.json 的 name 必須對應 MagicObjectHelper 中的權限常數；RolePermissionService.GetRoleListPermissionAllName() 回傳的二維陣列外層索引 需對應選單頂層順序（首頁、專案管理、系統管理、資料定義、登出）。 角色實際勾選的權限存於資料庫 RoleView.TabViewJson，既有角色若要存取新頁面，須由角色管理頁重新勾選。

十一、編碼需求

  • 所有新增的程式碼檔與本 PRD 文件皆以 UTF-8（繁體中文） 撰寫，不得有亂碼。
  • Menu.json 等含中文之設定檔維持 UTF-8 編碼，確保選單名稱顯示正確。

十二、驗收條件

  1. 選單出現「資料定義 > 分類清單」，且位於「系統管理」之後、「登出」之前；無權限角色看不到、無法進入頁面。
  2. 列表預設依「更新時間」由新到舊排序，最近新增／編輯的分類排在最前面。
  3. 新增分類：名稱必填；名稱與既有分類重複（忽略大小寫、去頭尾空白後）時被拒絕並顯示友善訊息。
  4. 編輯分類：可修改名稱、描述、啟用狀態；名稱唯一性比對排除自身；儲存後該筆回到列表最前方。
  5. 刪除分類：確認後實體刪除。
  6. 啟用狀態可於新增／編輯切換，列表正確顯示啟用／停用。
  7. appsettings.json 版本號於實作建置時 +1（0.2.33 → 0.2.34），相關文件同步更新。
