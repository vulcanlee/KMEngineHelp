產品需求（PRD）

產品需求文件（PRD）：PDF 型 RAG 處理（結構化解析・語意切片・可追溯引用）

  • 文件版本：2.0
  • 文件狀態：部分實作（通用 RAG 已實作；PDF 結構感知處理規劃中）
  • 現行系統版本：1.0.62
  • 首次實作版本：通用 RAG 0.2.123–0.2.128；PDF 走 LLM 轉 Markdown 1.0.54（部分解決「讀懂」面向）；PDF 結構感知藍圖（版面／頁碼／chunk metadata）未實作
  • 最後核對日期：2026/07/25
  • 建立日期：2026-06-19
  • 狀態：部分實作＋設計藍圖。通用知識庫 RAG（嵌入索引／混合檢索／跨來源問答／檢索品質評測）已於階段三 0.2.123–0.2.128 實作；PDF 走 LLM 轉 Markdown（保留表格語法與圖表描述）已於 1.0.54 實作，解決本 PRD「讀懂」面向的一部分；「結構化 PDF 專屬解析（頁碼定位／條款切片／雙欄版面／OCR 分流／chunk metadata）」仍未實作，屬日後增強方向。
  • 編碼：UTF-8（繁體中文，含 BOM）

一、背景與目的

1.1 現況與藍圖界線

已實作現況（0.2.123–0.2.128 起）：PDF 可經文件轉文字轉 Markdown；知識來源可聚合／清洗／蒸餾；通用切塊、嵌入、混合檢索、跨來源問答、出處與檢索品質評測均已提供。現況以 文件轉文字 PRD 與 嵌入索引與混合檢索 PRD 為準。

1.0.54 起的部分進展（PDF 走大語言模型轉換）：MarkItDownSettings:PdfUseLlm 開啟後，PDF 不再經 MarkItDown，而是以 base64 file 內容送 LLM 轉 Markdown。內建提示詞（槽位鍵 文件-PDF轉Markdown）要求：不省略不摘要、表格轉為 Markdown 表格語法並保留每一格、圖片與圖表在原位置以描述段落表達其內容與數值、標題階層對應原文、數學式以 LaTeX 呈現。

這解決了本 PRD「讀懂」面向的一部分——表格結構與圖表資訊不再於純文字抽取中遺失。但它不涵蓋本 PRD 的其餘核心範圍：

  • 沒有 PDF 類型判斷（原生文字型／掃描型／圖文混排）與 OCR 分流
  • 沒有頁碼、章節、條款編號等版面座標與定位資訊
  • 產出仍是單一 Markdown 文字，沒有結構化 chunk metadata（文件ID／頁碼／章節／表格編號／圖片描述）
  • 因此仍無法做到「答得出來源在哪一頁、哪一條」的可追溯引用

規劃中藍圖：本文件後續的條款、雙欄、掃描 OCR、版面分析、結構化 chunk metadata 與專用 Agent 工具鏈尚未實作。

當系統未來要讓 agent 對「一堆 PDF」做 RAG（檢索增強生成）時，最常見也最表面的做法是「先轉文字 → 切片 → 丟向量庫」。但真實專案的 PDF 往往不是乾淨純文字，而是合約、財報、掃描件、技術文件，內含條款、表格、圖表、圖片、雙欄排版、流程圖、程式碼區塊、註腳、頁首頁尾。若直接當一般文本抽取，會出現：

  • 切片斷裂：標題與正文、表格與上下文被機械式切開。
  • 表格結構混亂：欄列關係被攤平成亂序文字。
  • 頁首頁尾重複召回：每頁重複的頁眉頁腳被當成內容反覆檢索。
  • 圖片/圖表資訊遺失：純文字抽取直接丟棄視覺內容。
  • 無法追溯引用：模型即使答對，也說不出來源在哪一頁、哪一章、哪一條。

本系統現況（基準，1.0.62 核對）： PDF 有兩條轉換路徑——markitdown（純文字抽取）或 1.0.54 起的 LLM 轉換（PdfUseLlm，提示詞要求保留表格語法與圖片描述，見 §1.1）——之後使用已實作的通用清洗、蒸餾、切塊、嵌入、混合檢索、問答與評測。兩條路徑產出的都是單一 Markdown：目前仍無 PDF 類型判斷、OCR、版面／頁碼保留及結構化 chunk metadata。系統亦具備多模態 CompleteWithImageAsync／CompleteWithFileAsync，用於圖片解讀與原始檔案模式 LLM 生成，但不等同結構化 PDF RAG。

目標： 在 PDF 進入「清洗 → 蒸餾 → 知識庫」之前，先讓它被正確讀懂、正確切分、正確引用。本 PRD 強化五階段路線圖（匯入 → 清洗 → 蒸餾 → 建立知識庫 → 智慧應用，見 開發建議與路線圖、知識庫架構研究與建議）中的「匯入」環節，並為「階段三：建立知識庫」產出結構化、帶 metadata、可追溯的 chunk。

定位：本 PRD 解決「PDF 型 RAG 的難點」＝讀懂・切分・引用＋評測。向量化檢索本身（embedding 供應商抽象、pgvector、混合檢索＋rerank）屬路線圖階段三，不在本 PRD 重複規格，本 PRD 只負責產出可被階段三索引的結構化 chunk。

二、需求決策

項目決策
處理起點先判斷 PDF 類型，再選解析策略，不一律抽純文字
解析方式原生文字型→文字解析；掃描型→OCR；圖文混排/表格密集/流程圖→版面分析＋視覺/多模態
結構保留盡量保留頁碼、標題層級、章節關係、段落邊界、表格位置、圖片說明、註腳、頁首頁尾
切片方式依語意與結構切片，非固定字數；標題不離正文、條款盡量完整、表格與圖表專處理
chunk 內容每個 chunk 帶 metadata（文件ID/頁碼/章節/條款/表格編號/圖片描述/版本時間/來源類型/Teams）

引用一律可追溯引用（頁碼、章節、原文片段、表格編號），對應 chunk metadata

向量檢索embedding/pgvector/混合檢索＋rerank 沿用路線圖階段三，本 PRD 不重複規格
權控chunk 繼承來源 Teams 標籤，檢索與引用全程套用既有團隊權控

三、功能概述與非目標（YAGNI）

本 PRD 涵蓋（PDF 結構化 ingestion 與可追溯基礎）：

  1. PDF 類型判斷與對應解析策略。
  2. 文件結構還原（頁碼、標題層級、章節、段落、表格、圖片、註腳、頁眉頁腳）。
  3. 語意切片與 chunk metadata。
  4. 表格／圖片／圖表的專門處理。
  5. Agent 工具鏈介面定義（Search / Read Page / Extract Table / Chart Analysis / Citation）。
  6. 可追溯引用機制。
  7. 評測閉環與品質指標。

非目標（本 PRD 不做，屬其他階段或未來延伸）：

  • ❌ Embedding 供應商抽象、向量庫（pgvector）建置、混合檢索＋rerank、完整問答 UI —— 屬路線圖階段三。
  • ❌ 蒸餾為 Wiki 實體頁（知識頁審核） —— 屬路線圖階段二（見 strategy/04）。
  • ❌ 非 PDF 來源（逐字稿、圖片辨識）的結構化 —— 先以 PDF 為主，其餘沿用既有管線。
  • ❌ 取代既有 markitdown 文件轉文字功能 —— markitdown 保留為「快速純文字」備援路徑。

四、PDF 類型判斷與解析策略

處理一律先判斷類型，類型判斷錯，後面切片、檢索、回答都會失真。

類型特徵判斷依據（建議）解析策略
原生文字型說明書、產品文件、論文可抽取文字字元層充足、文字覆蓋率高、影像佔比低直接文字解析＋版面座標
掃描型紙本合約、發票、拍照轉檔幾乎無可抽取文字、整頁為影像先 OCR 再做版面/結構還原
圖文混排/表格密集/流程圖財報、型錄、簡報轉檔影像/圖表佔比高、表格多、雙欄版面分析＋視覺/多模態並用
  • 判斷可採「逐頁」粒度（同一份 PDF 可能混合原生頁與掃描頁），逐頁選策略。
  • 結果記錄每頁的判定類型與信心，供後續除錯與評測。

五、文件結構還原需求

不可把整份文件抽成一大段純文字。生產環境應盡量保留：

  • 頁碼（每段內容必須知道自己在第幾頁）。
  • 標題層級與章節關係（H1/H2/H3… 與所屬章節路徑）。
  • 段落邊界。
  • 表格位置（頁、座標）與表格邊界。
  • 圖片說明（caption）與圖片位置。
  • 註腳。
  • 頁首/頁尾：須辨識並標記，使其不被當成正文重複召回（去重的重要來源）。

關鍵不變量：每一段內容都要記錄它在原文中的位置（頁碼、座標/bbox、章節路徑），這是後續引用、校驗、來源追蹤的基礎。

六、語意切片與 chunk metadata

切片原則：依語意與結構，而非機械式固定字數（如每 500/800 字）。

內容型態切片方式
標題＋正文不拆開；同一標題下的數個段落可組成一個 chunk
合約條款單一條款盡量完整保留為一個 chunk
表格單獨轉為結構化文本成一個 chunk，不當一般段落切
圖表/圖片先生成摘要/描述，連同頁碼與標題一起保存

每個 chunk 應附 metadata：

欄位說明
文件 ID來源 PDF 識別
頁碼起訖頁
章節標題 / 章節路徑所屬標題層級
條款編號 / 表格編號 / 圖片編號結構錨點
內容型態文字 / 表格 / 圖表 / 圖片 / 條款
圖片描述視覺內容摘要（圖表/圖片型 chunk）
版本時間來源版本/匯入時間
來源類型PDF（未來可擴充其他來源）
Teams 標籤繼承來源，供檢索與引用的團隊權控
位置錨點頁、座標/bbox（供引用定位）

可選強化（contextual chunk）： 為每個 chunk 補一段上下文說明（例如「本段來自某合約的付款條款，主要說明尾款支付條件」），讓檢索回來的片段不只是孤立句子，模型能更快理解它在整份文件中的語意角色。

七、表格／圖片／圖表專門處理

  • 表格：轉為結構化文本（Markdown 表格／HTML／CSV／JSON 擇一），保留欄列關係與表頭；附表格編號與頁碼。
  • 圖片：以多模態模型生成視覺描述（既有 CompleteWithImageAsync），存為可檢索文字＋原圖位置。
  • 圖表（chart）：生成摘要與關鍵數據點，連同頁碼/標題保存；不直接忽略。
  • 多模態一律沿用既有 IChatCompletionClient（雲端/地端可切換），不另建新 LLM 客戶端。

八、Agent 工具鏈

到 agent 使用階段，不建議把整份 PDF 一次塞進 context（浪費 token、抓不到重點）。應把 PDF 處理能力拆成多個工具，讓 agent 依問題類型按需呼叫：

工具用途輸入（草案）輸出（草案）
Search PDF片段檢索查詢字串、文件範圍、Teams 範圍命中 chunk 清單（含 metadata 與引用錨點）
Read Page讀取指定頁文件 ID、頁碼該頁結構化內容（文字/表格/圖說）
Extract Table抽取表格文件 ID、表格編號/頁碼結構化表格（含表頭、欄列）
Chart / Visual Analysis理解圖表/圖片文件 ID、圖編號/頁碼圖表摘要與數據點
Citation Source回傳引用chunk ID / 錨點頁碼、章節、原文片段、表格編號

行為原則：簡單問題→先檢索相關段落；跨年度比較/趨勢等複雜問題→定位章節、抽表、歸納；流程圖/圖片問題→交給視覺分析工具，而非只靠文字搜尋。

註：本 PRD 定義工具介面與職責；底層檢索引擎（向量/關鍵字/rerank）由路線圖階段三提供。Search PDF 在階段三前可先以關鍵字/結構查詢實作，階段三接上向量檢索後增強。

九、可追溯引用

  • 回答一律附頁碼、章節、原文片段，必要時附表格編號。
  • 引用錨點對應 chunk metadata（第六節）的位置欄位，確保「說得出來源」。
  • 目的：防止模型憑空編造；即使回答自然流暢，也能被驗證。

十、評測閉環

評測不能只看最終答案對不對，要往下拆成細指標：

指標量測
檢索片段正確率檢索回的 chunk 是否切題
頁碼準確率引用頁碼是否正確
表格解析正確表格欄列是否未錯亂
OCR 漏字率掃描件文字是否漏字
圖表理解正確圖表摘要/數據是否正確
引用支撐度原文引用是否真能支撐最終回答
  • 延伸既有「清洗品質評測」精神（見 資料清洗與品質保證 PRD、清洗品質評測：功能、欄位、價值），建立 PDF-RAG 專屬評測集（標準問題＋預期引用/頁碼/表格答案）。
  • 評測為迴歸基準，量到問題即回頭修解析/切片/工具，形成閉環。

落地方式與現有技術棧對齊：.NET 主體以 System.Diagnostics.Process 呼叫 Python 工具（同 markitdown / yt-dlp 模式），多模態沿用 OpenAI。

十三、相依與風險

  • 外部工具安裝：版面解析/OCR 需額外本機 Python 工具與安裝（沿用 外部工具安裝與路徑設定 的路徑設定模式）。
  • 多模態成本與延遲：圖表/掃描頁走視覺模型，token 成本與處理時間上升，需控管併發與成本。
  • 掃描件品質：OCR 受原稿品質影響，漏字風險→須評測把關。
  • 複雜表格：跨頁、合併儲存格、巢狀表格解析難度高。
  • 座標/頁碼對位：引用準確度依賴位置對位的正確性。
  • 效能與大檔：大型 PDF 解析與切片耗時，需背景化與分段。
  • LLM 未設定降級：未設定 LLM 時，圖表理解/上下文說明等步驟須優雅略過並記註記（沿用清洗管線降級慣例）。

十四、容量與限制

沿用 容量邊界與限制：

  • 單檔上傳上限 1 GB；文件轉文字逾時 600s；多模態單檔 ≤ 20MB（圖表/掃描頁分頁處理以符合）。
  • chunk 大小設上限（避免單 chunk 過大影響檢索），具體值實作時依模型上限定案。
  • LLM/生成逾時沿用既有設定（120s / 300s）。

十五、與現有架構整合

  • 背景管線模式：沿用四條既有管線同構設計 I*Queue（Singleton）→ *BackgroundService → *Processor（Scoped），新增 PDF 結構化解析管線；提供 Cleanup/Retry/Cancel。
  • 團隊權控（資安）：chunk 繼承來源 Teams；檢索/引用在查詢層即過濾（BuildTeamAccessPredicate），非管理員只見「無團隊或與角色團隊交集」。
  • 選單與權限：若新增頁面，須三處同步（MagicObjectHelper、RolePermissionService、Menu.json，位置索引對應）。
  • API：一律 ApiResult<T>，分頁 PagedResult<T>。
  • 儲存：結構化內容存檔、DB 存相對路徑（同清洗結果慣例）。
  • 文件/版本慣例：docs/*.md UTF-8 含 BOM；每次可建置異動 SystemVersion +1。

十六、分階段落地建議

  1. MVP：原生文字型 PDF 的結構還原（頁碼/標題/段落）＋ 語意切片 ＋ chunk metadata ＋ 可追溯引用（Citation Source、Read Page）。
  2. 第二批：掃描型 OCR ＋ 表格結構化（Extract Table）。
  3. 第三批：圖表多模態理解（Chart Analysis）＋ 完整 agent 工具鏈 ＋ PDF-檢索品質評測集。
  4. 銜接階段三：將結構化 chunk 接上向量索引/混合檢索/rerank（路線圖階段三），Search PDF 由關鍵字升級為向量＋關鍵字混合。

十七、驗收條件（可量測）

  1. 系統能對一份 PDF 逐頁判定類型（原生/掃描/混排）並記錄。
  2. 解析輸出保留頁碼、標題層級、章節路徑、段落、表格位置、圖片說明、註腳；頁眉頁腳被標記且不重複召回。
  3. 切片依語意/結構產生，標題不離正文、條款完整、表格獨立、圖表有摘要；每個 chunk 帶完整 metadata 與位置錨點，並繼承 Teams。
  4. 任一檢索結果可回傳頁碼＋章節＋原文片段（＋表格編號）的引用。
  5. 具 PDF-檢索品質評測集，可輸出檢索正確率、頁碼準確率、表格解析、OCR 漏字、圖表理解、引用支撐度等指標。
  6. 全程套用團隊權控；非管理員看不到非授權團隊的 chunk 與引用。
