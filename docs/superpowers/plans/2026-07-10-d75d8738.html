KnowledgeExtraction.AI 安全優先穩定化計畫

現況摘要

健康狀態：DONE_WITH_CONCERNS。工具基線約 8.9/10，但這不是安全分數。

面向結果判讀
Release 建置成功、21 warnings6 個業務程式 nullable 警告；15 個 Razor 產生碼警告
xUnit484/484 通過基礎不錯，但非 migration 程式行覆蓋粗估僅 30.4%，整體 branch coverage 17.8%
文件編碼全數通過UTF-8 BOM 與亂碼護欄有效
套件弱點2 個 HighSQLitePCLRaw.lib.e_sqlite3 2.1.11、Microsoft.OpenApi 2.4.1
CI0 個 workflow文件宣稱已建立 CI，但實際不存在
資料生命週期104 次 CleanTrackingHelper.Cleanscoped DbContext 綁定 Blazor circuit，陳舊追蹤補丁已成為系統性債務

首要原因：

  • PasswordHelper.cs 使用單次 SHA-256；改用 ASP.NET Core PasswordHasher<TUser> 的版本化 PBKDF2 格式，降低資料庫外洩後的離線破解風險。Microsoft PasswordHasher
  • NuGet 掃描結果已推翻舊文件中的「無漏洞」結論；SQLite 套件有 High advisory，而 Microsoft.OpenApi 2.x 至 2.7.4 受影響。SQLite advisory、Microsoft.OpenApi advisory
  • ServiceCollectionExtensions.cs 使用 scoped DbContext；Microsoft 明確指出 Blazor Server circuit 會跨元件共享 scoped context，建議每次操作建立 context。Blazor EF Core guidance

實作變更

第一波：安全缺口

  • 新增 MyUser.MustChangePassword，產生 SQLite 與 SQL Server 雙 migration；既有非空本機密碼標記為必須重設，OAuth-only 帳號不受影響，系統 support 帳號由啟動程序安全升級。
  • 新增 IPasswordHashService，新密碼一律使用 PasswordHasher<MyUser>；舊 SHA-256 只允許驗證至首次登入，登入後強制進入變更密碼頁，成功後改存新格式並清除旗標。
  • API 登入遇到 MustChangePassword=true 時不核發 JWT，回傳明確的密碼重設要求；Web Cookie 登入仍可進入受限的變更密碼流程。
  • BootstrapSettings 新增 SeedSupportAccount。Production 預設停用；啟用時，SupportPassword 若空白、預設值或未達強度即 fail-fast。既有新格式 support 密碼不得每次啟動覆寫。
  • 在資料專案明確引用 SQLitePCLRaw.bundle_e_sqlite3 3.0.3，它改用 SQLite 3.50.4.5 以上的 native package；Web 專案明確引用 patched Microsoft.OpenApi 2.7.5。SQLite bundle 3.0.3

第二波：防退化護欄

  • 修正 6 個業務 nullable 警告；Razor CS8669 僅在 Web 專案針對產生碼做定向抑制，最終 Release 建置必須 0 warning。
  • 兩處靜默 IOException 改為結構化 LogWarning，符合專案「catch 不得靜默」規範。
  • 新增 global.json 鎖定 .NET 10 SDK，以及 .github/workflows/dotnet-ci.yml，在 Windows runner 執行：
  • Release restore/build，warning 視為失敗。
  • 完整 xUnit 與 coverage。
  • scripts/Test-DocsEncoding.ps1。
  • JSON 格式 NuGet 弱點掃描；任何 High/Critical 即失敗。
  • 初始 coverage 門檻設為：排除 migrations/產生碼後 line ≥30%、branch ≥15%，之後只升不降。
  • 校正 docs/planning/03-缺口與風險清單-TODO.md 的 CI、warning、漏洞狀態，改記錄「最後驗證日期＋實際命令」，避免完成勾選永久失真。
  • 釐清 AutoMapper 16 的 production license 警告；本機 PoC 可暫緩購買或替換，但文件不得再描述成「留空即可免費正式使用」。

第三波：局部架構治理

  • 同時註冊 IDbContextFactory<BackendDBContext>，先遷移最容易被背景工作改動的 KnowledgeSourceService、清洗／蒸餾／索引 Processor 與 Wiki 流程；每個 public operation 建立一個 context，私有方法共用該 operation context。
  • 保留其他既有 scoped 服務，避免一次改寫全系統；已遷移區域移除對應 CleanTrackingHelper.Clean，以跨 context 更新測試驗證不再讀到陳舊資料。
  • Production 不再於 Program.cs 自動 migration；Development/Testing 保留便利行為，正式部署使用檢查過的 SQL script 或 migration bundle。EF Core production migration guidance
  • UseConfiguredForwardedHeaders 移至 HSTS、HTTPS redirect、認證前，並由設定列出 trusted proxies/networks。Forwarded Headers guidance
  • 增加三條瀏覽器 smoke tests：登入與強制改密碼、首頁儀表板載入、非管理員團隊資料隔離。
  • 目前維持單機 Channel 背景架構；不導入 RabbitMQ、Hangfire 或獨立 Worker。多實例部署確定後再處理 durable queue 與競態。

介面與資料變更

  • Entity：MyUser.MustChangePassword : bool。
  • 設定：BootstrapSettings.SeedSupportAccount : bool。
  • 內部介面：IPasswordHashService.Hash、Verify、IsLegacyHash。
  • 外部 DTO 不變；只有 /api/Auth/login 在必須改密碼時新增明確拒絕行為。
  • 模型異動必須產生雙 provider migrations，文件同步更新。

驗收測試

  • 舊 SHA-256 使用者可用舊密碼登入一次，但只能前往變更密碼；變更後舊密碼失效、新密碼可登入且儲存值不再是 64 字元 SHA-256。
  • OAuth-only 帳號不被誤導向變更密碼；API 不會為待重設帳號核發 JWT。
  • Production 在 support seed 啟用但密碼空白／弱密碼時拒絕啟動；停用 seed 時不建立或覆寫 support 帳號。
  • dotnet list ... package --vulnerable --include-transitive 不得再列出漏洞。
  • Release build 0 warning、全部測試通過、coverage 不低於基線、文件編碼全綠。
  • SQLite 實際 CRUD／migration 啟動測試通過；SQL Server migrations 可成功產生 idempotent script。
  • 反向代理整合測試驗證 forwarded HTTPS scheme、HSTS 與 redirect 不形成迴圈。

假設與限制

  • 採用未收到 D4 回覆時的推薦方案：「安全優先穩定化」。
  • 部署目標是本機單實例 PoC，因此外部佇列與全面服務拆分不在本輪。
  • 所有既有本機帳號採首次登入強制重設；support 為系統帳號例外，由安全設定值升級。
  • 不修改目前使用者已變更的 AGENTS.md、CLAUDE.md。
  • 每個可建置交付依規範將 SystemVersion 加 1、同步繁體中文 BOM 文件；不自動 commit，只提供建議 commit message。
