知識頁審核與問答疑問釐清及需求（階段三起點）

本文件回應使用者實際操作「知識頁審核」後提出的五個疑問與需求，逐一對照程式現況（已查證）給出答案、缺口與建議方向。 本文件為釐清與規劃性質，不含逐檔逐函式的實作規格；文件內的「建議方向」供下一步討論，非已實作功能。 截至版本 0.2.119（2026-06-26 整理；現況以 0.2.118 程式碼為準）。

【2026-06-27 更新】本文件為階段三起點的釐清快照。其所提的階段三（檢索／RAG／知識庫）、跨來源問答與出處鑽取，均已於 0.2.123–0.2.128 實作完成；下方盤點表已同步標記，釐清內文保留為當時脈絡。

1. 前言與結論速覽

先給總結：使用者的理解大致正確。

  • 蒸餾目前是「一筆已清洗知識來源 → 多筆 Wiki 頁」的扁平結構。頁與頁之間其實已有 [[概念標題]] 互連設計，但沒有首頁／索引／最上層歸納頁，[[link]] 也尚未變成可點擊導覽——所以看起來「不像 wiki」。這是缺口，不是誤解。
  • 蒸餾紀錄的溯源鏈在資料層是存在的（Wiki 頁 → 知識來源 → 成員 → 原始素材 → 檔案），但UI 沒有把它呈現出來。
  • 「問答的參考資料該來自哪一層」的疑慮完全成立，而且是目前最關鍵的設計缺口；現有問答只用單一來源的清洗／原始內容，沒有用到蒸餾頁、也沒有跨來源檢索（RAG）。
  • 「問答依身份決定可見資料」現有權控機制可直接沿用，不需另造新機制。
  • 待辦：階段一（清洗）、階段二（蒸餾）已完成；階段三（檢索/RAG/知識庫）亦已於 0.2.123–0.2.128 完成（本文件撰寫當時尚未開始）。

2. 疑問一：蒸餾「像不像 wiki」？首頁／索引缺口

現況

  • 蒸餾流程：已清洗 KnowledgeSource（Status=已清洗）→ LLM 蒸餾 → 產生多筆 WikiPage（一概念一頁）。
  • 程式：Business/Services/Distillations/DistillationProcessor.cs（ProcessCoreAsync 逐頁寫檔、建紀錄）、DistillationEnhancer.cs（呼叫 LLM、解析 JSON 頁陣列）。
  • 頁與頁的互連其實已經設計了：
  • 資料欄位 WikiPage.LinkTitles 存放本頁以 [[概念標題]] 連到的其他概念（多值分隔字串）。
  • 蒸餾提示詞（Business/Services/Prompts/LlmPromptDefaults.cs 的 DistillationGenerate）已要求 LLM「提到其他概念時以 [[該概念標題]] 互連」並回傳 links。

缺口（使用者理解正確）

  1. 沒有首頁／索引／最上層歸納頁：WikiPage 是扁平清單，沒有一個入口頁能看到「這批知識的最上層分類/主題歸納」。
  2. [[概念]] 未變成可點擊導覽：目前 LinkTitles 只是字串，前端未把它渲染成可點擊、跳到對應 Wiki 頁的連結。
  3. 無連結圖資料表：頁間引用沒有實體化成關聯資料，無法做圖遍歷、反向引用（「哪些頁連到我」）或關係視覺化。

建議方向（供討論，非本次實作）

  • 知識首頁/索引頁：新增一個入口頁，依 Categories（或對概念再做一層歸納）呈現最上層清單，點選後進入該主題的 Wiki 頁集合。
  • [[概念]] 可點擊：渲染 Markdown 時把 [[標題]] 解析為連結，以 Title 比對對應 WikiPage 後跳轉（找不到時標示為「待建立概念」）。
  • （選配）連結關係實體化：把頁間引用存成關聯資料表，支援反向引用查詢與關係圖檢視。

3. 疑問二：蒸餾紀錄能不能回溯到來源與原始檔（溯源 lineage）

現況：資料層的溯源鏈是完整的

WikiPage（蒸餾頁）
  └─ KnowledgeSourceId（外鍵，FK，來源刪除時連帶刪頁）
       ↓
KnowledgeSource（知識來源清單）
  └─ Items：List<KnowledgeSourceItem>（聚合成員）
       ↓
KnowledgeSourceItem
  └─ ItemType + ItemId（軟參照，指向下列三種原始素材之一）
       ↓
MediaTranscription / DocumentExtraction / ImageRecognition（原始素材）
  └─ 檔案路徑欄位：
       MediaRelativePath / OriginalMediaRelativePath（音訊/影音）
       SourceRelativePath（文件原始檔）
       ImageRelativePath（圖片原始檔）
  • 也就是說：從任一蒸餾頁，理論上可一路回溯到它來自哪一筆知識來源、再到哪個原始音訊／影音／文件／圖片檔。
  • 程式依據：AccessDatas/Models/WikiPage.cs（KnowledgeSourceId）、KnowledgeSource.cs（Items）、KnowledgeSourceItem.cs（ItemType/ItemId）、三個原始素材 Model。

缺口

  1. UI 沒有呈現這條鏈：使用者在蒸餾頁看不到「我來自哪筆來源、哪個原始檔」。
  2. 原始素材無反向指標：MediaTranscription 等不知道自己屬於哪個 KnowledgeSource，必須反查 KnowledgeSourceItem 才能得知。
  3. ItemId 是軟參照：無資料庫 FK 完整性保證（設計上為了跨三型別共用）。

建議方向（供討論，非本次實作）

  • 在 Wiki 頁／問答答案旁顯示「來源出處」面板：列出所屬知識來源 → 構成它的原始素材 → 可下載的原始檔連結（沿用既有下載權控，見第 5 節）。
  • （選配）為原始素材補上「所屬知識來源」的反向檢視或關聯，減少反查成本。

4. 疑問三：問答時，送進 LLM 的參考資料該用哪一層？（核心議題）

使用者以「員工手冊：入職滿 3 年可享什麼健檢福利」為例，擔心提示詞的參考資料來源會影響答案品質。這個疑慮成立。

現況

  • 系統已有問答：Business/Services/DataAccess/KnowledgeSourceChatService.cs ＋ Web/Components/Pages/KnowledgeSources/KnowledgeSourceChatPage.razor（ChatGPT 風格、多輪、串流）。
  • 但目前限制：
  • 只針對單一知識來源問答；
  • 參考資料二選一：清洗後內容（GetCleanedContentAsync）或原始彙整內容（GetOriginalContentAsync）；
  • 完全沒有用到蒸餾 Wiki 頁；
  • 沒有向量化／embedding／RAG，無法跨來源檢索。
  • 因此「員工手冊」這種需要跨多個來源、語意檢索的問答，目前架構做不到。
  • Prompt 組法：四層解析（單次操作→DB→appsettings→程式 fallback），system = 系統提示 ＋ 詳簡指示 ＋ 參考資料。

三層資料來源比較（不預設答案，供使用者決策）

面向原始檔／原始彙整內容清洗後內容蒸餾 Wiki 頁
資訊完整度最高（含所有細節）高（保留資訊價值）中（精煉、可能省略細節）
雜訊多（口語、重複、雜訊）低（已去重去雜訊）最低（重組為知識）
Token 成本最高中高低
去敏/遮罩可能未遮罩（風險）已遮罩個資/機密已遮罩（承自清洗）
概念化/可推理低中高（一概念一頁）
跨來源彙整能力弱弱較強（概念可互連）
可追溯到原始事實強（本身就是原始）中較弱（已重組，需回溯）
適合的問題型態需逐字、原話、細節佐證需完整事實但要乾淨需概念、定義、跨主題歸納

對「健檢福利」例子的解讀

  • 若答案需要精確條款數字（滿 3 年 = 哪一級健檢、補助金額），偏向需要清洗/原始層的事實佐證；
  • 若使用者問的是概念性、跨章節問題（福利制度概覽），蒸餾層更適合做導引。
  • 單用蒸餾層可能遺失關鍵數字；單用原始層則雜訊多、token 大、且有未遮罩風險。

建議方向（折衷，供討論）

  • 分層／混合檢索：以蒸餾頁做概念導引與命中定位，再用清洗/原始內容做事實佐證與引用（答案附出處）。
  • 待決策點（需使用者拍板）：
  • 問答是單一來源還是跨來源知識庫？
  • 主要檢索層選哪一層、是否採混合？
  • 答案是否一定要附出處（可追溯到原始檔）？
  • 是否導入向量索引/embedding（這是階段三的核心工作）。

5. 疑問四：問答時依使用者身份決定可見資料，如何設計

現況：權控機制已存在且已套用

  • 介面：Business/Services/Other/IRecordAccessScopeProvider.cs（實作 Web/Auth/RecordAccessScopeProvider.cs，同時支援 Blazor 與 JWT/Cookie 兩情境）。
  • 工具：Business/Helpers/TagStringHelper.cs
  • BuildTeamAccessPredicate（SQL 層，把權控推到資料庫查詢）；
  • IsTeamAccessible（記憶體層，單筆判斷）。
  • 規則：管理員全可見；非管理員只能看「無團隊（公開）或與其角色團隊有交集」的紀錄。
  • 已套用於 KnowledgeSourceService、WikiPageService 的各查詢與內容讀取，以及檔案下載 Controller；現有問答的參考資料讀取（GetCleanedContentAsync/GetOriginalContentAsync）也已過權控。

結論：未來 RAG 不需新機制，沿用即可

未來跨來源 RAG 的權控插點：

使用者提問
  → 向量/關鍵字檢索取得候選片段（來自蒸餾頁/清洗/原始）
  → 依該使用者的 RecordAccessScope 逐筆過濾命中（用 IsTeamAccessible 或在查詢層 BuildTeamAccessPredicate）
  → 僅以「有權」片段組成 prompt 送 LLM
  → 答案附出處（出處本身也須受同一權控）

風險提醒

  • 跨來源檢索時，務必逐筆過濾，避免把使用者無權的內容混進 context（context 洩漏＝資安漏洞）。
  • 答案顯示的出處/原始檔下載也要受同一權控，不能繞過。
  • 多輪對話的歷史 context 已在初次載入時過權控；若改為動態檢索，每輪檢索都要重新套 scope。

歷史釐清項（階段三已完成，保留當時決策脈絡）

  1. 目標問答情境：已以AI 知識問答與 檢索品質評測支援跨來源檢索；後續仍可用真實 PoC 問題補評測集。
  2. 是否跨來源：已採整個知識庫跨來源檢索，並於檢索層逐筆套團隊權控。
  3. 主要檢索層：已採 Wiki 與 Cleaned 混合索引；答案附出處時回到命中 chunk 與來源。
  4. 向量庫選型偏好：已沿用現有 OpenAISettings 雲端/地端嵌入設定。
  5. 答案是否必附出處：AI 知識問答已提供來源出處與鑽取；蒸餾 Wiki 頁本身的來源面板仍可視需求補強。
  6. PoC 樣本：仍需使用者提供真實素材做人工驗證，追蹤於 planning/07 第五階段。
