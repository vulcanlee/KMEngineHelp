行銷與提案

同一個問題問到第三次，你就不敢問了

新人卡住的地方，從來不是技術太難，是不知道該問誰、還敢不敢再問一次。

那個你已經在椅子上坐了四十分鐘的下午

蔡明翰到鼎峰系統整合（示範情境）報到第三週。

那天下午他卡在一個環境設定上。文件他看過了，寫得沒錯，但照著做就是跑不起來。他在網路上搜了半小時，找到的答案都是通用情境，跟公司內部這套接法對不上。

他把頭轉向坐斜對面的資深工程師老陳。老陳戴著耳機，螢幕上開著三個視窗，正在處理一個看起來很急的東西。

蔡明翰把頭轉回來。

他打開內部群組，訊息打到一半又刪掉。因為這個問題，他上週三問過一次類似的，老陳當時很好心地講了三分鐘。他記得那三分鐘裡有一句「這個之前有跟你說過齁」——老陳講得很輕鬆，沒有責備的意思，但那句話在他腦子裡留下來了。

於是他繼續自己試。四十分鐘後試出來了，用的方法後來被 code review 說「這樣可以但不是我們的做法」。

那天他學到的最大一課，其實不是那個環境設定。是在一個新環境裡，「問」這件事是有成本的，而且成本會隨著次數往上加。

新人真正的瓶頸從來不是能力，是提問額度——你心裡默默給自己設的那個每週只能問三次的上限。

這不是你臉皮薄，是公司的知識只存在人身上

先把一件事講清楚：這不是你的問題，也不是老陳的問題。

你會需要問人，是因為公司裡真正有用的東西，大部分沒有被寫下來。

寫下來的那些是流程——安裝步驟、環境需求、專案結構。這些文件通常存在，而且大致正確。

沒寫下來的是判斷——為什麼我們不用那個套件？這個錯誤訊息看起來像 A 問題，為什麼實際上通常是 B 造成的？這段設定為什麼要多加一行？哪個服務重啟前一定要先做什麼？

這些沒有一條寫得成文件。它們是資深同事三年、五年一次一次踩出來的，而且他們自己往往不覺得那算「知識」，只覺得那是常識。

於是知識的傳遞方式變成：新人卡住 → 打斷資深同事 → 口頭講三分鐘 → 講完就消失。這對新人來說有心理成本，對資深同事來說有時間成本，而最浪費的是——同樣那三分鐘，明年新人來了還要再講一次。

你缺的不是勇氣，是一個不用消耗人情就能問到答案的地方。

老陳那三分鐘，本來可以留下來

這正是知識庫系統在解決的事。它不是雲端硬碟，也不是把檔案丟給 AI 就算數——它是一條把「原料」煉成「可查詢知識」的產線。

上週三老陳講的那三分鐘，如果有被錄下來（或是當時的群組訊息有被收進來），原料大概長這樣：

喔那個啊，你不能直接用預設的連線字串啦，我們測試機那台要走內網，
帳號是 devuser 密碼 Dev@2024 那組，然後最重要的是那個 timeout 要拉到 60，
預設 30 秒會在資料量大的時候斷掉，之前有人被這個雷過三次。
啊還有喔，改完設定一定要先停服務再重啟，直接重啟會鎖檔。

系統把它送進清洗程序——去掉贅字、遮蔽敏感資訊、分類、摘要——出來是這樣：

## 測試環境資料庫連線設定

- **連線來源**：測試環境須走內網連線，不可使用預設連線字串（憑證已遮罩）。
- **必要調整**：timeout 需由預設 30 秒調整為 60 秒，否則資料量大時會中斷。
- **操作順序**：修改設定後須先停止服務再重新啟動，直接重啟會造成檔案鎖定。

再進一步蒸餾，它變成一頁可以互相連結的概念頁：

# 連線 timeout 過短導致查詢中斷
預設 timeout 在大量資料查詢時不足，是測試環境最常見的失敗原因。
相關步驟參見 [[測試環境連線設定]] 與 [[服務停止與重啟順序]]。

於是那個下午，蔡明翰不需要看老陳的耳機在不在。他打一句話進系統：

「測試環境連線一直斷掉怎麼辦？」

得到的是：

通常是 timeout 設定過短，預設 30 秒在資料量大時會中斷，建議調整為 60 秒。另外設定修改後須先停止服務再重啟，避免檔案鎖定。 〔出處：內部技術指導紀錄 → 原始逐字稿〕

有兩件事值得注意。第一，答案後面附著出處，你點下去可以看到當初是誰、在什麼情境下講的。這對新人特別重要——你敢照著做，是因為你知道這不是網路上不知道哪來的答案，是你們公司自己的做法。第二，測試環境的帳號密碼一個都沒有出現，它們在進入知識庫之前就被遮掉了。

你的第三次提問，可以不必再消耗任何人的耐心。

那我查到的東西，會不會其實我不該看

新人常有的另一個顧慮是反過來的：既然什麼都問得到，那我是不是會不小心看到不該看的？

不會，而且這套系統把它做成兩條不能違反的鐵則。

一條是遮蔽失敗，整筆就算失敗。帳號、密碼、客戶個資這類東西不是「盡量遮」，而是只要沒遮乾淨，整筆內容直接退回重跑，絕不放行到下游。所以你查到的答案裡不會出現憑證——你需要的是「timeout 要改成 60」這個判斷，不是那組密碼。

另一條是權限綁在團隊上，每一次查詢的當下驗證。你查得到的，就是你這個角色本來就該看得到的；不屬於你的，你連它存不存在都問不出來，系統只會回「查無資料」。

所以你可以放心地問任何問題——問得到的，就是你可以用的。

那知識庫裡的答案，會不會是三年前的做法

會過期，如果沒有更新機制的話。所以更新被設計成一條可以重跑的產線。

做法改了、設定變了、套件升級了，承辦人對原檔案按「上傳新版本」，系統自動建立版本鏈：新版標成 v2，舊版標示「已被取代」，版本歷史可回溯稽核，接著自動重新清洗、重新蒸餾、重建索引。

這對新人的意義很實際：你查到的是現在的做法，不是被 code review 打槍的那種「可以但不是我們的做法」。

上手期會變成什麼樣子

以一般知識管理導入經驗為基準，新人的上手週期可以從一到兩個月縮短到兩三週，大約減半；同類問題的重複發問下降六成以上。這是合理的導入目標與期望值，並非實測保證值，實際成效取決於團隊累積了多少素材與使用習慣。

不過這些數字對你來說可能太抽象。具體會變的是這幾件事：

你卡住的時候，第一個動作從「看看老陳有沒有空」變成「先問一次系統」。問完還是不會，你再去找人——而那時候你問的問題會漂亮很多，因為你已經知道八成，只缺最後那兩成的判斷。

老陳也會發現，他不用再對第三個新人講同一段話了。他講一次，被收進去，之後每一個新人都問得到。

這才是資深同事真正該被使用的方式：講一次，留下來，而不是每年重講一次。

你早晚會變成那個被問的人

再過兩年，坐在那個位子上、戴著耳機、被新人猶豫著要不要打斷的人，會是你。

到那時候你會希望，你講過的那些「這個要注意一下喔」，是隨著你的耐心一次一次消耗掉，還是被留在一個地方，讓下一個蔡明翰在他自己的那個下午，一分鐘就查到。

如果你想看看團隊的狀況，歡迎來聊聊：你們手上有哪些技術文件、指導紀錄與內部討論，新人最常卡在哪一類問題，可以從哪裡開始試點，我們可以一起評估導入範圍與 PoC 規模。
