全部文件 ／ 系統架構

系統架構

資料生命週期與維護（更新、刪除、級聯與孤兒）

文件目的

集中說明本系統「來源素材 → 知識來源 → 清洗 → 蒸餾 → 索引 → 問答」全鏈的資料如何被轉換、彼此如何關聯、更新與刪除時會連動什麼、哪裡會產生孤兒或不一致，以及目前作法的優缺點與改善建議（含可實作清單）。

  • 白話版與操作情境見 新手完整操作指南 §十六：資料維護與生命週期。
  • 實體與 DbSet 的權威定義見 資料模型與資料庫；兩層內容分工見 Wiki 與 Cleaned 的角色差異；版本化/時效狀態機見 知識型態抽象 × 版本化 × 時效性。

本文件描述現況與改善建議。標示「建議」「Backlog」的段落尚未實作，請勿當成既有行為。

1. 全景：六站資料流與紀錄轉換鏈

每一站的「使用者動作 → 服務/佇列 → 處理器/AI → 產出紀錄與檔案」：

站觸發（按鈕/動作）服務 → 佇列 → 背景服務處理器 / 轉換者產出紀錄（Entity）與檔案內容性質
①音訊「新增」上傳檔案或貼影片連結（自動處理）MediaTranscriptionService.AddAsync/AddUrlSourceAsync → TranscriptionQueue → TranscriptionBackgroundServiceTranscriptionProcessor → OpenAITranscriptionClient（gpt-4o-transcribe）MediaTranscription；原檔於 MediaUploadPath（連結另存 OriginalMediaPath），逐字稿 .txt 於 TranscriptionFilePath忠實轉錄
①文件「新增」或「批次上傳壓縮檔」（自動處理）DocumentExtractionService.AddAsync/AddBatchFromZipAsync → DocumentExtractionQueue → DocumentExtractionBackgroundServiceDocumentExtractionProcessor → MarkItDownConverter（外部 CLI，非 AI）DocumentExtraction；原檔於 DocumentExtractionUploadPath，Markdown 於 MarkdownFilePath忠實萃取
①圖片「新增」上傳後須手動按「解讀圖片」才處理ImageRecognitionService.AddAsync（僅建列、狀態「未解讀」）→ EnqueueRecognitionAsync → ImageRecognitionQueue → ImageRecognitionBackgroundServiceImageRecognitionProcessor → OpenAIChatCompletionClient.CompleteWithImageAsync（gpt-5.4 視覺）ImageRecognition；原圖於 ImageUploadPath，解讀文字 .txt 於 ImageRecognitionTextPathAI 詮釋（依提示詞）
②聚合/knowledge-sources「新增」+「管理成員」KnowledgeSourceService.AddItemAsync（僅收 Status==已完成 的素材）—（不轉換內容，只建立成員關聯）KnowledgeSource + KnowledgeSourceItem（軟參照素材）關聯，不改內容
③清洗「清洗」（選清洗規則設定）KnowledgeSourceService.TriggerCleaningAsync → CleaningQueue → 背景服務CleaningProcessor（KnowledgeSourceContentAggregator 彙整原文 → CleaningEnhancer 去重/遮罩/分類/摘要）清洗後 Markdown 於 CleanedSourcePath；KnowledgeSource.CleanedContentRelativePath/CleanedAt；狀態→已清洗（低信心→待審核）AI 轉換
④蒸餾「蒸餾」（已清洗後才可）WikiPageService.TriggerDistillationAsync → DistillationQueue → 背景服務DistillationProcessor → DistillationEnhancer（一概念一頁、[[連結]]）多筆 WikiPage（內容於 WikiOutputPath）；完成即自動排入索引AI 轉換
⑤索引「建立索引／重建索引」（蒸餾後自動觸發）；「全量重建索引」KnowledgeSourceService.TriggerEmbeddingIndexAsync/TriggerEmbeddingIndexAllAsync → EmbeddingIndexQueue → 背景服務EmbeddingIndexProcessor（Chunker 切塊 → IEmbeddingClient 嵌入）VectorEmbedding（SourceLayer＝Cleaned 或 Wiki；含 ChunkText/Embedding/AnchorRef/ContentHash）向量化（切塊自上游文字）
⑥問答/knowledge-base-chat 提問KnowledgeBaseChatService.RetrieveAsync（改寫→權控→混合檢索）RetrievalService（向量+關鍵字融合）→ LLM 生成僅檢索 VectorEmbedding；每輪寫入 KnowledgeBaseQueryAudit（只存長度/分數/命中 id）讀取 AI 轉換後內容

補充：音訊與文件另有可選的「依提示詞產生」二次 LLM 加工（LlmGenerationService / DocumentLlmGenerationService，gpt-5.4），產物另存 GeneratedContentPath，屬旁支、不進入清洗/蒸餾主鏈。

重要不變量：所有大宗內容（逐字稿、Markdown、清洗結果、Wiki 頁）只存檔案，DB 僅存相對路徑；唯 VectorEmbedding.ChunkText/Embedding 內嵌於 DB。

2. 實體關聯與級聯設定

2.1 文字 ER 圖

[MediaTranscription] [DocumentExtraction] [ImageRecognition]   ← 三管線素材（各自資料表）
        └────────── 軟參照 (ItemType + ItemId，無硬 FK) ──────────┐
                                                                  ▼
                                     [KnowledgeSourceItem] ──FK KnowledgeSourceId (Cascade)──► [KnowledgeSource]
                                                                                                     │ Id
                                    ┌──── FK KnowledgeSourceId (Cascade) ─────────────┬─────────────┘
                                    ▼                                                 ▼
                               [WikiPage]                                      [VectorEmbedding]
                               版本鏈：PreviousVersionPageId /                  KnowledgeSourceId (Cascade FK)
                               SupersededByPageId（自我參照）                    WikiPageId (Restrict FK，可空) ─► WikiPage.Id
                                    ▲                                          SourceLayer = "Cleaned" | "Wiki"
                                    └──── Wiki 層 chunk 參照對應 Wiki 頁 ──────────┘

[KnowledgeBaseQueryAudit]  ← 無 FK，僅稽核每輪問答

2.2 FK 與 DeleteBehavior（BackendDBContext.OnModelCreating）

OnModelCreating 先把所有 FK 預設為 Restrict，再逐一覆寫為 Cascade：

關係FK 欄位DeleteBehavior說明
KnowledgeSource → KnowledgeSourceItemKnowledgeSourceIdCascade刪來源連動刪成員列
KnowledgeSource → WikiPageKnowledgeSourceIdCascade刪來源連動刪其 Wiki 頁
KnowledgeSource → VectorEmbeddingKnowledgeSourceIdCascade刪來源連動刪其向量（跨來源檢索/權控的根）
WikiPage → VectorEmbeddingWikiPageId（可空）Restrict（刻意）避免 SQL Server 多重串聯路徑；Wiki 頁向量由索引管線顯式清理
KnowledgeSourceItem → 素材ItemType+ItemId無 FK（軟參照）只以字串型別＋Id 指向素材，DB 不強制關聯

2.3 級聯方向總結

  • 往下（刪 KnowledgeSource）＝完整級聯：KnowledgeSourceService.DeleteAsync 先手動刪實體檔（清洗 .md、各 Wiki .md），再 Remove(source)，EF Cascade 連動刪 KnowledgeSourceItem/WikiPage/VectorEmbedding 的 DB 列。此方向乾淨、無殘留。
  • 往上（刪某筆素材）＝無級聯：MediaTranscriptionService.DeleteAsync（及 DocumentExtractionService/ImageRecognitionService 同型）只刪自己的檔與列，完全不觸及 KnowledgeSourceItem（因無硬 FK）。→ 產生孤兒與下游過時，見 §5。

3. 內容誰轉換、是否失真、問答用哪層、可否追溯

3.1 各站「原文保留 vs AI 轉換」

產物轉換者忠實原文？
音訊逐字稿gpt-4o-transcribe（ASR）忠實轉錄（口語轉文字，含繁簡轉換）
文件 MarkdownMarkItDown CLI（非 AI）忠實萃取（確定性轉檔）
圖片解讀文字gpt-5.4 視覺AI 詮釋（依提示詞產生，非原始像素文字）
清洗內容CleaningEnhancer（LLM）AI 轉換：去重、遮罩（刻意抹除機密）、分類、摘要
Wiki 頁DistillationEnhancer（LLM）AI 轉換：重組為概念頁

3.2 問答（RAG）用的是哪一層、會不會失真

  • 問答只檢索 VectorEmbedding，其 SourceLayer 只有 Cleaned（清洗內容切塊）與 Wiki（蒸餾頁切塊）兩種——都是 AI 轉換後的文字，原始素材文字不直接進入檢索。組裝上下文時 Wiki 層優先、Cleaned 層次之。
  • 因此檢索層內容必然經過摘要/重寫，且遮罩會刻意抹除敏感片段，逐字保真度在檢索層本就會下降。系統以三點緩解：
  • 同時索引 Cleaned 與 Wiki 兩層（Cleaned 較貼近原文），非只用最濃縮的 Wiki。
  • 可追溯到原始檔（見 3.3），真值永遠一鍵可達。
  • 另提供單一來源對話（KnowledgeSourceChatService）的「對原始來源對話」模式，直接餵未清洗彙整原文（非 RAG、非嵌入、單來源）。

3.3 出處追溯鏈

每個命中 chunk 帶 KnowledgeSourceId、SourceLayer、WikiPageId、AnchorRef，組成 KnowledgeBaseSourceAdapterModel。UI 顯示「出處」面板（標題、層別徽章、錨點、片段），並提供「鑽取來源」展開成員、直接「下載原始檔」：

答案 → 命中 chunk(VectorEmbedding) → KnowledgeSourceId → KnowledgeSourceItem 成員 → 原始素材檔
                                     └ AnchorRef 定位章節/段落

下載端點：/api/MediaTranscription/{id}/source、/api/DocumentExtraction/{id}/markdown、/api/ImageRecognition/{id}/image。

4. 更新與重處理機制

4.1 更新既有素材：上傳新版本（版本鏈，0.3.21 起）；無就地換檔

  • 素材（三管線）無就地二進位換檔：要更新一份檔案的新版本，改按每列的「上傳新版本」（AddNewVersionAsync），系統會建立版本鏈（VersionNumber/IsLatest/PreviousVersionId/SupersededById）：新版沿用原標題/描述/分類/團隊，舊版標為 IsLatest=false＋SupersededById；並把引用舊版的知識來源成員自動重指到新版、所屬來源設 ContentStale（KnowledgeSourceMaintenanceHelper.RepointOwningSourcesToNewVersionAsync）。音訊/文件新版自動入列處理，圖片新版維持「未解讀」需手動解讀。主清單只顯示每個版本鏈的最新版（三素材 GetAsync 加 Where(x => x.IsLatest)，0.3.28 起）；舊版與其原始檔都完整保留、不刪除，經每列「版本歷史」按鈕（GetVersionHistoryAsync 沿 PreviousVersionId/SupersededById 列出 v1…vN、依版本序號遞增、套用團隊權控）檢視與下載（音訊＝來源檔＋逐字稿、文件＝Markdown、圖片＝原圖）。
  • 仍可就地編修「萃取後的文字」（ContentEditDialog → Update*ContentAsync，覆寫同一檔、更新 UpdatedAt，並標記所屬來源過時，見 §4.2）。
  • KnowledgeSource.UpdateAsync 只更新中繼資料（標題/說明/分類/團隊）；當 Teams 變更時以 ExecuteUpdateAsync 把標籤傳播到子 WikiPage/VectorEmbedding（只改標籤、不重嵌入）。

4.2 過時以旗標被動追蹤、須手動重跑

  • KnowledgeSource.ContentStale：在成員新增/移除/排序（AddItemAsync/RemoveItemAsync/MoveItemAsync）、刪素材清孤兒、編修素材文字、以及上傳素材新版本自動重指成員時被設為 true，僅為提示旗標、不自動重處理，重清洗後清除。
  • 可於「資料一致性巡檢」頁一覽並批次重跑（見 §5-B）。

4.3 重處理按鈕各做什麼

動作服務行為刪除舊資料？
重清洗TriggerCleaningAsync/RetryCleaningAsync重跑清洗、覆寫清洗 Markdown覆寫同檔
重蒸餾WikiPageService.TriggerDistillationAsync/RetryDistillationAsync不刪舊 Wiki：建新版本、supersede 舊 current（保留供 as-of/稽核）、舊向量 IsCurrent=false否（版本化保留）
清空蒸餾ClearDistillationAsync刪光所有 Wiki 頁 + Wiki 層向量，重置為「待蒸餾」是（保留來源、清洗、Cleaned 層向量）
重建/全量索引TriggerEmbeddingIndexAsync/TriggerEmbeddingIndexAllAsync增量冪等：以 ContentHash 比對，刪不再需要的 chunk、新增新 chunk、未變者不重嵌入只刪差集
Wiki 編修/核准UpdateContentAsync/ApproveAsync → TryEnqueueSourceReindexAsync唯一自動關閉過時的路徑：編修/核准 Wiki 後自動重排索引增量

5. 缺口分析與現況（含已修正項）

A、C 已於 0.3.20 修正；B 已提供巡檢頁大幅緩解；D 仍為選配、未實作。實作細節見 §6 與 變更紀錄。

缺口 A — 刪素材產生孤兒成員 + 下游過時（✅ 已修正，0.3.20）

  • 原問題：刪 MediaTranscription/DocumentExtraction/ImageRecognition 只刪自己；因 KnowledgeSourceItem 軟參照無 FK，成員變孤兒、下游過時，僅在顯示時標「（來源已不存在）」。
  • 現況（已修正）：三個素材 DeleteAsync 在刪除前呼叫 KnowledgeSourceMaintenanceHelper.MarkOwningSourcesStaleAsync(..., removeOrphanItems: true)，於同一交易移除孤兒成員並將所屬來源設 ContentStale=true。此即原建議方案 (a)。
  • 仍需人工：ContentStale 為提示，實際重跑清洗仍由使用者決定（可用巡檢頁一鍵批次，見 §6）。

缺口 B — 孤兒清理／一致性巡檢（✅ 已提供巡檢頁，0.3.20）

  • 原問題：無孤兒清理或一致性一覽，只能人工逐筆處理。（EmbeddingIndexProcessor 的「清除孤兒 chunk」僅單一來源重索引時對 VectorEmbedding 對帳，範圍不同。）
  • 現況（已緩解）：新增 admin 頁 /data-consistency（DataConsistencyService）：唯讀列出孤兒成員與過時來源，並可「清除所有孤兒成員」與「重新清洗所有過時來源」（逐筆重用帶權控的 TriggerCleaningAsync）。屬原建議 (a)「唯讀盤點 + 一鍵重跑」。
  • 未做：定時自動修復（誤刪風險高，暫不採用）。

缺口 C — 素材內容編修不設過時（✅ 已修正，0.3.20）

  • 原問題：就地改逐字稿/Markdown/解讀文字後，下游不知情、連旗標都不設。
  • 現況（已修正）：UpdateTranscriptContentAsync/UpdateMarkdownContentAsync/UpdateRecognitionTextContentAsync 落檔後呼叫同一 helper（removeOrphanItems: false），將所屬來源設 ContentStale=true（成員保留），來源頁與巡檢頁即會提示需重跑。不自動重跑（避免非預期成本）。

缺口 D — 素材無版本鏈（✅ 已修正，0.3.21）

  • 原問題：WikiPage/VectorEmbedding 有版本化，但素材無版本鏈，重傳＝新紀錄、難追「同一份檔的歷次版本」。
  • 現況（已修正）：三素材各加 VersionNumber/IsLatest/PreviousVersionId/SupersededById；每列「上傳新版本」（AddNewVersionAsync）建立版本鏈、取代舊版，並自動把引用舊版的成員重指到新版＋標記來源過時（見 §4.1）。屬「記錄版本＋自動接手」。0.3.28 起主清單只顯示最新版，舊版經每列「版本歷史」檢視存取（見 §4.1）。

6. 實作清單狀態

優先項目狀態影響範圍需 migration？
P1-A刪素材時清孤兒 KnowledgeSourceItem 並將所屬來源設 ContentStale✅ 已完成（0.3.20）三素材 DeleteAsync + KnowledgeSourceMaintenanceHelper否
P1-B一致性巡檢：唯讀報表列出孤兒/過時來源 + 一鍵清除/重跑✅ 已完成（0.3.20）DataConsistencyService + /data-consistency 頁否
P2素材內容編修後設 ContentStale✅ 已完成（0.3.20）三素材 Update*ContentAsync + helper否
P3素材版本化✅ 已完成（0.3.21）三素材 Entity/Adapter + AddNewVersionAsync + 三 View + 雙 migration是（雙資料庫各一，已產生）

實作核心：KnowledgeSourceMaintenanceHelper 的 MarkOwningSourcesStaleAsync（刪素材/編修共用）與 RepointOwningSourcesToNewVersionAsync（上傳新版本用），皆不自行 SaveChanges、與呼叫端同一交易原子提交；巡檢由 DataConsistencyService.GetReportAsync/CleanupOrphansAsync 提供；版本鏈由三素材 AddNewVersionAsync 建立（migration AddSourceVersionChain 雙資料庫）。
