系統架構

資料模型與資料庫

文件目的

說明本專案的資料庫採用方案、BackendDBContext 結構、各 Entity 與彼此關聯，以及 Migration 與啟動 Seed 的行為。

1. 資料庫採用方案

  • 預設：SQLite，連線字串由 MagicObjectHelper.GetSQLiteConnectionString(databasePath) 動態組成；databasePath 來自 appsettings.json 之 SystemSettings.ExternalFileSystem.DatabasePath（預設 C:\temp\KnowledgeExtraction\DB）。
  • 正式：SQL Server；可透過 SystemSettings.DatabaseProvider=SqlServer 切換，並使用 KnowledgeExtraction.AccessDatas.SqlServerMigrations 作為專用 migration assembly。
  • Collation：Chinese_Taiwan_Stroke_CI_AS（於 BackendDBContext.OnModelCreating 統一指定）。

2.2 全域刪除政策

OnModelCreating 預設將所有外鍵的 DeleteBehavior 設為 Restrict：父資料表若仍有子資料時不可被強制刪除。

2.3 Cascade 例外

下列三組「主表 → 附件表」改為 DeleteBehavior.Cascade，主表刪除時連動清除附件紀錄：

Project         → Project.Files          → ProjectFile.ProjectId
MyTask          → MyTask.Files           → MyTasFile.MyTasId
Meeting         → Meeting.Files          → MeetingFile.MeetingId
KnowledgeSource → KnowledgeSource.Items  → KnowledgeSourceItem.KnowledgeSourceId
KnowledgeSource → WikiPage               → WikiPage.KnowledgeSourceId
KnowledgeSource → VectorEmbedding        → VectorEmbedding.KnowledgeSourceId

VectorEmbedding → WikiPage（FK WikiPageId，可空）刻意維持 Restrict（非 Cascade），以避免 SQL Server 多重串聯路徑；Wiki 頁對應向量由索引管線於重蒸餾/編修時顯式清理。

⚠️ 知識圖譜六表刻意不建立任何 WikiPage 外鍵（同樣是為了避開 SQL Server 多重串聯路徑）：

  • GraphEdge.SourceWikiPageId / GraphEdge.TargetWikiPageId 是純索引整數，無 FK、無導覽屬性——它們只是給遍歷用的索引鍵。邊由 GraphEdgeService.RebuildForSourceAsync 於蒸餾完成、Wiki 頁核可／編修時冪等重建，因此不需要 Cascade 也不會累積孤兒。
  • GraphNode.WikiPageId 是軟錨（指向該實體的錨定 Wiki 頁），同樣無 FK。
  • GraphEntityAlias 與 GraphJobState 既無 FK 也無 Teams，屬全域治理資料。

因此刪除 Wiki 頁不會被圖譜資料擋住，也不會連動清除圖譜列；圖譜的一致性靠「檢索期只採計錨定到現行 Wiki 頁的三元組」與重建機制維持，而非資料庫層約束。

KnowledgeSourceItem 為軟參照（以 ItemType＋ItemId 指向 MediaTranscription/DocumentExtraction/ImageRecognition，不做硬 FK）；Cascade 僅作用於 KnowledgeSource → Items 這層，刪除來源會連動清掉其成員列，但不影響被參照的原始素材。

⚠️ 反向缺口（刪素材→孤兒）：因成員為軟參照無硬 FK，刪除某筆素材（MediaTranscription/DocumentExtraction/ImageRecognition）不會連動清除引用它的 KnowledgeSourceItem，也不會使下游清洗/蒸餾/向量失效——*Service.DeleteAsync 僅刪素材自身的檔與列。結果是成員變孤兒（KnowledgeSourceService.GetAsync 顯示為「（來源已不存在）」）、下游內容過時，且無孤兒清理/一致性排程，須人工重跑清洗→蒸餾→索引。完整分析、優缺點與可實作清單見 資料生命週期與維護 §2.3、§5、§6。

注意：附件「資料表紀錄」會被 EF Core Cascade 處理；但實體檔案仍須由 Service 層在刪除前後手動移除。詳見 檔案上傳機制。

GraphJobStateJobType、Status、ResultCount、ErrorMessage、TriggeredBy/TriggeredByName、StartedAt/CompletedAt、CreatedAt/UpdatedAt全域圖譜作業狀態（1.0.95）。JobType＝社群摘要重建／LLM 別名建議；無 Teams。因為這兩條作業是全域單例（非 per-record），無法掛在任何一筆紀錄的狀態欄上，故另立此表供 /pipeline-jobs 觀測、取消與重啟復原。⚠️ 多執行個體部署時，記憶體旗標只反映本機，本表才是全域真相。
McpAccessKeyId、Name、KeyValue、UserId、IsEnabled、CreatedAt、UpdatedAtMCP 專用 API Key（1.0.9）。KeyValue 以明文存 DB（僅管理員可於 /mcp-api-keys 檢視）；UserId 對映既有帳號，決定經 X-API-Key 認證後的團隊權控範圍；IsEnabled 供逐把即時啟用/停用（免重啟）。

分類/團隊標籤欄位（Categories／Teams）：型別為可空字串，以分隔字元包夾的字串儲存多個名稱（不做外鍵關聯，是名稱字串快照）。AdapterModel/DTO 對外以 List<string> 呈現，由 TagStringHelper 負責轉換與查詢述詞。團隊欄位另作為「團隊資料權控」的依據，詳見 認證授權與權限機制。

實際欄位請以 src/KnowledgeExtraction/KnowledgeExtraction.AccessDatas/Models/ 內的程式碼為主。

4.2 啟動時自動處理

Program.cs 的資料庫初始化區塊會在 app.Build() 後執行：

  1. 若有任何 Migration → dbContext.Database.Migrate()。
  2. 否則 → dbContext.Database.EnsureCreated()。
  3. Seed 預設角色：RoleView.Name == MagicObjectHelper.預設角色（不存在則新增），其 TabViewJson 來自 RolePermissionService.GetRolePermissionAllNameToJson()。
  4. Seed 預設使用者：MyUser.Account == MagicObjectHelper.開發者帳號（不存在則新增），密碼採同帳號值 + Salt SHA 雜湊，並關聯到上一步的 RoleView。

啟動 Seed 為冪等行為：每次啟動會重新覆寫預設角色的 TabViewJson，並重置 IsAdmin = true，確保開發者帳號永遠可登入。

5. 命名差異提示

  • DbSet 名稱仍維持 MyTas / MyTasFile（早期命名），Entity 已更名為 MyTask / MyTasFile。新增 Migration 時請留意此命名差異避免產生不必要的 rename。
  • 對應的 commit 紀錄為 MyTas 全面更名為 MyTask 並重建 migration（commit 05ab875）。
