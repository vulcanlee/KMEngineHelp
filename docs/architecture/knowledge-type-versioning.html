  • 文件版本：1.0

  • 對應版本：設計提案（尚未實作；施工時各項 Entity/欄位/DbSet 名稱以現行碼為準核對）

承接 策略 13 的近期路線（0–3 個月）；架構原則見 開發慣例與限制速查、資料模型見 資料模型與資料庫、RAG 落地見 知識庫 RAG 設計與執行。本文只設計「知識型態抽象、版本化/生效狀態、時效性（最新來源保證）」三塊；合規比對應用與安全強化另立文件。

一、背景與目標

現況系統是「匯入導向、扁平切塊、快照式」的知識庫。策略 13 指出：合規（旗艦）與客戶 A（可迭代標準）都需要「可版本、有生效狀態、永遠用最新且經核可來源」的知識，而這無法靠現行快照式索引達成。

目標（本設計要達成的可驗證結果）：

  1. 用一層「知識型態（Knowledge Type）」設定，讓同一套閉環支援不同應用型態（合規標準、規格、一般問答），不為每客戶重寫。
  2. 讓知識條目可迭代改版並保留歷史，明確標示「現行版／生效日／被誰取代」。
  3. 讓檢索只取現行（或指定時點）且經核可的版本；來源更新後索引能增量刷新、不回舊版或草稿。

非目標（YAGNI，本次不做）：GraphRAG/關聯邊（屬客戶 B 中期）、合規自動比對 agent（中期）、text-to-SQL（長期選配）、資料連接器（長期）。這些在策略 13 已排序，勿在此階段一起做。

📌 追記：其中 GraphRAG／關聯邊已於 1.0.83～1.0.88 另案實作（見 Graph RAG 導入分析與實作藍圖），本設計文件的範圍未因此改變；其餘三項仍未實作。

二、知識型態（Knowledge Type）抽象

2.1 概念

把目前寫死在管線裡的行為參數化。一個知識型態 = 一組設定，掛在「集合／知識來源」上，決定其閉環行為：

設定維度值域（本階段）對應現有機制
匯入模式檔案匯入 / 直接編修撰寫既有匯入管線 + 內容線上編修
結構層級扁平 chunk / 條款級(clause)既有 chunk；條款級為新增
生命週期快照 / 版本化＋生效狀態＋審核既有審核流程 + 本文版本化
檢索策略混合檢索 / 加 metadata filter 取現行版既有混合檢索 + 本文 filter
清洗/蒸餾設定沿用 CleaningProfile既有
提示詞沿用四層 LlmPromptResolver既有

設計原則：知識型態是既有「設定驅動、不改碼」慣例（CleaningProfile、四層提示詞、供應商可切換）的自然延伸，而非新框架。多數行為差異先用設定表達，只有結構層級與生命週期需要新增資料模型支援。

2.2 資料模型

新增 KnowledgeType（知識型態定義）實體：型態名稱、匯入模式、結構層級、生命週期、檢索策略、預設 CleaningProfileId、IsEnabled。 KnowledgeSource（與/或新的 Collection，見 §五）新增 KnowledgeTypeId 外鍵，繼承其型態設定。

施工核對點：確認掛載點放在 KnowledgeSource（現有）或新的 Collection；預設型態＝「一般問答＋快照」，確保既有資料零行為變更（向後相容）。

三、版本化與生效狀態

3.1 狀態機

對「版本化」型態的知識條目（現行以 WikiPage 承載，或新增「標準條目」實體），採明確狀態機：

草稿(draft) → 審查中(in-review) → 已核可(approved) → 現行(current)
                                            │
                                            └→（新版核可並生效）→ 舊版轉 已汰換(superseded)
                                  審查退回 → 退回(rejected) → 回草稿
  • 同一「概念/條款」可有多個版本；至多一個 current。
  • 沿用既有 WikiPage 審核關卡（待審核/已完成/已退回）作為 draft→approved 段，擴充出 current/superseded 與版本鏈。

3.2 資料模型（改，須雙 migration）

在版本化條目實體上新增欄位（名稱待核對）：

  • Version（版次，整數或語意版號）
  • EffectiveStatus（draft/in-review/approved/current/superseded/rejected）
  • EffectiveDate（生效日）、ExpiryDate（可空，被取代時填）
  • SupersededByPageId（指向新版）、PreviousVersionPageId（版本鏈）
  • BaselineId（可空，凍結里程碑用；基線為選配，先留欄位）
  • Owner（維護負責人）、LastReviewedAt（最後確認為現行的時間）
  • ChangeSummary（本版變更摘要）

標籤欄位（若此實體含 Categories/Teams）續走 TagStringHelper 分隔字串＋精確比對；AutoMapper 以 ForMember 雙向。權控標籤（Teams）繼承來源，不因改版而遺失。

3.3 索引與版本的關係

VectorEmbedding 已有 WikiPageId/KnowledgeSourceId/ContentHash。版本化後：

  • 每個 chunk 記錄其來源版本（新增欄位或以 WikiPageId 對應到帶版本的條目）。
  • 舊版被取代時，其 chunk 標記為非現行（見 §四失效），不刪除（保留 as-of 查詢與稽核能力）。

四、時效性與「最新最正確來源」保證

回應「系統運行後原始資料不斷更新，如何確保知識庫用最新且經核可來源」。三個機制：

4.1 檢索時 metadata filter 取現行版

RetrievalService / DualDbVectorStore 的查詢，在權控過濾之外再加生效狀態過濾：預設只取 current 且 approved 的內容，排除 draft/superseded；支援可選 as-of 時點查詢（合規需引用「當時有效版本」）。

4.2 事件觸發增量重索引 + 失效標記

沿用既有背景佇列 + Processor 模式（如 EmbeddingIndexProcessor / ITranscriptionQueue 同構）：

  • 來源條目變更（改版/核可/汰換）時入列「重索引」事件。
  • 只對受影響條目的 chunk 以 ContentHash 做增量重嵌（既有已支援增量），並失效舊版 chunk 的現行標記。
  • 好處：避免全量重建；staleness gap 從「批次週期」縮短到「事件秒級」。

4.3 四維新鮮度/信任評分（避免「分數高但庫過時」）

在條目 metadata 記錄並於管理面呈現：Freshness（LastReviewedAt）、Ownership（Owner 是否存在）、Lineage（可溯回來源）、Canonical alignment（是否 current）。缺 owner／久未複查者於知識缺口/評測儀表板標示（該儀表板為策略 13 近期項）。

五、顯式集合（Collection）

現況靠 Teams/Categories/KnowledgeSourceId 隱式分組，多應用邊界不清。新增 Collection（知識庫/集合）實體作為「一個知識應用」的邊界：掛 KnowledgeTypeId、預設 Teams、名稱/描述。KnowledgeSource 歸屬某 Collection。

範圍控制：本階段 Collection 僅作分組與型態掛載，不引入跨 Collection 聯邦（federated，屬長期）。

六、資料模型變更清單與雙 migration

變更內容Migration
新增 KnowledgeType型態定義Sqlite + SqlServer 各一
新增 Collection應用邊界Sqlite + SqlServer 各一
版本化欄位條目實體加版本/生效狀態/owner 等Sqlite + SqlServer 各一
VectorEmbedding 加來源版本/現行標記支援取現行版與 as-ofSqlite + SqlServer 各一

鐵則：每項模型變更在 AccessDatas(Sqlite) 與 AccessDatas.SqlServerMigrations(SQL Server) 各產一份 migration（開發慣例）；Update/Delete 前 CleanTrackingHelper.Clean<T>()；編輯前 Clone()；注意 DbSet MyTas ≠ Entity MyTask 之類命名不要誤動。

七、新頁面與選單三處同步

新頁面用途
知識型態管理CRUD 型態設定（沿用既有 CRUD 腳手架）
集合(Collection)管理CRUD 集合、掛型態、設預設 Teams
標準/條目版本頁版本 diff、生效狀態切換、審核、版本鏈檢視

鐵則：每個新頁面權限三處同步——MagicObjectHelper（權限常數）＋RolePermissionService（權限樹）＋Menu.json（選單），以位置索引對齊；檢視用建構式注入 Service、[Inject] 注入框架類；AntDesign 多選用 SelectMode.Multiple＋Values/OnSelectedItemsChanged。

八、對既有不變量的衝擊檢查表

  • ✅ 團隊權控：新檢索/查詢（含生效狀態過濾）一律套 IRecordAccessScopeProvider＋TagStringHelper.BuildTeamAccessPredicate，於檢索層過濾；生效狀態過濾疊加在權控之上，不取代。以 RagEvalSample 越權洩漏測試驗證。
  • ✅ 標籤：Categories/Teams 續走 TagStringHelper；版本繼承來源 Teams。
  • ✅ 雙 migration：見 §六。
  • ✅ 選單三處同步：見 §七。
  • ✅ 向後相容：預設型態＝一般問答＋快照，既有資料行為不變。
  • ⚠️ 向量庫規模化：本設計沿用現行 byte[]＋應用層餘弦即可運作；但生效狀態過濾增加查詢條件，規模成長後仍建議依策略 13 升級 pgvector/Qdrant（獨立項，非本設計前置）。

九、分階段落地（對齊策略 13 近期 0–3 個月）

  1. 知識型態 + 集合（骨架） → 驗證：可建立型態/集合、既有資料掛預設型態零行為變更。
  2. 版本化欄位 + 狀態機 + 版本頁 → 驗證：同一條目可多版本、至多一 current、可改版保留歷史與變更摘要、審核可核可/退回。
  3. 檢索 metadata filter 取現行版（含 as-of） → 驗證：查詢預設只回 current+approved；as-of 可回指定時點版；越權不外洩。
  4. 事件觸發增量重索引 + 失效標記 → 驗證：條目改版/核可後秒級刷新，舊版 chunk 不再命中為現行。
  5. 四維新鮮度呈現 → 驗證：缺 owner／久未複查條目於儀表板標示。

每次可建置產出 appsettings 版本號 +1（純設計文件本身不升版）。

十、驗收標準（端到端）

  • 建一個「合規標準」型態的集合，逐條匯入標準；改版後：查詢只回現行版、能查「上一版是什麼/改了什麼」、舊版標為 superseded 且不進 LLM context。
  • 非授權團隊對該集合的越權內容在檢索層即被擋（測試驗證）。
  • 來源條目核可後，索引在事件觸發下增量刷新（非全量），且答案引用的是最新經核可版本。

十一、開放問題與風險

  • 版本化承載體：擴充 WikiPage vs 新增「標準條目」實體——建議先擴充 WikiPage（複用既有審核/蒸餾/繼承 Teams），條款級結構若不足再新增；施工前定案。
  • 基線(Baseline)：先留 BaselineId 欄位、暫不做完整基線凍結 UI（YAGNI），待合規客戶確認需求。
  • as-of 查詢成本：保留舊版 chunk 會增加索引量；規模成長與向量庫升級一併評估。
  • 與客戶 JTBD 對齊：版本化/生效狀態的具體欄位（如是否需 EffectiveDate/ExpiryDate）應向合規客戶驗證後定稿，避免過度設計（呼應策略 13 §十五）。
  • 合規比對與安全強化：屬後續文件；本設計的版本化/現行版過濾是其前置。

十二、施工定案與落地（0.3.12 → 0.3.14 完整實作）

更新（0.3.14）：VER-1 完整版本狀態機與 VER-2 失效標記/as-of 已完整實作（承載體＝擴充 WikiPage）。以下保留原施工定案脈絡，並於各節標注實作結果。

VER-1（已完整實作 0.3.14；承載體＝擴充 WikiPage）

  • 承載體定案：擴充 WikiPage（複用既有審核關卡 WikiPageService.ApproveAsync/RejectAsync、Teams 繼承來源、ConfidenceScore、線上編修、蒸餾多頁生成）。條款級結構若不足，再另立「標準條目」實體。
  • 欄位設計（施工時雙 migration）：Version、EffectiveStatus(draft/in-review/approved/current/superseded/rejected)、EffectiveDate、ExpiryDate?、SupersededByPageId?、PreviousVersionPageId?、Owner、LastReviewedAt、ChangeSummary；BaselineId? 先留欄位不做 UI。EffectiveDate／ExpiryDate 等是否納入，應向合規客戶驗證後定稿（避免過度設計，遵 §十一）。
  • 關鍵衝突（實作時務必處理）：DistillationProcessor 現行「重蒸餾＝刪除舊 Wiki＋舊向量、全新重建」（DeleteExistingPagesAsync）與版本化的「保留舊版→標 superseded→建版本鏈」語意相反，須改寫取代邏輯；VectorEmbedding 需加「來源版本／現行標記」欄位，供 VER-2 的失效標記與 as-of 查詢。
  • 實作結果（0.3.14）：
  • WikiPage 已加 Version/EffectiveStatus(current/superseded/null)/EffectiveDate/ExpiryDate/SupersededByPageId/PreviousVersionPageId/Owner/LastReviewedAt/ChangeSummary（BaselineId 依 YAGNI 未加）。概念鍵＝(KnowledgeSourceId, Title)，每概念至多一個 current。
  • DistillationProcessor 重蒸餾不再刪除舊版：自動核可的新版即成 current、舊 current→superseded＋版本鏈；WikiPageService.ApproveAsync 核可時做同樣 current↔superseded 轉移。
  • 治理欄位（Owner/ChangeSummary）於蒸餾頁編輯；/knowledge-wiki 顯示版本歷史。
  • 雙 migration AddVersioningFields（含既有已完成頁 backfill 為 current）。

VER-2（已完整實作 0.3.12 MVP + 0.3.14 失效/as-of）

  • 事件觸發自動重索引（0.3.12）：Wiki 頁線上編修（WikiPageService.UpdateContentAsync，僅已核可頁）與核可（ApproveAsync）後自動排入該來源重索引（TryEnqueueSourceReindexAsync → IEmbeddingIndexQueue），沿用 EmbeddingIndexProcessor 增量冪等引擎。
  • 失效標記 + 只取現行版 + as-of（0.3.14）：
  • VectorEmbedding 加 IsCurrent/EffectiveDate/ExpiryDate；汰換舊版時其向量 IsCurrent=false（ExecuteUpdate）、保留不刪（供 as-of/稽核）。
  • EmbeddingIndexProcessor 只索引 current 頁、diff 只作用於 IsCurrent=true（superseded 向量不被當孤兒刪除）。
  • 檢索（DualDbVectorStore/RetrievalService）以 EffectiveVersionFilter 疊加在權控之上：預設只回現行版；RetrievalQuery.AsOf 取時點現行 Wiki 版本（Cleaned 恆納入）。/rag-diagnostics 試檢索提供 as-of 日期。
