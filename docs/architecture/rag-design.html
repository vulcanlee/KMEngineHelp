一、RAG 全流程

AI 知識問答採 Retrieval-Augmented Generation（RAG）：先從已索引的知識庫找出相關 chunk，再把這些 chunk 以附出處 context 的形式交給 LLM 產生回答。

flowchart TD
    A["知識來源已清洗"] --> B["知識蒸餾產生 WikiPage"]
    B --> C["DistillationProcessor 觸發 EmbeddingIndexQueue"]
    C --> D["EmbeddingIndexProcessor 讀取 Cleaned 與已完成 Wiki"]
    D --> E["Chunker 依段落、標題、overlap 切塊"]
    E --> F["IEmbeddingClient 批次產生 embedding"]
    F --> G["VectorEmbedding 儲存 chunk、metadata、byte[] 向量"]
    H["使用者提問"] --> I["KnowledgeBaseChatService 取最近對話"]
    I --> I2["Query Rewrite 視需要補全查詢"]
    I2 --> J["RetrievalService 混合檢索：向量 + 關鍵字 + 圖鄰域"]
    G --> J
    B --> GE["GraphEdgeService 由 LinkTitles 建 GraphEdge"]
    B --> GX["圖抽取：LLM 三元組 → 人工審核 → GraphNode/GraphTriple"]
    GE --> J
    GX --> J
    J --> K["套團隊權控後取 TopK"]
    K --> KT{"兩段式門檻：依最高分判定信心"}
    KT -->|查無依據| KX["程式層直接回覆查無依據，不呼叫 LLM"]
    KT -->|信心不足/足夠| L["組附出處 context：Wiki 優先，Cleaned 佐證"]
    L --> M["IChatConversationClient 串流呼叫 LLM（信心不足者於回答前加註提示）"]
    M --> N["回答 + 出處鑽取 + 原始檔下載"]

核心程式：

  • Chunker：段落/標題感知切塊。
  • EmbeddingIndexProcessor：建立或更新 VectorEmbedding。
  • DualDbVectorStore：以 DB 中的 byte[] 向量做應用層 cosine 搜尋。
  • RetrievalService：向量、關鍵字與圖鄰域三路混合檢索（見 §4.2）。
  • GraphEdgeService／GraphExtractionProcessor／GraphCommunityBuilder：Graph RAG 的建邊、三元組抽取與社群摘要（見 §4.2／§4.3）。
  • KnowledgeBaseQueryRewriteService：在短問句或多輪代詞情境下補全檢索 query。
  • KnowledgeBaseChatService：每輪取權限、檢索、組 context、呼叫 LLM。

二、切塊與索引

切塊輸入有兩層：

  • Cleaned：知識來源清洗後 Markdown，保留較完整的事實與條款內容。
  • Wiki：知識頁審核後的已完成 Wiki 頁，作為概念導引與摘要式命中。

Chunker 不是固定字數硬切。它會：

  • 以空行切段落，盡量不拆斷段落。
  • 追蹤最近的 Markdown 標題，寫入 AnchorRef，供出處定位。
  • 累積到目標字元數後 flush。
  • 若單段超過硬上限，依硬上限切段。
  • flush 後把上一個 chunk 尾端字元帶入下一塊，形成 overlap。

切塊參數位於 SystemSettings.Retrieval：

參數預設何時生效說明
ChunkTargetChars800建立索引時chunk 目標字元數，累積到此長度後切塊。
ChunkMaxChars1200建立索引時單一 chunk 硬上限，超長段落會依此切開。
ChunkOverlapChars120建立索引時相鄰 chunk 保留的尾段重疊字元數。

調整切塊參數後，既有 VectorEmbedding 不會自動改變。必須重新蒸餾，或在「知識來源加工」對來源按「建立索引／重建索引」（見下節），新的 chunk 與 embedding 才會套用新規則。

重要：索引只在「蒸餾完成當下」自動觸發。 若內容在嵌入索引管線上線前就已蒸餾、或當時尚未設定嵌入，VectorEmbedding 會是空的，導致問答一律「查無相關依據」。此時不需重蒸餾——到「知識來源加工」對已清洗來源按「建立索引」即可（KnowledgeSourceService.TriggerEmbeddingIndexAsync → IEmbeddingIndexQueue → EmbeddingIndexProcessor 增量建立）。/system-health 的「向量索引涵蓋率」檢查會在索引為空或未設定嵌入時示警。

2.1 更新策略：成員異動後如何重整（變多/變少都正確汰換）

當知識來源的成員有異動（新增/移除/重排），既有清洗、蒸餾、索引會變陳舊。系統採「重跑管線、各步驟自動汰換產物」策略，不需手動刪除：

階段策略內容變多內容變少
清洗（Cleaning）覆蓋重新彙整、覆寫 Cleaned Markdown（刪舊檔寫新檔）同左
蒸餾（Distillation）版本化（VER-1，0.3.14）重蒸餾產生新版頁；自動核可即成 current不再刪除舊版：舊 current→superseded（保留＋標記），新版成 current（概念鍵＝來源+標題）
索引（Embedding）增量 diff（現行感知）新 chunk 進 toAdd → 新增（IsCurrent=true）現行版消失的 chunk 進 toDelete → 刪除；superseded 向量 IsCurrent=false 保留不刪

「增量」是 diff（新增＋刪孤兒＋不變保留）；diff 只作用於 IsCurrent=true 的現行版 chunk。索引以 (SourceLayer, WikiPageId, ContentHash) 為鍵比對。VER-1（0.3.14）起重蒸餾/核可保留舊版並標 superseded（見下與 版本化設計 §十二）。

成員異動的過期提示：成員新增/移除/重排會把該來源標記 ContentStale = true，清單頁顯示「內容已變更，建議重新清洗→蒸餾」；重新清洗成功完成後旗標清除。建議重跑順序：重新清洗 →（清洗完成後手動）蒸餾 →（蒸餾完成自動）建立索引。註：成員的「原始內容」若在其他頁面被編輯，系統不會自動偵測，請一樣重新清洗。

Wiki 內容變更事件觸發自動重索引（VER-2，0.3.12）：Wiki 頁線上編修（已核可頁）與核可（待審→已完成）後，系統會自動排入該來源重索引（WikiPageService.TryEnqueueSourceReindexAsync → IEmbeddingIndexQueue，走同一增量 diff 引擎），縮短「編修/核可後內容尚未進向量庫」的 staleness gap；守衛同 TriggerEmbeddingIndexAsync（來源須已清洗、非 in-flight）。

版本化與只取現行版 + as-of（VER-1/VER-2，0.3.14）：WikiPage 有版本鏈與 EffectiveStatus（current/superseded）；重蒸餾/核可保留舊版並標 superseded、其向量 VectorEmbedding.IsCurrent=false（保留不刪）。檢索以 EffectiveVersionFilter 疊加在權控之上：預設只回現行版（IsCurrent）；RetrievalQuery.AsOf 取時點現行 Wiki 版本（Cleaned 不版本化、恆納入）。生效狀態過濾疊加不取代權控——越權洩漏仍須為 0。

查詢期範圍篩選（0.3.22；團隊維度 0.3.36）：RetrievalQuery/VectorQuery 新增 SourceIds（知識來源）、Categories（分類）與 Teams（團隊）可選篩選，向量路徑（DualDbVectorStore）與關鍵字路徑（RetrievalService）皆套用（分類、團隊皆用 TagStringHelper.BuildContainsAnyPredicate 精確成員比對）。同樣疊加在團隊權控之上、只縮不放；留空＝不限（維持現狀）。AI 知識問答頁提供「限定知識來源／分類／團隊」多選以支援「多客戶／多系統／多團隊」精準問答；其中分類下拉只列「可存取知識中實際用到的分類」（KnowledgeBaseChatService.GetFilterCategoriesAsync）、團隊下拉只列「登入者可存取團隊」（GetFilterTeamsAsync；管理員為全部啟用團隊）。團隊篩選只能在可存取集合內再縮小、無法擴權（下拉僅列可存取團隊，且 BuildTeamAccessPredicate 存取述詞仍先套）。

設定驗證規則：

  • ChunkTargetChars > 0
  • ChunkMaxChars >= ChunkTargetChars
  • ChunkOverlapChars >= 0
  • ChunkOverlapChars < ChunkTargetChars

違反規則時 Chunker 會丟出 InvalidOperationException，避免產生品質不明的索引。

三、Embedding 與向量儲存

Embedding 設定位於 OpenAISettings：

參數預設說明
EmbeddingProviderCloud空白時沿用 GenerationProvider；可設 Cloud 或 Local。倉庫現值為 Cloud。
EmbeddingModeltext-embedding-3-large雲端嵌入模型。
EmbeddingDimensions1024雲端 dimensions 參數；目前系統把 1024 維視為文件與查詢向量必須一致的運作約定。
LocalEmbeddingModelbge-m3地端 OpenAI 相容端點使用的嵌入模型。

目前落地方式：

  • 文件 chunk 與查詢使用同一 embedding 模型。
  • 向量會 L2 normalize。
  • 向量以 float32 打包成 byte[] 存在 VectorEmbedding.Embedding。
  • DualDbVectorStore 先用團隊權控縮小候選，再在應用層 decode 向量並計算 cosine。
  • 目前沒有使用 pgvector、sqlite-vec 或 SQL Server VECTOR；IVectorStore 保留未來替換路徑。

換 EmbeddingModel、LocalEmbeddingModel 或 EmbeddingProvider 後，舊向量與新向量不應混用，需要重建索引。改 EmbeddingDimensions 風險更高，除了重建索引外，也必須確認所有既有向量已清除或重建，避免 cosine 比對時維度不一致。

四、混合檢索

檢索設定位於 SystemSettings.Retrieval：

參數預設何時生效說明
TopK10查詢時最終送進問答 context 的命中數上限。
CandidateTopK50查詢時向量路徑與關鍵字路徑各自取回的候選上限。向量路徑依 cosine 排序取前 N；關鍵字路徑依命中詞數排序取前 N（1.0.16 起，見下方說明）。
VectorWeight0.7查詢時融合分數中的向量相似度權重。
KeywordWeight0.3查詢時融合分數中的關鍵字命中權重。
GraphWeight0.2查詢時融合分數中的圖鄰域權重（Graph RAG P1，1.0.83）。設 0 即完全關閉圖檢索路徑（連查詢都不發）。
GraphMaxHops2查詢時圖鄰域擴展跳數（P8，1.0.90）。設 1 即為 1.0.89 之前的單跳行為。範圍 1～3；可於 /rag-diagnostics 熱調。
GraphHopDecay0.5查詢時跳數衰減：第 h 跳強度＝種子強度 × decay^(h-1)（第 1 跳不衰減）。範圍 [0,1]；可熱調。
GraphMaxNodes200查詢時單次檢索的鄰居頁總數上限（安全閥）。達上限即停止擴展並記 log。無 DB 覆寫、只讀 appsettings、改了要重啟。
GraphGlobalCommunityCap20查詢時全域問答 map-reduce 取用的社群摘要上限（每個社群一次 LLM，直接決定成本）。1.0.89 起可設定。
GraphMaxCommunities50重建社群時社群摘要重建保留的社群數上限（每群一次 LLM；超出者取成員數最大的前 N 群並記 log）。1.0.89 起可設定。
GraphAliasNameCap300別名建議時LLM 別名建議送出的實體名上限（超出者取出現次數最多者並記 log）。1.0.89 起可設定。
MinScore0.0查詢時逐筆最低融合分數門檻（低於則濾除單一命中）。
RejectThreshold0.15查詢時整體信心下限：最高分命中低於此值即視為查無依據（見第五節之一）。
LowConfidenceThreshold0.30查詢時信心不足門檻：最高分介於兩門檻之間時照答但加註提示（見第五節之一）。

⚠️ GraphGlobalCommunityCap／GraphMaxCommunities／GraphAliasNameCap／GraphMaxNodes 這四個只讀 appsettings，沒有 DB 覆寫、改了要重啟（與 GraphWeight／GraphMaxHops／GraphHopDecay 等查詢期參數不同——那些走 RetrievalParamOverride 可在 /rag-diagnostics 熱套用）。它們是低頻的成本閘門與安全閥，刻意不為此再開 migration。四者皆以 Math.Max(1, 設定值) 夾住，填 0 或負數會退回 1 而不是靜默停擺；GraphMaxHops／GraphHopDecay 亦在讀取時夾住上下界（appsettings 直接填超界值時 SetParamsAsync 的驗證擋不到）。

RetrievalService 會執行三條路徑：

  • 向量路徑：對使用者問題即時 embedding，呼叫 IVectorStore.SearchAsync，以 cosine 排序。
  • 關鍵字路徑：把問句依空白與常見標點切詞，並保留完整問句，對 ChunkText 做 Contains 查詢。
  • 圖檢索路徑（Graph RAG，GraphWeight > 0 時才執行）：見下方「4.0 圖檢索第三路」。

關鍵字路徑的候選集排序（1.0.16）。 命中述詞是 OR（含任一詞即入選），符合條件的列數常遠大於 CandidateTopK。因此截斷前必須先排序：SearchKeywordAsync 在 DB 端以「命中詞數」（CASE WHEN ChunkText LIKE '%詞%' THEN 1 ELSE 0 END 的加總）OrderByDescending，再以 Id 做決定性 tie-break，最後才 Take(CandidateTopK)。

在此之前為無序 Take，取回哪幾筆由資料庫回傳順序決定（實務上接近主鍵順序）——命中全部詞的高相關 chunk，只要 Id 較大就永遠進不了候選集，連被打分的機會都沒有。這是召回層缺陷，任何下游排序改善（含未來的 rerank）都無法補救。

DB 端的 LIKE 大小寫／定序語意隨資料庫而異，屬近似排名，僅用於挑選候選；最終 KeywordScore = 命中詞數 / 總詞數 仍以記憶體端 OrdinalIgnoreCase 重算，跨 Sqlite/SQL Server 一致，分數語意與既有門檻校準基準不變。

融合公式：

Score = VectorWeight * VectorScore + KeywordWeight * KeywordScore + GraphWeight * GraphScore

缺少某一路分數時以 0 計。最後依融合分數排序、套 MinScore、取 TopK。

未設定 embedding 時，向量路徑會略過或失敗後退回 keyword-only。這能讓頁面繼續運作，但不等於完整跨來源語意檢索；PoC 與正式導入仍應先設定 embedding 並完成索引。

4.1 兩段式信心門檻與查無依據攔截

MinScore 是「逐筆」下限（過濾個別低分命中），預設 0.0 等於不過濾。為避免「知識庫其實沒有相關內容、但 RAG 仍撈出弱相關 chunk 導致 LLM 答非所問或臆造」，KnowledgeBaseChatService 另以「最高分命中」的融合分數做整體信心判定（門檻判定放在編排層，不放在通用的 RetrievalService）。

依排序後最高分命中的融合分數 topScore 分三段：

區間信心（RetrievalConfidence）系統行為
topScore < RejectThreshold 或命中數 = 0Insufficient程式層直接回覆固定訊息「您的問題在知識庫中查無相關依據…」，不呼叫 LLM，不附出處（不洩漏低品質內容）。
RejectThreshold ≤ topScore < LowConfidenceThresholdLowConfidence照常呼叫 LLM 回答，但由程式層在回答最前面加上固定提示「⚠️ 信心不足…」，仍附出處。
topScore ≥ LowConfidenceThresholdSufficient正常回答。

兩段訊息由程式層常數（KnowledgeBaseChatService.InsufficientMessage / LowConfidencePrefix）保證，不依賴 LLM 自律。

門檻值須以真實資料校準。 融合分數分佈依資料而定，RejectThreshold=0.15、LowConfidenceThreshold=0.30 僅為起點。KnowledgeBaseChatService.RetrieveAsync 的稽核已持久化到 KnowledgeBaseQueryAudit（EVAL-2），可據此回填校準。

執行期可覆蓋（0.3.3）。 兩段式門檻可於管理員頁 /rag-diagnostics 依 topScore 分佈檢視建議值與效果模擬後直接套用並熱生效（免改 appsettings、免重啟）。機制：RetrievalSettingOverride 單列覆蓋表 + IRetrievalSettingsProvider（解析優先序：DB 覆蓋 → appsettings → 程式預設）；RetrieveAsync 每輪取「有效門檻」用於判定與稽核記錄。可於該頁「回復預設」清除覆蓋。詳見 RAG 補強總彙整（EVAL-3／RQ-1／EVAL-5）與 RAG 問題診斷手冊。

4.2 圖檢索第三路（Graph RAG，1.0.83～1.0.90）

RetrievalService.SearchGraphAsync 在向量與關鍵字之外加第三路「圖鄰域加分」。GraphWeight = 0 時整條路徑不執行（連 DB 查詢都不發）。

流程：

  1. 種子頁：取 vector ∪ keyword 命中中屬「Wiki 層」的 chunk，其所屬 WikiPage 即為種子；種子強度＝該頁最佳 chunk 的融合前分數 VectorWeight*v + KeywordWeight*k。
  2. BFS 逐跳擴展（P8，共 GraphMaxHops 跳、預設 2）——每一層的鄰居來源有二：
  3. 概念連結邊（P1）：GraphEdge，由蒸餾產物 WikiPage.LinkTitles 的 [[標題]] 冪等重建（GraphEdgeService，不呼叫 LLM）。此查詢與 frontier 相依，每一層都要重查。
  4. 已核可三元組（P2＋P4/P5）：GraphTriple（Status = 已完成）的兩端實體，經 EntityNameNormalizer.Canonical（Trim＋FormKC＋小寫）與 EntityAliasResolver.Resolve（已核可別名的 union-find 傳遞閉包）解析後，對應到「跨來源頁集合」pagesByCanon，展開成無向的「頁↔頁」邊。只處理與當前 frontier 有交集的三元組（控成本）。別名對照、pagesByCanon 與已套 ACL 的三元組清單皆與 frontier 無關，在 BFS 迴圈外只建一次。

第 h 跳的傳播強度＝種子強度 × GraphHopDecay^(h-1)，故第 1 跳不衰減（GraphMaxHops=1 時即 1.0.89 之前的單跳行為）；多路徑到同一頁取 max；已走訪過的頁不重複加分。鄰居總數達 GraphMaxNodes 時取強度最高者填滿並停止擴展，且記 LogInformation（不靜默截斷）。

  1. 回映 chunk：鄰居頁的「現行 Wiki 層」chunk 以該強度加分，並套與另兩路一致的 as-of 版本與查詢期篩選（SourceIds／Categories／Teams）。此步驟在迴圈外只做一次。

leak=0 紅線：邊、節點（GraphNode）、三元組、鄰居 chunk 四層查詢各自都套 TagStringHelper.BuildTeamAccessPredicate；其中邊的權控每一跳都要套。特別是——他隊的三元組即使兩端頁面本身公開也不得用來加分（關係本身即是知識），他隊節點的錨頁也不得進入 pagesByCanon。這些已由測試釘住。

⚠️ 多跳不得成為越權的旁路：他隊的邊被濾掉後，其目標頁就不會進入 frontier，因此下一跳也無法借道該頁繼續走——整條路徑在該處斷開。已由測試釘住（A 公開 →[他隊邊]→ B →[公開邊]→ C，非管理員查 A 時 B 與 C 都不得出現）。

/rag-diagnostics 的「試檢索」面板另有「圖分」欄，可單獨觀察此路貢獻；GraphWeight／GraphMaxHops／GraphHopDecay 走與其他查詢期參數相同的覆蓋鏈（DB 覆蓋 → appsettings → 程式預設）並熱生效。

目前限制：跳數上限 3（再深請先評估專用圖庫，見 Graph RAG 藍圖 §4.4）、無節點/社群摘要嵌入。

4.3 全域問答（社群摘要 map-reduce，P3）

AI 知識問答頁另有「一般／全域」切換。全域模式不走上述三路檢索，改對 GraphCommunity（已核可三元組以 Label Propagation 分群後、每群由 LLM 產出的標題與摘要）做 map-reduce：每個可存取社群各一次 LLM 取重點（map），再彙整成答（reduce），上限為 Retrieval.GraphGlobalCommunityCap（預設 20）。答案末尾附「參考社群」，不產出 chunk 層出處引用；無可用社群時直接回「查無依據」。

⚠️ 社群摘要的 ACL 比一般權控更嚴：社群摘要混合了多個成員節點的知識，因此判定為「社群 Teams 聯集 ⊆ 使用者團隊（子集，非交集）或社群純公開」（GraphCommunityService.IsAccessible）。這與其他所有紀錄的「交集即可」不同，是刻意的收緊。

社群為全域衍生聚合、整批重建、無審核，由管理員在 /knowledge-graph-review 手動觸發；該工作刻意不進 PipelineNames，故不出現在 /pipeline-jobs。

4.4 圖譜瀏覽（P8，1.0.90）

/knowledge-graph-review 的「圖譜瀏覽」分頁可輸入實體名稱、檢視其 N 跳鄰域（關係表格 ＋ inline SVG 放射狀圖；不引入任何外部前端圖庫，符合無 CDN 依賴的前提）。

⚠️ 這與檢索的圖遍歷是兩張不同的圖：檢索遍歷的是頁（WikiPage），本分頁遍歷的是實體（正規化名稱），兩者刻意不共用程式碼（GraphTripleService.GetNeighborhoodAsync）。

  • 輸入名稱先經 Canonical 再經已核可別名 Resolve（故查「TSMC」等同查「台積電」），與檢索／社群偵測的三個 canonical 點語意一致。
  • 只取已核可三元組；三元組與兩端節點兩層都套團隊權控——任一端節點越權，整條關係就不出現。
  • 跳數上限 3、節點上限 100；達上限時以 Truncated 回報並在畫面顯示警告（不靜默截斷）。
  • 可見性沿用「知識圖譜審核」頁權（角色_知識圖譜審核），不新增權限常數、不動選單三處同步。

圖譜的資料模型、審核流程與各階段取捨詳見 Graph RAG 導入分析與實作藍圖 §9 與各篇 changelog。

五、Query Rewrite 與 LLM 回答

AI 知識問答在檢索前會先判斷是否需要 Query Rewrite。預設只在 Auto 模式下，且最近對話存在、問題過短或含「它／這個／剛剛／上述」等上下文標記時啟用。清楚完整的問題會直接用原始 query 檢索。

Query Rewrite 使用 OpenAISettings.QueryRewriteModel，預設 gpt-5.4-mini，逾時由 OpenAISettings.QueryRewriteTimeoutSeconds 控制。地端模式可用 LocalQueryRewriteModel 指定小模型，留空則沿用 LocalGenerationModel。提示詞鍵為 知識庫-查詢改寫，同樣走四層解析。

改寫結果只用於 IRetrievalService.RetrieveAsync；BuildMessagesAsync 仍把使用者原始問題放入本輪 user 訊息。若改寫失敗、逾時或輸出空白，預設回退原始 query，不中斷問答。

KnowledgeBaseChatService.RetrieveAsync 每輪都會重新取得 IRecordAccessScopeProvider.GetAsync()，再把 scope 交給 IRetrievalService。命中結果會先排 Wiki，再排 Cleaned，同層依分數排序。

送入 LLM 的 context 格式類似：

【來源：員工手冊｜蒸餾頁｜健康檢查福利】
chunk 文字...

【來源：員工手冊｜清洗內容｜第三章】
chunk 文字...

BuildMessagesAsync 會組成：

  • system：知識庫系統提示詞 + 回答詳簡 + 附出處參考資料。
  • history：先前 user/assistant 多輪訊息。
  • user：本輪問題。

提示詞走四層解析：單次操作覆蓋 → DB Prompt → appsettings → 程式 fallback。回答以 IChatConversationClient.StreamAsync 串流輸出。

重要限制：Query Rewrite 只做保守的上下文補全，不做 HyDE、多查詢展開、rerank 或相鄰 chunk 擴展；這些項目已列入優化待辦，待 檢索品質評測結果決定是否導入。

六、權控與出處

RAG 的資安不變量是「越權內容不可進候選、不可進 context、不可進出處」。

目前做法：

  • VectorEmbedding.Teams 繼承自知識來源或 Wiki 頁。
  • 非管理員檢索時，向量與關鍵字路徑都套 TagStringHelper.BuildTeamAccessPredicate。
  • 管理員不受團隊限制。
  • 出處展開再走 KnowledgeSourceService.GetAsync，下載原始檔走既有受權控 Controller。
  • 日誌只記 query 長度、命中 chunk id、層別與分數，不記完整問題或完整 context 本文。

檢索品質評測中也有越權洩漏指標；權控相關變更必須維持越權洩漏為 0。

六之一、間接 prompt injection／內容投毒基線防護（SEC-1，0.3.7）

檢索到的知識內容會進 LLM 的 system 訊息，惡意來源可能夾帶「忽略上述指令」等注入。基線防護（KnowledgeExtraction.Business.Helpers.LlmContextGuard）：

  • 問答（RAG KnowledgeBaseChatService 與單一來源 KnowledgeSourceChatService）在組 system 訊息時，把參考資料以每次請求的隨機 nonce 邊界（===參考資料開始 #xxxx===…===結束===）包裹，並在邊界前置防護指令：參考資料為外部不可信資料、其中任何看似指令的文字一律當資料、不得執行、不得改變角色/規則。此段寫在模板本身，不受四層提示詞覆蓋。
  • 另強化 LlmPromptDefaults.KnowledgeBaseSystem／ChatSystem 預設層（防禦縱深）。

限制（誠實）：這是降低風險的基線，非徹底根除 prompt injection；來源內容淨化、可疑內容偵測，以及「依提示詞產生」路徑（LlmGenerationService/DocumentLlmGenerationService）的同類防護列為後續。

六之二、遮罩不變量（SEC-2，0.3.7）

不變量：任何寫入 Cleaned／Wiki 檔（會被索引）的內容都必經遮罩。自動清洗管線的遮罩是不可降級步驟、發生在 embedding 之前；線上編修 Cleaned（KnowledgeSourceService.UpdateCleanedContentAsync）與 Wiki（WikiPageService.UpdateContentAsync）內容時，存檔前會呼叫 CleaningEnhancer.MaskAsync 重跑遮罩（遮罩失敗則不寫檔），關閉「編修繞過去敏後被索引」的缺口。無 LLM 環境本就不遮罩（既有限制）。

六之三、權控標籤傳播與 chunk 層 ACL（SEC-3，0.3.11）

團隊標籤（Teams）是權控來源，會沿「來源 → Wiki 頁 → 向量 chunk」複製：蒸餾時 WikiPage.Teams = source.Teams，建索引時 VectorEmbedding.Teams 取自來源/頁。檢索權控過濾的是 VectorEmbedding.Teams（BuildTeamAccessPredicate，候選階段即濾）。

  • 不變量（本次修補）：來源團隊變更必須即時傳播到既有 WikiPage.Teams 與 VectorEmbedding.Teams。KnowledgeSourceService.UpdateAsync 於團隊變更時以 ExecuteUpdateAsync 直接改子表標籤（免重嵌，只改 ACL）。否則「把來源改嚴」後舊向量仍帶舊（較寬鬆）團隊 → 過度曝露，且 RagEval 的越權檢查用同一舊值、內部一致而抓不到。
  • 粒度現況：VectorEmbedding.Teams 本就是 per-chunk 欄位，檢索與評測（RagEvaluator.LeakHits）皆已 per-chunk 運作；資料模型已足以支援 chunk 層 ACL。目前每個 chunk 的 Teams 一律繼承自來源，尚無「同一來源不同段落不同存取權」的產生路徑。
  • 決策：完整「段落層」差異化標記（需切塊器輸出標籤、UI 標記入口、增量鍵納入 Teams、回應層 PEP 二次驗證）待具體 JTBD 再導入；現階段維持來源/團隊層，並以 檢索品質評測「越權洩漏＝0」守底線。

七、參數調整指引

問題優先檢查/調整是否需重建索引
答案一律查無依據先查 /system-health 的「向量索引涵蓋率」；多半是索引從未建立。到「知識來源加工」對已清洗來源按「建立索引」；並確認 embedding 已設定。管理員在問答頁也會看到診斷提示。不需（建立索引即可）
召回不到相關段落增加 TopK 或 CandidateTopK；檢查 embedding 模型；調整 chunk 目標大小/overlap。改 chunk 或模型需重建
命中太多雜訊提高 MinScore；調整 VectorWeight/KeywordWeight；縮小 TopK。不需
庫外問題仍硬答 / 答非所問提高 RejectThreshold（更易判為查無依據）；視需要調整 LowConfidenceThreshold。先查日誌的「最高分」分佈再校準。不需
正常問題被誤判查無依據降低 RejectThreshold；確認 embedding 已設定且索引完整。不需
關鍵詞精確命中差提高 KeywordWeight；改善使用者問句或資料標題。不需
語意相近但關鍵詞不同提高 VectorWeight；確認 embedding 模型品質。換模型需重建
chunk 太小導致上下文不足增加 ChunkTargetChars 或 ChunkOverlapChars。需要
chunk 太大導致答案混雜降低 ChunkTargetChars 或 ChunkMaxChars。需要
出處不準檢查 AnchorRef、Wiki 頁內容、Cleaned 內容與切塊參數。改內容/切塊需重建

已實作的索引維運：

  • 手動建立／重建索引：「知識來源加工」每列對「已清洗」來源提供「建立索引／重建索引」按鈕（TriggerEmbeddingIndexAsync），不需重蒸餾即可建立或更新 VectorEmbedding（以 ContentHash 增量）。
  • 索引涵蓋率健康檢查：/system-health 的「向量索引涵蓋率」會在「有已清洗來源但索引為空」或「未設定嵌入」時示警。
  • 問答查無依據診斷：管理員在問答查無依據時，會看到原因提示（嵌入未設定／索引為空）；一般使用者僅看到通用訊息。
  • 問答稽核紀錄持久化（0.3.2）：每輪問答檢索寫入一列 KnowledgeBaseQueryAudit（最高分 TopScore、信心、命中數、命中明細 JSON、當下門檻值、問句長度）。隱私邊界：只存長度與分數，不存問句本文、context 本文或 chunk 文字。由 KnowledgeBaseChatService.RetrieveAsync 三分支寫入，稽核失敗以 try/catch 隔離、不影響回答。此表是 topScore 分佈統計與門檻校準的資料基礎（見 RAG 補強總彙整 EVAL-2）。

尚未實作但常見的下一步增強：

  • adjacent chunk expansion：命中 chunk 後自動補前後 chunk。
  • rerank：用 cross-encoder 或 reranker 重新排序候選（分析見 RAG rerank 是否導入分析）。
  • query rewrite / multi-query：把使用者問題改寫成多個查詢增加召回。
