一、問題背景

使用者針對AI 知識問答提出五個問題，釐清後歸納出真正的設計缺口：

  1. 送給 LLM 的是 chunk 文字本身（非原始完整檔案），且為多個 top-K 命中（預設 TopK=10），非只送第一個。
  2. 採混合檢索 Score = 0.7×向量cosine + 0.3×關鍵字，全部 top-K 命中都進 context。
  3. 缺口：MinScore 預設 0.0，等於完全不過濾。庫內沒有相關內容時，RAG 仍撈出弱相關 chunk 全送進 LLM，容易答非所問或臆造。
  4. 「查無依據」原本只在命中數 = 0 時觸發，且僅靠 system prompt 指示 LLM 自律，無程式層硬性攔截；命中數 > 0 但分數都很低時系統仍硬答。
  5. 其他可能缺口：無 rerank、無相鄰 chunk 擴展、低分時無攔截、分數未對使用者透明。

二、需求決策（經 brainstorming 釐清）

決策點結論
低分時策略兩段式：高分照答；全部過低 → 硬攔截回查無依據；中間 → 照答但加註信心不足
變更範圍只做兩段式門檻（不含 rerank／相鄰 chunk 擴展／分數透明化，YAGNI）
訊息呈現程式層決定（不靠 LLM 自律）

三、設計

以「排序後最高分命中」的融合分數 topScore 分三段，判定 RetrievalConfidence：

區間信心系統行為
topScore < RejectThreshold 或命中數 = 0Insufficient程式層直接回固定訊息，不呼叫 LLM，不附出處
RejectThreshold ≤ topScore < LowConfidenceThresholdLowConfidence照常呼叫 LLM，回答前加固定提示，仍附出處
topScore ≥ LowConfidenceThresholdSufficient維持現狀正常回答

設計要點：

  • 門檻判定放在編排層 KnowledgeBaseChatService（擁有「訊息呈現」職責），不放在通用的 RetrievalService。
  • 逐筆下限 MinScore 維持不動，與「以最高分判定整體信心」是不同概念。
  • 兩段使用者訊息由程式層常數保證：InsufficientMessage、LowConfidencePrefix。
  • 門檻值設定化於 SystemSettings.Retrieval，預設 RejectThreshold=0.15、LowConfidenceThreshold=0.30，僅為起點，須以真實資料校準。

五、驗證

  • dotnet test：384 個測試全綠（含 4 個新增信心測試）。
  • 手動實測（建議用真實知識庫）：
  • 庫內明確主題 → 正常回答附出處（Sufficient）。
  • 邊緣／模糊問題 → 回答前出現「⚠️ 信心不足」（LowConfidence）。
  • 完全庫外問題 → 回「查無相關依據」、不呼叫 LLM、不附出處（Insufficient）。

七、後續（0.2.145）：索引未建立的診斷與手動重建

實測發現「不論問什麼都查無依據」的真正原因常是向量索引從未建立（VectorEmbedding 為空）：內容在嵌入索引管線上線前就蒸餾、或當時未設定嵌入，而索引只在「蒸餾完成當下」自動觸發、且原本無手動重建工具。為此補強：

  • 手動建立／重建索引：「知識來源加工」每列對「已清洗」來源新增按鈕，KnowledgeSourceService.TriggerEmbeddingIndexAsync → IEmbeddingIndexQueue → 既有 EmbeddingIndexProcessor（增量），不需重蒸餾。並新增「索引」狀態欄。
  • 問答診斷分流：KnowledgeBaseQueryResult.DiagnosticHint——命中 0 時，僅管理員會看到原因（嵌入未設定／索引為空），一般使用者只看到通用「查無相關依據」。
  • system-health「向量索引涵蓋率」檢查：索引為空或未設定嵌入時示警。
  • Query Rewrite 維持現狀：短問句（如「RAG」）在無對話歷史時不改寫，屬設計使然（避免單一關鍵詞亂擴寫），僅於文件說明。
