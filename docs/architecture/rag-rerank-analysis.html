一、先釐清一個前提（重要）

原始提問是「對於這些超過 RejectThreshold 設定值的 chunk，是否也需要 re-rank」。這裡有個常見誤解需先澄清，否則會把 rerank 放錯位置：

  • RejectThreshold 不是逐一過濾 chunk 的門檻。 它是對「本回合最高分命中 topScore」做的回合級判定：topScore < RejectThreshold → 整個回合視為「查無依據」、直接不呼叫 LLM；否則整批通過。它決定「這一題要不要回答」，不決定「留下哪些 chunk」。（見 KnowledgeBaseChatService.RetrieveAsync、設計文件 §四之一。）
  • 真正決定「哪些 chunk 進 LLM」的是：RetrievalService 先各取 CandidateTopK=50 候選（向量路徑 + 關鍵字路徑）→ 融合分數 Score = 0.7·向量 + 0.3·關鍵字 → 套 MinScore 濾除 → OrderByDescending(Score) → Take(TopK=10)。

所以 rerank 的正確語意不是「對超過 RejectThreshold 的 chunk 重排」，而是：在 CandidateTopK 候選集上，用一個更精準的排序器取代（或補強）目前的線性融合分數，再取 TopK。

目前系統沒有任何 rerank／cross-encoder 實作；唯一排序就是上述融合分數的線性排序。

召回基準已於 1.0.16 改變，本文結論須據新基準重新驗證。 在 1.0.16 之前，關鍵字路徑的候選集是無序截斷（Take(CandidateTopK) 前無 OrderBy），高命中 chunk 可能根本沒進 CandidateTopK。這代表本文第三、四節「召回夠、排序差」的判定前提在當時無法成立——過去若觀察到 Precision@k 偏低，成因可能是召回而非排序。1.0.16 已改為在 DB 端依命中詞數排序後才截斷（見 知識庫 RAG 設計與執行 第四節）。觸發條件 2 的評測應在 1.0.16 之後重跑，勿沿用舊數據下結論。

二、Re-rank 是什麼、為什麼網路上常推薦

典型 RAG 檢索是「雙塔（bi-encoder）」：query 與 chunk 各自獨立編碼成向量，再算 cosine。它快、可預先索引，但query 與 chunk 沒有交互注意力，對「語意細膩差異、否定、條件限定」容易排序失準。

Re-rank（二階重排）通常用 cross-encoder / reranker 模型（如 BGE-reranker、Cohere Rerank）：把 (query, chunk) 成對餵進模型，輸出更貼近人類相關性判斷的分數，對第一階撈回的候選重排。它精準，但每個候選都要跑一次模型，故只用於「先用便宜檢索撈 N 個候選 → 對這 N 個重排 → 取前 K」。

網路推薦 rerank 的前提，多半是「檢索召回還行、但排序不夠好，導致最相關段落沒排進前 K」。

三、在「本系統現況」下的效益評估

面向評估
是否可能有幫助有可能。本系統已是「向量 + 關鍵字」線性融合，rerank 能改善最終 TopK 的排序精準度，讓最相關 chunk 更穩定排到前面，對「有命中但答案不準」類問題有潛在幫助。
目前是否有證據需要它仍沒有。 評測地基已於 0.3.2/0.3.3/0.3.9 完成（EVAL-2 稽核持久化、EVAL-3 topScore 分佈與門檻校準、EVAL-1 評測基線快照），但尚未跑出「召回夠、排序差」的證據（相關 chunk 有進候選卻常落在 TopK 之外）。沒有這個證據前導入 rerank 仍是「憑感覺優化」。
成本：延遲每查詢要對 CandidateTopK（預設 50）個候選各跑一次 cross-encoder，明顯增加問答延遲（雲端 API 往返或地端模型推論）。
成本：部署需額外的 reranker：雲端（如 Cohere Rerank，另一組金鑰與費用）或地端（部署 BGE-reranker，吃資源）。與現有「雲端/地端可切換」架構要一致設計。
與現有替代槓桿比較近期更高效益且更低成本的槓桿是：① 用真實 topScore 分佈校準兩段式門檻（RQ-1）；② adjacent chunk expansion（RQ-2）解決「章節被切開、答案缺上下文」；③ 調 VectorWeight／KeywordWeight、TopK、切塊參數。這些多半改設定即可，不需新模型。

四、建議：有條件的 P2（暫緩，設定為評測驅動）

結論：現階段不導入 rerank，列為「有條件的 P2」。 這與既有多份文件的一致立場相同（planning/08「若融合分數在評測集表現不足再導入」、strategy/12「rerank 列為 v2 選配」）。

導入的觸發條件（滿足才做）：

  1. ~~已完成 EVAL-1（建立 檢索品質評測基線）與 EVAL-2/EVAL-3（稽核持久化 + topScore 分佈）。~~ ✅ 已於 0.3.2/0.3.3/0.3.9 完成。
  2. 評測顯示：召回沒問題（相關 chunk 有進 CandidateTopK），但排序不佳（相關 chunk 常落在 TopK 之外或偏後，Precision@k／NDCG 偏低）。（目前的關卡——尚未出現此證據。）
  3. 先嘗試調融合權重、TopK、切塊、門檻仍無法改善。

若上述都成立，rerank 才是對症下藥。

五、若未來要導入：建議做法（供日後實作參考，本次不實作）

  • 插入點：RetrievalService.RetrieveAsync 中「融合排序後、Take(TopK) 之前」。對融合後的候選（可略多於 CandidateTopK 或取融合前 K 大者）呼叫 reranker，取 rerank 分數重排後再 Take(TopK)。門檻判定（RejectThreshold）建議改用 rerank 分數或維持融合分數，需一併在評測上驗證。
  • 可設定開關：新增 RetrievalSettings.RerankEnabled（預設 false）、RerankModel、RerankCandidateCount、RerankProvider（雲/地端），沿用現有「雲端/地端切換」慣例；未設定或關閉時完全走現有路徑（零風險回退）。
  • 抽象：比照 IEmbeddingClient／IVectorStore，定義 IRerankClient，雲端與地端各一實作，便於替換與測試。
  • 權控不變量：rerank 只重排「已通過團隊權控的候選」，不得引入越權內容（越權洩漏須維持 0）。
  • 評測回歸：導入前後都要跑 檢索品質評測比較 Precision@k／NDCG／延遲，確認「精準度提升 > 延遲成本」。
  • 成本控制：CandidateTopK 若為 50，可考慮 rerank 只吃融合前 20–30 個候選以壓低延遲。

六、一句話總結

Re-rank 在本系統可能有用但尚無證據需要；當務之急是先把「評測基線 + topScore 分佈 + 門檻校準」的地基打好（成本低、效益明確）。把 rerank 列為評測驅動的有條件 P2，等數據顯示「召回夠、排序差」時，再以可開關、雲/地端可切換的 IRerankClient 插在「融合後、取 TopK 前」導入。
