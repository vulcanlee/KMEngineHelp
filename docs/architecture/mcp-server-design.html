系統架構

MCP Server 整合設計與使用指南

本文件為技術設計規格 + AI Agent 使用指南。說明如何在 KnowledgeExtraction.AI（智庫引擎）加入 MCP（Model Context Protocol）Server，讓外部 AI Agent（Claude、其他 MCP client）能直接、安全地查詢企業知識庫。

狀態：已實作（1.0.1→1.0.9；MCP 核心 Phase 0–5 於 1.0.1→1.0.6，變更歷程見 changelog）。四個知識工具（knowledge_ask/knowledge_search/knowledge_list_sources/knowledge_get_document）＋連通診斷 knowledge_ping、JWT/API Key 雙認證、分級日誌與稽核皆已落地並有測試。1.0.8 起 MCP 問答會寫入聊天紀錄並補 Token 用量歸屬（見 changelog）；1.0.9 起 API Key 改存資料庫並提供 /mcp-api-keys 網頁啟用/停用管理，已新增 McpAccessKey Entity 與雙資料庫 migration（Sqlite 20260717053352 ／ SqlServer 20260717053434，見 changelog）。以下部分程式碼為設計骨架示意，實際簽章以原始碼為準。

1.0.91（Graph RAG P9）起暴露圖譜能力：knowledge_ask 新增 mode 參數（local 預設／global 走社群摘要全域問答），並新增第五個知識工具 knowledge_graph_neighbors（查某實體的 N 跳鄰域關係）。詳見 §5.6、§5.7 與 changelog。

1. 概述與目標

1.1 什麼是 MCP

MCP（Model Context Protocol）是一套由 Anthropic 提出、開放的用戶端／伺服器協定，讓大型語言模型（LLM）驅動的 AI Agent 能以標準化方式呼叫外部系統的「工具（tools）」、「資源（resources）」與「提示（prompts）」。AI Agent 是 MCP Client，我們的系統對外提供能力就是 MCP Server。

一旦本系統成為 MCP Server，任何支援 MCP 的 AI 工具（Claude Desktop、Claude Code、其他 Agent 平台）即可把「查詢企業知識庫」當作內建工具使用，而不需為每個 Agent 客製一套 API 串接。

1.2 為何在本知識庫加入 MCP

本系統已具備完整 RAG 檢索能力（混合檢索、團隊權控、出處回溯），但這些能力目前只透過 Blazor 頁面（Interactive Server circuit）呼叫，尚未對外以 HTTP API 暴露。MCP 正好補上這道橋接：

  • 對外賦能：讓客戶端的 AI Agent 直接問答企業知識，成為「客戶端 AI 代理人服務」的落地介面。
  • 零重寫：MCP 工具可直接注入既有服務（KnowledgeBaseChatService、IRetrievalService、KnowledgeSourceService），不需重寫檢索邏輯。
  • 權控一致：走 HTTP transport 時可沿用既有 JWT 認證與團隊權控，安全邊界與現有 Web API 完全一致。

1.3 目標與非目標

範圍內容
✅ 目標以 HTTP transport 在既有 Web 專案內嵌 MCP Server，暴露知識查詢工具（初版 4 個；1.0.91 起 5 個，新增 knowledge_graph_neighbors），全面套用團隊權控
✅ 目標提供 AI Agent 連線設定與使用範例
❌ 非目標（本階段）提供「寫入型」工具（新增/修改知識）；提供 MCP resources/prompts；stdio 本機模式

2. 套件選型

2.1 官方且最主流的套件：ModelContextProtocol

.NET 生態中，官方且使用人數最多的 MCP SDK 是 ModelContextProtocol（GitHub：modelcontextprotocol/csharp-sdk），由 Anthropic 與 Microsoft 官方合作維護。NuGet 上以此為主流實作，其他第三方套件皆非官方、活躍度遠低於此。

該 SDK 拆成三個 NuGet 套件：

套件用途是否採用
ModelContextProtocol.Core只需 client 或低階 server API、最少相依否
ModelContextProtocol主套件，含 hosting／DI 擴充（適合 stdio 伺服器與 AI 整合）間接相依
ModelContextProtocol.AspNetCoreHTTP-based MCP server（Streamable HTTP / SSE）✅ 採用

2.2 結論

本系統為 ASP.NET Core（Blazor Server + MVC）Web 應用，MCP Server 內嵌其中最自然，故採 ModelContextProtocol.AspNetCore（會一併帶入主套件）。這讓 MCP endpoint 與現有 API 共用同一 Kestrel、同一認證管線、同一 DI 容器。

版本策略：本 SDK 已進入 1.x 穩定線。實作時以當下 NuGet 最新穩定版為準（dotnet add package ModelContextProtocol.AspNetCore），並與專案 net10.0 相容性確認。

3. 整體架構

3.1 落點

MCP Server 內嵌於 KnowledgeExtraction.Web 專案，新增一個 MCP endpoint（預設對映路徑 /mcp），與既有 MapControllers()、MapRazorComponents<App>() 並存。

外部 AI Agent (MCP Client)
        │  Streamable HTTP + JWT Bearer
        ▼
┌────────────────────────────────────────────┐
│ KnowledgeExtraction.Web  (Kestrel)          │
│                                             │
│  app.MapMcp("/mcp")  ← 新增                 │
│      │ .RequireAuthorization()              │
│      ▼                                       │
│  MCP 工具類 (McpServerToolType)              │
│   knowledge_ask / knowledge_search /         │
│   knowledge_list_sources / knowledge_get_    │
│      │  建構式注入（per-request scope）       │
│      ▼                                       │
│  既有 Scoped 服務（不修改）                    │
│   KnowledgeBaseChatService                   │
│   IRetrievalService                          │
│   KnowledgeSourceService                     │
│   IRecordAccessScopeProvider ← 團隊權控關鍵   │
│      │                                        │
│      ▼                                        │
│  DualDbVectorStore → Sqlite / SqlServer       │
└────────────────────────────────────────────┘

3.2 資料流（以 RAG 問答為例）

  1. AI Agent 呼叫 knowledge_ask，帶 JWT 於 Authorization header。
  2. MCP endpoint（.RequireAuthorization()）驗證 JWT → 建立 request scope。
  3. 工具方法建構式注入 KnowledgeBaseChatService。
  4. RetrieveAsync 內部每輪呼叫 IRecordAccessScopeProvider.GetAsync()，由 HttpContext 的 Sid claim 解析使用者與角色團隊。
  5. 混合檢索（向量 + 關鍵字）在檢索層即套團隊權控：非管理員只取回「無團隊（公開）或與角色團隊交集」的向量片段。
  6. 組附出處 context 回傳給 Agent。

關鍵：權控發生在檢索層，越權內容永遠不會被取回，MCP 工具無從繞過。

4. MCP Server 註冊（Program.cs）

服務註冊統一落在既有的 ServiceCollectionExtensions.AddApplicationServices()（由 Program.cs 呼叫）。endpoint 對映則加在中介軟體管線的 MapControllers() 附近。

// ── 服務註冊（AddApplicationServices 內或 Program.cs 服務段） ──
builder.Services
    .AddMcpServer()
    .WithHttpTransport()          // Streamable HTTP transport
    .WithToolsFromAssembly();     // 掃描 [McpServerToolType] 工具類

// IHttpContextAccessor 已由既有程式註冊（RecordAccessScopeProvider 依賴它）；
// 若尚未註冊需補 builder.Services.AddHttpContextAccessor();

// ── 中介軟體管線（UseAuthentication/UseAuthorization 之後） ──
app.MapMcp("/mcp")
   .RequireAuthorization();        // 沿用既有授權；預設 JWT/Cookie 皆可
   // .RequireRateLimiting("api");  // 可選：與現有 API 共用限流政策

註：app.MapMcp("/mcp") 對映 Streamable HTTP 端點於 /mcp。.RequireAuthorization() 讓未帶有效憑證的呼叫被擋在工具執行之前。

5. 工具定義設計

各工具皆定義為 [McpServerToolType] 類別，方法標 [McpServerTool]（初版四個，1.0.91 新增第五個 knowledge_graph_neighbors，見 §5.7）。工具類由 DI 於每次呼叫時建立（request scope），因此可用建構式注入既有 Scoped 服務——與本專案「建構式注入 Service」的慣例一致。

型別對照（實作時務必與既有簽章一致）：

  • KnowledgeBaseChatService.RetrieveAsync(string query, IEnumerable<ChatMessage>? history, IReadOnlyList<int>? sourceIds, IReadOnlyList<string>? categories, IReadOnlyList<string>? teams, CancellationToken) → KnowledgeBaseQueryResult(ContextText, Sources, Confidence, TopScore, DiagnosticHint)
  • IRetrievalService.RetrieveAsync(string queryText, RetrievalQuery query, CancellationToken) → IReadOnlyList<RetrievalHit>
  • KnowledgeSourceService.GetAsync(DataRequest) → DataRequestResult<KnowledgeSourceAdapterModel>；GetAsync(int id) → KnowledgeSourceAdapterModel
  • IRecordAccessScopeProvider.GetAsync() → RecordAccessScope(bool IsAdmin, IReadOnlyList<string> Teams)

5.1 knowledge_ask — AI 知識問答（RAG Q&A）

輸入問句（可帶對話歷史），回傳「含出處的參考資料 context」與信心判定。這是最核心的工具。

[McpServerToolType]
public sealed class KnowledgeAskTool
{
    private readonly KnowledgeBaseChatService chatService;

    public KnowledgeAskTool(KnowledgeBaseChatService chatService)
        => this.chatService = chatService;

    [McpServerTool(Name = "knowledge_ask")]
    [Description("向企業知識庫提出自然語言問題，回傳含出處的參考資料與信心判定。結果已依呼叫者所屬團隊過濾，只含其有權存取的內容。")]
    public async Task<object> AskAsync(
        [Description("使用者的問題，例如：公司差旅報銷的流程是什麼？")] string question,
        [Description("可選：限定的分類名稱清單；null 或空＝不限")] string[]? categories = null,
        [Description("可選：限定的團隊名稱清單（只會縮小、不會擴權）；null 或空＝不限")] string[]? teams = null,
        CancellationToken cancellationToken = default)
    {
        var result = await chatService.RetrieveAsync(
            question,
            history: null,
            sourceIds: null,
            categories: categories,
            teams: teams,
            cancellationToken);

        return new
        {
            answerContext = result.ContextText,
            confidence = result.Confidence.ToString(),   // Insufficient / LowConfidence / Sufficient
            topScore = result.TopScore,
            sources = result.Sources                      // 出處清單（標題、來源層別等）
        };
    }
}

多輪追問：可另加一個帶 history（ChatMessage[]，role = user/assistant）的多輪版本，或讓本工具接受選填的 history 參數對映到 RetrieveAsync 的 history。

5.2 knowledge_search — 知識搜尋（檢索片段）

回傳與問句最相關的原始 chunk 片段與分數，讓 Agent 自行組織答案（比 knowledge_ask 更低階、更透明）。

[McpServerTool(Name = "knowledge_search")]
[Description("對知識庫做混合檢索（向量語意＋關鍵字），回傳最相關的內容片段與出處。結果已套團隊權控。")]
public async Task<object> SearchAsync(
    [Description("查詢語句")] string query,
    [Description("回傳片段數上限；null＝用系統預設 TopK")] int? topK = null,
    CancellationToken cancellationToken = default)
{
    var scope = await accessScope.GetAsync();            // IRecordAccessScopeProvider 注入
    var hits = await retrievalService.RetrieveAsync(
        query,
        new RetrievalQuery(scope, TopK: topK),
        cancellationToken);

    return hits.Select(h => new
    {
        text = h.Entity.ChunkText,
        sourceLayer = h.Entity.SourceLayer,              // Wiki / Cleaned
        score = h.Score,
        vectorScore = h.VectorScore,
        keywordScore = h.KeywordScore
    });
}

5.3 knowledge_list_sources — 列出／查詢知識來源

分頁列出呼叫者可存取的知識來源（可加關鍵字、分類、團隊過濾）。

[McpServerTool(Name = "knowledge_list_sources")]
[Description("分頁列出呼叫者有權存取的知識來源清單，可依關鍵字過濾。結果已套團隊權控。")]
public async Task<object> ListSourcesAsync(
    [Description("關鍵字（比對標題/描述）；可為 null")] string? search = null,
    [Description("頁碼，從 1 起")] int page = 1,
    [Description("每頁筆數")] int pageSize = 20,
    CancellationToken cancellationToken = default)
{
    var request = new DataRequest { Search = search, /* 分頁欄位依 DataRequest 定義帶入 */ };
    var result = await sourceService.GetAsync(request);   // 內建團隊權控
    return new { total = result.Count, items = result.Result };
}

DataRequest／DataRequestResult<T> 為既有分頁 DTO，實作時對照 KnowledgeSourceService.GetAsync 的欄位使用方式。

5.4 knowledge_get_document — 取得完整文件內容

依知識來源 ID 取回清洗後全文。直接複用 KnowledgeSourceService.GetCleanedContentAsync（已內建團隊權控），不重複權控檢查。

實作採單一 unavailable 錯誤碼：因既有服務對「不存在／未清洗／無權／缺檔」皆回 null，且強行區分 forbidden 與 not_found 會洩漏來源存在性，故收斂為單一 unavailable（權控拒絕的 Warning 已由 service 內部記錄）。

[McpServerTool(Name = "knowledge_get_document")]
[Description("依知識來源 Id 取回清洗後的完整內容。若不存在、尚未清洗完成或您無權存取，回傳 error=unavailable。")]
public async Task<KnowledgeDocumentResult> GetDocumentAsync(
    [Description("知識來源 Id")] int sourceId,
    CancellationToken cancellationToken = default)
{
    var content = await sourceService.GetCleanedContentAsync(sourceId); // 內建權控；null＝不存在/未清洗/無權/缺檔
    if (content is null)
        return new KnowledgeDocumentResult(sourceId, null, null, "unavailable");

    var source = await sourceService.GetAsync(sourceId); // 權控已於上一步驗證，取標題
    return new KnowledgeDocumentResult(sourceId, source.Title, content, null);
}

5.5 knowledge_ping — 連通性診斷（保留）

Phase 0 起提供的最小工具，回傳固定訊息（"KnowledgeExtraction MCP server is alive."），供部署後快速確認「連得上、被列舉、能呼叫」。無業務邏輯、不碰資料；亦受 McpAccess 授權保護。

5.6 knowledge_ask 的 mode 參數（Graph RAG P9，1.0.91）

knowledge_ask 新增選填參數 mode：

mode行為
local（預設，省略即此值）精準檢索：向量＋關鍵字＋圖鄰域三路混合，回傳含出處的片段。與 1.0.90 之前完全相同。
global全域問答：對「呼叫者有權的社群摘要」做 map-reduce（Graph RAG P3），適合「綜觀全部／整體趨勢／系統性根因」類問題。

global 模式的回傳差異（呼叫端必須知道）：

  • sources 恆為空、topScore 恆為 0——社群摘要沒有 chunk 層出處，也沒有相似度可言。
  • confidence 僅表示「有無取到可用的社群重點」（Sufficient / Insufficient）。
  • 取用的社群改由新欄位 usedCommunities（標題清單）回報。
  • 不套用 categories / teams 篩選（社群是跨來源的全域聚合，逐社群篩選沒有意義）。
  • 無可用社群時 answerContext 會帶回可行動的原因（提示管理員需先建立社群摘要），而非空字串。

無法辨識的 mode 值會明確拋錯，不靜默退回 local——否則呼叫端會以為自己走了 global。

5.7 knowledge_graph_neighbors — 實體 N 跳鄰域（Graph RAG P9，1.0.91）

查詢某實體在知識圖譜中的鄰域關係，供 Agent 回答「A 和 B 有什麼關聯」這類問題。

  • 參數：entityName（別名自動解析，查「TSMC」等同查「台積電」）、maxHops（1～3，預設 2）。
  • 回傳：nodes（實體名＋跳數，0＝查詢實體本身）、relations（主詞—關係—受詞＋跳數）、found、truncated。
  • 只回傳已經人工核可的三元組；節點上限 100，達上限時 truncated=true（不靜默截斷）。
  • 本工具為純資料庫查詢、不呼叫 LLM，故不推 OperationContext、不記 Token 用量。

⚠️ 這與檢索的圖遍歷是兩張不同的圖：檢索遍歷「頁」（WikiPage），本工具遍歷「實體」（正規化名稱）。

6. 團隊權控整合（硬性不變量）

CLAUDE.md 將團隊權控列為最關鍵不變量（違反會造成資安漏洞）。所有 MCP 工具必須遵守：

  • 優先複用既有服務內建的權控：KnowledgeBaseChatService.RetrieveAsync、IRetrievalService.RetrieveAsync（需帶 RetrievalQuery.Scope）、KnowledgeSourceService.GetAsync、GraphTripleService.GetNeighborhoodAsync 皆已在查詢層套權控，MCP 工具直接呼叫即可，不得另走繞過權控的低階查詢。

⚠️ mode=global 的權控路徑（P9 的紅線，已由 McpAccessScopeTests 釘住）

全域問答的 ACL 由 GraphCommunityService.GetAccessibleSummariesAsync 把關，它經 IRecordAccessScopeProvider 取 scope。 而 RecordAccessScopeProvider 在 MCP 情境（無 Blazor circuit）下有三條解析路徑，三條都安全：

  1. McpIdentityResolver.ResolveAsync 已填入 CurrentUserService（含 IsAdmin／TeamList）→ 直接用它。
  2. 未填時 fallback 到 HttpContext 的 Sid claim（MCP 的 API Key／JWT 認證會帶）→ 從 DB 取回角色團隊。
  3. 兩者皆無法解析 → 回 (false, [])＝fail-closed，只看得到公開內容。

前提是工具必須先 ResolveAsync 再呼叫 GlobalMapAsync（KnowledgeAskTool 已是此順序）。 另注意社群摘要的 ACL 比一般紀錄更嚴：需社群 Teams 聯集 ⊆ 使用者團隊，或社群純公開—— 因此「甲隊∪乙隊」的社群對只屬甲隊的呼叫者也不可見。

  • 自行查詢時必須套用標準 pattern：
var scope = await accessScope.GetAsync();
if (!scope.IsAdmin)
    dataSource = dataSource.Where(
        TagStringHelper.BuildTeamAccessPredicate<KnowledgeSource>(x => x.Teams, scope.Teams));
  • 單筆記憶體端檢查用 TagStringHelper.IsTeamAccessible(stored, allowedTeams, isAdmin)（管理員恆 true）——見 §5.4 取全文。
  • 規則語意：非管理員只能看「無團隊（公開）或與角色團隊交集」的紀錄；管理員不受限。

⚠️ MCP 工具不得新增任何略過 IRecordAccessScopeProvider 的查詢路徑。新增工具時，把「是否已套權控」列為 code review 必檢項。

7. 認證與權控方案（兩案皆已實作）

MCP client 需要一種方式證明身分，系統才能解析其團隊範圍。兩案皆已落地：/mcp 端點套具名授權 policy McpAccess，允許 Bearer（JWT）／Cookie／McpApiKey 任一 scheme 認證通過（見 §4）。

方案 A：JWT Bearer（推薦）

MCP client 於每次請求帶 Authorization: Bearer <JWT>。JWT 由既有 IJwtTokenService 依 JwtSettings 簽發。實作補上 ClaimTypes.Sid claim（原先缺漏，導致 JWT 非管理員只見公開內容）；RecordAccessScopeProvider 從 HttpContext.User 的 Sid 反查 MyUser + 角色團隊（RoleView.DefaultTeamsJson），得到 RecordAccessScope。

  • 優點：與現有 Web API 完全一致的認證與權控，零新機制；每位使用者天然對映其團隊範圍；可複用限流、稽核。
  • 缺點：JWT 有期限，Agent 端需處理取得/更新 token（可用既有 Auth / ExternalAuth 端點換發）。

方案 B：MCP 專用 API Key

實作為 DB 型金鑰（1.0.9 起）：client 以專用標頭 X-API-Key: <金鑰> 帶入（避免與 JWT 的 Authorization 衝突）。金鑰存於資料庫 McpAccessKey 表（{ Name, KeyValue, UserId, IsEnabled, CreatedAt, UpdatedAt }），由管理員於 /mcp-api-keys 網頁 CRUD 與啟用/停用。自訂 McpApiKeyAuthenticationHandler 經 McpAccessKeyService.FindEnabledMatchAsync（載入啟用中金鑰、定時比對 CryptographicOperations.FixedTimeEquals）驗證後，發帶 ClaimTypes.Sid = UserId 的身分 → RecordAccessScopeProvider 沿用不變，金鑰對映到某個既有帳號的團隊範圍。

  • 優點：對機器對機器（M2M）整合友善，無 token 過期問題；可為每個外部客戶發一把 key；可即時啟用/停用單一金鑰（免重啟）；沿用既有權控（免改）。
  • 缺點：金鑰以明文存 DB（僅管理員可於網頁檢視），team 範圍綁在對映帳號上。（1.0.6 初版為設定型金鑰 appsettings.json Mcp:ApiKeys，1.0.9 已改為 DB 型並移除該設定路徑。）

比較

面向方案 A：JWT Bearer方案 B：MCP API Key
開發成本低（複用既有）中（需新機制）
權控粒度每使用者（精準）每 key（粗）
到期/更新需刷新 token不過期（需撤銷機制）
稽核沿用既有身分稽核需自建 key 稽核
適用有登入身分的互動型 AgentM2M / 固定客戶整合

現況：兩案皆已落地，可依 client 型態擇一——互動型 Agent 用 JWT、固定 M2M 整合用 API Key。

8. AI Agent 如何使用此 MCP Server

MCP Server 上線後，AI Agent 端只需在其 MCP 設定中新增一個「HTTP / Streamable HTTP」型伺服器，指向 /mcp 端點並帶授權標頭。

8.1 通用 MCP client 設定（JSON 示意）

{
  "mcpServers": {
    "knowledge-extraction": {
      "type": "http",
      "url": "https://your-host.example.com/mcp",
      "headers": {
        "Authorization": "Bearer <你的 JWT>"
      }
    }
  }
}

8.2 取得 JWT

呼叫既有登入端點（例如 POST api/Auth/...）以帳密換取 JWT，將回傳的 token 填入上方 Authorization。Token 到期後重新換發。

8.3 連線後 Agent 會看到的工具

連線成功後，Agent 會在工具清單中看到：knowledge_ask、knowledge_search、knowledge_list_sources、knowledge_get_document、knowledge_graph_neighbors（1.0.91 起），並可依各工具的 Description 自動判斷何時呼叫。

8.4 透過 MCP Server 能做到哪些事

  • 用自然語言問答企業知識，並取得出處（可追溯到來源）。
  • 檢索原始片段，讓 Agent 自行彙整、比對、摘要。
  • 盤點知識來源（有哪些文件、屬於哪些分類/團隊）。
  • 取回單一文件全文做深入閱讀或再加工。
  • 以上全部自動套用呼叫者的團隊權限——Agent 永遠看不到使用者無權存取的內容。

10. 分級日誌與稽核設計

MCP Server 被呼叫時，每個重要動作都要寫入日誌，並依嚴重性分到不同等級（Level），以利日後除錯與分析。設計完全沿用專案既有日誌慣例（docs/operations/日誌與設定檔說明.md、docs/architecture/開發慣例與限制速查.md §1.1），不新增另一套機制。

10.1 沿用既有基礎設施

  • 框架與輸出：NLog（nlog.config），單組每日檔案 target（AppCatchAll 規則、minlevel 為唯一等級開關、autoReload 改檔即生效），可經 /log-settings 頁面熱切等級。MCP 日誌自然落入同一檔案，無需新增 target。
  • Layout 情境欄位：既有 layout 每筆帶 ${aspnet-TraceIdentifier}（每 HTTP 請求的關聯 id，MCP 呼叫天然具備）＋ user=/op=/id= 三個情境欄位（來自 BeginScope）。
  • 情境 scope helper：每個工具方法開頭用 LogScope.Of 建立作業情境，讓下游所有日誌自動帶上「誰、做什麼操作、哪筆 Id」：
using var _ = logger.BeginScope(LogScope.Of("McpAsk",
    ("UserAccount", userAccount), ("RecordId", sourceId)));

UserAccount 由 IRecordAccessScopeProvider／HttpContext 身分解析取得；op 用 McpAsk/McpSearch/McpListSources/McpGetDocument 區分工具。

10.2 各工具「三點式」呼叫日誌（開始 / 成功 / 失敗）

比照專案「外部呼叫三點式」鐵則，每次工具呼叫都記開始、成功或失敗三態：

[McpServerTool(Name = "knowledge_ask")]
public async Task<object> AskAsync(string question, /* … */ CancellationToken ct)
{
    using var _ = logger.BeginScope(LogScope.Of("McpAsk", ("UserAccount", userAccount)));
    logger.LogInformation("MCP 工具呼叫開始。tool=knowledge_ask questionLen={Len}", question?.Length ?? 0);
    try
    {
        var result = await chatService.RetrieveAsync(question, /* … */ ct);
        logger.LogInformation(
            "MCP 工具呼叫成功。tool=knowledge_ask 命中數={HitCount} 最高分={TopScore} 信心={Confidence}",
            result.Sources.Count, result.TopScore, result.Confidence);
        return /* … */;
    }
    catch (Exception ex)
    {
        logger.LogError(ex, "MCP 工具呼叫失敗。tool=knowledge_ask");
        throw;
    }
}

10.3 各等級（Level）記什麼

等級MCP 情境（記什麼）
Trace逐工具參數細節、檢索中間值（預設關，深度除錯才臨時開）
Debug工具進入點與參數摘要（topK、分類/團隊過濾值、sourceId）、身分解析結果（IsAdmin、團隊數量）（Prod 不開）
Information里程碑：工具呼叫開始、呼叫成功（帶 metrics：命中數/最高分/信心/耗時）、MCP endpoint 連線建立
Warning可恢復/預期失敗：knowledge_get_document 無法取得（unavailable：不存在／未清洗／無權）、查無依據（Insufficient）、稽核寫入失敗、API Key 無效、JWT/授權未過
Error例外、檢索/DB 失敗、下游服務（OpenAI 嵌入）錯誤（LogError(ex, …)）
Critical幾乎無法運作（如 DB 完全不可用），沿用既有全域處理

權控拒絕務必記 Warning：這是資安可歸責事件（誰嘗試存取越權來源），對照既有 KnowledgeSourceService 的權控拒絕 Warning 慣例。

10.4 稽核（Audit）——比照 KnowledgeBaseQueryAudit

MCP 問答（knowledge_ask）應寫入既有 KnowledgeBaseQueryAudit 稽核表（EVAL-2 + SEC-5），與 Blazor 問答同軌，並沿用其三大不變量：

  • 只存身分＋metrics，不存本文：記 UserAccount/UserName/IsAdmin/Teams、查詢長度、HitCount/TopScore/Confidence、命中明細（{id, layer, score}）；不存問句本文、context 或 chunk 文字。
  • 日誌＋DB 雙軌：寫 DB 前先記一筆結構化 LogInformation（IsAdmin=… Teams=… 命中數=… 最高分=… 信心=…）。
  • 稽核失敗不得影響主流程：整段以 try/catch 包裹，失敗只記 LogWarning(ex, "MCP 問答稽核持久化失敗（不影響回答）。")。

可選：於稽核加一個「來源通道」欄位以區分 Blazor/MCP（需動 Entity → 須補雙資料庫 migration）；若不想動 Entity，改以日誌 op=McpAsk 區分即可。此為實作時的取捨點。

10.5 遮罩與隱私（不變量）

  • 不記 JWT／API Key／密碼／token，不記問句本文與回傳內容本文；情境 scope 只放帳號/團隊名/操作/Id（沿用 LogScope.Of 註解約束）。
  • catch 不得靜默：即使吞例外也要留 Warning/Debug 與原因（受 LoggingConventionTests 守則測試把關）。

11. 安全性與限制

  • 權控不可繞過：見 §6。所有工具皆須經 IRecordAccessScopeProvider；新增工具的 code review 必檢此項。
  • 限流：可對 /mcp 套 .RequireRateLimiting("api")，與現有 API 共用限流政策，避免濫用。
  • 稽核與日誌：見 §10。MCP 問答寫入 KnowledgeBaseQueryAudit，重要動作分級寫日誌，與現有 SEC-5 稽核、日誌可診斷化強化一致。
  • 提示注入防護：知識內容作為 context 回傳給外部 Agent 時，沿用既有 SEC-1/SEC-2 的注入防護與遮罩不變量觀念。
  • 為何不用 stdio：stdio transport 無 HttpContext，無法沿用 JWT 身分解析與團隊權控，且不適合對外多租戶場景；故本設計採 HTTP transport。

13. REST 對應：KnowledgeGraphController（1.0.96）

§5.6（knowledge_ask 的 mode=global）與 §5.7（knowledge_graph_neighbors）那兩項圖譜能力，1.0.96 起對等開放給一般 REST 呼叫端，供無法講 MCP 協定的系統整合（Controllers/KnowledgeGraphController.cs，雙路由 api/[controller] 與 api/v1/[controller]，[Authorize(JwtBearer)]）。

MCP 工具REST 端點行為差異
knowledge_ask（mode=global）POST /api/v1/KnowledgeGraph/global-askLLM 未設定時回 503（MCP 是拋工具錯誤）。兩者都只做 map 不做 reduce
knowledge_graph_neighborsGET /api/v1/KnowledgeGraph/neighbors?entityName=&maxHops=maxHops 超出 1～3 回 400；MCP 則靜默夾住

兩處刻意不同，不是不一致：

  1. maxHops 超界：REST 以 [Range(1, GraphTripleService.MaxNeighborhoodHops)] 明確回 400；MCP 靜默夾住。理由是呼叫端性質不同——MCP 的呼叫端是 LLM，夾住比報錯更能讓對話繼續；REST 的呼叫端是程式，明確報錯才能讓 bug 及早浮現。慣例見 Web API 設計慣例。
  2. LLM 未設定：回 503（服務依賴未備妥）而非 500。同上文件。

共用與刻意不共用：

  • ✅ 身分解析重用 McpIdentityResolver：由 Sid claim 反查填入 CurrentUserService，與 MCP 走同一條把關程式碼。權控完全交給既有服務（GraphTripleService／GraphCommunityService），控制器本身不做任何權限判斷——這是刻意的，避免權控邏輯出現第二份實作。
  • ❌ Token 作業別刻意不重用 Blazor 常數：用專屬的 LlmTokenUsage.OperationApiGraphGlobalAsk 並標記 LlmChatLog.OriginApi，否則報表上分不出是網頁使用者還是外部程式打的。見 LLM 提示詞與用量透明化 §5。
  • ❌ DTO 刻意不含 sources 與 topScore：全域模式本來就沒有 chunk 層出處與相似度，留空欄位只會讓呼叫端誤以為「這次剛好沒有」。改回傳 usedCommunities。

非目標（與 MCP 一致）：沒有寫入型端點——無法透過 REST 新增或核可三元組。審核是治理動作，刻意只留在網頁上。

⚠️ 已知限制：

  • global-ask 沒有 HTTP 層的 leak=0 端到端測試（服務層已覆蓋）；上線前建議手動以非管理員帳號驗一次。
  • 沒有 API 專用節流，成本只靠 Retrieval.GraphGlobalCommunityCap（預設 20）控管。對外開放時請在前端閘道加限流。

操作說明見 知識圖譜（Graph RAG）使用指南 §十。
