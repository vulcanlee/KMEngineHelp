系統架構

開發慣例與限制速查（AI / 開發者必讀）

文件目的

這是 AI 協作與開發者動手前的單一入口：集中列出本系統「改錯就會壞」的鐵則、不變量與踩雷點，並指向更深入的文件。先讀本檔的「鐵則」，再依連結深入對應 docs；當與其他文件衝突時，以本檔的不變量為準。

本檔採「一句話 + 連結」原則，不複製深文件內容；細節請點連結。

1. 必守鐵則 / 不變量（DO & DON'T）

1.1 流程與編碼

  • 版本號：每次完成一次可建置的異動，appsettings.json 的 SystemSettings.SystemInformation.SystemVersion +1（唯一版本來源），並於 commit message 說明。純文件/腳本變更可不升版。（→ 維護規範）
  • 文件編碼：docs/*.md 必須 UTF-8 含 BOM、繁體中文、不得有亂碼；提交前跑 pwsh -File scripts/Test-DocsEncoding.ps1 必須全綠（檢查 BOM=True 且無 U+FFFD）。
  • 文件同步：每次程式異動後，同步更新相關 docs（資料模型、安全、索引、發行說明等）。（→ 維護規範）
  • ⚠️ 新增 changelog 必須寫兩份索引：docs/changelog/README.md（表格）與 docs/README.md 的「changelog — 變更紀錄」分區。兩者無任何守門測試，只漏其中一份不會有任何錯誤——1.0.81～1.0.88 共九筆（含 Graph RAG P1～P6）就是只寫了前者、後者停在 1.0.80，到 1.0.88 才被發現並補回（見 文件債補正）。同理，新增 migration 要補 EFCore 指令備忘 的清單（該次也漏了三筆）。
  • 既有分析／設計文件已被後續實作推翻時，優先「追記」而非改寫：那些文件記錄的是當時的判斷依據（例如 Graph RAG 藍圖 §2 的「導入前現況盤點」），直接改寫會抹除決策脈絡。作法是文首加實作現況區塊、各節加一句追記，並明確標出仍未實作的部分。
  • 新增 @page 路由時，須在 Datas/HelpTopics.json 登記頁面說明，或列入 PageHelpCatalogTests.RoutesWithoutHelp 並附排除理由（1.0.101）。二者皆無會讓 EveryPageRoute_IsEitherInCatalog_OrExplicitlyExcluded 紅燈——這是刻意的，逼出「這一頁要不要有說明」的自覺決定，而不是讓新頁面靜默地沒有說明入口。
  • 改動頁面的控制項（新增/移除按鈕、改欄位、改分頁）時，須同步該頁說明檔的「三、畫面上有哪些按鈕、各自做什麼」（Datas/Help/<slug>.md，檔名規則見 PageHelpService.ToSlugFileName）。⚠️ 這一條沒有守門測試——正則比對 markup 的誤報率會高到讓人把檔案加進排除清單，而一有排除清單守門就開始腐爛（ToastConventionTests 的教訓）。所以它是流程紀律，不是機器檢查。
  • 每份說明檔的前言必須含「一分鐘看懂這一頁」區塊（1.0.103）：H1 標題與一句摘要之後，接一個 ### 一分鐘看懂這一頁 小標 ＋ 至少 5 條清單（實際全部寫 6 條：解決什麼問題／誰會用到／在流程的哪一站（維運類可改寫成「它在系統的哪個位置」）／開始前要準備／做完會得到／它不做什麼）。由 PageHelpCatalogTests.EveryHelpDocument_HasSubstantiveQuickLookPreamble 守著（含每條的字數下限，擋敷衍的一句話）。⚠️ 小標必須是 ### 不可寫成 ##——## 會被 PageHelpMarkdownParser 切成第七個章節，讓左側章節導覽多一項且六大段白名單守門紅燈；另有 QuickLookHeading_IsNeverWrittenAsATopLevelSection 專門把這個成因寫在錯誤訊息裡。內容紀律：不得與底下「一、功能摘要」重複（摘要講「能做哪些操作」，這一段講「為什麼要有這頁、輪不輪得到我、做完得到什麼」），且同樣受下一條的「不含任何可調參數」限制。
  • in-app 說明（Datas/Help/）與 docs/guides/ 的分工是硬性的：guides 是權威、完整、含參數與公式；in-app 說明是入門、短、不含任何可調參數與數學。參數／門檻／公式一律不進 in-app 說明——它必然過時，而過時的參數說明會害人調錯。每份說明檔結尾固定一行指向權威文件檔名。
  • ILogger 使用規範（可診斷化）：日誌框架為 NLog（建構式注入 ILogger<T>；手動 new 的 helper 由建立端以 ILoggerFactory.CreateLogger<T>() 注入）。等級：Trace＝最細流程/迴圈逐步/大量診斷細節（預設關，深度診斷才開）；Debug＝流程節點/輸入參數/外部工具參數與 stdout-stderr 摘要/CRUD 進入點（Prod 預設不開）；Information＝里程碑（建立/更新/刪除成功、狀態轉換、外部 API 起訖、啟動環境摘要）；Warning＝可恢復/預期失敗（找不到、驗證未過、團隊權控/頁面權限拒絕、靜默放棄的加值步驟）；Error＝例外/外部行程非 0 結束或逾時/IO 失敗/API 非 2xx（用 LogError(ex, ...)）。鐵則：①外部呼叫（OpenAI/ffmpeg/yt-dlp/抖音/MarkItDown）一律「開始→成功→失敗（含 ExitCode/StatusCode/StdErr 或回應前 ~500 字）」三點式；②catch 不得靜默——即使吞例外不中斷，也要留一筆日誌與原因（空 catch {} 由 LoggingConventionTests 守則測試擋下）；③不記 ApiKey/密碼/token、不記請求/回應本文（情境 scope 只放帳號/團隊名/操作/Id）。
  • 分級與臨時切換（0.3.23）：預設等級＝nlog.config 的 <logger name="*" ruleName="AppCatchAll" minlevel="info">（info）。MEL（appsettings 的 Logging:LogLevel:Default）設為 Trace 放行，把實際等級交給這條 NLog 規則決定（NLog provider 的 IsEnabled 會依規則短路，故仍高效）。臨時看 Debug/Trace 有兩種方式、皆免重啟：(a) 把該行 minlevel 改 Trace 存檔（autoReload 立即生效），改回 info 恢復；(b) 管理員頁 /log-settings（NLogLevelController 以 ReconfigExistingLoggers 執行期切換，暫時覆蓋，存檔/重啟後回到檔案預設）。
  • 執行環境情境（0.3.23）：以 ILogger.BeginScope(LogScope.Of("Operation", ("RecordId", id)))（KnowledgeExtraction.Share.Helpers.LogScope）把「當時運作情境」附到範圍內每筆日誌；NLog layout 已加 user=/op=/id= 欄位（＋既有 TraceId）。請求層（UseHttpRequestLogging）自動帶使用者＋操作；背景管線帶 Operation＋RecordId。啟動時以 RuntimeEnvironmentInfo.StartupSummary 記一次系統摘要（OS/版本/DB/LLM 提供者）；例外時以 RuntimeEnvironmentInfo.Snapshot() 附機器/程序/記憶體快照。堆疊由 NLog layout（toString,StackTrace）自動渲染。
  • 未處理例外一律留日誌：API 走 ApiExceptionFilterAttribute、MVC 全域走 /Error、Blazor 元件包在 LoggingErrorBoundary（OnErrorAsync 記 LogError＋快照）——皆含堆疊＋TraceId＋快照。
  • 臨時開 Debug/Trace 詳見 日誌與設定檔說明。
  • 頁面例外不會走 HTTP 例外處理器：App.razor.cs 的 RenderModeForPage() 讓除 /Auths/* 外的所有頁面都用 InteractiveServerRenderMode(prerender: false)，因此頁面內的例外走 Blazor circuit、不經過 UseExceptionHandler。能走到 /Error 的只有 SSR 外殼本身的失敗與非 Blazor 端點；Controller 另有 ApiExceptionFilterAttribute。診斷「為什麼 /Error 沒被觸發」時先想到這一點。
  • Blazor Server SignalR 訊息上限：Program.cs 已於 AddInteractiveServerComponents().AddHubOptions(...) 將 MaximumReceiveMessageSize 提高至 10MB（預設僅 32KB）。勿改回預設——長逐字稿/長文字經 AntDesign TextArea 由用戶端同步回伺服器時會超過 32KB → circuit 中斷 → 反覆重連（畫面閃爍）＋ Cannot send data ... 'Connected' State。（見 2026-06-17 提高 SignalR 訊息上限）

1.2 資料層（EF Core）

  • DbSet 名稱 ≠ Entity 名稱：DbSet 為 MyTas/MyTasFile，Entity 為 MyTask/MyTasFile（早期命名）。新增 migration 時留意避免誤產生 rename。（→ 資料模型與資料庫 §5）
  • 雙 provider migration：每次模型變更要各產生一次 —— Sqlite 於 KnowledgeExtraction.AccessDatas；SQL Server 於 KnowledgeExtraction.AccessDatas.SqlServerMigrations（產生時設 SystemSettings__DatabaseProvider=SqlServer）。（→ EFCore）
  • 追蹤清理：Service 在 Update/Delete 前呼叫 CleanTrackingHelper.Clean<T>(context)，避免追蹤衝突。
  • Cascade 範圍：僅 Project/MyTask/Meeting → 各自 Files 為 Cascade，其餘外鍵為 Restrict；且實體檔案仍須 Service 層手動刪除（EF 只處理資料列）。（→ 資料模型與資料庫 §2.2–2.3、檔案上傳機制）
  • AI 對話紀錄＝中繼資料入庫、全文存磁碟（1.0.39）：聊天採「中繼資料入庫、全文存檔」。LlmChatLog（每輪一列，含 SessionId/TurnIndex）與 LlmChatSession（每段對話一列：誰／何時／哪個頁面 Origin／標題／輪數／最後活動）只存中繼資料；提問、回覆與當時系統提示詞設定條件存於 ExternalFileSystem.ChatLogPath 下——per-turn .md（既有）與 per-session sessions/{yyyy}/{sessionId}.json（ChatSessionService，UTF-8 無 BOM）。ChatLogService.WriteAsync 帶 SessionId 時委派 ChatSessionService.AppendTurnAsync 彙整；寫紀錄失敗一律隔離、絕不中斷聊天。使用者端「我的對話／續談」（MyChatSessionsDrawer）讀 session 時以 requireOwnerAccount 本人越權保護；管理員 /chat-sessions 不套本人限制。
  • 新增 LLM 提示詞槽位要同步 3 處（1.0.77）：①Models/Systems/LlmPromptKeys.cs 的常數 ＋ AllKeys ②LlmPromptsSettings 的屬性 ＋ Get() 的 case ③appsettings.json 的 LlmPrompts 區段（值留空即可＝沿用程式 fallback）。由 Tests/LlmPromptSlotTests.cs 守著。
  • ⚠️ 漏 ② 是靜默失效：Get() 回 null → 直接跳到程式 fallback，而 DB 層仍正常，所以不會有人發現 appsettings 那層失效了。手寫的 LlmPromptResolverTests 抓不到——沒有人會為「自己剛忘記接線的鍵」補一條測試（已實測：注入一個新槽位鍵後，該檔 8 條全綠、LlmPromptSlotTests 紅燈）。
  • 槽位鍵字串的唯一來源是 LlmPromptKeys，放在 Models 而非 Business，因為相依方向是 Business → Models（LlmPromptsSettings 在 Models、需要引用這些常數）。1.0.77 之前兩邊各寫死一份、互不引用。
  • DB /prompts 覆蓋槽位時名稱必須逐字精確（x.Name == name）。打錯無錯誤、無日誌，只會安靜退回內建預設。/prompts 名稱欄已有即時判定提示；判定用 LlmPromptKeys.IsSlotKey，必須與 DB 一樣是精確比對，寬鬆比對會給出「看起來對了但不生效」的錯誤保證。
  • ⚠️ Prompt 表同時是「系統槽位覆蓋層」與「使用者自由提示詞清單」（4 個檢視用 PromptService.GetAllEnabledAsync() 當選單）。所以任意名稱合法，/prompts 不可改成槽位下拉限定，只能提示、不能阻擋。
  • 選單／實體名詞改名的四個硬排除（1.0.76）：改名時禁止跨檔全域取代，一律逐處手改。下列四類即使字面命中也不可動：
  • MagicObjectHelper 的 角色_* 常數值（DB 既存值，寫在每個角色的 RoleView.TabViewJson）。⚠️ 7 個識別字（角色_工作項目／角色_圖片清單／角色_分類清單／角色_團隊清單／角色_提示詞清單／角色_清洗設定檔／角色_知識來源管理清單）在文字上包含常見的舊名，全域取代會波及它們 —— 那會編譯失敗（好結果），但若有人「順手改識別字讓它編過」，常數值就一起被改掉＝所有既有角色掉權限。由 PermissionConstantCanaryTests 硬編守著（MenuPermissionAlignmentTests 兩邊同源，保護不了這件事）。
  • 會 SaveChanges 落地到資料列的字串。例：MeetingService.cs 掛載會議錄音時寫入的 MediaTranscriptionAdapterModel.Description（$"由會議記錄（Id=…）掛載上傳"）—— 它同時顯示在清單描述欄，長得像 UI 標籤，改了卻會讓新舊資料列分歧且無法回溯。
  • 送給 LLM 的提示詞（LlmPromptDefaults／DB 提示詞）：改字會改變模型行為。
  • 會議紀錄（紀）約 100 處：那是 AI 產出的會議紀要文件，與選單改名無關。只有 會議記錄（記）才是舊選單名。禁用 會議[記紀]錄 這類寬鬆 regex；MeetingViewView.razor.cs 與 LlmPromptDefaults.cs:59 都有「同一句／同一字串內兩種寫法都出現」的情形。
  • 定位用的安全 regex（只看字串常值、排除權限識別字）：rg -n '"[^"]*舊名[^"]*"' src/KnowledgeExtraction | rg -v '角色_|MagicObjectHelper'
  • 驗收一律以 git diff --stat HEAD -- '*MagicObjectHelper.cs' '*RolePermissionService.cs' 必須無輸出為準。
  • 註解／XML doc／log 樣板刻意不改（1.0.71 起的既有原則）：混進來會讓 diff 膨脹，反而遮蔽真正有風險的那幾行。
  • 清單查詢的排序必須無條件收斂到預設值（1.0.73）：Skip/Take 若沒有 ORDER BY，回傳順序未定義 → 翻頁會重複或漏列。所以排序不可包在 if (SortField 非空) 內，一律用 (SortField, SortDescending) switch { …, _ => 預設 }（範本：KnowledgeSourceService／WikiPageService），讓 _ => 一次兜住三個洞：①SortField 為空 ②SortDescending 為 null ③SortField 不在支援清單。
  • ⚠️ 第 ② 個洞才是實際的使用者症狀來源，也最容易被漏掉：DataRequest.SortDescending 是 bool?，而 AntDesign 表頭排序循環到「取消」時 SortField 仍是欄位名、只有方向變 null。1.0.56 修完 Take 後，這 5 支（RoleViewService／MyUserService／MeetingService／MyTasService／ProjectService）的內層還留著 37 處 … : dataSource，症狀持續到 1.0.73。只補外層 else 修不掉。
  • 預設一律「最近更新新到舊 ＋ Id 決定性 tie-break」。注意 RoleView／MyUser 的欄位名是 UpdateAt（無 d），其餘是 UpdatedAt。
  • 由 Tests/ListDefaultSortPagingTests.cs 守護；該檔註解說明了「哪一組測試真正抓得到、哪一組在 SQLite 下抓不到」，新增測試前先讀。
  • 新增素材型別（KnowledgeSourceItem.ItemType）必須同步 4 處（1.0.70）：成員是軟參照（ItemType＋ItemId、無硬 FK），所以每加一種素材型別都要逐一補齊，漏一處就是靜默錯誤：①KnowledgeSourceContentAggregator（讀內容）②KnowledgeSourceService.GetMaterialInfoAsync（顯示資訊）③該型別 Service 的刪除與內容編修路徑（呼叫 KnowledgeSourceMaintenanceHelper.MarkOwningSourcesStaleAsync，刪除用 removeOrphanItems: true、編修用 false）④DataConsistencyService 的 existing 字典與 GetSummaryAsync 的 OR 條件。1.0.25 加入第四種「會議紀錄」時只補了 ①②，結果 ③ 讓編修/刪除會議後所屬來源不會標記過時，而 ④ 讓每一筆正常的會議紀錄成員都被判為孤兒 —— 管理員在 /data-consistency 按「清除孤兒」就會真的刪掉它們。由 Tests/DataConsistencyTests.cs 與 Tests/MeetingKnowledgeSourceStaleTests.cs 守護。

1.4 多值標籤（分類 / 團隊）

  • 儲存格式：以分隔字元包夾的字串（如 \nA\nB\n），對外以 List<string> 呈現。轉換/查詢一律走 TagStringHelper（KnowledgeExtraction.Business/Helpers/TagStringHelper.cs）。
  • 過濾/比對：用 TagStringHelper.BuildContainsAnyPredicate（OR）做查詢；務必精確成員比對（「團隊」不可誤中「團隊2」）。
  • 清單顯示用唯讀字串屬性（如 CategoriesText/TeamsText），勿在 Razor 內對 List 直接做欄位範本而踩到型別問題。

1.5 團隊資料權控（資安不變量）

  • 可見性規則（非管理員）：紀錄 Teams 為空（公開）或 與使用者角色團隊有交集才可見；管理員（MyUser.IsAdmin）不受限。
  • 全路徑強制：套用於五紀錄的 Service（清單/單筆/下載）、Project/MyTask/Meeting 的 Repository（清單/單筆/編輯/刪除）、Controller，以及 MCP 工具（Web/Mcp/）。任何新查詢、新 Controller、新下載端點、新 MCP 工具都必須透過 IRecordAccessScopeProvider 取得 (IsAdmin, AllowedTeams)，並用 TagStringHelper.BuildTeamAccessPredicate（查詢）或 IsTeamAccessible（單筆）套用，否則就是資安漏洞。

  • LLM 串流的逾時分兩種，不可混用（1.0.33 ＋ 1.0.98）：OpenAIChatCompletionClient.StreamAsync 以 HttpCompletionOption.ResponseHeadersRead 讀 SSE，故 GenerationTimeoutSeconds（HttpClient.Timeout）只界定取得回應 headers 的時間、不涵蓋讀取 body——這是 1.0.33 為了解除長內容的總生成時間硬上限而刻意設計的，⚠️ 不可改回總時長逾時（實測單一清洗步驟合法地連續串流 14 分鐘，改回去會在第 2 分鐘砍掉它）。1.0.33 自陳的殘留風險「連線中途完全停滯可能久候」由 1.0.98 的 GenerationStreamIdleTimeoutSeconds 補上：以 linked CTS 對每次讀取設閒置逾時、收到任何一行就 CancelAfter 重設。⚠️ 必須以 cancellationToken.IsCancellationRequested 區分兩種取消：使用者取消照原樣拋 OperationCanceledException（CleaningProcessor 才認得出「已取消」而非「失敗」）、閒置逾時丟 TimeoutException（PipelineRetryHelper.IsTransient 對它回 false → 不重試、直接標失敗並顯示可行動原因）。⚠️ yield return 不能寫在含 catch 的 try 內，讀取要抽成區域函式、yield 留在 try 之外。此逾時同時作用於 Blazor 知識問答串流與 MCP。

1.8 背景處理管線（佇列＋背景服務＋Processor）

  • 所有背景管線同構：一律為 I*Queue（Channel<PipelineJob> Singleton）→ *BackgroundService（出列、OperationContext.Push 後建 DI scope）→ *Processor（Scoped，更新狀態／進度／錯誤訊息）。新管線一律比照。
  • 目前共 7 條（1.0.45 起）：①媒體轉錄 ②文件轉文字 ③圖片識別 ④資料清洗 ⑤知識頁審核 ⑥嵌入索引 ⑦會議紀錄產生。
  • ⚠️ 舊文件曾寫「三條匯入管線」，那是管線只有三條時的說法，已隨管線增加而過時；PipelineNames／PipelineCancellationRegistry／PipelineRetryHelper 的同名註解已於 1.0.20 一併更正。
  • 管線間的觸發：轉錄成功後以「加值步驟」入列會議紀錄管線（TranscriptionProcessor.TryEnqueueMeetingMinutesAsync）。加值步驟必須放在終態寫入之後且自帶總 try/catch——放之前若拋例外會被外層 catch 接到，把「其實已成功」的轉錄標成失敗。
  • 重啟回復只撈自己的狀態：管線的 RecoverPendingAsync 不得撈其他管線負責的狀態值（如會議紀錄管線只撈「產生中」，不撈「轉錄中」），否則會在前置作業尚未完成時就重跑而必然失敗。
  • 狀態常數放 AdapterModel：等待中／處理中／已完成／失敗／已取消（圖片另有初始「未解讀」）。
  • 取消：背景服務處理每筆時向 IPipelineCancellationRegistry（Singleton，Business/Services/Pipelines/）註冊 linked token；Service 的 Delete/Cancel 以 TryCancel(PipelineNames.X, id) 中止；Processor 出列時跳過「已取消」。
  • ⚠️ 佇列無法列舉：7 條佇列都是 Channel.CreateUnbounded，讀取即消耗。所以「取消還在排隊的工作」不是從佇列移除，而是把 DB 狀態改成「已取消」、由 Processor 出列時跳過 —— 每條管線的 Processor 都必須有這道前置檢查，漏了就等於該管線完全不支援取消（會議紀錄管線就漏了，直到 1.0.78：出列後照跑、還多付一次 LLM token）。
  • 也因此「還有多少待處理」一律由 DB 狀態推導，不可用 Channel.Reader.Count：出列瞬間 job 已離開 channel 但 DB 還沒寫成處理中（少算）、取消後 job 仍躺在 channel 裡（多算）、重啟後 channel 歸零但 DB 仍是處理中（少算一整批）。見 PipelineJobQueryService。
  • 7 條管線的取消統一入口是 PipelineJobCancelService（1.0.78，供 /pipeline-jobs 使用）：它只做 switch 分派、不重寫取消語意（CleanTrackingHelper.Clean ＋ 團隊權控 ＋ TryCancel fall-through 全部沿用各 Service 既有方法）。⚠️ 清洗／蒸餾／索引三條同表、同 Id、同「已取消」字面值，分派接錯時 Success 仍為 true、UI 仍彈成功、DB 也真的多一個「已取消」，只是在錯的欄位上 —— 測試必須斷言「目標欄位變更且另兩欄未被動到」。
  • 重試：Processor 核心抽 ProcessCoreAsync，外層依 PipelineRetryHelper.IsTransient 自動重試（最多 2 次）；手動重試走 Service 的 RetryAsync（僅失敗/已取消）。
  • 重啟回復：背景服務啟動時把「等待中／處理中」重新入列（佇列在記憶體，重啟即遺失）。
  • 進度事件（1.0.23）：管線每完成一個處理動作要呼叫 IPipelineProgressReporter.Report("繁中訊息"[, Level])（Business/Services/Pipelines/），前端輪詢後逐則彈 toast。比照 ITokenUsageRecorder 樣板：Singleton＋Channel、非阻塞、失敗隔離、不碰 DbContext，故 Processor 任一深處都能直接呼叫；管線名／紀錄 Id／提交者全部自動取自 OperationContext.Current，呼叫端只給訊息、不傳參數。落地由 PipelineProgressWriterBackgroundService 以自建 scope 的獨立 BackendDBContext 執行，並負責清除 3 天前的舊事件。
  • 不要加批次計時器：writer 刻意採「await foreach 阻塞等待 ＋ TryRead 只撈已在通道裡的」模式，寫入延遲僅個位數毫秒；任何湊批等待都會直接疊加在使用者感受到的延遲上（前端已有 0~5 秒輪詢延遲）。
  • 事件訊息不得含紀錄標題或任何內容本文（逐字稿／清洗結果／LLM 回覆），只放階段名、計數、字數、檔案大小。事件查詢以 UserAccount 精確相等過濾而非團隊權控，訊息保持無狀態才能在權限異動後仍不外洩。
  • 入列一律帶提交者：Service 層呼叫 EnqueueAsync 必須傳 currentUserService.CurrentUser.Account/.Name，否則身分到不了 OperationContext，token 用量會歸屬不到人、進度通知一則也發不出來（PipelineEnqueueIdentityTests 守護）。背景服務的 RecoverPendingAsync 刻意傳 null（非使用者觸發，無人等 toast），屬例外。
  • 註：IDocumentExtractionQueue 原本是唯一未採 PipelineJob 的佇列（排裸 int、背景服務未 Push OperationContext），已於 1.0.23 補齊為與其他 7 條同構。
  • 影片轉碼（加值步驟）：URL 來源保留的原始影片於下載後經 VideoTranscoder 正規化為 H.264/AAC MP4（非 H.264 MP4 才轉，如 HEVC/VP9），確保「下載來源檔案」可在一般 Windows 播放器直接播放；轉碼失敗只記 LogWarning、保留原檔、不中斷主流程。
  • 變更紀錄見 2026-06-10 三管線佇列化重試取消。

1.8.1 資料清洗管線與品質保證（QA-1..QA-4）

  • 第四條管線：ICleaningQueue → CleaningBackgroundService → CleaningProcessor，比照 §1.8；CleaningProcessor 另呼叫 CleaningEnhancer 做 LLM 去重/遮罩/分類/摘要/信心自評（重用 IChatCompletionClient）。
  • KnowledgeSource 狀態機（常數於 KnowledgeSourceAdapterModel）：草稿 → 等待中 → 處理中 → 已清洗／待審核（QA-2 低信心）／失敗／已取消；已退回（QA-3 人工退回）。DbSet 名 KnowledgeSource 與 Entity 同名（無 MyTas 式落差）。
  • 遮罩失敗即整筆失敗：CleaningEnhancer 遮罩步驟不吞例外（漏遮＝外洩風險），其餘步驟可降級；LLM 未設定（IsChatLlmConfigured() 為 false）則整段略過。
  • 信心自動門檻：清洗完成依 SystemSettings.Cleaning.ConfidenceThreshold（預設 0.70）路由：信心 ≥ 門檻 → 已清洗；否則（或信心 null）→ 待審核。
  • 人工審核（QA-3）：KnowledgeSourceService.ApproveAsync/RejectAsync 強制 角色_知識審核 動作權限＋團隊權控（→ 認證授權）。
  • 清洗結果儲存與編修：清洗結果只存檔案、不存 DB——CleaningProcessor 以 Encoding.UTF8 寫入 ExternalFileSystem.CleanedSourcePath 下 {年}/{guid}.md，DB 僅存相對路徑 CleanedContentRelativePath（無內容欄位）。「檢視清洗結果」走 ContentEditDialog（ShowPreview/Note），存回經 KnowledgeSourceService.UpdateCleanedContentAsync（比照其他 Update*ContentAsync：CleanTrackingHelper.Clean → 團隊權控 → 原地覆寫同檔、Encoding.UTF8、僅更新 UpdatedAt、不改狀態、不需 migration）。（見 2026-06-17 清洗結果可編修複製預覽）
  • 清洗規則設定（CleaningProfile）：命名的五段清洗提示詞（去重/遮罩/分類/摘要/信心，皆可空＝該步驟用內建預設），管理頁 /cleaning-profiles（權限 角色_清洗設定檔）。知識來源「清洗」可選設定檔並寫回 KnowledgeSource.CleaningProfileId（重試沿用）。提示詞套用優先序：來源有指定設定檔→各步驟「設定檔非空用設定檔、空用內建預設」並略過全域 清洗-*；未指定（null）→沿用全域 清洗-*→內建預設。CleaningEnhancer.EnhanceAsync(rawBody, CleaningPromptSet? overrides, ct) 帶入；清洗品質評測 EvaluateOneAsync 不傳（行為不變）。（見 2026-06-17 清洗設定檔、清洗規則設定 PRD）
  • 清洗品質評測（QA-4）：CleaningEvaluator（純函式）量化遮罩召回率/分類 P-R-F1/摘要涵蓋率＋門檻掃描；可接受門檻已鎖定於 strategy/05 §五（量測非硬閘，套用門檻＝改 appsettings）。無任何已評測樣本（門檻列 EvaluatedCount 全為 0）時，RecommendThreshold 回傳 null（尚無推薦門檻），不可對空序列 .Max()/.Min()（見 2026-06-17 修復黃金評測空樣本崩潰）。
  • LLM 雲端/地端切換：OpenAISettings.GenerationProvider(Cloud/Local) + LocalBaseUrl/LocalGenerationModel/LocalApiKey(選填)/LocalGenerationTimeoutSeconds；地端可免金鑰，範圍僅 chat/生成＋視覺（語音轉錄維持雲端）。切換於啟動時生效（改設定需重啟，比照 DatabaseProvider）。設定見 日誌與設定檔說明。
  • 容量上限與靜默失敗風險見 容量邊界與限制。
  • LLM 提示詞統一四層解析（0.2.110）：所有提示詞一律走 LlmPromptResolver.ResolveAsync(key, perOpOverride, fallback)，優先序（高→低）＝單次操作覆蓋 → DB Prompt(同名鍵) → appsettings LlmPrompts → 程式 fallback（LlmPromptDefaults）。鍵見 LlmPromptKeys（清洗五鍵沿用舊名）。新增需要提示詞的 LLM 功能時，請走 resolver，不要再寫死或自建分支；已知槽位在 LlmPromptsSettings（強型別）＋ LlmPromptDefaults（fallback）各補一筆，動態擴充走 DB 鍵表。轉錄沿用 OpenAISettings.Prompt 當其 fallback、另加 DB「轉錄-提示」。appsettings 改值需重啟；DB 免重啟。詳見 LLM 提示詞與用量透明化。
  • 知識來源「AI 對話」（ChatGPT 風格、多輪、串流）：清單頁操作欄「AI 對話」下拉可選對清洗後內容或對原始來源對話，導向獨立全頁 /knowledge-sources/{id}/chat?mode=cleaned|original（沿用 角色_知識來源管理清單 權限，未新增選單節點）。
  • 串流：新介面 IChatConversationClient（與單輪 IChatCompletionClient 並存，皆由 OpenAIChatCompletionClient 實作）以 stream=true SSE 逐塊回傳；Blazor 端 await foreach 累加並節流重繪（每約 60ms）。多輪記憶＝KnowledgeSourceChatService.BuildMessages 每次把先前所有 user/assistant 輪次連同 system（系統提示詞＋參考資料）一併送出。僅記憶體保存、不需 migration。
  • token 用量日誌：串流請求帶 stream_options.include_usage=true，從最後一個 usage 分塊記錄「送出(prompt)/接收(completion)/理解(reasoning)/合計(total)」。所有 LLM 呼叫（chat 文字/視覺/檔案/串流＋語音轉錄）皆額外記 完整明細=，由 TokenUsageFormatter.Format 遞迴攤平 usage 物件所有數值欄位（cached/audio/reasoning… 任意子欄位皆涵蓋，不需列舉）。語音轉錄 OpenAITranscriptionClient 改 response_format=json 取 text 並記 usage（whisper-1 無 usage 記「不可用」）。提示詞盤點與透明化方案見 LLM 提示詞與用量透明化。
  • 上下文內容：清洗後走 KnowledgeSourceService.GetCleanedContentAsync；原始來源走新 GetOriginalContentAsync，兩者皆內建團隊權控（無權限/無內容回 null）。原始彙整邏輯抽至 KnowledgeSourceContentAggregator，由 CleaningProcessor 與對話功能共用（確保兩處看到的內容一致）。對話頁「檢視參考資料」可看到實際送進模型的內容原文；BuildMessages 另記參考資料長度（只記長度、不記本文）。
  • 問答稽核明細（全文檔案式）＋滿意度回饋（0.3.29）：AI 知識問答與知識來源 AI 對話兩個檢視在每輪答完（finally）呼叫 ChatLogService.WriteAsync：提示詞與回覆全文寫實體檔案（ExternalFileSystem.ChatLogPath 下 {年}/{guid}.md、UTF8Encoding(false)），DB 只寫 LlmChatLog 索引列（使用者/時間/Origin(KnowledgeBase|KnowledgeSource)/來源Id·標題/信心/topScore/WasBlocked/RelativePath/Feedback）——內容不入 DB，與清洗結果同慣例。含「查無依據」（未送 LLM）也記一筆。記錄失敗一律 try/catch 隔離、不中斷聊天。回饋（👍/👎，可改可取消）由提問者本人透過 ChatFeedbackBar → SetFeedbackAsync 更新 Feedback/FeedbackAt。查閱頁 /chat-logs 管理員專用（CheckIsAdmin() 把關、比照 檢索診斷與調校；Menu.json id 47 adminOnly，不進權限樹、不動 MagicObjectHelper/RolePermissionService）。首頁儀表板顯示最近 30 天全站滿意/不滿意計數（DashboardService）。隱私注意：此為刻意保留全文（與 SEC-5 稽核只存長度不同），以管理員專用查閱＋可設定目錄控管。模型變更＝雙 provider migration（AddLlmChatLog）。
  • 續談還原出處與投票（1.0.99 追記）：ChatSessionTurn 新增 Sources（直接重用 KnowledgeBaseSourceAdapterModel）、ChatSettingsSnapshot 新增 QueryMode——兩者都在對話 JSON 全文檔內，不是 Entity，故不需 migration；舊檔為 null，向後相容。⚠️ 兩個聊天檢視的 sourcesByMessage／settingsByMessage／logIdByMessage／feedbackByMessage 都以 ChatMessage 物件實例為鍵（class、未覆寫 Equals ⇒ reference equality），而 ResumeSession 用全新實例重建訊息串，因此凡是新增這類「以訊息為鍵」的附加狀態，都必須同步在 ResumeSession 內重建，否則續談後靜默消失（1.0.99 之前出處與投票列就是這樣不見的，而且沒有任何錯誤訊息）。歷史輪的 logId 由 ChatLogService.GetSessionTurnFeedbacksAsync 以 LlmChatLog.SessionId+TurnIndex 反查，服務端以登入者帳號精確過濾、帳號為空回空清單（fail-closed）。⚠️ 同批補上 SetFeedbackAsync 的擁有者驗證（x.Id == id && x.UserAccount == account）——它原本完全沒有，過去因 logId 只可能來自本人當輪而無法被利用，任何讓 logId 改由查詢取得的改動都必須先確認這道守門還在。舊對話刻意不回填出處：以當初的問題重跑檢索會產出與當時不同的「假出處」。
  • Token 用量記錄（0.3.30）：每次 OpenAI 呼叫（chat/embedding/transcription 三 client、4 擷取點）在 TokenUsageFormatter.Format 旁呼叫 ITokenUsageRecorder.Record(model, callType, usageToken)（singleton，內含 Channel，非阻塞、失敗隔離）；TokenUsageParser 沿用攤平邏輯回傳結構化用量（常見欄位＋DetailsJson）；TokenUsageWriterBackgroundService（hosted）以自建 scope 的獨立 BackendDBContext 批次落地到 LlmTokenUsage（勿與作業共用 context）。作業/使用者情境由新 OperationContext（AsyncLocal，Share/Helpers） 帶入：互動端於 KB/來源對話 View 的 SendAsync Push（user 取自 CurrentUserService）；背景端在 6 個 *BackgroundService 迴圈 Push，且提交者身分經佇列帶入——ICleaningQueue 等 EnqueueAsync(int, string? userAccount, string? userName, …)＋佇列載荷改 PipelineJob(Id, UserAccount, UserName)，入列服務（KnowledgeSourceService/MediaTranscriptionService/ImageRecognitionService/WikiPageService）傳 CurrentUser，系統復原入列傳 null。查閱頁 /token-usage 管理員專用（Menu.json id 48 data_usage，不進權限樹）；首頁儀表板顯示近 30 天各類 token 全站彙總。新增背景佇列時記得沿用 PipelineJob 帶身分。模型變更＝雙 provider migration（AddLlmTokenUsage）。⚠️ UI 直接觸發 LLM（不經佇列）走另一條規則，見 §1.7「UI 直接觸發 LLM 前必須 OperationContext.Push」——1.0.80 前有 9 條這類路徑漏接。
  • 系統提示詞：對話頁可自由輸入，或從既有 Prompt（PromptService.GetAllEnabledAsync）下拉帶入後再編輯。
  • 回答長度：由對話頁「回答詳簡」(簡潔/標準/詳細，預設標準) 控制；KnowledgeSourceChatService.ResolveVerbosityInstruction 依等級回傳長度指示，併入 system 訊息（模型本身無 max_tokens 限制）。
  • 輸入框即時更新：對話輸入框用 Value+OnInput（非 @bind-Value），否則 AntDesign 僅失焦才更新值，會造成「送出」鈕需先點輸入框外面才啟用。
