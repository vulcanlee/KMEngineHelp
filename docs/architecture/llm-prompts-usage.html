LLM 提示詞與用量透明化

目的：集中說明本系統「每次呼叫大語言模型（LLM）時，到底送出哪些系統/提示詞、如何組合、哪些預設文字寫死在程式裡」，並評估「把這些提示詞搬到 appsettings.json 或資料庫」的可行性、影響，提出多種讓系統更有彈性、與 LLM 互動更透明的方案。

適用版本：0.2.109 起。與本檔相關的鐵則見 開發慣例與限制速查 §1.1（ILogger / 不記金鑰與本文）。

摘要（TL;DR：為什麼這樣設計、怎麼用、看哪裡）

為什麼這樣設計：提示詞直接決定 LLM 輸出的品質與風格，但需求會隨使用者、情境、部署環境而變。全部寫死在程式裡 → 任何微調都要改碼、重編譯、重部署；全部開放 → 又可能讓人改壞「有格式契約」的提示詞（如信心只能輸出小數）。

想達到的結果：用四層優先序兼顧彈性與安全 —— 平台給合理預設、進階使用者可線上覆蓋、單次操作可臨時改寫，且程式永遠保有「一定能動」的底線：

單次操作覆蓋（最高）→ DB「AI 提示詞」(同名鍵) → appsettings LlmPrompts → 程式 fallback LlmPromptDefaults（最低）

任一層有值就用該層、否則往下退；全空＝用程式預設（系統第一次啟動即如此，不會自動寫入 DB）。

要實際操作，看這幾節：

  • 每個提示詞的鍵名 / appsettings 屬性名 / 預設全文 → §10.1「槽位鍵一覽」＋ §3「程式預設AI 提示詞」。
  • 怎麼把新提示詞寫到某一層、同名定義在多層時誰贏 → §10.2「如何操作各層」＋ §10.3「覆蓋範例與衝突解析」。
  • 設計取捨、與其他系統的比較 → §7、§7.1、§11。

1. 範圍

系統對外的 AI 呼叫只有 OpenAI（或 OpenAI 相容地端）兩類端點：

  • chat/completions（文字 / 視覺 / 檔案 / 串流）— 由 OpenAIChatCompletionClient 實作。
  • audio/transcriptions（語音轉錄 Whisper / gpt-4o-transcribe）— 由 OpenAITranscriptionClient 實作。

模型由 OpenAISettings 決定：聊天/生成用 GenerationModel（預設 gpt-5.4）、轉錄用 Model（預設 gpt-4o-transcribe）；可切雲端/地端（GenerationProvider）。

3. 程式預設AI 提示詞（完整文字）

唯一真實來源（single source of truth）＝ Business/Services/Prompts/LlmPromptDefaults.cs 的 const string（自 0.2.110 起集中於此；原散落於 CleaningEnhancer／KnowledgeSourceChatService 的常數已搬入）。本節為對照副本，與程式內容不一致時以程式碼為準；如需修改預設，請改 LlmPromptDefaults.cs 並同步本節。

這些是第四層「程式 fallback」——第一次啟動時 DB 與 appsettings 皆空，系統即用以下文字（不會寫入 DB，見 §10）。要覆蓋請走上層（DB「AI 提示詞」同名鍵／appsettings LlmPrompts／單次操作）。括號內為 LlmPromptDefaults 常數名（＝對應的槽位鍵見 §10）。

3.1 清洗五步驟

  • CleaningDedupe（清洗-去重）：

你是資料清洗助手。請移除以下內容中的重複段落與明顯雜訊（重複客套、無意義填充），保留所有有資訊價值的內容，維持原意與繁體中文。直接輸出清理後的內容，不要任何額外說明或前後綴。

  • CleaningMask（清洗-遮罩）：

你是資安遮罩助手。請將以下內容中的個資與機密（身分證號、電話、Email、地址、金融帳號、密碼、金鑰等）以【已遮罩】取代，其餘內容原樣保留，維持繁體中文。直接輸出遮罩後內容，不要任何額外說明。

  • CleaningClassify（清洗-分類）：

請閱讀以下內容，建議 1-5 個最貼切的主題分類標籤。僅輸出分類名稱、以「、」分隔於同一行，不要其他文字。

  • CleaningSummary（清洗-摘要）：

請為以下內容寫一段約 100-200 字的繁體中文重點摘要；摘要後另起一行，以「關鍵實體：」開頭列出重要的人/組織/產品/主題（以「、」分隔）。直接輸出，不要額外說明。

  • CleaningConfidence（清洗-信心）：

請評估你對上述清洗結果（去重、遮罩、摘要、分類）整體正確與完整的信心，僅輸出 0 到 1 之間的一個小數（例如 0.85），不要任何其他文字。

3.2 知識來源對話

  • ChatSystem（對話-系統；系統提示詞欄留空時）：

你是一位專業的知識助理，請依據下方提供的參考資料，以台灣繁體中文回答使用者的問題；若參考資料中找不到答案，請明確說明。

  • 「回答詳簡」指示：
  • ChatConcise（對話-簡潔）：回答請精簡扼要，以重點/條列為主、盡量簡短，避免冗長鋪陳。
  • ChatStandard（對話-標準，預設）：回答請重點清楚、篇幅適中，避免不必要的冗長。
  • ChatDetailed（對話-詳細）：回答可完整詳盡，必要時補充背景、結構與範例。

3.3 轉錄 ASR 提示（特例：fallback 在 OpenAISettings.Prompt）

轉錄提示詞不在 LlmPromptDefaults；其平台預設/最底層 fallback 沿用 Models/Systems/OpenAISettings.cs 的 Prompt（已在 appsettings），另由 DB「轉錄-提示」覆蓋（見 §10）。

  • OpenAISettings.Prompt（預設，僅中文轉錄時帶入）：

請以台灣繁體中文輸出逐字稿，例如：軟體、資訊、程式、伺服器。

4. 既有可客製機制與優先序

系統其實已有相當的客製能力，只是分散在不同地方：

  • 清洗：優先序＝CleaningProfile 各步驟欄位（非空）→ 否則 DB Prompt 表以鍵名「清洗-去重/遮罩/分類/摘要/信心」→ 否則硬編碼預設。前兩者皆可由管理 UI（清洗規則設定、AI 提示詞）線上編輯、免重啟。
  • 對話：對話頁「系統提示詞」欄可自由輸入或從 Prompt 表下拉帶入；「回答詳簡」控制長度。
  • 轉錄：OpenAISettings.Prompt（appsettings，改需重啟）。
  • 逐字稿/文件 LLM 產生、圖片辨識：提示詞本來就由使用者於操作當下輸入或選取（無預設）。

結論：目前真正「只能改程式」的硬編碼預設，剩下 DefaultSystemPrompt、三段「詳簡指示」，以及清洗五步驟在「未建 DB 覆蓋時」的最後底線。

5. token 用量日誌（現況，0.2.109 起）

  • 所有 chat/completions 呼叫（含串流）記一行 Information：送出(prompt)/接收(completion)/理解(reasoning)/合計(total)，並額外附 完整明細=——由 TokenUsageFormatter.Format 遞迴攤平 usage 物件的所有數值欄位，因此任何子欄位（prompt_tokens_details.cached_tokens、*.audio_tokens、completion_tokens_details.reasoning_tokens 等）都會出現，不需事先列舉。
  • 語音轉錄改 response_format=json：逐字稿取 text，並記 OpenAI 轉錄用量…完整明細=（gpt-4o-transcribe 會回 input_tokens/output_tokens/…；whisper-1 無 usage 則記「不可用」）。
  • 遵守鐵則：只記 token 數字，不記 ApiKey 與請求/回應本文。

5.1 Token 用量查閱頁（/token-usage，管理員專用）

逐筆列出每次 OpenAI 呼叫的用量（時間／使用者／作業／型別／模型／各類 token），並提供篩選、統計與報表：

  • 篩選：帳號或姓名、起始日／結束日、作業、型別、模型。頂端顯示「篩選範圍合計」（輸入／輸出／快取／推理／合計）。
  • 帳號或姓名（可輸入可下拉）：以 AntDesign Input（自行輸入關鍵字做模糊比對）＋ Select（EnableSearch 下拉選取）組合。下拉來源＝MyUser 全部啟用帳號 ∪ 用量紀錄中出現過的帳號（以帳號去重），選項 Value＝帳號、Label＝「姓名（帳號）」（供顯示與搜尋），並在最前面固定一個「（系統自動）」專用選項——選取後只篩「帳號與姓名皆空」的系統自動紀錄（後端 TokenUsageQueryFilter.SystemOnly）。下拉選取會寫入輸入框（filterUserKeyword 為單一真實來源）。
  • 五個頁籤（1.0.80 起）：前四個是統計維度 依使用者／依作業／依模型／依型別 的彙總（依使用者含輸入／輸出／快取／推理／合計與呼叫次數），統計涵蓋「全部篩選結果」，非僅當前分頁（後端 TokenUsageQueryService.AggregateAsync）；第五個是 明細（N），即逐筆用量表格（1.0.80 前位於頁籤區下方，已移入此頁籤；N＝篩選範圍總筆數，伺服器端分頁）。
  • PDF 報表下載：ReportPdfExporter（QuestPDF，繁中字型已註冊）產出含「統計 + 全部明細」的 PDF，經 keChat.downloadFileFromStream 串流下載；明細為全部篩選結果（不受畫面分頁限制，後端 ExportRowsAsync）。

6. 把硬編碼提示詞搬到 appsettings.json：可行性與影響

可行。系統已用 services.Configure<OpenAISettings>() / Configure<SystemSettings>() 綁定設定，新增一個區段（如 LlmPrompts）即可比照。但有三個必須正視的影響：

  1. 改檔需重啟：現行各 Client 在建構式以 options.Value 取快照，設定變更不會熱重載。若要免重啟，需改用 IOptionsMonitor<T> 或把提示詞放 DB。
  2. 與 DB 覆蓋的優先序要明確：清洗已是「Profile → DB Prompt → 預設」三層；若再加 appsettings，要明確定義 appsettings 是「取代硬編碼底線」而非凌駕 DB，否則會混亂。
  3. 改錯提示詞會影響功能正確性：例如信心提示詞被改成不只輸出小數，會讓信心解析失敗→改走待審核。務必保留硬編碼 fallback 與測試。

7. 方案與取捨（擇一或混合）

方案 1：集中式 LlmPromptsSettings（appsettings）＋硬編碼 fallback

  • 作法：新增 LlmPrompts 區段（清洗五步驟、對話系統提示詞、詳簡三段、轉錄提示詞），程式以 IOptions 讀取、值為空時用硬編碼預設。
  • 優點：集中、版本控管、部署一致；變動小。
  • 缺點：改檔需重啟；非技術人員仍需改 JSON；多環境要各自維護。

方案 2：統一到 DB Prompt 表（已存在），以「鍵」對應用途

  • 作法：把對話系統提示詞、詳簡三段、轉錄提示詞，比照清洗的「清洗-去重」鍵模式，改用約定鍵（如「對話-系統」「轉錄-提示」）由 PromptService 取得；找不到鍵才用硬編碼預設。
  • 優點：可由現有「AI 提示詞」管理 UI 線上編輯、免重啟、可加權限/稽核；對使用者最透明（看得到、改得到）。
  • 缺點：DB 依賴（讀取成本，可快取）；需要治理鍵名；首次部署要塞預設資料（或維持 fallback）。

方案 3（推薦）：四層優先序，平台預設下放、單次操作可覆蓋

  • 優先序：程式 fallback → appsettings 平台預設 → DB 覆蓋（Prompt/Profile）→ 單次操作覆蓋（對話頁輸入、清洗規則設定）。
  • 作法：先做方案 2（DB 化最有感、免重啟），appsettings 平台預設為可選層；硬編碼永遠是最終保險。
  • 優點：彈性與安全兼顧、與現有機制相容、漸進可落地。
  • 缺點：層數多需文件化清楚（本檔即為此）。

方案 4（透明化，與上者並行）

  • UI 顯示「本次實際送出的完整提示詞/訊息」：對話頁已有「檢視參考資料」，可延伸顯示完整 system 訊息與每則 token 用量；清洗頁可加「檢視實際提示詞」。
  • token 用量落 DB：除日誌外，將每次 usage 寫入資料表，提供用量統計/成本報表。

7.1 方案 3 概念澄清與其他考量

針對方案 3 常見的四個疑問逐一說明：

Q1：「程式 fallback」是什麼？ 就是寫死在 C# 原始碼裡的預設提示詞常數（如 CleaningEnhancer.DefaultDedupePrompt、KnowledgeSourceChatService.DefaultSystemPrompt）。它是最底層的保險：編進執行檔、永遠存在；當上層（appsettings／DB／單次操作）都沒有提供值時就用它。即使設定檔被清空、DB 沒資料或連不上，功能仍能用一個合理預設運作。它位於優先序最底。

Q2：原先系統預設是否還會繼續存在？ 會，而且刻意保留。 上層只是在「有值時」覆蓋（override）它；一旦上層為空就自動退回程式 fallback，永不刪除——這是「一定能動」的保證。

⚠️ drift 警告：若又把同一段預設文字抄一份到 appsettings.json，等於同一預設存在兩處（程式 + json），日後容易各改各的而分歧。建議 appsettings 預設留空＝「沿用程式預設」，只有要改時才填值；程式 fallback 純當緊急底線。

Q3：能否透過 appsettings「重新定義」原先預設？ 可以——把提示詞放進設定區段（如 LlmPrompts），執行時該值非空就用設定檔的、不用寫死的，等於不重新編譯就能改平台預設。代價：目前設定為建構式 options.Value 快照，改檔需重啟才生效（要免重啟需改 IOptionsMonitor 或改放 DB）。

Q4：能否透過 appsettings「自行擴充」？

想做的事只靠 appsettings說明
改既有提示詞內容✅ 可以填對應槽位即覆蓋
為「程式已會依鍵查找」的槽位新增條目✅ 可以（需字典式綁定）僅在程式會去查那個鍵時才生效，如清洗的「清洗-去重」鍵
發明全新的 LLM 功能/提示詞❌ 不行設定只是資料；沒有對應程式去讀它、呼叫 LLM，填了也沒人用

一句話：appsettings 能「重新定義／微調已知槽位」，但不能「無中生有創造新行為」。真正要「動態增加任意提示詞槽位」，沿用 DB Prompt 鍵表比強型別設定類更適合（可線上加、免改 schema）。

其他考量與建議

  1. 強型別 vs 字典綁定：已知槽位用具名屬性（編譯檢查、不怕打錯鍵）；需動態擴充走 DB 鍵表。
  2. 多層必配透明化：層數越多越難一眼看出「這次用了哪一層」→ 建議 UI/日誌顯示本次實際提示詞與其來源層級。
  3. 格式契約提示詞要防呆：如「信心只輸出小數」，改錯會壞功能 → 標記進階/危險並保留格式檢查。
  4. 多環境：可用 appsettings.{Environment}.json 讓 dev/prod 用不同提示詞。
  5. 變更治理：提示詞屬影響產出品質的「軟設定」，DB 可記編輯者/時間、appsettings 走 git，皆要可回溯。
  6. 機密：提示詞不得含金鑰，設定檔不放敏感資料。

8. 透明化建議（彙整）

  1. 日誌完整 token（已於 0.2.109 完成）。
  2. UI 顯示實際提示詞與用量：讓使用者「所見即所送」，是最直接的透明化。
  3. 提示詞 DB 化＋管理 UI（方案 2/3）：使用者可自助調整，免改檔免重啟。
  4. opt-in Debug 記錄完整 messages：僅在診斷時開啟，預設關閉（鐵則：不記請求/回應本文）。
  5. 用量報表：token 落 DB 後可做每功能/每使用者/每來源的成本檢視。

9. 建議落地順序（roadmap）

  1. （已做）完整 token 日誌、轉錄 usage。
  2. 對話頁/清洗加「檢視實際提示詞」唯讀面板（純前端、低風險）。
  3. （已做，0.2.110）方案 3 四層提示詞解析 —— 見 §10。
  4. （可選）appsettings LlmPrompts 改 IOptionsMonitor 熱重載（目前改值需重啟）。
  5. （可選）token 用量落 DB ＋ 報表頁。

10. 落地紀錄：方案 3 四層提示詞解析（0.2.110）

所有提示詞統一走 LlmPromptResolver.ResolveAsync(key, perOperationOverride, fallback)，優先序（高→低）：

  1. 單次操作覆蓋（perOperationOverride）：對話頁系統提示詞欄、清洗規則設定欄位。
  2. DB 覆蓋：Prompt 表中啟用且同名（鍵）的提示詞（PromptService.GetEnabledContentByNameAsync）。可在「AI 提示詞」線上編輯、免重啟。
  3. appsettings 平台預設：LlmPrompts 區段對應屬性（LlmPromptsSettings）。改值需重啟；值留空＝跳過此層。
  4. 程式 fallback：LlmPromptDefaults 常數（最底層保險，永遠存在）。

任一層為非空白即採用，否則往下退；LlmPromptResolver 以 Debug 記錄本次採用層級（PerOp/DB/Appsettings/Fallback）。不自動 seed：DB 空＝用 fallback。

10.2 如何把提示詞寫到各層

  • 單次操作覆蓋（最高、最即時、通常不留存）：
  • 對話系統提示詞：對話頁上方「系統提示詞」欄直接輸入（只影響本次對話）。
  • 清洗：在「清洗規則設定」（/cleaning-profiles，權限 角色_清洗設定檔）建立/編輯設定檔的對應步驟欄位，清洗時選用該設定檔。
  • DB 覆蓋（全站生效、免重啟、可線上編輯）—— 最常用的客製方式：
  • 登入後到側邊選單「基礎資料設定 → AI 提示詞」（路由 /prompts，需 角色_提示詞清單 權限）。
  • 按「新增」：名稱填上表的「DB 名稱（鍵）」（例如 對話-系統，須完全一致）、內容填你的提示詞、啟用打勾，儲存。
  • 立即生效（下次該功能呼叫 LLM 即採用，無需重啟）。停用或刪除該筆即退回下層。

名稱必須與鍵完全相同（系統以名稱比對）；名稱具唯一性，無法建立兩筆同名。

  • appsettings 平台預設（部署層級、需重啟）：
  • 編輯 appsettings.json 的 LlmPrompts 區段，填對應屬性名，例如 "ChatSystem": "你是公司內部知識助理…"。
  • 重啟應用程式後生效（設定於建構式快照、不熱重載）。值留空＝跳過此層。
  • 程式 fallback（最低、需改碼）：改 LlmPromptDefaults.cs 常數並重新建置 —— 等同改「出廠預設」，一般不需要。

11. 與其他知識庫 / LLM 系統的比較：這種設計常見嗎？

結論：「提示詞可外部設定、甚至分層覆蓋」是業界常見方向，但做到幾層、開放給誰改各家差異很大。

  • 開發框架 / 開源平台（傾向高度可配置）：LangChain、LlamaIndex 用 PromptTemplate 把提示詞抽成可替換物件；Dify、Flowise、RAGFlow 等低/無程式碼平台更直接在 UI 上編輯系統提示詞與範本。理念與本系統一致：提示詞是「軟設定」、應可不改碼調整。
  • 企業 / 受管產品（傾向只開放「最上層」、隱藏內部）：ChatGPT 的「自訂指令」、Claude 的「專案指示」、多數 RAG SaaS 通常只讓使用者改最上層的 system instructions，而把內部的檢索/重寫/安全提示詞隱藏、寫死或集中控管。
  • 高合規垂直系統（傾向寫死）：醫療、金融、法遵類常刻意不開放內部提示詞。

為什麼有些系統「不加」這種分層覆蓋？

  1. 品質與一致性：提示詞是產品的一部分；開放修改會讓輸出不可預測，難以保證品質與回歸測試結果。
  2. 保護「格式契約」：許多提示詞綁定下游解析（本系統的信心只能輸出小數）；改壞會直接讓功能失效。
  3. 安全與防濫用：system prompt 常含安全護欄與防越獄規則，公開或開放編輯等於把護欄交出去。
  4. 支援成本：使用者自改後「結果不如預期」會變成支援負擔，難以區分是 bug 還是設定。
  5. 簡單性（YAGNI）：多數使用者不需要也不想碰提示詞；多一層設定就是多一份維護與文件。

本系統為何仍採分層：本系統定位是可被單一團隊/個人客製的內部知識萃取工具，使用者往往同時是維運者，需要「不改碼就能依領域調整提示詞」的彈性；同時以「程式 fallback 永遠在 + 格式契約提示詞標記為進階/危險（§7.1）」抵銷上述風險。這正是方案 3「彈性與安全兼顧」的取捨。
