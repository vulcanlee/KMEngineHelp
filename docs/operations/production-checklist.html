部署與維運

正式部署與安全檢查清單

目標

  • ☑建立腳手架上線前必查項目，避免開發用設定被複製到正式環境。

本文件是每次正式部署前的人工/環境檢查清單；未勾項不代表程式功能尚未完成，也不視為產品 backlog。

⚠️ 2026-07-26 重要更正：本清單原本有 4 項不實宣稱

本檔曾以 [x] 宣稱「Production 沿用開發金鑰／support 預設密碼／Redis 留空／Swagger 未設定會直接中止啟動」。 這 4 項全部不成立：StartupSafetyValidator 已於 1.0.68 整支移除（連續兩次擋住正式部署 IIS 500.30）， 健康檢查的金鑰判定亦於 1.0.69 移除。而出貨的 appsettings.json 至今仍是 SigningKey = "DevelopmentOnly-…"、SupportPassword = "1qaz@WSX"。

更嚴重的是：docs/planning/08-優化建議清單-TODO.md 明寫本清單是移除守門後「僅剩的補償方式」—— 也就是唯一的補償控制不但是空的，還反過來告訴維運人員「程式會幫你擋」。 因此本次把 4 項改為 [ ] ＋ 標明「無程式檢查」，並在 JWT 與預設帳號兩節補上可執行的人工核對項。

1.0.72 後續補強：金鑰與 support 密碼兩項已恢復軟偵測——啟動時記一筆 Error 日誌、 /system-health「身分驗證」項轉黃燈，但仍不會中止啟動（刻意如此，避免重演 1.0.68 被移除的原因）。 因為那只是「有人去看才會發現」的提示，下方人工核對項仍須每次執行。Swagger 與 Redis 兩項刻意未恢復： Redis 已有 /system-health「分散式快取」項實測連線，Swagger 未設定時沿用安全側預設。

JWT 與認證

  • 將 JwtSettings:SigningKey 改由 secret manager、環境變數或部署平台 secret 提供。
  • ☐⚠️ 不會擋啟動，但 1.0.72 起會提示：Production 沿用開發用 signing key 不會被中止啟動（原守門於 1.0.68 移除），但會在日誌記一筆 Error（Production 安全風險：…）且 /system-health「身分驗證」項轉黃燈。→ 仍須執行下方「人工核對」，因為提示只在有人去看日誌或健康檢查頁時才會被發現。
  • 確認 signing key 長度、亂數強度與輪替流程。
  • 確認 access token 與 refresh token 有效期符合系統風險等級。
  • 記錄 refresh token 採 stateless signed JWT，無法可靠撤銷單一 token；若需要撤銷能力，需改成落庫或加入 token version 機制。
  • 確認 ApiResult.Exception 正式環境完整回傳的資訊揭露風險已被接受，或另開需求改成依環境遮蔽。

人工核對（每次部署後必做）

  • ☐取得正式站台實際生效的 JwtSettings:SigningKey，確認三件事：
  • 不以 DevelopmentOnly- 開頭
  • 長度 ≥ 32
  • 不等於倉庫 appsettings.json 內那個公開預設值

⚠️ 最常見的錯誤做法：在預設值後面「再接一段字」而不是整個換掉。這樣長度會變長、看起來像改過了， 但前綴仍在 → 金鑰仍可從公開原始碼推導。1.0.69 就實際遇過這個情況（長度已達 202、前綴仍是 DevelopmentOnly-）。

  • ☐生效值的判定順序（由後者覆蓋前者，請從最高優先序往下找）：

環境變數 JwtSettings__SigningKey → web.config 的 <environmentVariables> → appsettings.Production.json → appsettings.json

  # 於站台主機執行
  [Environment]::GetEnvironmentVariable('JwtSettings__SigningKey','Machine')
  Select-String -Path .\web.config, .\appsettings.Production.json -Pattern 'SigningKey'

⚠️ appsettings.Production.json 只覆寫它自己列出的鍵；沒列到的鍵一律沿用基底 appsettings.json（也就是開發預設值）。

預設帳號

  • 部署前停用、刪除或透過 BootstrapSettings / 環境變數重新設定預設 support 帳號。
  • ☐⚠️ 不會擋啟動，但 1.0.72 起會提示：Production 沿用 support 預設密碼（support 或 1qaz@WSX）不會被中止啟動（原守門於 1.0.68 移除），但會併入上述 Error 日誌與「身分驗證」黃燈。→ 仍須執行下方「人工核對」。
  • 若系統需要保留預設管理者，必須將 BootstrapSettings:SupportPassword 改由部署 secret 提供；首次啟動強制改密碼可另開功能化任務。
  • 檢查文件、seed、測試資料中沒有可被正式環境沿用的密碼。

人工核對（每次部署後必做）

  • ☐確認生效的 BootstrapSettings:SupportPassword 不是 support、也不是 1qaz@WSX。

這兩組都寫在倉庫與文件裡，等同公開。

  [Environment]::GetEnvironmentVariable('BootstrapSettings__SupportPassword','Machine')
  Select-String -Path .\web.config, .\appsettings.Production.json -Pattern 'SupportPassword'
  • ☐若 SupportAccount 仍是 support，確認該帳號已停用或已改密碼。
  • ☐知悉一個重要限制：support 密碼每次啟動都會被設定值覆寫（Program.cs 的 bootstrap 流程），

所以「在畫面上改密碼」會在下次重啟時被設定檔的值蓋回去。要真正改掉，必須改設定值本身。

Swagger 與 API

  • 正式環境確認 Swagger UI 是否關閉，或限制在內網/VPN/授權後使用。
  • ☐⚠️ 無程式檢查（原「未明確設定即中止啟動」的守門於 1.0.68 移除）：出貨範本 Swagger:EnabledInProduction 為 false，若 appsettings.Production.json 未列出該鍵，會沿用基底的 false（安全側），但不會有任何提示。請人工確認生效值為 false。
  • 確認所有 CRUD API 均需要 Bearer token。
  • 確認 API validation、401、403、404、500 都維持 ApiResult<T> 格式。
  • 確認檔案下載成功時維持原生 File stream，錯誤才回 ApiResult<T>。
  • 確認新用戶端使用 /api/v1/...，既有 /api/... 僅作相容路由。

快取

  • 確認 CacheSettings:Provider：單機可用 Memory，多節點部署應改 Redis 以共享快取。
  • ☐⚠️ 無程式檢查（原守門於 1.0.68 移除）：Provider=Redis 但 RedisConnection 留空不會中止啟動。但這一項有現成的替代驗證：/system-health 的「分散式快取」項會實際嘗試連線，連不上即紅燈——部署後開一次該頁即可確認。
  • 將 CacheSettings:RedisConnection 改由部署 secret / 環境變數提供，勿進版控。

部署設定

  • 設定 HTTPS、HSTS、反向代理 header 與正式網域。
  • 設定 NLog 路徑與 log retention，避免敏感資料長期保留。
  • 設定資料庫備份、migration 執行策略與 rollback 流程。
  • 檢查 CORS、cookie、SameSite、upload/download 目錄權限。
  • 確認 /health/live 與 /health/ready 已納入部署平台或監控系統。
  • 確認 /system-health 只有管理員可存取，且頁尾最後 100 筆原始日誌不會暴露 secret。

知識圖譜（Graph RAG）人工核對

  • ☐雙資料庫 migration 都已套用：AddGraphEdge、AddGraphExtraction、AddGraphCommunity、AddGraphEntityAlias、AddGraphEntityAliasConfidence、AddGraphIndexes、AddGraphHopParams、AddRagEvalGraphFields、AddGraphJobState（SQLite 與 SQL Server 各一套）。⚠️ SQL Server 上 GraphEntityAlias.Status 參與索引鍵，受 nvarchar(450) 長度限制。
  • ☐確認 GraphWeight 的實際生效值（到 /rag-diagnostics 看，不是看 appsettings.json）。該值可由資料庫覆寫，兩者不一致是常態而非錯誤；設 0 代表圖檢索整路關閉。
  • ☐四個成本／安全閥已依預期負載設定並已重啟服務：GraphMaxNodes（200）、GraphGlobalCommunityCap（20）、GraphMaxCommunities（50）、GraphAliasNameCap（300）。這四項沒有線上熱調路徑，改了不重啟等於沒改。
  • ☐已至少重建過一次社群摘要（到 /knowledge-graph-review 頁頂按「重建社群摘要」，確認狀態列出現社群數）。⚠️ 沒做這一步，AI 知識問答的「全域」模式無法使用——這是部署後最常漏掉的一項。
  • ☐若對外開放 /api/v1/KnowledgeGraph/*：確認前端閘道已加限流（該端點沒有 API 專用節流，全域問答成本是社群數的倍數）。
  • ☐確認 GraphMaxHops 生效值（預設 2）符合預期。⚠️ 從 1.0.89 之前升級者，多跳會使既有檢索評測基線位移，請重跑評測建立新基線。

驗收標準

  • dotnet build src/KnowledgeExtraction/KnowledgeExtraction.slnx -v:minimal --no-incremental 成功。
  • dotnet test src/KnowledgeExtraction/KnowledgeExtraction.Tests/KnowledgeExtraction.Tests.csproj -v:minimal 成功。
  • dotnet list src/KnowledgeExtraction/KnowledgeExtraction.slnx package --vulnerable --include-transitive 未列出已知弱點。
  • ./scripts/Test-DocsEncoding.ps1 成功。
  • 知識圖譜越權洩漏＝0（人工驗證）：以非管理員帳號登入，確認 ①「AI 知識問答」全域模式取不到他隊社群的內容 ②「知識圖譜審核 → 圖譜瀏覽」查他隊實體時回「查無實體」而非顯示關係 ③看不到「實體合併」分頁（僅管理員）。任一項越權可見即為安全失敗，不得上線。⚠️ 這一條必須人工做——POST /api/v1/KnowledgeGraph/global-ask 目前沒有 HTTP 層的 leak=0 端到端測試（僅服務層有覆蓋），見 認證授權與權限機制 § 安全待辦。
