RAG 問題診斷手冊（維運用）

把「使用者問答異常」的排查，從零散的參數表／問題對照表，強化成一套症狀 → 檢查 → 建議調整 → 是否需重建索引的決策手冊；並涵蓋「檢索診斷與調校網頁」（EVAL-4，✅ 0.3.6）與「查詢期參數化設定 UI」（EVAL-5，✅ 0.3.9）兩者的實作說明。

  • 文件用途：把「使用者問答異常」的排查，從零散的參數表／問題對照表，強化成一套症狀 → 檢查 → 建議調整 → 是否需重建索引的決策手冊；並涵蓋「檢索診斷與調校網頁」（EVAL-4，✅ 0.3.6）與「查詢期參數化設定 UI」（EVAL-5，✅ 0.3.9）兩者的實作說明。
  • 主要讀者：維運人員、客服、導入顧問、系統負責人
  • 對應版本：0.3.14（含 EVAL-4 診斷頁 0.3.6、EVAL-5 查詢期參數化 0.3.9、VER-2 as-of 試檢索 0.3.14）
  • 編碼：UTF-8（繁體中文，含 BOM）
  • 建立日期：2026/07/08

本手冊是「決策流程」；參數定義與完整脈絡見 知識庫 RAG 設計與執行（§四參數表、§七參數調整指引）。兩層概念見 Wiki 與 Cleaned 角色差異。待辦追蹤見 RAG 系統補強總彙整。

一、先看三個「狀態源」（排查前必看）

任何診斷都從這三處取得客觀狀態，避免憑感覺調參：

狀態源看什麼位置
/system-health「向量索引涵蓋率」是否有已清洗來源但索引為空／是否未設定嵌入系統健康頁
問答稽核日誌每輪「最高分 topScore／信心級別／命中明細 #Id(layer,score)」；持久化稽核另記提問者帳號（SEC-5，可歸責「誰問了什麼」）。注意：KnowledgeBaseQueryAudit 只存身分＋長度＋分數、無本文；若要看完整提問與回覆全文，是另一個獨立機制 LlmChatLog（0.3.29，全文存檔、管理員 /chat-logs 查閱），兩者勿混淆。NLog 結構化日誌 + KnowledgeBaseQueryAudit 表（/rag-diagnostics 近期稽核可查）
管理員問答診斷提示查無依據時系統自動提示「嵌入未設定／索引為空」問答頁（僅管理員可見）

「跨查詢的 topScore 分佈統計」已於 0.3.6 落地於 /rag-diagnostics（見 §四），不需再人工從日誌彙整。

二、四大症狀決策樹（強化版）

以下把原始診斷流程樹補上「判斷依據、對應參數、是否重建索引、對應程式」。

症狀 A｜一律查無依據（幾乎每題都答「查無相關依據」）

A. 一律查無依據
├─ 1. 先看 /system-health「向量索引涵蓋率」
│     ├─ 顯示「未設定嵌入」 → 設定 OpenAISettings 的 Embedding*（雲端 ApiKey 或地端端點）
│     └─ 顯示「索引為空」   → 到「知識來源管理清單」對已清洗來源按「建立索引」；多筆可用工具列「全量重建索引」一次排入（RQ-8，增量冪等、背景處理）
├─ 2. 確認來源狀態鏈：已清洗？已蒸餾？Wiki 已核准（已完成）？
│     └─ VectorEmbedding 為空的常見主因：內容在索引管線上線前就蒸餾，或當時未設嵌入
├─ 3. 確認 embedding 模型一致：查詢與文件必須同模型、同維度（1024）
│     └─ 換過 EmbeddingModel/Dimensions 但沒重建索引 → 維度/語意不一致 → 重建索引
└─ 4. 門檻是否設太嚴：RejectThreshold 是否被調得過高（見症狀 C 反向）
  • 是否重建索引：情境 1（建立索引即可，不需重蒸餾）；情境 3（換模型/維度需重建）。
  • 對應：KnowledgeSourceService.TriggerEmbeddingIndexAsync／TriggerEmbeddingIndexAllAsync（RQ-8 全量）、EmbeddingIndexProcessor、OpenAISettings.Embedding*。

症狀 B｜有命中但答案不準（有撈到內容，但答得不對／不完整）

B. 有命中但答案不準
├─ 1. 召回廣度：適度增加 TopK / CandidateTopK（讓更多相關 chunk 有機會進 context）
├─ 2. chunk 顆粒：
│     ├─ 太小 → 上下文被切碎 → 增加 ChunkTargetChars / ChunkOverlapChars（需重建索引）
│     └─ 太大 → 一塊混多主題 → 降低 ChunkTargetChars / ChunkMaxChars（需重建索引）
├─ 3. Wiki 是否過度摘要：命中集中在 Wiki 層且細節缺失
│     └─ 確認 Cleaned 層有進索引當佐證；必要時提高對 Cleaned 的權重來源（見 Wiki/Cleaned 角色差異）
├─ 4. 是否需要 adjacent chunk expansion（章節/條款被切開）→ 補強清單 RQ-2（未實作）
└─ 5. 融合權重：語意對但關鍵詞不同→提高 VectorWeight；關鍵詞精確命中差→提高 KeywordWeight
  • 是否重建索引：情境 2（改切塊要重建）；情境 1、5（調 TopK／權重不需重建）。
  • 注意：先窮盡「調設定」再考慮 rerank；rerank 是評測驅動的有條件 P2，見 rerank 分析。

症狀 C｜庫外問題仍硬答（知識庫沒有的內容，卻臆造回答）

C. 庫外問題仍硬答 / 答非所問
├─ 1. 看稽核日誌的 topScore 分佈：庫外問題的最高分通常偏低
├─ 2. 提高 RejectThreshold（更容易判為「查無依據」直接不呼叫 LLM）
├─ 3. 視需要提高 LowConfidenceThreshold（更容易加上「⚠️ 信心不足」前綴）
└─ 4. 校準原則：以「真實庫內問題的最高分下緣」與「庫外問題的最高分上緣」之間取值
  • 是否重建索引：不需（純查詢期門檻）。
  • 對應：RejectThreshold／LowConfidenceThreshold（SystemSettings.Retrieval）、KnowledgeBaseChatService 兩段式判定。門檻校準＝補強清單 RQ-1，前提是 EVAL-2/EVAL-3 有分佈數據。

症狀 D｜出處錯誤（答案還行，但出處指向不對）

D. 出處錯誤
├─ 1. 看該筆出處層別：是「清洗內容」還是「蒸餾頁」？
├─ 2. 檢查 AnchorRef：是否指到錯誤章節（切塊把標題與內文切開？）
├─ 3. 若為蒸餾頁：檢查 WikiPage 對應與內容是否忠於來源
├─ 4. 若為清洗內容：檢查 Cleaned Markdown 結構（標題層級是否正常）
└─ 5. 修正內容或切塊後 → 重建索引
  • 是否重建索引：改內容／切塊需重建。
  • 對應：Chunker（AnchorRef 產生）、VectorEmbedding.AnchorRef／WikiPageId。

症狀 E｜「整體／綜觀」類問題答不出來，或全域模式說沒有可用社群

這一類是 Graph RAG（1.0.83～1.0.96）才有的症狀，與向量／關鍵字檢索無關。

E. 綜觀類問題答不出來
├─ 1. 先分辨是哪一種問題
│     ├─ 「A 跟 C 有什麼關聯」（多跳）      → 走下面 2～5（圖檢索路徑）
│     └─ 「整體風險/趨勢/系統性根因有哪些」 → 走下面 6～8（全域問答路徑）
├─ 2. Chat LLM 有設定嗎？（/system-health 看 LLM 可用性）
│     └─ 沒設定 → 三元組抽取、社群摘要、全域問答全部不能用
├─ 3. 該來源的 Wiki 頁核可了嗎？
│     └─ 未核可 → 抽取會跑完但抽不到東西（抽取讀的是「已完成且現行」的 Wiki 頁）
├─ 4. 三元組核可了嗎？（/knowledge-graph-review「三元組審核」）
│     └─ 還在「待審核」或已被「退回」 → 完全不影響檢索。核可後即時生效
├─ 5. GraphWeight 是不是 0？（/rag-diagnostics 看實際生效值，不是看 appsettings）
│     ├─ 是 0 → 圖檢索整路關閉（連查詢都不發）
│     └─ 不是 0 但沒效果 → 看 GraphMaxHops 是否為 1（單跳撈不到 2 跳外的關聯）
├─ 6. 「重建社群摘要」執行過嗎？（審核頁頂端狀態列的社群數）
│     └─ 從未重建 → 全域問答無社群可用（系統會回可行動的原因，不是空白）
├─ 7. 這個使用者符合社群 ACL 嗎？
│     └─ 社群摘要採「社群團隊聯集 ⊆ 使用者團隊」的子集判定，比一般紀錄的交集判定更嚴
└─ 8. 問法對嗎？
      └─ 具體條款/數字請改用「一般（精準檢索）」模式；全域模式沒有出處可核對
  • 是否重建索引：都不需要。圖譜與向量索引是兩條獨立的路，重建索引不會補上三元組，重抽三元組也不會動到向量。
  • 要不要重建社群摘要：核可別名後要（社群才會套用實體合併）；核可三元組後不必（檢索即時生效），但社群內容會與最新核可狀態有落差，適時重建。
  • 對應：RetrievalService.SearchGraphAsync（圖分）、GraphCommunityService（社群 ACL）、KnowledgeBaseChatService.GlobalMapAsync（全域 map-reduce）。
  • 想量化「圖到底有沒有用」：/rag-evaluation 的四個圖指標（圖召回增益／圖參與率／圖獨有命中／平均取用社群數），見 知識圖譜使用指南 §九。

⚠️ 升級後檢索結果「變多」不一定是壞了：GraphMaxHops 預設為 2（1.0.90 起多跳生效），會讓召回增加、既有評測基線位移。請重跑評測建立新基線；要回到單跳行為就把 GraphMaxHops 設 1。

三、「問題歸屬」快速分流（判斷根因在哪一層）

維運最需要的是：問題到底出在資料品質、清洗、蒸餾、還是 RAG 設計/參數？ 用下表快速歸屬：

觀察較可能的根因層先做
一律查無依據、/system-health 示警RAG 索引未建 / 嵌入未設建立索引 / 設定嵌入
命中都在但內容本身就殘缺、含雜訊資料品質 / 清洗檢視 Cleaned 內容、調清洗規則設定重清洗
概念頁把關鍵細節摘掉、答案空泛蒸餾檢視 Wiki 頁、重蒸餾，或問答時倚重 Cleaned
內容都在、就是排序/召回差RAG 參數調 TopK/權重/切塊/門檻（本手冊 §二）
敏感資訊外洩到答案清洗遮罩（蒸餾不補救）回清洗階段補遮罩、重清洗→重蒸餾→重索引（SEC-2）
出處指錯段落切塊 / 內容結構檢查 AnchorRef、重建索引
多跳關聯題答不出來、或全域模式無社群圖譜層（Graph RAG）到 /knowledge-graph-review 確認 Wiki 頁已核可、三元組已核可、社群已重建；到 /rag-diagnostics 確認 GraphWeight 生效值不為 0（本手冊 §二 症狀 E）

四、系統內「檢索診斷與調校網頁」（EVAL-4，✅ 0.3.6 完整落地於 /rag-diagnostics）

已完整落地（0.3.6）：/rag-diagnostics（管理員，CheckIsAdmin 擋人；側邊選單「系統管理」adminOnly + 頁面守門＝雙層防護）已含下列全部五區——① 索引健康（每來源清洗/蒸餾/已核准Wiki/Cleaned·Wiki chunk 數/最後索引時間 + 紅黃綠燈 + 未設嵌入提示）、② topScore 分佈（直方圖/百分位/信心佔比）、③ 目前vs建議門檻 + 效果模擬 + 直接套用/回復（見 §五）、④ 症狀自檢（自動列出當前問題與建議動作）、⑤ 試檢索（輸入問句看候選 chunk 的向量/關鍵字/融合分、層別、AnchorRef、片段與信心；不呼叫 LLM、不寫稽核）。另有 近期問答稽核紀錄 逐筆分頁表（可依信心篩選；無問句本文）。至此 /rag-diagnostics 為完整「RAG 維運中心」。

目標：把 §一～§三 的人工排查變成一頁可視化自助診斷，維運不必翻日誌。此目標已達成——各區的實際功能見上方落地說明，逐項操作見 新手完整操作指南 §14.3；資料源為 KnowledgeSource 的三個狀態、VectorEmbedding 統計與問答稽核紀錄。

不變量：所有查詢與試檢索都必須套團隊權控（此頁限管理員，但仍不得繞過越權洩漏＝0 的原則）；不顯示完整敏感 context 於日誌。

五、「參數化設定 UI」（EVAL-5，✅ 0.3.9 查詢期參數全數落地於 /rag-diagnostics）

已落地（0.3.9）：/rag-diagnostics 除既有的 RejectThreshold／LowConfidenceThreshold（0.3.3）外，新增「查詢期檢索參數」區塊，可直接調整 TopK／CandidateTopK／VectorWeight／KeywordWeight／MinScore 並熱套用（免改 appsettings、免重啟）。

機制：

  • 查詢期參數用獨立單列覆蓋表 RetrievalParamOverride（與門檻表 RetrievalSettingOverride 分表，避免兩者的「回復預設」互相清除），同走 IRetrievalSettingsProvider（讀取優先序：DB 覆蓋 → appsettings → 程式預設）。
  • RetrievalService 由原本直接吃 IOptions<SystemSettings> 改為每次檢索即時解析 GetEffectiveParamsAsync()，因此頁面套用後下一次檢索即生效；並可「回復預設」。
  • 驗證：TopK ≥ 1、CandidateTopK ≥ TopK、VectorWeight／KeywordWeight／MinScore ∈ [0,1]（不合法即擋下，不寫入）。
  • 稽核：覆蓋表記錄 UpdatedAt／UpdatedBy。

刻意不納入熱套用的參數：切塊三參數（ChunkTargetChars／ChunkMaxChars／ChunkOverlapChars）改動須重建索引才生效，性質與查詢期參數不同，維持於 appsettings.json，不在此頁熱套用（頁面亦明示此點）。

與評測基線的關係（調參—量測閉環）：在 /rag-diagnostics 調完查詢期參數後，到 /rag-evaluation「評測全部」並與基線（EVAL-1，見檢索品質評測使用指南 §四）比對逐指標差異，即可判斷此次調整是變好還是變差——診斷頁調參、評測頁量測、診斷頁看 topScore 分佈是否改善，形成完整閉環。

六、落地順序建議（呼應補強清單）

  1. 先打數據地基：EVAL-2（稽核持久化）→ EVAL-3（topScore 分佈統計）。沒有數據，門檻校準與診斷網頁都只是空殼。
  2. 再做可視化：EVAL-4 診斷網頁（先做「索引健康區 + 參數現值區 + 症狀自檢區」，分佈區待 EVAL-2/3）。
  3. 再做可調參：EVAL-5 參數化設定 UI（✅ 0.3.9 查詢期參數全數上線；索引期／切塊參數因需重建索引仍維持 appsettings）。
  4. 資安紅線並行不等：SEC-1／SEC-2 不需等上述，應優先處理。
