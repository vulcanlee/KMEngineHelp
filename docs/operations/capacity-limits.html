部署與維運

容量邊界與限制

彙整各匯入/處理管線的容量上限、逾時、格式限制與超限行為，避免「超限靜默失敗」踩雷

  • 文件用途：彙整各匯入/處理管線的容量上限、逾時、格式限制與超限行為，避免「超限靜默失敗」踩雷
  • 主要讀者：維運、部署、客服與導入人員
  • 編碼：UTF-8（繁體中文，含 BOM）

數值對齊程式常數（如有調整以程式為準）；設定項說明見 日誌與設定檔說明，外部工具見 外部工具安裝與路徑設定。

一、上傳檔案大小上限

管線單檔上限常數位置超限提示
文件轉文字1 GBDocumentExtractionService.MaxUploadFileSize✅ 新增前檢查，提示「檔案 {名} 超過 1GB 限制」
圖片解讀50 MBImageRecognitionService.MaxUploadFileSize✅ 提示「檔案 {名} 超過 50MB 限制」
音訊／影片轉錄2 GBMediaTranscriptionService.MaxUploadFileSize✅ 提示「檔案 {名} 超過 2GB 限制」（會議錄音上傳 /meeting 亦走此服務同上限）
  • 前端 InputFile 以後端常數呼叫 OpenReadStream(maxSize)，避免 Blazor 預設 30MB 緩衝上限造成讀取中斷。
  • 影片連結（YouTube／抖音）為網址匯入、無本地上傳大小限制，但受下載逾時與來源限制影響（見第三節）。

文件轉文字：批次上傳壓縮檔（.zip）

「批次上傳壓縮檔」入口會解壓 zip、為裡面每個支援的檔案各建立一筆記錄（標題取自檔名，去副檔名）。為防 zip bomb，有下列上限（超過即整批拒絕、不建立任何記錄）：

項目上限常數位置
單一 zip 可匯入檔案數500 個DocumentExtractionService.MaxBatchFileCount
單一 zip 解壓後總量2 GBDocumentExtractionService.MaxBatchUncompressedBytes
  • 子資料夾內的檔案一律遞迴取出（忽略資料夾結構，僅用檔名）。
  • 不支援副檔名的檔案、以及嵌套的 .zip 會被略過，並於匯入結果視窗列出清單；成功者各自排入既有轉換佇列。
  • zip 本身上傳仍受單檔 1GB（MaxUploadFileSize）串流上限；壓縮檔損毀無法讀取時整批拒絕並提示。

圖片解讀：批次上傳壓縮檔（.zip）

「批次上傳壓縮檔」入口會解壓 zip、為裡面每張支援的圖片各建立一筆記錄（標題取自完整原始檔名）。與文件轉文字不同，圖片批次匯入不自動排入解讀佇列，記錄維持「未解讀」狀態，AI 視覺解讀由使用者之後手動觸發。為防 zip bomb，有下列上限（超過即整批拒絕、不建立任何記錄）：

項目上限常數位置
單一 zip 可匯入圖片數500 張ImageRecognitionService.MaxBatchFileCount
單一 zip 解壓後總量2 GBImageRecognitionService.MaxBatchUncompressedBytes
  • 子資料夾內的圖片一律遞迴取出（忽略資料夾結構，僅用檔名）。
  • 非圖片格式（非 ImageFormatValidator 允許清單）、以及嵌套的 .zip 會被略過，並於匯入結果視窗列出清單。
  • zip 本身上傳受單檔 50MB（ImageRecognitionService.MaxUploadFileSize）串流上限；壓縮檔損毀無法讀取時整批拒絕並提示。

二、影音轉逐字稿：Whisper 上限與自動分段

語音轉錄採 gpt-4o-transcribe，單次請求有大小與長度上限，系統會自動分段後逐段轉錄再合併。

項目值常數
單段檔案大小上限25 MBOpenAISettings.MaxChunkSizeMB
單段音訊長度上限1200 秒（模型上限 1400 秒，預留餘裕）OpenAISettings.MaxChunkDurationSeconds
分段數估算max(⌈大小/25MB⌉, ⌈總長/1200s⌉)MediaChunker / TranscriptionProcessor
  • 分段以 FFmpeg 依時間切割、統一轉 MP3（chunk_000.mp3…）。FFmpeg 必須安裝且路徑正確（見風險）。
  • 分段任一步失敗 → 整筆標記「失敗」並記錄錯誤訊息；可於該紀錄重試。

五、超限/失敗行為與「靜默失敗」風險

已有明確前端提示：文件/圖片/音訊超大小、圖片/音訊不支援格式 → 通知欄即時中文提示。

需注意（可能不直覺或需查紀錄才知原因）：

  1. 文件轉文字格式不支援：自 0.2.92 起前端以 <InputFile accept> 預檢、後端以 DocumentFormatValidator 驗證，非允許清單（含 .txt、.pdf、Office 等）會直接擋下並提示「僅接受：…」；清單內檔案若 MarkItDown 仍轉換失敗，須點該筆「檢視錯誤訊息」才知原因。
  2. FFmpeg 未安裝/路徑錯誤：啟動時不檢查，首次音訊分段才會報錯。部署前請依「外部工具安裝與路徑設定」驗證 OpenAISettings.FfmpegPath。
  3. 抖音/yt-dlp 下載逾時或來源限制：逾時即標記失敗，可重試；cookies 設定不全可能下載失敗。
  4. 音訊長度偵測失敗：MediaChunker 取得長度失敗時回 0，可能影響分段估算。
  5. Kestrel/SignalR 預設大小：Program.cs 未顯式設定 MaxRequestBodySize；如未來經非 InputFile 路徑上傳大檔，需顯式提高 Kestrel 限制。目前各上傳走 InputFile 串流並以後端常數放寬，常規情境無虞。
  6. LLM 未設定：未設定聊天/生成 LLM（雲端 ApiKey 或地端 LocalBaseUrl/LocalGenerationModel）時，清洗會略過 LLM 增強（去重/遮罩/分類/摘要），僅輸出彙整＋繁體正規化，並於結果加註記。詳見 日誌與設定檔說明 的 OpenAISettings。
  7. 問答稽核明細無上限、無清理（0.3.29）：AI 知識問答與知識來源 AI 對話每一輪聊天各寫一個 .md 全文檔至 ChatLogPath（依年度分層），屬熱路徑且目前無保留/自動清理策略，檔數與磁碟用量會隨使用持續成長。維運上應定期監控該目錄磁碟用量，必要時自行歸檔/清理舊年度資料夾（清理僅影響「查看全文」，不影響 DB 索引與滿意度統計）。DB 端 LlmChatLog 每輪僅一列中繼資料，成長量小。
  8. Token 用量表無上限、無清理（0.3.30）：每次 OpenAI 呼叫各寫一列 LlmTokenUsage（純數字、無內容）。呼叫頻繁的部署下資料列會持續累積、目前無保留/清理策略，管理員應留意資料表大小，必要時自行封存/清除舊資料（清理僅影響 /token-usage 查閱與首頁近 30 天統計）。寫入走 Channel ＋背景批次落地，不阻塞 LLM 主流程。
  9. 🟡 知識來源清洗的內容被輸出上限截斷（1.0.112 已修）：聚合後的內容沒有任何大小或成員數上限，而清洗的去重／遮罩兩步要「整份重新輸出」。1.0.112 起遮罩被截斷即整筆清洗失敗、去重被截斷則退回原文並留 > 註記：。⚠️ 1.0.112 之前這是唯一完全靜默的失敗（狀態仍「已清洗」、信心可能還很高、沒有任何註記，整條 RAG 建立在殘缺內容上），該版之前清洗的知識來源仍需檢查。判斷方法與分盒策略見 §七 與 知識來源分盒與規模上限指南。

圖譜的上限分兩類：安全閥（防大圖遍歷爆炸）與成本閥（每次 LLM 呼叫都要錢）。

⚠️ 四個 appsettings 成本／安全閥（GraphMaxNodes／GraphGlobalCommunityCap／GraphMaxCommunities／GraphAliasNameCap）沒有線上熱調路徑，改了必須重啟服務。相對地 GraphWeight／GraphMaxHops／GraphHopDecay 可在 /rag-diagnostics 即時調整——所以appsettings 上看到的值不一定是生效值。四項成本閥填 0 或負數時以 1 計，不會靜默停擺。

⚠️ 全域問答的成本是社群數的倍數，不是一問一次 LLM：20 個社群的一題全域問答約 21 次呼叫（20 次 map ＋ 1 次 reduce）。REST 端點沒有 API 專用節流，對外開放時請在前端閘道加限流。

⚠️ 每次檢索與全域問答仍會全表載入已核可別名與社群（已加索引與行程內快取，但未做分頁）。超大圖時這是已知的效能待優化項，見 GraphRAG 待辦盤點。

參數語意與調校見 日誌與設定檔說明 §4.7.3；操作與 FAQ 見 知識圖譜使用指南。

七、知識來源聚合與清洗的容量邊界

前六節談的是「單筆素材」的上限。本節談把多筆素材聚合成一個知識來源之後的規模邊界——這一段的行為與前面幾條很不一樣，而且含一種完全靜默的失敗。

7.1 上限一覽

項目上限常數位置超限行為
一個知識來源的成員數無上限KnowledgeSourceContentAggregator.BuildAsync不擋
聚合後的內容總量無上限同上（全部讀進單一 StringBuilder）不擋
送進 LLM 的內容量由模型上限決定CleaningEnhancer.ComposeStepPrompt（prompt + "\n\n\n" + 整份全文）見 7.2

⚠️ 實際天花板是模型的「輸出上限」，不是輸入上下文。 清洗的去重與遮罩兩步是「把整份內容重新輸出一遍」（CleaningEnhancer 去重步驟／MaskAsync），所以受限於模型一次能吐出多少字；分類／摘要／信心只輸出短內容，不受影響。

7.2 三種超限行為

模式觸發行為有無提示
A 輸入超限超過模型輸入上下文遮罩步驟丟 InvalidOperationException（HTTP 400）；該例外非暫時性（PipelineRetryHelper.IsTransient 回 false）→ 不重試、直接標記失敗✅ 狀態「失敗」＋錯誤訊息含 HTTP 狀態
B 輸出被截斷輸入塞得進、輸出撞上限1.0.112 起會攔下：遮罩被截斷 → 整筆清洗失敗並說明原因；去重被截斷 → 退回未去重原文並留 > 註記：。1.0.112 之前是串流正常結束、內容非空 → 被當成功（狀態「已清洗」卻殘缺）✅ 1.0.112 起有（失敗訊息或註記）<br>❌ 1.0.112 之前完全沒有
C 檢索稀釋未截斷但單盒內容過多候選 CandidateTopK=50 → 最終只有 TopK=10 段進 LLM；正確段落可能擠不進前 10，且兩段式門檻不會攔（主題相關、分數不低）❌ 無提示，答案不完整但有自信

🟡 B 曾經是本文開頭要避免的「超限靜默失敗」中唯一完全無痕跡的一種，1.0.112 已修。 做法：新增 OpenAIChatCompletionClient.CompleteStreamingCheckedAsync（讀 SSE 的 finish_reason），只讓清洗的去重與遮罩改用；CompleteStreamingAsync 的行為與另外 10 個呼叫端完全不變。⚠️ 1.0.112 之前清洗的知識來源仍可能已被靜默截斷，需用 分盒與規模上限指南 §4.2 的三步檢查確認。

PDF 萃取那條路有這道檢查（PdfMarkdownLlmClient.EnsureNotTruncated，PdfMarkdownLlmClient.cs:103；判定用的 IsTruncatedByOutputLimit 是 public static、可重用），但其註解明寫刻意不放進共用方法，以免行為擴散到另 4 個呼叫端。清洗因此沒有這道保護。改善建議見 知識來源規模守門 TODO。

7.3 相關行為與可觀測性

  • 各步驟失敗的痕跡不同：去重／分類／摘要可降級並在清洗後檔案開頭寫 > 註記：；信心解析不出 → 轉「待審核」並記註記；遮罩失敗＝整筆清洗失敗（刻意的安全設計）；被截斷則毫無註記。
  • 蒸餾同樣是單次呼叫帶整份清洗後全文，且須輸出 JSON 陣列；JSON 解析失敗會降級成單一 Wiki 頁並加註記（DistillationEnhancer.ParsePages）。
  • 嵌入索引不是瓶頸：切塊後每批 64 筆嵌入（EmbeddingIndexProcessor.EmbedBatchSize），以 ContentHash 增量重建。
  • 「跑很久」多半正常：CleaningProcessor 的 1.0.98 註解記載實測——大內容時去重／遮罩各可達十餘分鐘；§三 的串流逾時是閒置逾時而非總時長，調高它對截斷沒有幫助。
  • 低比值回溯偵測（1.0.116 起）：「清洗後 ÷ 彙整前」比值低於 SystemSettings.Cleaning.CleanedRatioWarnBelow（預設 0.30）時，清洗對話窗警示，且 /data-consistency 的「低比值來源」會列出全庫可疑者。專門用來找出 1.0.112 之前已被靜默截斷、沒有留下痕跡的舊資料；⚠️ 會有誤報（內容本來就高度重複者）。0 或負數＝停用。
  • 清洗前有軟上限警告（1.0.114 起）：彙整量超過 SystemSettings.Cleaning.AggregateWarnBytes（預設 200000 位元組）時，「確認清洗」對話窗顯示警示並要求勾選確認才能送出。是提示不是阻擋（TriggerCleaningAsync 行為不變）；0 或負數＝停用；需重啟生效。預設值是保守起點，請以實測校準。
  • 彙整量在畫面上看得到（1.0.113 起）：知識來源加工的「管理成員」與「確認清洗」兩個對話窗顯示 彙整量：約 X（Y 個可用成員，Z 個略過）；已清洗過者另顯示清洗後大小與比值（KnowledgeSourceService.MeasureAsync → KnowledgeSourceContentAggregator.MeasureAsync，只讀 FileInfo.Length 不讀內容，故為估計值）。⚠️ /reports/content-inventory 仍只統計筆數，無字數或位元組（ContentInventoryReportService）。刻意不做成列表欄位：一頁 20 筆 × 每盒 15 成員＝每次渲染 300 次檔案查詢。

判斷方法、實測上限的步驟、分盒與拆檔策略，見 知識來源分盒與規模上限指南。快速版：清洗後 .md ÷ 成員萃取檔總大小，比值正常在 0.5～1.0；低於 0.3 且沒有 > 註記： 就要懷疑是模式 B。
