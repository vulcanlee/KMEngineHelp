1.2 只是標成過時，內容不動

你做的效果

⚠️ 「過時」只是一個標籤，不擋任何事。 舊的清洗內容與向量索引原封不動留著，問答照樣拿它們作答。要讓它真的更新，只有一條路：重新清洗 → 重新蒸餾 → 重建索引。

1.3 完全沒反應（改了但既有資料不會跟著變）

你做的為什麼沒反應
刪除或改名分類分類是以分隔字串存在每一筆紀錄的 Categories 欄位裡，沒有外鍵。刪掉分類主檔，紀錄上那個名字還在（幽靈分類）
刪除或改名團隊同上，Teams 欄位也是分隔字串
刪除或改名提示詞、專案分類同上，引用端不檢查主檔
只改素材的標題／分類／團隊刻意的設計：中介資料不進清洗的聚合內容，所以不標過時。有測試釘住這條
刪除清洗規則設定已經清洗完的內容不受影響（清洗當下就把結果寫成檔案了）

二、主線五類詳解

2.1 刪除知識來源

程式進入點：KnowledgeSourceService.DeleteAsync。

  1. 檢查團隊權限（TagStringHelper.IsTeamAccessible）。非管理員刪不了別人團隊的來源。
  2. 先刪磁碟檔：該來源的清洗檔，以及它底下每一頁 Wiki 的實體檔（DeletePhysicalFile）。
  3. 再刪 DB 列，由外鍵連帶處理：KnowledgeSourceItem、WikiPage、VectorEmbedding、GraphEdge、GraphNode、GraphTriple 全部設為 Cascade（見 BackendDBContext.OnModelCreating）。

先刪檔再刪列是刻意的順序：DB 的連帶刪除不會碰磁碟，若順序反過來就找不到該刪哪些檔，會留下永久孤兒檔。

匯入產物不會被刪。 那些錄音、PDF、圖片是獨立的紀錄，刪知識來源不會動到它們——你可以用同一批素材重新編一個知識來源。

2.2 刪除素材

程式進入點：MediaTranscriptionService／DocumentExtractionService／ImageRecognitionService／MeetingService 的 DeleteAsync。

  1. 先取消背景作業（三個匯入型會呼叫 cancellationRegistry.TryCancel）——正在轉錄中的紀錄也刪得掉，不會留下跑到一半的工作。
  2. 刪磁碟檔：各自的原始檔、轉出文字、AI 產生內容（會議紀錄型的附件與 AI 會議紀錄 .md 自 1.0.122 起才會一併刪，見 §7.1）。
  3. 呼叫 KnowledgeSourceMaintenanceHelper.MarkOwningSourcesStaleAsync，且 removeOrphanItems: true：引用它的成員列當場移除，同時把那些知識來源標成 內容已過時。

⚠️ 這一步不會碰清洗檔、不會碰向量索引。所以：

你刪掉了那份錄音，但問答還是查得到它的內容。

因為清洗當下已經把成員內容抄成一份獨立的清洗檔，向量索引也是從那份檔案建的。要讓內容真的從問答中消失，必須重新清洗。 詳見 §五。

2.3 編修素材的文字

改逐字稿、改轉出的 Markdown、改 AI 會議紀錄的全文 → 只標過時，成員列保留（素材還在，只是內容變了）。

判斷準則很明確：有沒有寫回「知識來源聚合時會讀的那個檔案」。以會議紀錄為例，聚合讀的是 GeneratedContentRelativePath 指向的 .md 全文，不是摘要／決議／出席者那三個欄位——所以套用 AI 產出欄位不標過時，編修全文才標。

2.4 素材上傳新版本

KnowledgeSourceMaintenanceHelper.RepointOwningSourcesToNewVersionAsync：成員的 ItemId 自動改指向新版素材，來源標過時。你不必手動去每一個知識來源重掛一次。

2.5 刪除單一 Wiki 頁

程式進入點：WikiPageService.DeleteAsync。

  1. 檢查團隊權限。
  2. 刪該頁的實體檔。
  3. 先刪指向該頁的 VectorEmbedding，再刪頁本身。

第 3 步是必要的：VectorEmbedding → WikiPage 這條外鍵刻意設成 Restrict（不是 Cascade），為的是避免 SQL Server 判定多重串聯路徑。所以刪頁時要由程式顯式清向量，否則刪不掉。重蒸餾與編修頁時也走同一條規則，由索引管線負責。

3.2 管理者才碰得到的（列出來是為了完整）

物件刪除時會發生什麼
分類、團隊、提示詞、專案分類只刪主檔。引用端是分隔字串、無外鍵，既有紀錄不受影響也不會被擋
清洗規則設定只刪設定。已清洗的內容不受影響

知識圖譜的社群摘要與概念連結邊沒有「刪除按鈕」——它們由重建作業整批清除後重算（GraphCommunityBuilder、GraphEdgeService 用 ExecuteDeleteAsync），不是逐筆刪。

3.3 外鍵政策的全貌

BackendDBContext.OnModelCreating 開頭就把所有外鍵預設設成 Restrict，再逐一覆寫成 Cascade。所以「沒有明講的就是不連帶刪、而且有子資料時父資料刪不掉」。

  • 覆寫成 Cascade：專案→附件、工作任務→附件、會議→附件、知識來源→（成員／Wiki 頁／向量／圖譜邊／圖譜節點／三元組）
  • 保留 Restrict 且由程式手動處理：工作任務→子工作（自我參照，SQL Server 不允許 Cascade）、向量→Wiki 頁（避免多重串聯路徑）
  • 根本沒有外鍵：成員↔素材（靠 ItemType＋ItemId 軟參照）、分類／團隊／提示詞（分隔字串）、圖譜社群／別名／作業狀態、各種稽核與統計表

四、磁碟檔與資料庫列是兩回事

資料庫的連帶刪除永遠不會碰磁碟。每一支服務都要自己刪檔，漏了就是永久孤兒檔——不佔功能、只佔空間，而且沒有任何巡檢會抓。

目前會主動刪檔的：知識來源（清洗檔＋Wiki 頁檔）、Wiki 頁、四種素材、專案與工作任務的附件。

⚠️ 一個已知例外見 §七之一。

五、⚠️「以為刪掉了，其實還查得到」

這是本文件最重要的一節，同時是資安問題。

發生情境：你上傳了一份含敏感內容的文件，發現不該放，於是到「文件轉文字」把它刪掉。

你以為的結果：內容消失了。

實際的結果：

層狀態
原始檔與轉出文字✅ 已刪
該素材的紀錄✅ 已刪
知識來源的成員列✅ 已移除
知識來源狀態標成 內容已過時
清洗後的內容❌ 還在（清洗時已抄成獨立檔案）
向量索引❌ 還在（從清洗檔建的）
Wiki 頁❌ 還在
AI 知識問答❌ 照樣查得到、照樣拿它作答、出處也照樣列出來

正確的處置順序：

  1. 刪掉素材
  2. 到「知識來源加工」對受影響的來源按重新清洗（此時該成員已不在，內容就不會再被納入）
  3. 重新蒸餾
  4. 重建索引
  5. 到 AI 知識問答實際問一次，確認查不到了

第 2 步之後 內容已過時 才會被清掉——全系統只有重新清洗完成這一個地方會清除這個標記（CleaningProcessor）。

⚠️ 但重跑管線不等於內容被清除

重新蒸餾採的是版本化，不是覆蓋（DistillationProcessor）：

  • 舊的現行版 Wiki 頁 → 標成「已汰換」，保留不刪，供稽核與時點查詢
  • 它的向量 → IsCurrent = false，退出一般檢索

也就是說，重跑完管線後那些頁還在資料庫與磁碟上，只是問答不會再拿它們作答。對「內容過時了要更新」而言這是好設計；但如果你的目的是把敏感內容真正移除，這樣不夠乾淨。

真正要移除，只有一條路：刪掉整個知識來源（§2.1）——那會把清洗檔、全部 Wiki 頁（含已汰換的）、全部向量索引一次帶走。代價是同一批素材要重編一個新的知識來源。

判斷準則：「內容過時」→ 重跑管線就好；「這份東西不該存在」→ 刪掉整個知識來源。

六、怎麼知道現在有哪些東西不一致

到「系統管理 → 資料一致性巡檢」（/data-consistency），三個區塊：

區塊抓什麼怎麼處理
孤兒成員引用的素材已不存在的成員列按清除。正常流程不會產生（刪素材時當場就移除了），出現通常代表是 1.0.122 之前走 REST API 刪會議留下的（見 §7.1），或是更早的舊版留下的
過時來源內容已過時 的知識來源逐筆或批次重新清洗
低比值來源清洗後／彙整前的比值偏低者，可能是 1.0.112 之前被靜默截斷重新清洗一次驗證

管理員看全庫；非管理員依團隊權控過濾。

另外「系統管理 → 診斷與日誌 → 檢索診斷與調校」（/rag-diagnostics）也會把過時來源數列進健康檢查與建議事項。知識來源清單頁本身則在該列直接顯示過時徽章。

七、已知落差（1.0.119 查證時發現）

以下是現況陳述，不是預期行為。列在這裡是為了讓你在遇到時知道不是自己操作錯。第一項已於 1.0.122 修正，其餘兩項仍待處理。

7.1 ~~用 REST API 刪會議，行為與畫面不一樣~~（1.0.122 已修正）

DELETE /api/meeting/{id} 走 MeetingRepository.DeleteAsync、畫面走 MeetingService.DeleteAsync，是兩條不同的程式路徑。1.0.122 之前 API 那條不刪實體檔、也不清孤兒成員與標過時，會留下磁碟孤兒檔、孤兒成員，而且引用它的知識來源不會被標成過時——使用者完全不會知道那個來源的內容已經失準。

修法：連帶處置收進 MeetingDeletionHelper.PrepareDeleteAsync，兩條路徑呼叫同一份（與 KnowledgeSourceMaintenanceHelper 同一個形狀：不呼叫 SaveChanges，交由呼叫端提交）。MeetingDeleteParityTests 釘住兩條路徑的結果必須一致，含一條反證確認權限不足時什麼都不動（權限檢查必須在刪檔之前，順序反了會變成「刪不掉但檔案已經沒了」）。

順帶修掉同一版查出的第二個洞：Meeting.GeneratedContentRelativePath（AI 會議紀錄的 .md）兩條路徑原本都沒刪，畫面刪也會留孤兒檔。現在兩條都會刪。

7.2 四個素材的 DeleteAsync 沒有團隊權控檢查

MediaTranscriptionService／DocumentExtractionService／ImageRecognitionService／MeetingService 的 DeleteAsync 都沒有 IsTeamAccessible 檢查，而：

  • 同一個檔案裡的 RetryAsync 有
  • KnowledgeSourceService.DeleteAsync 與 WikiPageService.DeleteAsync 有
  • MeetingRepository.DeleteAsync（API 路徑）有

實務上的可利用性低——清單查詢本身已套團隊權控，Blazor Server 的元件狀態在伺服器端，使用者只刪得到畫面上渲染出來的那幾列。但這是防禦縱深的不一致：同一個服務的兩個方法標準不同。

7.3 分類／團隊／提示詞刪除時不檢查是否還被引用

因為標籤欄位是分隔字串、沒有外鍵，刪除主檔既不會被擋、也不會回寫既有紀錄。結果是紀錄上留著一個「主檔已不存在」的名字（幽靈分類）。

這是既有的設計取捨（見 知識庫命名規範與範例 對「改不動」欄位的說明），不是新問題；列在這裡是因為它符合本文件「刪了會發生什麼」的主題。

剩下兩項要不要修、怎麼修，屬於另一項工作。§7.2 刻意四支一起改——只補 MeetingService 一支會製造「四支裡三支沒有、一支有」的新不一致。
