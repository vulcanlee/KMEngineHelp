部署與維運

維護規範

文件目的

定義本專案在「每次提交異動」時必須遵循的最低規範，包含版本遞增、文件同步、檔案編碼，以及 commit 前的自我檢查清單。

任何 PR 或 commit 在進入主線前，請先逐項對照本文件確認。

1. 規範一：每次更新必須 bump 版本

唯一版本來源是：

src/KnowledgeExtraction/KnowledgeExtraction.Web/appsettings.json
└─ SystemSettings.SystemInformation.SystemVersion

1.1 版號格式

Major.Minor.Patch (YYYY/MM/DD)

例：0.1.69 (2026/05/11)

1.2 遞增規則

異動性質應遞增的位元
一般 bug 修正、文件更新、UI 微調、欄位細節Patch +1
新增功能、新 API、新 Entity、新增頁面Minor +1，Patch 歸 0
不相容性變更、資料庫結構大改、整體架構重組Major +1，Minor 與 Patch 歸 0

1.3 日期同步

括號內日期必須更新為 commit 當天日期，格式 YYYY/MM/DD，與 Asia/Taipei 時區的當天一致。

1.4 檢查方式

Select-String -Path "src/KnowledgeExtraction/KnowledgeExtraction.Web/appsettings.json" -Pattern "SystemVersion"

2. 規範二：影響到既有文件就必須同步更新

請參照下表檢核：

異動類型必須同步更新的文件
新增 / 修改 / 刪除 Entity 或欄位資料模型與資料庫.md
新增 / 變更 Migration資料模型與資料庫.md + EFCore.md（若操作流程改變）
新增 / 變更 API Controller、回應格式、Search DTOWeb API 設計慣例.md
變更登入、登出、權限、Menu.json、RoleView 結構認證授權與權限機制.md + 必要時 記住我登入原理說明.md
變更登入頁 UI / 功能login-redesign.md
變更支援文化、新增 Resource 字串、AntDesignLocaleFactory多語系與本地化.md
變更附件機制、新增上傳模組檔案上傳機制.md
變更日誌規則、新增 NLog target、appsettings.json 區段日誌與設定檔說明.md
變更專案結構、依賴方向、啟動流程、DI 註冊架構總覽.md
新增 / 移除一份 docs 文件依分類規則放入對應 docs/<分類>/ 子目錄（無適用分類時自動新增分類目錄），並同步更新 docs/README.md 與主 readme.md 第 9 節「文件索引」

一次異動可能同時觸及多份文件，請完整對照後再 commit。

3. 規範三：UTF-8 編碼

3.1 適用範圍

  • docs/**/*.md：必須為 UTF-8 含 BOM，並以繁體中文撰寫，不得有亂碼。
  • .razor、.cs、.json、.css 與非 docs/ 的 .md：採 UTF-8，並確認繁體中文未出現 ?、亂碼方塊或其他不可讀字元。

3.2 推薦設定

  • 文件目錄內的 Markdown 請使用 UTF-8 BOM；這是 scripts/Test-DocsEncoding.ps1 的檢查條件。
  • 程式與設定檔請維持 UTF-8，避免 PowerShell 預設 UTF-16 LE。
  • 編輯後請確認繁體中文未出現 ?、亂碼方塊或其他不可讀字元。

3.3 PowerShell 自我驗證

powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Test-DocsEncoding.ps1

對於 PowerShell 自身建立的檔案（例如 Out-File、Set-Content），請明確指定 UTF-8；若是 docs/*.md，需使用 UTF-8 BOM。

3.1 規範四：文件引用程式碼一律用「符號名」，不用行號

文件引用程式碼時，寫檔名 + 符號名（類別／方法／region），不要寫行號：

  • ✅ ServiceCollectionExtensions.AddApplicationServices、Program.cs 的 EnsureDirectoryExists 呼叫序列
  • ❌ Program.cs:155-169、Login.razor.cs:111-115

原因：1.0.59 的文件稽核發現，六份長青文件中的行號引用無一存活——程式一改就全部失準，且不會有任何工具提醒。符號名則相對穩定，即使搬移檔案也還找得到。

同理，不要在文件中複製程式碼的完整清單（DI 服務清單、常數全文、設定鍵列舉）。複製一份就是多一個漂移來源；請改為指向單一真實來源的檔案，必要時只放「代表性節錄」並明講它不完整。

4. Commit 前自我檢查清單

4.1 先跑一鍵檢查（1.0.118 起）

pwsh -NoProfile -File scripts/Test-All.ps1

這一行把五道守門一次跑完，不必再記五條指令：

順序守門檢查什麼大約耗時
1Markdown 轉換核心scripts/md_render.py 的輸出與黃金檔相符（1.0.121 起）< 1 秒
2文件編碼docs/**/*.md 是 UTF-8 含 BOM、無亂碼< 1 秒
3文件連結與錨點相對連結的目標檔案存在、#錨點 對得到標題約 1 秒
4說明網站乾跑由 docs/ 產生說明網站時沒有解析不到的連結（--check 不寫檔）約 2 秒
5單元測試dotnet test 全綠約 1～2 分鐘

第 1 道排在最前面是因為：轉換核心壞了，第 3、4 道的結果就不可信（產出的 HTML 本來就不對）。若它紅燈而你確定是刻意的行為變更，跑 python scripts/Test-MdRender.py --update 更新黃金檔，並在 commit message 說明為什麼。

三個刻意的行為：

  • 第一道失敗不會中斷，全部跑完才收尾。這幾項彼此獨立，一次看到全部的失敗清單，比修一項、再跑一次、再發現下一項省時間。
  • 由便宜到昂貴排序：前四道加起來幾秒內就有結果，最慢的測試放最後。
  • 結束碼：全通過 0、任一項失敗 1，可直接當 CI 或 git hook 的判斷依據。

⚠️ 這個腳本不檢查版本號有沒有 +1，也不檢查文件內容有沒有跟著改（第 1、2 節）——那兩件事沒有機械判準，仍然要靠下面的清單自己對。全綠時腳本會再提醒一次版本號。

4.2 CI

.github/workflows/ci.yml 在推上 main 時於 GitHub Actions 跑同一支 Test-All.ps1。

刻意只呼叫腳本、不在 workflow 裡把守門清單再列一次：列兩份的話，日後新增守門一定會漏改其中一份，CI 就會在沒人發現的情況下少檢查一項。守門清單的唯一真實來源是 scripts/Test-All.ps1。

這個判斷在 1.0.121 得到印證：那一版新增第五道守門，ci.yml 一個字都不用改。

CI 跑在 ubuntu-latest。若日後有測試因 Linux 環境差異而失敗（本機只在 Windows 驗過），把 runs-on 改成 windows-latest 即可，代價是私有 repo 的分鐘數以兩倍計。

4.3 逐項確認清單

本節是每次 commit / release 的操作檢查清單；項目需依當次異動逐項確認，不視為常駐 backlog。

請於 commit 前逐項確認（建議貼到 PR 描述中）：

  • appsettings.json 的 SystemVersion 已遞增（含日期）。
  • 本次異動所影響的 docs 文件已同步更新（對照第 2 節）。
  • docs/*.md 皆通過 scripts/Test-DocsEncoding.ps1（UTF-8 BOM、無亂碼）（§4.1 已涵蓋），其他新增 / 修改檔案皆採 UTF-8。
  • 新 / 改 API：已寫 Debug 進站、Information 成功、Warning 失敗、Error 例外四類日誌。
  • 新 / 改 Entity：已執行 Add-Migration 並通過 Update-Database。
  • 新 / 改 Razor 元件：已驗證 Sidebar 權限項目（若需要）。
  • 本機 dotnet build src/KnowledgeExtraction/KnowledgeExtraction.Web/KnowledgeExtraction.Web.csproj 成功。
  • 文件相對連結可正確開啟（docs/ 內互引、與 readme.md 之間皆通）（§4.1 已涵蓋）。

5. 異動範例

假設本次新增了「Issue（議題追蹤）」實體：

  1. 新增 KnowledgeExtraction.AccessDatas/Models/Issue.cs。
  2. 新增 Migration → 更新 資料模型與資料庫.md、EFCore.md。
  3. 新增 IssueController、DTO → 更新 Web API 設計慣例.md。
  4. 新增 Menu.json 節點與權限 → 更新 認證授權與權限機制.md。
  5. 若有附件 → 更新 檔案上傳機制.md。
  6. 主 readme.md 第 4、6 節（功能列表 / 結構樹）若改變需同步。
  7. appsettings.json：SystemVersion 由 0.1.x → 0.2.0（屬於新功能 → Minor +1，Patch 歸 0），日期更新為 commit 當天。

6. 執行測試套件

只是要「提交前跑一輪」的話，用 §4.1 的 scripts/Test-All.ps1 就好。下面是要單獨跑某一組時的指令。

# 全部測試
dotnet test src/KnowledgeExtraction/KnowledgeExtraction.Tests/KnowledgeExtraction.Tests.csproj

# 只跑某一組
dotnet test src/KnowledgeExtraction/KnowledgeExtraction.Tests/KnowledgeExtraction.Tests.csproj --filter "FullyQualifiedName~KnowledgeBaseChatServiceTests"

# 文件編碼檢查（繁中 UTF-8 含 BOM、無亂碼）
pwsh -NoProfile -File scripts/Test-DocsEncoding.ps1

開發伺服器鎖檔（最常見的測試失敗原因）：若本機正在跑 Web 開發伺服器，bin/Debug 的 DLL 會被鎖住，dotnet test 因無法覆寫而失敗。解法是暫停開發伺服器，或把建置輸出重導到 repo 內的臨時資料夾——必須留在 repo 內，否則會定位原始碼的測試（如 CrudActionIconTests）會找不到檔案：

dotnet test src/KnowledgeExtraction/KnowledgeExtraction.Tests/KnowledgeExtraction.Tests.csproj `
  --filter "FullyQualifiedName~KnowledgeBaseChatServiceTests" `
  -p:BaseOutputPath="src/KnowledgeExtraction/_ketestout/"
# 跑完刪除：Remove-Item -Recurse -Force src/KnowledgeExtraction/_ketestout

測試基礎設施：KnowledgeExtraction.Tests 使用 in-memory SQLite（Data Source=:memory:）＋ EnsureCreatedAsync() 由 model 直接建表——新增 DbSet 後測試資料庫會自動包含新表，不需在測試裡跑 migration。
