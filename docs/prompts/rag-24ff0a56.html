RAG 的機制討論與調整

使用 superpowers 技能

在這個知識庫系統已經有設計 RAG 這樣的機制，並且使用向量資料庫來儲存每個 chunk 內的 embedding 向量，另外也有 Top-K 的設計，並且也有設計 RejectThreshold 機制，可以排除低品質的 chunk，最後會將 top-k 設定數值的 chunk 送至 LLM 來進行問答，不過，對於這些超過 RejectThreshold 設定值的 chunk，是否也需要像網路上一些文章或影片所提到的，需要進行 re-rank 嗎?

目前文件有參數表，也有問題對照表，對於維運人員遇到問題時，是否還需要可能還是需要一個更直覺的判斷流程，或者一個網頁來進行各種狀況的分析，並且提出建議，而系統是否可以提供相關參數化的調整與設定機制，這裡有個RAG問題診斷流程可以參考，並且補強這裡的流程，讓這個 RAG 系統可以變得更加穩定與可靠，也可以在上線之後，可以快速的蒐集問題與找出問題在哪裡，是資料品質不佳，又或者是在清洗和蒸餾階段的作法不好，又或者是 RAG 設計上有問題，或者需要調整 RAG 的參數

使用者問答異常
│
├─ 一律查無依據？
│   ├─ 檢查 embedding 是否設定
│   ├─ 檢查 VectorEmbedding 是否為空
│   ├─ 檢查來源是否已清洗
│   └─ 執行建立索引
│
├─ 有命中但答案不準？
│   ├─ 檢查 TopK / CandidateTopK
│   ├─ 檢查 chunk 是否太小或太大
│   ├─ 檢查 Wiki 是否過度摘要
│   └─ 檢查是否需要 adjacent chunk expansion
│
├─ 庫外問題仍硬答？
│   ├─ 查看 topScore 分佈
│   ├─ 提高 RejectThreshold
│   └─ 提高 LowConfidenceThreshold
│
└─ 出處錯誤？
    ├─ 檢查 AnchorRef
    ├─ 檢查 Cleaned Markdown 結構
    ├─ 檢查 WikiPage 對應
    └─ 重新建立索引

對於現這這個系統上的設計，是否還有哪些建議補強的地方，現在文件中檔案，又有那些關於 rag 的建議或者代辦工作，或者尚未實作項目，將這些問題與工作都全部整理與彙整出來，我需要逐一來處理這些事情，並且依照重要性或者其他分類做法來排列這些清單項目

有人和我提到 : 建議補上「Wiki 與 Cleaned 的角色差異」，針對這個問題，幫忙分析一下
