資料清洗階段設計與分析

(A) 檢視「資料匯入」階段現況缺口與修正方向；(B) 設計「資料清洗」階段的完整架構、品質保證機制與可行性驗證方式，作為日後開發的藍圖。

  • 文件用途：(A) 檢視「資料匯入」階段現況缺口與修正方向；(B) 設計「資料清洗」階段的完整架構、品質保證機制與可行性驗證方式，作為日後開發的藍圖。
  • 主要讀者：開發團隊、技術負責人、決策層
  • 文件版本：1.0
  • 建立日期：2026/06/10
  • 編碼：UTF-8（繁體中文，含 BOM）

五階段流程：資料匯入 → 資料清洗 → 知識頁審核 → 建立知識庫 → 智慧應用。本文件聚焦前兩階段；「知識頁審核」（將清洗後內容蒸餾為 Wiki 實體頁）另立文件。路線圖見 04-開發建議與路線圖，待釐清問題見 05，代辦清單見 planning/07-資料清洗開發代辦清單-TODO。

〇、結論先講（TL;DR）

  1. 匯入階段約完成 70–75%，三條管線（文件→Markdown、媒體→逐字稿、圖片→解讀文字）可運作，但缺重試/取消、圖片未佇列化、容量邊界不一致等（見 Part A）。
  2. 「資料零散破碎」的結構性根因：三類匯入紀錄（MediaTranscription/DocumentExtraction/ImageRecognition）彼此無關聯、無歸屬容器，全是頂層獨立單筆紀錄。
  3. 解法核心：新增「知識來源（KnowledgeSource）」實體，把多筆零散素材聚合成一個有主題、可清洗、可權控的完整來源；清洗一律以「來源」為單位進行（見 Part B）。
  4. 品質保證採分階段疊加：全自動先求有 → LLM 信心分數門檻 → 人工審核關卡 → 清洗品質評測集量化。
  5. 一切沿用既有慣例：佇列＋背景服務、團隊權控（TagStringHelper）、雙資料庫 migration、標籤字串＋AutoMapper、設定驅動供應商切換——不另起爐灶。

Part B — 資料清洗階段設計（本文件重點）

B-1. 設計目標與「資料清洗」的定義

把匯入後零散、破碎、單一的素材（單一檔案／影片／錄音／圖片），整理成乾淨、彙整、具主題、可權控的「來源級資料」。

本階段做：彙整、去重、品質過濾、正規化（含繁體統一）、敏感資訊遮罩、分類/標籤建議、摘要與實體擷取。 本階段不做：知識頁審核（蒸餾成一概念一頁、[[wiki-links]] 互連的 Wiki 實體頁）、切塊、Embedding、向量索引——這些屬後續階段。

B-2. 核心概念：知識來源（KnowledgeSource）

這是解決「資料零散」的關鍵。把「清洗的單位」從單筆紀錄，提升為「主題來源」。

  • 一個 KnowledgeSource = 一個主題來源，內含 1..N 筆匯入紀錄（成員 item）。
  • 範例：一場產品會議 = 會議錄音逐字稿（MediaTranscription）＋ 簡報 PDF 萃取（DocumentExtraction）＋ 白板照片解讀（ImageRecognition）＝ 同一個來源。
  • 單一素材也包成來源：即使只有一個檔案，也視為「只含一個 item 的來源」。如此所有清洗都統一經由 KnowledgeSource，模型一致、下游（蒸餾/索引）只需面對「來源」一種輸入。
  • 權控沿用既有機制：來源帶 Categories/Teams 標籤，套 TagStringHelper.BuildTeamAccessPredicate/IsTeamAccessible + IRecordAccessScopeProvider，非管理員只能看「無團隊(公開)或與角色團隊交集」的來源。
  • 為何不直接在三類紀錄加 ProjectId：Project 是「專案管理」語意（含任務、會議、進度），與「知識彙整」職責不同。用獨立的 KnowledgeSource 作知識層容器，職責清楚、不汙染專案模型。

B-3. 資料模型變更

模型變更必產雙資料庫 migration：SQLite 於 KnowledgeExtraction.AccessDatas、SQL Server 於 KnowledgeExtraction.AccessDatas.SqlServerMigrations 各一。DbSet 命名避免再製造 MyTas ≠ MyTask 式落差。

新增 KnowledgeSource 實體（沿用既有處理型紀錄的欄位慣例）：

欄位型別說明
Idint主鍵
Titlestring來源主題標題
Descriptionstring?描述
Categoriesstring?分類標籤（分隔字串，AutoMapper ForMember ⇄ List）
Teamsstring?團隊標籤（權控用，同上）
Statusstring草稿 / 整理中 / 清洗中 / 待審核 / 已清洗 / 失敗
ProgressPercentageint清洗進度 0–100
ErrorMessagestring?失敗訊息
CleanedContentRelativePathstring?清洗後彙整產物（Markdown）相對路徑 {yyyy}/{guid}.md
ConfidenceScoredouble?LLM 自評信心（QA-2 啟用）
CleanedAtDateTime?清洗完成時間
ReviewedAtDateTime?人工審核完成時間（QA-3）
ReviewedBystring?審核者（QA-3）
CreatedAt / UpdatedAtDateTime時間戳

新增 KnowledgeSourceItem 成員關聯（多對多、跨型別）：

欄位型別說明
Idint主鍵
KnowledgeSourceIdintFK → KnowledgeSource（Cascade delete，比照 ProjectFile）
ItemTypestringMediaTranscription / DocumentExtraction / ImageRecognition
ItemIdint對應紀錄 Id（多型參照）
SortOrderint來源內排序
CreatedAtDateTime加入時間
  • 採 ItemType + ItemId 多型字串參照（沿用本專案「標籤以字串、避免硬 FK」的務實風格）：一筆紀錄可被多個來源引用（例如一份共用規範文件可同時屬於多個主題來源）。
  • AutoMapper 比照既有 ForMember 模式做 List⇄字串與物件映射；Update/Delete 前 CleanTrackingHelper.Clean<T>()、編輯前 Clone()。

B-4. 清洗管線（沿用佇列＋背景服務模式）

新增 ICleaningQueue + CleaningBackgroundService + CleaningProcessor，完全比照 IDocumentExtractionQueue/DocumentExtractionBackgroundService/DocumentExtractionProcessor（位於 KnowledgeExtraction.Web/BackgroundServices/ 與 KnowledgeExtraction.Business/Services/）。模式：入列來源 Id → 背景服務取出 → Processor 處理 → 更新 Status/Progress/Error。

對一個 KnowledgeSource 觸發清洗，依序執行：

步驟動作備註
1. 彙整讀取所有成員 item 的抽取文字（.md/.txt），依 SortOrder 串接來源若有 item 尚未完成匯入，標記等待或排除
2. 去重與品質過濾移除重複段落、低價值/雜訊內容規則 + LLM 輔助
3. 正規化格式統一、修正明顯轉錄錯字、繁體統一繁體沿用 OpenCC（ChineseConverter）
4. 敏感資訊遮罩PII／機密辨識與遮罩，遮罩後內容才往下走準確率以清洗品質評測集量化（B-5、QA-4）
5. 分類/標籤自動化LLM 建議 Categories/Teams，寫回來源沿用既有標籤體系；人工可調整
6. 摘要與實體擷取產生來源摘要與關鍵實體供下游蒸餾/檢索使用
7. 產出彙整成「清洗後來源 Markdown」寫入 CleanedContentRelativePath，更新狀態/進度/信心分數依 QA 階段決定直接「已清洗」或進「待審核」

供應商抽象：清洗用到的 LLM 以介面抽象、設定驅動切換（雲端/地端），沿用既有 OpenAI 設定注入慣例，避免綁死單一供應商。

B-5. 品質保證（分階段疊加）

對應「如何確認資料品質可用」，分四階段逐步加嚴，先求有再求好：

階段機制行為目的
QA-1（MVP）全自動清洗跑完即標記「已清洗」把管線端到端跑通
QA-2LLM 自評信心分數 + 自動門檻高信心自動「已清洗」；低於門檻轉「待審核」把人力集中在有疑慮的來源
QA-3人工審核關卡「待審核」→ 人工確認/校正 → 才標「已清洗」可供下游品質可控、可追溯（ReviewedBy/ReviewedAt）
QA-4清洗品質評測集人工標註小型樣本，量化遮罩漏判/誤判率、分類準確率、摘要品質回歸測試與 prompt/門檻調校依據

B-6. 可行性與品質驗證（如何確認作法可行）

  1. 小規模 PoC：挑 1–2 個真實來源（如一場含多素材的會議）建立 KnowledgeSource，跑完整清洗管線，人工檢視彙整品質、遮罩正確性、分類合理性。
  2. 清洗品質評測集量化：對抽樣樣本計算遮罩漏判/誤判率、分類準確率，設定可接受門檻（門檻數值於 05-待釐清問題 補登後鎖定）。
  3. 抽樣審核：上線後持續抽樣人工檢視，回饋調整 prompt 與門檻。
  4. 驗收標準：既有匯入產物可被聚合為來源並完成清洗、產出帶分類/標籤/摘要/遮罩的彙整內容、遮罩準確率達門檻、清洗狀態/進度/錯誤可於 UI 追蹤、權控正確（非授權團隊看不到來源）。

B-7. 預期功能架構與新頁面

新頁面「知識來源管理」（Blazor / AntDesign，沿用本專案 UI 慣例）：

  • 來源 CRUD；把既有匯入紀錄「加入/移除」為成員（跨三型別挑選、可排序）。
  • 觸發清洗、即時進度（沿用 5 秒輪詢）、檢視清洗後彙整內容。
  • 待審核佇列與審核動作（QA-3：確認/退回/校正）。
  • UI 不變量：Service/AntDesign 服務用建構式注入、框架類（AuthenticationStateHelper/NavigationManager）用 [Inject]；進頁 OnInitializedAsync → AuthenticationStateHelper.Check → CheckAccessPage；編輯前 Clone()；多選 Select 用 Mode="SelectMode.Multiple" + Values/OnSelectedItemsChanged（不用 @bind-Values:after）。

權限三處同步（新增頁面權限）：MagicObjectHelper、RolePermissionService、Datas/Menu.json（以位置索引對應）。

架構流向：

[匯入紀錄] 逐字稿/Markdown/圖片解讀
      │  （使用者或 LLM 輔助歸群）
      ▼
[KnowledgeSource] ← KnowledgeSourceItem(多型) 聚合多筆素材
      │  觸發清洗 → CleaningQueue → CleaningBackgroundService → CleaningProcessor
      ▼
彙整→去重→正規化→遮罩→分類→摘要  →  CleanedContentRelativePath(.md)
      │  （QA：信心分數/人工審核/黃金評測）
      ▼
[已清洗來源]  →（下一階段）知識蒸餾 → Wiki 實體頁 → 建立知識庫

三、重用既有元件（避免另起爐灶）

既有元件重用方式
佇列＋背景服務（I*Queue/*BackgroundService/*Processor）新增清洗佇列，完全比照
團隊權控（TagStringHelper.BuildTeamAccessPredicate/IsTeamAccessible + IRecordAccessScopeProvider）來源查詢/檢視/清洗一律套用
標籤轉換（TagStringHelper.ToList/ToStored + AutoMapper ForMember）KnowledgeSource 的 Categories/Teams
OpenCC（ChineseConverter）正規化的繁體統一
雙 migration、設定驅動供應商切換、NLog/健康檢查直接沿用
Cascade delete（比照 Project→ProjectFile）KnowledgeSource→KnowledgeSourceItem

四、風險與待釐清

  • KnowledgeSourceItem 多型字串參照 vs 三個可空 FK：本文件採前者（務實、貼合既有風格），實作前可再評估強一致性需求。
  • 遮罩/分類可接受準確率門檻數值 → 於 05 補登。
  • 清洗 LLM 用雲端或地端 → 沿用供應商抽象，先以雲端做 PoC。
  • Project/Meeting/Task 附件是否納入清洗（A8）→ 視需求，可讓附件也能加入知識來源；本期先不納入。
  • 大量素材的清洗成本與延遲 → 以佇列序列化處理控制，必要時分批。
