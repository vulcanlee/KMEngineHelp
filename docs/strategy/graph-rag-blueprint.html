1. 摘要（三句話結論）

  1. 本系統目前「不支援」完整的 Graph RAG，但已具備一半材料：蒸餾階段早已產出「概念節點（WikiPage）＋概念連結（WikiPage.LinkTitles 的 [[標題]]）＋信心＋版本」，這是一張尚未正規化、也還沒有遍歷引擎的「概念圖」。缺的是實體/關係/三元組抽取、正規化邊表與圖檢索。
  2. 它有價值，但不是全面必需，而是「補齊唯一缺口」的工具：本系統已滿足企業對「可溯、權控、保鮮、可審、成本可控」的需求，唯一較弱的是「複雜／多跳／全域性問答」（例如「從所有客訴歸納三個系統性根因」）。Graph RAG 正好切中這一格；對「單點事實查詢／FAQ」則幫助有限。
  3. 可以低破壞、分階段導入：採「新資料表＋旁掛背景管線＋預設關閉＋不動既有檢索預設」的設計，先把既有 LinkTitles 具體化為可遍歷的邊（P1），再視實際問題型態加上 LLM 三元組抽取與社群摘要（P2～P3）。全程維持 leak=0 權控不變量與人在迴路審核。（實際執行至 P6：P4～P6 是實作 P3 後為解除「社群多落在單一來源」限制而衍生的延伸階段，見 §9。）

2. 本系統是否支援 Graph RAG（現況盤點）

能力面向現況佐證（檔案）
知識圖譜（實體節點＋關係邊）❌ 無實體/關係/三元組抽取、無正規化邊表全庫無 GraphNode/GraphEdge/Relation/Triple 類別
概念節點🟡 已有（一頁一概念）Models/WikiPage.cs（Title 為概念鍵）
概念連結（邊的雛形）🟡 已有，但存成分隔字串、無遍歷引擎WikiPage.LinkTitles（[[概念]]）；蒸餾產出 {Title, Content, Links[], Confidence}（Services/Distillations/DistillationEnhancer.cs）
圖遍歷／多跳查詢❌ 無（Cypher/遞迴遍歷皆無）—
社群摘要（global 全域問答）❌ 無—
檢索✅ 向量＋關鍵字混合檢索（非圖）Services/Embeddings/RetrievalService.cs

結論：本系統在 Graph RAG 光譜上處於「🟡 雛形」——概念節點與概念連結已由蒸餾階段自然產出，但缺正規化圖儲存與遍歷檢索。 換言之，Graph RAG 的一半材料本系統早就在產了，這是導入時最大的既有優勢（詳見路線總論 §7.2）。

📌 上表為「導入前」盤點。P1～P8 實作（1.0.83～1.0.90）後：實體節點＋關係邊 ✅（GraphNode/GraphTriple/GraphEdge）、圖遍歷／多跳查詢 ✅（BFS，GraphMaxHops 預設 2、上限 3，見 RetrievalService.SearchGraphAsync）、社群摘要與 global 全域問答 ✅（GraphCommunity＋問答頁「一般／全域」切換）、檢索 ✅（向量＋關鍵字＋圖三路融合）。

3. 價值與適用場域（是否僅適用特定場域）

先用使用者提供的情境切入：「把所有客戶投訴丟進去，問『三個最根本的系統性問題是什麼』」。傳統向量檢索只會抓回「語義最像」的幾段各別投訴逐條羅列，難以跨投訴建立「A 因為 B、B 又牽動 C」的關係鏈，也難以「綜觀全部」歸納。這正是 Graph RAG 的兩個強項：跨文件關聯推理（多跳） 與 全域性歸納（社群摘要）。

3.1 高價值場域

場域為何 Graph RAG 有感
客訴／事故根因歸納需跨多筆記錄找共同因子與因果鏈，非單點檢索可得
跨文件關聯問答（「A 與 B 有什麼關係？」）沿關係邊多跳，向量檢索最弱之處
全域趨勢／整體結論（「綜觀全部…」）社群摘要預先彙整概念群，回答宏觀問題
合規／盡職調查、跨合約/手冊比對需串接分散條款、建立實體間關係
組織/專案的人—事—物網路天生是圖結構

3.2 邊際有限場域

場域為何幫助有限
單點事實查詢（「某人叫什麼名字」）現行混合檢索已足夠
FAQ／單文件問答答案就在單一片段，無需多跳
內容彼此獨立、少關聯的知識庫圖稀疏，建圖投報率低

結論：Graph RAG 對本系統是「補齊企業需求清單上唯一缺口（複雜／多跳／全域問答）」的工具，而非全面必需的銀彈。 是否值得導入應由實際問題型態決定（見 §10 觸發條件），而非為追新而做。

4. 規劃與設計（架構）

設計原則：沿用既有資產、新表不動舊表、旁掛管線、預設關閉、權控不變。

4.1 資料模型（新增，雙庫皆關聯式）

新增兩張表（放 KnowledgeExtraction.AccessDatas/Models/），欄位刻意對齊既有 VectorEmbedding/WikiPage 的權控與版本慣例：

  • GraphNode（實體/概念節點）：Id、Name（實體名，比對鍵）、Type（人/組織/產品/概念…）、KnowledgeSourceId、WikiPageId?（錨回蒸餾頁）、Categories、Teams（權控欄位，必要）、Confidence、SourceLayer、版本 IsCurrent/EffectiveDate/ExpiryDate（對齊 VER-2）、ContentHash、時間戳。
  • GraphEdge（關係邊，三元組的關係）：Id、SourceNodeId、TargetNodeId、Relation（關係型別）、KnowledgeSourceId、WikiPageId?、Categories、Teams（權控欄位）、Confidence、IsCurrent/EffectiveDate/ExpiryDate、ContentHash。
  • 第一步可先極簡：把既有 WikiPage.LinkTitles（[[標題]]）具體化成 GraphEdge（來源頁→目標頁、Relation="wiki-link"），不必先做實體抽取即可得到可遍歷的概念圖。

索引：(Teams)、(KnowledgeSourceId)、SourceNodeId、TargetNodeId，供權控過濾與遍歷。

4.2 抽取管線（新增「圖抽取」階段，仿既有三件套）

沿用專案既有的背景管線模式（I*Queue Singleton Channel + *Processor Scoped + *BackgroundService，見 Web/Extensions/ServiceCollectionExtensions.cs、Web/Program.cs）：

  • 新增 GraphExtractionQueue / GraphExtractionProcessor / GraphExtractionBackgroundService。
  • 接入點：蒸餾完成後（目前 DistillationProcessor 完成即自動入列嵌入索引），旁掛入列「圖抽取」；KnowledgeSource 新增 GraphStatus（＋百分比/錯誤/時間戳），與既有 Status/DistillationStatus/EmbeddingIndexStatus 並列。
  • 抽取方式：以蒸餾產物（Wiki 頁＋Links）為輸入，LLM 抽「實體—關係—實體」三元組，沿用既有四層提示詞解析＋信心自評＋人工審核＋增量重建（ContentHash） 慣例（比照 CleaningEnhancer/DistillationEnhancer）。P1 階段可跳過 LLM，直接由 LinkTitles 建邊。

4.3 檢索整合（併入現有混合檢索）

  • 新增 GraphRetrieval：local（由問句命中的節點沿邊 1～2 跳取鄰域）＋ global（用社群摘要回答全域問題）。
  • 把圖檢索結果併入 RetrievalService 的融合分數（現為 VectorWeight×向量 + KeywordWeight×關鍵字，可再加 GraphWeight×圖），沿用 top-k 與兩段式信心門檻（KnowledgeBaseChatService）。
  • ACL 紅線：圖節點/邊帶 Teams，遍歷前先過濾（比照 TagStringHelper.BuildTeamAccessPredicate），確保多跳不會繞過權控、維持 leak=0。

4.4 雙庫與圖查詢（不強上圖庫）

  • 現況雙庫（Sqlite／SqlServer）皆無圖原生能力；向量已是純 BLOB＋應用層 cosine（DualDbVectorStore）。
  • 1～2 跳遍歷用關聯式邊表即可：SQLite/SQL Server 皆支援遞迴 CTE，或在應用層做有限跳數 BFS（規模小、可控）。多數企業問題 2 跳內即足夠。
  • 何時才需專用圖庫（Neo4j／PostgreSQL AGE）：當(a) 需要 3 跳以上深度遍歷、(b) 邊數達百萬級、(c) 需要複雜圖演算法（PageRank、社群偵測）且關聯式方案效能不足時，才評估導入——屆時可經一層 IGraphStore 抽象替換（比照現有 IVectorStore）。P1～P2 不需要。（實作現況：P1～P6 全部以關聯式邊表落地，未導入專用圖庫；三項觸發條件皆未達成。）

5. 導入 Graph RAG 的優點與缺點

5.1 優點

優點說明
多跳／跨文件關聯推理沿關係邊回答「A 與 C 透過 B 相連」這類問題，補齊向量檢索最弱項
全域趨勢與根因歸納社群摘要支援「綜觀全部…」「三個系統性根因」等宏觀提問
答案更可解釋出處可附「關係路徑」，比單純片段更能說明推理依據
起步成本低LinkTitles 已是邊的雛形，P1 可不呼叫 LLM 就先建圖
知識資產再利用蒸餾成果（概念頁）直接升級為可推理的知識圖，複利累積

5.2 缺點

缺點說明／緩解
建圖需額外 LLM 抽取成本與處理時間上升；緩解：P1 先用 LinkTitles、增量重建（ContentHash）只重跑異動
圖品質依賴抽取準確度錯誤關係可能誤導答案；緩解：信心自評＋人工審核（比照 WikiPage 審核）＋兩段式門檻
關聯式遍歷有規模上限深跳/大圖效能受限；緩解：限制跳數、先過濾 ACL 縮小候選、必要時才上圖庫
維運與審核負擔上升多一條管線與一種審核對象（見 §7）
ACL 必須延伸到節點/邊做不好即安全風險（多跳繞過權控）；列為導入的硬性驗收條件

6. 與現有功能的衝突評估（是否會衝突）

逐項檢視，結論皆為「可並存、不衝突」，前提是遵守下列不變量：

面向是否衝突說明
團隊權控 leak=0否（但為最高紅線）節點/邊帶 Teams、遍歷前過濾；沿用 TagStringHelper.BuildTeamAccessPredicate、以檢索品質評測 leak 指標把關
既有混合檢索/問答否圖檢索為可加開的第三路，GraphWeight 預設 0＝行為完全不變
清洗／蒸餾管線否圖抽取旁掛在蒸餾之後，不改既有階段輸入輸出
雙庫 migration需配合新表要產兩份 migration（AccessDatas 的 Sqlite 與 AccessDatas.SqlServerMigrations 各一）
版本時效（VER-2）否節點/邊沿用 IsCurrent/EffectiveDate/ExpiryDate，與既有 as-of 一致
選單/權限需配合新審核頁若為 adminOnly，只改 Menu.json＋圖示白名單；若開放角色則需三處同步（MagicObjectHelper/RolePermissionService/Menu.json）
既有 Blazor/EF 慣例否沿用建構式注入、Clone()、CleanTrackingHelper、三件套佇列
成本／效能需控管建圖 LLM 成本、遍歷延遲；以預設關閉、增量重建、跳數上限控管

刻意不衝突的設計選擇：新表（不動 VectorEmbedding/WikiPage 結構）、旁掛管線（不動既有階段）、GraphWeight 預設 0（不動既有檢索預設）、預設關閉（不影響現有使用者）。因此既有 RAG 問答、清洗、蒸餾、評測、權控全部不受影響。

7. 對使用者操作的改變與使用複雜度（會不會變複雜）

分族群評估——對絕大多數使用者，複雜度幾乎不增：

使用族群改變複雜度
一般問答使用者仍是同一個輸入框、預設行為不變；多跳/全域問題「答得更好」，出處可能多出關係路徑幾乎不增（不需學新操作）
管理員／審核者新增「知識圖譜瀏覽/審核」選單、三元組審核（類比既有 WikiPage 審核）、圖品質診斷指標主要增加處（多一種審核對象）
系統維運多一條背景管線與 GraphStatus 狀態要看略增（沿用既有管線監控頁模式）

緩解：功能預設關閉、漸進開啟；不強迫既有使用者改變工作流；審核可比照 WikiPage 的既有 UX，降低學習成本。

8. 從輸入到蒸餾階段的變化

現況管線與導入後對照（新增只在蒸餾之後旁掛，前段不變）：

現況：  輸入(轉錄/文件/圖片) → 知識來源加工 → 清洗 → 蒸餾(WikiPage + [[LinkTitles]]) → 建索引(向量) → 混合檢索問答
導入後：輸入(不變) ─────────→ 加工(不變) → 清洗(不變) → 蒸餾(不變，產出即圖的節點+邊雛形)
                                                              │
                                                              ├─【新增】圖抽取：由蒸餾產物建 GraphNode/GraphEdge
                                                              │          （P1 用 LinkTitles；P2 用 LLM 抽三元組 + 人工審核）
                                                              ├─【新增】社群分群 + 群摘要（P3，供 global 問答）
                                                              └→ 建索引(節點可選嵌入) → 混合檢索(+ 圖檢索融合) 問答
階段現況導入後
輸入（三管線匯入）產出逐字稿/Markdown/解讀文字不變
知識來源加工彙整成員不變
清洗 Cleaning去重/遮罩/分類/摘要/信心不變
蒸餾 Distillation產 WikiPage＋LinkTitles＋信心＋版本不變（其產物同時成為圖的節點與邊雛形）
圖抽取（新增）—建 GraphNode/GraphEdge；P1 由 LinkTitles、P2 由 LLM 三元組＋人工審核
建索引 EmbeddingCleaned/Wiki 兩層切塊嵌入節點/群摘要可選嵌入
狀態機Status/DistillationStatus/EmbeddingIndexStatus＋ContentStale新增 GraphStatus；ContentStale 觸發連動重抽（沿用增量 ContentHash）

📌 與實作的差異：上圖「圖抽取」與「社群分群＋群摘要」皆已落地（P1～P3），並額外做了跨來源實體合併與別名治理（P4～P6）。圖檢索已於 P8（1.0.90）由 1 跳擴展為 BFS N 跳（預設 2、上限 3），達成本節設計提到的 1～2 跳。惟「節點/群摘要可選嵌入」標為選配、至今未實作。

9. 可執行實作藍圖（分階段 PoC）

10. 導入觸發條件（何時該做／不該做）

  • 該做的訊號：使用者開始頻繁問「X 和 Y 有什麼關聯？」「綜觀全部…」「根本原因是什麼？」，且檢索品質評測顯示這類跨文件/全域問題召回不足。
  • 先不做的訊號：問題多為單點事實/FAQ、知識彼此獨立關聯稀疏、或既有混合檢索已能滿足。
  • 建議優先序：對齊路線總論——先補 rerank/ANN（依評測數據），Graph RAG 列 P1～P2，晚於 rerank、早於 Agentic RAG（詳見 路線總論 §7.4、§9）。（實際執行順序與此不同：Graph RAG 先行至 P6，rerank 至今仍只有 分析文件、Agentic RAG 未實作。）

11. 結論與建議

  1. 是否支援：目前為「🟡 雛形」——蒸餾已產概念節點＋概念連結，缺正規化圖與遍歷；Graph RAG 的一半材料早就在產。
  2. 是否有價值／是否僅特定場域：對「複雜／多跳／全域問答」高價值（客訴根因、跨文件關聯、全域趨勢、合規比對），對單點事實/FAQ 邊際有限——是補齊唯一缺口的工具，不是銀彈。
  3. 如何做：新表＋旁掛「圖抽取」管線＋圖檢索融合，先由 LinkTitles 起步（P1），再上 LLM 三元組與社群摘要（P2～P3）；不強上專用圖庫。（已如此執行並延伸至 P6，全程未導入專用圖庫。）
  4. 衝突與影響：採「新表＋旁掛＋預設關閉＋不動既有檢索預設」設計，與現有功能可並存不衝突；唯一硬性紅線是 ACL 必須延伸到節點/邊、維持 leak=0，並記得雙庫各一 migration、選單/權限同步。
  5. 使用複雜度：一般使用者幾乎無感（答得更好，不需學新操作）；複雜度主要落在管理員/審核者（多一種審核對象），以預設關閉、漸進開啟、沿用既有審核 UX 緩解。
  6. 一句話：基礎已很強，不必為追新而重寫；把 Graph RAG 當作「按需補齊多跳/全域問答」，在既有治理框架（ACL／引用／審核／評測）內、以既有 LinkTitles 低風險起步，才是對本系統與客戶最務實的做法。
