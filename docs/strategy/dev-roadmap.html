開發建議與路線圖

初步技術驗證（現有可重用點）與 3–6 個月分階段開發路線圖

  • 主要讀者：開發團隊、技術負責人、決策層
  • 文件版本：1.0
  • 建立日期：2026/06/08
  • 編碼：UTF-8（繁體中文，含 BOM）

架構選型見 03-知識庫架構研究與建議；待釐清問題見 05；應產出成果物見 06。

一、初步技術驗證：現有可重用點與改造切入點

本節只盤點、不寫程式。目的是讓後續開發立基於既有慣例，降低風險與工時。

1. 非同步佇列 ＋ 背景服務（可重用為清洗/索引管線）

  • 既有：TranscriptionBackgroundService、DocumentExtractionBackgroundService（位於 KnowledgeExtraction.Web/BackgroundServices/）搭配 ITranscriptionQueue / IDocumentExtractionQueue。
  • 模式：入列 → 背景服務取出 → Processor 處理 → 更新狀態/進度(0–100%)/錯誤訊息。
  • 改造切入：新增「清洗佇列」與「索引佇列」沿用同一模式，加入清洗階段（去重/遮罩/分類標籤/摘要）與向量索引階段。

2. 文件轉文字處理器（清洗階段的輸入來源）

  • 既有：DocumentExtractionProcessor（MarkItDown 產出 .md）與轉錄逐字稿（OpenAI＋OpenCC 繁體化）。
  • 改造切入：把這些 Markdown／逐字稿作為清洗管線輸入，串接「蒸餾為 Wiki 實體頁 → 切塊 → Embedding → 索引」。既有產物本就是 Markdown，與 LLM 知識 Wiki（同為 Markdown）天然契合。

3. 團隊權控（延伸至知識單元檢索）

  • 既有：TagStringHelper（BuildTeamAccessPredicate / IsTeamAccessible）＋ IRecordAccessScopeProvider，標籤以分隔字串精確比對。
  • 改造切入：chunk 繼承來源文件 Teams 標籤；檢索查詢時即帶入團隊範圍過濾（檢索層過濾，非取回後再濾）。

4. 既有工程慣例（直接沿用）

  • 雙資料庫 migration（SQLite AccessDatas 與 SQL Server AccessDatas.SqlServerMigrations 各一）。
  • AutoMapper（List⇄分隔字串以 ForMember 處理）、編輯前 Clone()、Update/Delete 前 CleanTrackingHelper.Clean<T>()。
  • 設定驅動切換（OpenAI 金鑰由環境變數注入、快取 Memory↔Redis 可切換）——延用於 Embedding/LLM 供應商與地端/雲端切換。
  • CRUD 腳手架與既有 Category/Team 標籤體系——清洗的「分類標籤自動化」可直接套用既有標籤模型。
  • 健康檢查/系統健康頁、NLog——擴充為清洗/索引/問答的監控與稽核。

注意既有命名陷阱：DbSet 名稱 MyTas ≠ Entity MyTask；新增頁面權限三處同步（MagicObjectHelper、RolePermissionService、Menu.json）；模型變更要產雙 migration。

二、3–6 個月分階段路線圖

每階段格式：目標 → 主要工作項 → 驗收標準。版本號於每次可建置產出時 +1（依專案慣例）。

註：原「階段一：清洗強化」已依五階段流程（資料匯入 → 資料清洗 → 知識頁審核 → 建立知識庫 → 智慧應用）拆為兩個獨立階段。資料清洗的完整設計見 08-資料清洗階段設計與分析。

階段一（約 1 個月）：資料清洗

  • 目標：把匯入後零散、破碎的原始內容，整理成乾淨、彙整、具主題、可權控的「來源級資料」。
  • 工作項：
  • 知識來源（KnowledgeSource）：新增來源實體 + 跨型別成員關聯，把多筆零散素材（逐字稿/萃取/圖片解讀）聚合成一個完整來源；清洗以「來源」為單位。
  • 去重與品質過濾（移除重複/低價值內容）。
  • 正規化（格式統一、修正轉錄錯字、OpenCC 繁體統一）。
  • 敏感資訊遮罩（PII/機密辨識與遮罩，遮罩後內容才往下走）。
  • 分類與標籤自動化（套用既有 Category/Team 標籤）。
  • 摘要與關鍵資訊/實體擷取。
  • 沿用背景佇列模式新增「清洗佇列」。
  • 品質保證分階段疊加：全自動 → 信心分數門檻 → 人工審核關卡 → 清洗品質評測集。
  • 驗收：
  • 既有轉錄/萃取產物可聚合為來源並進入清洗管線，產出帶分類/標籤/摘要/遮罩的彙整內容。
  • 遮罩對抽樣樣本達可接受準確率（門檻於 [05] 確認）。
  • 清洗狀態/進度/錯誤可於 UI 追蹤；權控正確（非授權團隊看不到來源）。

階段二（約 0.5–1 個月）：知識頁審核　✅ 已實作（0.2.117）

落地說明見 知識頁審核 PRD 與 changelog 2026-06-24。一來源蒸餾為多個互連 Wiki 實體頁、繼承 Teams 標籤、完整信心門檻與人工核准/退回關卡。

  • 目標：把清洗後的來源蒸餾為精煉、可推理的知識。
  • 工作項：
  • 知識頁審核：LLM 將清洗後內容蒸餾為精煉的 Wiki 實體頁（Markdown，一概念一頁、以 [[wiki-links]] 互連），萃取真實可用知識而非原文搬運。
  • Wiki 實體頁繼承來源 Teams 標籤。
  • 驗收：
  • 能由已清洗來源蒸餾出 Wiki 實體頁並正確互連、繼承 Teams 標籤。
  • 蒸餾產物品質可由抽樣人工檢視確認。

階段三（約 1.5–2 個月）：建立知識庫

  • 目標：知識可被快速、權控地搜尋。
  • 工作項：
  • 切塊（chunk，繼承來源 Teams 標籤）。
  • Embedding 供應商抽象（雲端/地端可切換）。
  • PostgreSQL ＋ pgvector 向量索引 ＋ 關鍵字索引（Wiki 實體頁與 chunk 皆索引）。
  • 混合檢索 ＋ rerank；查詢先讀 Wiki 精煉條目、必要時回退 chunk 檢索取證據。
  • Wiki 維護（lint/maintain）流程：一致性健檢、補缺、發掘連結。
  • 權控檢索 API（檢索層即套團隊過濾）＋ 存取稽核。
  • 驗收：
  • 給定查詢可回傳帶出處、且符合提問者團隊權限的結果。
  • 非授權團隊內容不會出現在檢索結果或 LLM 上下文（以測試驗證）。
  • 數萬文件規模下檢索延遲在可接受範圍。
  • 每次查詢留有稽核軌跡。

階段四（約 1.5–2 個月）：旗艦應用 MVP

  • 目標：旗艦一（KB 問答助理）可用；旗艦二（Agent 工作流）出雛形。
  • 工作項：
  • KB 問答助理：自然語言提問 → 權控檢索 → 帶出處答案 → 答案遮罩。
  • 問答 UI（沿用 Blazor／AntDesign 慣例與建構式注入）。
  • AI Agent 自動化工作流：先做單一情境可行性雛形（PoC）。
  • 驗收：
  • 問答助理能對知識庫內容回答並標示出處，越權內容不外洩。
  • 內部選定情境（如會議知識留存或 SOP 查詢）可實測 ROI 指標。
  • Agent 雛形能完成一個多步驟任務的端到端示範。

三、開發原則

  • 立基既有慣例：沿用佇列/背景服務、團隊權控、雙 migration、設定驅動切換，不另起爐灶。
  • 權控不可後補：檢索層即過濾，從第一版就驗證越權不外洩。
  • 供應商抽象：Embedding/LLM 以介面切換雲端/地端，避免綁死單一供應商。
  • 小步驗收：每階段有明確、可測的驗收標準，能獨立驗證再進下一階段。
  • 文件同步：每次異動同步更新相關文件（專案慣例）。

四、風險與相依

  • 地端 LLM/Embedding 的品質與算力是最大不確定性（見 05）。
  • 向量庫拓樸（與現有 SQLite/SQL Server 的關係）需先定案。
  • 遮罩準確率、混合檢索調校、成本控管為持續調優項。
