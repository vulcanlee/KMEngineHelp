策略與規劃

多客戶、多客製、多型號的知識庫規劃分析

撰寫日期：2026-07-29　｜　定位：導入規劃分析報告（可自用、亦可對客戶／實施顧問呈報） 範圍：同一套系統賣給不同客戶、各有客製與不同資料庫／作業系統時，知識該怎麼切；同類商品不同型號時，問答能不能靠型號代碼找對來源；以及真實情境的操作建議與誠實的準確率預估。 說明：本報告所有「本系統現況」主張皆對回程式碼檔案與行號（見 §2 的 F1～F13）。凡屬推論而非查證者，一律明寫「推論」；準確率一節不給單一總體數字，改為分情境給區間並附推理依據，另附「怎麼量出你自己的真實數字」。 前置閱讀：本文是 14-企業知識庫技術路線分析 的續篇。那一篇已完整處理「本系統的 RAG 技術定位」與「Karpathy LLM Wiki 模式對照」，本文不重複，只補它沒談的一層：當同一套系統賣給 N 個客戶、同一產品有 N 個型號時，知識該怎麼切。

一、先講企業真實需要

技術討論很容易一開始就跳到「要不要用分類」。但分類只是手段，先確認要解決的到底是什麼。

1.1 三個真實痛點

一家做專案的軟體公司，賣同一套系統給十家客戶之後，通常會同時出現這三件事：

痛點具體長什麼樣現在怎麼解
沒人講得清「這家到底改了什麼」客戶 A 的簽核流程多兩關、客戶 B 的報表欄位不一樣、客戶 C 用 SQL Server 而其他家用 SQLite問當初做的人。他休假就卡住
客製細節只活在某個人腦裡「那個排程要先關掉再升版」這種事，從來沒有寫下來過老手離職就永久遺失
新人接手要翻三個月文件散在共用磁碟、Teams、Email、某人的筆電靠帶人，成本極高

這三件事的共同結構是：知識存在，但取用成本高到等於不存在。知識庫要解的是取用成本，不是儲存問題——儲存從來不是瓶頸。

1.2 企業真正要的不是「AI 很聰明」

導入知識庫最常見的失敗，不是「AI 答不出來」，而是「AI 很有自信地答錯」。

對做專案的公司來說，這件事的代價很具體：工程師照著 AI 給的步驟去客戶 A 的機器上操作，結果那是客戶 B 的流程。這種錯誤比「查無資料」嚴重得多——查無資料會讓人去問人，答錯會讓人直接動手。

所以企業真正需要的三件事，依序是：

  1. 答錯要能追出處——每個答案都要能點回原始文件核對。本系統的出處鑽取與原始檔下載就是為此。
  2. 答不出來要老實說——寧可回「查無相關依據」，也不要硬掰。本系統的兩段式信心門檻（F8）在程式層直接攔截，不呼叫 LLM，不依賴 LLM 自律。
  3. 看不到的東西就是看不到——客戶 A 的人不該看到客戶 B 的任何內容，而且過濾要發生在「找資料」那一步，不是事後遮起來。本系統的團隊權控（F9）在候選階段就過濾。

這三件事本系統都已內建。本文接下來要處理的，是第四件事——怎麼讓它找對「哪一家客戶、哪一個型號」。這件事系統提供了工具，但規劃做不對就不會生效。

二、這套系統實際上怎麼找資料

後面所有建議都建立在這一節。先把機制講清楚，才知道哪些做法有效、哪些是白費力氣。

2.1 一次問答的完整路徑

你打一個問題
   ↓
（視需要）查詢改寫：補全代詞與過短問句
   ↓
三路並行找資料：向量 ＋ 關鍵字 ＋ 圖鄰域
   ↓
套團隊權控（沒權限的根本不進候選）
   ↓
套查詢期篩選（限定知識來源／分類／團隊）
   ↓
融合分數排序，取前 TopK 段（預設 10）
   ↓
兩段式門檻：最高分太低就直接回「查無依據」，不呼叫 LLM
   ↓
組成附出處的參考資料交給 LLM 寫答案

2.3 由這些事實直接推出的三個結論

這三個結論決定了本文後面所有建議：

結論一（來自 F3）：想用分類做「客戶 × 文件類型」的二維切分，做不到。 同時選「客戶-台積電」與「文件-佈署」，得到的是聯集（台積電的所有文件，加上所有客戶的佈署文件），不是交集。這是本文最重要的一個發現，它直接決定了命名規則該怎麼訂。

結論二（來自 F4＋F5＋F1）：光是在問句裡加型號代碼，不可靠。 關鍵字路的權重上限只有 0.3，而且同一節第二塊之後的 chunk 根本不含型號字樣。要可靠地鎖定型號，只能靠 F2 的硬篩選。

結論三（來自 F7）：命名本身就是給 LLM 的辨識訊號。 知識來源標題與章節標題都會進入 LLM 看到的參考資料。所以即使檢索撈混了幾個型號，命名良好時 LLM 仍有機會自己區辨——但這靠 LLM 自律，是保險不是保證。

三、問題一：多客戶、多客製、多資料庫、多作業系統

3.1 先說為什麼「用分類做多維切分」一定會失敗

直覺的做法是把每個維度都做成分類標籤：

客戶-客戶A、客戶-客戶B、客戶-客戶C
文件-使用手冊、文件-工程維運、文件-系統設定、文件-佈署
環境-SQLServer、環境-SQLite、環境-Windows2025、環境-Ubuntu

然後問答時同時選「客戶-客戶A」＋「文件-佈署」，期待得到「客戶A 的佈署文件」。

這行不通。 因為分類篩選是「或」（F3）。你實際得到的是：

客戶A 的所有文件（使用手冊、維運、設定、佈署…）
      ∪
所有客戶的佈署文件（客戶A、客戶B、客戶C…）

範圍不但沒縮小，反而比只選一個還大。而且畫面上不會有任何提示告訴你這件事——你會以為篩選生效了。

這是一個很容易踩、而且踩了不會自己發現的坑。所以：

分類只能用來表達「一個維度」。想表達多維度的交集，必須換工具。

3.2 建議的三層切分模型

正確的做法是讓三種工具各司其職，各自負責一個維度：

層工具負責的維度為什麼是它
第一層：誰能看團隊客戶／租戶邊界這是系統唯一的硬權限（F9）。客戶的人會登入時，這一層是資安紅線
第二層：問答時鎖定範圍知識來源（盒子）客戶 × 系統 × 大版本 × 文件族這是「限定知識來源」的抓手（F2），也是清洗、蒸餾、索引的處理單位
第三層：主題篩選分類只放文件用途（單一扁平維度）受限於 F3 的「或」語意，只能承擔一個維度

核心主張：把「客戶」這個維度放進「知識來源盒子」，不要放進分類。

理由有三：

  1. 盒子的篩選是硬過濾（F2），選了就只在那個範圍內找，可靠度 100%。
  2. 盒子的標題會進 LLM 的參考資料（F7），等於免費多一層辨識訊號。
  3. 盒子本來就是加工單位——同一個客戶的內容一起清洗、一起蒸餾、一起失效重跑，本來就該裝在一起。

3.3 命名規則

因為來源標題會進 LLM 的參考資料（F7），標題必須單獨看得懂。「佈署手冊」這種名字對 LLM 毫無幫助——它看到十段前綴都是「佈署手冊」，無從分辨。

建議格式（由粗到細，用全形分隔符隔開，讓人與 LLM 都好讀）：

{客戶}｜{系統或產品線}｜{大版本}｜{文件族}

範例（以下皆為泛例，請自行代換成你們的實際名稱）：

來源標題說明
客戶A｜MES｜v3｜佈署與環境建置客戶 A 的 MES 系統 v3 版佈署文件
客戶A｜MES｜v3｜工程維運與故障排除同上，但維運面
客戶A｜MES｜v3｜客製差異說明最有價值的一盒：這家跟標準版差在哪
客戶B｜MES｜v2｜佈署與環境建置另一家、另一版
標準版｜MES｜v3｜使用手冊不綁客戶的共通內容

搭配的分類詞庫（只有一個維度：文件用途，控制在 10 個以內）：

使用手冊、工程維運、系統設定、佈署安裝、客製差異、
規劃會議、專案管理、教育訓練

為什麼分類不放客戶、不放型號、不放環境：那些維度已經由盒子承擔了。分類重複表達同一件事只會讓下拉變長，而且因為「或」語意（F3），多選時反而會擴大範圍。

⚠️ 分類詞庫要刻意維持很小。 超過 20 個之後，貼標籤的人就開始猜、開始不一致，篩選也就不再可靠。詞庫小、每個詞邊界清楚，比詞庫完整重要得多。

3.4 環境維度（資料庫、作業系統）怎麼放

這一維最麻煩，因為它跟文件用途正交——「佈署文件」與「SQL Server」是兩個獨立維度，而 F3 的「或」語意讓你無法取交集。

判準不是「重不重要」，而是「差異佔全文的比例」：

情況建議做法理由
環境差異只佔全文一小部分（例如只有連線字串與備份指令不同）同一份文件，用章節分：## SQL Server 設定、## SQLite 設定章節標題會進 AnchorRef 與出處（F4），使用者看得到答案來自哪一節
環境差異很大（整套安裝流程、目錄結構、服務註冊方式都不同）拆成不同的盒子：客戶A｜MES｜v3｜佈署-WindowsServer2025差異大到混在一起時，檢索會兩邊都撈到，LLM 容易混答
環境是客戶固定屬性（客戶 A 永遠是 SQL Server）不需要獨立維度，寫在該客戶的盒子裡即可這是最常見的情況。不要為了「架構完整」去建一個實際上不會單獨查詢的維度

最後一列最常被忽略。 多數專案公司的實際情況是「客戶 A 就是那套環境」——環境根本不是獨立維度，而是客戶的屬性。硬把它拆成獨立標籤只會增加維護成本，卻沒有任何查詢會用到它。

3.5 一份大文件，還是拆多份？

判準不是長度，而是這兩個問題：

  1. 它們會不會一起改？ 一起改的放一起，分開改的拆開。
  2. 它們會不會一起失效？ 客戶 A 升到 v4 時，哪些文件同時作廢？那些就是同一盒。

長度不是判準的原因：切塊器會自動處理長文件（預設每塊約 800 字、重疊 120 字），一份三百頁的手冊不會因為長而檢索不到。真正會出問題的是該分開的沒分開——客戶 A 與客戶 B 的內容在同一盒裡，就永遠無法用「限定知識來源」把它們分開。

維護性的實際考量：一份文件維護不易是真的，但拆太細也有代價——盒子數量爆炸後，「限定知識來源」的下拉會長到沒人願意用。實務上的平衡點是：

每個客戶 3～6 個盒子（佈署／維運／客製差異／使用手冊／會議與 PM），而不是每份文件一個盒子。

3.6 問答時怎麼「自動」找到指定客戶的文件

先說結論，避免期待落空：

系統不會自己猜你問的是哪一家客戶。 「自動」是有條件的，而且有三層，可靠度差很多。

層機制可靠度需要做什麼
第一層：硬篩選問答頁的「限定知識來源」多選100%（這是資料庫層的過濾條件）使用者要自己選。可教育成「問客戶 A 的事之前先選客戶 A」
第二層：命名進參考資料來源標題與章節標題會進 LLM 的參考資料（F7）中～高（靠 LLM 判讀）標題要含客戶名（§3.3）
第三層：內容自帶客戶名關鍵字路命中（F1，權重 0.3）低～中文件內容每節都要提到客戶名

建議的實務做法：

  • 一般使用者：養成「先選限定知識來源，再問」的習慣。這是唯一 100% 可靠的做法，而且只多兩秒。
  • 問題本身就帶客戶名時（例如「客戶A 的排程服務怎麼重啟」）：第二、三層會發揮作用，但不要依賴它——特別是當多家客戶的文件內容高度相似時。
  • 如果客戶的人會登入自己的系統：用團隊把客戶隔開（F9）。這種情況下他根本看不到別家的內容，「自動」就是天然成立的，因為候選集裡只有他家的資料。

💡 最乾淨的架構：如果每個客戶都是獨立部署（各自一套系統、各自一個資料庫），那這整個問題就消失了——一套系統裡只有一家客戶的資料。多客戶共用一套系統時，才需要本文的所有規劃。 先確認你是哪一種。

3.7 會議紀錄與 PM 文件，要不要跟手冊放同一盒？

不要。 這是實務上代價很高、但很少人事先想到的一個決定。

原因是權威性與時效性不同：

文件類型它說的是什麼三個月後還算數嗎
使用手冊、佈署文件現在的事實算數（除非改版）
規劃會議紀錄當時的討論，可能後來被推翻常常不算數
PM 的專案文件（時程、風險、決議）當時的計畫部分算數，部分過期

混在同一盒的後果很具體：使用者問「這個功能的規格是什麼」，AI 撈到三個月前那場「初步討論先這樣做」的會議紀錄，於是回答了一個後來已經被推翻的設計。而且答案有出處、看起來很可信。

建議做法：

  • 分盒：客戶A｜MES｜v3｜規劃會議與決議、客戶A｜MES｜專案管理文件，與手冊類的盒子分開。
  • 分類也分開（規劃會議、專案管理），這樣要排除它們時可以用分類篩掉。
  • 會議紀錄的標題一定要帶日期，讓它進 LLM 參考資料時（F7）自帶時間資訊，AI 才有機會說「依 2026-05 的會議紀錄…」。
  • 善用版本與時效欄位（F11）：規劃文件定案後，把被推翻的舊版標記失效，避免它繼續被檢索到。

📌 一個好用的紀律：會議紀錄與 PM 文件只進知識庫，不進「標準答案」。也就是說，允許它們被查到（有價值），但在問答時養成「問現行規格請限定手冊類的盒子」的習慣。

3.8 匯入路徑：這些文件怎麼進系統

順帶說明各類文件對應的匯入管線：

文件類型匯入方式

四、問題二：同類商品、不同型號

4.1 直接回答

能做到，但不是靠「在問句裡加型號代碼」。

問句加型號會有一些幫助，但不足以依賴。下面用實際的機制算給你看，然後給可靠的做法。

4.2 為什麼「問句加型號」不可靠：三個證據

證據一：連字號會被切開（F5）。

系統的切詞分隔符包含 -。所以查 EPS-3000 時，實際產生的比對詞是：

["EPS", "3000", "EPS-3000"(完整問句)]

證據二：同一節第二塊之後的 chunk 不含型號（F4）。

切塊器把章節標題存進中繼欄位 AnchorRef，不併進 chunk 本文。所以一份「EPS-3000 規格說明」文件切出來的塊是：

第 1 塊：包含「## EPS-3000 規格」這一行 → 關鍵字找得到
第 2 塊：只有規格內文 ＋ 前一塊的 120 字尾巴 → 可能已經不含型號
第 3 塊起：幾乎確定不含型號 → 關鍵字完全找不到

規格表、參數表這類內容通常很長，也就是說最關鍵的那幾塊，往往正是不含型號的那幾塊。

證據三：關鍵字權重上限只有 0.3（F1）。

算一個具體的例子。問「EPS-3000 的保固期是多久」，比對詞是 ["EPS", "3000", "的保固期是多久", 完整問句] 共 4 個：

chunk命中的詞關鍵字分數對融合分數的貢獻
EPS-3000 的保固章節EPS、30002 ÷ 4 = 0.500.3 × 0.50 = 0.15
EPS-5000 的保固章節EPS1 ÷ 4 = 0.250.3 × 0.25 = 0.075

差距只有 0.075。 而兩份文件講的都是「保固期」，向量分數幾乎一樣（推論：內容結構相似時差距通常在 0.05 以內）。

結果是：正確型號的內容會排前面一點點，但錯誤型號的內容照樣進入前 10 名、照樣被送進 LLM。LLM 看到兩個型號的保固條款，可能答對、可能答錯、也可能把兩者混在一起。

4.3 四種做法，由強到弱

#做法可靠度代價
①每個型號一個知識來源盒子 ＋ 問答時「限定知識來源」100%（資料庫層過濾，F2）使用者要多選一次；型號多時下拉會長
②型號當分類 ＋ 問答時「限定分類」高（同樣是硬過濾）⚠️ 只有在「分類這個維度只拿來放型號」時才可靠。一旦分類同時放文件用途，多選就會變成「或」（F3）而失效
③文件每一節都重複帶出型號中～高要改文件寫法；改完要重建索引
④只在問句加型號低，不可依賴零成本，但如 §4.2 所示效果有限

建議：①為主，③為輔。 ① 保證找對型號，③ 讓萬一沒選篩選時也有機會答對，而且能提升 ① 的盒內排序品質。

② 要特別小心：如果你已經照 §3.3 把分類拿來放文件用途，就不要再把型號塞進去。兩個維度擠在一個「或」語意的欄位裡，兩邊都會失準。

4.4 型號別名

知識圖譜有別名合併能力（F10）：把 EPS-3000、EPS3000、eps 3000、EPS 3000 系列 登記成同一個實體的別名之後，查任何一個寫法都等同查全部。

但要知道它的界線：

  • 別名必須經過人工核可才生效。
  • 它作用在圖檢索路徑，權重只有 0.2（F1），而且要先有 Wiki 層命中當種子才會啟動。
  • 所以它是輔助，不能取代 §4.3 的 ① 或 ③。

適合用它的情境：同一個型號在不同文件裡寫法不一致（業務寫 EPS3000、工程寫 EPS-3000、客戶叫它「三千型」）。這種情況下別名很有價值。

4.5 型號的書寫規約（建議寫進你們的文件撰寫規範）

  1. 型號代碼避免連字號——寫 EPS3000 而不是 EPS-3000（F5：連字號會被切開）。若既有文件已大量使用連字號，改用 §4.3 ① 的硬篩選，不要指望關鍵字。
  2. 每一個章節標題都帶完整型號——## EPS3000 保固條款，而不是 ## 保固條款。
  3. 長表格的每一列都帶型號——規格表第一欄放型號，這樣不論切在哪裡，每一塊都含型號。
  4. 文件開頭放一段「適用型號」宣告，並在每個大段落開頭重述一次。
  5. 不同型號的差異，優先寫成「差異表」而不是分散在各章——差異集中在一處，檢索與人工查閱都更準。

5.3 會出錯的反例（最值得先看的一節）

六、預估準確率

⚠️ 以下全部是推論值，不是你的實測數字。 推論依據寫在每一項底下。真實數字請照 §7 用系統內建的檢索品質評測跑出來——那才是可以拿去對客戶承諾的數字。

先定義兩個要分開看的準確率，混在一起談是多數討論失焦的原因：

  • 對象正確率：撈到的內容，是不是正確那家客戶／正確那個型號的？
  • 段落正確率：在對象正確的前提下，有沒有撈到回答得了這個問題的那一段？

6.1 四種情境

情境對象正確率（推論）說明與推理依據
A. 什麼都不做<br>多客戶多型號混一盒、不用篩選、文件不帶名約 20%～50%（N＝3～5 家時）推理：內容高度相似時，向量分數（權重 0.7）差距極小，排序接近由細微差異決定；關鍵字路因 chunk 不含客戶名／型號（F4）而幾乎不貢獻。期望值接近 1/N，因部分 chunk（每節第一塊）確實含名而略高。<br>⚠️ 最危險的不是低準確率，而是它不會被攔截——主題確實相關，最高分很高，不會觸發查無依據（F8），所以它會很有自信地答錯
B. 只在問句加客戶名／型號<br>其他都不做約 50%～75%（chunk 帶名率高時）<br>幾乎無提升（chunk 不帶名時）推理：如 §4.2 算式，關鍵字路最多帶來約 0.075～0.15 的分數差距。這足以把正確內容往前推，但不足以把錯誤內容排除在前 10 名之外。實際效果幾乎完全取決於「chunk 到底帶不帶名」（F4）
C. 用「限定知識來源」硬篩100%這不是推論，是定義：篩選是資料庫層的過濾條件（F2），不在範圍內的資料根本不會進入候選集。剩下的誤差全部落在段落正確率
D. 硬篩 ＋ 每節帶名 ＋ 型號別名100%（對象）<br>段落正確率回到一般 RAG 水準對象由 C 保證；③ 與別名（F10）提升的是盒內的排序品質

6.2 段落正確率能到多少

這一項與本文的規劃無關，取決於一般的 RAG 品質（文件寫得好不好、切塊參數、嵌入模型、門檻校準）。

業界對「良好整理過的企業語料」常見的驗收區間是 Recall@10 落在 0.7～0.9（這是業界經驗範圍，不是本系統的實測值）。本系統尚未實作重排序（F13），所以在候選品質不佳時沒有補救機制，實務上建議先把文件寫法與切分做對，再談調參數。

想要「一定找對客戶／型號」，唯一可靠的做法是硬篩選（限定知識來源）。 文件寫法與型號別名能改善排序品質，但它們是加分項，不是保證。 任何宣稱「AI 會自己分辨」的說法，在這套系統的實際機制下都不成立。

  2. /reports/qa-activity 的「被封鎖數」——那些是使用者想知道、但系統答不出來的題目，是現成的考題清單。
  3. /chat-logs（問答稽核明細）裡使用者實際問過的話。
  4. 每一題標註：
  5. 期望命中的知識來源（標題）——這正好對應「有沒有找對客戶／型號」。
  6. 期望的章節錨點（可選）——用來量出處準不準。
  7. 模擬的團隊身分——用來測越權洩漏。每個客戶至少出一題跨客戶的題目（模擬客戶 A 的身分，問客戶 B 才有的東西，期望撈不到）。

7.3 針對本文兩個問題的專用量法

這是本節最實用的一段。

因為 PrecisionAtK 比對的正是「命中的來源標題是否在期望清單內」，只要你照 §3.2 把「一個客戶／一個型號 ＝ 一個知識來源盒子」，那麼：

PrecisionAtK 與 RecallAtK 就直接等於「有沒有找對客戶／找對型號」的準確率。

不需要另外建立量測機制。做法：

  1. 出一組題目，每題只標一個期望來源（該客戶／該型號的盒子）。
  2. 不開任何篩選跑一次 → 得到情境 A／B 的真實數字。
  3. 開「限定知識來源」再跑一次 → 驗證情境 C 是否真的 100%。
  4. 兩組數字的差距，就是「硬篩選」對你們的實際價值。

7.4 其他可用的觀察工具

  • /rag-diagnostics 的「試檢索」：可以單獨看向量分、關鍵字分、圖分三路的分項貢獻。想驗證 §4.2 的算式在你們資料上是否成立，用這個最直接。
  • /reports/retrieval-quality：看真實問答的零命中比例與分數分布。⚠️ 但它不能用來比較調整前後（使用者問法會變，不是乾淨的對照組），比較一律用 §7.1 的基線。
  • /system-health 的向量索引涵蓋率：驗收前先確認索引不是空的（反例 10）。

優先限制建議改法預估效益風險與成本
P1分類篩選是「或」，無法取交集（F3）讓「限定分類」多選支援「且」語意，或加一個「全部符合／符合任一」切換最高。直接解掉 §3.1 的根本問題，多維標籤就能用了改動集中在 BuildContainsAnyPredicate 的呼叫端；⚠️ 語意改變會影響既有使用者的預期，建議做成可切換而非直接改掉
P2chunk 不含章節標題（F4）切塊時把當前標題（或標題路徑）前置進 chunk 本文高。同時改善型號辨識與一般檢索品質；能讓 §4.3 的做法 ③ 自動生效，不必靠人工改文件需要重建全部索引；chunk 會變長，切塊參數要重新校準；建議先用 §7 的基線量出實際增益再決定
P3切詞會切開連字號（F5）分隔符移除 -，或加型號代碼樣式的保留規則中。解掉 EPS-3000 被切開的問題改動小；⚠️ 會改變既有的關鍵字分數分布，兩段式門檻要重新校準（F8）
P4中文不斷詞（F6）導入中文斷詞中～高，但影響面廣成本高於前三項；建議先做完 P1～P3 量過再評估
P5無重排序（F13）導入 rerank視資料而定已有專題分析，見 RAG rerank 是否導入分析
P6無「多維標籤」資料模型把分類從單一字串欄位改成具名維度架構最乾淨成本最高（資料模型、migration、UI、既有資料轉換全都要動）。只有在 P1 做完仍不夠用時才考慮

建議的推進順序：先做 P1，再用 §7 的基線量 P2 的實際增益。 P1 成本低效益高；P2 效益高但要重建索引，值得先量再做。不要一開始就跳到 P6——多數情況 P1＋P2 就夠了。

九、落地檢查清單

依序做，不要跳。前面沒做好，後面會白費。

第一階段：先想清楚（不碰系統）

  • ☐確認是多客戶共用一套系統還是各自獨立部署。獨立部署的話，本文大半內容不需要
  • ☐列出所有客戶／型號，確認實際會有幾個盒子
  • ☐決定分類詞庫（上限 10 個，只放文件用途）
  • ☐決定來源命名規則（§3.3），寫成一頁規範發給所有會建資料的人
  • ☐確認環境維度（資料庫／作業系統）是獨立維度還是客戶屬性（§3.4）

第二階段：建骨架

  • ☐建團隊（客戶會登入時，這是資安紅線）
  • ☐建角色，設定預設團隊
  • ☐建分類（照第一階段決定的詞庫，不要多建）
  • ☐建使用者，指派角色

第三階段：先驗證再推廣

  • ☐只匯入第一個客戶的資料，走完清洗 → 蒸餾 → 知識頁審核 → 建立索引
  • ☐確認 /system-health 的向量索引涵蓋率正常（反例 10）
  • ☐出 20～30 題考題，存基線（§7）
  • ☐跑越權測試：模擬該客戶身分，確認 LeakHits = 0
  • ☐驗證「不開篩選」與「開限定知識來源」的數字差距（§7.3）
  • ☐數字可接受，才推廣到其他客戶

第四階段：長期維運

  • ☐訂下「問特定客戶的事，先選限定知識來源」的使用紀律
  • ☐定期看 /data-consistency（過時來源是靜默的，不看不會知道）
  • ☐定期看 /reports/qa-activity 的被封鎖數，補使用者真正要的資料
  • ☐每次調整檢索設定前後，都跑一次基線比對
