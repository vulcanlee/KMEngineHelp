開場框架：先建立心智模型

一句話定位

智庫引擎把企業分散的文件、會議與影音資料，轉化成「乾淨、去敏、可用自然語言問答、每個答案都附出處、且受團隊權限控管」的知識資產。

核心閉環（全系統的骨幹敘事）

匯入 → 清洗 → 蒸餾 → 索引 → 應用
  • 匯入：影音轉錄、文件轉文字、圖片辨識，把任意來源變成純文字/Markdown。
  • 清洗：LLM 逐步「去重 → 遮罩(去敏) → 分類 → 摘要 → 信心自評」，產出標準化、去敏後的內容。
  • 蒸餾：把清洗內容編譯成「一概念一頁、[[互連]]」的版本化 Wiki 知識頁（預編譯的精煉知識）。
  • 索引：切塊 → 嵌入向量 → 存入資料庫，供檢索。
  • 應用：AI 知識問答（RAG）、對外 MCP 工具、專案協作、品質評測、統計報表。

定位框架：受治理的「RAG × LLM Wiki 混合體」

Andrej Karpathy 於 2026 提出「LLM Wiki——編譯知識優於每次檢索原始碎片」的觀點，並點名其風險是「把幻覺固化成看似權威的頁面」。本系統的蒸餾層正是這種「編譯後知識」，但同時保留檢索層（RAG）作為佐證與可溯源基礎，再以企業治理（團隊 ACL、逐句出處、人工審核、版本鏈、品質評測）壓制固化幻覺的隱憂——因此定位為「受治理的 RAG × LLM Wiki 混合體」。（延伸論述見 docs/strategy/2026-07-16-企業知識庫技術路線分析-RAG-LLM-Wiki-Graph-Agentic.md。）

技術棧與分層（給維運開發者）

  • 平台：.NET 10 / Blazor Server（Interactive Server）＋ AntDesign Blazor；資料層 EF Core；日誌 NLog。
  • 分層：*ViewView（Blazor 檢視）→ *Service（回 AdapterModel）／*Controller（回 DTO）→ BackendDBContext。
  • 非同步骨架：耗時階段皆為「佇列（Channel）＋背景服務（BackgroundService）＋Processor」四條同構管線。
  • 核心資安不變量：所有查詢/下載/API/MCP 一律經 IRecordAccessScopeProvider + TagStringHelper 於檢索層過濾團隊權限（越權不外洩，leak=0）。

19 項功能與特色

1. 端到端知識精煉閉環（匯入 → 清洗 → 蒸餾 → 索引 → 應用）

  • 摘要說明：一條全自動、但每步可人工介入的知識加工流水線，把原始素材煉成可問答的治理級知識。
  • 詳細描述：五個階段各自獨立、以狀態機串接（來源需「已清洗」才能蒸餾、蒸餾核可後自動入列嵌入索引）。每階段皆可單獨重跑、可人工審核/退回。技術對應：CleaningProcessor、DistillationProcessor、EmbeddingIndexProcessor（Business/Services/…）。
  • 為什麼需要：企業知識散落在會議錄音、PDF、簡報、圖片中，單靠「接上檔案就問」無法產生可信、去敏、結構化的知識。
  • 解決的痛點：資訊分散、格式雜亂、人工整理成本高、知識品質不一。
  • 價值：把「一次性問答工具」升級為「可累積、可傳承的知識資產」；每一步可審核，品質可控。
  • 哪些人會需要：知識管理負責人、需要建立內部知識庫的技術團隊、資料治理團隊。
  • 競品對照：多數企業搜尋產品（Glean、Notion AI、Microsoft 365 Copilot）走「連接既有來源即時檢索」路線，不含「轉錄→去敏清洗→蒸餾成 Wiki」的內容加工管線；開源 Onyx/RAGFlow 偏重連接與檢索，亦無完整的「清洗＋蒸餾」精煉閉環。本系統的差異在於把原始素材主動加工成治理級知識，而非只索引現況。

2. 多平台影音一鍵轉錄（含抖音瀏覽器攔截）

  • 摘要說明：把 YouTube、小紅書、抖音連結或本機影音檔，一鍵轉成繁體逐字稿，並可再生成會議紀錄/待辦。
  • 詳細描述：影片連結以 yt-dlp 抽音訊；抖音因 web API 需 JS 即時簽章、yt-dlp 無法處理，改以 Node + Playwright 助手腳本用已登入瀏覽器攔截音訊串流；超大/超長檔以 ffmpeg 平均切段後逐段轉錄再合併；轉錄走 OpenAI 語音模型，中文結果再以 OpenCC 簡轉繁保底。技術對應：MediaUrlDownloader、DouyinAudioDownloader、MediaChunker、OpenAITranscriptionClient、ChineseConverter。
  • 為什麼需要：大量企業知識以「會議/教學/訪談影音」形式存在，且中文內容常散在抖音/小紅書等難以自動化擷取的平台。
  • 解決的痛點：會議追蹤不完整、影音內容無法被搜尋、跨平台素材擷取困難、簡繁混雜。
  • 價值：把「聽過就忘」的影音轉為可檢索、可問答的文字知識；抖音攔截能力技術門檻高、對手罕見。
  • 哪些人會需要：內訓/教育團隊、行銷與內容團隊、需要保存會議與訪談的各部門。
  • 競品對照：NotebookLM 可貼上 YouTube 連結摘要，但不含企業級多來源批次轉錄與抖音/小紅書擷取；Glean/Copilot/Notion AI 以連接既有檔案為主，不內建影音下載/切段/轉錄管線。本系統的多平台擷取（尤其抖音瀏覽器攔截）為少見的差異化能力。

3. 多格式文件轉文字轉 Markdown（批次 ZIP、防 zip bomb）

  • 摘要說明：把 PDF、Office、網頁、EPUB 等統一轉成 Markdown，作為後續清洗/技能的乾淨輸入。
  • 詳細描述：以 Microsoft MarkItDown 執行檔轉檔（UTF-8 輸出、含逾時強制中止）；支援上傳 ZIP 批次匯入多檔，逐一驗證格式、拒絕巢狀 ZIP、限制檔數與解壓總量（防 zip bomb），回傳成功/略過/失敗清單。技術對應：MarkItDownConverter、DocumentExtractionService.AddBatchFromZipAsync、DocumentFormatValidator。
  • 為什麼需要：企業文件格式繁雜，後續 LLM 清洗/檢索需要一致的純文字/Markdown 表述。
  • 解決的痛點：格式不一、逐檔手動轉換耗時、批次匯入的安全風險（惡意壓縮包）。
  • 價值：一致化輸入、批次省時、內建資安防護。
  • 哪些人會需要：需將大量既有文件納入知識庫的團隊、資料遷移專案。
  • 競品對照：多數平台以連接器索引原檔（Glean/Notion AI），對「深度版面理解」以 RAGFlow 最強（表格/雙欄）。本系統走「先轉 Markdown 再加工」路線、內建批次與防護；但複雜 PDF 的結構感知解析（條款/表格/圖表）目前為規劃中（見 docs/prd/README.md），此點誠實標示為尚未具備。

4. 圖片視覺辨識（OCR ＋ 視覺理解）

  • 摘要說明：把圖片交給視覺模型，依選定提示詞解讀成文字，納入知識來源。
  • 詳細描述：讀取圖片位元組，呼叫具視覺輸入的 Chat 模型（帶 image bytes 與 contentType）輸出文字並落檔；亦支援批次 ZIP 匯入。技術對應：ImageRecognitionProcessor、OpenAIChatCompletionClient.CompleteWithImageAsync。
  • 為什麼需要：白板、截圖、掃描件、流程圖等含大量無法被文字檢索的知識。
  • 解決的痛點：圖片內容無法搜尋、人工謄打成本高。
  • 價值：把視覺資訊轉為可檢索文字，且可用提示詞客製解讀角度（OCR vs 圖表理解）。
  • 哪些人會需要：工程/製造（圖面、流程圖）、設計、需處理掃描件的行政/法遵。
  • 競品對照：主流企業搜尋產品多做圖片內文字索引；本系統的差異是以可自訂提示詞的視覺理解（不只 OCR）並納入同一條清洗/索引管線。

5. 智慧清洗管線（去重／PII 遮罩／分類／摘要／信心自評）

  • 摘要說明：LLM 五步驟把彙整內容清洗成標準化、去敏後的 Markdown，並自評信心決定是否需人工審核。
  • 詳細描述：五步為 去重 → 遮罩(PII 去敏) → 分類(最多 5 類) → 摘要 → 信心自評(0~1)；遮罩步驟刻意不吞例外（確保進索引前必已去敏），其餘步驟可降級並註記；信心 ≥ 門檻標「已完成」、否則「待審核」。清洗規則設定（CleaningProfile）可逐步覆寫提示詞。技術對應：CleaningEnhancer、CleaningProcessor、CleaningProfileService。
  • 為什麼需要：原始素材含重複、雜訊與個資；直接進索引會造成品質低落與資料外洩風險。
  • 解決的痛點：雜訊污染檢索、個資/機敏外洩、無法分類治理。
  • 價值：embedding 前先去敏是關鍵資安設計；分類與摘要提升可治理性；信心分數啟動人在迴路。
  • 哪些人會需要：資料治理/法遵、資安、知識庫維運者。
  • 競品對照：Guru/Bloomfire 提供內容驗證與可信度分數，屬市場少數領先者；一般 RAG 產品多不含「嵌入前 PII 遮罩＋逐步信心自評」的清洗治理。本系統把「去敏＋品質分級」內建為管線必經步驟。

6. 知識頁審核與版本化互連 Wiki（as-of 時效）

  • 摘要說明：把已清洗內容蒸餾成「一概念一頁、[[互連]]」的 Wiki 知識頁，並做版本鏈與生效狀態管理。
  • 詳細描述：LLM 產出 JSON（每頁 title/content/links/confidence）；重蒸餾不刪舊版，新頁 Version+1 並掛前版指標，信心達標自動成為「現行版」、舊版標記 superseded 保留供 as-of 時點查詢與稽核。技術對應：DistillationEnhancer、DistillationProcessor（版本鏈 VER-1）、WikiPageService。
  • 為什麼需要：檢索原始碎片難以回答「概念性、跨文件」問題；預編譯的精煉知識更穩定、可導覽。
  • 解決的痛點：知識碎片化、版本混亂、無法回溯「某時點的正確答案」。
  • 價值：預編譯知識提升回答品質與一致性；版本鏈與 as-of 保障可稽核、可回溯（呼應 Karpathy「編譯優於檢索」但補上治理）。
  • 哪些人會需要：知識管理者、需要穩定 SOP/政策頁的部門、稽核。
  • 競品對照：Glean/Atlassian 具企業知識圖雛形；本系統的「LLM 蒸餾成互連 Wiki＋版本鏈＋as-of」是把「LLM Wiki」概念產品化並加上時效治理，市場少見完整實作。

7. 混合檢索 RAG（融合＋查詢改寫＋兩段式信心＋含出處）

  • 摘要說明：向量語意與關鍵字雙路檢索加權融合，配查詢改寫與信心門檻，回傳附出處答案。
  • 詳細描述：向量路徑（cosine＋權控）與關鍵字路徑（LIKE）並行，以 向量權重0.7＋關鍵字權重0.3 融合取 TopK；多輪對話對依賴上下文的短問句做條件式查詢改寫（失敗回退原句）；以最高分分三段——< 0.15 拒答（不呼叫 LLM）、< 0.30 標示信心不足、否則正常答；回答附來源（Wiki 導引在前、Cleaned 佐證在後）。查詢期參數可於診斷頁熱套用免重啟。技術對應：RetrievalService、DualDbVectorStore、KnowledgeBaseQueryRewriteService、KnowledgeBaseChatService。
  • 為什麼需要：純向量會漏專有名詞、純關鍵字缺語意；無信心門檻易生幻覺；無出處無法查核。
  • 解決的痛點：召回不全、幻覺、答案不可溯源、參數僵化。
  • 價值：語意與精確互補、抑制幻覺、可溯源、可線上調參；嵌入未設定時自動退化為關鍵字檢索（韌性）。
  • 哪些人會需要：所有知識庫使用者、RAG 維運者。
  • 競品對照：主流產品多支援帶引用的檢索回答（Coveo/Notion AI/Copilot）；本系統差異在融合權重、兩段式信心門檻與門檻可線上校準皆為透明可調的工程化設計，適合需要自控的技術團隊。

8. 團隊資料權控（檢索層即過濾，leak=0，三入口共用）

  • 摘要說明：非管理員只能看到公開或與其團隊有交集的知識，權控在檢索層生效，越權內容永不外洩。
  • 詳細描述：IRecordAccessScopeProvider 解析「是否管理員＋授權團隊」，同時支援 Blazor、Web API、MCP（HttpContext claims）三情境；標籤以「換行包夾」格式儲存並以精確成員比對產生 EF 可轉 SQL 的權控述詞；每輪問答重新取 scope（避免身分切換沿用舊權限）。技術對應：RecordAccessScopeProvider、TagStringHelper.BuildTeamAccessPredicate。
  • 為什麼需要：企業知識有部門機敏，AI 助理若能繞過權限就是重大資安破口。
  • 解決的痛點：跨團隊資料外洩、AI 繞過權限、各入口權控不一致。
  • 價值：單一權控真相源在檢索層統一把關，Blazor/API/MCP 共用同一套規則，達成 leak=0。
  • 哪些人會需要：資安、法遵、任何多部門/多租戶部署。
  • 競品對照：Coveo（early-binding 權限鏡射最強）、Glean（權限映射即時驗證）為市場領先；本系統的差異是開源可自建、且把權控下沉到向量檢索層並跨三入口共用，對重視資料自主的中型企業特別合適。

9. MCP Server（讓外部 AI Agent 安全查庫）

  • 摘要說明：內建 MCP 伺服器，提供五個知識工具＋連通診斷（1.0.91 起含知識圖譜鄰域查詢與全域問答模式），讓 codex/Claude 等外部 Agent 把企業知識庫當工具用。
  • 詳細描述：以 AddMcpServer().WithHttpTransport() 掃描 [McpServerToolType]，端點 /mcp（Streamable HTTP）套授權政策與限流；工具含 knowledge_ask（RAG 問答含出處與信心）、knowledge_search、knowledge_list_sources、knowledge_get_document、knowledge_ping；McpIdentityResolver 讓 MCP 呼叫沿用同一團隊權控、聊天紀錄與 token 歸屬。技術對應：Mcp/KnowledgeAskTool 等、MapMcp("/mcp")、McpIdentityResolver。
  • 為什麼需要：AI Agent 時代，知識庫需能被任何相容 Agent 安全呼叫，而非各自客製串接。
  • 解決的痛點：Agent 整合破碎、外部工具繞過權控/稽核。
  • 價值：一次串接、處處可用；且權控/稽核/成本歸屬與 UI 完全一致（安全的對外知識端點）。
  • 哪些人會需要：導入 AI Agent 的技術團隊、平台整合者、生態夥伴。
  • 競品對照：Guru 已提供 MCP；多數產品逐步跟進。本系統差異在MCP 呼叫完全沿用內部團隊權控與稽核治理（不是另開一個弱權控的對外通道），對合規部署是關鍵。

10. 認證授權與資料庫化金鑰治理

  • 摘要說明：Cookie／JWT／Google OAuth／MCP API Key 多重認證，MCP 金鑰存資料庫、可即時啟用停用。
  • 詳細描述：Web UI 走 Cookie、API 走 JWT、外部 Agent 走專屬 X-API-Key；MCP 金鑰以 McpAccessKeyService 做 CRUD 與啟用/停用切換，認證時以 CryptographicOperations.FixedTimeEquals 常數時間比對（防時序側信道）命中「啟用中」金鑰；角色權限樹（RolePermissionService）與側欄以位置索引對齊。技術對應：McpApiKeyAuthenticationHandler、McpAccessKeyService、RolePermissionService。
  • 為什麼需要：不同用戶端需不同認證；金鑰需可即時撤銷、可歸責到具體使用者。
  • 解決的痛點：金鑰寫死設定檔難撤銷、無法停用單一整合、權限難集中管理。
  • 價值：金鑰網頁化治理（即時停用、對映使用者、常數時間比對）、角色權限集中可調。
  • 哪些人會需要：系統管理員、資安、平台維運。
  • 競品對照：企業級產品普遍具 SSO/權限；本系統差異在把 M2M 金鑰做成可即時啟用停用、可歸責的 DB 管理頁，適合自建部署的運維需求。

11. AI 可觀測性與成本治理

  • 摘要說明：完整記錄「誰問了什麼、花了多少 token、答得好不好」，且稽核不落地問答本文。
  • 詳細描述：問答稽核明細（LlmChatLog，索引入庫、全文存檔）帶來源、信心、滿意度回饋；Token 用量明細（LlmTokenUsage）以 OperationContext 把作業/使用者/團隊沿呼叫鏈歸屬（含 MCP 專屬作業）；問答稽核（KnowledgeBaseQueryAudit）只存長度與分數指標、不存本文（隱私邊界）；NLog 分級日誌帶 TraceId。技術對應：ChatLogService、TokenUsageRecorder/OperationContext、KnowledgeBaseQueryAudit。
  • 為什麼需要：AI 導入後需可觀測（品質）、可歸責（成本）、可稽核（合規），且稽核本身不能造成新外洩。
  • 解決的痛點：AI 成本不透明、問答品質無數據、稽核與隱私衝突。
  • 價值：成本可依部門/作業歸屬、品質有滿意度數據、稽核守住隱私邊界。
  • 哪些人會需要：IT 治理、財務/成本控管、資安稽核、RAG 維運。
  • 競品對照：Guru/Bloomfire 具知識缺口/驗證治理；本系統差異在把「可觀測性＋成本歸屬＋不落地本文的稽核」整合為一體，兼顧治理與隱私。

12. RAG 品質評測與基線

  • 摘要說明：以清洗品質評測與 檢索品質評測量化檢索品質，並可凍結基線做「調參前後」比較，防止退化。
  • 詳細描述：黃金樣本（上游清洗品質）與 檢索品質評測（下游檢索品質，純函式、確定性、不需 LLM 生成）量化指標；RagEvalBaseline 以單列 upsert 凍結某時點的整體彙總與當時生效參數，供「目前 vs 基線」對比。技術對應：GoldenSampleService、RagEvaluationService/RagEvaluator、RagEvalBaseline。
  • 為什麼需要：調整門檻/權重/模型時，若無客觀基線，品質變化只能憑感覺。
  • 解決的痛點：改動後品質退化難察覺、無法量化「有沒有變好」。
  • 價值：檢索品質可量化、可回歸；調參有客觀護欄。
  • 哪些人會需要：RAG 工程/維運、品質保證。
  • 競品對照：多數商用產品的評測藏在後端不對客戶開放；本系統把評測與基線做成可操作的內建功能，對需要自證品質的技術團隊很有價值。

13. 本機／雲端 LLM 可切換（資料主權）

  • 摘要說明：生成與嵌入各自可在雲端（OpenAI）與地端（OpenAI 相容伺服器）間切換，滿足資料不出境。
  • 詳細描述：OpenAISettings 提供 GenerationProvider/EmbeddingProvider（Cloud/Local）；地端嵌入預設 bge-m3（原生 1024 維），雲端 text-embedding-3-large 以 dimensions=1024 鎖定（Matryoshka 截短），維度固定確保雲/地端索引相容。技術對應：OpenAISettings、OpenAIEmbeddingClient、OpenAIChatCompletionClient。
  • 為什麼需要：許多企業因法遵/機敏要求資料不得送第三方雲。
  • 解決的痛點：雲端 AI 的資料外流疑慮、成本不可控、不可離線。
  • 價值：可地端部署達成資料主權；嵌入維度固定避免雲/地端切換造成索引不相容。
  • 哪些人會需要：金融/醫療/政府/製造等重合規產業、重視成本與離線的團隊。
  • 競品對照：Glean 提供客戶 VPC，多數 SaaS（NotebookLM/Notion AI/Copilot）為純雲、資料需送其環境；本系統的真・地端可切換（生成與嵌入皆可離線）是對資料自主客戶的核心差異化。

14. 韌性背景管線與雙資料庫平台

  • 摘要說明：所有耗時工作以背景管線非同步處理，可取消/自動重試/重啟自動復原；同一套碼支援 SQLite 與 SQL Server。
  • 詳細描述：每階段為「Channel 佇列＋*BackgroundService＋Processor」；暫時性錯誤自動重試（線性退避），可即時取消處理中工作，應用重啟時自動把中斷的工作重新入列；資料庫依設定切換 SQLite（免安裝、單檔）或 SQL Server（企業級），權控述詞刻意兩 provider 皆能轉 LIKE，每次模型變更維護雙 migration。技術對應：PipelineRetryHelper、PipelineCancellationRegistry、各 *BackgroundService、AddConfiguredDatabase。
  • 為什麼需要：長時間的轉錄/清洗/嵌入不能卡住 UI，且服務重啟不該遺失進行中的工作；不同規模客戶需不同資料庫。
  • 解決的痛點：長任務阻塞、當機遺失進度、部署門檻高。
  • 價值：對維運開發者是強說服力的穩健性；POC 用 SQLite 零安裝、正式切 SQL Server 免改碼。
  • 哪些人會需要：系統維運/開發人員、需要從 POC 平滑升級到正式環境的團隊。
  • 競品對照：SaaS 產品把這些藏在雲端後端、客戶不可見亦不可控；開源 Onyx/Dify/RAGFlow 各有工作流與部署選項。本系統的差異在這些工程韌性與雙資料庫彈性對維運者完全透明可控，是「可自建、可維運」取向的體現。

15. 專案協作與多來源檔案管理（含單一來源 AI 對話）

  • 摘要說明：不只是知識庫，也是可管理專案、任務、會議與其附件的協作平台，並能針對「單一知識來源」直接對話。
  • 詳細描述：專案/任務/會議各有 CRUD 與檔案附件（支援子任務、標籤與團隊權控）；每個知識來源可開啟單一來源 AI 對話（只針對該來源問答，不跨庫）。技術對應：ProjectService(/projects)、MyTasService(/Task)、MeetingService(/meeting)、KnowledgeSourceChatService（/knowledge-sources/{id}/chat）。
  • 為什麼需要：知識常伴隨專案/會議情境產生；且有時使用者只想針對某一份文件深入問答。
  • 解決的痛點：知識與工作情境脫節、跨庫問答時抓不準單一文件、附件散落。
  • 價值：知識在工作流中就地累積；單一來源對話提供精準、聚焦的問答體驗。
  • 哪些人會需要：專案團隊、會議主持/記錄者、需要逐份文件深問的分析人員。
  • 競品對照：Notion 等把知識與工作區結合；本系統的差異是協作情境直接串接同一條清洗/蒸餾/權控管線，且提供受權控的「單一來源對話」。

16. 知識百科與 WikiLink 導覽

  • 摘要說明：以「一概念一頁、[[互連]]」的方式瀏覽蒸餾後的知識，像逛內部維基一樣沿連結導覽。
  • 詳細描述：知識百科頁以概念頁與其 [[links]] 互連關係導覽，呈現現行版並支援 as-of 時效閱讀；與蒸餾管理頁（/knowledge-distillation）分工——前者是「讀者導覽」、後者是「維護管理」。技術對應：WikiPageService、路由 /knowledge-wiki（KnowledgeWikiView）。
  • 為什麼需要：問答適合「有明確問題」時；但使用者也需要「探索式」地瀏覽與建立全貌。
  • 解決的痛點：只有搜尋框無法探索、看不到知識間的關聯結構。
  • 價值：把精煉知識變成可導覽的內部維基，兼顧「問答」與「瀏覽」兩種認知模式。
  • 哪些人會需要：新進人員（快速建立全貌）、知識管理者、需要探索關聯的分析者。
  • 競品對照：Glean/Atlassian 具知識圖雛形；本系統把蒸餾出的互連 Wiki 直接做成可沿連結導覽的閱讀體驗，並與版本/時效治理一致。

17. 統計報表與經營儀表板

  • 摘要說明：首頁儀表板與多張報表，把「用量、問答活躍度、滿意度、檢索品質、內容盤點」變成可決策的數據。
  • 詳細描述：首頁 /App 內嵌儀表板摘要；報表區（/reports/*）含 Token 用量報表、滿意度/回饋、問答活躍度、檢索品質、內容盤點等。技術對應：DashboardService、Reports/TokenUsageReportService、ChatReportService、RetrievalQualityReportService、ContentInventoryReportService。
  • 為什麼需要：導入知識庫後，管理者需要數據回答「用得多不多、答得好不好、花多少錢、內容夠不夠」。
  • 解決的痛點：AI 導入成效無法量化、成本與品質缺乏經營視角。
  • 價值：把可觀測性資料升級為經營級報表，支撐續投資與優化決策。
  • 哪些人會需要：管理者、IT 治理、成本控管、知識營運負責人。
  • 競品對照：企業級產品多有使用分析；本系統差異在報表與內部清洗/檢索/稽核資料同源，且對自建部署完全可見、可延伸。

18. 提示詞平台（DB 提示詞、四層覆蓋、線上編輯免重啟）

  • 摘要說明：集中管理各業務的 LLM 提示詞，可線上編輯、免重啟生效，並有明確的四層覆蓋優先序。
  • 詳細描述：LlmPromptResolver 依高→低取第一個非空白值：① 單次操作覆蓋（對話頁系統提示詞、清洗規則設定、技能自訂）② DB Prompt 表（線上編輯、免重啟）③ appsettings LlmPrompts 平台預設 ④ 程式內建 fallback。技術對應：LlmPromptResolver、PromptService、路由 /prompts。
  • 為什麼需要：提示詞需能隨業務快速迭代，但又要有穩定保底與 per-operation 客製。
  • 解決的痛點：提示詞寫死程式碼、改一次要重新部署、無法分業務管理。
  • 價值：提示詞由管理員線上調整、免部署即可迭代；四層覆蓋兼顧彈性與穩定。
  • 哪些人會需要：Prompt/AI 工程、知識庫維運、需要按業務調校語氣/規則的團隊。
  • 競品對照：多數 SaaS 的提示詞不對客戶開放；本系統把提示詞做成可線上編輯、有明確覆蓋優先序的平台，對需要自控 LLM 行為的技術團隊很有價值。

19. 系統健康與資料一致性維運

  • 摘要說明：給維運者的操作中心——系統健康評分、資料一致性巡檢、線上調日誌級別、檢索診斷與調校試打。
  • 詳細描述：系統健康監控彙整關鍵指標並計分；資料一致性巡檢偵測版本/索引/孤兒資料等不一致；日誌級別可執行期線上調整（免重啟）；檢索診斷與調校頁可即時試打檢索、校準門檻/權重。技術對應：SystemHealthService（/system-health）、DataConsistencyService（/data-consistency）、/log-settings、RagDiagnosticsService（/rag-diagnostics）。
  • 為什麼需要：自建部署需要可自我診斷、可線上調參，而非每次都要停機或改設定檔重啟。
  • 解決的痛點：線上問題難即時定位、調參要重啟、資料不一致難察覺。
  • 價值：對維運開發者是強說服力的「可運維性」——健康可視、問題可診斷、參數可線上校準。
  • 哪些人會需要：系統維運/開發人員、SRE、技術支援。
  • 競品對照：SaaS 把維運藏在雲端後端、客戶不可見；本系統把健康、一致性、日誌與 檢索診斷與調校做成對維運者透明可操作的頁面，是「可自建、可維運」取向的關鍵。

專為企業客戶設計與交付的功能

以下能力偏向「企業導入與交付」情境，與前 19 項核心功能互補；凡有實作界線者均誠實標註，未實作不宣稱。

E1. 單一登入（SSO）與帳號生命週期

  • 摘要說明：Google OAuth2 SSO（Cookie 導向）＋記住我（持久化登入）＋ API 走 JWT；首次 SSO 登入自動建立「停用中」帳號待管理員啟用。
  • 詳細描述／技術對應：GoogleOAuthSettings（Enabled/ClientId…）、ExternalAuthController（/Auths/Google/Login、/Auths/Google/Callback）、JwtTokenService（/api/Auth/login|refresh|me）、記住我以 AuthenticationProperties.IsPersistent 產生持久化 Cookie。
  • 為什麼企業需要：企業要求以既有身分（Google Workspace）登入、避免額外帳密；新帳號需管理員審核把關。
  • 價值：降低導入門檻、集中身分治理、「首登待啟用」兼顧便利與控管。
  • 誠實界線：第三方登入目前以 Google 為主；其他 IdP（Azure AD／SAML／泛用 OIDC）尚未內建。

E2. 企業組織治理（使用者／角色／團隊／分類）

  • 摘要說明：完整的使用者、角色權限、團隊、分類管理，對映企業組織結構並驅動資料權控。
  • 詳細描述／技術對應：/myusers、/roleviews（權限樹 RolePermissionService ＋ Menu.json 三處同步、存 RoleView.TabViewJson）、/teams、/categories；角色可設預設團隊 RoleView.DefaultTeamsJson。
  • 為什麼企業需要：多部門、多角色需要細緻的頁面權限與資料可見範圍治理。
  • 價值：一套後台即可維護組織權限；與檢索層團隊權控（#8）連動，達成 leak=0。
  • 誠實界線：為「團隊＋角色」單層模型，非階層式組織樹/權限繼承（如需深層 OU 繼承需另行擴充）。

E3. 私有／地端部署、資料主權與企業級資料庫

  • 摘要說明：可完全私有部署於企業內網；資料庫可切換 SQLite／SQL Server；所有資料/媒體存放路徑可設定；LLM 可走地端。
  • 詳細描述／技術對應：DatabaseProvider（Sqlite/SqlServer）＋獨立 SqlServer migration 專案；ExternalFileSystem 十餘個路徑可設定（DB 存索引、全文/媒體落檔＝資料分層儲存）；LLM GenerationProvider=Local（Ollama/LM Studio/vLLM，免金鑰）；交付含 docs/operations/全新機器部署SOP.md、正式部署與安全檢查清單.md。
  • 為什麼企業需要：法遵/機敏要求資料與模型不出企業環境、可控存放位置、可沿用既有 SQL Server。
  • 價值：資料主權、可離線化的知識問答、標準化交付流程降低導入風險。
  • 誠實界線：語音轉錄仍需雲端 OpenAI（尚無地端 ASR），有影音轉逐字稿需求時非 100% 離線；DB 備份/還原屬維運層（無內建一鍵備份還原）。

E4. 可擴展性：分散式快取（Redis 可切換）

  • 摘要說明：快取抽象層，Provider 可在 Memory 與 Redis 間切換，支撐多實例/水平擴展。
  • 詳細描述／技術對應：ICacheService/DistributedCacheService（建於 IDistributedCache）、CacheSettings（Provider/RedisConnection/InstanceName/DefaultExpirationMinutes）。/system-health 的「分散式快取」項會實測 Redis 連線是否可用。
  • 為什麼企業需要：使用者規模擴大時需要跨實例共享快取與水平擴展。
  • 價值：從單機平滑升級到多實例、切 provider 免改程式；正式環境有防呆保護。
  • 誠實界線：提供分散式快取基礎；完整叢集/負載平衡部署拓撲由部署方規劃。

E5. 合規稽核、成本治理與報表匯出

  • 摘要說明：問答稽核（不存本文）＋ Token 用量團隊歸屬 ＋ 報表/聊天 PDF 匯出，滿足企業「可歸責、可計費、可呈報」。
  • 詳細描述／技術對應：KnowledgeBaseQueryAudit（只存身分/分數指標，不存問答本文）、LlmTokenUsage（含團隊歸屬）＋/reports/*、ReportPdfExporter/ChatPdfExporter（PDF 匯出）、密碼以 SHA256＋每人隨機鹽儲存。
  • 為什麼企業需要：稽核可歸責、成本可按部門攤提、成果可輸出成報告呈報決策層。
  • 價值：治理與隱私兼顧（稽核不落地本文）、成本透明、報表可離線分發。
  • 誠實界線：稽核與用量表目前無自動保留/清理策略，需維運人工歸檔；資料級備份/還原屬維運層。

E6. 資料可見度與團隊權控（記錄級可見度限制）

  • 摘要說明：每筆紀錄以「團隊標籤」控管可見度；非管理員只見公開或與其團隊交集的紀錄，權控在檢索層生效，且 Blazor／API／MCP 三入口一致。
  • 詳細描述／技術對應：專案/會議/任務/知識來源/媒體等紀錄以 Teams 分隔字串標籤＋TagStringHelper 精確成員比對；IRecordAccessScopeProvider/RecordAccessScopeProvider 解析範圍；問答/檢索/下載皆套 BuildTeamAccessPredicate，管理員豁免。（延伸自核心第 8 項，此處聚焦企業「資料可見度治理」角度。）
  • 為什麼企業需要：部門機敏（財務/HR/法務）不可跨部門外洩，且 AI 問答也不得繞過可見度。
  • 價值：記錄級、可設定的可見度限制；「檢索層過濾」確保越權內容不進入 context／出處／MCP 回傳（leak=0）。
  • 誠實界線：以「團隊交集」為可見度模型（公開 or 交集）；更複雜規則（如欄位級遮罩、否定授權、跨團隊臨時授權）需另行擴充。

E7. 個資遮蔽與敏感資料保護（PII 去敏）

  • 摘要說明：內容進索引前先由 LLM 遮蔽個資/機敏；線上編修存檔前再次重遮；並以清洗品質評測量測遮罩召回率。
  • 詳細描述／技術對應：清洗管線的「遮罩（mask）」步驟（CleaningEnhancer，此步不吞例外以確保進索引前必已去敏）；編修 Cleaned/Wiki 存檔前 MaskAsync 重跑；清洗品質評測 MaskRecall/MaskLeaks 指標（CleaningEvaluator）；稽核只存指標、不存本文。
  • 為什麼企業需要：知識庫常含姓名/電話/證號/合約金額等個資，直接進 AI 索引即為外洩風險與法遵問題。
  • 價值：「嵌入前去敏」把個資擋在向量索引與問答之外；重遮與召回率指標讓去敏可驗證、可持續改善。
  • 誠實界線：遮罩品質取決於 LLM 與提示詞；未設定 LLM 時不執行遮罩（會記警告），建議搭配清洗品質評測持續驗證。

E8. 使用者滿意度回饋與品質洞察

  • 摘要說明：使用者可對每則答案給「👍 滿意 / 👎 不滿意」回饋；管理者從明細與滿意度報表掌握知識庫的使用品質。
  • 詳細描述／技術對應：ChatFeedbackBar（掛在AI 知識問答頁與知識來源對話頁）→ ChatLogService.SetFeedbackAsync 寫入 LlmChatLog.Feedback/FeedbackAt；管理端 /chat-logs（可依滿意/不滿意/未回饋篩選、查看全文）＋ /reports/feedback（ChatReportService：滿意率、依使用者回饋排名、每日趨勢，可匯出 PDF）；首頁儀表板顯示近 30 天滿意/不滿意筆數。
  • 為什麼企業需要：導入 AI 後需要「使用者實際覺得答得好不好」的品質信號，才能持續改善知識庫內容與提示詞。
  • 價值：形成「回饋 → 找出不滿意 → 調整內容/門檻/提示詞」的品質改善迴路；滿意率可作為導入成效 KPI。
  • 誠實界線：目前為二元 👍/👎，尚無自由文字意見欄位；不滿意項目的逐筆明細需到 /chat-logs 用「不滿意」篩選檢視。

E9. 使用量與活躍度統計（含 per-user 排名）

  • 摘要說明：五張報表＋首頁儀表板，量化問答量、活躍使用者、滿意度、Token 成本、檢索品質與內容清點。
  • 詳細描述／技術對應：/reports/qa-activity（問答量、依來源分布、使用者活躍度排名、封鎖/低信心數、每日趨勢）、/reports/feedback（滿意率、使用者回饋排名）、/reports/token-usage-report（使用者 Token 用量排名、依作業/模型分布）、/reports/retrieval-quality（TopScore/命中率/信心分布）、/reports/content-inventory（依型別/團隊/分類/狀態計數）；首頁儀表板 DashboardService 近 30 天摘要。皆可依團隊過濾、多數可匯出 PDF。
  • 為什麼企業需要：管理者需要數據回答「用得多不多、誰在用、答得好不好、花多少錢、內容夠不夠」。
  • 價值：使用量與活躍度可視、可依使用者/團隊切分，支撐續投資與優化決策。
  • 誠實界線：per-user 統計是依「提問者/呼叫者帳號」（問答次數、回饋、Token 用量）；「內容貢獻者統計（誰建立/貢獻了多少知識來源/內容）」目前不具備——內容資料表尚無「建立者」欄位，內容面統計僅到型別/團隊/分類/狀態維度。

結語：延伸與外溢價值

有了上述 19 項作為底座，技術讀者可進一步構想以下延伸方向：

  • 複雜/多跳問答（Graph RAG / Agentic RAG）：Graph RAG 已於 1.0.83～1.0.88 分六階段實作——概念連結邊、LLM 三元組抽取＋人工審核、社群摘要＋「全域」問答模式、跨來源實體合併與別名治理，並以第三路「圖檢索」併入混合檢索（GraphWeight 預設 0.2、可設 0 關閉）。1.0.90 起支援多跳遍歷（BFS，預設 2 跳、上限 3，含跳數衰減與節點上限），並可於審核頁「圖譜瀏覽」分頁目視任一實體的 N 跳鄰域。Agentic RAG 尚未實作（見 Graph RAG 導入分析與實作藍圖 §9）。
  • 垂直應用：以同一套清洗/蒸餾/檢索能力，快速組裝出審圖、SOP 產生、稽核 checklist、考題生成、客服問答助理等情境（跨部門 28 案見 docs/strategy/09-企業應用情境型錄.md）。
  • 合規旗艦化：本機/雲端可切換＋團隊權控＋遮罩＋稽核，天生適合往「地端合規知識平台」定位深化，服務金融/醫療/政府/製造等重合規產業。

一句話總結：智庫引擎是一套「可自建、可維運、受治理」的知識精煉與問答平台——它不只回答問題，更把企業零散資訊編譯成可累積、可傳承、可稽核的知識資產，並以統一權控安全地開放給人與 AI Agent 使用。
