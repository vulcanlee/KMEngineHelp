一、摘要與建議（決策摘要）

重新框定：RAG 是地基，不是產品

普通 RAG（解析→切塊→向量→檢索→生成）是企業自建知識庫的基礎設施，不是最終產品。傳統知識庫偏「文件檢索／PDF 問答」，但在合規場景（國標、法規、企業內規）面對「文件量大、標準互相引用、版本持續更新」時，單純檢索會導致遺漏、錯誤、資訊不透明——這正是客戶真正的痛點所在，也是產品要往上加值的地方。

核心判斷

  1. 本系統不是「基本款 RAG」，而是已具備市場少數玩家才有的進階能力：蒸餾成互連 Wiki 知識圖、QA-1..4 品質分級＋人工審核、兩段式信心門檻、檢索層即過濾的團隊權控、地端/雲端可切換。這些對應到市場「知識驗證治理」「權限感知檢索」「答案帶引用」「衍生應用」等差異化能力，多半已有雛形或同級實作。
  1. 兩個客戶案與合規場景指向同一底層缺口：本系統目前是「匯入導向、扁平切塊、快照式」；而合規標準（客戶 A）與系統規格/schema（客戶 B）都需要「可編修/結構化、關聯感知、有版本/生效狀態、可溯源」的知識。這是同一條產品主軸的不同實例。
  1. 市場方向明確：企業知識庫正從「RAG 問答」走向「知識即行動系統」——連接器即時同步、權限感知檢索、答案帶引用、代理式工作流(agentic actions)、評測可觀測性、知識驗證/新鮮度，已從加分項變成標配門檻。但 agentic 也伴隨高取消率與 ROI 風險（見 §六、§七）。

建議（回答你的核心問題）

  • 產品定位 → 合規管理知識平臺為對外旗艦，可組態知識型態平台為底座。合規是最能戳中痛點、最願付費的旗艦垂直；底層仍是可組態平台，才能推廣到其他客戶、避免每客戶重寫。
  • 加功能 / 建系統 / 外溢應用？ → 正解是平台化：抽出「知識型態（Knowledge Type）」設定層（見 §十二），客戶 A/B 與合規各為一個型態實例；外溢應用（技能/Agent）作差異化與變現層；垂直模組僅在單一大客戶願付費時才做。
  • 要不要改架構 / 加頁面？ → 需要，但是延伸而非重建：三項資料模型延伸（版本/生效狀態、顯式集合、關聯邊）＋一次向量庫升級，皆守既有不變量（雙 migration、TagStringHelper、選單三處同步、檢索層權控）。新頁面少量（標準編修/版本、合規比對、結構化匯入、影響分析、知識缺口/評測儀表板），多可沿用既有 CRUD 腳手架。（見 §十三）
  • 多版本／永遠用最新最正確來源？ → 以「文件級 metadata（effective_date / status / owner / 版本鏈）＋事件觸發增量重索引＋檢索時 metadata filter 只取現行版」解決，並補四維新鮮度評分。（見 §八）
  • 資料安全？ → 現有三支柱（檢索層權控、清洗遮罩、地端可切換）踩在市場主流；最大缺口是間接 prompt injection／內容投毒、embedding 前遮罩落實、稽核鏈路完整性。（見 §十）

一句話結論

把系統定位為「面向合規管理的知識平臺」，但務實地走「持續監控＋自動比對＋人工複核」的半自動路線，而非「全自動合規大腦」；底層以可組態知識型態平台承接合規與其他客戶，才能兼顧痛點命中與規模化。

二、重新框定：RAG 是地基，不是產品

2.1 普通 RAG 管線（客戶已能理解的基礎）

企業文件解析→切分成小段(chunk)→轉向量存入向量庫；使用者提問時先檢索相關片段，再把片段交給大模型生成回答。這是「企業自建知識庫」的基礎做法，本系統已完整具備（且優於基本款：混合檢索＋兩段式信心門檻＋帶出處）。

2.2 為何在合規場景不足

單純檢索問答在合規場景會遇到三個結構性問題：

  • 文件量大且互相引用：一份標準常引用其他標準/條款，答案需沿「引用鏈」判斷，扁平切塊會切斷關聯（呼應 §九 GraphRAG）。ISO/IEC 明言標準「互相關聯、構成必須維持完整性的系統」（ISO/IEC Directives）。
  • 版本持續更新：法規/標準會改版，答案必須引用「當時有效版本」；快照式索引易回舊版或草稿（見 §八）。
  • 容錯度極低：合規引用錯一個公差值/條款即為實質錯誤，需可溯源、可稽核、可人工複核，而非「檢索分數高就好」——分數高 ≠ 來源正確（Production RAG 2025）。

結論：合規場景要的不是更強的搜尋，而是「結構化理解＋版本治理＋溯源＋比對＋人工複核」——這需要在 RAG 地基上再加 AI Agent 與治理層（§六、§七）。

3.3 規模化瓶頸

  • 向量以 byte[]（float32×1024）存於 SQLite/SQL Server，檢索為應用層餘弦比對，無 Faiss/Milvus/pgvector、無倒排索引與查詢快取；數萬文件規模下延遲與成本是風險。
  • 落差提醒：03、04 原規劃 PostgreSQL＋pgvector，實作採 SQLite/SQL Server byte[]＋應用層餘弦；向量庫升級應列中期。

  • Agentic RAG / actions：Gartner 預測 2026 年底 40% 企業應用內建 task-specific agents（2025 <5%）（Gartner PR，analyst-cited）。
  • 知識新鮮度/驗證：核心指標 staleness gap；Gartner APT（Accurate/Pertinent/Trusted）標準，警示 ROT 內容（Atlan）。

  • 權限感知檢索：「安全邊界應在向量層而非應用層」（TianPan）。→ 我們正是如此，是護城河。
  • 知識庫作為 Agent 記憶/工具底座：KB 讓無狀態 agent 重建脈絡並以準確標準約束幻覺（KMSlh）。
  • 地端/資料主權：2025 Q2 企業 AI 硬體支出年增 166%（AI Magazine，analyst-cited）。→ 我們踩在主流訊號上。

六、合規知識平臺定位的誠實評估

待評估的定位宣言：「該企業級知識庫系統的定位，不是簡單問答工具，而是面向企業合規管理的知識平臺。系統可識別文件狀態、追蹤法規版本、理解表格語意、建立知識路徑，並提供完整的原文溯源與可解析答案。」

這句話方向正確、但六個要素的可行性與 ROI 差異很大。逐項誠實拆解（可行性／落地難度／是否真需求／成本回收）：

要素可行性落地難度是否客戶真需求成本/回收判斷定調
識別文件狀態（草稿/現行/汰換）高低（metadata+狀態機）高（合規必須）低成本高回收✅ 可落地，優先做
追蹤法規版本（版本鏈/生效日/變更）中高中（VersionRAG 式版本感知）高中成本高回收✅ 可落地，旗艦價值
理解表格語意分裂高高（公差/允收表）抽取可用；理解/彙總需專門管線且複雜表仍有殘餘錯誤⚠️ 限定承諾（見下）
建立知識路徑（關聯/引用鏈）中中高（GraphRAG/知識圖）高（標準互引）中高成本、差異化高⚠️ 值得投資，先低成本試點
原文溯源高低（我們已有帶出處）高低成本高回收✅ 已具備，強化到儲存格/條款級
可解析答案（可稽核推理）中高中高中成本高回收✅ 可落地（reasoning path/引用）

「理解表格語意」需特別誠實：表格抽取結構在 2024–2026 已成熟（Docling/TableFormer 複雜階層表達約 97.9% cell accuracy，Docling；合併儲存格需 HTML 表示，Azure DI）；但表格語意理解與數值推理（跨欄/跨頁/彙總）在純向量 RAG 下常失敗，需「結構化表示＋text-to-SQL/程式化判斷」專門管線（TableRAG, EMNLP 2025、TabRAG）。複雜合併/跨頁表在合規場景仍有殘餘錯誤率、需人工複核（Upstage 失敗深析、製藥 RAG 效能）。措辭建議：宣言宜寫「保留表格結構並支援結構化查詢」，避免暗示「對任意複雜合規表都能自動免核地正確彙總」——後者以現行成熟度不成立。

真的是客戶要的嗎？還是空泛口號？

  • 不是空泛口號的部分：識別文件狀態、追蹤法規版本、原文溯源、可解析答案——這四項可落地、成本回收好、且直接解「版本更新導致遺漏/不透明」的痛點，是真需求。
  • 是「口號風險」的部分：若把定位承諾成「全自動合規大腦」「任意複雜表格都能自動判讀」「零人工的合規保證」——以現行技術成熟度做不到，且投入極高、回收有限（見 §七 ROI 風險）。
  • 落地優先序建議：先做 ①文件狀態＋版本追蹤＋溯源（低成本高回收、旗艦價值）→ 再做 ②知識路徑/引用鏈（低成本試點 LazyGraphRAG）→ ③表格結構化查詢（限定承諾、含人工複核）→ 最後才談自動比對 agent。務實定位：面向合規的「半自動、可稽核、人在迴路」知識平臺，而非全自動合規大腦。

七、AI Agent 為合規帶來的功能（真需求 vs 過度包裝）

7.1 加 AI Agent 後能多做什麼（客戶會想要的）

純 RAG 只做「檢索＋問答」；合規 agent 疊加多步流程、狀態追蹤、跨文件比對、任務派工：

  • 法規版本追蹤＋更新影響分析：監控來源、比對新舊版 redline、依業務線摘要影響、開出帶負責人/期限的補救任務（Regology Regulatory Change Agent）。
  • 對映內規＋gap analysis：把新法規自動連到既有政策/控制，指出哪些內部文件要改、哪裡有缺口（ComplianceNLP（KG-augmented RAG））。
  • 合規檢查/自動比對：拿設計/合約/流程比對標準，列出不符合項（對應型錄 09 情境 1 審圖、4 規範查詢、20 合約審查、21 法規遵循；能力包①⑤）。
  • cross-reference（標準互引解析）：這是市場最弱環節，多為研究前沿（VersionRAG、ComplianceNLP），也最能形成差異化。
  • 多步推理＋human-in-the-loop＋稽核軌跡：每個 agent 動作留 immutable log 打包成可供內稽/監理的證據束（digiqt）。

7.2 真需求還是口號？（誠實的 ROI 警示）

  • 需求是真的：Gartner 預測 2025 年 >50% 大型企業用 AI/ML 做持續法規合規檢查（2021 <10%），反映從「查得到」轉向「持續監控＋自動比對」（A-Team，analyst-cited）。
  • 但 ROI 是硬傷：Gartner 預測 >40% agentic AI 專案 2027 底被取消，原因是成本攀升、價值不明、風控不足；並直指「agent washing」過度包裝（Gartner 2025-06-25，analyst-cited）。另有二手轉引稱 89% AI agent pilot 從未規模化。
  • 廠商自陳準確率須存疑：AI-native GRC 宣稱新法規對映控制準確率 92–96% vs 舊規則 71–78%（AuditBoard）——為廠商論述、非獨立驗證。
  • 法律/合規界共識：人工複核不可省，AI 輸出天花板鎖在「輔助」而非「取代」（LegalOn、Harvey）。

判讀：安全的產品定位是「持續監控＋自動比對＋人工複核」的半自動流程，不是「全自動合規大腦」。承諾自主，極易踩進 Gartner 那 40% 取消率。

八、客戶 A：設計標準（可迭代）＋ 時效性與最新來源保證

8.1 真正的 Jobs-to-be-Done（假設）

把設計結構標準當活的規範經營：逐條(clause-level)管理、迭代改版並保留歷史（知道現行版/生效日/改了什麼）、審查核可、最終能拿新設計比對標準列出不符合項。

8.2 市場怎麼做（關鍵能力）

  • 需求/規範管理原生強者：Jama Connect（版本比對、基線 baseline、Live Traceability、Jama Connect Advisor 依 INCOSE/EARS 給品質分數，features、AI 方案）；IBM DOORS Next（基線＝唯讀組態凍結已核可狀態、artifact 級 audit history、明確 approval points，baselines）。
  • Confluence：原生僅頁面版本＋content status，正規受控需 App 補（版本控制）。
  • docs-as-code / ADR：ADR 為 immutable、只改 status（如 superseded）故不過時（ADR、Log4brains）。
  • AI 合規比對已落地/近落地：法務（Spellbook）、工程/建築 ACC（把法規轉機器可執行邏輯，ScienceDirect），但多為輔助人工、需複核。

8.3 時效性與「永遠用最新最正確來源」（回應你的問題）

系統運行後原始資料不斷迭代更新，要確保知識庫用最新且經核可的版本，市場做法（皆附引用）：

  • 文件級 metadata 為一等公民：effective_date / status（draft/current/superseded）/ owner / 版本鏈；檢索時一律套 metadata filter 只取現行版或某 as-of 時點版——同時解決「多版本」與「排除草稿/過時」（VersionRAG、Salesforce+RAG）。
  • 事件觸發增量重索引＋失效標記：由文件變更事件觸發，只重嵌受影響的 5–20 個 chunk 並失效其快取，秒級完成；1% 文件/日變動時比全量重建省約 100×（Incremental Updates in RAG、Update RAG Without Rebuilding）。
  • 四維新鮮度/信任評分：Freshness（最後確認為現行的時間）、Ownership（有無 owner）、Lineage integrity（可否溯回權威來源）、Canonical alignment（與權威定義是否一致）；避免「檢索分數高但庫本身過時」的陷阱（Production RAG 2025）。
  • 標準互引的版本連動（差異化機會）：借用 ISO/IEC 的 dated vs undated 引用語意——dated 只該版適用、被引文件改版須逐一審查影響；undated 自動取最新版（CEN BOSS、ISO/IEC Directives）。自動化「引用鏈影響掃描」市場最不成熟，若場景引用密集可自建為護城河。

8.4 建議：改架構？加頁面？

  • 資料模型（改，需雙 migration）：WikiPage/標準實體加版本鏈與生效狀態（Version、EffectiveStatus、SupersededByPageId、BaselineId、Owner、LastReviewedAt、變更摘要）；或新增「標準/規範」知識型態專用實體。
  • 檢索（改）：加入 metadata filter 只取現行/as-of 版；文件變更觸發增量重索引與快取失效。
  • 新頁面：標準/規範編修與版本頁（版本 diff、生效狀態、審核）；（中期）合規比對頁（上傳設計→對現行標準逐條比對→列疑慮與依據，重用型錄情境 1/20）。
  • 可重用：蒸餾、審核流程、信心門檻、LlmPromptResolver 四層提示詞、團隊權控、內容線上編修。

九、客戶 B：系統規格 + DB 結構

9.1 JTBD（假設）

不只是搜尋規格，而是：影響分析（改一個 schema 欄位/規格會影響哪些下游）、新人上手問答（可溯源）、text-to-SQL、規格追溯（需求↔設計↔schema↔程式碼）。

9.2 市場怎麼做

  • 程式碼/服務知識：Sourcegraph 以 SCIP 建語意索引跨 repo 定義/引用、願景「程式碼宇宙全域知識圖」（SCIP、Cody enterprise）；Cortex/Backstage 把「程式碼＋服務元資料＋文件」統一成可搜尋 catalog（Backstage 概覽）。
  • DB schema 文件化與問答：dbt docs 自動產 lineage（dbt docs）；data catalog（Atlan/Collibra/DataHub/Alation）皆有 column-level lineage＋impact analysis（Atlan lineage）。
  • Text-to-SQL 成熟度（現實）：商用（Snowflake Cortex Analyst 靠語意模型宣稱 90%+，Cortex Analyst）；但開放 benchmark BIRD 最佳僅約 82%、人類 92.96%（BIRD）——語意層/schema 註解是準確率關鍵，且需人工複核。
  • GraphRAG 的角色：向量 RAG 對關係型查詢弱，共識是混合式——向量處理細節/單跳，知識圖處理關係/多跳/影響分析與全域彙整，並提供可稽核 reasoning path（知識圖 vs RAG、Graph RAG）；需求→程式碼可追溯性結合 RAG＋KG 在汽車業案例達高準確率（Springer）。

9.3 現有能力 / 缺口 / 建議

  • 已能：蒸餾的 [[wiki-links]] 本質是知識圖雛形，天生適合表達 schema/規格實體與關聯；問答帶出處、團隊權控已具備。
  • 硬缺口：結構化匯入（schema/DDL/規格→實體＋關係，而非扁平 chunk）；圖譜式檢索/關聯查詢。
  • 建議：把隱式 [[links]] 提升為顯式關聯邊（實體節點＋帶型別關係，需雙 migration）；檢索加圖遍歷第三路徑，先用 LazyGraphRAG 查詢時動態建圖低成本試點（LazyGraphRAG）；新增結構化匯入頁與影響分析查詢頁（帶 reasoning path）。text-to-SQL 列長期選配（上限約 82%、需語意層與複核）。

十、資料安全設計改善建議

對照現況（檢索層團隊權控、清洗階段 PII 遮罩、NLog 稽核、地端可切換）——這三支柱正好命中 2025 業界最強調的重點。以下依缺口優先序，並對應 OWASP GenAI/LLM Top 10 2025。

  1. 間接 prompt injection／內容投毒防護（最高優先，目前最可能的空白）：惡意指令可藏在被檢索的文件裡（poisoned PDF/工單/爬取頁），因組織「預設信任自家知識庫」特別有效（OWASP LLM01、Lakera 間接注入）；USENIX Security 2025 指僅 5 份構造文件即可 >90% 操縱回應（LLM04/LLM08）。建議：檢索內容與系統指令做信任邊界隔離（delimiter/角色分離）、對 retrieved chunk 做注入偵測、ingestion 端內容來源信任分級與投毒偵測。
  2. 確認遮罩在 embedding 之前：避免原始 PII 進入向量，阻斷 embedding inversion（向量外洩可重建 50–70% 原文，Repello）。
  3. 權控細緻度升級：確認為 chunk 層 ACL 而非只文件層；評估回應層 PEP（Policy Enforcement Point）再驗證以防「跨文件語意聚合」推敲敏感資訊（arXiv PEP）。
  4. 向量儲存的租戶/團隊隔離＋加密/金鑰管理：at-rest AES-256、傳輸 TLS、CMK、停用向量匯出、查詢速率限制（Kiteworks）。
  5. 稽核鏈路補全：確保「誰問了什麼→命中哪些來源→回了什麼」可完整重建並匯出、含人為覆寫事件，且 log 本身不落敏感原文，對齊 SOC2/ISO 27001/GDPR（Gruve、EDPB 2025 特別點名 RAG）。

十一、知識重新組織的建議

回應「企業知識庫的核心不只是把文件集中管理，而是把分散在不同系統、不同流程、不同載體中的知識重新組織起來」。

這句話正確，而且市場主流做法不是把知識「搬進單一庫」，而是加一層語意/圖層把分散知識連起來：

  • Canonical 知識層＋知識圖：把資料、業務知識、術語語意統一成 Enterprise Data Graph，給人與 agent 可信 context；實體掛 canonical ID 與權限、查詢時強制存取控制（Atlan）——與本系統團隊權控不變量高度呼應。
  • Federated Knowledge Graph（2025 主流論述）：接受「語意是在地的」，各業務域自建自管本地圖，再由全域語意層解決跨域不一致，保留自治又連成整體（Pistoia Alliance、seddryck）。
  • 連接器（connectors）：用連接器把分散在不同系統的 metadata 串成語意 overlay，而非強制資料搬遷。

對本系統的建議：

  • 短期：以顯式集合(Collection)＋蒸餾 Wiki 知識圖作為「重組層」的第一步（我們已有蒸餾與 [[links]]，是天然基礎）。
  • 中期：把 [[links]] 升為顯式關聯邊，形成可導覽的知識圖（呼應 §九）。
  • 長期：加資料連接器把散落在檔案伺服器/IM/DB 的知識串入（不必都搬進單庫），對齊 federated 思路與市場入門門檻。

十二、產品策略三路線比較與推薦

路線做法適用成本對合規/A/B 契合跨客戶複用
A｜可組態知識型態平台抽「知識型態」設定：匯入模式×結構層級×生命週期×檢索策略×應用模板服務「每客戶都不同」中（一次性平台投資）高（各為型態實例）最高
B｜垂直情境模組為審圖/規格庫/合規各建專屬模組單一大客戶願付費高（每情境重寫）高（但只對該情境）低
C｜外溢應用以 KB 為底座長技能/Agent/行動差異化與變現中高間接（放大價值）高

推薦：合規旗艦 + 平台底座（A 為主軸、C 為變現、B 按需）

「知識型態（Knowledge Type）」抽象——把目前寫死的閉環參數化，一個型態＝一組設定：

  • 匯入模式：檔案匯入 / 直接編修撰寫 / 結構化解析（schema、規格、標準）。
  • 結構層級：扁平 chunk / 條款級 / 實體-關係圖。
  • 生命週期：快照 / 版本化＋基線＋生效狀態＋審核（合規必需）。
  • 檢索策略：混合檢索 / 加圖遍歷 / metadata filter 取現行版。
  • 應用模板：問答 / 合規比對 / 影響分析。

這一層延伸系統既有設計思維（CleaningProfile、四層提示詞、供應商可切換、通用佇列管線——皆「以設定驅動、不改碼」）。合規＝「版本化標準＋比對」型態；客戶 B＝「結構化/圖譜規格」型態。驗證後型錄 09 的 28 情境多能用型態＋模板拼出，不必逐一重寫。垂直模組僅在單一大客戶願付費時做（否則不可規模化）。

十五、風險與開放問題

  • 待向客戶確認 JTBD：客戶 A/B 與合規需求為本文假設（客戶自己也尚未完全講清）；動工前應以本文情境向客戶驗證，避免過度設計。
  • 合規平台「口號化 / 高成本低回收」風險（最需警惕）：Gartner 指 >40% agentic 專案 2027 底取消、多缺 ROI 並有 agent washing（Gartner）。對策：定位「半自動＋人在迴路」，避免承諾自主；先做低成本高回收要素（狀態/版本/溯源），再逐步加 agent。
  • 表格語意「過度承諾」風險：複雜合併/跨頁合規表仍有殘餘錯誤率，須人工複核關卡；宣言措辭限定為「保留結構＋結構化查詢」。
  • 多框架重工與規則維護長尾成本：合規若把每框架當獨立工作流會爆炸（CyberSaint）；規則/prompt 變更需變更控制與回測。
  • GraphRAG 過度設計風險：03 已列「高關聯需求才需要」；以 LazyGraphRAG 低成本試點先驗證價值。
  • text-to-SQL 報酬風險：開放 benchmark 上限約 82%、需語意層與複核。
  • 向量庫遷移成本：從 byte[]＋應用層餘弦遷到 pgvector/Qdrant 需資料搬遷與雙 DB 拓樸決策。
  • 地端 LLM/Embedding 品質與算力：既有已知風險（05 風險清單），影響地端型客戶的合規比對/圖譜/表格品質。
  • 引用數字時效：analyst-cited 與廠商自陳數字（如 92–96% 準確率、40% 取消率、166% 硬體支出）正式對客戶引用前建議查證一手來源。

本文為活文件，隨客戶需求驗證與平台能力演進持續更新。相關後續：知識型態抽象與版本化/時效性設計、合規比對與安全強化建議另立架構規格文件；各擴展可各自展開為 docs/prd/ 功能 PRD。
