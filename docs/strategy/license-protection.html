1. 文件定位與商業背景

1.1 定位

本文承接 docs/strategy/02-商業價值與行銷策略.md（地端授權年費＋導入服務＋維運訂閱；雲端依使用者數／知識量分級）與 docs/strategy/05-待釐清問題與技術風險清單.md（「地端授權 vs 雲端訂閱的計費單位與級距」列為待釐清）。本文把「授權計費維度」落地為可簽發、可驗證、可執法的技術機制。

1.2 商業目標

  • 提供 6 個月免費試用，讓客戶把知識灌入系統、累積資料黏著度（switching cost）。
  • 試用到期後轉付費；廠商須能以「離線簽發授權碼」授予／延長使用權，並精細控制功能模組、用量、帳號數。
  • 授權過期或無效 → 完全阻擋登入，除輸入新授權碼外不可操作。

1.3 部署前提與強度定位

  • 地端封閉網路，完全離線為主；不得依賴外部時間源或線上啟用伺服器。
  • 客戶端原始碼／二進位在客戶掌握中 → 本機制目標為 中等強度：提高破解成本、嚇阻一般客戶違約，而非對抗專業逆向。此邊界於第 13 章誠實列明。

2. 整體架構與角色

2.1 角色

  • 客戶端（知識庫主機）：執行中的 Blazor Server / ASP.NET Core .NET 10 應用。內嵌「廠商公鑰」，負責產生機器指紋、驗證授權碼、執法阻擋。
  • 廠商端（簽發系統）：新增獨立 console 專案 KnowledgeExtraction.LicenseTool（OutputType=Exe，不進主部署）。保管私鑰、依客戶購買狀態簽發授權碼。
  • 離線交換媒介：純文字字串（機器指紋請求字串、授權碼），可經 email／隨身碟傳遞。

2.2 離線啟用時序

3. 機器指紋（Host ID）設計

3.1 目的

把授權碼「綁定」到特定部署主機，防止同一份授權碼被複製到多台機器。指紋只用於綁定與比對，不含任何個資或機敏資料（法遵考量見第 13 章）。

3.2 採集特徵（Windows 優先；容錯設計）

逐項採集下列硬體／OS 特徵，各自雜湊為子指紋：

代號特徵取得方式穩定度
F1Windows MachineGuidRegistry HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid高（重灌 OS 才變）
F2主機名稱 MachineNameEnvironment.MachineName中
F3系統磁碟序號WMI Win32_DiskDrive.SerialNumber（主碟）高
F4主網卡 MACNetworkInterface 取實體卡、排除虛擬／Loopback中（VM 遷移可能變）
F5CPU 識別WMI Win32_Processor.ProcessorId高
F6主機板／BIOS 序號WMI Win32_BaseBoard.SerialNumber高

3.3 組合與容錯比對

  • 每個子指紋以 SHA-256 各自雜湊，組成「子指紋集合」。授權碼內存放的是簽發當時採集到的子指紋集合雜湊值（不存原始值）。
  • 容錯比對（多數符合即通過）：啟用時記錄 N 個子指紋；日後驗證時，只要當前主機與已記錄集合 符合 ≥ 門檻（建議 6 取 4） 即視為同一主機。寬容單一零件更換／VM 遷移，降低誤殺。
  • 對外顯示的「Host ID」為整體集合再雜湊後的短碼（Base32，便於人工朗讀／核對）。

3.4 跨平台考量

目前僅 Windows；Linux 部署時 F1／F3／F6 取得方式不同（/etc/machine-id、lsblk、DMI）。以介面 IHostFingerprintProvider 抽象，先實作 WindowsHostFingerprintProvider，Linux 留待第 14 章待決。

3.5 程式落點

  • 純採集邏輯（跨專案共用、無 DB 相依）→ KnowledgeExtraction.Share/Helpers（如 HostFingerprintHelper），比照現有 MagicObjectHelper／RuntimeEnvironmentInfo。
  • 需注入設定／記錄的封裝 → KnowledgeExtraction.Business/Services/DataAccess。
  • 執行期快取 → SystemStartupState（Singleton；避免每次請求重跑 WMI）。

4. 金鑰體系與授權碼格式

4.1 金鑰體系（非對稱）

  • 沿用 Web/Auth/JwtTokenService.cs 的「簽章 + TokenValidationParameters 驗證」骨架思路，但因 JWT 目前用對稱 HMAC（SymmetricSecurityKey），授權碼必須改用非對稱：廠商私鑰簽、客戶端內嵌公鑰驗，避免客戶用同一把金鑰偽造授權碼。
  • Codebase 目前無 RSA／ECDsa／X509 用法，需新引入 System.Security.Cryptography。
  • 演算法建議：ECDSA P-256（或 Ed25519）。理由：金鑰／簽章短，適合離線人工傳遞的字串；P-256 為 .NET 內建 ECDsa 直接支援。備選 RSA-2048（相容性最廣但簽章較長）。
  • 公鑰內嵌：以常數／內嵌資源方式編進客戶端組件（並可放一份於 LicenseSettings），避免單純替換設定檔即換公鑰。私鑰僅存於廠商端 LicenseTool（離線保管、不進版控、不進部署）。

4.2 授權碼封裝格式（類 JWT，離線可驗）

Base64Url(header).Base64Url(payload).Base64Url(signature)，三段以 . 連接。header 標示演算法與授權碼版本。

4.3 Payload 欄位

欄位說明
ver授權碼格式版本（供日後演進／金鑰輪替）
cust客戶識別（公司代號／合約號）
fp機器指紋子指紋集合雜湊（多值，供容錯比對）

exp到期日（UTC，日級）

4.4 請求字串格式

Base64Url(JSON)，內容：機器指紋子指紋集合、客戶自填識別資訊、客戶端版本（讀自 SystemSettings:SystemInformation:SystemVersion）、產生時間。供 LicenseTool 可讀並回填 fp／cust。

4.5 請求字串是否加密

釐清：請求字串本身非機密（只是指紋與客戶名），真正需要防偽的是「授權碼」——靠廠商私鑰簽章即可，客戶無法偽造。

  • 最低要求：請求字串至少加 CRC／雜湊校驗，避免人工複製漏字導致簽出錯誤指紋。
  • 可選加強：以廠商公鑰加密請求字串（防止傳遞途中被竄改指紋、把授權綁到攻擊者主機）。取捨：加密會讓字串變長、且客戶端也要內嵌加密邏輯，對「中等強度」屬過度設計。建議 MVP 僅做校驗，不加密；日後如需再升級。

5.3 DB＋檔案雙寫防單點刪除

DB 之外，另在檔案系統寫一份鏡像檔（落點：SystemSettings.ExternalFileSystem.DatabasePath 同目錄，即 C:\temp\KnowledgeExtraction\*，複用 SystemHealthService.DirectoryIsWritable 探測可寫）。內容為簽章保護的 TrialStartedAt 與 MonotonicMaxSeenUtc。啟動時DB 與檔案取較嚴格值（試用起算取較早、時鐘取較大），任一被刪即以另一方補回，防止「刪 DB 重裝重刷試用」。

5.4 雙 migration（CLAUDE.md 不變量）

於 KnowledgeExtraction.AccessDatas（SQLite）與 KnowledgeExtraction.AccessDatas.SqlServerMigrations（SqlServer）兩個專案各產生一支 migration。SystemSettings.GetDatabaseProvider() 決定 provider；BackendDBContext 需加 DbSet<LicenseState>。

6. 試用期機制

  • 起算點：首次啟動時若 LicenseState 無資料且無授權碼 → 寫入 TrialStartedAt = now、Status = Trial，同時寫檔案鏡像。
  • 期限：TrialStartedAt + 6 個月（實際天數列入設定 LicenseSettings.TrialDays，預設 183；最終值第 14 章待決）。
  • 防繞過：DB＋檔案雙寫；且以單調時鐘偵測時間回撥（把系統時間調回過去以延長試用會被偵測，見第 8 章）。
  • 狀態轉換：Trial →（輸入有效授權碼）→ Activated；Trial →（超過試用天數）→ Expired（鎖定）；Activated →（超過 exp）→ Expired。
  • 到期一律完全阻擋登入。

7. 分散式授權檢查設計（核心防篡改）

7.1 原則

不提供單一 IsLicensed() 函式。授權判定拆成多個獨立檢查點，嵌入不同層與正常商業邏輯中，各點自帶「驗簽＋讀狀態＋單調時鐘」的小段判斷，任一發現異常即進入鎖定。目的：改一處無法解鎖全系統。

7.2 檢查點佈署

#位置（真實檔案）手法

7.3 降低「一次全找到」

  • 各檢查點命名不含 license 字樣（如混用 EnvironmentGate、RuntimeGuard、FeatureAvailability、UsageQuota 等中性名）。
  • 判斷邏輯內聯進既有方法，不集中成單一 helper。
  • 驗簽用的公鑰以多來源交叉（內嵌常數 + 設定），並以常數時間比對（複用 CryptographicOperations.FixedTimeEquals，同 McpAccessKeyService.FindEnabledMatchAsync）。
  • 可選：啟動期做輕量「程式碼完整性」自檢（關鍵組件雜湊比對），但明確標註此為嚇阻性、非防護性。

7.4 誠實邊界

中等強度無法防逆向工程、記憶體修改、重打包（原始碼在客戶手上）。本設計只提高破解成本與違約門檻。詳見第 13 章。

8. 時鐘防篡改（離線，單調遞增時鐘）

8.1 設計

  • 在 LicenseState.MonotonicMaxSeenUtc 記錄「曾見過的最大時間戳」，並鏡像至檔案。
  • 寫入時機：啟動時、定時（背景服務每 N 分鐘）、以及每次授權檢查點觸發時 → 若 now > MonotonicMaxSeenUtc 則更新為 now。
  • 回撥偵測：若 now < MonotonicMaxSeenUtc - 容忍值（如 5 分鐘 ClockSkew） → 判定時間被調回 → 標記 Status = Tampered。

8.2 反應策略

  • Tampered → 立即鎖定（導向 /license），或（較寬容選項）縮短寬限、要求重新啟用。建議 MVP 直接鎖定，客服可核發新授權碼解除。
  • 到期判斷同時參考 now 與 MonotonicMaxSeenUtc：取兩者較大者與 exp 比較，確保「調回時間」無法延長使用。

9. 執法點與使用者流程

9.1 阻擋登入實作面

  • 新增 /license 啟用頁（Razor 元件，不套用需授權的 Layout，避免自我鎖死）。
  • middleware（檢查點 2）與 AuthenticationStateHelper.Check（檢查點 3）在未授權時一律導向 /license；白名單：/license、/Auths/Logout、/health/*、靜態資源。

9.2 管理員啟用流程

/license 頁提供：顯示「請求字串」（可複製）與 Host ID 短碼、貼上授權碼欄位、「啟用」按鈕。啟用時：公鑰驗簽 → 指紋容錯比對 → 寫入 LicenseState（DB＋檔案）→ 成功則解鎖。

9.3 授權資訊顯示

  • 授權管理頁（管理員可見）：剩餘天數、目前方案、各功能模組開關狀態、各項用量（現用量 / 上限，用量數字複用既有統計，如 context.KnowledgeSource.CountAsync、VectorEmbedding.CountAsync，見 SystemHealthService.CheckDatabaseStatsAsync）、帳號數 / 上限。
  • 健康檢查頁「授權狀態」項（第 9.4 章）。

9.4 健康檢查項

比照 SystemHealthService.CheckMcpServerAsync 新增 CheckLicenseAsync，用 CreateItem("授權狀態", "License", weight, status, evidence, failureMessage)：顯示狀態、到期日、剩餘天數、指紋是否吻合、時鐘是否異常。到期／tampered → Unhealthy；逼近到期 → Degraded。

10. 廠商端簽發系統（KnowledgeExtraction.LicenseTool）

10.1 專案

新增 console 專案 KnowledgeExtraction.LicenseTool（OutputType=Exe，不加入主部署、不進 Docker/發佈）。可參考 Share/Helpers 共用密碼學工具（簽章／Base64Url 封裝），與客戶端共用同一份 payload schema（放 Models 或 Share）。

10.2 流程

  1. 輸入請求字串 → 解碼／校驗 → 讀出指紋與客戶資訊。
  2. 操作者依客戶購買狀態設定授權維度（到期日、功能旗標、用量／帳號上限）。
  3. 用私鑰簽發授權碼 → 輸出字串。
  4. 記錄簽發歷史（MVP 可用本機 SQLite／CSV；欄位：客戶、指紋、方案、簽發時間、到期日、授權碼）。

10.3 私鑰保管

私鑰離線保管（加密檔／HSM／密碼管理器），絕不進版控與部署。金鑰輪替策略見第 13 章。

10.4 未來

可升級為網頁簽發後台（含客戶／合約管理、批次簽發、到期提醒）。第 14 章待決。

11. 商業模式建議

針對「地端知識庫 ＋ 6 個月試用轉付費」情境：

模式說明優點缺點
一次買斷（永久授權）一次付費永久使用客戶心理門檻低無持續營收；更新／維運難收費
純訂閱（年費）每年續費，過期停用營收可預期；本機制天然支援到期執法客戶對地端「還要每年付費」抗性
混合（授權年費＋維運訂閱）授權費涵蓋使用權，維運訂閱涵蓋更新／支援／模型調校兼顧持續營收與客戶接受度；對接 strategy 02需清楚切分「授權」與「維運」權益
用量分級依功能模組／用量／帳號數分級定價與本機制四維度天然對齊；可低價入門、隨用量升級需明確用量計量與升級流程

建議

採 混合模式：授權年費（依方案分級）＋ 維運/更新訂閱，並以本機制的四個維度作為分級槓桿：

  • 依功能模組：基礎版（文件轉文字＋RAG 問答）／進階版（加影音轉逐字稿、圖片辨識、知識頁審核）／旗艦版（加 MCP、統計報表）。
  • 依用量：知識來源／文件／向量筆數級距。
  • 依帳號數：席次分級。
  • 依期限：年約為主；6 個月試用到期後轉年約。

理由：地端客戶接受「年費＋維運」優於純訂閱的停用焦慮；四維度讓業務有充足的向上銷售（upsell）空間，且全部可由授權碼即時調整、無需改程式。定價數字列第 14 章待決。

12. 分階段實作路線圖（Phases）

每階段皆須遵守 CLAUDE.md 不變量：模型變更同時產生 SQLite 與 SqlServer 雙 migration；SystemSettings:SystemInformation:SystemVersion 版本號 +1（格式 x.y.z (yyyy/MM/dd)）；文件同步更新。

Phase 0：密碼學與設定基礎

  • 產出：LicenseSettings（內嵌公鑰、發行者、TrialDays、寬限天數、指紋門檻）註冊於 ServiceCollectionExtensions.AddConfiguredOptions；Share/Helpers 密碼學工具（ECDSA 簽/驗、Base64Url 封裝）；payload schema。
  • 驗收：單元測試「簽/驗」往返成立；錯誤簽章被拒。

Phase 1（MVP）：期限＋簽章驗證＋阻擋登入＋單一啟用頁

  • 產出：LicenseState 表＋雙 migration＋LicenseStateProvider；/license 啟用頁；middleware 閘（檢查點 2）＋AuthenticationStateHelper.Check 內聯（檢查點 3）；到期／無效完全阻擋。
  • 驗收：無授權→鎖定並導向 /license；貼上有效授權碼→解鎖；過期→再次鎖定。

Phase 2：功能模組旗標

  • 產出：FeatureFlags 解析；關鍵功能進入點（檢查點 5）與背景服務（檢查點 4）依旗標開關。
  • 驗收：關閉某模組→該功能與其背景服務停用、UI 提示。

Phase 3：用量與帳號上限

  • 產出：用量計量（複用既有 Count 查詢）；達上限阻擋新增；帳號數上限於建立使用者時檢查。
  • 驗收：逼近／達上限的阻擋與提示正確。

Phase 4：機器指紋

  • 產出：IHostFingerprintProvider ＋ Windows 實作；容錯比對；啟用時綁定、驗證時比對；SystemStartupState 快取。
  • 驗收：換單一零件仍通過；整機更換則需重新啟用。

Phase 5：單調時鐘防回撥

  • 產出：MonotonicMaxSeenUtc 雙寫；回撥偵測→Tampered；到期判斷取 max(now, seen)。
  • 驗收：調回系統時間→偵測並鎖定。

Phase 6：分散檢查強化

  • 產出：檢查點 1（需新建啟動閘，原 StartupSafetyValidator 已於 1.0.68 移除）、更多內聯點、中性命名、輕量完整性自檢。
  • 驗收：移除單一檢查點無法整體解鎖。

Phase 7：廠商簽發工具

  • 產出：KnowledgeExtraction.LicenseTool console；簽發歷史；私鑰保管流程。
  • 驗收：由請求字串簽出可被客戶端接受的授權碼。

Phase 8：健康項與管理頁

  • 產出：SystemHealthService 授權健康項；授權管理頁（剩餘天數／用量／功能狀態）。
  • 驗收：健康頁與管理頁正確反映授權狀態。

13. 風險、限制與誠實邊界

  • 能擋：一般客戶「試用到期後繼續用」「複製到多台機器」「調系統時間延長試用」「刪 DB 重刷試用」「改單一設定換公鑰」。
  • 擋不了：原始碼／二進位在客戶手上 → 專業者可逆向、記憶體修改、移除檢查點、重打包。本機制為中等強度嚇阻，非強保護。
  • 誤殺與客服：硬體更換／VM 遷移可能使指紋不符 → 靠「多數符合」寬容；仍不符時走客服重新啟用（重出請求字串→簽新授權碼）。時鐘 Tampered 亦以客服核發新碼解除。
  • 金鑰風險：私鑰外洩＝可偽造任意授權碼。對策：私鑰離線保管；payload 含 ver 支援金鑰輪替（新版客戶端內嵌新公鑰、舊碼設落日）；輪替需隨版本發佈。
  • 法遵／隱私：指紋僅雜湊硬體識別碼，不含個資；請求字串中客戶自填資訊由客戶掌控。文件應載明資料用途。

14. 待決問題清單

  1. 定價數字：各方案年費、維運訂閱比例、用量級距、席次定價。
  2. 試用天數最終值（183？）與到期寬限天數。
  3. 機器指紋最終採用哪幾項特徵、容錯門檻（6 取 4？）。
  4. 時鐘 Tampered 反應：直接鎖定 vs 縮短寬限。
  5. 簽發後台是否網頁化、是否納入客戶／合約管理。
  6. 跨平台 Linux 部署的指紋與檔案落點方案。
  7. 演算法最終選型：ECDSA P-256 vs Ed25519 vs RSA-2048。
  8. 請求字串是否加密（MVP 建議僅校驗）。
  9. 授權管理頁的權限範圍（僅 support／管理員帳號？）。
