1.2 治理欄位的一個缺口

WikiPage 的 Owner 與 ChangeSummary 可在知識頁治理對話窗手動編輯（UpdateGovernanceAsync(id, owner, changeSummary)，只有兩個參數）；但 LastReviewedAt 只在核可時自動寫入（WikiPageService.cs:441），沒有「重新確認仍有效」的專屬動作。

客戶問「怎麼標記我已經複查過了」時，誠實的答法是：目前沒有專屬按鈕，替代做法是把盤點結論寫進「本版變更摘要」。不要含糊帶過——這是客戶做知識治理時一定會碰到的。

二、第一次導入訪談清單（18 問）

第一次會議就要問到這 18 題。問不到的項目，後面一定會變成變更。

A. 知識邊界（決定團隊與權控，最高優先）

  1. 哪些內容絕對不能讓某些人看到？請具體到「哪一類文件、哪些人」。
  2. 客戶或外部人員會不會登入這套系統？（會＝團隊是資安紅線，驗收要加越權測試）
  3. 有沒有法規或客戶合約要求的資料隔離義務？
  4. 哪些內容其實可以公開給全公司？（這一題常被忽略，但它決定了多少內容可以不貼團隊）

B. 素材現況（決定工時與可行性）

  1. 現在的文件放在哪裡？共用磁碟、SharePoint、還是個人電腦？
  2. 同一份文件有幾個版本在流通？誰知道哪個是現行版？（第二種知識流失的探針）
  3. 有沒有會議錄音、訪談錄音？有多少？
  4. 有沒有紙本或掃描件？比例多少？
  5. 有沒有 CAD、圖檔、外文文件？（CAD 不支援，要先講）
  6. 最重要的知識，有沒有根本沒被記錄下來的？（第一種流失。答「有」就要規劃訪談）

C. 使用者與組織（決定導入成敗）

  1. 誰會是知識庫管理員？他有多少工時？
  2. 每個部門的知識窗口是誰？他的主管同意這件事佔用工時嗎？
  3. 使用者的 IT 熟悉度？（決定要不要做操作訓練）
  4. 有沒有人會抗拒？（例如「我的經驗是我的價值」）

D. 驗收期待（決定會不會被客訴）

  1. 客戶心中「成功」的定義是什麼？請他講一個具體場景。
  2. 他期待的準確率是多少？他知道這個數字怎麼量嗎？（這一題不問清楚，驗收一定吵架）
  3. 有沒有既有系統需要整合？（ERP／PLM／MES／工單）
  4. 有沒有 LLM 金鑰？可以用雲端 LLM 嗎，還是必須地端？（見 §三 Q3）

兩題必問：第 6 題（版本混亂＝第二種流失，知識庫會放大它）與第 16 題（準確率期待＝驗收糾紛的根源）。

三、客戶會問的 15 個問題與誠實答法

原則：寧可當場說「做不到」，不要事後解釋。

Q1「準確率多少？」 → 要分兩件事。對象正確率（有沒有找到正確那個型號／客戶的資料）：用「限定知識來源」硬篩選是 100%，因為那是資料庫層的過濾，不在範圍內的根本不進候選。不篩選、多型號混在一起時，可能低到 20～50%。段落正確率（有沒有找到答得了這題的那一段）：取決於文件品質，業界對整理過的語料常見驗收區間是 Recall@10 落在 0.7～0.9。這些是推論值，你的真實數字要用系統內建的檢索品質評測跑出來。 詳見 §6。

Q2「會不會亂講？」 → 有兩層保護。第一層是兩段式信心門檻：最高分低於下限時，程式層直接回「查無相關依據」，不會呼叫 AI——這不依賴 AI 自律。第二層是每個答案都附出處，可以點開看原始段落。但這兩層擋不住「你匯入了錯的資料」——匯入過期的規範，它會很有自信地引用過期的規範。

Q3「資料會不會外流？」 → 取決於兩件事，要分開講。(a) 部署：系統可以完全裝在你們的機器上。(b) LLM：如果用雲端 LLM，內容會送到該服務商；系統支援切換地端模型（見 LLM 雲端地端切換），代價是效果與速度。⚠️ 另外要主動說明：使用 MCP 對外整合時，問句與上下文全文會落地儲存（見 MCP 服務使用說明書 §七）。

Q4「跟直接用 ChatGPT 差在哪？」 → 三件事：(a) 它查的是你們的私有資料；(b) 每個答案都有出處可以驗證；(c) 有權控——採購的底價業務問不到。通用聊天工具三件都沒有。

Q5「要多久才看到效果？」 → 一個月，一個部門。全公司同時上線的導入基本上都失敗。第一個月的驗收標準不是指標，是有一個部門的人願意主動用它。

Q6「需要幾個人維護？」 → 1～2 位知識庫管理員（不需要全職，但需要固定工時）＋ 每部門 1 位知識窗口。如果答案是「大家一起維護」，等於沒有人，六個月後會變成另一個共用磁碟。

Q7「可以取代 ERP／PLM 嗎？」 → 不能，而且不該。它不做即時數值查詢、不做統計計算、不做交易操作。它是知識層，不是系統的替代品。整合是後續選項。

Q8「我們有五千份文件，全部丟進去要多久？」 → 技術上不慢，但不要這樣做。三個理由：(a) 未整理的內容會稀釋有用的內容，讓檢索品質下降；(b) 沒有人審核得完；(c) 而且一盒也不能塞太多——清洗的去重與遮罩會把整份彙整內容重新輸出一遍，超過模型輸出上限時會被靜默截斷（狀態仍是「已清洗」卻少了一大段，沒有任何提示，S3）。建議第一批 20～30 份、一盒 5～15 個成員、全部人工看過、驗收通過再擴大。這一題要主動勸阻，不要迎合。 分盒與拆檔的完整方法給客戶看 知識來源分盒與規模上限指南。

Q9「支援哪些格式？」 → 常見 Office、PDF、圖片、音訊、影片都支援，格式與大小上限見 資料匯入指南 與 容量邊界與限制。⚠️ CAD 原生檔不解析，要先講清楚。PDF 走 LLM 萃取，需要金鑰。

Q10「沒有 LLM 金鑰能用嗎？」 → 可以匯入、聚合、清洗（降級：只做彙整與繁體化，跳過五段強化），但清洗品質評測完全無法執行、蒸餾也一定要金鑰。也就是說：無金鑰環境只能走到流程的一半。要完整驗收，金鑰是前提。

Q11「客戶 A 看不到客戶 B，怎麼保證？」 → 團隊權控在候選階段就過濾（不是事後遮起來），沒有權限的資料根本不會進入候選集。而且系統可以量給你看：建越權測試題，模擬該客戶身分去問別家的事，指標必須是 0 洩漏。這是可驗證的，不是口頭保證——建議把它寫進驗收條件。

Q12「上線之後可以改分類名稱嗎？」 → 不建議，代價很高。 分類與團隊是以名稱字串存在每一筆紀錄上，改主檔不會回頭改既有紀錄。所以命名要在匯入前定案——這也是我們會先給你們一份命名規範的原因。

Q13「AI 答錯了誰負責？」 → 答案是內部參考，不是對外承諾。每個答案都有出處，關鍵決策要點開出處核對原始文件。對客戶的承諾（規格、交期）一律走既有簽核流程。這一句建議寫進使用規範，讓全體使用者知道。

Q14「可以問它幫我算嗎？（成本、公差疊加、統計）」 → 不行。語言模型的算術不可靠，這套系統也不是設計來做計算的。它可以告訴你「計算的依據與規則在哪份文件」，計算本身用專業工具。

Q15「上線後要調參數嗎？誰調？」 → 檢索側有 7 個參數可以在診斷頁熱套用、免重啟；但清洗的信心門檻不行，那個要改設定檔並重啟。原則是：先把內容與命名做對，再談調參數。而且每次調整前後都要跑一次評測基線比對，否則你不知道是變好還是變壞。

五、踩雷急救手冊

症狀根因怎麼修修完驗什麼
「分數突然變差」客戶改了知識來源盒子標題（N4）把評測樣本的「期望命中來源標題」改成新標題（複製貼上），或改回原標題重跑評測，與舊基線比對
「改了提示詞沒效果」名稱沒有逐字相符（N5），或被更高層蓋掉從 LlmPromptKeys 清單複製貼上；確認四層覆蓋順序哪一層在生效實跑一次清洗，看結果是否改變
「清單頁與問答頁的分類不一樣」幽靈分類（C1＋C2）修分類提示詞（明列詞庫、不得自創）；已污染的紀錄需人工重貼分類重新清洗一筆，確認 AI 只給詞庫內的分類
「篩選後範圍反而變大」多選分類是「或」語意（F3）改用「限定知識來源」；分類收斂成單一維度比對開／不開篩選的命中數
「什麼都問不到」沒建索引建立索引系統健康監控的向量索引涵蓋率
「圖譜抽取跑完抽不到東西」來源的知識頁未核可先核可知識頁再抽取圖指標的三元組數
「AI 回答的還是舊版內容」素材更新後沒重跑下游（過時是靜默的）重新清洗→蒸餾→重建索引資料一致性巡檢的過時來源歸零
「清洗完的工程文件沒有用了」遮罩提示詞把型號與公差一起遮掉遮罩提示詞加「不要遮罩型號、尺寸、公差」的例外清單用同一份樣本重跑，確認數值都在
「全部都變待審核」信心提示詞被改壞，解析不出數字信心提示詞改回「只輸出 0 到 1 的小數」重跑一筆，看信心欄位有值
「整筆清洗失敗」遮罩步驟失敗（唯一不可降級的步驟）看日誌的遮罩錯誤；常見是提示詞把輸出格式搞壞或內容過長重跑成功且敏感資料已遮
「清洗失敗，訊息裡有 HTTP 400」彙整內容超過模型輸入上限（S2）。非暫時性錯誤，所以不會重試分盒或上傳前拆檔；不要調逾時或重試重跑成功
「明明有這份文件卻查不到」、尤其是排在後面的成員輸出被截斷（S3）。1.0.112 起會直接失敗或留註記；該版之前完全無提示先確認這一筆是哪個版本清洗的。最快的處置是重新清洗一次（新版會直接告訴你）。要人工判斷則：比長度（清洗後 .md ÷ 成員萃取檔總大小，正常 0.5～1.0；<0.3 且無 > 註記： 即為截斷）→ 抽查尾段 → 分盒／拆檔 → 重跑清洗→蒸餾→重建索引比值回到正常區間；出 2 題只有最後一章才答得出來的考題

急救的第一步永遠是問「你最近改了什麼」。上表十項裡有六項的根因是「客戶改了某個設定或名稱」，而這些改動都不會報錯。

六、客戶常見誤解與糾正話術（8 條）

誤解糾正（建議說法）
「有了 AI 就不用整理資料了」「反過來——AI 讓整理過的資料價值放大，也讓沒整理的資料問題放大。它會很有自信地引用你們過期的那份規範。」
「先全部丟進去，以後再整理」「以後不會來。而且未整理的內容會稀釋有用的內容，讓檢索品質下降。我們先做 20～30 份，做出一個成功案例。」
「AI 會自己分辨是哪個型號」「不會。要可靠鎖定型號，唯一的方式是用『限定知識來源』硬篩選。文件寫法與別名是加分項，不是保證。」
「分類多選就是交集」「是聯集。同時選兩個分類，範圍會比只選一個更大——而且畫面不會提示你。所以分類只放一個維度。」
「上線就結束了」「上線那天品質最好，之後每天都在衰減——除非有人負責盤點。這是我們要先確認 Owner 的原因。」
「這可以取代我們的 ERP／工單系統」「不能，也不該。它是知識層——回答『依據與經驗』，不回答『現在多少錢』。整合是後續可以談的。」
「AI 講的不能信」（資深人員）「不用相信它，去驗證它。每個答案都可以點開看原始段落。您試兩次，覺得出處不對我們就修。」
「我們的知識都在老師傅腦裡，這系統可以挖出來嗎」「系統挖不出來，訪談可以。我們會協助設計訪談提綱、錄音、轉逐字稿。這一步是人的工作，但只要做一次就永久留下。」
