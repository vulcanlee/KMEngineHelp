階段三：知識庫與 RAG 設計規格

本文件是知識庫計畫階段三（檢索 / RAG / 知識查詢）的設計規格，承接階段一（資料清洗）與階段二（知識頁審核）的產出，作為後續實作的藍圖。 規格沿用既有研究與工程慣例，與 03-知識庫架構研究與建議、04-開發建議與路線圖、05-待釐清問題與技術風險清單、prd/PDF型RAG處理-prd 對齊。 疑問緣起見 planning/10-知識蒸餾與問答疑問釐清及需求 第 6 節。

本文件為設計規格（藍圖）。 文中的資料模型、介面、管線為撰寫當時（版本 0.2.120，2026-06-26）的設計；對應實作已於 0.2.123–0.2.128 完成（嵌入索引、混合檢索、跨來源問答、檢索品質評測），落地細節以程式、changelog 與 知識庫 RAG 設計與執行 為準。

落地差異提醒（0.2.141）：早期藍圖曾規劃 sqlite-vec / SQL Server VECTOR；目前實作採 VectorEmbedding.Embedding 的可攜 byte[]（float32 打包）與應用層 cosine 搜尋。切塊參數已由 Chunker 常數移至 SystemSettings.Retrieval，詳見 知識庫 RAG 設計與執行 §二。

1. 背景與目標

1.1 承接前兩階段

  • 階段一（清洗）：把匯入素材（音訊/影音/文件/圖片）聚合為知識來源，經五步清洗（去重/遮罩/分類/摘要/信心）產出 CleanedContentRelativePath 乾淨內容。
  • 階段二（蒸餾）：把已清洗來源蒸餾為多筆互連 WikiPage（一概念一頁、[[link]] 互連、繼承 Teams、含信心與人工核准）。
  • 階段三（本規格）：把「已清洗、已蒸餾、已審核」的知識接上向量索引 + 權控檢索 + 跨來源問答，讓使用者用自然語言跨整個知識庫提問，並得到附出處、受權控的答案。

1.2 目標場景

以「員工手冊：入職滿 3 年可享什麼健康檢查福利」為代表——問題本質上要跨多筆來源、做語意檢索、答案要能回溯到原始條款/檔案，且依使用者身份只看得到有權的內容。這正是現有單一來源問答（KnowledgeSourceChatService，無向量、無跨來源）做不到、本階段要補齊的能力。

1.3 本規格鎖定的決策

#決策內容
1本輪產出設計規格文件（不寫程式）
2檢索範圍跨來源知識庫（一次檢索整庫）
3檢索層策略雙層混合：蒸餾 Wiki 頁做概念導引/命中，清洗內容做事實佐證與出處
4向量庫拓樸地端優先、緊貼現有雙庫：向量存於 VectorEmbedding 表，SQLite 用 sqlite-vec、SQL Server 用 2025 原生 VECTOR，走既有雙 migration；不引入第三種 DB 引擎
5答案出處必附出處，可鑽取回清洗內容/原始素材/原始檔，沿用 PDF RAG PRD §九 引用慣例

1.4 非目標（本階段不做）

  • PDF 結構化解析（原生/掃描/表格/圖表）——屬 prd/PDF型RAG處理 範疇，本階段先以現有清洗/蒸餾文字為索引來源。
  • rerank 模型（列為 v2 選配，見 §7.4）。
  • 多實例水平擴展競態防護（見 planning/09）。

2. 架構總覽

2.1 雙層混合檢索流程

使用者提問（多輪）
   │  取得 RecordAccessScope（IsAdmin, Teams）
   ▼
查詢嵌入（IEmbeddingClient.EmbedAsync）
   ▼
混合檢索（檢索層即套團隊權控過濾）
   ├─ 第一層：蒸餾 Wiki 頁（概念導引、命中定位）  ← 向量 + 全文
   └─ 第二層：清洗內容 chunk（事實佐證、出處）    ← 向量 + 全文
   ▼
分數融合 + 取 topK（依門檻過濾）
   ▼
組裝 context（精煉 Wiki 條目 + 佐證 chunk，附 metadata/出處）
   ▼
組 prompt（四層提示詞解析；「無依據時明說」）
   ▼
LLM 串流回答（IChatConversationClient.StreamAsync）
   ▼
答案 + 出處清單（可鑽取至來源→成員→原始檔，受同一權控）
   ▼
寫稽核軌跡（誰/何時/問什麼/命中哪些 chunk/答什麼）

2.2 為什麼是雙層

  • 蒸餾 Wiki 頁精煉、概念化、可解釋，適合做「概念命中與導引」，作答品質高、token 省。
  • 清洗內容 chunk保留事實細節（如具體數字/條款），適合做「佐證與出處」，補足蒸餾可能遺失的細節並提供可追溯來源。
  • 兩者皆已去敏（遮罩），皆繼承 Teams，可在同一檢索與權控框架下處理。

3. 向量庫設計（緊貼現有雙庫）

3.1 設計取向與對 pgvector 的偏離說明

strategy/03 §三 原推薦 PostgreSQL + pgvector 為向量庫預設。本規格刻意改採「緊貼現有 SQLite／SQL Server 雙庫」，理由與取捨如下：

改變理由

  • 避免第三種 DB 引擎：現有系統嚴格維持 SQLite（開發/單機）與 SQL Server（正式）雙庫＋雙 migration 不變量；導入 PostgreSQL 會新增部署、備援、維運面，違背「可立即啟動、單機可跑」的產品取向。
  • 資料不外流 / 地端優先：向量與內容留在既有業務庫，與「地端優先」一致。
  • 沿用既有慣例：向量表走既有雙 migration、EF Core、團隊權控述詞，學習與維護成本最低。

取捨（須知曉的限制）

  • SQL Server 需 2025+（原生 VECTOR 型別與向量函式）；若客戶環境較舊，退而求其次以「應用層暴力比對」或延後升級。
  • sqlite-vec 規模上限較低：適合單機/中小知識庫；資料量大時檢索延遲上升。
  • 保留升級路徑：以 IVectorStore 介面抽象向量寫入/查詢（見 §3.4），日後若規模成長，可在不動上層的情況下換成 pgvector 或地端 Qdrant。

本偏離須回填 strategy/05 的 T1（向量庫拓樸）決策欄。

3.2 VectorEmbedding 資料模型（設計）

新增實體 VectorEmbedding（仿 WikiPage.cs 寫法，置於 KnowledgeExtraction.AccessDatas/Models/）：

索引/關聯

  • OnModelCreating：VectorEmbedding → KnowledgeSource、VectorEmbedding → WikiPage 皆 OnDelete(Cascade)（仿既有 WikiPage → KnowledgeSource）。
  • 一般查詢索引：(KnowledgeSourceId, SourceLayer)；向量索引依各 provider 機制建立（sqlite-vec 虛擬表 / SQL Server 向量索引）。

3.3 雙 migration 策略

  • 同一模型變更，於 KnowledgeExtraction.AccessDatas（SQLite）與 KnowledgeExtraction.AccessDatas.SqlServerMigrations（SQL Server）各產一套 migration（沿用既有不變量）。
  • 向量欄在兩 provider 的落地不同：SQLite 經 sqlite-vec（可能需虛擬表 + 對應主表），SQL Server 用原生 VECTOR(1024)。此差異以 provider 條件化的 migration 處理；IVectorStore 抽象隔離上層。
  • 維度固定 1024（見 §4.4）：維度即 schema 承諾；日後若改維度，需改 VECTOR(n) 的雙 migration 並全量重建索引。

3.4 向量存取抽象

定義 IVectorStore（隔離 provider 差異與未來升級）：

  • UpsertAsync(IEnumerable<VectorEmbedding>, ct)：寫入/更新向量。
  • SearchAsync(float[] queryVector, VectorQuery query, ct)：向量近鄰查詢，VectorQuery 帶 TopK、SourceLayer 篩選、Teams 權控述詞、相似度門檻。
  • 預設實作 DualDbVectorStore（依 DatabaseProvider 走 sqlite-vec 或 SQL Server VECTOR）。

4. 嵌入與供應商

4.1 IEmbeddingClient 介面（仿 IChatCompletionClient）

public interface IEmbeddingClient
{
    Task<IReadOnlyList<float[]>> EmbedAsync(IReadOnlyList<string> texts, CancellationToken ct);

  • 實作 OpenAIEmbeddingClient：仿 OpenAIChatCompletionClient.cs 結構（AddHttpClient、IOptions<OpenAISettings>、token 用量記錄），呼叫 /embeddings 端點。
  • 批次嵌入（一次多筆 text）以降低往返成本。

4.2 雲端/地端切換（沿用既有模式）

  • 在 OpenAISettings（Models/Systems/OpenAISettings.cs）新增嵌入相關欄位，並仿 ResolveChatLlm()/ChatLlmConfig 新增 ResolveEmbeddingLlm()/EmbeddingLlmConfig：
  • 雲端：EmbeddingModel（預設 text-embedding-3-large）、EmbeddingDimensions（預設 1024，對應請求的 dimensions 參數）、沿用 BaseUrl/ApiKey。
  • 地端：LocalEmbeddingModel（預設 bge-m3）、沿用 LocalBaseUrl/LocalApiKey。
  • EmbeddingProvider（Cloud/Local）切換旗標，預設沿用 GenerationProvider 取向。
  • appsettings.json 的 OpenAISettings 區段新增上述欄位；IsEmbeddingConfigured() 驗證。
供應方預設模型維度備註
雲端text-embedding-3-large1024帶 dimensions=1024（Matryoshka 截短，品質損失極小）

兩者皆 1024，故 VECTOR(1024) 在雲端/地端間可互換、不改 schema（換模型族仍建議重建索引以維品質，但欄位維度不變）。

4.3 無金鑰降級

  • 無金鑰降級：未設定嵌入金鑰/端點時，索引管線標記「未設定嵌入，略過」，問答退回現有單一來源清洗/原始內容模式（不致整站不可用）——沿用清洗/蒸餾既有降級精神。

4.4 Embedding 產生策略與維度（已定案）

維度 = 1024（schema 硬承諾，VECTOR(1024)）。產生方式與策略如下：

  1. 產生對象：對每個 chunk 的 ChunkText（Wiki 層 + Cleaned 層）產生向量；查詢字串在檢索時即時嵌入。
  2. 流程：切塊（§5）→ 批次送多筆 text（降低往返成本）→ IEmbeddingClient.EmbedAsync → L2 正規化 → 存固定長度 float[1024]。
  3. 相似度：餘弦相似度（向量已 L2 正規化，等同內積）。
  4. 對稱密集檢索：文件與查詢使用同一模型、同一維度嵌入（非 query/document 雙塔）。
  5. 維度互換：1024 為雲端（text-embedding-3-large + dimensions=1024）與地端（bge-m3 原生 1024）的共同維度，使供應方可切換而不動 schema。
  6. 模型追蹤與重建：VectorEmbedding.EmbeddingModel 記錄來源模型——
  7. 換模型（同 1024 維） → 建議全量重建索引以維持向量空間一致（不可混用不同模型的向量比相似度）。
  8. 改維度 → 需改 VECTOR(n) 的雙 migration + 全量重建。
  9. 繁體中文：內容在清洗階段已 OpenCC 繁化，直接以繁中嵌入；選用多語模型確保召回品質。
  10. 降級：未設定嵌入端點時略過索引、問答退回單一來源模式（見 §4.3）。

殘留待辦：地端 bge-m3 對本資料的實際召回品質，需於 PoC 以評測集實測並微調（見 §11、§12.3 Q1）。

5. 切塊（Chunking）與 Metadata

5.1 切塊原則（沿用 04 + PDF RAG PRD §六）

  • 段落/語意感知切片，非機械固定字數；盡量不拆斷標題與其正文、不拆斷完整條款。
  • 重疊（overlap）保留少量上下文以利語意連續。
  • chunk 繼承來源/頁的 Teams 與 Categories（權控與篩選用）。

5.2 兩層的切塊輸入

  • Wiki 層：每個 WikiPage 內容（通常已是一概念一頁，多數情況一頁一 chunk 或依小節切）。
  • Cleaned 層：CleanedContentRelativePath 的清洗 Markdown，依段落/小節切為多 chunk。

5.3 Metadata 欄位（出處定位）

每 chunk 帶：KnowledgeSourceId、SourceLayer、WikiPageId?、Ordinal、AnchorRef（章節/段落/條款）、Teams、Categories、ContentHash。沿用 PDF RAG PRD §六 的 metadata 精神（頁碼/表格編號等待 PDF 階段補）。

5.4 待調參數（標示，待 PoC 實測）

  • chunk 目標長度、重疊大小、邊界判定法（標點/小節/語意）。
  • 依 PoC 召回率與成本迭代（見 §11、strategy/05 T2）。

6. 嵌入索引建立管線（仿蒸餾三層）

6.1 三件套（仿 Distillations/）

  • IEmbeddingIndexQueue / EmbeddingIndexQueue：Channel.CreateUnbounded<int>(SingleReader)，Singleton 註冊（仿 IDistillationQueue/DistillationQueue）。
  • EmbeddingIndexBackgroundService：ExecuteAsync 迴圈消費、RecoverPendingAsync 重啟回復、取消註冊（仿 DistillationBackgroundService）。
  • EmbeddingIndexProcessor：狀態機 + 重試（PipelineRetryHelper）+ 進度（UpdateStatusAsync）+ 取消（PipelineCancellationRegistry，新增 PipelineNames.EmbeddingIndex）。

6.2 處理核心（ProcessCoreAsync 設計）

  1. 讀取來源的清洗內容（CleanedContentRelativePath → 根 ExternalFileSystem.CleanedSourcePath）與其蒸餾頁（WikiPage.ContentRelativePath → 根 ExternalFileSystem.WikiOutputPath），NormalizePath + File.ReadAllTextAsync(UTF8)。
  2. 切塊（§5），繼承 Teams/Categories，算 ContentHash。
  3. 比對既有 VectorEmbedding（依 ContentHash）做增量重建：新增/變更才呼叫 IEmbeddingClient.EmbedAsync，刪除孤兒 chunk。
  4. IVectorStore.UpsertAsync 寫入向量。
  5. 進度與狀態回寫。

6.3 狀態欄位

在 KnowledgeSource（必要時 WikiPage）新增 EmbeddingIndexStatus（待索引/等待中/處理中/已索引/失敗/已取消）、EmbeddingIndexProgressPercentage、EmbeddingIndexErrorMessage、IndexedAt（仿既有 DistillationStatus 等欄位）。模型變更須再產雙 migration。

6.4 觸發時機

  • 蒸餾完成（DistillationStatus=已蒸餾）後自動入列；
  • 清洗內容更新或 Wiki 頁編修/核准後標記需重建；
  • 提供手動「重建索引」入口（仿既有重蒸餾）。

7. 混合檢索與雙層策略

7.1 混合檢索（沿用 03 §一推薦）

  • 向量檢索（語意）＋全文檢索（精確關鍵字：SQLite FTS5 / SQL Server 全文索引或 LIKE 後備）並行，分數融合後取 topK。
  • 兩路皆在檢索層即套團隊權控過濾（§8）。

7.2 雙層取用規則

  1. 先檢索 Wiki 層 取概念命中（導引、定義、跨主題歸納）。
  2. 再檢索 Cleaned 層 取事實佐證 chunk（細節、數字、條款，供出處）。
  3. context 組裝：精煉 Wiki 條目在前（導引），佐證 chunk 在後（事實 + 出處 metadata）。

7.3 分數融合（設計）

  • 初版採加權分數融合（向量分數 vs 全文分數權重），權重與相似度門檻為待調參數（§11、strategy/05 T3）。
  • 對同一概念的 Wiki/Cleaned 命中做去重與互補（避免重複塞入相同事實）。

7.4 rerank（v2 選配）

  • 初版不導入 rerank 模型；待評測顯示融合不足時，再評估 cross-encoder/BGE-rerank 的準確度/延遲取捨（strategy/05 T3）。

8. 權控檢索（資安關鍵）

8.1 核心不變量

  • chunk 繼承來源/頁 Teams（寫入 VectorEmbedding.Teams）。
  • 檢索查詢即套權控過濾（非取回後再濾）：非管理員只看「無團隊（公開）或與其角色團隊交集」的 chunk。
  • 取得範圍：IRecordAccessScopeProvider.GetAsync() → RecordAccessScope(IsAdmin, Teams)。
  • SQL 路徑沿用 TagStringHelper.BuildTeamAccessPredicate<VectorEmbedding>(x => x.Teams, scope.Teams)；向量近鄰結果若無法直接帶述詞，於同一查詢以 Teams 條件預過濾候選集，確保越權內容永不進入候選與 LLM context。
  • 記憶體端二次校驗用 TagStringHelper.IsTeamAccessible。

8.2 跨來源逐筆過濾

  • 跨來源檢索時，每一筆命中都要過權控；管理員不受限。
  • 答案的出處顯示與原始檔下載也受同一權控（下載沿用既有 Controller 權控，如 DocumentExtractionService.GetMarkdownAsync 內的 IsTeamAccessible）。

8.3 測試用例（驗收必含）

  • 非授權團隊內容不得出現在檢索結果、context、答案、出處或下載。
  • 公開（無團隊）內容對所有人可見；管理員可見全部。
  • 多輪對話每輪檢索都重新套 scope（避免身份切換後沿用舊 context）。

9. 問答編排與提示詞

9.1 跨來源問答服務

  • 新增 KnowledgeBaseChatService（或擴充 KnowledgeSourceChatService）支援跨來源問答：
  • PrepareAsync：不再綁單一 id，改為對整庫檢索。
  • 流程：取 scope → 嵌入 query → 混合檢索（權控）→ 組 context → BuildMessagesAsync（沿用現有四層提示詞 + 詳簡切換）→ IChatConversationClient.StreamAsync 串流。
  • 沿用現有 ChatMessage、多輪 history、串流 token 日誌。

9.2 RAG 提示詞槽位（沿用四層解析）

  • 在 LlmPromptKeys 新增鍵，如 知識庫-系統、知識庫-無依據；於 LlmPromptDefaults 給 fallback；appsettings.json 的 LlmPrompts 加對應欄位。
  • 預設系統提示精神：「依據下方附出處的參考資料作答；找不到依據時明確說明，不得臆造；以台灣繁體中文回答。」

9.3 context 組裝格式

  • 每段參考資料前置出處標頭（來源標題、層別、章節/錨點），讓 LLM 能在答案中引用，並利後處理產生出處清單。

10. 引用與稽核

10.1 答案必附出處

  • 每個答案附出處清單：命中 chunk → 所屬 Wiki 頁/清洗來源 → 知識來源 → 成員（KnowledgeSourceItem）→ 原始素材檔（音訊/影音/文件/圖片），可一路鑽取與下載。
  • 鑽取鏈沿用既有溯源資料關聯（見 planning/10 §3）；下載受既有權控。
  • 沿用 prd/PDF型RAG處理-prd.md §九 的引用錨點精神（章節/條款；頁碼/表格待 PDF 階段補）。

10.2 稽核軌跡

  • 新增查詢稽核（誰、何時、問句、命中的 chunk Id 與分數、回答摘要、套用的 Teams 範圍），供資安稽核與品質回溯。落地形式（資料表 vs 結構化日誌）於實作時定，預設先走結構化 NLog（沿用現有 token/權控日誌慣例）。

11. 評測與品質

11.1 新增 RAG 檢索評測指標

  • 檢索：Precision / Recall / NDCG@k、命中正確率。
  • 出處：出處正確率（答案引用是否對應真實 chunk/章節）。
  • 權控：越權洩漏測試（非授權必為 0 命中）。
  • 效能/成本：檢索延遲、嵌入與 LLM token 用量。

11.2 與既有清洗品質評測銜接

  • 既有清洗品質評測聚焦上游清洗品質（信心門檻 0.70、遮罩召回 ≥0.98、分類 F1 ≥0.70、摘要覆蓋 ≥0.60，已鎖定 2026-06-12）。
  • 本階段新增下游檢索/生成品質評測集（query + 期望命中 chunk + 期望答案 + 期望出處），與既有清洗品質評測頁併行呈現。

11.3 PoC 驗證（與 planning/07 第 5 階段合流）

  • 用 1–2 份真實手冊/SOP 走完整「匯入 → 清洗 → 蒸餾 → 索引 → 跨來源問答」，人工檢視答案正確性、出處可追溯、權控正確、遮罩無漏。
