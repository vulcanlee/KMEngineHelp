知識庫架構研究與建議

知識庫「單一 vs 混合架構」與「地端 vs 雲端」的研究與選型建議

  • 文件用途：知識庫「單一 vs 混合架構」與「地端 vs 雲端」的研究與選型建議
  • 主要讀者：架構師、開發團隊、決策層
  • 文件版本：1.0
  • 建立日期：2026/06/08
  • 編碼：UTF-8（繁體中文，含 BOM）

範圍假設：中型規模（數萬文件、數百使用者）、地端與雲端皆須支援、企業環境須具備權控、遮罩、存取日誌。本文給出單一明確的推薦架構與理由，並標示與現有系統的整合點。

一、檢索架構選項比較（單一 vs 混合）

方案原理優點缺點適用
純向量檢索文本切塊→Embedding→向量相似度語意理解佳、實作直觀對精確詞、代碼、料號、專有名詞命中差；可能漏關鍵字語意問答為主
關鍵字／BM25倒排索引、詞頻精確詞命中強、可解釋、便宜不懂語意、同義/換句話差精確查找、法規/料號
混合檢索（Hybrid）向量 ＋ 關鍵字並行，分數融合後重排（rerank）兼顧語意與精確、召回最穩多一層融合/重排，工程稍複雜多數企業情境（推薦）
GraphRAG／知識圖譜抽取實體關係建圖，沿關係推理跨文件關聯、多跳推理強建圖成本高、維運複雜、過度設計風險高關聯推理需求才需要
LLM 知識 Wiki（蒸餾預編譯）LLM 將來源蒸餾為一個概念一頁的 Markdown 實體頁，以 [[wiki-links]] 互連；查詢讀「已合成」的精煉知識知識複利累積、答案品質高、可解釋、與既有 Markdown 產物天然契合需 ingest/maintain 流程、頁面一致性需 lint、即時性較弱追求「真實可用知識」而非原文搬運（本計畫採用）

結論：中型知識庫單靠純向量會在「精確詞、專有名詞、料號/條號」上吃虧；建議採混合檢索 ＋ rerank為檢索骨幹，並疊加一層「LLM 知識 Wiki（蒸餾預編譯）」作為精煉知識來源。GraphRAG 列為未來選配（非近期範圍）。

📌 後續進展（追記）：GraphRAG 已於 1.0.83～1.0.88 分六階段實作完成，並以第三路「圖檢索」併入既有混合檢索（融合式 Vw*向量 + Kw*關鍵字 + Gw*圖，GraphWeight 預設 0.2、可設 0 關閉）。採關聯式邊表、未導入專用圖庫。詳見 Graph RAG 導入分析與實作藍圖 §9。rerank 至今仍只有分析文件、未實作。

LLM 知識 Wiki（Karpathy 概念）與蒸餾

Karpathy 提出的「LLM Wiki」是一個由 LLM 主動維護的 Markdown 知識庫：每個檔案是一個概念的維基式條目、以 [[wiki-links]] 互連，並以三類流程運作——

  • Ingest（蒸餾匯入）：LLM 讀新內容，蒸餾出精煉條目、更新相關頁、建立交叉連結、標記矛盾。
  • Query（查詢）：直接讀「已蒸餾合成」的條目作答（預編譯），而非每次重查原文。
  • Lint/Maintain（健檢維護）：定期掃描一致性、補缺、發掘新連結，知識自我修復。

對本計畫的意義：

  • 正好實踐使用者要的蒸餾——萃取出真實可用的知識，而非原文搬運。
  • 與現有系統高度契合：文件轉文字已產出 Markdown、轉錄已產出逐字稿，正是蒸餾 Wiki 的輸入；產物也是 Markdown，落地容易。
  • 與混合檢索互補：Wiki 條目（精煉、可解釋）作答品質高；原始 chunk 檢索補足長尾與出處追溯。建議兩層並用：先讀 Wiki 條目，必要時回退到 chunk 檢索取證據。

二、地端 vs 雲端取捨

兩種都要支援，差異主要在「Embedding／LLM 來源」與「向量庫部署位置」。建議採可切換的供應商抽象層，讓同一套程式以設定切換。

構件雲端優先模式地端／私有模式
Embedding雲端 Embedding API地端 Embedding 模型（經內部閘道）
LLM（問答生成）雲端 LLM API地端 LLM 或私有閘道管控
向量索引託管向量服務或自管自管（與資料同處企業環境）
資料落地可上雲不出企業環境
取捨速度快、功能新、維運省合規、資料自主、需自備算力與維運

既有系統已有「OpenAI 設定可由環境變數注入、快取 Memory↔Redis 可切換」的慣例，與本處「供應商可切換」的設計一致，延用同樣的設定驅動模式即可。

三、向量庫選型（中型規模）

選項部署優點缺點建議定位
PostgreSQL ＋ pgvector地端/雲端皆可與關聯資料同庫、權控/交易/備援成熟、維運單純、支援 hybrid（向量＋全文）超大規模需調校推薦預設（中型規模綽綽有餘，地端友善）
Qdrant地端/雲端皆可向量檢索效能佳、過濾條件強、可自管多一個服務要維運向量量體更大或需專用向量引擎時
雲端託管向量服務（如 Azure AI Search / 各家服務）雲端免維運、整合快資料須上雲、不適合地端模式純雲端客戶選配

結論：以 PostgreSQL ＋ pgvector 作為預設向量庫——同時滿足地端與雲端、與現有 EF Core/權控自然整合、維運成本低；向量量體成長後再評估 Qdrant。

註：現有系統開發用 SQLite、正式用 SQL Server。知識庫索引建議獨立採 PostgreSQL＋pgvector（業務資料與向量索引可分庫），避免綁死 SQL Server 的向量支援差異；最終資料庫拓樸列入 05 待釐清。

四、Embedding 與 LLM 選型原則

  • 抽象優先：定義 IEmbeddingProvider / IChatCompletionProvider 介面，雲端與地端各一實作，由設定切換（呼應現有快取/OpenAI 設定模式）。
  • 雲端模式：用成熟雲端 Embedding／LLM，先求功能與品質。
  • 地端模式：經內部 LLM 閘道管控，可換地端開源模型；品質/算力為已知風險（見 05）。
  • 繁體中文：延用現有 OpenCC 繁體化慣例，確保知識庫與答案皆為台灣繁體。

五、企業環境必備能力

這三項是「能不能在企業落地」的關鍵，必須內建而非事後補。

1. 權控（延伸現有團隊權控）

  • 現況：紀錄層級的團隊權控（IRecordAccessScopeProvider ＋ TagStringHelper），非管理員只看「無團隊(公開)或與角色團隊交集」的紀錄。
  • 延伸：知識單元（chunk）繼承來源文件的 Teams 標籤；檢索時即過濾（在向量查詢條件帶入團隊範圍，而非取回後再濾），避免越權內容進入 LLM 上下文。

2. 敏感資訊遮罩

  • 在清洗階段做 PII/機密遮罩，索引「遮罩後」內容；原文另存受控。
  • 問答回覆同樣套遮罩，避免從上下文洩漏。

3. 存取日誌與稽核

  • 記錄「誰、何時、問了什麼、命中哪些來源、回了什麼」。
  • 延用現有 NLog 與請求計時/例外記錄基礎，擴充查詢稽核軌跡。

六、推薦架構（單一明確建議）

「蒸餾預編譯的 LLM 知識 Wiki」＋「混合檢索（向量 pgvector ＋ 關鍵字）＋ rerank」雙層，加上權控過濾 ＋ 遮罩 ＋ 稽核；供應商（Embedding/LLM）可由設定在雲端/地端切換。

資料流：

來源內容(已匯入)
   │
   ▼ 清洗：去重/品質過濾 → 遮罩 → 分類標籤 → 摘要/重點擷取
   ├─▶ 知識蒸餾：LLM 萃取為 Wiki 實體頁(Markdown, [[wiki-links]])
   │      （繼承來源 Teams 標籤；定期 lint/maintain 維護一致性）
   ▼ 切塊(chunk)（繼承來源 Teams 權控標籤）
   ▼ Embedding（雲端或地端，介面可切換）
   ▼ 寫入索引：PostgreSQL + pgvector（向量）＋ 全文/關鍵字（Wiki 頁與 chunk 皆索引）
─────────────────────────────────────────────
查詢：使用者提問
   ▼ 套團隊權控過濾（檢索層即過濾）
   ▼ 先讀 Wiki 精煉條目；必要時回退混合檢索(向量+關鍵字)→ rerank 取證據
   ▼ 組裝上下文（遮罩後內容＋出處）
   ▼ LLM 生成帶出處答案（雲端或地端）
   ▼ 記錄稽核軌跡（好答案可回填為新 Wiki 頁）

與現有系統的整合點

  • 匯入/處理管線：沿用既有非同步佇列 ＋ 背景服務模式（TranscriptionBackgroundService / DocumentExtractionBackgroundService），新增「清洗」與「索引」管線。
  • 清洗輸入：DocumentExtractionProcessor（MarkItDown 產出 Markdown）與轉錄逐字稿，是清洗階段的天然輸入。
  • 權控：TagStringHelper 的團隊權控述詞延伸到 chunk 級檢索過濾。
  • 設定驅動：延用 appsettings＋環境變數注入（如現有 OpenAI/Redis 模式）切換供應商與部署模式。
  • 資料層：沿用 EF Core 與「雙資料庫 migration」慣例；向量索引獨立於 PostgreSQL＋pgvector。

具體改造切入點與檔案路徑見 04 開發建議與路線圖的「初步技術驗證」。
