知識來源規模守門開發代辦清單 TODO

對應文件：知識來源分盒與規模上限指南（使用者側的規避方法）、容量邊界與限制 §七（邊界事實）。 鐵則：本清單三項皆不需要模型變更、不需要 migration（P2／P3 若加入可設定門檻，只動 appsettings.json 的既有 SystemSettings 區段）；每次可建置產出 appsettings.json 版本 +1；文件 UTF-8 含 BOM（scripts/Test-DocsEncoding.ps1）。 建立日期：2026/07/30　｜　狀態：✅ 三項全數完成（P1 → 1.0.112、P2 → 1.0.113、P3 → 1.0.114） 查證紀錄：2026/07/30 逐項對回原始碼確認三項皆未實作（finish_reason 僅存在於 PdfMarkdownLlmClient、無任何彙整量顯示、無清洗前警告），隨後開始實作。

一、為什麼需要這組守門

知識來源的聚合對成員數與內容總量完全沒有上限（KnowledgeSourceContentAggregator.BuildAsync），而清洗的去重與遮罩兩步要把整份內容重新輸出一遍（CleaningEnhancer.ComposeStepPrompt ＝ prompt + "\n\n\n" + 整份全文）。於是規模過大會有三種結果：

模式行為目前有無守門
A 輸入超限遮罩丟 HTTP 400 → 非暫時性 → 不重試、直接失敗✅ 有（失敗且訊息可見）
B 輸出被截斷串流正常結束、內容非空 → 被當成功，狀態「已清洗」、無任何註記✅ 1.0.112 已修（P1）
C 檢索稀釋候選 50 → 只有 TopK=10 段進 LLM，兩段式門檻不會攔❌ 無（屬規劃層問題，可用分盒繞過；見 §四「刻意不做的」）

B 曾是全系統唯一完全無痕跡的失敗，已於 1.0.112 修正（P1）。 在那之前，後果是整條 RAG（切塊／嵌入／問答）建立在殘缺內容上，而使用者的感受是「明明有這份文件卻查不到」——會被誤判為檢索問題，然後去調檢索參數（無效）。⚠️ 1.0.112 之前清洗的資料仍可能已被截斷，需人工檢查或重新清洗。

本清單三項的目標依序是：先讓它被發現（P1）→ 再讓它能被預先判斷（P2）→ 最後在使用者按下去之前攔住（P3）。

二、待辦項目

P1 — 清洗的去重／遮罩加上輸出截斷偵測 ✅ 已完成（1.0.112）

  • ☑在清洗的去重與遮罩兩步偵測模型是否因輸出上限截斷（finish_reason == "length"）。

實作結果（1.0.112）

位置做了什麼
IChatCompletionClient.CompleteStreamingCheckedAsync新增方法，帶預設實作回報「未截斷」→ 既有測試假件與另 10 個呼叫端一行都不用改
OpenAIChatCompletionClientStreamAsync 本體抽成 StreamCoreAsync(…, onFinishReason)（公開簽章與行為不變）；SSE 迴圈擷取 choices[0].finish_reason；覆寫 CompleteStreamingCheckedAsync
CleaningEnhancer 去重截斷 → 不採用輸出、退回未去重原文、加 > 註記：
CleaningEnhancer.MaskAsync截斷 → 擲例外、整筆清洗失敗（截斷尾段未經遮罩，必然有未遮到的個資／機密）

測試（新增 10 條，全量 1057 → 1067 全綠）：length 判為截斷；反證 stop／tool_calls／content_filter／無 finish_reason 皆不誤判；大小寫不敏感；CompleteStreamingAsync 被截斷時行為不變（釘住另 10 個呼叫端）；去重截斷退回原文並留註記且遮罩收到的是原文；遮罩截斷擲例外且不再跑後續三步；未截斷時行為與加偵測前完全一致。

原始規劃備註（保留供對照）

為什麼是最高優先：成本最低、效益最大。它把唯一的靜默失敗變成大聲失敗——不需要使用者學任何新知識，也不需要改變作業習慣。

現成可重用的東西：PdfMarkdownLlmClient.IsTruncatedByOutputLimit(string responseJson) 已是 public static，判定邏輯（讀 choices[0].finish_reason）可直接重用，不必重寫。

要注意的兩件事：

  1. ⚠️ 不要直接改共用的 OpenAIChatCompletionClient.ParseContent。 PdfMarkdownLlmClient.cs:85-115 的 remarks 已說明原因：該方法另有 4 個呼叫端（一般對話、查詢改寫、圖片、手動送檔產生），那些路徑被截斷未必要當失敗，改共用方法會把行為變更擴散到整站。本專案「外科式變更」原則的既有實例，照著做。
  2. 清洗走的是串流路徑（CompleteStreamingAsync → StreamAsync），現成的 IsTruncatedByOutputLimit 吃的是完整的非串流回應 JSON。SSE 的 finish_reason 出現在最後幾個 chunk 的 choices[0].finish_reason，需要在串流迴圈中額外解析並回傳給呼叫端（例如讓 CompleteStreamingAsync 回 (string Text, bool Truncated)，或另開一個帶截斷旗標的多載，避免改動既有簽章影響其他呼叫端）。

驗證方式：

  • 單元測試：模擬 SSE 最後一塊帶 "finish_reason":"length"，斷言清洗擲例外／標記失敗。
  • 反證測試：finish_reason 為 stop 時不得誤判為截斷（避免把正常清洗改成失敗，這個迴歸很嚴重）。
  • 實跑：拿一份刻意過大的素材跑清洗，確認狀態變「失敗」且錯誤訊息說明是輸出截斷。

風險：若判定寫錯方向（把正常當截斷），會讓所有清洗失敗。上線前必須有反證測試。

實作結果（1.0.113）

位置做了什麼
KnowledgeSourceContentAggregator先重構：把「成員 → 候選內容檔完整路徑」抽成 ResolveMemberPathsAsync，讓讀內容與量大小共用同一份對應規則（含影音類「逐字稿為空 → 退回依提示詞產生」的 fallback）。再新增 MeasureAsync，只讀 FileInfo.Length、不讀內容
KnowledgeSourceService.MeasureAsync(id)包一層給 UI，套團隊權控；一併回傳清洗後檔案大小
KnowledgeSourceSizeAdapterModel新增；含 CleanedRatio（清洗後 ÷ 彙整前，四捨五入 2 位）
CompactNumberHelper.ToByteSize新增（1.2 KB／3.5 MB）；與 token 計數用的 ToCompact 分開
管理成員對話窗彙整量：約 X（Y 個可用成員，Z 個略過）；加入／移除／上下移後重新量測
確認清洗對話窗同上；已清洗過者多一行 上次清洗後：X（比值 0.62）——即分盒指南的「比長度」檢查，出現在最需要它的時機

⚠️ 一個刻意保留的近似：BuildAsync 判定成員可用是「讀進來的內容不是空白」，MeasureAsync 為了不讀檔改用「檔案存在且長度 > 0」。所以「檔案只含空白字元」時量測會算可用、彙整會略過。畫面文案因此一律寫「約」，並有一條測試把這個已知差異釘住（MeasureAsync_WhitespaceOnlyFile_IsKnownDivergenceFromBuild）。

⚠️ 刻意不做的兩件事：不加列表欄位（一頁 20 筆 × 每盒 15 成員＝每次渲染 300 次檔案查詢）；不加 DB 欄位存彙整量（需雙 migration，即時量測已足夠）。

測試（新增 20 條，全量 1067 → 1087 全綠）：四型素材位元組加總；未完成／無檔案成員計入略過；空來源回 0；🔴 一致性測試 MeasureAsync 可用數 == BuildAsync 採用數且標題確實出現／不出現在彙整本文；影音 fallback 兩邊取同一個檔；空白檔的已知差異；服務層的清洗後比值、未清洗時為 null、團隊權控拒絕與允許；ToByteSize 的 B／KB／MB／GB 邊界。

原始規劃備註（保留供對照）

為什麼：目前沒有任何畫面顯示這個數字——ContentInventoryReportService 只統計筆數（依媒體型別／團隊／分類／狀態），沒有字數或位元組。使用者要判斷規模只能自己去 SystemSettings.ExternalFileSystem 各路徑下人工比對檔案大小，門檻太高，實務上等於沒人會做。

效益：讓 分盒與規模上限指南 §五 的實測步驟與 §十 的「比長度」檢查變成點兩下就能做的事，而不是維運任務。

實作注意：

  • 成員的萃取輸出是檔案（不在 DB），所以字數要讀檔取得。⚠️ 不要在列表頁同步讀大量檔案——一頁 20 筆盒子、每盒 15 個成員就是 300 次檔案 I/O。建議用 FileInfo.Length 取位元組（不必讀內容）並快取，或在清洗完成時把統計值寫回 DB 欄位（後者需 migration，屬另一個決策）。
  • 顯示「位元組」比「字數」便宜得多（不必讀檔內容），而且對判斷規模已經足夠。建議先做位元組版。

驗證方式：對照人工在檔案系統加總的數字；量測列表頁載入時間沒有明顯退化。

原始規劃備註（保留供對照）

為什麼：P1 讓失敗被發現、P2 讓規模看得到，但兩者都是事後。P3 是在使用者按下去之前就攔住——尤其對「一次加了 40 個成員」這種情況，事前提示能省下十幾分鐘的清洗與一次失敗。

設計要點：

  • 門檻必須可設定（SystemSettings.Cleaning 下新增一項，例如聚合位元組警告門檻），且預設值要保守但不能擋住正常使用——這是軟警告，不是硬阻擋。
  • 文案要說明「為什麼」與「怎麼辦」，並指向 分盒與規模上限指南，不要只說「內容過大」。
  • 依賴 P2（要先有估計值才能比門檻），所以順序上排最後。

驗證方式：門檻設低時出現提示且可繼續；設高時不出現；文案在對話窗內不破版。

三、建議推進順序

P1 → P2 → P3。

  • P1 單獨做就有價值，而且不依賴其他兩項。若只做一項，做這個。
  • P2 是 P3 的前置。
  • C（檢索稀釋）不在本清單：它可以用分盒與「限定知識來源」完全繞過，屬規劃層問題；若要在程式層改善，見 多客戶多型號規劃分析 §8 的 P1（分類多選支援「且」語意）與 P2（chunk 併入章節標題），那兩項的效益更廣。

四、刻意不做的

不做理由
在聚合階段自動截斷或自動分批送 LLM自動分批會讓「去重」失去跨批視野（重複段落跨批就抓不到），而自動截斷等於把靜默失敗變成內建行為。寧可失敗，不要自動殘缺。
硬性限制成員數不同素材的內容密度差異可達百倍（掃描 PDF 對純文字檔），用成員數當硬上限會既擋到正常使用、又擋不住真正超大的情況
在請求裡帶 max_tokensPdfMarkdownLlmClient.cs 的既有註解已說明：模型預設輸出上限通常大於我們能合理硬設的值，硬設反而會更早截斷。目標是「截斷要被發現」，不是「提高上限」
