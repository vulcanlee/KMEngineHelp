開發歷程總覽與未來建議

本文件依 git 推送紀錄（功能分支 → --no-ff 合併）整理，呈現專案開發主題、時間點與版本號， 並據此做出總結、建議與未來方向。資料截至 2026-06-26（版本 0.2.128，階段三知識庫與 RAG 已完成）。

1. 總覽

  • 期間：2026-06-02 ～ 2026-06-26（約 25 個日曆天）。
  • 版本：自腳手架 0.2.10 演進至 0.2.128。
  • 開發強度：高度集中於 06-02~05、06-09~12、06-16~24；其間數日近乎停擺。06-20~24 一波密集推進，完成知識來源 AI 對話、四層提示詞解析、知識頁審核（階段二）與階段三 RAG 設計規格。
  • 開發模式：AI 代理人驅動、單人高速開發，全程遵循嚴謹工程慣例：
  • 每個主題開一條功能分支，以 --no-ff 合併回 main（保留主題邊界）。
  • 每次異動 appsettings 版本號 +1，並撰寫 docs/changelog/ 發行說明。
  • 文件與程式同步維護；docs/*.md 一律 UTF-8 含 BOM（scripts/Test-DocsEncoding.ps1 守護）。
  • 模型變更產生雙資料庫 migration（SQLite 與 SQL Server）。
  • 紀錄查詢一律套團隊權控不變量。

3. 開發總結與說明

從 git 紀錄可看出一條清晰的價值演進主軸，由「把素材變文字」逐步走向「把文字變可信知識」：

  1. 匯入與轉錄（階段 1–2）：先打通音訊／影片轉錄與多平台下載（含技術門檻最高的抖音 playwright 助手）。
  2. 治理與權控（階段 3）：補上分類、團隊標籤與團隊資料權控，使資料可分群、可控管。
  3. AI 加值（階段 4）：提示詞、逐字稿 LLM 產生、圖片視覺解讀，讓內容能被理解與再加工。
  4. 工程化與品保（階段 5–6）：三管線佇列化／重試／取消＋重啟回復，再到清洗管線 QA-1~QA-4 與

清洗品質評測——把「清洗」從能跑變成可量測、可校準、可審核。

  1. 知識資產化與打磨（階段 7–8）：知識來源聚合、內容線上編修、清洗規則設定，並補齊使用者手冊與行銷簡報。
  2. 可診斷化與知識問答前奏（階段 10–12）：日誌涵蓋率補強讓系統可診斷化；知識來源「AI 對話」（多輪、串流、詳簡）與四層提示詞解析，把「能理解內容」推進到「能對內容問答」（惟仍為單一來源、無向量檢索）。
  3. 知識頁審核與檢索規格定案（階段 13）：知識頁審核（階段二）把已清洗來源蒸餾為互連 Wiki 實體頁，完成「文字→可信知識資產」；隨後階段三「知識庫與 RAG」設計規格（含 embedding 策略與維度）定案，為跨來源、權控、附出處的問答鋪好藍圖。

近期態勢：自階段 7 起曾從「功能擴張」轉向「穩定化／除錯」（如 0.2.76→0.2.86 的「Blazor circuit 長壽命 DbContext 讀到陳舊追蹤實體」根因，最終於 0.2.86 做全管線系統性修正；抖音下載連修三版 0.2.85→0.2.87）。 06-20 之後重心再次回到價值擴張：知識來源 AI 對話、提示詞解析、知識頁審核（階段二）相繼落地，並以階段三 RAG 設計規格收束方向。專案已具相當功能完整度，正站在「進入檢索／問答（階段三）實作」的起跑線。

4. 建議

依 git 觀察提出（非既有功能，屬建議）：

  1. 測試覆蓋擴增：現有約 240 個測試偏重清洗管線；建議補服務層（Retry/Cancel/權控）與關鍵 UI

流程的整合測試，讓「陳舊追蹤」這類回歸能被自動攔截。

  1. 根因的系統性防護：陳舊追蹤問題目前是「逐處補 CleanTrackingHelper.Clean」。建議評估更治本的

作法——查詢預設 AsNoTracking、或讓會被背景服務變更的讀取走獨立 DI scope／DbContext 工廠， 從架構上消除長壽命 circuit context 的陳舊風險。

  1. 抖音下載韌性：保留 cookie／Range 後備與半自動（需桌面瀏覽器）限制的明確說明；長線評估

無頭環境或官方授權途徑，降低維運脆弱度。

  1. CI 與版本里程碑：目前 repo 無 git tag。建議導入 CI（build＋test＋編碼檢查）並對重要版本

打 tag（如 0.2.58 管線化、0.2.66 清洗品質評測、0.2.84 清洗規則設定），便於追溯與回滾。

  1. 上線安全與容量：延續既有安全檢查與容量邊界文件，在正式部署前完成 HTTPS／密鑰／預設帳號

與容量上限的最終把關。

5. 未來開發方向（Roadmap）

  1. 蒸餾（Distillation）：✅ 已實作（0.2.117，階段二）——已清洗來源蒸餾為多個互連 Wiki 實體頁、繼承 Teams 標籤、含信心門檻與人工核准/退回。見 知識頁審核 PRD。
  2. 檢索／RAG 與知識查詢（階段三）：✅ 已實作（0.2.123–0.2.128）。已把清洗、蒸餾、審核後的知識接上向量索引與權控檢索／問答，完成「知識資產化」最後一哩。六步驟皆完成：IEmbeddingClient/OpenAIEmbeddingClient 與雲端/地端切換（0.2.123）、VectorEmbedding 實體與雙 migration ＋ IVectorStore（0.2.124）、Chunker ＋ 嵌入索引管線（0.2.125）、混合檢索 IRetrievalService（檢索層即套團隊權控，0.2.126）、跨來源問答頁 ＋ 出處鑽取（0.2.127）、檢索品質評測集與指標（0.2.128）。設計藍圖見 階段三：知識庫與 RAG 設計規格。
  3. 多實例部署競態防護：目前佇列入列為單實例 read-then-write，水平擴展前需處理競態。
  4. 權限細化與對外 API 化：更細的資源層級權限，並把核心能力以穩定 API 對外開放。
  5. 觀測性強化：在現有健康監控與 NLog 之上，補管線吞吐、失敗率、LLM 用量等指標儀表板。
