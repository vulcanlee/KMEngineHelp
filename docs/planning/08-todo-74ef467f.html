RAG 後續增強（Query Rewrite v1 不做，待評測後決定）

  • ☐HyDE 檢索（召回 / 中）：先由 LLM 產生假設性答案，再用假設答案檢索，可改善語意鴻溝與專業書面語命中；但會增加一次模型呼叫與查詢漂移風險。建議先觀察 Query Rewrite v1 的 檢索品質評測結果，再決定是否排入。
  • ☐Multi-query expansion（召回 / 中）：把同一問題展開為多個等價或互補查詢後合併命中，適合複雜、跨面向、比較型問題；需處理候選去重、分數融合與成本上升。
  • ☐Rerank 二階重排（準確度 / 中）：對混合檢索候選 chunk 以 cross-encoder 或 reranker 重排，可改善 TopK 精準度；缺點是延遲與模型部署成本增加。若現有融合分數在評測集中表現不足，再評估導入。
  • ☐Query drift semantic guard（正確性 / 中）：用 embedding 相似度或規則檢查改寫後查詢是否偏離原始問題；Query Rewrite v1 先靠保守提示詞與失敗 fallback，後續若出現誤改寫案例再補。
  • ☐Adjacent chunk expansion（上下文 / 中）：命中 chunk 後自動補前後 chunk，改善答案缺少上下文或章節條款被切開的問題；可與 Query Rewrite 互補，但會增加 context 長度與引用去重成本。

由壞 Host 請求事故衍生（2026-07-25）

  • ☐壞 Host 請求造成未處理 500，日誌一次噴 5 條 ERROR（可觀測性 / 中）
  • 症狀：正式環境（IIS）偶發 GET / 未處理例外，

System.UriFormatException: Invalid URI: The hostname could not be parsed.， 堆疊起自 NavigationManager.Initialize。單一請求會連噴 5 條 ERROR——因為 /Error 頁 自己也是 Razor 元件，重跑時 Host 依然是壞的，例外處理器跟著失敗。

  • 根因：Blazor SSR 渲染前用 Request.Scheme ＋ Request.Host 組 baseUri；Host 缺失或無法

解析時組出 http:///，Uri 解析失敗。AllowedHosts 為 *，框架內建的 HostFiltering 全放行， 這類請求才會走到渲染。與轉發標頭無關（UseConfiguredForwardedHeaders 只處理 XForwardedFor|XForwardedProto，不含 Host）。

  • 重現方式（已實測）：用原始 socket 送 HTTP（curl／HttpClient 會自動補 Host，測不出來）：

`GET / HTTP/1.0

（無 Host）或 Host: ` 留空 → 500；正常 Host → 200。

  • 結論：設 AllowedHosts 為實際主機名即可零程式碼解決。 框架內建的 HostFiltering 本來就是

幹這個的，缺 Host 會直接回 400，比自訂中介軟體簡單。代價：appsettings.json 是共用基底 設定，主機名設錯或漏列會讓全站回 400，需由部署端以環境變數 AllowedHosts 覆寫並實測。 順帶也擋掉 Host 標頭注入（可解析但不屬於本站的 Host）。

  • 目前刻意不處理：這是掃描器垃圾流量造成的日誌噪音，不是資安漏洞。曾實作自訂 Host 防護

中介軟體，但評估後認為對系統複雜度的增加不划算而移除。日誌若被洗版再回來處理即可， 上面的重現方式與結論可直接沿用，不必重查一次。

部署與機密保管（2026-07-25）

  • ☐正式環境機密的保管方式（安全 / 中）：文件建議把 JwtSettings__SigningKey、

BootstrapSettings__SupportPassword、OpenAISettings__ApiKey 放在 IIS 站台的 web.config <environmentVariables>（存檔即生效、不需重部署）。但這代表機密以明文存在站台目錄，會隨備份／ 複製擴散。若日後有合規要求，應改用 Windows 認證管理員、DPAPI 加密設定區段，或外部密碼保管服務。

  • ☐support 帳號密碼每次啟動都被設定檔重設（安全 / 低）：Program.cs 的預設帳號建立區塊會在

每次啟動覆寫 support 的密碼。好處是設定即真相，壞處是無法在畫面上改密碼、且設定檔一旦外流即等同 帳號外流。可考慮改為「只在帳號不存在時建立」，並提供首次登入強制改密碼。
