Graph RAG 待辦盤點（P1～P9 完成後）

建立日期：2026-07-28　｜　對版：1.0.91　｜　定位：Graph RAG 九個階段交付後的剩餘事項總表

本文回答一個問題：Graph RAG 還有哪些事情需要處理？ 內容含「要做的」與「刻意不做的（附理由）」，避免同一個問題被反覆重新討論。

相關：Graph RAG 導入分析與實作藍圖（§9 分階段藍圖）、各階段 changelog、12-RAG 系統補強總彙整與優先序

功能面已覆蓋藍圖 §9 的全部規劃項目。剩下的問題不在功能，而在「量測、效能、可觀測性、暴露面」四類。

2. 要做：P10～P13

P10　圖檢索評測題組　✅ 已於 1.0.92 完成

詳見 changelog。實作時另發現並修掉一個資安缺口：GlobalMapAsync 取的是評測執行者的環境身分而非樣本標註的模擬身分，等於全域問答的權控從來測不到。

問題：九個階段做完，沒有任何數據能回答「圖到底有沒有提升召回」。Services/Embeddings/RagEvaluator.cs 全檔沒有圖的概念；RagEvalParamSnapshot 只記 TopK／VectorWeight／KeywordWeight／MinScore 與兩個門檻，沒記 GraphWeight／GraphMaxHops／GraphHopDecay，所以既有基線根本無法對應到產生它的圖參數。

這是目前最大的風險：後續任何優化都沒有判準，也無法證明沒有改壞。

要點：RetrievalHit 已帶 VectorScore／KeywordScore／GraphScore 三個分項，因此確定性的圖指標不必跑第二次對照組檢索——直接由單次檢索推導「沒有圖就召不回的命中」即可，零額外成本。另加 global 模式評測（需 LLM），並補上 GlobalMapAsync 的模擬身分參數，否則 global 的權控從來測不到。

P11　檢索熱路徑快取　✅ 已於 1.0.94 完成

詳見 changelog。⚠️ 最大的設計約束是「只能快取未套 ACL 的原始列」——快取全域共用且鍵不含身分，存進過濾結果就會讓先檢索者的可見範圍被後檢索者取用。

問題：RetrievalService.SearchGraphAsync 每次檢索都全表載入已核可別名、全部錨頁節點、全部已核可三元組（含雙 join）——RetrievalService.cs:143 / 157 / 178。P4 記載、P7 只補索引、P8 再記，至今未做。

紅線：只能快取未套 ACL 的原始列，per-request 才在記憶體過濾；絕不快取已套 ACL 的結果。別名表無 Teams，可直接快取建好的對照表。

P12　全域圖譜作業狀態表 ＋ 零三元組重抽入口　✅ 已於 1.0.95 完成

詳見 changelog。關鍵設計：刻意不進 PipelineNames（那是 per-record 管線的常數集，硬塞會讓 recordId 失去意義），改以 JobType 字串識別但仍重用取消註冊表。

問題一：社群重建／別名生成的狀態只活在記憶體（GraphCommunityBuildState、GraphAliasBuildState），而 PipelineJobQueryService 一律由 DB 狀態推導、刻意不讀佇列深度——所以這兩個作業在 /pipeline-jobs 看不到、不能取消、服務重啟靜默丟失訊號。不建表就無解。

問題二：「抽取／重抽三元組」入口在知識來源頁，而知識圖譜審核頁是三元組導向的，看不到「零三元組（抽取失敗）」的來源——而那正是最需要重抽的情況（P7 自陳）。

P13　圖譜唯讀 Web API　✅ 已於 1.0.96 完成

詳見 changelog。實作時另修掉一個既有問題：host 型整合測試的間歇性紅燈（ApiTestApplicationFactory 寫行程層級環境變數、多實例並行互相蓋掉）。

問題：Web/Controllers/ 沒有圖譜控制器，P9 的兩項能力只有 MCP 用戶端能用，一般 REST 呼叫端取用不到。開兩支唯讀端點（全域問答、實體鄰域），走與 MCP 同一條 ACL 把關程式碼，不另寫一套。

3. 已知破口：暫不處理（附出處與理由）

項目出處暫不處理的理由
同名不同物誤併（兩來源不相關的「王小明」）P4精確名合併是 GraphRAG 實體解析的基準做法；要解需嵌入式實體解析，成本遠高於目前受益
不支援逐團隊別名P5別名為全域治理；若未來確有「僅某團隊套用」需求，再擴 Teams 欄與 ACL
別名無稽核歷程P5目前核可紀錄已足夠追溯；歷程表屬治理強化，非正確性問題
NameCap=300 跨批同義對漏配P6目前以單次（≤cap）LLM 呼叫為主；分批比對需跨批交叉，複雜度不成比例
三個成本上限不可線上熱調（需重啟）P7刻意只做 appsettings 層；若確有線上調參需求，再比照 GraphWeight 走四點同步鏈
GraphMaxNodes 截斷非全域最佳P8它是防爆安全閥、不是排序機制，語意本就如此
圖譜瀏覽 SVG 節點多時擁擠P8表格才是完整資料的權威呈現，SVG 為輔助
MCP global 只做 map 不做 reduceP9刻意設計：MCP 工具回傳「參考資料」而非「最終答案」，與 knowledge_ask 既有語意一致
MCP 無圖譜專用節流P9GraphGlobalCommunityCap（預設 20）已限住單次成本；頻率節流待實際壓力出現再做
無寫入型 MCP 圖譜工具P9與 MCP 文件的既有非目標一致：受治理資料一律經人工審核介面寫入

4. 選配未做

  • 節點／社群摘要向量嵌入：藍圖 §8 即標為選配，P8 仍列未實作。目前圖檢索以「頁↔頁」邊與三元組展開為主，尚未出現需要對節點做語意近似的場景。
  • rerank：至今僅有 分析文件，未實作。藍圖 §10 原建議優先序是 rerank 早於 Graph RAG，實際執行順序相反——建議待 P10 的評測數據出來後再依數據決定。

5. 未達觸發條件：建議不做

  • 專用圖庫（Neo4j／PostgreSQL AGE）：藍圖 §4.4 的三個觸發條件——(a) 需 3 跳以上深度遍歷、(b) 邊數達百萬級、(c) 需 PageRank 等複雜圖演算法且關聯式方案效能不足——目前皆未達成。跳數上限目前為 3，已足夠。屆時可經一層 IGraphStore 抽象替換（比照現有 IVectorStore）。
  • Agentic RAG：屬另一條技術路線，見技術路線分析，不在 Graph RAG 範圍內。

6. 驗證債

  • P9 自陳未執行：以真實 MCP 用戶端＋兩把不同團隊的 API Key 做端到端交叉驗證（需部署環境與金鑰）。單元測試已釘住 RecordAccessScopeProvider 的三條解析路徑與 global 的社群子集判定，但端到端未實跑，留給部署後驗收。
  • docs/guides/ 22 份操作手冊仍對版 1.0.71，未涵蓋知識圖譜審核頁、圖譜瀏覽與全域問答的操作說明（文件債補正一文已記載）。
