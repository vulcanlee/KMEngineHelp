背景管線處理過程逐則 toast 通知（1.0.23）

  • 日期：2026/07/20
  • 版本：1.0.22 → 1.0.23
  • 類型：功能新增（＋順手修一個既有 bug）
  • 觸發來源：使用者上傳會議影片後，網頁上只看到 2 則通知（開始、完成），但後端日誌顯示中間有一長串處理動作（取得時長、切片、逐段轉錄、簡繁轉換、存逐字稿、送 LLM…），希望這些過程都能在畫面上看到
  • 相關：會議 AI 自動化、會議模組 UI 優化（1.0.21）

一、問題的本質：中間階段沒有回報通道

原本畫面上那 2 則通知分別來自：

通知來源機制
「已開始轉錄…」MeetingRecordingUploadModal.razor.cs上傳成功當下同步彈出
「《標題》會議紀錄已產生」MeetingViewView.NotifyMinutesTransitions5 秒輪詢比對 Meeting.MinutesStatus 轉換

中間所有動作只寫進 NLog 日誌，完全沒有對 UI 曝光。背景管線與 UI 之間唯一的連結是「寫 DB 狀態欄位 → 前端輪詢讀取」，而狀態欄位只有一個當下值。

光是「輪詢讀當下狀態」解不了這個問題：使用者提供的日誌顯示，20:00:57.4319 ~ .4659 這 0.03 秒內連續發生了「第 2/2 段轉錄完成 → 轉錄完成 → 會議紀錄排入佇列」三件事。5 秒才看一次的輪詢必然把它們壓成一則。

二、做法：追加式事件表 ＋ 游標輪詢

新增 PipelineProgressEvent 資料表，管線每完成一個動作就 append 一列；前端以「上次看過的最大 Id」為游標撈新事件，一次撈齊、逐則彈 toast。不新增 SignalR 或記憶體事件匯流排——沿用既有輪詢基礎建設，風險最低。

Processor 任一深處
  └─ progressReporter.Report("已切成 3 段，開始逐段轉錄。")   ← 非阻塞、無 DbContext、失敗隔離
       └─ Channel（記憶體）
            └─ PipelineProgressWriterBackgroundService（自建 scope 的獨立 DbContext）
                 └─ PipelineProgressEvent 資料表（追加式）
                      └─ 前端每 5 秒以 Id 游標撈新事件 → 逐則彈 toast

端到端延遲 ＝ 寫入約 5ms ＋ 輪詢等待 0~5 秒 ＝ 最差 5 秒、平均 2.5 秒，與既有狀態通知的延遲特性一致。

整套直接照抄既有的 token 用量樣板

ITokenUsageRecorder（Singleton＋Channel、非阻塞、失敗隔離）＋ TokenUsageWriterBackgroundService（自建 scope 批次落地）這組樣板與需求幾乎同構，沿用而非另創。兩點刻意不同：

面向ITokenUsageRecorderIPipelineProgressReporter
無情境時仍寫入（稽核資料要留全）直接丟棄（沒有提交者就沒人看得到）
輸入解析TokenUsageParser 解析 JSON不需要——訊息已是成品字串

最大的省法：OperationContext 已經夠用

OperationContext（AsyncLocal）的 OperationInfo(Operation, RecordId, UserAccount, UserName, Teams) 已由各 *BackgroundService 迴圈 Push，且 Operation 推的字串與 PipelineNames 常數值相同。所以呼叫端只需要：

progress.Report("已切成 3 段，開始逐段轉錄。");

管線名、紀錄 Id、提交者全部自動帶入，不必逐層傳參數，Processor 深處任何地方都能呼叫。

獨立一支 writer，且刻意不加批次計時器

沒有併進 TokenUsageWriterBackgroundService，因為兩者的 flush 策略相反：token 用量是無人等待的稽核資料、批越大越有效率；進度事件有使用者盯著螢幕，必須低延遲。

writer 採「await foreach 阻塞等待 ＋ TryRead 只撈已在通道裡的、撈不到就立刻寫」模式，典型情況是「1 筆 → 立刻 SaveChanges」。若照 token 那支加「等 500ms 湊批次」只會白白疊加延遲，而事件到達速率本來就低（每條管線每幾秒才 1 則），湊批幾乎永遠只湊到 1 筆。

三、畫面行為

6 個背景管線清單頁（會議記錄、音訊轉錄、文件萃取、圖片清單、知識來源、AI 技能）都接了 PipelineProgressToaster。以上傳一支會被切成 3 段的會議影片為例：

開始處理媒體檔案…
媒體長度 00:42:15，準備轉錄。
檔案較大，將切成 3 段分批轉錄。
第 1/3 段轉錄完成（33%）。
第 2/3 段轉錄完成（67%）。
第 3/3 段轉錄完成（100%）。
已完成簡繁轉換（台灣繁體）。
逐字稿已儲存（約 12,340 字）。
✅ 語音轉錄完成。
已排入會議紀錄產生佇列…
開始產生會議紀錄…
已讀入逐字稿（約 12,340 字），送交 AI 分析…
✅ 會議紀錄產生完成。

最後既有的右下角 NotificationService 卡片照舊出現，兩套通知並存不衝突。

三個 UI 決策

  1. 開頁不補播歷史：InitializeAsync() 把游標設到目前最大 Id。階段訊息過期後毫無價值（使用者要的是「現在到哪」），補播只會在開頁瞬間洗版；終局結果本來就有 NotificationService 卡片與清單狀態欄呈現，不會漏。
  2. 對話窗開啟時 silent: true：只推進游標不彈。若停著不推進，關窗瞬間會一次爆出整段累積的事件。
  3. PumpAsync 放在「有無進行中項目」檢查之前：終局那幾則正好發生在狀態剛翻成終態的那一刻，放後面會被吃掉。代價是每 5 秒多一次索引 seek，有 (UserAccount, Id) 覆蓋索引且通常回 0 列，可忽略。

為什麼逐則彈出不會洗版

切 20 片時每片要呼叫一次 OpenAI、每片耗時 10~40 秒，所以 20 則進度是分散在 5~13 分鐘內產生的，每次輪詢平均只撈到 0~1 則。日誌裡那個 0.03 秒爆發 3 則的情形是唯一的爆量點，上限就是 3~4 則。真正的兩個洗版風險（開頁補播、關窗爆量）已由上述決策 1、2 解掉，故不做節流或合併。仍保留 MaxToastPerTick = 8 作為防禦性上限。

四、權控：UserAccount 精確比對，刻意不套團隊權控

這是本次唯一的資安判斷點，論證寫在 PipelineProgressQueryService 的 XML 註解裡（避免未來維護者看到查詢沒用 TagStringHelper 而誤以為是漏洞）：

事件的 UserAccount 來自 OperationContext ← PipelineJob ← 由入列服務在 UI 執行緒寫入 CurrentUser.Account，而所有入列服務在入列之前都已跑過團隊權控。因此「事件的 UserAccount = X」蘊含「X 當時對該紀錄有權限」，X 看自己的事件不構成越權。WHERE UserAccount = @me 這個條件嚴格窄於團隊權控。

額外防線：事件訊息不得含紀錄標題或任何內容本文，只放階段名、計數、字數、大小。保持訊息無狀態，即使日後使用者被移出團隊，舊事件也不會洩漏。管理員亦不豁免——這是 UI 回饋不是稽核查詢。

五、順手修掉的既有 bug：文件萃取管線的身分遺失

追查入列點時發現，IDocumentExtractionQueue 是 8 條管線中唯一沒有採用 PipelineJob 的：它排的是裸 int，且 DocumentExtractionBackgroundService 從未 OperationContext.Push（只有 LogScope）。

後果不只是本次的進度通知發不出來——該管線的 token 用量長期歸屬不到使用者。

已補齊為與其他 7 條同構（Channel<PipelineJob>、EnqueueAsync 帶 userAccount/userName、背景服務 Push OperationContext），並新增 PipelineEnqueueIdentityTests 掃描原始碼守護：Service 層不得出現單一引數的 EnqueueAsync(x) 呼叫。

這部分拆為獨立 commit，與主功能分開。

八、已知限制

  • 重啟復原的作業沒有進度通知：RecoverPendingAsync 刻意以 null 身分入列（非使用者觸發，無人在等 toast）。
  • 會議紀錄產生階段本質無中途進度：MeetingMinutesGenerationService.GenerateAsync 是單次非串流 LLM 呼叫，只能報「送出」與「回覆」兩點，中間那 20 秒無法細分。
  • 事件保留 3 天：這是短命 UI 回饋資料，非稽核紀錄。若日後要做「處理歷程回顧」需重新評估保留策略。
