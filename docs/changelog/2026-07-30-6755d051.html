低比值回溯偵測：自動找出可能已被靜默截斷的舊資料（1.0.115 → 1.0.116）

  • 變更日期：2026/07/30
  • 版本：1.0.115 → 1.0.116
  • 性質：程式變更（src/）＋測試＋文件。無模型變更、無新表、無 migration。
  • 對應盤點項：後續四項的第一項（原盤點清單的 #6＋#7 合併）
  • 編碼：UTF-8（繁體中文，含 BOM）

一、解決什麼

規模守門三項（1.0.112～114）站在三個時間點防止未來的截斷。但留下一個沒有答案的問題：

1.0.112 之前清洗的知識來源，可能已經被靜默截斷，而且無從從資料本身分辨。

那時候狀態是「已清洗」、信心分數可能還很高、沒有任何註記。先前的建議是「人工用三步法逐筆檢查，或乾脆全部重新清洗」——兩者都不現實。

唯一看得出端倪的是「清洗後 ÷ 彙整前」的比值，而 P2（1.0.113）已經把這個比值算出來了。這一版就是拿它來自動指認。

二、看得到什麼

在哪裡顯示
清洗對話窗「上次清洗後」那一行下方，比值低於門檻時顯示警示，說明可能是 1.0.112 之前被截斷、建議重新清洗一次驗證、並提醒也可能只是內容本來就高度重複
資料一致性巡檢（/data-consistency）新增第三個區塊「低比值來源（N）」，把全庫比值偏低者一次列出（標題／比值／彙整量／清洗後／清洗時間／單筆「重新清洗」）。預設依比值由小到大排序，最可疑的在最上面

門檻：SystemSettings.Cleaning.CleanedRatioWarnBelow，預設 0.30（取自分盒指南 §4.2 的「正常 0.5～1.0、低於 0.3 高度懷疑」）；0 或負數＝停用；剛好等於門檻不算可疑。

三個刻意的設計選擇

① 判斷仍做成模型上的純計算屬性。 與 P3 一致：邊界（低於／等於／高於門檻、未清洗、門檻停用）可以用不碰 DB 與 UI 的測試釘住。

② 文案一律寫「可能」與「值得看一下」，不寫「壞了」。 內容本來就高度重複的素材（大量制式表單、範本化工單）合理地會有很低的比值——那是誤報。把提示寫成判決會讓使用者對整個功能失去信任。

③ 巡檢只查有清洗內容的來源。 這一項的成本是全部檢查裡最高的（每筆要量測成員檔案大小），所以未清洗者完全不碰，並在文件中明白告知「來源很多時這一頁會比以前慢」。

一處既有測試的機械性更新

DataConsistencyService 多了兩個建構式參數，所以 DataConsistencyTests.Fx.CreateConsistencyService 必須跟著改。這是建構式呼叫的機械性更新，沒有任何斷言被改動；而且新參數的門檻預設為 0（停用），既有測試的行為完全不變。

四、測試（新增 14 條；全量 1098 → 1112，0 失敗）

純模型邊界（CleaningAggregateWarnTests）：

  • 比值 0.29 可疑／0.30 剛好等於門檻不可疑／0.31／0.95 不可疑
  • 未清洗（CleanedRatio 為 null）不警示——否則每一筆草稿都會被標紅
  • 門檻 0／-1 停用（即使比值 0.00）
  • 程式預設值為 0.30
  • 🔴 設定漂移守門：讀 repo 真實 appsettings.json，斷言該鍵存在且與程式預設一致

巡檢掃描（KnowledgeSourceMeasureTests，沿用該檔已能寫檔的夾具，不複製第二份）：

  • 比值 0.05 → 被列出，且 TotalBytes／CleanedBytes／Ratio 三個數字都正確
  • 比值 0.8 → 不被列出
  • 未清洗的來源不進入這項檢查
  • 門檻 0 → 完全不回傳
  • 🔴 團隊權控：非管理員只看到自己團隊的那一筆

七、對使用者的實際意義

先前「1.0.112 之前的舊資料怎麼辦」只有兩個選項：人工逐筆稽核，或全部重新清洗。現在是：

  1. 開 /data-consistency
  2. 看「低比值來源」那一節列出哪幾筆
  3. 逐筆按「重新清洗」——若真的被截斷，這次會直接失敗並說明原因

⚠️ 清單為空不代表一定沒問題（截斷幅度小的可能不到門檻），但它把「全部都要查」縮小成「先查這幾筆」。
