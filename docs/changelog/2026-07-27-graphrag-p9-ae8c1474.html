Graph RAG P9：MCP 暴露圖譜能力（1.0.90 → 1.0.91）

  • 日期：2026-07-27
  • 版本：1.0.90 → 1.0.91
  • 類型：新增功能（Graph RAG 第九階段；無新表、無 migration）

背景

P1～P8 把 Graph RAG 做完整了，但全部只有 Blazor UI 使用者能用：Web/Mcp/ 的五個工具沒有任何圖譜參數，Web/Controllers/ 也沒有圖譜 API。也就是說外部 AI Agent 透過 MCP 只能做精準檢索，問不出「綜觀全部」也問不出「A 和 B 有什麼關聯」——而這兩件事正是導入 Graph RAG 的理由。

本階段把兩項圖譜能力接到 MCP：knowledge_ask 的 global 模式、以及新工具 knowledge_graph_neighbors（直接重用 P8 的 GetNeighborhoodAsync）。

動工前先驗的紅線（結論：安全，且已補測試釘住）

計畫列的唯一 leak=0 風險是：GraphCommunityService.GetAccessibleSummariesAsync 用 IRecordAccessScopeProvider.GetAsync() 取 scope，而 MCP 沒有 Blazor circuit——萬一取不到正確身分，global 模式就會以錯誤 scope 放行他隊社群摘要。

逐條讀 Web/Auth/RecordAccessScopeProvider.cs 後確認三條解析路徑都安全：

  1. McpIdentityResolver.ResolveAsync 已填 CurrentUserService（含 IsAdmin／TeamList）→ 直接用它。
  2. 未填時 fallback 到 HttpContext 的 Sid claim（MCP 的 API Key／JWT 認證會帶）→ 從 DB 取回角色團隊。
  3. 兩者皆無法解析 → 回 (false, [])＝fail-closed，只看得到公開內容。

前提是工具要先 ResolveAsync 再呼叫 GlobalMapAsync——KnowledgeAskTool 本來就是這個順序。另有既有實證：KnowledgeSearchTool 早就在 MCP 下用同一個 provider。

⚠️ 既有的 MCP 測試都用 stub scope，等於這條路徑從來沒被測過。本次新增 Mcp/McpAccessScopeTests，直接測真正的 RecordAccessScopeProvider，把上述三條路徑各釘一條（外加管理員旗標的傳遞）。

變更

1. knowledge_ask 新增 mode 參數

mode行為
local（預設，省略即此值）精準檢索：向量＋關鍵字＋圖鄰域三路混合。與 1.0.90 之前完全相同。
global全域問答：對「呼叫者有權的社群摘要」做 map-reduce（P3）。

global 模式的回傳差異（已寫進工具的 [Description]，Agent 讀得到）：

  • sources 恆為空、topScore 恆為 0——社群摘要沒有 chunk 層出處，也沒有相似度可言。
  • confidence 僅表示「有無取到可用的社群重點」。
  • 取用的社群改由新欄位 usedCommunities（標題清單）回報；KnowledgeAskResult 另加 mode 欄位讓呼叫端能自我確認。
  • 不套用 categories／teams 篩選（社群是跨來源全域聚合，逐社群篩選沒有意義）。
  • 無可用社群時 answerContext 帶回可行動的原因（提示先建立社群摘要），而非空字串。
  • 聊天紀錄的 ScopeNote 加上「模式：local/global」。

⚠️ 無法辨識的 mode 值明確拋 ArgumentException，不靜默退回 local——靜默退回會讓呼叫端以為自己走了 global。大小寫與前後空白則接受（"Global " → global）。

2. 新工具 knowledge_graph_neighbors

仿 KnowledgeSearchTool 結構（McpToolLog.BeginToolScope ＋ McpIdentityResolver），包一層 P8 的 GraphTripleService.GetNeighborhoodAsync：

  • 參數：entityName（別名自動解析）、maxHops（1～3，預設 2）。
  • 回傳：nodes（實體名＋跳數）、relations（主詞—關係—受詞＋跳數）、found、truncated。
  • 只回傳已核可三元組；三元組與兩端節點兩層都套團隊權控；節點上限 100，達上限 truncated=true。
  • 純資料庫查詢、不呼叫 LLM，故刻意不推 OperationContext、不新增 LlmTokenUsage.Operation* 常數（沒有 token 可歸屬，加了只會多一個永遠是 0 的作業別）。
  • 註冊方式：WithToolsFromAssembly() 會自動掃描 [McpServerToolType]，不需改 DI 或 Program.cs。

安全與相容（leak=0）

  • global 模式的 ACL 由 GetAccessibleSummariesAsync 把關，且社群摘要採更嚴的子集判定——需社群 Teams 聯集 ⊆ 使用者團隊或純公開。已由測試釘住：只屬甲隊者看不到「乙隊」社群，也看不到「甲隊∪乙隊」社群。
  • knowledge_graph_neighbors 的 leak=0 由 GetNeighborhoodAsync 的雙層權控保證（任一端節點越權，整條關係就不出現）。
  • 向後相容：省略 mode 時行為與 1.0.90 完全相同（回歸測試釘住）；KnowledgeAskResult 只新增欄位（mode／usedCommunities），既有欄位語意不變。

已知限制（未來增量）

  • global 模式只做 map、不做 reduce：回傳的是各社群重點的彙整文字，最後的綜合成答留給呼叫端的 Agent 自己做（與 Blazor UI 會再跑一次 reduce 串流不同）。這是刻意的——MCP 工具回傳「參考資料」而非「最終答案」，與 knowledge_ask 既有語意一致。
  • global 模式的 LLM 成本＝可存取社群數次呼叫（受 GraphGlobalCommunityCap 控管，預設 20）。Agent 若頻繁呼叫會放大成本，目前沒有針對 MCP 的額外節流。
  • 仍沒有寫入型圖譜工具（新增/核可三元組），與 MCP 文件的既有非目標一致。
  • 圖譜能力仍未暴露為 Web API Controller（只有 MCP）。

  • Mcp/KnowledgeAskToolTests +7：省略 mode 等同 local（回歸）、global 取用社群且無 chunk 出處、global 的 leak=0（他隊與跨隊社群都不可見）、無社群回 Insufficient 且帶原因、mode 大小寫/空白不敏感（Theory 2 列）、未知 mode 拋錯。
  • Mcp/KnowledgeGraphNeighborsToolTests +5：欄位對映、預設 2 跳可達第 2 跳、maxHops=1 不含第 2 跳、他隊關係不得外洩（leak=0）、查無實體回 found=false。
