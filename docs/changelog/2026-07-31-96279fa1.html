一、解決什麼

「我改了或刪了這筆，會連帶發生什麼」在整個 docs/ 裡沒有任何一份文件回答。散落的片段有（知識來源加工與清洗規則設定使用指南 的「成員異動後該怎麼做」、系統監控與健康檢查指南 的巡檢頁說明），但沒有一處把「哪些東西會跟著消失、哪些只是被標成過時、哪些完全沒反應」講在一起。

這是日常操作最常撞到的一類問題，而且猜錯的代價很高——可能誤刪整條知識線，也可能以為刪掉了其實還在。

二、查證方法（不是推測）

三個切面逐一交叉，每一條都讀到程式：

切面範圍
DB 連鎖BackendDBContext.OnModelCreating 的 11 條 OnDelete、37 個 DbSet
磁碟檔每一支服務的刪除路徑有沒有主動刪實體檔
過期標記ContentStale 的全部寫入點與唯一清除點，以及它到底擋不擋事

原本估的是「20 個有 DeleteAsync 的服務」，實際查下來 GraphEdgeService 與 GraphCommunityBuilder 不是使用者可按的刪除（它們用 ExecuteDeleteAsync 做整批重建前的清除），所以真正的數字是 18 個。文件裡照 18 寫。

三、查出來最重要的三件事

3.1 ⚠️ 刪掉素材後，問答還是查得到

刪除影音轉錄／文件轉文字／圖片解讀／會議紀錄時：原始檔與轉出文字會刪、引用它的孤兒成員當場移除、知識來源標成 內容已過時。

但清洗檔與向量索引原封不動。 清洗當下已經把成員內容抄成一份獨立檔案，向量是從那份檔案建的——所以那份你以為已經刪掉的文件，AI 知識問答照樣拿它作答、出處也照樣列出來，直到你重新清洗為止。

這同時是資安問題：使用者發現不該上傳而刪除時，會誤以為內容已經移除。

3.2 ⚠️ 而且「重跑管線」也不夠乾淨

重新蒸餾採的是版本化，不是覆蓋（DistillationProcessor）：舊的現行版 Wiki 頁標成「已汰換」保留不刪（供稽核與時點查詢），只是向量 IsCurrent = false 退出一般檢索。

所以重跑完管線，那些頁還在資料庫與磁碟上。要真正移除只有一條路：刪掉整個知識來源——那會把清洗檔、全部 Wiki 頁（含已汰換的）、全部向量一次帶走。

判斷準則寫進文件：「內容過時」→ 重跑管線就好；「這份東西不該存在」→ 刪掉整個知識來源。

3.3 「過時」只是標籤，不擋任何事

ContentStale 的寫入點有六處（素材刪除／編修／換版、成員新增／移除／換順序），清除點只有一個：重新清洗完成（CleaningProcessor）。

它只在三個地方顯示（知識來源清單的徽章、/data-consistency、/rag-diagnostics），不阻擋任何操作。

四、一項要更正的先前推測

規劃這一項時我寫過「刪素材會留下孤兒成員」。不對。 四個素材服務傳的是 MarkOwningSourcesStaleAsync(..., removeOrphanItems: true)，孤兒成員當場就被移除了。

巡檢頁的「孤兒成員」區塊仍有存在意義——舊版資料，以及下面 §5.1 那條路徑會產生。

五、順帶查出的三項落差（本版不修，只記錄）

寫進文件 §七，並在此明列。這一階段的承諾是「把現況說清楚」，改行為要配測試，混進來會讓交付範圍失控。

5.1 用 REST API 刪會議，行為與畫面不一樣

DELETE /api/meeting/{id} 走 MeetingRepository.DeleteAsync，畫面走 MeetingService.DeleteAsync——兩條不同的程式路徑。

團隊權控刪附件實體檔清孤兒成員＋標過時
畫面（MeetingService）❌ 見 5.2✅✅
REST API（MeetingRepository）✅❌❌

從 API 刪會議會留下磁碟孤兒檔、孤兒成員列，而且引用它的知識來源不會被標成過時——使用者不會知道那個來源已經失準。

MeetingKnowledgeSourceStaleTests 完整釘住 Service 那條路徑（6 條測試，含兩條刻意的反證），但沒有涵蓋 Repository 這條。

5.2 四個素材的 DeleteAsync 沒有團隊權控檢查

MediaTranscriptionService／DocumentExtractionService／ImageRecognitionService／MeetingService 的 DeleteAsync 都沒有 IsTeamAccessible，而同檔案的 RetryAsync 有、KnowledgeSourceService 與 WikiPageService 的刪除有、MeetingRepository（API）也有。

實務可利用性低（清單查詢已套權控、Blazor Server 元件狀態在伺服器端，使用者只刪得到畫面上渲染出來的列），但這是同一個服務兩個方法標準不同的防禦縱深不一致。

5.3 分類／團隊／提示詞刪除不檢查是否還被引用

標籤欄位是分隔字串、無外鍵，刪主檔既不被擋也不回寫紀錄，留下「主檔已不存在」的名字。這是既有設計取捨、不是新問題，但符合本文件主題故一併列出。
