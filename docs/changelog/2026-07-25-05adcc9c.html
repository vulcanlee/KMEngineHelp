啟動安全檢查守門修正（1.0.65）

  • 日期：2026/07/25
  • 版本：1.0.64 → 1.0.65
  • 類型：資安修正
  • 影響範圍：Production 啟動流程、系統健康監控「身分驗證」項

一、問題

StartupSafetyValidator（Program.cs:47，在 builder.Build() 之前執行的 fail-fast 檢查）有兩個守門永不觸發：

守門程式比對的常數appsettings.json 實際值
JWT 金鑰DevelopmentOnly-ChangeThisJwtSigningKey-AtLeast32CharsDevelopmentOnly-ChangeThisJwtSigningKey-AtLeast32CharsSigningKeySigningKeySigningKeySigningKey
support 密碼support1qaz@WSX

string.Equals 永遠為 false，因此以倉庫現狀直接跑 Production，四項檢查全數通過——沿用開發預設金鑰與內建管理密碼都不會被擋下。

根因

「硬編字面值必須等於 appsettings.json 預設值」這個假設會隨時間漂移，而且沒有任何機制強制兩者同步。 兩個放大因素：

  1. 同一份錯誤常數存在兩處。SystemHealthService 也各自維護一份 DevelopmentSigningKey，用於「身分驗證」健康項（權重 15）判定 usesDevelopmentKeyInProduction——同樣永不觸發。各自維護正是持續漂移的來源。
  2. 既有測試一直是綠燈，但它測的是舊字面值。ApiIntegrationTests.ProductionSafetyValidation_WithDevelopmentDefaults_ShouldFailFast 手動餵入 …AtLeast32Chars 與 support，而非真實設定值，所以缺陷長期無人察覺。

二、修正

2.1 新增 Web/Configuration/UnsafeDefaults.cs

集中「什麼算不安全預設值」的判定，供啟動驗證器與健康檢查共用：

  • IsUnsafeSigningKey —— 改以 DevelopmentOnly- 前綴判定（StringComparison.Ordinal）。這是本 repo 的既有命名慣例，日後金鑰再加長尾巴、換字串內容都擋得住。空白不算（空白／過短由 JwtSettings 的 [Required]／[MinLength(32)] 負責）。
  • IsUnsafeSupportPassword —— 密碼沒有自然前綴，改維護一份已知不安全值集合：support（BootstrapSettings 類別內預設值）與 1qaz@WSX（appsettings.json 現值）。

2.2 兩處呼叫端改為共用

  • StartupSafetyValidator：移除私有常數，兩處 string.Equals 改呼叫 UnsafeDefaults。另三項檢查（Swagger 明確設定、Redis 連線字串）本來就正確，未動。
  • SystemHealthService：移除重複常數，改用 UnsafeDefaults.IsUnsafeSigningKey。行為變化：Production 沿用開發金鑰時，「身分驗證」項現在真的會轉為異常。

2.3 新增 StartupSafetyValidatorTests（26 個測試）

關鍵一條 Validate_WithRepositoryAppSettings_RejectsProduction：直接從磁碟載入本 repo 的 KnowledgeExtraction.Web/appsettings.json，斷言 Production 驗證必須拋例外、且訊息同時含 JwtSettings:SigningKey 與 BootstrapSettings:SupportPassword。定位檔案沿用 MenuPermissionAlignmentTests 既有的「從輸出目錄逐層往上找原始碼」寫法。

這是唯一能結構性防止同類漂移的作法：日後任何人改動 appsettings.json 的預設金鑰或 support 密碼卻沒同步 UnsafeDefaults，這條測試立刻紅燈。

其餘涵蓋：現值與歷史字面值都被擋、Swagger 空白與 Redis 空連線被擋、安全設定完全通過（避免退化成「總是拋」）、非 Production 即使帶不安全值也直接通過、UnsafeDefaults 兩個判定式的 null／空白／大小寫邊界。

既有的 ApiIntegrationTests 那條保持不動——新邏輯下它仍通過（舊字面值符合前綴、support 在清單內），留著正好記錄歷史字面值。

三、刻意不做的事

  • 沒有改動任何設定值本身。SigningKey 與 SupportPassword 的開發預設維持原樣——那是開發便利性，且 guides 有十餘處以 1qaz@WSX 作為教學範例。守門只在 ASPNETCORE_ENVIRONMENT=Production 生效，開發與測試環境完全不受影響。
  • 沒有新增其他檢查。appsettings.Production.json 的 OpenAISettings:ApiKey 預設是佔位字串「在此填入 OpenAI API Key」且無人守門，但「沒有 API Key」不等於「不安全」（可能是刻意只用地端模型），擋啟動會誤傷合法部署。另記 backlog。
