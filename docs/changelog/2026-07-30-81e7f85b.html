三、本次新查證到的系統行為

以下是撰寫過程中對程式確認、且既有文件未記載的行為。兩項都屬「不會報錯」類。

#行為出處對使用者的意義
C1清洗第三步「分類」的 AI 建議結果會直接合併寫回 source.Categories，完全不檢查該名稱是否存在於分類主檔CleaningProcessor.cs:169-175（TagStringHelper.ToStored(merged)）產生「幽靈分類」
C2兩個「分類下拉」的資料來源不同：各清單頁的分類過濾讀分類主檔（CategoryService，見 KnowledgeSourceView.razor.cs:22,98）；AI 知識問答的「限定分類」讀已索引內容裡實際用到的分類（KnowledgeBaseChatService.GetFilterCategoriesAsync，由 VectorEmbedding.Categories 取 Distinct）同左幽靈分類會出現在問答頁下拉、卻不在清單頁下拉；兩邊詞彙不一致且無任何警告

解法已寫入文件：分類提示詞要明列詞庫並要求「只能從清單挑、逐字相符、不得自創」（基礎設定內容設計指南 §5.4）。

既有 基礎設定指南 §四 已記載 C2 的其中一半（「問答頁下拉不是讀主檔」），本次補齊另一半（反向也成立：AI 造的分類會出現在問答頁下拉）以及 C1 這個成因。

四、五段清洗提示詞的輸出契約（文件內容的事實基礎）

取自 LlmPromptDefaults.cs 的內建預設與 CleaningEnhancer.cs 的接手處理：

步驟輸出契約失敗行為出處
去重清洗後內容本身，無任何說明前後綴可降級：沿用未去重內容並記備註CleaningEnhancer.cs try/catch
遮罩敏感資訊以 【已遮罩】 取代⚠️ 不吞例外——整筆清洗失敗（刻意的安全設計）MaskAsync（無 try/catch 包覆）
分類名稱以「、」分隔於同一行可降級：不給分類ParseCategories（分隔符含 、, ，\n ; ；）
摘要一段摘要＋另起一行 關鍵實體：可降級：無摘要LlmPromptDefaults.CleaningSummary
信心只有一個 0～1 小數解析不出 → null → 整筆轉「待審核」ParseConfidence；CleaningEnhancer.cs 註解明載

另記四層提示詞覆蓋順序（CleaningEnhancer.cs:132-136 的 promptResolver.ResolveAsync）：清洗設定檔欄位 → 提示詞清單同名保留鍵 → appsettings → 程式 fallback。appsettings.json 的 LlmPrompts 區段目前 20 個鍵全為空字串，所以實際生效的預設值來自 LlmPromptDefaults。
