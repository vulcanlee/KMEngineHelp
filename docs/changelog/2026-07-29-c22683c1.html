AI 知識問答「新對話」按鈕、「我的對話」關鍵字搜尋（1.0.104 → 1.0.105）

  • 日期：2026-07-29
  • 版本：1.0.104 → 1.0.105
  • 類型：功能新增（AI 知識問答／我的對話）
  • 有 migration：AddChatSessionQuestionsIndex（SQLite 20260729113727；SqlServer 20260729113744）

背景

使用者提出兩個缺口：

  1. 「AI 知識問答」頁沒有任何方式開始新的一段對話。sessionId 在首次送出時 lazy 建立，之後只能一直往同一段追加；想換題目只能重新整理頁面。而同一段對話的前文會被帶進 AI 的脈絡，主題跳掉還沿用舊對話容易讓答案被帶偏。
  2. 「我的對話」抽屜沒有搜尋。對話一多只能一頁一頁翻，而清單上只有「首輪提問前 40 字」的標題——第 2 輪之後問了什麼既看不到也搜不到。

分頁維持原狀（AntDesign Pagination、每頁 10 筆）：確認過現況已足夠，本次不動。

設計決策

搜尋範圍：提問文字＋標題，不含 AI 回答

資料庫裡原本完全沒有問答文字——LlmChatSession 只有中繼資料（標題、時間、輪數），全文存在磁碟 sessions/{yyyy}/{sessionId}.json。要能同時搜得到內容又讓 SQL 正確分頁，只有把可搜文字放進資料庫一途。

因此新增 LlmChatSession.QuestionsIndex：該段對話各輪提問以 \n 串接（換行分隔可避免跨輪誤命中），上限 4000 字、超出從尾端截斷（保留最早輪次）。

⚠️ 刻意不建索引、也不設 HasMaxLength：查詢是 LIKE '%關鍵字%'，前置萬用字元讓 B-tree 索引失效（補了也用不到），SQL Server 的 nvarchar(max) 更無法直接建索引；長度只在程式端截斷，DB 端不設限就永遠不會因超長導致 SaveChanges 失敗。

null ＝尚未建索引，這是回填的唯一判準

QuestionsIndex 為 null 代表該列還沒建索引，"" 代表已處理但無可索引內容。這個區分讓一次性回填能收斂，也讓搜尋在回填尚未跑完時仍可靠 Title 命中（predicate 有 QuestionsIndex != null 的短路）。

維護時「重算」而非「串接舊值」

AppendTurnAsync 在寫檔前已把本輪加進 file.Turns，記憶體裡就是完整清單，所以新對話與續談兩條路徑都只要 QuestionsIndex = BuildQuestionsIndex(file.Turns) 一行。回填器共用同一個函式，兩條路徑產出逐字相同，不會有「續談後 DB 值落後」或「回填與 append 互相覆蓋成不一致」的情形。

串流中「新對話」停用而非中斷

串流中若清空狀態，SendAsync 的 finally 仍會執行 LogTurnAsync：該輪會被寫進已清成 null 的 session、序號被推進，設定快照還會落在已不存在於 messages 的孤兒鍵上。要正確處理必須把「取消 → 等 finally 結束 → 再清」串起來，複雜度遠高於需求；輸入區既有的「停止」已提供中斷路徑。因此以 Disabled="@isStreaming" ＋ handler 內 early-return 兩層擋下。

變更

1. 資料模型（LlmChatSession ＋ 雙 provider migration）

  • LlmChatSession 新增 string? QuestionsIndex。
  • BackendDBContext 的 LlmChatSession 區塊補註解說明「刻意不建索引」的理由，避免日後有人補一個用不到的索引。
  • Migration 雙份：KnowledgeExtraction.AccessDatas（TEXT）與 KnowledgeExtraction.AccessDatas.SqlServerMigrations（nvarchar(max)），皆只有一筆 AddColumn、無 CreateIndex。

2. ChatSessionService

  • 新增 BuildQuestionsIndex(IEnumerable<ChatSessionTurn>) 與 QuestionsIndexMaxLength = 4000。
  • AppendTurnAsync：新建與續談兩條路徑各補一行維護 QuestionsIndex。
  • QueryMySessionsAsync 新增 string? keyword（置於 CancellationToken 之前，唯一呼叫端無位置參數傳 ct，來源相容），predicate 比對 Title 與 QuestionsIndex。大小寫敏感度依資料庫而定（Sqlite 敏感、SQL Server 依 collation），與管理員總覽的使用者關鍵字行為一致。
  • 新增 BackfillQuestionsIndexAsync(batchSize, ct)：撈 QuestionsIndex == null 的列（追蹤查詢）逐列讀全文檔轉換，回傳本批處理列數。

3. 一次性回填（ChatSessionIndexBackfillWorker）

新檔 Web/BackgroundServices/ChatSessionIndexBackfillWorker.cs，啟動後延遲 10 秒開始、每批 200 列、批間喘息 200ms，每批開新 scope 取新 DbContext（避免變更追蹤器累積整表），撈到 0 筆即結束。

⚠️ 收斂性是關鍵：讀檔失敗／檔案不存在／JSON 壞掉時仍寫入空字串，否則每次啟動都會重撈同一批而永不結束。已由測試釘住（Backfill_MissingFile_MarksProcessed_AndSecondRunDoesNothing）。

命名刻意不以 BackgroundService 結尾：它不是業務管線，不屬於 SystemHealthService.ExpectedPipelineBackgroundServices（由 PipelineNames 反射推導）的範圍。

4. 「我的對話」抽屜（MyChatSessionsDrawer）

  • 抽屜最上方新增搜尋列：Input（OnPressEnter）＋「搜尋」＋「清除」。
  • 搜尋列渲染在 loading 判斷之前：載入中與查無結果時都看得到，才有辦法改關鍵字或清除。
  • 不用 AllowClear：AntDesign 的叉叉不會觸發 OnPressEnter，會出現「輸入框空了但清單還停在舊結果」的錯覺，改用明確的「清除」鈕。
  • 查詢條件變更一律回到第 1 頁；抽屜關閉再開時關鍵字重置。查無結果時文案改為「找不到符合的對話」。

因為是共用元件，「知識來源 AI 對話」頁的抽屜也一併有了搜尋（該頁的 QuestionsIndex 同樣會維護）。

5. 「新對話」按鈕（KnowledgeBaseChatView）

標題列新增（順序：新對話 → 我的對話 → 系統提示詞設定）。StartNewChat() 清空 ResumeSession 的同一組七個容器（messages／sourcesByMessage／logIdByMessage／feedbackByMessage／settingsByMessage／expandedSourcePanels／expandedSources），並將 sessionId = null、nextTurnIndex = 0。

刻意不動：所有設定欄位（需求明定保留）、memberCache（純 id→model 快取，ResumeSession 也沒清）、userInput（使用者正在打的草稿）。sessionId 設為 null 後由下次送出才產生新識別碼，因此不會留下 0 輪的空對話。

測試

新增 ChatSessionKeywordSearchTests（11 條）：

面向守住什麼
索引維護首輪寫入、續談串接（\n 分隔）、超長截斷至 4000
搜尋語意命中第 2 輪以後的提問、命中標題、不命中 AI 回答、空白關鍵字＝不過濾
權控加了關鍵字之後仍限本人與來源出處（他人同關鍵字的對話不外洩）
回填舊格式檔可回填並搜到、缺檔列標記後第二次呼叫回 0（收斂）、不覆蓋已建索引的列

全量測試 1048 條全綠。
