一、解決什麼

清洗的去重與遮罩要把整份彙整內容重新輸出一遍，所以真正的天花板是模型的輸出上限。使用者需要在按下「清洗」之前知道這一盒有多大——但在此之前系統沒有任何畫面顯示這個數字：

  • /reports/content-inventory 只統計筆數（依媒體型別／團隊／分類／狀態）
  • 要判斷規模只能自己去 SystemSettings.ExternalFileSystem 各路徑下人工比對檔案大小

門檻太高，實務上等於沒人會做。1.0.113 起這個數字在畫面上。

二、看得到什麼

在哪裡顯示
知識來源加工 → 管理成員彙整量：約 1.2 MB（12 個可用成員，2 個略過）。加入／移除／上下移成員後即時更新
知識來源加工 → 清洗（確認清洗對話窗）同一行；若已清洗過，再多一行 上次清洗後：780 KB（比值 0.62）

清洗對話窗那一行比值就是 分盒指南 §4.2 的「比長度」檢查，而且出現在最需要它的時機——你要（重新）清洗之前，先知道上次是不是被截斷了。

為什麼先重構才加功能

BuildAsync 與 MeasureAsync 若各自維護一份「成員 → 檔案」的 switch，遲早會漂移成「量到的檔案和實際彙整的不是同一批」——而那種錯誤在畫面上看不出來，只會讓使用者依一個錯的數字做分盒決定。抽出 ResolveMemberPathsAsync 之後，兩邊連影音類的 fallback 順序（逐字稿優先、空的才退回「依提示詞產生」的內容）都是同一份規則，並有一致性測試釘住。

⚠️ 一個刻意保留的近似

判定「成員可用」的方式
BuildAsync（彙整）讀進來的內容不是空白
MeasureAsync（量測）檔案存在且長度 > 0（為了不讀檔）

所以「檔案只含空白字元」時，量測會算它可用、彙整會略過。這是有意識的取捨——列表與對話窗不該為了一個數字去讀數 MB 內容。處置：

  • 畫面文案一律寫「約」
  • 程式註解與 KnowledgeSourceSizeAdapterModel 的 XML 註解都寫明
  • 有一條測試把這個差異釘成已知行為（MeasureAsync_WhitespaceOnlyFile_IsKnownDivergenceFromBuild），而不是日後才被發現的迴歸

刻意不做的

不做理由
列表欄位顯示彙整量一頁 20 筆 × 每盒 15 成員 ＝ 每次渲染 300 次檔案查詢
加 DB 欄位存彙整量需雙資料庫 migration；即時量測已足夠
讀檔案內容來量測同上的 I/O 理由
比值用顏色暗示好壞「0.5～1.0 才正常」會隨模型與素材類型變動，寫進 UI 樣式就會過時。判準留在 分盒指南
/reports/content-inventory 加字數維度選配項，本次未做；報表仍只統計筆數

四、測試（新增 20 條；全量 1067 → 1087，0 失敗）

新檔 KnowledgeSourceMeasureTests.cs（自帶夾具，設齊四個素材根目錄＋清洗根目錄；不動既有夾具）：

  • 四型素材（文件／逐字稿／圖片解讀／會議紀錄）的位元組加總
  • 未完成、檔案不存在的成員計入 SkippedCount；空來源回 0
  • 🔴 一致性測試（本組最重要）：MeasureAsync 的可用數 等於 BuildAsync 的採用數，且可用者的標題確實出現在彙整本文、不可用者不出現
  • 影音 fallback：逐字稿為空時兩邊都取「依提示詞產生」的那一個檔，且量到的位元組等於該檔內容
  • 已知差異釘樁：空白檔案 → 量測算可用、彙整略過
  • 服務層：清洗後大小與比值（0.50）、未清洗時比值為 null、團隊權控拒絕（回全 0）與允許（有交集）
  • CompactNumberHelper.ToByteSize：B／KB／MB／GB 邊界與 0

⚠️ 既有測試一條都沒有修改。 既有的 SpyEmbeddingIndexQueue 是 public，直接重用而不重複實作。
