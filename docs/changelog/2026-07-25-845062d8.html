背景管線健康檢查改為由 PipelineNames 推導（1.0.66）

  • 日期：2026/07/25
  • 版本：1.0.65 → 1.0.66
  • 類型：可觀測性修正
  • 影響範圍：/system-health 的「背景管線」檢查項（權重 8）

一、問題

SystemHealthService.CheckBackgroundPipelines 的 expected[] 硬編六條背景服務名稱，漏掉 MeetingMinutesBackgroundService。系統實際有 7 條業務管線（PipelineNames 有 7 個常數），因此會議紀錄產生管線若未註冊，健康檢查不會偵測到——該項仍是綠燈，evidence 也顯示「六條…就緒」。

這個檢查項的存在意義就是「管線沒起來要看得出來」，漏掉一條等於對該管線完全失明。

根因

與 1.0.65 修正的 StartupSafetyValidator 是同一類根因：硬編清單與真實來源各自演化，沒有任何機制強制同步。這份 expected[] 至少錯過兩次同步：

  • 1.0.20 新增會議紀錄管線 → PipelineNames 加了常數、AddHostedService 加了註冊，但 expected[] 沒加。
  • 1.0.45 移除 AI 技能產生器（管線 8 → 7）→ 相關程式清乾淨，但 expected[] 的「六條」措辭與內容也沒重新校對。

二、修正

改為由 PipelineNames 反射推導，程式裡不再有清單：

typeof(PipelineNames) 的所有 public const string  →  值 + "BackgroundService"

命名慣例經查證完美成立——7 個常數各自都有對應的 {值}BackgroundService 類別。推導結果排序後固定，讓「缺少：…」訊息穩定可讀。

同時修掉兩處會再漂移的數字：XML 註解不再寫死條數；evidence 的「六條…就緒」改由清單長度帶入。

hostedServices 注入與 Unhealthy 判定邏輯維持不變——缺任一條仍為紅燈。

為什麼是反射而不是「列出常數 + 測試守住」

兩者都能修好眼前的 bug，差別在日後新增第 8 條管線時：列清單的作法要記得加一行（測試會提醒），反射的作法自動納入。既然命名慣例已經完美成立、而且這份清單已經漏過一次，選結構上不可能再漏的作法。

三、新增 BackgroundPipelineHealthCheckTests（6 個測試）

不建構 SystemHealthService（相依龐大），改用結構性慣例測試，比照 MenuPermissionAlignmentTests 的作法：

  • 命名慣例成立——每個 PipelineNames 常數都找得到對應的 {名稱}BackgroundService 型別。這是反射推導能成立的前提：有人加了常數卻沒建服務、或改了命名慣例，這裡先紅燈。
  • 推導結果 == 常數 ＋ 後綴。
  • 會議紀錄管線在範圍內——本次修正的核心，刻意寫死名稱不隨推導邏輯變動，即使日後有人改壞推導也擋得下。
  • 七條全數涵蓋，防止誤刪常數而悄悄縮小檢查範圍。
  • 非管線的寫入服務不被誤納（PipelineProgressWriter、TokenUsageWriter）。

四、刻意不做的事

TokenUsageWriterBackgroundService（未註冊 → Token 用量默默不再記錄）與 PipelineProgressWriterBackgroundService（未註冊 → 管線進度不更新）目前沒有任何健康檢查涵蓋。它們沒有對應的 PipelineNames 常數，不屬於「背景管線」項的語意範圍；要涵蓋需新增一個檢查項（24 → 25 項），連帶多份文件的項數記載要同步。已記入 planning/08 backlog。
