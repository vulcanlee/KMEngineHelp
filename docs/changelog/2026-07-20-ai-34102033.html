一、端到端流程

會議清單點「上傳錄音」
  → MeetingService.AttachRecordingAsync（UI 執行緒完成團隊權控）
    建立 MediaTranscription（繼承會議的 Categories/Teams）
    寫回 Meeting.SourceTranscriptionId；MinutesStatus = 轉錄中
  → 既有轉錄管線：TranscriptionQueue → BackgroundService → Processor
  → 轉錄成功後的「加值步驟」TryEnqueueMeetingMinutesAsync
    MinutesStatus = 轉錄完成，入列會議紀錄產生佇列
  → MeetingMinutesQueue → MeetingMinutesBackgroundService → MeetingMinutesProcessor
    MinutesStatus = 產生中 → 讀逐字稿檔 → MeetingMinutesGenerationService
  → LlmPromptResolver 取「會議-紀錄生成」→ LLM → 解析 JSON
      markdown       → 落地 GeneratedContentPath/{yyyy}/{guid}.md
      summary/decisions/participants → 只填空白欄位
      actionItems[]  → PendingActionItemsJson（草稿，不建工作）
    MinutesStatus = 已產生
  → 使用者開「待辦確認」勾選 → MeetingActionItemService 批次建立工作項目

本階段零 migration —— 階段三（1.0.19）已把 10 個欄位全部建好。

二、五個設計決策與理由

2.1 這是第 8 條管線（更正舊文件的錯誤）

規劃階段的文件寫「第五條管線」，實查後確認既有已有 7 條：媒體轉錄、文件萃取、圖片識別、資料清洗、知識蒸餾、AI 技能產生、嵌入索引。本次新增的是第 8 條。

docs/architecture/開發慣例與限制速查.md §1.8 原本寫「三條匯入管線同構」——那是管線只有三條時的說法，已隨管線增加而過時多年。本次一併更正為列出全部 8 條，PipelineNames／PipelineCancellationRegistry／PipelineRetryHelper 三處的同名過時註解也一併修正。

2.2 自動產生「只填空白欄位」（解掉一個設計衝突）

先前決策有矛盾：一邊定「AI 產生會覆寫摘要／決議／出席者，但產生前跳確認對話窗」，一邊定「轉錄完成後自動觸發」。自動觸發時沒有人在現場，跳不了確認。

解法：自動產生時只填原本空白的欄位，絕不覆寫使用者已寫的內容；Markdown 全文一律落檔。使用者若想改用 AI 版本，到會議頁按「套用 AI 結果」，那時才跳確認並覆寫。自動化因此永遠不會弄丟任何人工輸入。

2.3 加值步驟放在「已完成」寫入之後

TranscriptionProcessor 的觸發鉤子刻意放在 UpdateStatusAsync(StatusCompleted) 之後。放之前若拋例外，會被 ProcessAsync 的外層 catch 接到而把轉錄標成失敗——但轉錄其實是成功的。

鉤子本身自帶總 try/catch（比照 VideoTranscoder.EnsurePlayableAsync 的加值步驟慣例）：失敗只 LogWarning，不影響轉錄結果。

2.4 JSON 解析失敗記日誌，不沿用既有的靜默降級

全專案原本只有一處解析 LLM 回傳的 JSON：DistillationEnhancer.ParsePages。它用「第一個 {／[ 到最後一個 }／]」的括號掃描（可順帶越過 ``` `json `` 圍欄），但**失敗時是空的 catch (JsonException) { }`，完全不記日誌**。

括號掃描的做法沿用了（有測試涵蓋圍欄與前後綴文字），但解析失敗一律 LogWarning 並記下回應前 500 字。靜默 catch 違反日誌鐵則（LoggingConventionTests 擋空 catch {}，但有型別的 catch (JsonException) { } 擋不到），模型不聽話時要留得下線索。

降級行為：整份回應當 Markdown 落檔、其餘欄位留空、狀態仍為「已產生」——不會整筆失敗。

2.5 重啟回復只撈「產生中」

MeetingMinutesBackgroundService.RecoverPendingAsync 刻意不撈「轉錄中」。那是轉錄管線的狀態，TranscriptionBackgroundService 會自行復原該筆轉錄，完成後加值步驟會再次入列本管線。撈了會造成「轉錄還沒好就跑產生」而必然失敗。

三、待辦草稿的生命週期

AI 抽出的待辦不會自動建立工作項目——LLM 會把閒聊當待辦，自動寫入會污染工作清單且難以清理。一律由使用者在確認對話窗勾選（可就地微調標題／負責人／期限）後才建立。

建立的工作繼承會議的 ProjectId／Teams／Categories；Owner 空白時填「未指定」（該欄位為 Required）；DueDate 解析不出 YYYY-MM-DD 時 EndDate 留空，不自行推測日期。

建立後草稿保留並標記 Created（置灰、不可再勾），供追溯「AI 當初建議了什麼、我採納了哪些」，同時避免重複建立。

四、其他變更

  • 上傳上限 1GB → 2GB（MediaTranscriptionService.MaxUploadFileSize，同步更正錯誤訊息文字）
  • MediaTranscriptionService 抽出 AddCoreAsync：原 AddAsync 只回傳 VerifyRecordResult，拿不到新建的 Id，而會議需要它寫入 SourceTranscriptionId。抽共用核心後新增 AddForMeetingAsync 回傳 (Result, Id)，AddAsync 委派過去，行為完全不變。
  • 新提示詞鍵「會議-紀錄生成」：走既有四層解析。注意 LlmPromptsSettings.Get() 的 switch 用的是寫死的中文字面值而非 LlmPromptKeys 常數，新增鍵要改三處（常數、屬性、switch），漏掉 switch 會讓 appsettings 層靜默失效。
  • MeetingService 新增 GetGeneratedContentAsync／UpdateGeneratedContentAsync（原地覆寫同檔，比照四種內容編修的既有慣例）／ApplyGeneratedFieldsAsync。

實作過程中抓到的一個 build 抓不到的錯

ContentEditDialog 沒有 OnClose 參數（它用 @bind-Visible），但一開始寫成了 OnClose="..."。Razor 對未知元件參數不會在建置期報錯，會在執行期才拋「does not have a property matching the name」。是靠實際去讀該元件的 [Parameter] 宣告才發現，已改為 @bind-Visible。
