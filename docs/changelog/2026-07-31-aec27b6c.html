一、解決什麼

說明網站原本只有三個角色：知識庫管理者、導入顧問、知識庫系統銷售人員 —— 全部都是「建置或推銷這套系統的人」。

真正每天用它找答案、也要把自己手上資料放進去的那個人，在整個說明網站裡沒有入口。而那是人數最多的一群，也是對外版最該服務的對象。

盤點既有 docs/ 後發現，使用者要的東西大部分已經寫過了，只是散在寫給建置者看的文件裡：AI知識問答使用指南 寫得很好、資料匯入指南 夠用、企業實戰情境劇本 有「要準備哪些資料」。真正的空白只有三塊，這一版就補那三塊，其餘一律策展既有文件、不複製內容。

二、三份新文件（docs/guides/）

全部採兩層寫法：前半白話、看完就能操作；後半「想知道為什麼」，並明講第一次可以先跳過。

文件補哪個空白
知識庫使用者上手指南沒有任何一份是使用者視角的端到端動線。五個站各一句話、每一站怎麼算過關（看哪個狀態字樣，不靠感覺）、第一次的 30 分鐘路線、清洗規則設定「怎麼選」（不教怎麼寫）、看到「內容已過時」怎麼辦
我該準備與蒐集哪些資料完全沒有的一塊——沒有任何文件告訴使用者去哪找、問誰、哪些不該放
在大知識庫裡問到對的答案檢索策略散在三份文件裡，沒有整合成使用者能用的說法

三份文件裡最值得看的幾句

「不要從『我有哪些檔案』開始，要從『我希望它以後能回答什麼』開始。」 動手前先寫下 5～10 個問句——寫得出來就知道要蒐集什麼，寫不出來就先別開始。那幾個問句後來就是驗收清單。

最有價值的知識通常不在文件裡，在同事腦袋裡。 給了三個現成問句可以直接拿去問（「新人接你的工作，前兩週最容易做錯的三件事是什麼？」等），錄音丟進去就好，不必先整理成漂亮文件。

多客戶／多型號時，「限定知識來源」是唯一可靠的做法。 把型號寫進問句只是加一點相關度分數，而不同型號的文件本來就長得很像，那點分往往不夠把對的推到前面。另外提醒限定分類多選是「或」不是「且」（得到聯集，不是交集）。

⚠️ 純圖表與流程圖效果最差：系統會描述圖上看得到的東西，但圖的意義通常不在圖上。真的重要就把結論用文字寫一段一起放。

三、說明網站（scripts/）

3.1 help_site_data.py

  • 新增 _SVG_USER（自繪 inline SVG：人像＋問號對話框，用 --w2／--a2）
  • ROLES 插在第一筆：id: user、tone: 2（藍）。排第一是因為人數最多，也是對外版最常被點的那張
  • SCENARIOS["user"] 九個情境：我在哪一站／準備與蒐集資料／上傳資料／變成能問的知識／開始問問題／縮小範圍／問不到答案／為什麼我看不到／改了或刪了東西
  • CURATED_SLUGS 加四筆：三份新文件 ＋ 階段 A 的 更新與刪除的連鎖影響.md（情境 9 會指向它，連結會被分享）

3.2 Build-HelpSite.py 的 page_index()——兩處寫死的字串

這是本階段最容易漏、漏了就自相矛盾的地方：

  • 卷首文案「同一套系統，三種人要看的東西完全不同」→ 四種人
  • 「不確定自己是哪個角色？」卡片裡的三條 <li> → 四條（新增「要把自己手上的資料放進來、並且靠它找答案」，排第一）

⚠️ .roles 的 CSS 完全不用改：它用 grid-template-columns:repeat(auto-fit,minmax(300px,1fr))，四張卡在寬螢幕排一列、窄螢幕自動折 2×2。

四、驗證

  • pwsh -NoProfile -File scripts/Test-All.ps1 → 四道守門全綠（測試 1120 通過／0 失敗，本版 src/ 零變更）
  • python scripts/Build-HelpSite.py --both → 447／390 頁（較上一版 +4：三份新文件 ＋ 一個角色頁）、無法解析的文件連結 0
  • Build-HelpSite.py 的 validate_data 會逐一驗證 SCENARIOS 與 CURATED_SLUGS 的每一條路徑，打錯字會當場建站失敗並指出哪一條——這是本階段最強的守門，九個情境共 21 條文件引用全數通過
