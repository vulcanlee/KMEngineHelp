IIS 部署文件補強（純文件，版本不變 1.0.67）

  • 日期：2026/07/25
  • 版本：維持 1.0.67（依 開發慣例與限制速查 §1.1「純文件／腳本變更可不升版」）
  • 類型：文件補洞
  • 程式異動：無

一、起因

正式環境（IIS，C:\KMEngine）回 HTTP 500.30，事件紀錄顯示是 1.0.65 的 StartupSafetyValidator 主動中止啟動：

Production 啟動安全檢查失敗：JwtSettings:SigningKey 不可在 Production 使用開發預設值。
BootstrapSettings:SupportPassword 不可在 Production 使用預設密碼。

守門本身運作正常——它擋下的是「Production 沿用開發預設 JWT 金鑰與 1qaz@WSX」這個實際存在的問題。

真正的障礙是文件沒告訴部署者該怎麼在 IIS 上設定這兩個值：

  • 全新機器部署SOP.md §6.2 只寫 setx /M。對 IIS 內處理序裝載，Machine 範圍環境變數要重啟 IIS／WAS 工作處理序才讀得到——「明明設了卻沒生效」最常見的原因。
  • IIS佈署與可攜工具設定.md 完全沒有出現 web.config 或 environmentVariables——而那才是 IIS 上的標準做法，且存檔即回收生效、不需重建重部署。

二、補了什麼

IIS佈署與可攜工具設定.md

新增 §5.1「在 IIS 設定環境變數」：

  • web.config 的 <environmentVariables> 完整範例（含 ASPNETCORE_ENVIRONMENT、JWT 金鑰、support 密碼、OpenAI 金鑰）。
  • 階層鍵用雙底線 __、<environmentVariables> 必須放在 <aspNetCore> 元素內。
  • 與 setx /M 的差異對照表：前者存檔即生效、設定隨站台走；後者需重啟 IIS／WAS，適合多站台共用。
  • 機密放在站台目錄的權衡（會隨備份／複製擴散，請控管 ACL）。
  • 產生強金鑰與強密碼的 PowerShell 指令。
  • 提醒：support 密碼每次啟動都會依設定值重設，改設定即等於改登入密碼。

§9 疑難排解新增兩列：HTTP 500.30 的判讀、以及事件紀錄看不出原因時如何開 stdout log（含查完要記得關掉）。

全新機器部署SOP.md

  • §6.2 標明 IIS 優先用 web.config，並附精簡範例與連結。
  • 新增 §6.4「首次以 Production 啟動失敗（HTTP 500.30）怎麼查」：事件檢視器步驟、四項檢查的訊息對照處置表、以及「appsettings.Production.json 只覆寫它自己列出的鍵，沒列到的一律沿用 appsettings.json」這個最常見的觸發陷阱、stdout log 開關步驟。
  • 特別註明：此檢查在 NLog 初始化之前執行，所以 NLog:BasePath 底下不會有紀錄，只能從事件紀錄或 stdout log 取得。

開發慣例與限制速查.md

新增一條既有事實（查證時發現，與本次文件補強無關但值得記）：頁面例外不會走 HTTP 例外處理器——App.razor.cs 的 RenderModeForPage() 讓除 /Auths/* 外的所有頁面都用 InteractiveServerRenderMode(prerender: false)，因此頁面內的例外走 Blazor circuit、不經過 UseExceptionHandler。診斷「為什麼 /Error 沒被觸發」時會用到。

三、關於一併移除的實驗性程式碼

本次調查過程中曾實作過兩項功能，評估後認為對系統複雜度的增加不划算，已全部移除、未進版控：

曾實作移除原因
Host 標頭防護中介軟體（擋下無法解析的 Host、回 400）擋的是掃描器垃圾流量造成的日誌噪音，不是資安漏洞；且設 AllowedHosts 為實際主機名即可零程式碼達到同樣效果
UseExceptionHandler 的 CreateScopeForErrors = true實測發現它能消除 already initialized，但對壞 Host 這類錯誤 /Error 仍渲染不出來；加上頁面例外根本不走 HTTP 例外處理器，實際涵蓋面很窄
啟動安全檢查的緊急跨過開關正解（設環境變數）比跨過檢查更快也更安全，逃生口反而是個容易被遺忘的後門

壞 Host 問題的症狀、重現方式、根因與「設 AllowedHosts 即可解決」的結論已完整記入 優化建議清單，日後若日誌被洗版可直接取用，不必重查一次。
