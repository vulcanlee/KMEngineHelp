會議模組 UI 優化：待辦對話窗、上傳提示、自動更新、清單精簡（1.0.21）

  • 日期：2026/07/20
  • 版本：1.0.20 → 1.0.21
  • 類型：UI 優化 ＋ 一個既有 bug 修正
  • 觸發來源：1.0.20 上線後實際操作回報的四個問題
  • 相關：會議 AI 自動化（1.0.20）

一、修了什麼

1.1 待辦確認對話窗「事項」欄只看得到一個字

根因不是欄寬設定，是樣式從來沒生效。 MeetingActionItemsModal.razor 引用的四個 class （meeting-action-items-modal、-hint、-table、-item-created）在整個專案的任何 CSS 檔中都不存在， 上傳對話窗的三個 class（meeting-upload-body、-hint、-file）同樣如此。

結果是對話窗維持 AntDesign 預設寬度（約 520px），扣掉固定欄寬 60+140+140+90 = 430px 後， 不設寬度的「事項」欄只剩約 50px —— 剛好一個中文字。

修法：把 .meeting-action-items-modal 加進 app.css 既有的 .meeting-view-modal 加寬選擇器清單 （90vw × 90vh、內容區可捲動），並補上七個 class 的實際樣式。

⚠️ 為什麼樣式要寫在全域 app.css 而不是 .razor.css：AntDesign Modal 的內容不受 scoped CSS 管轄。 這正是專案原本就把 .meeting-view-modal 放在 app.css 的原因。寫進 scoped 檔會靜默失效。

1.2 「狀態」欄看起來像壞掉的輸入框

原本它是唯讀顯示，且只在已建立時才渲染文字，未建立時是完全空白的 90px 白格 —— 看起來像個壞掉的輸入框。

修法：拆成兩欄。

  • 工作狀態（新增，130px）：可選的下拉，值域為 MyTasAdapterModel.StatusOptions（未開始／進行中／已完成／暫緩／等待），

建立工作項目時帶入。沿用 MyTasEditModal 的既有 Select 寫法。

  • 建立狀態（原「狀態」改名，80px）：未建立顯示「待建立」、已建立顯示「已建立」，不再有空白格。

1.3 上傳對話窗看不到支援格式與大小限制

修法：

  • MediaFormatValidator 補上 AcceptAttribute（照抄 DocumentFormatValidator 的既有成對寫法），

<InputFile> 加 accept，檔案選擇器直接只列得出支援的格式

  • 加一行「支援格式：… 單檔上限 2GB」（沿用 mt-2 text-muted 慣例）
  • 提示句改為明列四個階段：轉錄中 → 轉錄完成 → 產生中 → 已產生

1.4 上傳後沒有進度回饋

MeetingViewView 是唯一沒有輪詢的管線頁 —— 其餘五頁（媒體轉錄、文件萃取、圖片識別、知識來源、AI 技能） 早就有同一套做法，會議頁在 1.0.20 加管線時漏掉了。

修法：完整沿用既有 pattern，5 秒 System.Threading.Timer ＋ 三道防護：

防護作用
isPolling 旗標防重入
任一對話窗開啟時 return不打斷使用者輸入
hasActive 檢查沒有進行中項目就完全不打 DB

「轉錄完成」也算進行中 —— 它是轉錄結束到會議紀錄排入佇列之間的過渡狀態，漏算會讓輪詢在管線中途停掉。

另沿用 KnowledgeSourceView.NotifyPipelineTransitions 的形狀，只在狀態轉換發生時通知一次 （否則每 5 秒會重複跳同一則）：轉為「已產生」跳 Success toast 並告知下一步可做什麼，轉為「失敗」跳 Error。

1.5 清單摘要爆版、欄位過多

AI 產生的 Markdown 摘要整份塞進儲存格，把列高撐到數十行；16 欄也逼使用者大幅左右捲動。

修法：精簡為 8 欄（標題、摘要、會議紀錄狀態、開始日期、所屬專案、分類、團隊、操作）， 摘要改為單行截斷、hover 由原生 title 屬性顯示全文。

移除的 8 欄（描述、與會人員、會議形式、主持人、地點、結束日期、建立時間、更新時間） 只是不在清單顯示，編輯表單完全不動，MeetingAdapterModel 的屬性一個都沒刪。

二、順帶修掉的既有 bug：待辦對話窗的編輯被靜默丟棄

MeetingActionItemService.CreateTasksAsync 原簽章只收索引：

public async Task<VerifyRecordResult> CreateTasksAsync(int meetingId, IReadOnlyList<int> selectedIndexes)

drafts 一律從 DB 的 JSON 重新反序列化，使用者在對話窗對事項／負責人／期限的就地編輯全部被丟棄 —— 這些欄位可輸入卻存不進去。同樣的原因也讓 1.2 的狀態下拉無法運作（選的值傳不到服務層）， 所以這個 bug 不修，狀態下拉就做不出來。

修法：改收「索引 ＋ 使用者編輯後的草稿」。

public async Task<VerifyRecordResult> CreateTasksAsync(
    int meetingId, IReadOnlyList<(int Index, MeetingActionItemDraft Draft)> selected)

DB 的草稿仍是權威：索引用來對位並檢查 Created 旗標與清單長度，防止前端送來偽造索引或重複建立； 前端資料只採用其欄位值。狀態另經 ResolveStatus 做值域檢查，非法值退回預設的「未開始」。 團隊權控（TagStringHelper.IsTeamAccessible）完全未動。

MeetingActionItemDraft 新增 Status（string?）。刻意留 null 不寫預設值：該檔至今沒有任何 using， 不值得為一個預設值讓 Meetings 命名空間依賴 Models.AdapterModel。 向後相容：JsonSerializerOptions 沒開 UnmappedMemberHandling.Disallow、沒有 [JsonRequired]， 舊 JSON 缺此欄位時反序列化為 null，行為與預設值一致。

三、順手修正的過期文案

MediaTranscriptionView 的上傳提示寫「單檔上限 1GB」，但 MediaTranscriptionService.MaxUploadFileSize 早在 1.0.20 就放寬到 2GB —— 文案是過期的，會直接誤導使用者。一併改為 2GB 並補上 accept。

五、測試

dotnet test 616 個測試全數通過（會議待辦相關由 8 個增為 12 個）。

新增的測試：

測試驗證什麼

六、尚未執行的人工驗收

本次全屬 UI 改動，自動化測試涵蓋不到畫面呈現。以下尚未實機驗證：

  1. 對話窗確實加寬到 90vw、事項欄看得到完整標題
  2. 「建立狀態」顯示「待建立」而非空白格
  3. 工作狀態下拉可展開、預設「未開始」
  4. 編輯後建立 → 工作項目用的是編輯後的值（bug 修正的核心驗證）
  5. 上傳窗看得到格式與 2GB 提示、檔案選擇器只列支援格式
  6. 上傳後不手動重新整理，狀態自己跑完四階段
  7. 完成時跳出 toast 並告知下一步
  8. 沒有進行中項目時不再持續打 DB
  9. 對話窗開啟時輪詢暫停
  10. 離開頁面時 Dispose 有被呼叫、timer 釋放
  11. 清單 8 欄、摘要單行、hover 顯示全文
  12. 非管理員的團隊權控未因改簽章而被繞過
