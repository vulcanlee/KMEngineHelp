Production 機密軟偵測（不擋啟動）與寫入背景服務納入健康檢查（1.0.71→1.0.72）

  • 日期：2026-07-26
  • 版本：1.0.71 → 1.0.72
  • 類型：資安補強（軟偵測）＋可觀測性補強

需求

兩件被前幾版明確延後的事，這次一起補完。

一、Production 機密完全沒有任何偵測

三道防線在三個版本內依序被拆掉：

版本發生什麼
1.0.65查出 StartupSafetyValidator 的兩個守門永不觸發（比對的字面值與 appsettings.json 實際值不相等），改以 DevelopmentOnly- 前綴判定
1.0.68該驗證器連續兩次擋住正式部署（IIS 回 500.30，現場難以從該錯誤碼判讀原因）→ 整支移除
1.0.69/system-health「身分驗證」項仍紅（金鑰被改過但仍以 DevelopmentOnly- 開頭）→ 移除該判定

結果是系統沒有任何地方會提示「Production 正在用開發預設金鑰或預設密碼」。而出貨的 appsettings.json 至今仍是 SigningKey = "DevelopmentOnly-…"（94 字元）與 SupportPassword = "1qaz@WSX"——任何看得到原始碼的人都能偽造 JWT。

更關鍵的是：docs/planning/08-優化建議清單-TODO.md 把「列入部署檢查清單、每次部署後人工核對」寫成僅剩的補償方式，但那份清單當時反而以 [x] 宣稱「程式會直接中止啟動」（4 處，已於本版前的純文件 commit 更正）。唯一的補償控制是空的，還在誤導維運人員。

二、兩支寫入背景服務不在健康檢查範圍內

1.0.66 把背景管線檢查改為由 PipelineNames 反射推導，但推導只涵蓋業務管線。TokenUsageWriterBackgroundService 與 PipelineProgressWriterBackgroundService 沒有對應常數，因此完全不在任何檢查範圍內——SystemHealthService 的註解自承這件事，測試裡甚至有一條主動斷言它們被排除。

後果不對稱地嚴重：TokenUsageWriter 沒起來＝Token 用量默默不再記錄，而那是成本治理與 5 份統計報表的資料基礎，且不會有任何錯誤訊息；PipelineProgressWriter 沒起來＝進度不更新、完成 toast 消失，使用者只會覺得「卡住了」。

變更

機密軟偵測：只提示，絕不中止

還原 Web/Configuration/UnsafeDefaults.cs（從 git 取回 1.0.65 的版本——它的前綴判定邏輯已驗證過，不重新設計），新增純函式：

public static IReadOnlyList<string> DetectProductionRisks(
    IConfiguration configuration, string environmentName)

回傳清單而非「拋例外」，是為了讓「不會中止啟動」這件事寫在簽章上。 兩個消費端：

  1. Program.cs：在 builder.Build() 之後（L374 附近，緊接既有的「執行環境摘要」）記一筆 Error：

Production 安全風險：偵測到不安全的預設設定值 N 項，站台仍會正常啟動，請依部署檢查清單更換。… 以 #region 包住並在註解寫死三條鐵則：① 必須在 Build() 之後（在那之前拿不到 ILogger，訊息不進 NLog）② 不得 throw／Environment.Exit ③ 不得改用 ValidateOnStart（那會在 Build() 期間拋例外，等於回到 1.0.68 被移除的行為）。

  1. SystemHealthService.CheckAuthentication：接線壞 → Unhealthy；接線正常但有風險 → Degraded（黃燈），evidence 尾端附 ⚠️ 與原因。刻意用黃不用紅：此項權重 15（全站第二高），而 Cookie/JWT 接線本身沒壞——1.0.69 之所以整條移除，正是因為紅燈被誤判為身分驗證故障。

判定只在 Production 生效（環境名比對不分大小寫）。開發／測試沿用預設值是正常的，報了只會變成雜訊。

刻意不恢復 Swagger 與 Redis 兩項判定：Redis 已被 /system-health「分散式快取」項實測連線涵蓋（比啟動期字串檢查更有效）；Swagger 未列出該鍵時沿用基底 false（安全側）。少兩個判定＝少兩個誤報來源。

寫入服務納入健康檢查：併入現有項，不新增第 25 項

新增硬編的 SystemHealthService.ExpectedWriterBackgroundServices（那兩支沒有 PipelineNames 常數，無法推導），與反射推導的管線清單取聯集後檢查，evidence 分開報數：

匯入/處理管線就緒：7/7；用量與進度寫入服務就緒：2/2。

為什麼不新增第 25 項（原本的估法）：盤點後發現「24 項」硬寫在 17 份文件裡，包含 marketing/*.html、presentation/*.html 這些會由 scripts/Build-DeckPptx.py／Build-FlagshipDeck.py 產生 .pptx 的檔案（得重生三種格式），還要重算「權重合計 232」；而兩案的可觀測性收益完全相同——服務沒起來一樣會亮燈。併入現有項只要動 3 份文件，檢查項數維持 24、權重維持 8。

1.0.66 的 ExpectedPipelineBackgroundServices 反射推導完全不動（那是它的成果，也是既有測試的斷言對象）。

測試

661 → 686（+25，全綠）。

  • 新增 UnsafeDefaultsTests。最關鍵那條：DetectProductionRisks_WithRepositoryAppSettings_ReportsBothSecrets 直接從磁碟載入本 repo 的 appsettings.json，斷言兩個機密都被指出。這是唯一能結構性防止「預設值漂移了、判定沒跟著改」的作法——1.0.65 前的守門失效，正是因為當時的測試餵手寫字面值而非真實設定檔。

邊界測試涵蓋 1.0.69 實際遇到的錯誤做法（在預設值後面接一段字，長度變成 202 但前綴仍在 → 仍要判為不安全）。

  • 新增 SystemHealthReportTests.GetReportAsync_Authentication_InNonProduction_StaysHealthy：防止偵測不慎在非 Production 也生效。若本機與 CI 永遠亮黃燈，燈號就再次失去意義（這正是 1.0.69 的痛點）。
  • BackgroundPipelineHealthCheckTests 那條反向斷言不刪，改變它守護的對象：改為同時斷言「不在推導清單」（推導的前提仍成立）＋「在寫入服務清單」（1.0.72 起必須被涵蓋）。並刪掉測試檔內的第二份私有清單，改用生產端常數；新增 EveryWriterService_HasMatchingType 守住硬編清單與真實型別一致。

影響與相容性

  • 不會改變啟動行為。這是本次最重要的相容性保證：偵測到風險時站台仍正常啟動，只是多一筆 Error 日誌。
  • ⚠️ 部署現場注意：日誌裡出現 Production 安全風險 這筆 Error 不是 500.30 的原因。已在 全新機器部署SOP.md §6.4 的 500.30 排查段明確標註，避免誤判。
  • Production 沿用開發預設值時，/system-health 總分會少約 3.2 分（權重 15 的一半，滿分 232），「身分驗證」項轉黃。這是預期行為。
  • 檢查項數維持 24、權重合計維持 232，17 份寫「24 項」的文件不需變動。
  • 無資料庫 migration、無 API 合約變更。
