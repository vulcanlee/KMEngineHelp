Graph RAG P8：多跳遍歷 + 圖譜瀏覽（1.0.89 → 1.0.90）

  • 日期：2026-07-27
  • 版本：1.0.89 → 1.0.90
  • 類型：新增功能（Graph RAG 第八階段；含一項預設行為變更）

背景

Graph RAG 的立論基礎是「補齊多跳／全域問答這唯一缺口」（見藍圖 §1），但 P1～P7 走完之後，RetrievalService.SearchGraphAsync 一直都只走 1 跳——種子頁沿 GraphEdge 一跳、三元組兩端展開一次就結束，沒有第 2 跳、沒有路徑衰減、也沒有節點數上限。也就是說「A 與 C 透過 B 相連」這種最典型的多跳問題，系統其實答不出來。

同時沒有任何圖譜視覺化：審核頁只有三元組表格，管理員無法目視「這張圖長什麼樣、抽得好不好」，只能逐列猜。

⚠️ 預設行為變更

GraphMaxHops 預設為 2（使用者決策），即升級後多跳直接生效，不需手動開啟。代價要講清楚：

  • 所有既有查詢的命中集合會變大、檢索延遲上升（每多一跳多一次 GraphEdge 查詢）。
  • 既有檢索品質評測基線可能位移，升級後應以 /rag-evaluation 重跑確認指標不退步。
  • 若要回到 1.0.89 的行為：於 /rag-diagnostics 把 GraphMaxHops 設為 1（熱生效、免重啟），或改 appsettings。此路徑已由回歸測試釘住。

變更

1. 三個新參數

SystemSettings.Retrieval 新增（緊接 GraphWeight）：

參數預設範圍熱調
GraphMaxHops21～3✅ DB 覆寫（/rag-diagnostics）
GraphHopDecay0.5[0,1]✅ DB 覆寫
GraphMaxNodes200≥1❌ 僅 appsettings（安全閥非品質旋鈕）

前兩者走 GraphWeight 的完整四點同步鏈：RetrievalParamOverride 加兩個可空欄＋雙庫 AddGraphHopParams migration、EffectiveRetrievalParams record、SetParamsAsync 簽章與 ValidateParams、RagDiagnosticsService.ApplyParamsAsync、/rag-diagnostics 的兩個 InputNumber。SetParamsAsync 是位置參數，共 13 處呼叫端一起改。

  • GraphMaxNodes 也放進 EffectiveRetrievalParams（讓 SearchGraphAsync 三個參數的讀法一致），但恆取 appsettings、無覆寫欄位，已由測試釘住。
  • GetEffectiveParamsAsync 對三者都夾住上下界：SetParamsAsync 的驗證只擋 DB 覆寫路徑，appsettings 直接填 GraphMaxHops=99 仍會流進來。
  • 順手修（本次改動直接暴露）：/rag-diagnostics 的「目前生效」摘要從 1.0.83 起就漏列 GraphWeight，OnApplyParamsAsync 的錯誤訊息也沒提到它——等於這個參數調了以後畫面不顯示現值。一併補齊三者。

2. SearchGraphAsync 由 1 跳改為 BFS N 跳

  • 抽出 ExpandFrontierAsync(frontier, visited, triplePairs, hopFactor, …)：回傳「本層新發現頁 → 傳播強度」。
  • 外層 BFS：visited 初值為種子頁；第 h 跳的 hopFactor = hop == 1 ? 1.0 : GraphHopDecay，故第 1 跳不衰減——這正是 GraphMaxHops=1 能與 1.0.89 行為相同的原因。多路徑到同一頁取 max，next 為空即提早結束。
  • ⚠️ 改多跳時最容易漏掉的一行：三元組展開的條件原本是「與種子頁有交集」，必須改為「與當前 frontier 有交集」，否則第 2 跳永遠展不開。
  • 效能：別名對照、pagesByCanon、已套 ACL 的三元組頁對三者與 frontier 無關，移到 BFS 迴圈外只建一次（原本三元組的 ACL 是逐筆判斷，現在改為一次性預過濾，語意相同）。只有 GraphEdge 查詢是 frontier 相依、必須每層重查。
  • GraphMaxNodes 守門：某層裝不下時取強度最高者填滿並停止擴展，且 LogInformation 記下被丟棄數量（不靜默截斷）。

3. 圖譜瀏覽（審核頁第三個分頁）

  • GraphTripleService.GetNeighborhoodAsync(entityName, maxHops)：輸入名稱先 Canonical 再經已核可別名 Resolve（查「TSMC」等同查「台積電」），只取已核可三元組，BFS 逐層擴展實體；跳數上限 3、節點上限 100，達上限以 Truncated 回報。
  • ⚠️ 這與檢索是兩張不同的圖：檢索遍歷「頁」（WikiPage），本功能遍歷「實體」（canonical 名稱），刻意不共用程式碼。
  • UI：/knowledge-graph-review 加第三個 <TabPane>「圖譜瀏覽」——關係表格 ＋ inline SVG 放射狀圖（中心為查詢實體、第 h 跳落在半徑 h×R 的同心圓，依索引均分角度）。不引入任何外部前端圖庫（無 CDN 依賴、Blazor Server）。沿用既有 角色_知識圖譜審核 頁權，不新增權限常數、不動選單三處同步。
  • ⚠️ Razor 踩雷：SVG 的 <text> 放在 @foreach 區塊內會被 Razor 當成語法標記而報 RZ1023: "<text>" tags cannot contain attributes，要包一層 <g> 才會被當作 SVG 元素。已在速查登記。

安全與相容（leak=0）

  • 多跳不得成為越權的旁路：邊的權控每一跳都要套。他隊邊被濾掉後其目標頁不進 frontier，因此下一跳無法借道——整條路徑在該處斷開。已由新測試釘住（A 公開 →[他隊邊]→ B →[公開邊]→ C，非管理員查 A 時 B 與 C 都不得出現）。
  • 節點與三元組的 ACL 改為迴圈外一次過濾，與原本逐筆判斷語意相同。
  • 圖譜瀏覽：三元組與兩端節點兩層都套權控（inner join ⇒ 任一端越權，整條關係就不出現）。
  • 向後相容：GraphMaxHops=1 即 1.0.89 行為（回歸測試釘住）；GraphWeight=0 仍完全關閉圖路。

已知限制（未來增量）

  • 跳數上限 3。再深請先評估專用圖庫（藍圖 §4.4 的觸發條件：≥3 跳深度、邊數百萬級、需 PageRank 等）。
  • GraphMaxNodes 的截斷是「取強度最高者填滿後停止」，不保證是全域最佳的 N 個節點；它是防爆安全閥，不是排序機制。
  • 圖譜瀏覽的 SVG 在節點多時會擁擠（放射狀佈局無避讓）；表格才是完整資料的權威呈現，SVG 為輔助。
  • 檢索熱路徑仍每次都全表載入已核可別名與錨頁節點（P7 只補了索引，快取未做）。多跳讓這件事更值得處理，但仍留待未來。
  • 節點／社群摘要嵌入、MCP／API 暴露圖譜能力仍未實作。
