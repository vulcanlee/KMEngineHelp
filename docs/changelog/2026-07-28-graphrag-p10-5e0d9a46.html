Graph RAG P10：圖檢索評測題組（1.0.91 → 1.0.92）

  • 日期：2026-07-28
  • 版本：1.0.91 → 1.0.92
  • 類型：新增功能（Graph RAG 第十階段；雙庫 migration AddRagEvalGraphFields）

背景

P1～P9 把 Graph RAG 做完了，但九個階段做下來，沒有任何數據能回答「圖到底有沒有提升召回」：

  • Services/Embeddings/RagEvaluator.cs 全檔沒有圖的概念，只算 Precision／Recall／NDCG／MRR／出處正確率／越權洩漏。
  • RagEvalParamSnapshot 只快照 TopK／CandidateTopK／VectorWeight／KeywordWeight／MinScore 與兩個門檻，沒記 GraphWeight／GraphMaxHops／GraphHopDecay——所以既有基線根本無從得知是在哪組圖設定下跑出來的。
  • 評測集裡沒有多跳題，也沒有全域問答題——而這兩類問題正是導入 Graph RAG 的理由。

也就是說，藍圖 §9 的「每階段共同要求：評測回歸，不得使既有指標退步」，對圖這一路從來沒有真正生效過。本階段補上這件事。

關鍵發現：不需要跑對照組

RetrievalHit 早就帶 VectorScore／KeywordScore／GraphScore 三個分項（IRetrievalService.cs 末行），只是評測層一直沒用。

因此「圖帶來多少召回」可由單次檢索推導，不必再跑一次「關掉圖」的對照組——省下一半評測成本，也避免兩次檢索之間狀態漂移。

變更

1. 三個圖檢索指標（確定性、不呼叫 LLM）

指標定義
GraphOnlyHitsGraphScore > 0 且向量與關鍵字分項皆為 0 的命中數——沒有圖就召不回的命中
GraphAssistedRateGraphScore > 0 的命中比例（圖參與了多少命中）
GraphRecallGain期望來源中「其命中全部來自圖路」的相異來源數 ÷ 期望數——「圖有沒有用」的主指標

⚠️ GraphRecallGain 是保守下界：融合重排效應（圖把原本落在 topK 之外的命中推進來）不計入。這是刻意的取捨——要精確量到重排效應就得跑對照組，成本加倍而結論方向不變。

⚠️ 來源層與命中層的判定刻意不同：某來源只要有任一筆命中帶向量或關鍵字分數，沒有圖也召得回，故不計入增益（即使同一來源另有圖獨有命中）。

2. 基線快照補上三個圖參數

RagEvalParamSnapshot 尾端追加 GraphWeight／GraphMaxHops／GraphHopDecay。

⚠️ 三者型別為可為 null，不是「預設 0」——舊基線的 ParamsJson 沒有這三個屬性，若用 0 當預設就會謊稱「該基線是在圖檢索關閉下跑的」，而事實是當時根本沒記。UI 對 null 顯示「未記錄（此基線於 1.0.92 之前擷取，重設基線即可補上）」。

3. global 模式評測（新樣本類型）

RagEvalSample 加 EvalMode（local 預設／global）與 ExpectedKeywords。global 樣本改走 KnowledgeBaseChatService.GlobalMapAsync，以「期望關鍵詞涵蓋率」與「取用社群數」計分。

Precision／Recall／NDCG／MRR／出處正確率一律留 0，UI 顯示為「—」而非誤導的 0——社群摘要沒有 chunk 層出處，也沒有相似度可言。

彙總報告的分母也分開（LocalCount／GlobalCount）：否則 global 樣本恆為 0 的檢索類指標會把整體平均拖低而誤導判讀。越權洩漏總數則跨模式加總（資安指標不分模式）。

4. ⚠️ 紅線：global 評測的身分問題（本階段真正的資安修補）

GlobalMapAsync → GraphCommunityService.GetAccessibleSummariesAsync 取的是 IRecordAccessScopeProvider.GetAsync() 的環境身分，也就是「按下評測按鈕的人」。而評測樣本標的是模擬身分（EvalIsAdmin／EvalTeams）。

兩者不一致的後果：管理員跑評測時，global 樣本會看到全部社群，等於全域問答的權控從來測不到——樣本標了「只屬甲隊」也沒用。

修法：GlobalMapAsync 與 GetAccessibleSummariesAsync 各加一個可選 RecordAccessScope? scopeOverride = null（null＝維持現行由 provider 取得）。既有呼叫端（Blazor 問答頁、MCP KnowledgeAskTool）一行未改、行為完全不變；只有評測會傳。

取回的社群另以相同的子集判定二次校驗寫入 LeakHits，作為回歸守門。

5. 種子樣本補兩筆圖題型

原本兩筆都是單點檢索題。新增「跨文件關聯／多跳」（刻意標兩個期望來源）與「全域歸納」（social 摘要＋期望關鍵詞）各一筆——若評測集裡沒有這兩類題，圖檢索的效果就永遠無從證明。

6. UI

  • 儀表板依模式分列：檢索類指標、圖指標（圖召回增益／圖參與率／圖獨有命中）、全域指標（關鍵詞涵蓋率／平均取用社群數）。
  • 表格加「模式」「圖增益」「關鍵詞涵蓋」三欄；不適用的欄位顯示「—」。
  • 編輯表單加評測模式切換，並依模式只顯示該模式用得到的欄位（global 顯示期望關鍵詞、local 顯示期望來源與錨點）。
  • 基線比較表加「圖召回增益」「圖參與率」「關鍵詞涵蓋率」三列。

相容性

  • 省略 EvalMode 時行為與 1.0.91 完全相同（回歸測試釘住）；migration 對既有列填 "local"（手動把鷹架產生的 "" 改掉，讓資料本身即正確）。
  • RagSampleMetrics 只新增欄位，舊 LastMetricsJson 反序列化後 Mode 保留初始值 local、圖指標為 0，不需回填。
  • scopeOverride 為 null 時所有既有路徑行為不變。

已知限制（未來增量）

  • GraphRecallGain 不計融合重排效應，是保守下界（見上）。要精確量測需跑「關掉圖」的對照組，成本加倍。
  • global 評測會呼叫 LLM，因此非確定性：同一樣本重跑兩次的關鍵詞涵蓋率可能不同。local 評測仍是完全確定性的。
  • global 評測成本＝可存取社群數次 LLM 呼叫（受 GraphGlobalCommunityCap 控管，預設 20）。「評測全部」若含多筆 global 樣本會放大成本，目前沒有針對評測的額外節流。
  • 關鍵詞涵蓋率為子字串比對，不做同義詞或詞形變化處理。
  • 未執行：以實際知識庫跑一輪完整評測並設為基線（需已索引的真實資料）。本次不宣稱已驗，留給部署後驗收。
