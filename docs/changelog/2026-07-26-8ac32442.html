變更紀錄

新增「待處理背景工作」管理者頁、儀表板管線分布補齊 7 條，並修正會議紀錄管線的四個缺陷（1.0.77→1.0.78）

  • 日期：2026-07-26
  • 版本：1.0.77 → 1.0.78
  • 類型：功能新增（管理者維運頁）＋資料正確性修正（會議紀錄管線）

需求

使用者要三件事：①儀表板看到「還有多少處理管線待處理」②一個管理者頁面列出待處理的背景工作 ③在該頁取消尚未執行的工作。

先確認的技術前提：佇列無法列舉

7 條管線的佇列全部是 Channel.CreateUnbounded<PipelineJob>，介面只有 EnqueueAsync／DequeueAllAsync，而 Channel<T> 讀取即消耗、無法非破壞式列舉。所以待處理清單一律由各實體的狀態欄位推導。

也刻意不用 Channel.Reader.Count ——它與 DB 狀態的落差是雙向且結構性的：出列瞬間 job 已離開 channel 但 Processor 還沒把 DB 寫成「處理中」（少算）；CancelAsync 已把 DB 改成「已取消」但 job 仍躺在 channel 裡（多算）；重啟後 channel 歸零而 DB 仍是「處理中」（少算一整批）。卡片數字必須等於頁面列數，這只有靠 DB 才做得到（已用測試釘住）。

③ 其實現有機制已支援，但有一條管線是例外

「取消還在排隊的工作」不是從佇列移除，而是把 DB 狀態改成「已取消」、由 Processor 出列時跳過。6/7 條管線的 Processor 早就有這道檢查——會議紀錄管線沒有。

追查後這條管線共有四個缺陷：

缺陷後果
MeetingMinutesProcessor 出列後不檢查狀態「改 DB 狀態來取消」對它完全無效——出列後照跑，還會付一次 LLM token
沒有「已取消」狀態常數，MarkCancelledAsync 寫的是「失敗」使用者按取消卻看到「失敗」，且與真失敗無法區分
完全沒有 Cancel 服務方法連 TryCancel(PipelineNames.MeetingMinutes, …) 都沒有任何呼叫者
排隊時寫 MinutesStatusTranscribed = "轉錄完成"，而 RecoverPendingAsync 只撈「產生中」排隊中的工作重啟後永久遺失、無人補救；且該值同時代表「排隊中」與「入列失敗的孤兒」，分不出來

另外 EmbeddingIndex 管線的 MarkCancelledAsync 與 Processor 檢查都已存在，只缺 Service 層入口。

儀表板的「處理管線狀態分布」則只有 4 條——蒸餾、嵌入索引、會議紀錄三條管線的積壓從來看不到。

變更

一、會議紀錄管線四個缺陷（先做，本批風險最高）

  • MeetingAdapterModel：新增 MinutesStatusQueued = "排隊中"、MinutesStatusCancelled = "已取消"，並同時補進 MinutesStatusOptions。

⚠️ 這第二步不是形式：MeetingService.ValidateBusinessRulesAsync 會用該清單驗證 MinutesStatus，漏補會讓處於新狀態的會議一改標題就被擋下，訊息還是「會議紀錄狀態 不是有效的選項。」——使用者完全無法把它連結到管線改動。已加反射測試釘死。

  • TranscriptionProcessor：排隊時寫入值由「轉錄完成」改為「排隊中」。
  • MeetingMinutesProcessor：開頭補「已取消則跳過」，寫法對齊 CleaningProcessor。
  • MeetingMinutesBackgroundService：新增 RecoverableMinutesStatuses = [排隊中, 產生中, 轉錄完成]；MarkCancelledAsync 的守門加「排隊中」、目標狀態由「失敗」改為「已取消」。

「轉錄完成」是刻意永久保留的：①收容升版前停在該值的既有資料 ②收容入列失敗的孤兒（TryEnqueueMeetingMinutesAsync 入列失敗只記 warning）。兩者的前置條件（轉錄已成功）都已滿足，重新入列安全且正確。仍刻意不撈「轉錄中」——那是轉錄管線的狀態。

  • MeetingViewView：輪詢的 hasActive 加「排隊中」。漏這一步會讓輪詢在管線中途停掉（該處註解自己就寫了這件事，1.0.21 修過同類 bug）。
  • MeetingService：建構式加 IPipelineCancellationRegistry，新增 CancelMinutesAsync。

二、EmbeddingIndex 取消入口

KnowledgeSourceService.CancelEmbeddingIndexAsync，同構於 CancelCleaningAsync。建構式不動（registry 早已注入）。 不做 RetryEmbeddingIndexAsync：TriggerEmbeddingIndexAsync 只擋 Pending/Processing，「已取消」可直接重新觸發，既有 UI 已有按鈕。

三、查詢與取消服務（刻意讀寫分離）

  • PipelineJobQueryService（讀）：只依賴 BackendDBContext。GetPendingJobsAsync() 走 5 次往返、依序 await（⚠️ 單一 DbContext 非執行緒安全）：3 個實體表各一次 ＋ KnowledgeSource 一次撈三欄後在記憶體 fan-out ＋ Meeting 一次。

列模型＝(管線, 紀錄)：KnowledgeSource 同時承載三條管線，做成一列一紀錄會讓同一筆被算三次或被合併掉。 IsProcessing 由服務端算好——跨管線的狀態字面值並不同構，不讓 UI 自己比對字串。

  • PipelineJobCancelService（寫）：注入 6 支既有 Service，只做 switch 分派、不重寫取消語意（CleanTrackingHelper.Clean ＋ 團隊權控 ＋ TryCancel fall-through 全部沿用）。未知管線回傳失敗、不擲例外。
  • 為何拆讀寫：DashboardService 要吃摘要，而它是每位使用者開首頁都會建的；讓它依賴含 6 支 Service 的胖物件會讓 DI 每次多建一堆物件，也讓測試從 trivial 變成要先組出五、六個相依物件。

四、儀表板

  • 管理者專區新增第 5 張卡「待處理背景工作」（可點進 /pipeline-jobs，副標分開顯示等待中／處理中）。

刻意不套 .dashboard-card-warning：有背景工作在跑是正常狀態，天天亮黃框會稀釋既有兩張黃卡（索引紅燈、資料不一致）「黃＝需要你處理」的語意。

  • 「處理管線狀態分布」4 條 → 7 條。既有第 4 條標題「知識來源」改為「知識來源清洗」，與新增的「知識來源蒸餾」「知識來源索引」共用前綴，讓讀者看出這是同一批紀錄的三個階段。

⚠️ Meeting.MinutesStatus 是 string? 而 StatusBreakdown 的 Expression<Func<T,string>> 不可空 → 用 ?? MinutesStatusNone（EF 譯 COALESCE）。寫成 x.MinutesStatus! 會編譯通過，但執行時產生一條 Status 為 null 的分布列（畫面出現無標籤橫條）。

五、/pipeline-jobs 頁面

adminOnly 診斷頁，依既有豁免規則只動 Menu.json ＋ MenuIconTests.AllowedLeafIcons，不加權限常數也不動權限樹（會打亂位置索引）。

⚠️ 輪詢防護③刻意偏離：慣例要求「沒有進行中項目就完全不打 DB」，但本頁的內容就是進行中項目——列空時不打 DB 就永遠發現不了新到的工作，頁面直接變死頁。保留防護①（isPolling）②（對話窗開啟不重載），③改為每 tick 無條件重載。成立條件：查詢是 5 次 AsNoTracking 投影、payload 隨在飛工作量而非全庫大小成長，且只有管理員能開此頁。已在速查登記為唯一合法例外。

也刻意不做狀態轉換 toast：本頁的列完成即消失，這本身就是訊號；替別人的工作彈「已完成」只是噪音。

逐列以 cancellingKeys（管線:Id）防重入——同一筆知識來源會出現在三條管線，只用 Id 會互相干擾。

測試

735 → 758（+23，全綠）。

檔案筆數關鍵
PipelineJobQueryServiceTests8GetSummary_TotalEqualsPendingJobsCount：卡片數字＝頁面列數這個核心不變量。另 CoversAllSevenPipelines（反射比對 PipelineNames，讓「漏掉某條管線」不可能再回歸）、KnowledgeSourceWithThreeActiveColumns_ProducesThreeRows、ExcludesTerminalStatuses（逐一列出每條管線的終態字面值——它們不同構，用「Contains(完成)」之類的啟發式會漏）
MeetingMinutesCancellationTests9Processor_WhenMinutesStatusCancelled_SkipsWithoutTouchingStatus（使用者指定必備）。另 MinutesStatusOptions_ContainsEveryMinutesStatusConstant 反射守死上述 Options 陷阱、RecoverableMinutesStatuses_… 守重啟遺失
PipelineJobCancelServiceTests3分派表完整性（原始碼掃描）＋兩條管線不得分派到相同呼叫 ＋ 未知管線不擲例外
KnowledgeSourceServiceTests（追加）3EmbeddingIndex 取消三態，關鍵斷言是「另外兩欄沒被動到」

已實證的兩件事

  1. Processor_WhenMinutesStatusCancelled_SkipsWithoutTouchingStatus 確實會紅。 暫時移除守門後，狀態變成「失敗」（重試迴圈吞掉 generationService: null! 的 NRE 並寫入終態）——證明沒有守門時 Processor 真的會繼續往下跑（實際情境就是繼續呼叫 LLM），而測試抓得到。
  2. PipelineJobCancelServiceTests 的分派檢查是原始碼文字層的守門，不是行為驗證。要用反射真的呼叫每一條分支，得先建出 6 支 Service（MediaTranscriptionService 一支就有 10 個相依），成本遠高於它能多抓到的東西。它保證「新增管線常數卻忘記加 case」會紅燈，但「case 接到正確方法」是由 KnowledgeSourceServiceTests 那三條欄位斷言負責。已寫進測試註解，避免日後誤判覆蓋率。

影響與相容性

  • 既有停在「轉錄完成」的會議資料不會自動變成「排隊中」，但 RecoverableMinutesStatuses 永久保留該值，所以它們在下次重啟時會被正常收容並重新入列——這反而修好了先前的孤兒。
  • 會議紀錄被取消時，狀態由「失敗」改為「已取消」。若有既有報表以 MinutesStatus == "失敗" 統計失敗率，數字會變得更準確（先前混入了使用者主動取消）。
  • 儀表板管理者專區由 4 卡變 5 卡；管線分布由 4 條變 7 條（GetDashboardAsync 的往返數 4 → 7，每次都是 GroupBy 計數）。
  • 「知識來源」這個分布標題改為「知識來源清洗」（已確認無測試斷言此字串）。
  • 無資料庫 migration（Meeting.MinutesStatus 是無約束的 string?）、無 API 合約變更。

本次刻意不做

  • 批次取消：TryCancel 回 false 會 fall-through 直接標記，而實際處理仍在跑、完成時會覆寫回終態；「全部取消」會在最可能有一堆處理中的時刻把這個窗口乘上 N。而收益極小——每條管線 SingleReader ＋ 同步 await，全系統最多同時 7 列是「處理中」。安全形狀是「全部取消等待中」（不進 TryCancel 分支、零競態），記入 backlog。
  • 不修 5 支既有 Cancel 的 fall-through 競態：那是已上線的共同語意，動它等於一次改 7 條管線的行為。本次只確保新寫的 2 支與既有 5 支同構。
  • 列模型不加「可否取消」欄位：本頁只列等待中／處理中，定義上都可取消，永遠 true 是死欄位。
