提示詞槽位鍵收成單一來源、/prompts 加即時判定提示、PDF 轉換偵測輸出被截斷（1.0.76→1.0.77）

  • 日期：2026-07-26
  • 版本：1.0.76 → 1.0.77
  • 類型：可用性修正 ＋ 資料正確性修正 ＋ 重複來源收斂

需求

使用者問「PdfUseLlm = true 時送給 LLM 的提示詞是什麼、能不能在 appsettings.json 指定、內建預設是什麼」。答案是可以（三層：DB /prompts > appsettings LlmPrompts:DocumentPdfToMarkdown > 程式 LlmPromptDefaults），但追這條鏈時查出三個會讓人「以為改了卻沒生效」或「拿到壞資料卻不知道」的缺口。

一、/prompts 打錯槽位名稱完全靜默

要覆蓋系統內建提示詞，Prompt.Name 必須逐字等於槽位鍵（DB 比對是 x.Name == name，精確）。但該頁的「名稱」是自由文字輸入、沒有任何提示——打成「文件-PDF轉 Markdown」（多一個空白）或「PDF轉Markdown」（少前綴），不會有任何錯誤、日誌或警告，只會安靜地退回內建預設。使用者會以為改好了。

二、槽位鍵字串在兩處各寫死一份

LlmPromptKeys.cs（Business）與 LlmPromptsSettings.Get()（Models）各有一份中文鍵字面值、互不引用。任一邊改字（含未來的全域替換）會讓 appsettings 層靜默失效（Get() 回 null → 直接跳到程式 fallback），而 DB 層仍正常運作，所以完全不會有人發現。

三、PDF 輸出被截斷會被當成成功

PDF 全文轉換是最容易撞到模型輸出上限的用途。撞到時回應仍是 HTTP 200、content 也有值，只是內容不完整——而程式不看 finish_reason。結果：殘缺的 Markdown 直接落檔、狀態「已完成」、無任何提示，之後整條 RAG（切塊／嵌入／問答）都建立在殘缺內容上。

變更

1. LlmPromptKeys 移到 Models，收成單一來源

LlmPromptKeys.cs 由 Business/Services/Prompts/ 移到 Models/Systems/，LlmPromptsSettings.Get() 的 switch 改為引用 LlmPromptKeys.X 常數，消除第二份字面值。

搬移方向是必然的：專案相依是 Business → Models，Models 不能引用 Business，而需要引用常數的 LlmPromptsSettings 就在 Models。9 個引用檔多數已有 using KnowledgeExtraction.Models.Systems;，實際只需補 1 個 using（KnowledgeSourceChatService）並修 1 處部分限定名（TranscriptionProcessor.cs:147 的 Prompts.LlmPromptKeys.Transcription）。

同時新增 AllKeys（畫面與測試用）、KeysWithoutAppSettings（記錄 轉錄-提示 刻意不走 appsettings、沿用 OpenAISettings.Prompt）、IsSlotKey()（精確比對）。

2. /prompts 名稱欄加即時判定

  • 名稱標籤加說明泡泡（Tooltip，比照 CleaningProfileViewView 的既有 HelpIcon 慣例），講清楚兩種用途。
  • 輸入框（BindValueMode.OnInput）下方即時顯示：
  • 命中 → ✅ 對應系統槽位「…」——儲存並啟用後會覆蓋該用途的系統內建提示詞（免重啟、立即生效）
  • 未命中 → ℹ️ 這是自訂提示詞，會出現在「依提示詞產生」與對話頁的提示詞選單中 ＋ 提醒覆蓋需逐字一致 ＋ 15 個槽位鍵的可點擊清單（點一下直接填入）

⚠️ 刻意不改成「槽位下拉限定」。 Prompt 表同時服務兩種用途：系統槽位覆蓋層，以及使用者自由提示詞清單——PromptService.GetAllEnabledAsync() 被 4 個檢視當選單來源（DocumentExtractionView／ImageRecognitionView／KnowledgeBaseChatView／KnowledgeSourceChatView）。任意名稱是合法且必要的，所以只能提示、不能阻擋。

判定用 LlmPromptKeys.IsSlotKey，與 DB 一樣是精確比對——若畫面比對比較寬鬆，就會對「多一個空白」給出「✅ 對應系統槽位」這種錯誤保證。

3. PDF 轉換偵測輸出被截斷

PdfMarkdownLlmClient.ExtractMarkdownAsync 在解析內容前檢查 choices[0].finish_reason == "length"，命中即擲例外 → 由 DocumentExtractionProcessor 走既有降級路徑改用 MarkItDown。

  • 抽為 public static bool IsTruncatedByOutputLimit(string)（純函式，比照同檔 ResolveModel 的既有作法以便直接單元測試），logging 與擲例外留在實例方法。
  • 解析失敗／欄位缺漏一律不阻擋——內容有效性由 ParseContent 把關，這道檢查不該把「解析不出來」升級成失敗。

⚠️ 刻意不放進共用的 OpenAIChatCompletionClient.ParseContent。 該方法另有 4 個呼叫端（一般對話、查詢改寫、圖片、手動送檔產生），那些路徑被截斷未必要當失敗，改共用方法會把行為變更擴散到整站。已用 git diff 確認該檔未被改動。

⚠️ 刻意不加 max_tokens：模型預設輸出上限通常大於我們能合理硬設的值，硬設反而會更早截斷。目標是「截斷要被發現」，不是「提高上限」。

finish_reason = "length"／"Length"（大小寫不敏感）必須判為截斷；"stop"／"tool_calls"／"content_filter" 不判；欄位缺漏、choices 為空、非合法 JSON 一律不阻擋。

影響與相容性

  • 提示詞解析行為完全未變：三層優先序、預設全文、Get() 的對應關係都一模一樣，只是鍵字串來源收成一份。
  • /prompts 只多了畫面提示，不阻擋任何名稱、不改變儲存邏輯。
  • PDF 轉換多一個失敗判定：先前被截斷會靜默採用，現在會降級改用 MarkItDown 並在訊息欄留下原因。這是修正——原行為是靜默資料損毀。
  • 無資料庫 migration、無 API 合約變更、無設定檔鍵名變更。
