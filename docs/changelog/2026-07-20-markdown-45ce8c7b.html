會議編輯窗：摘要與決議事項改為左編輯／右 Markdown 預覽（1.0.22）

  • 日期：2026/07/20
  • 版本：1.0.21 → 1.0.22
  • 類型：UI 優化
  • 觸發來源：使用者回報「修改會議」對話窗的摘要欄只有 4 行、看不到幾個字，且內容是 Markdown，希望右側有預覽、兩區都能複製
  • 相關：會議模組 UI 優化（1.0.21）

一、改了什麼

「修改會議」對話窗的摘要與決議事項兩欄，從 Rows="4" 的單一 TextArea 改為左編輯／右即時 Markdown 預覽的分欄版面，各 320px 高，兩區各一顆複製鈕。

版面與複製邏輯直接照抄 Components/Commons/ContentEditDialog.razor:51-84 的既有實作，沒有自創新做法。

兩顆複製鈕語意不同，刻意不統一

位置呼叫複製到的內容
左（編輯區）navigator.clipboard.writeTextMarkdown 原始碼（看得到 #、-）
右（預覽區）keChat.copyElementText（wwwroot/js/chat.js）渲染後的可見純文字（無 Markdown 符號）

這是 2026-07-13 編修對話窗左右複製 已確立的設計，沿用不改。

預覽做了 300ms debounce

OnInput 立即更新 CurrentRecord.Summary／Decisions（資料不可延遲，否則存檔會漏掉最後幾個字），但延後 300ms 才更新預覽文字觸發重繪。

理由有二：①docs/planning/08-優化建議清單-TODO.md 早就把「Markdown 預覽 debounce」列為待辦；②2026-06-17 逐字稿編修移除預覽修復閃爍 記錄過長內容即時轉 HTML 壓垮 SignalR 造成畫面閃爍。本次預覽是表單內常駐、且有兩個實例，風險比一次性對話窗高。

元件因此實作 IDisposable 釋放兩個計時器。

CSS 放全域 app.css

新增 .meeting-md-split / .meeting-md-pane / .meeting-md-pane-head / .meeting-md-preview。

寫全域不是隨意選擇：AntDesign Modal 的內容不受 scoped CSS 管轄，寫進 .razor.css 會靜默失效——這正是 1.0.21 修掉的那七個 class 從未生效的同一個坑。

高度固定 320px 而非 flex:1：meeting-view-modal 的 body 是 overflow-y:auto 而非 flex 撐滿，用 flex:1 會塌成 0 高度。

二、為什麼摘要欄裡會是 Markdown（釐清，非本次修改）

MeetingService.ApplyGeneratedFieldsAsync（MeetingService.cs:707-737）讀出落檔的 .md 全文，餵給 MeetingMinutesGenerationService.ParseResponse——但那個方法預期的是 LLM 的 JSON 回應。餵 Markdown 進去必然 Degraded: true，於是走：

item.Summary = parsed.Degraded ? markdown : (parsed.Summary ?? item.Summary);

把整份會議紀錄灌進摘要欄。程式碼註解也明說了這件事。

衍生現象：Decisions 與 Participants 只在 !parsed.Degraded 時才寫入，而該條件在這條路徑上永遠不成立——也就是說「套用 AI 結果」從來沒有真的套用過決議事項與出席者，實際只改了摘要。

自動產生路徑（MeetingMinutesGenerationService.GenerateAsync）解析的是真正的 JSON，不受此影響，摘要會是提示詞要求的「三到五句純文字」。

本次未修改上述行為，僅記錄現況。是否要讓「套用 AI 結果」真的套用三個欄位，待裁示。

三、未完成：多行欄位按 Enter 疑似會直接存檔關窗

MeetingEditModal.razor 的 <EditForm> 掛了 @onkeydown="OnModalKeyDownAsync"，處理器（.razor.cs）是：

if (args.Key == "Enter") { await Task.Delay(200); await OnModalOKHandleAsync(new MouseEventArgs()); }

keydown 會從子元素冒泡上來，而這裡沒有排除 textarea、沒有檢查 Shift、沒有看事件來源。同一套寫法在 9 個編輯對話窗都有，逐一檢查過沒有任何一個有防護。

若屬實，使用者在摘要欄連換行都打不出來，本次把欄位加大的意義會大打折扣。

但這是程式碼推論，尚未實機重現。 嘗試過的驗證途徑與結果：

  • 檢查 AntDesign 1.6.0 的 DLL：stopPropagation 字串確實存在，但無法判定它是否用在 TextArea 的 keydown 上（可能屬於 Modal／Dropdown 等其他元件）
  • 測試專案沒有 bUnit，為了驗證這一件事引入元件測試框架不成比例

因此刻意未動那 6 個檔案／9 個 TextArea。待人工確認後再處理：開任一編輯對話窗，游標放進 TextArea 按 Enter——若對話窗存檔關閉即屬實。

規劃中的修法（尚未實作）：新增 Components/Commons/MultilineInputGuard.razor，內容為 <div @onkeydown:stopPropagation="true">@ChildContent</div>，包住所有 <TextArea>；單行 <Input> 不包，維持既有的 Enter 送出便利行為。

實際需要動的檔案是 6 個／9 個 TextArea（MeetingEditModal ×4、MyTasEditModal、ProjectViewView、CategoryViewView、TeamViewView、WorkCategoryViewView 各 ×1）。另外三個有 Enter 處理器的檔案（MyUserView、McpAccessKeyView、RoleViewView）沒有任何 TextArea，不受影響。

四、已知地雷：Decisions 的 4000 字驗證衝突（未處理）

MeetingAdapterModel.cs:68 有：

[StringLength(4000, ErrorMessage = "決議事項長度不可超過 4000 字元")]
public string? Decisions { get; set; }

但 AI 寫入是直接改 entity，繞過 AdapterModel 驗證；DB 欄位為 nvarchar(max) 亦無限制。若 AI 產出超過 4000 字的決議，使用者一開編輯窗按儲存就會被驗證擋下，而且擋的是他沒有輸入過的內容。

Summary 與 Participants 無此問題（沒有 StringLength）。

本次把決議事項改成大面積編輯區，等同鼓勵放更長的內容，這顆地雷更容易被踩到。依裁示暫不處理，僅記錄。三個可能方向：放寬／移除該限制、AI 寫入端加截斷、維持現狀。

六、測試

dotnet build 成功；dotnet test 616 個測試全數通過（與 1.0.21 相同，本次未新增）。

七、尚未執行的人工驗收

本次全屬 UI 改動，自動化測試涵蓋不到，以下一項都未實機驗證：

  1. 左右等寬、各 320px 高，版面正常
  2. 開有 AI 摘要的會議，一開窗右側就有渲染結果（非空白）
  3. 左側打字後約 300ms 預覽跟上；連續快打不卡頓
  4. 左側「複製」得到 Markdown 原始碼（含 #、-）
  5. 右側「複製」得到純文字（無 Markdown 符號）
  6. 編輯後存檔，重開內容正確（debounce 沒有吃掉最後幾個字）
  7. 摘要清空時預覽區空白且不報錯
  8. 貼入數千字 Markdown 不出現閃爍或連線中斷
  9. 決議事項欄重複 2–8
  10. 第三節的 Enter 行為確認（決定是否要做那 6 個檔案的修改）
