清洗前的軟上限警告（1.0.113 → 1.0.114）

  • 變更日期：2026/07/30
  • 版本：1.0.113 → 1.0.114
  • 性質：程式變更（src/）＋測試＋文件。無模型變更、無新表、無 migration。
  • 對應待辦：知識來源規模守門 TODO 的 P3——至此三項全數完成
  • 編碼：UTF-8（繁體中文，含 BOM）

一、補上最後一道防線

清洗的去重與遮罩要把整份彙整內容重新輸出一遍，所以真正的天花板是模型的輸出上限。這一系列三項改善分別站在三個時間點：

版本做什麼時機
1.0.112（P1）真的被截斷時，遮罩失敗、整筆清洗中止並說明原因事後
1.0.113（P2）彙整量在「管理成員」與「確認清洗」對話窗看得到事中
1.0.114（P3，本次）超過門檻時先提醒，要勾選確認才能送出事前

P1 與 P2 讓問題「被發現」，P3 讓它「不要發生」——尤其對「一次加了 40 個成員」這種情況，事前提示能省下十幾分鐘的清洗與一次失敗。

二、行為

彙整量超過 SystemSettings.Cleaning.AggregateWarnBytes（預設 200,000 位元組，約 6.6 萬中文字）時，「確認清洗」對話窗顯示黃色警示，講三件事：

  1. 會發生什麼 —— 去重與遮罩要把整份內容重新輸出一遍，可能撞上模型的輸出上限
  2. 撞到會怎樣 —— 遮罩會失敗、整筆清洗中止（不會產出殘缺內容，但要等到跑完才知道）
  3. 怎麼辦 —— 先分盒，或在上傳前把過大的文件拆檔；指向「知識來源分盒與規模上限指南」

並且要勾選「我了解可能因輸出上限而失敗，仍要繼續」才能按下「清洗」。

這是提示，不是阻擋。 判準取決於實際使用的模型，硬擋會擋到正常使用。TriggerCleaningAsync 的行為完全不變——這純粹是 UI 層的事前提示，不是業務規則。

兩個刻意的設計選擇

① 判斷邏輯放在模型的純計算屬性，不放在 Razor。 ExceedsWarnThreshold 是純函式，所以邊界（小於／等於／大於、0、負數）可以用不碰資料庫也不碰 UI 的測試釘住；View 只讀一個 bool，不必注入 IOptions<SystemSettings>，也就不必動它的建構式。

② 沿用既有模式擋 OK 鈕。 Components/Commons/ContentEditDialog.razor:94 已經在用 OkButtonProps="@(new ButtonProps { Disabled = … })"，直接沿用而不自己發明一套。

一個容易漏掉的細節

每次開啟對話窗都要重設 cleaningOversizeConfirmed = false。 不重設的話，上一筆勾選過的狀態會殘留，下一筆超過門檻的來源就直接可以按下去了——警告等於失效，而且不會有任何症狀。

四、測試（新增 11 條；全量 1087 → 1098，0 失敗）

新檔 CleaningAggregateWarnTests.cs：

  • 邊界：199,999 不警告／200,000 剛好等於門檻不警告／200,001 警告
  • 停用：門檻 0、-1、long.MinValue → 即使 TotalBytes = long.MaxValue 也一律不警告

（若把停用寫成「一律警告」，每次清洗都多一道勾選，使用者會學會無腦勾——那比沒有警告更糟）

  • 未量測（TotalBytes = 0）不警告
  • 程式預設值為 200_000
  • 🔴 設定漂移守門：直接讀 repo 真實的 appsettings.json，斷言 SystemSettings:Cleaning:AggregateWarnBytes 存在且與程式預設值一致。沿用 UnsafeDefaultsTests 讀真實設定檔的既有作法——沒有這條，「程式加了設定但設定檔沒加」或「兩邊值不一致」都不會有任何測試紅燈

KnowledgeSourceMeasureTests 新增服務層流通測試（門檻可覆寫、停用時不警告）。

⚠️ 既有測試一條都沒有修改。
