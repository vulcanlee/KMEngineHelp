抽出共用的 Markdown 轉換核心 md_render.py（1.0.120 → 1.0.121）

  • 變更日期：2026/07/31
  • 版本：1.0.120 → 1.0.121
  • 性質：scripts/ 重構（行為零變更）＋新增一道回歸守門。src/ 零變更、無模型變更、無新表、無 migration、無新設定鍵。
  • 編碼：UTF-8（繁體中文，含 BOM）

一、解決什麼

scripts/ 底下有兩支各自把 Markdown 轉成 HTML 的腳本：Build-HelpSite.py（說明網站 448／391 頁）與 Build-OnboardingDocsHtml.py（5 份伴生 HTML，有進版控）。

兩者的區塊解析器幾乎逐行相同——圍欄程式碼、水平線、標題、引言遞迴、表格（含對齊列判定與欄數補齊）、清單（含核取方框）、段落合併，以及行內的「跳脫 → 保護 code → 粗體 → 連結 → 還原」骨架。約 130 行實質邏輯複製了兩份。

這是會出事的那種重複：1.0.102 的「Markdown 表格渲染修正」已經證明過，這類解析程式改一邊、另一邊靜默不動時建置成功、無例外、測試全綠，只有人眼看得出來。專案內已有 doc_slug.py 的先例（Build-HelpSite.py 與 Test-DocLinks.py 共用 slug 演算法，註解明講「避免兩邊算法漂移」），這一版把同樣的紀律套到轉換核心。

二、scripts/md_render.py（新）

只放解析，不放政策。 連結怎麼解、標題要不要 id、章節導覽要不要收，全部由呼叫端以 callback 注入；模組裡沒有任何一個 if 在判斷「這是哪一支腳本」。

callback必要用途
resolve_link(href, is_image)✅唯一的連結政策出口
make_id(raw)—標題 id；不傳就不輸出該屬性（伴生 HTML 走這條）
on_heading(level, raw, sid, top)—收章節導覽（只有說明網站要）
on_nonclickable()—計數（只有說明網站的統計要）

⚠️ 一項對原規劃的修正

原本規劃 resolve_link(href) -> (url|None, kind)。兩個欄位不夠——兩支腳本對同一種連結輸出的 HTML 不一樣：

外部連結不可點時的 title
伴生 HTMLrel="noopener"只放檔名
說明網站rel="noopener" target="_blank"放跳脫後的完整 href

改成回傳 (url, attrs, title) 三元組，attrs 與 title 都由呼叫端決定。政策 100% 留在呼叫端。

兩處逐字核對過的差異（都不改變輸出）

  1. 連結正規式：伴生腳本原本允許 href 帶空白（[^)]+），說明網站不允許（[^)\s]+）。掃過整個 docs/ 確認兩式結果零差異，統一用嚴格式。
  2. 標題正規式：說明網站原本用 doc_slug.HEADING_RE（會吃掉 ATX 尾端的 # 與空白），伴生腳本用寬鬆式。全 docs/ 零差異，統一用嚴格式——因為說明網站會把這裡取到的標題文字餵給 doc_slug 算 slug，兩邊用不同的式子會讓錨點靜默對不上。這是重構時順手消掉的一個隱患。

另外，伴生腳本原本完全不處理 ![]() 圖片語法；已確認那 5 份 md 零張圖片，所以核心統一處理不改變今天的產出。

三、⚠️ 順帶抓到一個既有的漂移

驗證第一步就發現：Build-OnboardingDocsHtml.py 重跑後，有兩份伴生 HTML 出現差異。

查證後確認不是重構造成的——把改動 git stash 起來、用重構前的舊程式重跑，得到一模一樣的差異。真正的原因是：那兩份 md 在 1.0.112 前後被更新過，但伴生 HTML 從來沒有重新產生，版控裡那兩份停留在舊內容（還在說「截斷完全沒有提示」，而 1.0.112 起已經會直接失敗或留註記）。

也就是說，「md 是唯一來源」這條紀律在這裡已經失效了一陣子，而且沒有任何東西會發現。本版一併重新產生並納入。

這正好說明為什麼要加第四節那道守門：只靠人記得重跑是不夠的。

四、scripts/Test-MdRender.py（新）＋ 黃金檔

  • scripts/testdata/md_render_fixture.md：涵蓋 H1～H6、圍欄程式碼、水平線、引言（內含表格與清單，驗遞迴）、表格（含欄數不足補齊）、有序／無序清單、[ ]／[x]／[X] 核取方框、行內 code／粗體／五種連結／圖片、段落跨行合併、HTML 跳脫。
  • 用兩種形態各跑一次（帶 id＋收 TOC／不帶 id），對應兩支呼叫端的用法。
  • 不符時印出逐行 unified diff；--update 可重新產生黃金檔（刻意要顯式指定）。

接進 Test-All.ps1 成為第一道

排第一是因為轉換核心壞了，後面兩道文件守門的結果就不可信（產出的 HTML 本來就不對）。實測 0.6 秒。

順手修掉一個同類的毛病：Test-All.ps1 收尾那句寫死「四道守門全部通過」，加了第五道之後就過期了。改成用實際跑過的道數。

⚠️ 依 1.0.118 的教訓，這支腳本自己的訊息不用表情符號，並加了 sys.stdout.reconfigure(errors="replace") 防 cp950 主控台炸掉。

五、驗證：產出零差異

重構的唯一驗收標準是行為完全不變。

驗證結果
說明網站完整版逐位元比對（重構前快照 vs 重構後）完全相同
說明網站對外版逐位元比對完全相同（兩版合計 853 個檔）
5 份伴生 HTML 對「舊程式剛產生的版本」逐位元比對5 份全部相同
scripts/Test-All.ps1五道全綠（測試 1120 通過／0 失敗，本版 src/ 零變更）
🔴 反證：故意把 <strong> 改成 <b>黃金檔守門紅燈、結束碼 1，並印出正確的差異行；還原後恢復綠燈

⚠️ 伴生 HTML 的比對基準刻意不是版控裡那份（那份是過期的，見第三節），而是「用重構前的程式重新產生的版本」。拿過期的當基準會把既有漂移誤算成重構的錯。

ci.yml 一個字都不用改

1.0.118 決定「CI 只呼叫 Test-All.ps1、不把守門清單再列一次」，理由是「列兩份的話日後新增守門一定會漏改其中一份」。這一版就是那個「日後」——新增第五道守門，ci.yml 零改動。

七、後續

scripts/ 這條線的重構到此為止。CSS 刻意沒有共用——兩支的調色盤雖然相同，但設計目標不同（單頁文件 vs 帶站台框架的網站），硬合反而難改。

仍掛著待決定的：1.0.119 查出的三項刪除／更新落差（見 更新與刪除的連鎖影響 §七），以及還原階段回報的兩個高嚴重性套件弱點。
