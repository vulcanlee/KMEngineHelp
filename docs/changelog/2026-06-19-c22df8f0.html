音訊轉錄抖音下載失敗後可直接重試，並強化下載斷線重試（0.2.85）

  • 日期：2026-06-19
  • 版本：0.2.84 → 0.2.85
  • 類型：缺陷修正 + 強化

問題

轉錄抖音影片時，下載階段失敗（紀錄已顯示「失敗」），但按「重試轉錄」卻回：

只有失敗或已取消的紀錄可以重試。

導致無法重新下載；重新整理網頁後再按同一顆按鈕卻可以。背景日誌可見下載失敗：

System.InvalidOperationException: 抖音助手執行失敗 (ExitCode=1)：
TypeError: terminated ... [cause]: SocketError: other side closed (code: 'UND_ERR_SOCKET')

根因

兩個獨立成因：

  1. 重試誤判＝EF Core 追蹤的陳舊實體：MediaTranscriptionView 以建構式注入

MediaTranscriptionService，在 Blazor Server 中其 BackendDBContext 綁定整個 SignalR circuit（長壽命）。新增抖音網址時實體被以「等待中」追蹤；之後背景服務（獨立 scope／獨立 context）將 DB 更新為 處理中→失敗，但列表 reload 全用 .AsNoTracking()，不會更新已追蹤的 實體。RetryAsync／CancelAsync 的查詢未先清掉本地追蹤，EF 從識別映射回傳陳舊的「等待中」 實體，狀態檢查因而失敗。重整網頁＝全新 circuit／context，識別映射清空，才讀到 DB 真實的 「失敗」狀態，故能重試。

  1. 下載失敗＝抖音 CDN 中途斷線且全鏈路無重試：抖音 CDN 偶爾中途關閉 TLS 連線

（UND_ERR_SOCKET: other side closed，屬瞬時網路／限流）。get-douyin-audio.mjs 的 fetch() 無逾時、無重試，斷一次即整體失敗；且 C# 端包成 InvalidOperationException，被 PipelineRetryHelper.IsTransient 判為不可重試，使 TranscriptionProcessor 的自動重試跳過。

修正

  • MediaTranscriptionService.RetryAsync／CancelAsync：查詢前加

CleanTrackingHelper.Clean<MediaTranscription>(context)，強制讀 DB 最新狀態 （比照 UpdateTranscriptContentAsync 既有慣例，亦符合 CLAUDE.md「Update/Delete 前 CleanTrackingHelper.Clean<T>()」）。

  • tools/douyin-audio/get-douyin-audio.mjs：下載段改為每次 25 秒逾時（AbortController）

+ 最多 3 次重試 + 遞增退避（1.5 秒 × 次數），重用同一預簽章 CDN 網址重抓，不需重啟瀏覽器； 重試耗盡後維持原本的失敗退出行為。未調整 C# 的 IsTransient（避免把設定／檔案錯誤也變成重試）。

影響範圍

  • 變更檔案：Business/Services/DataAccess/MediaTranscriptionService.cs、

tools/douyin-audio/get-douyin-audio.mjs、tools/douyin-audio/README.md、 src/.../KnowledgeExtraction.Web/appsettings.json（版本號）。

  • 無模型／資料庫變更，不需 migration。

驗證

  1. 同一瀏覽器 session 內新增抖音網址轉錄、不重整；待下載失敗顯示「失敗」後直接按「重試轉錄」，

應出現「已重新排入轉錄佇列」且狀態轉「等待中」，不再出現「只有失敗或已取消的紀錄可以重試」。

  1. 以正常抖音連結重跑，下載段在偶發斷線時會印出重試訊息並成功完成。
  2. 回歸：「取消轉錄」於處理中／等待中狀態仍正常運作。
