Graph RAG P13：圖譜唯讀 Web API（1.0.95 → 1.0.96）

  • 日期：2026-07-28
  • 版本：1.0.95 → 1.0.96
  • 類型：新增功能（Graph RAG 第十三階段；無新表、無 migration）

背景

P9（1.0.91）把「全域問答」與「實體鄰域」接到了 MCP，但只有 MCP 用戶端能用——Web/Controllers/ 沒有任何圖譜控制器，一般 REST 呼叫端（既有前端、第三方系統、排程腳本）取不到這兩項能力。這是 P9 changelog 自陳的限制，也是待辦盤點列為收尾計畫最後一項的缺口。

變更

1. 新增 KnowledgeGraphController

嚴格比照 docs/architecture/Web API 設計慣例.md 與 CategoryController：雙路由、[ApiController]、[ApiValidationFilter]、JWT [Authorize]、回傳 ApiResult<T>。

端點內容
POST /api/v1/KnowledgeGraph/global-ask包 KnowledgeBaseChatService.GlobalMapAsync。只做 map 不做 reduce，與 MCP knowledge_ask 的 mode=global 語意一致——回傳「參考資料」而非最終答案。
GET /api/v1/KnowledgeGraph/neighbors?entityName=&maxHops=包 GraphTripleService.GetNeighborhoodAsync（P8）。純 DB 查詢不呼叫 LLM。

2. 權控：不另寫一套

控制器只做「轉呼叫 ＋ 形狀轉換」，ACL 完全交給既有服務——GetAccessibleSummariesAsync 的社群子集判定、GetNeighborhoodAsync 的三元組與兩端節點雙層權控。與 MCP 走同一條把關程式碼。

身分解析重用 McpIdentityResolver：它的名稱雖以 Mcp 起頭，機制其實完全通用——「HttpContext 的 Sid claim → 反查使用者 → 填入 CurrentUserService」，JWT 認證的 API 請求正好適用。刻意重用而非另寫一份（也順帶讓 API 的稽核與聊天紀錄自然取得身分）。解不出身分時 RecordAccessScopeProvider fail-closed 為「非管理員、無團隊」。

3. ⚠️ 兩處刻意與 MCP 不同的行為

maxHops 超界回 400，不靜默夾住。 GetNeighborhoodAsync 內部本來就有 Math.Clamp(maxHops, 1, 3)，所以 MCP 工具送 99 會被無聲改成 3。REST 這邊改為 [Range(1, 3)] ＋ 既有 ApiValidationFilter 產生的 400——延續 P9 立下的「無法辨識的 mode 明確拋錯、不靜默退回」原則：呼叫端不該以為自己送的值生效了其實被吃掉。

LLM 未設定回 503，不是 500。 這是實作測試時發現的真問題：測試 host 沒有 ApiKey，global-ask 會在逐社群呼叫時炸成 500。但那是伺服器組態問題、不是呼叫端送錯東西，回 500 既不可行動也誤導。加前置守門 openAiSettings.IsChatLlmConfigured() → 503 ＋ 可行動訊息。

⚠️ 503 不在慣例文件的狀態碼表內。判斷是：該表列的是常見情境而非白名單，而 400（怪罪呼叫端）在此語意是錯的。已同步把 503 補進 Web API 設計慣例.md 的表格。

4. Token 歸屬與問答紀錄（完整可稽核）

global-ask 會呼叫 LLM，不處理的話用量會落入「（系統自動）」桶——正是 1.0.80 那次專門修過的老問題。

  • 新增 LlmTokenUsage.OperationApiGraphGlobalAsk ＋ OperationLabelHelper 的中文標籤「Web API 圖譜全域問答」。刻意不重用 OperationGraphGlobalChat（它的標籤已是 Blazor 頁面的「AI 知識問答（全域）」，重用會讓報表分不出是誰打的）。OperationLabelTests 會擋「沒標籤」與「標籤重複」。
  • OperationContext.Push 放在 action 內、與後續 await 同一方法範圍（AsyncLocal 才會流到底層 client），比照 KnowledgeAskTool。
  • 新增 LlmChatLog.OriginApi ＋ ChatLogService 的來源標籤分支「Web API 問答」；global-ask 比照 MCP 寫聊天紀錄。

5. DTO：精簡圖譜專用

GraphGlobalAskResultDto 刻意不含 sources 與 topScore——這支端點沒有 local 模式，社群摘要也沒有 chunk 層出處與相似度，兩者恆為空／0，回了反而讓呼叫端誤以為有出處可追。

6. 順手修：host 型整合測試的間歇性紅燈

新增第三個 ApiTestApplicationFactory 消費者後，完整測試回合出現整批紅燈（單獨跑該類別卻全過）。讀程式碼後根因明確：工廠建構式把設定寫進行程層級環境變數、Dispose 又把它們清成 null，而每個實例的 rootPath 都是隨機的——多實例並行時後者蓋掉前者的 DatabasePath，先結束者的 Dispose 清掉還在用的變數。

這解釋了 P12 那次 SystemHealthReportTests 的偶發紅燈（當時只如實記載、未歸因）。修法：三個 host 型測試類別改用共用的 ApiTestCollection（ICollectionFixture），只會有一個實例且 xUnit 不讓同 collection 的類別並行。

驗證

  • dotnet build 成功、警告數與位置完全相同（26 條 → 26 條，逐條比對零新增）。
  • dotnet test 950 全綠（既有 938 + 新增 12），連跑三次穩定（修掉共用工廠問題後不再出現間歇紅燈）：
  • 兩支端點未帶 JWT → 401
  • maxHops 0／4／99 → 400（Theory 3 列）；entityName 空 → 400；question 空 → 400
  • 查無實體 → 200 + found=false（不是 500）
  • 管理員看得到已核可關係
  • leak=0（HTTP 端到端）：種一個只屬「甲隊」的非管理員使用者、真的用它登入拿 JWT → 看不到乙隊關係，但仍看得到自己隊的關係（證明前者的 false 是權控造成、不是資料沒種進去）
  • LLM 未設定 → 503 ＋ 可行動訊息
  • 無 model 變更，本次不產 migration（已確認）。
  • scripts/Test-DocsEncoding.ps1 0 失敗；版本 1.0.96。

已知限制（未來增量）

  • ⚠️ global-ask 的 leak=0 沒有 HTTP 層測試：社群選取雖發生在 LLM 呼叫之前，但結果只透過「有產出重點的社群」外顯，測試 host 沒有 LLM 就沒有 usedCommunities 可斷言。它的權控由 GetAccessibleSummariesAsync 把關，已由 KnowledgeAskToolTests（P9）與 RagEvaluationServiceTests（P10）在服務層釘住「他隊與跨隊社群皆不可見」。本階段的 HTTP leak 證據來自 neighbors。
  • 仍沒有寫入型圖譜 API（新增／核可三元組），與 MCP 的既有非目標一致。
  • 沒有針對 API 的額外節流：global-ask 成本＝可存取社群數次 LLM 呼叫（受 GraphGlobalCommunityCap 控管，預設 20），頻繁呼叫會放大成本。與 MCP 的同一項限制並存。
  • 未執行：以真實 LLM 與 Swagger UI 做端到端驗證（需 API 金鑰與已建立的社群摘要）。本次不宣稱已驗。
