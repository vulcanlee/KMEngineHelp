清洗的輸出截斷偵測（1.0.111 → 1.0.112）

  • 變更日期：2026/07/30
  • 版本：1.0.111 → 1.0.112
  • 性質：程式變更（src/）＋測試＋文件。無模型變更、無新表、無 migration。
  • 對應待辦：知識來源規模守門 TODO 的 P1（三項中的第一項）
  • 編碼：UTF-8（繁體中文，含 BOM）

一、修掉什麼

清洗的去重與遮罩兩步要把整份彙整內容重新輸出一遍，所以真正的天花板是模型的輸出上限，不是輸入上下文。撞到輸出上限時 SSE 會正常結束、回傳文字非空——而舊程式只檢查「是否空白」，於是把殘缺內容當成成功：

  • 狀態仍是「已清洗」
  • 信心分數可能還很高（模型只評自己輸出的那一段）
  • 沒有任何註記
  • 之後整條 RAG（切塊／嵌入／問答）都建立在殘缺內容上

使用者的感受是「明明有這份文件卻查不到」，而且會被誤判為檢索問題，然後去調檢索參數（無效，因為那段內容根本不在索引裡）。

這是 1.0.112 之前全系統唯一完全無痕跡的失敗。

二、怎麼修

檔案變更
Business/Services/Transcription/IChatCompletionClient.cs新增 CompleteStreamingCheckedAsync，回傳 (string Text, bool TruncatedByOutputLimit)。帶預設實作（回報 false，沿用舊行為）
…/Transcription/OpenAIChatCompletionClient.cs①StreamAsync 本體抽成 StreamCoreAsync(messages, ct, onFinishReason)，公開的 StreamAsync 以 null 委派（簽章與外部行為零變化）；②SSE 迴圈擷取 choices[0].finish_reason；③覆寫 CompleteStreamingCheckedAsync，finish_reason == "length"（忽略大小寫）即回報截斷並記 LogWarning
…/Cleanings/CleaningEnhancer.cs去重與遮罩改用 checked 版本（見下表）

兩步的處置刻意不同

步驟被截斷時為什麼
去重不採用截斷輸出 → 退回未去重的原文 → 在清洗結果開頭寫 > 註記：去重步驟的輸出被模型輸出上限截斷…保住完整內容遠比省下重複段落重要。而且下一步遮罩會對同樣過大的內容再撞一次上限並讓整筆失敗，所以使用者仍會得到明確的失敗，不會拿到殘缺內容
遮罩擲例外 → 整筆清洗失敗，訊息說明是輸出被上限截斷並建議分盒或拆檔截斷的尾段根本沒有經過模型，那部分的個資與機密必然沒有被遮到。把它落檔等於把未遮罩內容送進索引。與「遮罩失敗＝整筆清洗失敗」的既有安全設計同一理由

分類／摘要／信心維持原樣——輸出只有幾十字，撞不到上限，加了只是噪音。

為什麼不改共用方法

CompleteStreamingAsync 有 11 個生產呼叫端（清洗 5 處、蒸餾、圖譜 3 處、會議紀錄、依提示詞產生 2 處）。改它的簽章或行為會把變更擴散到全部——這正是 PdfMarkdownLlmClient.cs:85-115 的 remarks 早已寫明的風險（該處的截斷檢查也是刻意不放進共用方法）。

本次改用「新增帶預設實作的介面方法」：

  • 只有清洗的兩步改用 → 另 10 個呼叫端行為完全不變（有測試釘住）
  • 測試假件（如 CleaningEnhancerTests 的 StreamTrackingFakeClient）一行都不用改

PDF 那支 IsTruncatedByOutputLimit 雖是 public static，但它吃的是完整的非串流回應 JSON，串流路徑拿不到那個結構，故無法直接重用——只沿用判定語意（忽略大小寫比對 "length"）。

三、測試（新增 10 條；全量 1057 → 1067，0 失敗）

OpenAIChatCompletionClientTests（沿用既有 Fixture.Create(idleSeconds, script) 腳本化 SSE）：

  • finish_reason == "length" → 判為截斷，且仍回傳已收到的文字（由呼叫端決定要不要用）
  • 🔴 反證（本組最重要）：stop／tool_calls／content_filter／完全沒有 finish_reason → 一律不得誤判。判定寫反會讓每一次清洗都失敗，這種迴歸比漏偵測嚴重得多
  • 大小寫不敏感（與 IsTruncatedByOutputLimit 語意一致）
  • 釘住既有行為：CompleteStreamingAsync 被截斷時仍照舊回傳文字、不擲例外

CleaningEnhancerTests（新增可回報截斷並記錄輸入的 TruncatingFakeClient）：

  • 去重截斷 → Notes 含截斷字樣，且遮罩步驟收到的是原始內容（不是被截斷的去重輸出）
  • 遮罩截斷 → 擲 InvalidOperationException（訊息含「截斷」），且不再跑分類／摘要／信心
  • 反證：兩步都沒截斷時，Body／ConfidenceScore／Notes（空）／呼叫次數與加偵測前完全一致

⚠️ 既有測試一條都沒有修改（沒有為了遷就新程式而改斷言）。

四、⚠️ 對既有資料的影響

1.0.112 之前清洗的知識來源，仍可能已經被靜默截斷——當時沒有任何痕跡，所以無法從資料本身分辨。

處置建議（已寫入文件）：

  1. 最快的做法是重新清洗一次：新版會直接失敗或留註記。
  2. 要人工判斷則用 分盒與規模上限指南 §4.2 的三步法：比長度（清洗後 .md ÷ 成員萃取檔總大小，正常 0.5～1.0）→ 找 > 註記： → 抽查尾段。
