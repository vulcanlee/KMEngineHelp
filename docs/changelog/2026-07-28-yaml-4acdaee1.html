變更紀錄

文件萃取支援 YAML（.yaml / .yml）（1.0.92 → 1.0.93）

  • 日期：2026-07-28
  • 版本：1.0.92 → 1.0.93
  • 類型：功能小幅擴充（允許清單）

需求

使用者詢問系統是否支援 YAML 上傳，盤點後確認完全不支援：src/ 全域搜尋 yaml／yml 零命中，也沒有任何 YAML 函式庫參考。

但 DocumentFormatValidator.AllowedExtensions 已收錄 .json、.xml、.csv、.md 等結構化／純文字格式，唯獨少了 .yaml／.yml。以格式性質而言比較像是當初漏列而非刻意排除——YAML 是設定檔、API 規格（OpenAPI）、CI 流程等企業文件的常見載體，納入知識庫有實際價值。

變更

程式碼只動一行

Business/Helpers/DocumentFormatValidator.cs 的允許清單加入 ".yaml", ".yml"。

允許清單是單一常數，下列六個連動點全部共用它，因此不需要個別修改：

連動點位置
前端 <InputFile accept>DocumentExtractionView.razor:198（AcceptAttribute）
UI「支援格式：…」文字（單檔／批次各一處）同檔 :199、:251（AllowedExtensionsText）
後端上傳驗證DocumentExtractionService.cs:165（BeforeAddCheckAsync）
ZIP 批次 zip bomb 預檢同檔 :415
ZIP 批次逐筆過濾（不支援者列入 Skipped）同檔 :448

為什麼不必動轉換流程——這是本次唯一的實質風險，已先查證

MarkItDownConverter 是副檔名無關的（直接 Process.Start(markitdown "in" -o "out")），能不能轉完全由外部 MarkItDown 決定，所以允許清單放行不等於轉得出來。查證系統實際設定的那份（MarkItDownSettings:MarkItDownPath，版本 0.1.6）：

  • _plain_text_converter.py 的 ACCEPTED_FILE_EXTENSIONS（.txt/.text/.md/.markdown/.json/.jsonl）不含 .yaml；ACCEPTED_MIME_TYPE_PREFIXES（text/、application/json、application/markdown）也不含 application/yaml。單看這兩個清單會得到「不支援」的錯誤結論。
  • 真正放行的是 accepts() 的第一道判斷 if stream_info.charset is not None: return True。MarkItDown 在 _get_stream_info_guesses() 會先用 magika 辨識串流內容，只要 is_text=True 就填入 charset。
  • 以 YAML 內容實測 magika：label=yaml, is_text=True, mime=application/x-yaml。
  • 端對端實測 markitdown sample.yaml -o sample.md：ExitCode 0，輸出為原始 YAML 文字（含中文正常）。

結論：.yaml／.yml 走 PlainTextConverter 純文字直通，與現有 .json 行為一致，因此 DocumentExtractionProcessor 不新增任何分支。

⚠️ 這條路徑依賴 magika 的內容辨識，不是副檔名白名單。若日後升級 MarkItDown 後 YAML 轉換失敗，先查的是 magika 而非副檔名對照表；退路是在 DocumentExtractionProcessor.ProcessCoreAsync 呼叫 MarkItDown 前加一條純文字直通分支。

刻意不改的地方

  • DocumentExtractionService.GuessContentType() 不動。它推得的 ContentType 唯一用途是 IsLlmFileSupported()，而該方法只允許 image/* 與 application/pdf。YAML 落到 application/octet-stream 不影響任何行為，加 text/yaml 是無作用的推測性變更（CLAUDE.md §2）。
  • ImageFormatValidator／MediaFormatValidator 與本次無關。
  • 無模型變更 → 無 migration；無新增頁面 → 不涉及 Menu.json／RolePermissionService／MagicObjectHelper 三處同步；不需要 YamlDotNet（系統只做格式轉換，不解析 YAML 語意）。

測試

DocumentFormatValidatorTests 的允許清單 [Theory] 新增 3 條：openapi.yaml、pipeline.yml、CONFIG.YAML（第三條同時涵蓋 OrdinalIgnoreCase 大小寫不敏感，與既有 NOTE.TXT 同風格）。

⚠️ 本批未取得測試執行結果：撰寫當下工作區存在另一批未提交的 Graph RAG 檢索快取進行中變更（GraphRetrievalCache／IGraphRetrievalCache 為未追蹤新檔），KnowledgeExtraction.Tests 因該批 WIP 而編譯失敗（GraphExtractionProcessorTests／GraphTripleServiceTests／GraphEntityAliasServiceTests／RetrievalServiceTests／Mcp/* 的建構式參數與型別不符），與本次變更無關。KnowledgeExtraction.Business 與 KnowledgeExtraction.Web 建置成功。待該批 WIP 收斂後需補跑一次測試確認全綠。

影響與相容性

  • 文件轉文字頁的檔案選擇器可選到 .yaml／.yml，「支援格式」提示同步出現這兩項。
  • ZIP 批次匯入中的 YAML 不再被列入「不支援格式」而略過，改為成功建立記錄。
  • 轉出的 Markdown 為 YAML 原文（未加程式碼區塊圍欄），與 .json 現行行為一致。
  • 既有記錄不受影響；無 API 合約變更。
