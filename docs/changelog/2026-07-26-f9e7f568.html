實體名詞用法統一 55 處：選單叫新名、訊息叫舊名的分裂收尾（1.0.75→1.0.76）

  • 日期：2026-07-26
  • 版本：1.0.75 → 1.0.76
  • 類型：一致性修正（純顯示字串）

需求

1.0.57 改選單名、1.0.58／1.0.70 補齊顯示標籤，但那三批的規則都是「只改值剛好等於舊選單名的標籤」，所以實體名詞用法一直沒動：使用者在選單看到「工作任務」，操作失敗時卻看到「新增工作項目失敗。」；表單標題寫「清洗規則設定」，刪除確認卻問「確定要刪除這筆清洗設定檔嗎？」。

這批把這個分裂收掉。

Service 訊息的命名規則（沿用手足服務既有寫法，非新創）

MediaTranscriptionService 早就寫「找不到要修改的轉錄資料。」而不是「音訊轉錄資料」；ImageRecognitionService 寫「重試圖片解讀失敗。」（新頁名）。本批沿用同一套：

  • 「…資料」類用中性實體名詞：「找不到要修改的文件資料。」（不是「文件轉文字資料」，那樣讀起來很怪）
  • 動作類用新頁名：「重試文件轉文字失敗。」「取消文件轉文字失敗。」

RAG 評測樣本 為何不動

RAG 是產業標準技術詞，全庫另有 20+ 處合理的技術用法；而舊選單名嚴格說是 RAG評測（無空格），RAG 評測（有空格）從來不是選單名。這正好符合 1.0.58 對「黃金樣本」的同一套豁免邏輯，因此 11 處全部保留。

黃金評測樣本 為何改成「黃金樣本」而不是「清洗品質評測樣本」

那 4 處講的是「這筆資料叫什麼」而非「這一頁叫什麼」。對齊依據是既有程式：DashboardService 的儀表板卡片標籤已是「黃金樣本」，GoldenSampleService 的 11 處訊息全部是「黃金樣本」。

⚠️ 四個硬排除（全部以 git diff 驗證）

這批的風險不在改了什麼，在不能改什麼。全程逐處手改、禁止跨檔全域取代。

#排除對象為什麼驗證
1MagicObjectHelper.cs、RolePermissionService.cs常數值寫在每個角色的 RoleView.TabViewJson。而 7 個識別字（角色_工作項目／角色_圖片清單／角色_分類清單／角色_團隊清單／角色_提示詞清單／角色_清洗設定檔／角色_知識來源管理清單）文字上包含本批要取代的舊名 —— 全域取代會波及它們（編譯失敗，好結果），但「順手改識別字讓它編過」就會連值一起改掉＝所有既有角色掉權限git diff --stat 兩檔無輸出 ✓
2會議紀錄（紀）約 100 處那是 AI 產出的會議紀要文件，與選單改名無關。只有 會議記錄（記）才是舊選單名git diff 中含「會議紀錄」的唯一一行，兩側逐字相同（該行只有 工作項目→工作任務 在變）✓
3MeetingService 掛載會議錄音的 Description它會 SaveChanges 落地到 MediaTranscription.Description 資料列。它同時顯示在「影音轉逐字稿」清單描述欄，長得像 UI 標籤，但改了會讓新舊資料列分歧且無法回溯未改，並在行內加註說明 ✓
4LlmPromptDefaults.cs 的 MeetingMinutes送給 LLM 的提示詞，改字會改變模型行為。而且同一個字串內「會議記錄助理」與「會議紀錄」兩種寫法都有提示詞本體未改，僅新增 <remarks> 說明 ✓

另外 MediaTranscriptionView.razor 的「需於設定檔設定 DouyinHelperScript」指的是 appsettings.json，與清洗設定檔無關，不可改（本批未動）。

註解／XML doc／log 樣板刻意不改（1.0.71 起的既有原則）：混進來會讓 diff 從 80 行膨脹到 130 行，反而遮蔽真正有風險的那幾行。
