變更

「知識庫」群組的子選單順序由

知識來源加工 → 清洗品質評測 → 知識頁審核 → AI 知識問答 → 檢索品質評測 → 知識百科 → 知識圖譜審核

改為（並以兩條分隔線分成三組）：

知識來源加工      /knowledge-sources          ┐ 群組 1：日常入口
AI 知識問答       /knowledge-base-chat        ┘
──────────────────────────────
清洗品質評測      /golden-samples             ┐
知識頁審核        /knowledge-distillation     ├ 群組 2：品質與審核
檢索品質評測      /rag-evaluation             ┘
──────────────────────────────
知識百科          /knowledge-wiki             ┐ 群組 3：瀏覽與圖譜
知識圖譜審核      /knowledge-graph-review     ┘

原順序是按功能加入時間累積而成，不反映實際使用頻率——每天都在用的「AI 知識問答」被排在第 4 位、夾在兩個評測/審核頁之間。

與 2026-07-25「專案分類選單位置調整」的差異：本次 Menu.json 的 id 刻意不重編號（維持 41、45、42、44、46、47、48 的非連號狀態）。id 在程式中完全沒有被使用（渲染 key 走陣列位置、選中狀態走 URL 前綴比對），重編號無益，反而會讓既有文件的 id 引用失效。

三處同步（位置索引耦合）

Menu.json 與 RolePermissionService 權限樹以位置索引對應（SidebarMenuService.ApplyChildPermissionStructure 是 permissionNames[index]，名稱不參與比對），因此換序必須成對修改：

  1. KnowledgeExtraction.Web/Datas/Menu.json — 知識庫 subMenu 換序、加 group 欄位。
  2. KnowledgeExtraction.Business/Services/Other/RolePermissionService.cs — 角色_知識庫問答 由第 4 個子權限移到第 1 個；並補上逐項對照註解。兩個動作型權限（角色_知識審核、角色_蒸餾審核，無選單頁）維持在群組末端。
  3. KnowledgeExtraction.Share/Helpers/MagicObjectHelper.cs — 常數宣告順序同步調整。const 宣告順序無語意，純為可讀性；所有字串值一律未動。

既有角色權限不受影響

角色權限存於 RoleView.TabViewJson，內容是權限名稱字串陣列，不是 id 也不是索引；讀取以 HashSet<string>.Contains 名稱比對，頁面授權 CheckAccessPage(MagicObjectHelper.角色_XXX) 同樣走字串常數。「位置索引」只存在於執行期記憶體，用途是把選單項配對到權限名稱。

預期副作用：/roleviews 角色編輯頁的勾選框順序會跟著改變（RoleViewView 直接由 RolePermissionService.InitializePermissionSetting() 建樹）。這是兩邊一致的正確結果。

守護力已實證（反證驗證）

在「只改 Menu.json、未改 RolePermissionService」的中間狀態實測，MenuPermissionAlignmentTests 的另外三個測試全數通過（它們只驗數量，換序時數量不變），EverySubMenuItem_PairsWith_ItsOwnPermissionName 則精準失敗：

[3][1] 選單「AI 知識問答」配到權限「黃金評測」，應為「知識庫問答」；[3][2] 選單「清洗品質評測」配到權限「知識蒸餾」，應為「黃金評測」；[3][3] 選單「知識頁審核」配到權限「知識庫問答」，應為「知識蒸餾」

補上 RolePermissionService 後恢復全綠。

分隔線機制（新增）

設計取捨：欄位而非陣列元素

分隔線做成掛在項目上的 group 欄位（SidebarMenuItemModel.Group，JSON 寫 "group": N，預設 0＝未分組），相鄰兩項 group 不同時畫一條線。

⚠️ 刻意不在 subMenu 陣列插入一筆 divider 元素：那會整段位移權限索引，逼得 ApplyChildPermissionStructure 的計數與四條對齊測試全部要改，且是靜默錯位風險最高的做法。純欄位對位置索引零影響。

判定集中在純函式 SidebarMenuItemModel.ShouldRenderDividerAfter(siblings, index)，兩條渲染路徑共用。

為什麼用「分組」而不是「在這一項之後畫線」

ShouldRenderDividerAfter 對已經過權限過濾的可見清單求值，因此某一項因無權限被隱藏時，線仍落在正確的分組交界，而不是跟著那一項一起消失、讓兩組合併。由此也自然得到三個保證：結尾不會有孤兒線、開頭不會有線、兩條線不會相鄰。

兩條獨立的渲染路徑都要改

側邊選單有兩套完全獨立的渲染實作：

狀態實作分隔線
展開AntDesign <Menu Mode="MenuMode.Inline"> → 遞迴 SidebarMenuNode.razor<MenuDivider />，寫在父層迴圈（＝SubMenu 的 ChildContent 直接子節點），判定需要兄弟清單
收合NavMenu.razor 手寫 HTML flyout（不走 AntDesign Menu）<div class="collapsed-flyout-divider">（父容器是 <div>，<li> 在此不合法）

AntDesign 1.6.0 的 MenuDivider 沒有 Key 參數、不進 Menu 的 key 簿記，因此不影響 SelectedKeys/OpenKeys。

樣式歸屬：<MenuDivider /> 是元件標籤，Blazor 不對元件打 scope 屬性，其 <li> 不帶 scope id，因此樣式必須寫在 NavMenu.razor.css 的 .sidebar-menu-shell ::deep .ant-menu-item-divider，無法從 SidebarMenuNode.razor.css 選到。

CloneWith 必須複製 Group：ApplyPermissionStructure 與 FilterMenuItems 各會 clone 一次，漏掉就是「分隔線完全不出現且不報任何錯」——最難查的靜默失效，已由測試釘住。

範圍限制

group 只在第二層子選單有效。頂層與第三層（僅用於 adminOnly 群組）的渲染路徑刻意沒有分隔線邏輯，由 MenuDividerTests.Group_OnlyAppearsAtSecondLevel 擋下誤加。

測試

新增 9 條（1048 → 1057）：

SidebarMenuServiceTests（+6）：分組邊界畫線／同組不畫／最後一項不畫孤兒線／過濾後邊界仍在（選擇分組做法的理由）／CloneWith_PreservesGroup＋FilterMenuItems_PreservesGroup（兩次 clone 都不能掉旗標）。

MenuDividerTests（+3，新檔）：知識庫 subMenu 的 url 序列（用路由而非顯示名，顯示名是可調文案）／group 值為 1,1,2,2,2,3,3／group 不得出現在頂層與第三層。

既有 MenuPermissionAlignmentTests（4）、PermissionConstantCanaryTests、MenuIconTests 皆未修改且全綠——DisplayNameToPermissionName 白名單不需異動（顯示名沒變），icon 也全部沿用原項。

  • 無 migration、無資料異動、無 API 變更。
  • appsettings.json SystemVersion 1.0.105 → 1.0.106。
  • 選單有快取（SidebarMenuService 的 sidebar:menu:raw，預設 30 分），部署後需重啟站台才會看到新順序與分隔線。

已驗證：dotnet build 建置成功、dotnet test 1057 全綠、反證驗證如上、起站無例外且版本正確。

⚠️ 尚未實機目視確認：選單需登入才渲染，本次沒有可用的瀏覽器工作階段，因此兩條分隔線的實際外觀未經目視驗證。若展開態看不到線（AntDesign 內部樣式壓成 0 高度），備案是把 <MenuDivider /> 換成原生 <li class="sidebar-menu-divider" role="separator"></li>，樣式改寫進 SidebarMenuNode.razor.css（原生元素會帶 scope 屬性，不需 ::deep），對 AntDesign 內部零相依。另建議以「只勾知識庫問答」的測試角色登入，確認側邊欄只出現「AI 知識問答」——這是唯一能實機抓出權限錯位的驗收步驟。
