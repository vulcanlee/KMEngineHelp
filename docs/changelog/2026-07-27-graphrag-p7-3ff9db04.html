Graph RAG P7：接線與效能修補（1.0.88 → 1.0.89）

  • 日期：2026-07-27
  • 版本：1.0.88 → 1.0.89
  • 類型：修正／效能（Graph RAG 第七階段；無新功能、無新表，只修補 P1～P6 留下的半成品、熱路徑全表掃描與硬編碼上限）

背景

P1～P6 在單日連交六版後，盤點出三個與「多跳／視覺化」無關、但直接影響可用性與成本的缺口：

  1. GraphTripleService.TriggerExtractionAsync 是半成品：自 P2 起就實作完成，但全 repo 沒有任何呼叫端（只有 CancelExtractionAsync 被 PipelineJobCancelService 用到）。實務上三元組抽取只能靠蒸餾完成時自動觸發——抽取失敗、LLM 當時未設定、或想在核可更多 Wiki 頁後重抽，使用者都無計可施。而且知識來源清單完全不顯示 GraphStatus（KnowledgeSourceService 全檔沒有 Graph 字樣），連「抽到哪了」都看不到。
  2. ⚠️ 順帶查出的資安缺口：TriggerExtractionAsync 完全沒有權控——沒有團隊權控、沒有前置狀態檢查。因為沒有呼叫端所以從未被觸發，但它一旦接上 UI 就是個洞（任何登入者可對他隊來源觸發 LLM 抽取）。
  3. 檢索熱路徑上四個全表掃描沒有索引：GraphCommunity 與 GraphEntityAlias 兩張表連一個索引都沒有（只有 PK），而它們都在熱路徑上——RetrievalService.SearchGraphAsync 每次檢索都撈全部已核可別名與全部錨頁節點，GraphCommunityService 每次全域問答都撈全表社群再於記憶體過濾 ACL。
  4. 三個決定 LLM 成本的上限寫死在程式碼裡：GlobalCommunityCap=20、MaxCommunities=50、NameCap=300。這三個數字每一個都直接乘上 LLM 呼叫次數，卻要改程式重編才能調。

變更

1. 接上手動重抽三元組（含補權控）

  • GraphTripleService.TriggerExtractionAsync 補守門，順序為：存在 → 團隊權控（TagStringHelper.IsTeamAccessible，非管理員只能操作無團隊或有交集的來源，拒絕時記 LogWarning）→ DistillationStatus == 已蒸餾（抽取輸入是該來源「已完成且現行」的 WikiPage，未蒸餾就是白花 LLM）→ IsChatLlmConfigured()（否則會走到背景才失敗、狀態變「失敗」）→ 非 in-flight。為此注入 IOptions<OpenAISettings>。
  • KnowledgeSourceView 加「圖譜」欄（顯示 GraphStatus，處理中附百分比，比照既有「蒸餾」「索引」欄）。GraphStatus 等四個欄位早已在 KnowledgeSourceAdapterModel 上、由 AutoMapper 依名稱自動對應，故 Service 層零改動。
  • 加「抽取／重抽三元組」動作（圖示 hub，與選單「知識圖譜審核」同一個圖示）：僅在「已蒸餾且非 in-flight」時顯示，確認框明講「候選一律待審核、重抽以（主詞｜關係｜受詞）去重、既有已核可／已退回不會被刪除、會消耗 Token」。
  • 輪詢與完成通知納入圖譜管線：PollTickAsync 的 hasActive 與 NotifyPipelineTransitions 的快照 tuple 都加上 GraphStatus（新增 IsActiveGraph）。不做這步，按下按鈕後畫面不會更新、也不會有完成通知，等於還是個看不出有沒有在動的按鈕。
  • CrudActionIconTests.AllowedCrudActionIcons 加入 hub（該測試是 CRUD 按鈕圖示的白名單守門，新增圖示的既定擴充點）。

2. 四個檢索熱路徑索引（雙庫 AddGraphIndexes，無欄位新增）

索引對應查詢
GraphTriple.StatusRetrievalService.SearchGraphAsync 與 GraphCommunityBuilder.RebuildAsync 都以「全庫已核可三元組」為條件（不帶 KnowledgeSourceId），用不到既有的 (KnowledgeSourceId, Status) 複合索引
GraphNode.WikiPageId每次檢索都撈全部錨頁節點（WikiPageId != 0）建 pagesByCanon
GraphEntityAlias.Status每次檢索都撈全部已核可別名建 union-find 對照；審核頁亦以狀態分頁
GraphCommunity.MemberCount全域問答每輪以 MemberCount 遞減排序取前 N

⚠️ SQL Server 那份另含一筆 AlterColumn：GraphEntityAlias.Status 由 nvarchar(max) 改為 nvarchar(450)（SQL Server 索引鍵長度上限所需）。scaffold 因此警告「An operation was scaffolded that may result in the loss of data」——該欄只存「待審核／已完成／已退回」三個短常數，實務無截斷風險。SQLite 那份沒有這筆（無此限制）。

3. 三個硬編碼上限改為 appsettings 可設定

SystemSettings.Retrieval 新增（緊接 GraphWeight）：GraphGlobalCommunityCap(20)、GraphMaxCommunities(50)、GraphAliasNameCap(300)，預設值與原常數完全相同。三個消費端（KnowledgeBaseChatService／GraphCommunityBuilder／GraphEntityAliasGenerator）改注入 IOptions<SystemSettings>，原 public const 移除。

  • 刻意只做 appsettings 層：不加 RetrievalParamOverride 欄位、不走 /rag-diagnostics 熱套用鏈——這三個是低頻的成本閘門，不值得為它們再開一輪雙庫 migration。代價是改了要重啟，已寫入文件。
  • 三者皆以 Math.Max(1, 設定值) 夾住：填 0 或負數會退回 1，而不是讓全域問答靜默回「查無依據」。
  • GraphCommunityBuilder 順帶補上「群數超過上限」的 LogInformation（原本靜默 Take(N)），與 GraphEntityAliasGenerator 的既有寫法一致。

安全與相容

  • leak=0 強化：TriggerExtractionAsync 從零權控變成有團隊權控，並由測試釘住「非管理員對他隊來源觸發 → 失敗且 GraphStatus 不變」。
  • ⚠️ CancelExtractionAsync 刻意不補權控：它由 adminOnly 的 /pipeline-jobs 呼叫，與 CancelEmbeddingIndexAsync／CancelCleaningAsync 等同輩一致採頁面層把關。單獨改它會與同輩不一致，屬另一個議題。
  • 向後相容：三個上限預設值不變、索引不改變任何查詢語意、抽取管線與審核流程完全未動。既有 836 條測試全數維持綠燈。

已知限制（未來增量）

  • 「抽取／重抽三元組」放在知識來源頁而非知識圖譜審核頁——後者是三元組導向的，看不到「零三元組（抽取失敗）」的來源，而那正是最需要重抽的情況。
  • 三個上限不可線上熱調（需重啟）；若日後確有線上調參需求，再比照 GraphWeight 走四點同步鏈升級。
  • 社群重建／別名生成仍不進 PipelineNames，故仍無法從 /pipeline-jobs 取消，服務重啟仍會靜默丟失重建訊號（P3 的刻意取捨，本次未動）。
  • 本次只補索引，沒有改掉「每次檢索都全表載入別名與錨頁節點」的作法（例如改為快取）。大圖時仍需進一步優化，屬 P4 changelog 已記載的遺留項。
