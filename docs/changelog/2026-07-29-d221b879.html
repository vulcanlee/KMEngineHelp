知識圖譜（Graph RAG）使用文件補齊（1.0.100）

  • 日期：2026-07-29
  • 版本：1.0.99 → 1.0.100
  • 類型：文件補齊（新增權威使用指南與 PRD、兩份主指南插入新章並重編號、技術文件補洞）

背景

Graph RAG 於 2026-07-27～28 分十三階段交付完畢（P1～P13，1.0.83 → 1.0.96），程式、雙庫 migration、測試都齊，但使用者側文件是全白卷：docs/guides/ 底下 22 份操作手冊，對「知識圖譜／三元組／社群摘要」的關鍵字命中數全部為 0。也就是說功能做完了，卻沒有任何一份文件告訴使用者這個頁面存在、要怎麼用、前置條件是什麼。

這筆債專案自己記錄過兩次——2026-07-27-GraphRAG文件債補正.md 的「已知限制」與 planning/2026-07-28-GraphRAG待辦盤點.md §6「驗證債」都白紙黑字寫著「guides 22 份仍對版 1.0.71，未涵蓋知識圖譜審核頁與全域問答的操作說明」，並註明「那是一次獨立的全量對版工作」。但之後又交付了 P7～P13 共六個版本，這筆債從未還。

缺漏不只使用者側。盤點後另外確認四類技術文件破洞：

  1. 資料模型零覆蓋：六張新表（GraphNode／GraphTriple／GraphEdge／GraphCommunity／GraphEntityAlias／GraphJobState）完全沒進 architecture/資料模型與資料庫.md，只散落在速查與各篇 changelog 裡；九組雙庫 migration 也不在該檔的 migration 表內。
  2. 設定與容量零覆蓋：operations/日誌與設定檔說明.md 的 SystemSettings.Retrieval 表缺全部七個 Graph* 參數，連 appsettings 快照都是舊的；operations/容量邊界與限制.md 沒有任何圖譜上限。
  3. 權限零覆蓋：security/認證授權與權限機制.md 的知識庫權限群組沒有 角色_知識圖譜審核——而該項是 1.0.84 起就存在的選單頁權限，且它的位置索引夾在 角色_知識瀏覽 與 角色_知識審核 之間，文件缺這一列等於那張表的位置索引不再對得上程式。
  4. PRD 覆蓋矩陣有實質破洞：prd/README.md §一 明訂「每個頁面都必須在此找得到歸屬 PRD」，但 /knowledge-graph-review 完全不存在於矩陣中，1.0.96 新增的兩支 REST 端點也無歸屬。程式側三處（MagicObjectHelper／RolePermissionService／Menu.json）都已同步，只差 PRD。

這類落差的風險是「功能存在但沒人知道怎麼用」：實測最常見的使用者卡點是「抽取跑完顯示已抽取、卻一條三元組都沒有」，根因是上游 Wiki 頁未核可——這條因果關係在本次之前任何一份使用者文件都查不到。

⚠️ 重編號的風險與處置

這是本次最容易出錯的部分，兩份主指南的性質差異很大：

Hands-on Lab新手完整操作指南
in-doc 錨點連結0 個（全檔沒有 ](#…)）~60 個引用點、31 條不同錨點
需改的交叉引用40 處純文字（第 N 章／小節前綴）章標題 9＋節標題 70＋錨點 31 條＋§N.N 42 處＋中文區間 3 處
風險低（純文字替換）高

處置紀律：

  1. 一律用「單次通過的映射替換」，不用降序鏈式替換。 鏈式替換（先 12.→13.、再 13.→14.）會把剛改好的又推一格，而且看起來完全正常——數字合法、無編譯、無測試會攔。本次改用 regex callback 一次算出 N+1，從根本上消除這個風險。
  2. 章級錨點用完整 slug 精確替換（如 #十五資料維護與生命週期更新刪除級聯與孤兒 → #十六…），不用中文數字的模糊替換。因為完整 slug 含章名，來源集合與目標集合天然不相交，單次通過即安全。
  3. 節級錨點的來源前綴 {13x, 18x, 20x} 與目標前綴 {14x, 19x, 21x} 不相交，故 22 條 String.Replace 單次通過安全。
  4. 每一步後跑錨點孤兒自檢：把全部 ](#…) 目標與「標題 slug 化」的集合比對，要求輸出空集合。⚠️ Test-DocsEncoding.ps1 只檢查 BOM 與 U+FFFD，壞掉的錨點沒有任何自動化守門——在 GitHub 上只表現為「點了沒反應」，code review 也看不出來。
  5. 兩份指南分開處理、先做低風險的 Lab 練手，並在中文數字區間寫法（第七到十四章）與阿拉伯數字區間（第 1–14、17–20 章）上人工逐行重讀——那些格式正則抓不到。
