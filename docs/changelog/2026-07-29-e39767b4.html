頁面說明系統：頂欄 Help 圖示 ＋ 近滿版說明對話窗（1.0.101）

  • 日期：2026-07-29
  • 版本：1.0.100 → 1.0.101
  • 類型：新功能（in-app 說明系統：1 個掛載點、41 條路由自動生效、40 份說明內容）

背景

系統有 49 條 @page 路由、功能密度很高（知識庫加工線六站、四個評測與診斷頁、圖譜審核四分頁、五張報表），但畫面上完全沒有任何自我說明機制。唯一的說明來源是 docs/guides/ 底下 24 份文件——寫得很完整（新手完整操作指南.md 330KB、知識圖譜使用指南.md 30KB），但使用者在操作當下看不到，得離開系統去翻檔案。

對「完全不懂知識庫、沒有 IT 背景」的使用者，這個落差最痛的表現是：他看著一頁四個分頁、十幾顆按鈕，不知道哪顆能按、按了會發生什麼、為什麼抽取跑完卻一條資料都沒有。

變更

掛載點：只改一處，41 條路由自動生效

Components/Layout/MainLayout.razor:10 的 <div class="top-row-title">@CurrentPageTitle</div> 拆成 <span class="top-row-title-text"> ＋ <PageHelpDialog />。

刻意不逐頁改 Page/View。原本的內容區標題三分歧（View 內 <h2> 約 15 頁、Page 內 <h1> 約 6 頁、20+ 個 CRUD 清單頁根本沒有標題），逐頁加要改 46 個檔案，而且沒標題的那些還得先補標題。掛在頂欄則是一處改動、全站生效，且位置固定——使用者在任何頁都知道去哪裡找說明。

MainLayout.razor.cs 零改動：該檔已 260 行、七個 [Inject]、兩塊狀態機，不再長第三塊。新元件自己取路徑、自己載索引、自己訂閱導覽事件。

為什麼用獨立索引檔，而不是「路由字串猜檔名」或擴充 Menu.json

方案為什麼不用
猜檔名無法表達「/App 與 /knowledge-base-chat 共用一份」；無法區分「刻意沒說明」與「漏寫」（兩者都只是「找不到檔」）；路由改名時沒有任何守門會紅
擴充 Menu.json那是全 repo 風險最高的檔（位置索引 ↔ RolePermissionService ↔ MagicObjectHelper 三處同步、三個測試盯著），為了說明去動它是把低風險功能綁到高風險檔上；而且它只覆蓋選單頁，/knowledge-sources/{id}/chat、/Profile、/ChangePassword 都不在裡面，仍需第二套機制 → 兩個真相來源

獨立 JSON 完全覆蓋 49 條、可表達共用與排除、.json 走預設 Content glob 自動複製、雙向測試可掃，且新增一頁說明不必重新編譯。

內容格式

六個 H2 逐字相符、按序、各一次，可選第七段：

## 一、功能摘要
## 二、這個頁面在做什麼
## 三、畫面上有哪些按鈕、各自做什麼
## 四、建議這樣操作，會得到什麼
## 五、名詞解釋
## 六、相關頁面
## 七、常見問題          ← 唯一白名單的選填章節

「六、相關頁面」的唯一合法行格式：- [顯示標題](/route)：說明。解析成 Blazor 按鈕渲染（不用 Markdown 連結，理由見下）。

刻意不用 YAML front matter：共用的 MarkdownRenderer 的 pipeline 沒有 UseYamlFrontMatter()，寫了 --- 會被當成 thematic break、第一段會靜默變形。想放的中繼資料（標題、路由）在索引檔裡有更好的家，所以不需要 front matter。（1.0.102 補記：後來確實動了那條共用 pipeline，但只加了 UsePipeTables()，並未加 UseYamlFrontMatter()——這一條決定仍然有效。）

⚠️ 四個已驗證的靜默失敗（全部已處置）

  1. 手機版說明鈕會整個消失。 MainLayout.razor.css:226-228 在 max-width:640.98px 把 .top-row-title 整個 display:none。塞進那個 div 的話窄視窗就完全沒有說明入口。→ 拆 .top-row-title-text，只隱藏文字。
  2. .md 不在 Web SDK 預設 Content glob 內。 Datas/Menu.json 能被複製是靠 **/*.json；.md 漏寫 glob 不會編譯失敗、不會報錯，只在發行環境表現為「所有說明都是待撰寫中」。dotnet run 抓不到。→ csproj 明寫 ＋ 測試斷言 ＋ 本次實測 dotnet publish，發行目錄確認有 40 個 .md。
  3. 路由比對絕不可沿用前綴比對。 MainLayout.razor.cs:137 的 IsMatchingUrl 是前綴比對（所以 /knowledge-sources/5/chat 的頂欄標題顯示「知識來源加工」）。說明若沿用，對話頁會靜默顯示清單頁的說明。→ MatchTopic 用「段數相同＋逐段比對、{...} 段萬用」，並先試「無參數且完全相等」以免清單頁被樣板搶走。已由測試明確釘住這條回歸。
  4. 導覽後對話窗會停在舊頁說明。 MainLayout 與 PageHelpDialog 跨導覽存活（這正是索引能快取在欄位裡的原因）。內部 Markdown 連結會被 Blazor 攔截走 SPA 導覽（WikiLinkPreprocessor → 知識百科已實證），但窗不會重建。→ 相關頁面用結構化按鈕（先 visible=false 再 NavigateTo）為主，外加訂閱 LocationChanged 自動關窗作為安全網（涵蓋作者在其他段落內嵌的連結）。

額外：讀檔一律用 File.ReadAllText（自動去 BOM）。若改用 OpenRead 手動解碼，開頭會留一個 U+FEFF，讓第一行的 # 不再是行首字元，前言解析會靜默錯位。parser 測試含 BOM 案例。

UI

  • 觸發鈕用 MaterialIcon + help_outline（與頂欄既有的 account_circle／expand_more 同一套）。刻意不用 CrudActionButton——那是 28px 帶框的表格動作鈕，頂欄的既有做法是裸 <button>（見 user-menu-trigger）。
  • 近滿版 CSS 寫在 .razor 的 <style>（不可寫 .razor.css——AntDesign Modal 以 portal 掛載，scoped CSS 會靜默失效；先例 ContentEditDialog.razor:7-38）；觸發鈕樣式才放 .razor.css。
  • 尺寸用 calc(100vw - 24px) / calc(100vh - 24px)、top:12px（比既有 .role-view-modal 系列的 90vw/90vh 更滿）。刻意不用 100vw：部分瀏覽器的 100vw 含垂直捲軸寬度會憑空多出水平捲軸。
  • .ant-modal-body 自己 overflow:hidden; padding:0，捲軸交給右側內容欄，左側章節導覽才能固定不動。overflow 兩軸明寫（hidden auto），只寫 overflow-y 會讓 overflow-x 隱含變 auto 產生假捲軸。
  • 章節導覽採「全部 ＋ 分段切換」，不做 JS 捲動：選「全部」時整份渲染（可 Ctrl+F、可線性通讀），點某一段則只渲染那一段（等於瞬間跳段）。換來零 JS 相依；代價是切段時右欄回到頂端而非「捲到該處」——但因為只剩一段，語意上就是頂端。導覽標籤直接取自 PageHelpMarkdownParser.RequiredHeadings（單一定義來源，改標題不會漏改導覽）。
  • 窄視窗（≤640.98px）：真正滿版（100vw/100vh、border-radius:0），章節導覽轉為橫向捲動的 chip 列。

快取

沿用 ICacheService.GetOrCreateAsync（CacheSettings.DefaultExpirationMinutes 預設 30），刻意不自建行程內快取：索引是每個 circuit 讀一次（存進元件欄位）、內容是使用者按鈕才讀（人為頻率），兩者都不在熱路徑上。（Graph RAG 的 IGraphRetrievalCache 繞開這一層，是因為它在每次檢索的熱路徑上快取已解析的字典。）附帶好處：改 .md 檔最多 30 分鐘生效、不必重啟。

每次導覽零 IO：OnInitializedAsync 一個 circuit 只跑一次載入索引，LocationChanged 只做純記憶體的 MatchTopic。

內容涵蓋

49 條 @page 全部有交代：41 條登記（40 份實體檔）＋ 8 條明示排除。

排除的 8 條（理由寫在 PageHelpCatalogTests.RoutesWithoutHelp 字典裡，逼出一次自覺的決定）：/（EmptyLayout Splash，無頂欄）、/Auths/Login、/Auths/Pending（NoFooterLayout，無頂欄）、/Auths/Logout（轉導頁）、/Error、/not-found（內容本身就是說明）、/counter、/weather（.NET 樣板殘留死頁，建議另案刪除）。

內容全部從 docs/guides/ 蒸餾而非重寫。撰寫紀律：docs/guides/ 是權威、完整、含參數與公式；Datas/Help/ 是入門、短、不含任何可調參數與數學——參數放 in-app 說明必然過時，而過時的參數說明會害人調錯。每份結尾固定一行指向權威文件檔名。

/system-health 與 /rag-diagnostics 兩份改用管理員語氣，且 /rag-diagnostics 明確寫出「不確定就不要改」「改之前先存基線」——那是全站唯一「調錯會把問答弄壞」的頁。

測試（62 條）

PageHelpCatalogTests（內容完整性守門，檔案定位沿用 MenuPermissionAlignmentTests.LocateMenuJson 的做法）：

群組攔到什麼
索引 ↔ 實際路由雙向新增頁面忘了寫說明會紅；索引寫了不存在的路由（打錯字／路由改名／頁面刪除）也會紅
索引自身無重複路由；route 以 / 開頭、title 不可空白
索引 ↔ 檔案雙向宣告了檔案卻不存在（最典型的靜默失敗）；磁碟上的孤兒檔；檔名必須符合 slug 規則
六大段逐字、有序、各一次；除白名單外的 H2 即紅（專攔「## 名詞說明」這種打錯字後靜默少一段）；每段 ≥40 字且無 TODO 標記
相關頁面每一個清單項都必須可解析（不可解析的行永遠不會變成按鈕，等於作者意圖靜默失效）；目標路由必須是真實 @page、不可指向自己
編碼UTF-8 含 BOM、無替代字元。必須放在 dotnet test 裡——scripts/Test-DocsEncoding.ps1 只掃 docs/，這批檔在 src/ 下掃不到
完整覆蓋契約所有已登記路由的 file 都不可為 null（零佔位的機器化保證）
csproj glob斷言含 Datas\Help 與兩個 CopyTo 屬性

PageHelpParsingTests（純函式）：slug 規則 10 例（含 {id} 與 {Id:int} 都要得到同一檔名）、MatchTopic 16 例（/knowledge-sources/5/chat 必須命中對話樣板、不可命中清單頁 ← 前綴比對的回歸釘；query／fragment／尾斜線／大小寫／段數不同／參數段不可為空）、Parse 8 例（含 BOM、### 不被誤判、縮排偽標題）、ParseRelatedPages 8 例（全半角冒號、不合格式的行不入清單）。

💡 測試在撰寫過程中抓到一個真實的撰寫錯誤：兩份檔案把三個路由寫成同一行（[A](/a)、[B](/b)、[C](/c)：說明），那樣三個都不會變成可點擊按鈕。已拆成三行。這正是「每一個清單項都必須可解析」那條守門的價值。

刻意不做（YAGNI）

  1. 不做全站說明搜尋——40 份檔的全文搜尋是獨立功能（要索引、排名、結果頁）。使用者已有 Ctrl+F（「全部」模式會渲染整份），而真正的搜尋需求已由「AI 知識問答」滿足。
  2. 不做說明內容的線上編輯。誘人（ContentEditDialog 現成），但要回答：誰能編？進 DB 嗎？要版本嗎？要審核嗎？和 git 什麼關係？一開始回答就是一個新子系統。現階段「改檔案、最多 30 分鐘生效」已滿足「非工程師可編輯、不必重新編譯」。
  3. 不做「清除說明快取」的管理員按鈕——30 分鐘 ＋ 重啟已足夠。
  4. ~~不改 MarkdownRenderer（7 個既有呼叫端共用，DisableHtml() 是 XSS 防線）。~~ ⚠️ 這一條在 1.0.102 已作廢：實際驗收發現該 pipeline 連表格都沒啟用，導致 40 份說明檔的 260 個表格全部渲染成字面的 | 欄 | 欄 |。見 2026-07-29-Markdown表格渲染修正。說明檔仍維持「純 Markdown、無原始 HTML」（DisableHtml() 未變）。
  5. 不做首次進站自動彈出說明／新功能導覽——那需要「看過了」的持久化狀態，是不同的東西。
  6. 不把 docs/ 掛成靜態檔或做 in-app 文件瀏覽頁——寫出檔名已足夠；掛靜態檔要處理 docs/security/、docs/architecture/ 的內部細節外洩。
  7. 不顯示「最後更新時間」——git 就是紀錄；檔案 mtime 會被 PreserveNewest 改掉，是錯的資料來源。
  8. 相關頁面不做權限過濾（第一階段）。要過濾就得建立「路由 → 權限常數」對照，那正是權限三處同步的雷區，而且 8 條非選單頁無權限名可對。目標頁本來就會顯示「你沒有權限存取此頁面」。第六段段首固定一句「以下頁面是否看得到，取決於你的權限設定」。
  9. 不做「說明內容 vs UI 實際按鈕」的同步測試——正則比對誤報率會高到讓人加排除清單，而一有排除清單守門就開始腐爛（ToastConventionTests 的教訓）。改以慣例文件的流程紀律處理。
  10. 不引入 bUnit（測試專案未使用，為此加一個框架不成比例；純函式已覆蓋所有邏輯分支，Razor 層只剩 markup）。
  11. 不刪 /counter、/weather（雖然該刪）。本次只列進排除清單留紀錄。

已知限制

  • 相關頁面不做權限過濾（見「刻意不做」第 8 項）。
  • 改 .md 檔最多 30 分鐘才生效（快取逾時），要立即生效需重啟。
  • 對話窗切換章節時右欄回到頂端而非捲到該段（見 UI 段的取捨）。
  • 錨點失效無自動化守門——但說明檔內不使用 in-doc 錨點，所以不受影響。
