變更紀錄

PDF 文件萃取可改用大語言模型（1.0.54）

  • 日期：2026-07-25
  • 版本：1.0.53 → 1.0.54
  • 類型：功能新增（文件萃取管線；預設關閉、行為不變）

問題

「文件萃取」頁（/document-extraction）上傳的所有檔案，一律由 DocumentExtractionProcessor 呼叫本機 markitdown.exe 轉成 Markdown，PDF 沒有任何專屬路徑。

MarkItDown 對 PDF 只做純文字抽取：圖片、圖表、流程圖完全遺失，複雜表格常被壓成無結構的文字。需要能在設定檔指定「遇到 PDF 時改呼叫大語言模型 API」，由 LLM 盡可能把 PDF 的全部內容（含無法直接抽取的圖片與表格）表達成 Markdown，並可指定使用哪一個模型。

變更

1. 設定（MarkItDownSettings 新增三個鍵）

"MarkItDownSettings": {
  "MarkItDownPath": "C:\\KMEngineTools\\python\\Scripts\\markitdown.exe",
  "TimeoutSeconds": 600,
  "PdfUseLlm": false,
  "PdfLlmModel": "",
  "PdfLlmTimeoutSeconds": 600
}
  • PdfUseLlm：PDF 是否改走大語言模型。預設 false，升級後行為完全不變，需手動開啟。
  • PdfLlmModel：指定模型；留空＝沿用 OpenAISettings.ResolveChatLlm() 的聊天模型（比照 QueryRewriteModel 的 fallback 慣例）。
  • PdfLlmTimeoutSeconds：0＝沿用聊天模型逾時。

2. 新增 PdfMarkdownLlmClient

KnowledgeExtraction.Business/Services/DocumentExtractions/PdfMarkdownLlmClient.cs。以 base64 data:application/pdf;base64,... 夾帶 type:"file" 內容送 chat/completions。

重用既有實作，未重寫 API 呼叫層：請求組法與回應解析直接沿用 OpenAIChatCompletionClient.BuildFileRequestBody 與 ParseContent（兩者本就是 public static，原供「依提示詞產生（原始檔案模式）」使用）。

依專案既有 typed client 慣例（OpenAITranscriptionClient / OpenAIChatCompletionClient / OpenAIEmbeddingClient 各有自己的 BaseUrl 與逾時），於 Program.cs 註冊專屬 AddHttpClient<PdfMarkdownLlmClient>，讓 PDF 的長逾時不牽動對話、清洗等其他 LLM 功能。

3. 提示詞（四層解析）

新增槽位鍵 LlmPromptKeys.DocumentPdfToMarkdown =「文件-PDF轉Markdown」，走既有 LlmPromptResolver：單次操作 > DB Prompt 表 > appsettings LlmPrompts > LlmPromptDefaults。可於「提示詞清單」/prompts 線上調整、免重啟。

勘誤（1.0.77 補註）：上面那句「單次操作 > DB > appsettings > fallback」講的是 LlmPromptResolver 的通則， 但這條路徑實際只有 3 層——DocumentExtractionProcessor 呼叫 ResolveAsync 時第 2 引數（perOperationOverride） 硬傳 null，而 PDF 自動萃取是背景管線、沒有使用者互動點，所以「單次操作覆蓋」這一層從未生效、也沒有入口。 實際生效的是：DB /prompts > appsettings LlmPrompts > LlmPromptDefaults。

內建預設提示詞要求：不省略不摘要、標題階層對應、表格轉 Markdown 表格語法、圖片與圖表在原位置以 > **[圖片]** 詳述內容與數值、圖表可還原時另附數據表、數學式用 LaTeX、直接輸出 Markdown 不加圍欄。

4. 流程分流與自動降級

DocumentExtractionProcessor.ProcessCoreAsync 在來源檔為 .pdf 且 PdfUseLlm 開啟時先試 LLM，成功即把 Markdown 寫到與 MarkItDown 相同的輸出路徑，後續流程完全共用。

  • LLM 只嘗試一次，任何失敗（金鑰未設定、API 錯誤、逾時、模型不支援 file 輸入）立即自動改用 MarkItDown 完成轉換。
  • 降級後狀態仍為「已完成」，訊息欄顯示「AI 解析 PDF 失敗，已自動改用 MarkItDown 轉換：…」（沿用現有 ErrorMessage 欄位，不新增欄位、不需 migration）。
  • 例外過濾加上 when (!cancellationToken.IsCancellationRequested)，確保使用者按取消時不會被誤判為降級。
  • 外層 ProcessAsync 的 3 次重試機制不動。

5. Token 用量

用量記為 Operation=DocumentExtraction（由 DocumentExtractionBackgroundService 既有的 OperationContext.Push 自動帶入）、CallType=File，Model 為實際使用的模型。另在 LlmTokenUsage 補上 OperationDocumentExtraction 常數與其他作業齊平。

影響範圍

  • 新檔 1 個；異動 MarkItDownSettings、LlmPromptsSettings、LlmPromptKeys、LlmPromptDefaults、DocumentExtractionProcessor、Program.cs、LlmTokenUsage、appsettings.json。
  • 無資料庫 migration（未新增欄位）。
  • 預設關閉，不開啟則行為與 1.0.53 完全相同。
  • zip 批次上傳中的 PDF 因走同一個 Processor，同樣適用。
  • appsettings.json SystemVersion 1.0.53 → 1.0.54。
