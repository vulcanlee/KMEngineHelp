變更紀錄

「專案分類」選單項移至「團隊清單」下方（1.0.55）

  • 日期：2026-07-25
  • 版本：1.0.54 → 1.0.55
  • 類型：使用體驗調整（選單順序）＋ 測試補強

變更

「資料定義」群組的子選單順序由

分類清單 → 團隊清單 → 提示詞清單 → 清洗設定檔 → 專案分類

改為

分類清單 → 團隊清單 → 專案分類 → 提示詞清單 → 清洗設定檔

Menu.json 的 id 一併重編為連號，維持專案「群組×10+序」慣例：61 分類清單、62 團隊清單、63 專案分類、64 提示詞清單、65 清洗設定檔。

三處同步

Menu.json 與 RolePermissionService 權限樹以位置索引對應（SidebarMenuService.ApplyChildPermissionStructure 是 permissionNames[index]，名稱不參與比對），因此換序必須成對修改：

  1. KnowledgeExtraction.Web/Datas/Menu.json — 資料定義 subMenu 換序、id 重編。
  2. KnowledgeExtraction.Business/Services/Other/RolePermissionService.cs — 角色_專案分類 由群組末端移到 角色_團隊清單 之後。
  3. KnowledgeExtraction.Share/Helpers/MagicObjectHelper.cs — 常數宣告順序同步調整。const 宣告順序無語意，純為可讀性；所有字串值一律未動。

既有角色權限不受影響

角色權限存於 RoleView.TabViewJson，內容是權限名稱字串陣列（例如 ["資料定義功能","分類清單","專案分類"]），不是 id 也不是索引。讀取時 RolePermissionService.SetPermissionInput 以 HashSet<string>.Contains 做名稱比對，與順序無關；頁面授權 CheckAccessPage(MagicObjectHelper.角色_XXX) 同樣走字串常數。

因此本次換序不影響任何既有角色已儲存的授權，也不需要資料庫 migration。「位置索引」只存在於執行期記憶體，用途是把選單項配對到權限名稱。

測試補強：堵住「靜默失效」盲點

原有的 MenuPermissionAlignmentTests 三個測試只檢查數量（頂層組數相等、子權限數量足夠、槽位存在）。同群組內換位時數量不變，只改 Menu.json 而漏改 RolePermissionService 仍會全綠，但權限已經錯位——正是 CLAUDE.md 警告的靜默失效。

新增 EverySubMenuItem_PairsWith_ItsOwnPermissionName：逐一比對每個非 adminOnly 選單子項與它實際配到的權限名是否語意相符。

實作時發現一個既有的刻意分歧：MagicObjectHelper.角色_會議項目 = "會議項目"，但 Menu.json 顯示名為「會議記錄」。以白名單明確記錄此例外，而非放寬比對規則把它吸收掉：

private static readonly Dictionary<string, string> DisplayNameToPermissionName = new(StringComparer.Ordinal)
{
    ["會議記錄"] = MagicObjectHelper.角色_會議項目,
};

守護力已實證：在「只改 Menu.json、未改 RolePermissionService」的中間狀態實測，既有三個測試全數通過，新測試則精準失敗並指出

[5][2] 選單「專案分類」配到權限「提示詞清單」，應為「專案分類」；[5][3] 選單「提示詞清單」配到權限「清洗設定檔」…

影響範圍

  • 無資料庫 migration、無資料異動、無 API 變更。
  • appsettings.json SystemVersion 1.0.54 → 1.0.55。
  • 選單有快取（SidebarMenuService 的 sidebar:menu:raw），部署後需重啟站台才會看到新順序。

驗證

  1. dotnet test 通過：639 個測試全數通過（原 638 + 新增 1）。
  2. 守護力反證：中間狀態下新測試如期失敗，補上 RolePermissionService 後恢復全綠。
  3. 實機（需重啟站台）：管理員登入確認子選單順序與五個頁面皆可進入；另以「只勾提示詞清單」的測試角色登入，確認側邊欄不會出現專案分類（此為唯一能抓出權限錯位的驗收步驟）。
