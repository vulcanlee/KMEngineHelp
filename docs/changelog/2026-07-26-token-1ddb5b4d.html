變更紀錄

Token 用量歸屬補線（9 條）、「（系統自動）」改名、新增明細頁籤

變更目的

使用者在 /token-usage 提出兩件事：①下方明細清單有大量「（系統/背景）」的使用者，希望能查出當時實際的發動者，不要因為「在系統或背景執行」就無法得知是誰；②想把最下方的明細表搬進頁籤區，成為第 5 個頁籤。

根因：那些「（系統/背景）」大多不是背景作業，是身分在傳遞時漏掉了

身分靠 OperationContext（AsyncLocal，Share/Helpers/OperationContext.cs）從上層流到底層 OpenAI client。TokenUsageRecorder 只讀 OperationContext.Current，上層沒 Push 時：

Operation = string.IsNullOrWhiteSpace(context?.Operation) ? callType : context.Operation;

→ 使用者變 null（顯示「（系統/背景）」），而且作業欄退化成英文 CallType。

所以畫面上作業欄顯示 Stream／Embedding／Text 這種英文原始字串的列，就是漏 Push 的指紋 —— 有正確 Push 的都會顯示中文（「影音轉逐字稿」「AI 知識問答」）。其中 Stream 不是 AI 知識問答（那條一直有正確帶到人）。

這是有紀錄的技術債：2026-07-12-Token用量記錄與查閱.md 自承「其餘互動作業（媒體/文件生成、RAG/黃金評測、RAG 診斷試檢索）仍會記錄，但作業欄暫退化為 API 型別、使用者可能為空（後續可再補 OperationContext.Push）」。最有力的佐證是 LlmTokenUsage 裡有 5 個常數從定義起就從未被寫入過任何一列（MediaGeneration／DocumentGeneration／GoldenSample／RagDiagnosticsTrial／RagEvaluation）—— 當初定義了常數，忘了接線。

補上的 9 條路徑（全部是使用者按出來的，身分就在手邊）

健康檢查歸給開頁的管理員是刻意的決定：/system-health 沒有任何排程會跑它（已確認 9 個 BackgroundService 無一碰 ISystemHealthService），100% 是管理員主動開出來的；歸屬後「誰一直在重整健康檢查頁燒 token」才查得到。SystemHealthService 與 CurrentUserService 同為 Scoped，建構式注入即可。

⚠️ Task.Run 射後不理的三條（1、2、3）為什麼 Push 要放在 lambda 裡面

  • 放 Task.Run 外面其實也會生效 —— Task.Run 會擷取當下的 ExecutionContext，AsyncLocal 值以複本凍結進去，外層 using Dispose 只還原 UI 端那一份。
  • 但不能那樣寫：using 的存活期（方法 return）與實際需要情境的期間（LLM 跑完）完全脫鉤，正確性只靠「EC 是 copy-on-write」這個隱性知識維繫。這是 Web/Mcp/McpIdentityResolver.cs:16 那條警告的同類反模式 —— 日後有人把 Task.Run 改成 await 就會靜默壞掉。
  • 因此一律：身分先在 UI 執行緒快照成 local（背景 CreateScope() 會拿到另一個空的 CurrentUserService），Push 放 lambda 內第一行、CreateScope() 之前（沿用既有的「Push 早於建 DI scope」慣例）。

路徑 2、3 共用同一個作業常數：sendOriginalFile 只決定 CallType（Stream／Image／File），業務作業都是「文件依提示詞產生」—— 這正是 Operation 與 CallType 兩欄分離的用意。

「（系統/背景）」→「（系統自動）」

補完 9 條之後，這個桶裡只剩 7 條管線 RecoverPendingAsync 系統重啟後自動復原未完成工作再入列的那批 —— 那才是真的無主。原本的名字是個混了「真系統作業」與「漏接線 bug」的垃圾桶，正因如此這個 bug 才藏得住；改名把語意收緊為「真的沒有人觸發」。

程式碼字面值 6 處：TokenUsageView.SystemOptionLabel、TokenUsageQueryService.BuildLabel、Reports/TokenUsageReportService、Reports/ChatReportService（2 處）。

ChatReportService 一起改的理由：它分桶的其實是「MCP 以 API Key 呼叫但身分反查不到的未具名呼叫者」，語意與「系統自動」不完全相同。但它與 token 排行並列顯示在同一個儀表板管理者專區，只改一邊會讓同一畫面出現兩種寫法、讀者會合理推論那是兩件不同的事。取視覺一致，語意差異記在這裡。

順手做的一個重構：TokenUsageView 內原有兩處與常數重複的字面值（PDF 副標題、UserLabel 回傳），改為引用 SystemOptionLabel。理由是 BuildFilter 用 StringComparison.Ordinal 拿下拉值與該常數比對來決定 SystemOnly —— 常數與字面值不同步時不會編譯失敗、不會有測試紅燈，只會讓「只看系統自動」的篩選靜默失效。這是本次改動直接暴露的風險，故一併消除。

新增第 5 個頁籤「明細（N）」

逐筆明細表原本固定在頁籤區下方，現整段搬移（非複製）進最右邊的 TabPane，標題 明細（{total}）（N＝篩選範圍總筆數）。DefaultActiveKey 維持 "user"，開頁第一眼仍是「依使用者」。

已查證 AntDesign 1.6.0 的延遲渲染行為（TabPane 條件為 _isActive || _hasRendered || ForceRender）：

  • 頁籤標題不受影響 —— tab bar 恆常渲染，而 total 由 LoadAsync() 在 OnInitializedAsync 就設好，點開前標題就有正確數字，不需要 ForceRender。
  • @bind-PageIndex／@bind-Total／OnChange 不會壞：延遲只是推遲 Table 掛載時機，掛載時值都已最新。
  • 唯一行為差異：RemoteDataSource 的 Table 初始化會觸發一次 OnChange → LoadAsync()，原本發生在開頁、現在發生在第一次點「明細」。兩者都是冪等重查。

「Token 用量明細」的詳細 Modal 刻意不搬進頁籤（它在 Tabs 之外，搬進去反而會被延遲渲染綁住）。

未變更 / 刻意不做

  • 不刪 OperationSkillGeneration。它不是死常數：OperationLabelHelper 註解已載明 1.0.45 功能移除後刻意保留讓歷史用量資料列仍顯示中文，且 OperationLabelTests.RemovedSkillGeneration_KeepsHistoricalLabel 有一條測試專門守住「不要順手把它清掉」。刪掉是資料顯示的功能倒退（歷史列會變回英文），零收益。只在 Entity 端補一行註解把理由鏡射過去 —— 因為原本只有 helper 那邊寫了理由，看 Entity 的人（包含本次規劃時）會誤判為死碼。
  • 不新增守門測試。使用者選擇改以速查文件登記不變量。代價要說清楚：下次新功能忘記 Push 時，一樣是建置成功、測試全綠、默默掉進「（系統自動）」桶。
  • 不改 6 支背景服務 Push 用字串字面值而非常數（TranscriptionBackgroundService 等）—— 超出本次範圍。
  • 不抽跨層共用的「（系統自動）」常數 —— 剩下幾處字面值分屬不同語意來源（LlmTokenUsage 與 LlmChatLog），硬綁會把「碰巧同字」誤植成「必須同字」。改以速查文件記載「這 6 處必須同字」。
  • docs/changelog/** 既有各篇與 docs/README.md 的歷史摘要行不改名 —— 那是當時的事實記載。

⚠️ 已知限制：舊資料回填不了

MediaTranscription／DocumentExtraction／ImageRecognition／KnowledgeSource 這些主體 Entity 上完全沒有 UserId／CreatedBy 欄位（已逐欄確認），RecordId 回查也查不到人；唯一的間接線索 PipelineProgressEvent.UserAccount 同樣來自 OperationContext、同批一起是 null。

因此只有 1.0.80 之後新產生的紀錄會帶使用者。 升版後翻舊資料仍會看到「（系統自動）」，那不是沒修好。

驗證

  • 最強的二元證據：GetFilterOptionsAsync 以 SELECT DISTINCT Operation 生出作業下拉。修好之前，MediaGeneration／DocumentGeneration／GoldenSample／RagDiagnosticsTrial／RagEvaluation 這 5 個值不可能存在於 DB（全庫從無寫入點）。各跑一次後重整 /token-usage，作業下拉應出現 5 個新中文選項。
  • 黃金樣本單筆評測應剛好產生 5 列 Stream（對照 CleaningEnhancer 的去重／遮罩／分類／摘要／信心五個呼叫點）—— 數量對得上代表 Push 涵蓋整條 await 鏈沒中斷。
  • 改名最容易靜默壞掉的地方：使用者下拉選「（系統自動）」→ 查詢，結果須只有無主列（驗 BuildFilter 的 Ordinal 比對仍與下拉同步）；該篩選下載 PDF，副標題須顯示「使用者：（系統自動）」。
  • 儀表板管理者專區：Token 排行與問答排行的無主桶兩邊都顯示「（系統自動）」。
  • 明細頁籤：點開之前標題就要有正確的 N；點開後表格、分頁、換頁、「詳細」視窗均正常。
  • SQL 對照：修好後不應再有 Operation IN ('Stream','Embedding','Image','File','Text') 且 UserAccount IS NULL 的新列 —— 那正是「作業退化成 CallType」的指紋。

758 測試全綠（數字不變）；文件編碼 0 FAILED；無 migration（LlmTokenUsage schema 一欄未動，新增的都是編譯期常數；改名純顯示層，DB 不存這個字串）。
