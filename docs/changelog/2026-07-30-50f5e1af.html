三、⚠️ 一個先前的判斷被證明是錯的

規劃階段我斷定「6 份文件連到 完整操作手冊.md#選單名與權限樹名對照表，但該標題的 GitHub slug 是 31-選單名--權限樹名-對照表…，所以這是壞錨點」，並打算修它。

寫完守門腳本一跑，錨點失敗數是 0。 查證後發現：docs/guides/完整操作手冊.md 第 102 行早就有 <a id="選單名與權限樹名對照表"></a>，就放在該標題正上方——正是我打算「補上去」的那個技巧。同檔另有兩處相同做法（知識來源列上動作、我的對話），所以 inline HTML 錨點在本專案已有先例。

結論：計畫中的「修壞錨點」項目不需要做，也沒有做。 全 docs 的 98 個頁內錨點與 1959 個 .md 連結目前全部解析成功。先寫守門腳本再動手，避免了去「修」一個沒有壞的東西。

四、關鍵設計決策

決策理由
slug 演算法抽成共用模組文件內約 100 個頁內錨點是照 GitHub 規則手寫的。產生器與守門腳本各自實作的話，會出現「守門說沒問題、產出的頁面卻跳不到」。已用 6 個真實案例驗證（含 14.6 問答稽核明細 (/chat-logs) → 146-問答稽核明細-chat-logs、3.1 選單名 ↔ 權限樹名 對照表（**…**） → 31-選單名--權限樹名-對照表…）
全部 425 份都轉，導覽只露策展子集文件之間的交叉連結不會斷；changelog 對顧問查版本差異其實有用
.html 連結改指向站內頁，不複製伴生檔建站中途實測發現：複製 docs/ 的 18 個伴生 HTML 會讓其內部「同目錄兄弟檔」的相對連結全部斷掉（實測 32 個死連結）。且 18 個伴生檔全部都有同名 .md，指回站內頁還能保有麵包屑、章節導覽與搜尋
對外版是「不產生檔案」而非隱藏連結靜態網站沒有權限機制，唯一可靠的隔離就是那個檔案不在資料夾裡。可用檔案存在性驗證
ASCII slug 檔名＋對照表避免中文 URL 編碼問題（SQL Server 切換說明.md 這類含空白的檔名尤其）。策展 103 份手工指定可讀英文名，其餘以「檔名 ASCII 片段＋8 碼雜湊」自動產生
只做標題與章節搜尋，不做全文全文索引會膨脹到 4～5 MB，每位訪客都要下載。現為 337 KB，已能「打一個詞跳到具體章節」
資料檔路徑一律驗證CURATED_SLUGS／SCENARIOS／INTERNAL_FILES 任一條打錯或檔案改名，建站當場失敗並指出哪一條，不產出半殘網站
刻意不重構 Build-OnboardingDocsHtml.py它已 commit 且正常運作、有既有輸出與明確目標檔；改它會讓兩件事同時變動（外科式變更）。整併建議寫進維運文件，未決定前兩支各自維護
