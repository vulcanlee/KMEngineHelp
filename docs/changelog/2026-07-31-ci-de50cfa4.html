提交前的一鍵檢查與一層薄 CI（1.0.117 → 1.0.118）

  • 變更日期：2026/07/31
  • 版本：1.0.117 → 1.0.118
  • 性質：工具與流程（scripts/、.github/）＋文件。src/ 零變更、無模型變更、無新表、無 migration、無新設定鍵。
  • 對應盤點項：後續四項的第三項
  • 編碼：UTF-8（繁體中文，含 BOM）

一、解決什麼

守門本身其實已經夠多了，問題是散在四個地方：

dotnet test src/KnowledgeExtraction/KnowledgeExtraction.Tests/KnowledgeExtraction.Tests.csproj
pwsh -NoProfile -File scripts/Test-DocsEncoding.ps1
python scripts/Test-DocLinks.py
python scripts/Build-HelpSite.py --both --check

四條指令要記，而且漏跑哪一條不會有任何提醒。實際上前面幾個版本就發生過：1.0.115 把 appsettings.json 的 BOM 弄掉（Test-DocsEncoding.ps1 只檢查 docs/**/*.md，抓不到），1.0.116～117 兩次都是靠人記得手動跑完四項。

這一版把四道收成一行，並在推上 main 時於 GitHub Actions 再跑一次同一支腳本。

二、scripts/Test-All.ps1

pwsh -NoProfile -File scripts/Test-All.ps1
順序守門實測耗時
1文件編碼（UTF-8 含 BOM、無亂碼）0.3 秒
2文件連結與錨點0.9 秒
3說明網站乾跑（--check，不寫檔）2 秒
4單元測試（1120 條）約 45～100 秒

三個刻意的行為

① 第一道失敗不會中斷，四道全部跑完才收尾。 這四項彼此獨立，一次看到全部的失敗清單，比修一項、再跑一次、再發現下一項省時間。收尾時列出總結表與「有 N 項未通過」。

② 由便宜到昂貴排序。 文件三道加起來 3 秒出結果，最慢的測試放最後。

③ 結束碼 0／1。 可直接當 CI 或 git hook 的判斷依據。

一件它刻意不做的事

不檢查 SystemVersion 有沒有 +1，也不檢查文件內容有沒有跟著改。 這兩件事沒有機械判準（改了什麼算「相關文件」？），做成守門只會製造假訊號。全綠時腳本改用提醒的方式提一句版本號。

三、.github/workflows/ci.yml

一個 job、一個實際步驟，內容就是呼叫 Test-All.ps1。

刻意不在 workflow 裡把四道守門再列一次。 列兩份的話，日後新增第五道守門一定會漏改其中一份，CI 就會在沒人發現的情況下少檢查一項——那正是這一版要消滅的失敗模式。守門清單的唯一真實來源是 scripts/Test-All.ps1。

另外加了 concurrency 群組並開 cancel-in-progress：連續推送時只留最後一次，不讓舊的跑完浪費分鐘數。

四、順手修掉的兩個守門本身的缺陷

這兩項不是新功能，是既有守門在當成守門用的時候會失效：

4.1 Test-DocLinks.py 在 Windows 主控台會整支掛掉

主控台預設是 cp950，編不出 🔴／🟡，print 直接丟 UnicodeEncodeError。腳本當場中止、結束碼 1——看起來像「有死連結」，其實是印不出來。之前都靠 PYTHONIOENCODING=utf-8 繞過。

修法是兩層：

  • 自己的訊息不用表情符號了，區段標題改成 [硬性]／[提醒] 純文字。反正嚴重度本來就靠字面在區分。
  • 另加 sys.stdout.reconfigure(errors="replace")：輸出有一部分來自 docs（檔名、連結字串），無法保證全都在 cp950 裡，讓編不出來的字元退化成替代字元而不是拋例外。

⚠️ 刻意不改主控台編碼（那會讓繁體中文變亂碼）。

4.2 Build-HelpSite.py 一律回傳 0

--check 是設計來當守門的，但 main() 不管有沒有「無法解析的文件連結」都 return 0——那道門等於永遠開著。改成有解析不到的連結時回傳 1。

⚠️ 對外版刻意排除對內文件而斷開的連結算在另一個計數（excluded_link），不會讓結束碼變成 1。

五、驗證

Test-All.ps1 自己沒有單元測試（PowerShell 腳本在這個 repo 沒有測試框架），所以用實跑驗證，正反兩面都做：

正面（乾淨的樹）：四項全通過、結束碼 0、總耗時約 103 秒。

反面（故意製造失敗）：暫時放一份 docs/_gate-selftest.md，不加 BOM且內含一個指向不存在檔案的連結，一次踩三道守門。結果：

[失敗] 文件編碼（UTF-8 含 BOM、無亂碼）（0.3 秒）
[失敗] 文件連結與錨點（0.8 秒）
[失敗] 說明網站乾跑（不寫檔）（1.8 秒）
[通過] 單元測試（44.9 秒）

有 3 項未通過：文件編碼（UTF-8 含 BOM、無亂碼）、文件連結與錨點、說明網站乾跑（不寫檔）

結束碼 1。這同時證明了三件事：三道守門都真的抓得到、第一道失敗之後沒有中斷（後面三道照跑）、以及 Build-HelpSite.py 的新結束碼有效。測試完該檔已刪除。

其餘：dotnet test 1120 通過／0 失敗（與 1.0.117 相同，本版 src/ 零變更）。

❌ 無法完成的驗證

ci.yml 沒辦法在本機驗證，第一次真正的驗證是推上 GitHub 之後。 已知的風險是 runs-on: ubuntu-latest——本機只在 Windows 驗過。已確認測試沒有硬寫 Windows 路徑（定位檔案的那幾條都用 Path.Combine 往上層找）、appsettings.json 沒有絕對路徑、--check 不會碰輸出目錄，但仍不能保證。若 CI 紅燈，把 runs-on 改成 windows-latest 即可，代價是私有 repo 的分鐘數以兩倍計。

六、順帶發現、本版沒有處理

dotnet test 的還原階段一直在報兩個高嚴重性套件弱點：
