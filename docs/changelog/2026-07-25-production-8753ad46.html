移除 Production 啟動安全檢查（1.0.68）

  • 日期：2026/07/25
  • 版本：1.0.67 → 1.0.68
  • 類型：功能移除（依使用者決定）
  • 影響範圍：Production 啟動流程

一、移除原因

StartupSafetyValidator 連續兩次擋住正式環境部署，IIS 回 HTTP 500.30：

Production 啟動安全檢查失敗：
JwtSettings:SigningKey 不可在 Production 使用開發預設值。
BootstrapSettings:SupportPassword 不可在 Production 使用預設密碼。

23:48 重新部署後 appsettings.Production.json 仍未補上這兩項，23:49 再次啟動失敗。使用者決定移除整支驗證器，不再讓啟動期檢查阻斷部署。

二、移除範圍

項目處置
Web/Configuration/StartupSafetyValidator.cs刪除（四項檢查全部：JWT 金鑰、support 密碼、Swagger 須明確設定、Redis 連線字串）
Program.cs 的呼叫點刪除；連同因此失效的 using KnowledgeExtraction.Web.Configuration;
Tests/StartupSafetyValidatorTests.cs刪除（26 個測試）
Tests/ApiIntegrationTests.ProductionSafetyValidation_WithDevelopmentDefaults_ShouldFailFast刪除
Web/Configuration/UnsafeDefaults.cs保留——/system-health 的「身分驗證」項仍用它判定「Production 是否沿用開發金鑰」

UnsafeDefaults 的邊界測試原本寄生在 StartupSafetyValidatorTests 裡，已搬到新的 UnsafeDefaultsTests.cs（15 個測試），避免健康檢查依賴的判定式變成零涵蓋。其 XML 註解也改寫過——原本寫著「由 StartupSafetyValidator 共用」「StartupSafetyValidatorTests 會驗證」，都已指向不存在的東西。

三、移除後的實際狀態（請務必知悉）

JwtSettings:SigningKey 與 BootstrapSettings:SupportPassword 現在沒有任何程式檢查。 沿用倉庫內公開的開發金鑰與 1qaz@WSX 不會被擋、也不會有啟動提示。

  • 風險：任何看得到原始碼的人都能用開發金鑰偽造 JWT；support 密碼是文件裡寫死的那組，且每次啟動都會依設定值重設。
  • 唯一的提示：/system-health 的「身分驗證」項在 Production 沿用開發金鑰時會顯示異常——唯讀燈號，不擋任何事。
  • 補償：這兩項已列入 planning/08 backlog，並建議納入部署檢查清單、每次部署後開 /system-health 確認。

Swagger 與 Redis 兩項設定正確性檢查也隨之移除（見 backlog）。

仍然會擋啟動的關卡（不在移除範圍）

Program.cs 對 JwtSettings 有 .ValidateDataAnnotations().ValidateOnStart()，而 SigningKey 標了 [Required]＋[MinLength(32)]。金鑰留空或短於 32 字元仍會 500.30，但訊息不同——實測輸出：

OptionsValidationException: DataAnnotation validation failed for 'JwtSettings' members:
'SigningKey' with the error: 'The SigningKey field is required.'

這是 ASP.NET Core 標準的選項驗證，與已移除的驗證器無關。下次遇到 500.30 時可用訊息型別分辨來源。

四、驗證

項目結果
倉庫現狀 ＋ Production 啟動成功啟動、首頁回 200、日誌 0 條「啟動安全檢查失敗」——這正是移除的目的
金鑰留空 ＋ Production 啟動仍失敗，但訊息為 OptionsValidationException（見上），確認來源是選項驗證而非已移除的驗證器
dotnet test668 通過 / 0 失敗（680 − 27 移除 ＋ 15 搬移）
殘留參照src/ 與 docs/（排除 changelog／archive）僅剩刻意的「已移除」註記
