修正三條管線狀態決策讀到陳舊追蹤實體（重試／取消／核准等誤判）（0.2.86）

  • 日期：2026-06-19
  • 版本：0.2.85 → 0.2.86
  • 類型：缺陷修正

問題

延續 0.2.85（音訊轉錄重試誤判）的同一根因稽核：在 Blazor Server 中，Service 以建構式注入 元件，其 BackendDBContext 綁定整個 SignalR circuit（長壽命）。背景服務以獨立 scope／獨立 context 更新同一筆資料的 Status。當 circuit 的 context 先前已追蹤過該實體（新增時 AddAsync、 或前次 tracked 查詢），之後用 tracked 查詢且未先 CleanTrackingHelper.Clean 讀回時，EF 會回傳 識別映射中的陳舊實體，使依 Status 的決策出錯——須重新整理網頁才能正確操作。

0.2.85 只修了 MediaTranscriptionService 的 RetryAsync／CancelAsync；全專案稽核發現其餘三條 管線（文件萃取、圖片解讀、知識來源清洗）的對應方法仍有同型問題。

根因

僅四條管線的實體會被背景服務改 Status（高風險）：MediaTranscription、DocumentExtraction、 ImageRecognition、KnowledgeSource。下列方法以 tracked 查詢讀回後直接依 Status 判斷，但未先 清掉本地追蹤：

  • DocumentExtractionService：RetryAsync、CancelAsync
  • ImageRecognitionService：RetryAsync、CancelAsync（先前僅 EnqueueRecognitionAsync 有防護）
  • KnowledgeSourceService：TriggerCleaningAsync、CancelCleaningAsync、RetryCleaningAsync、

ApproveAsync、RejectAsync

修正

在上述 9 個方法的 tracked 查詢前，加入專案既有慣例（CLAUDE.md 載明、MediaTranscriptionService 與 ImageRecognitionService.EnqueueRecognitionAsync 已採用）：

CleanTrackingHelper.Clean<TEntity>(context);

強制查詢讀到資料庫最新 Status。UpdateAsync／DeleteAsync 不依 Status 做決策，本次不調整。

影響範圍

  • 變更檔案：Business/Services/DataAccess/DocumentExtractionService.cs、

ImageRecognitionService.cs、KnowledgeSourceService.cs，以及 appsettings.json（版本號）。

  • 重用既有 CleanTrackingHelper.Clean<T>，三檔皆已 import，無模型／資料庫變更，不需 migration。

驗證

  1. dotnet build、dotnet test（既有約 240 案）全綠。
  2. 同一瀏覽器 session 內，對文件萃取／圖片解讀／知識來源清洗觸發背景失敗後，不重整直接按

重試／取消／核准／退回，應正確執行而非出現「只有失敗或已取消的紀錄可以重試」「正在清洗中」等誤判。
