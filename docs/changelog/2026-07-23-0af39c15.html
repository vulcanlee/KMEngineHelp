清洗 LLM 呼叫改走串流，根治 120 秒逾時（1.0.33）

  • 日期：2026-07-23
  • 版本：1.0.32 → 1.0.33

摘要

修正內容清洗管線呼叫 LLM 時，長內容因整段生成超過 120 秒而被 HttpClient.Timeout 取消（TaskCanceledException）並反覆重試的問題。清洗五步改走串流累積，解除總生成時間的硬上限。

根因

  • 清洗步驟原用非串流的 OpenAIChatCompletionClient.CompleteAsync（SendAsync 預設 ResponseContentRead，緩衝整個回應），HttpClient.Timeout=120s 涵蓋「送出＋整段生成＋讀完 body」。
  • CleaningEnhancer.EnhanceAsync 把整篇彙整內容一次整包送給 reasoning 模型 gpt-5.4，且連做去重／遮罩／分類／摘要／信心自評五步；內容一長，單步生成即超過 120 秒。
  • 逾時的 TaskCanceledException 被判為可重試，整段最多重跑 3 次仍逾時。
  • 120 秒設定於 Program.cs（chat typed client）← OpenAISettings:GenerationTimeoutSeconds。

修正

  • IChatCompletionClient 新增預設介面方法 CompleteStreamingAsync（預設委派至 CompleteAsync，故其他實作與測試假物件無需改動）。
  • OpenAIChatCompletionClient 覆寫 CompleteStreamingAsync：複用既有 StreamAsync（以 SSE、ResponseHeadersRead 讀取）逐塊累積為完整字串。HttpClient.Timeout 此時只界定「取得回應 headers」的時間，長內容的整段生成不再受總時間上限限制。
  • CleaningEnhancer 五個步驟（去重／遮罩／分類／摘要／信心自評）改呼叫 CompleteStreamingAsync；其餘降級與取消處理邏輯不變。
  • 測試：新增驗證「清洗各步驟走串流版、未走非串流緩衝版」；既有清洗測試（假物件僅實作 CompleteAsync，靠預設委派）維持通過。

備註

  • GenerationTimeoutSeconds 維持 120（現在只界定取得 headers 的時間）。
  • 只有清洗切換為串流；其他 chat 呼叫（圖片解讀／檔案／技能／蒸餾／會議紀錄／Query Rewrite）不變。
  • 無資料模型變更，不需要資料庫 migration。
  • 已知殘留風險（可接受）：移除總時間硬上限後，若連線中途完全停滯理論上可能久候；實務上停滯的 TCP 讀取仍會擲錯，且管線重試機制兜底。
