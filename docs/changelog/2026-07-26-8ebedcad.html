變更紀錄

五支清單修正分頁順序未定義，兩個產生流程補上防重入（1.0.72→1.0.73）

  • 日期：2026-07-26
  • 版本：1.0.72 → 1.0.73
  • 類型：資料正確性修正（兩項獨立）

需求

兩件都屬於「使用者已經受影響、但不會有任何錯誤訊息」的類型。

一、五個清單頁的分頁順序未定義

RoleViewService／MyUserService／MeetingService／MyTasService／ProjectService 的排序邏輯包在 if (!string.IsNullOrWhiteSpace(dataRequest.SortField)) 內，之後直接 Skip/Take。沒有 ORDER BY 的 Skip/Take 結果順序未定義 → 翻頁可能重複顯示或漏掉資料，而且不會報錯。

⚠️ 這裡有一個關鍵的誤判要記下來：這個問題被記錄成「外層 if 少了 else」，但只補 else 修不掉使用者回報的症狀。

追查 Web/Components/Views/Admins/RoleViewView.razor.cs 的 OnTableChange 後確認：DataRequest.SortDescending 是 bool?，而每個具名分支的內層是

dataSource = dataRequest.SortDescending == true
    ? …OrderByDescending(…)
    : dataRequest.SortDescending == false
        ? …OrderBy(…)
        : dataSource;          // ← 方向為 null 時直接不排序

而 AntDesign 表頭排序循環到「取消」時，SortField 仍然是欄位名、只有方向變成 null（GetCurrentSortModel 的 ?? sortModels.Last() fallback 就是為此存在）。所以使用者回報的「取消排序後翻頁重複」走的是內層那個洞，外層 else 根本碰不到。

全庫 … : dataSource; 共 37 處，正好全部落在這五支（Meeting 6／MyTas 11／MyUser 8／Project 9／RoleView 3）。1.0.56 修好 Take 之後，這個洞一直留到現在。

二、「依提示詞產生」沒有任何防重入

generatingIds 在兩個檢視裡只寫不讀（DocumentExtractionView 內連一個讀取點都沒有，等於死狀態）。重複點擊會同時送兩次 LLM 並寫同一個生成檔——付兩次 token，且使用者拿到哪一份不確定。

查證後發現是兩個窗口，不是一個：

  1. OnGenerateConfirmAsync 在 generateModalVisible = false 之前有 await（取萃取文字／原始檔案／逐字稿），那段期間 Modal 的「確定」仍可再按 → 進入本方法兩次。
  2. 第一次的 Task.Run 還在跑時，使用者可再開同一列的「依提示詞產生」再送一次。

變更

五支改寫為 switch expression

照既有範本（KnowledgeSourceService.cs:99-107、WikiPageService）改為

dataSource = (dataRequest.SortField, dataRequest.SortDescending) switch
{
    (nameof(XxxAdapterModel.Title), true) => …,
    (nameof(XxxAdapterModel.Title), false) => …,
    …
    _ => dataSource.OrderByDescending(x => x.UpdatedAt).ThenByDescending(x => x.Id)
};

一個 _ => 同時堵住三個洞（SortField 空、方向 null、欄位名不認得），而且淨減行數（MyTasService 那段 90 行 → 26 行）。全庫至此只剩一種排序寫法。

預設一律「最近更新新到舊 ＋ Id 決定性 tie-break」，與 CategoryService／WorkCategoryService／KnowledgeSourceService／WikiPageService 既有語意完全一致。欄位名已逐支確認：RoleView／MyUser 是 UpdateAt（無 d），Meeting／MyTask／Project 是 UpdatedAt。

產生流程三道守門（兩支對稱）

守門擋什麼
generatingIds.Contains(id) 於 OnOpenGenerateAsync／OnGenerateConfirmAsync 開頭窗口 ②：背景還在產生時又送一次（開窗前就擋掉）
新增 generateSubmitting 旗標（try/finally 復位）＋ Modal 的 ConfirmLoading="@generateSubmitting"窗口 ①：關窗前那段 await 期間重複按確定
列內產生鈕 Disabled="@generatingIds.Contains(context.Id)"讓使用者看得見「這筆正在跑」，而不是靜默忽略

DocumentExtractionView 因為要把守門包進 try/finally，把實際送出的部分抽為 StartGenerateAsync。順便補上 MediaTranscriptionView 缺的 MaskClosable="false"（DocumentExtractionView 原本就有）。

兩支的 generatingIds 宣告都補了 XML 註解，說明它只在 renderer 同步情境存取（背景 Task.Run 內一律經 InvokeAsync），不得從背景執行緒直接讀寫——順帶結掉 backlog 裡「generatingIds 單執行緒不變式註記」那項。

測試

686 → 708（+22，全綠）。

ListDefaultSortPagingTests（20 條）—— 附一個誠實的覆蓋率說明

每支 4 條：三種落到 _ => 的情形（SortField 空／欄位名還在但方向被取消／欄位名不認得）＋ 預設方向本身。

⚠️ 哪一組真正抓得到這個 bug，值得寫清楚以免日後誤判覆蓋率：

  • *_DefaultSort_IsUpdate*AtDescending 這 5 條才是。 它們讓資料時間遞增插入，所以正確結果（更新時間遞減）是插入順序的反序；缺少兜底排序時 SQLite 按 rowid ＝插入順序回傳，方向剛好相反 → 紅燈。修正前已實測這 5 條全紅、修正後全綠。
  • *_FallbackSort_PagesDoNotOverlap 那 15 條在 SQLite 下修正前也是綠的——沒有 ORDER BY 時 SQLite 對單表掃描會穩定回傳 rowid 順序，「未定義」在此並未實際發生。保留是為了守住頁數／筆數契約，以及換到 SQL Server 時的回歸，但不是本 bug 的證明。

初版測試我把插入順序寫成與預期降冪一致，結果 20 條在錯誤程式碼下全綠。改成時間遞增插入後才真正 RED。這件事本身就說明「先證明測試會紅」不能省。

另外用一支腳本逐支比對改寫前後的 (SortField → 實體欄位) 映射：RoleView 3／MyUser 8／Meeting 6／MyTas 11／Project 9 全部逐一相符，確認 37 個三元式攤平時沒有任何欄位被接錯（這是本批最容易靜默出錯的地方——欄位接錯會編譯通過、分頁測試也通過，只是「按標題排序」實際按了別的欄位）。

GenerateReentrancyGuardTests（2 條）

原始碼掃描式守門（範本：LoggingConventionTests／MenuIconTests／CrudActionIconTests）。刻意不引入 bUnit：測試專案目前沒有，為一個 HashSet.Contains 守門引入元件渲染框架不成比例（違反 CLAUDE.md §2）。測試註解已明確標示這是文字層守門、不是行為驗證——移除守門會紅燈，但不保證守門邏輯正確。

影響與相容性

  • ⚠️ 五個清單頁的首屏順序會變動：改為一律「最近更新新到舊」。先前在未指定排序時實際上是資料庫回傳順序（多半接近插入順序），所以使用者可能感覺到差異。這是修正而非退化——先前那個順序本來就不保證。
  • 取消表頭排序後翻頁不再重複或漏列。
  • 產生流程：重複點擊現在會顯示「此筆正在產生中，請等待完成後再送出。」並停用列內按鈕；正常單次操作行為不變。
  • 無資料庫 migration、無 API 合約變更、DataRequest 契約不變。
