變更紀錄

修好「API 刪會議」與畫面刪會議的行為不一致（1.0.121 → 1.0.122）

  • 變更日期：2026/07/31
  • 版本：1.0.121 → 1.0.122
  • 性質：src/ 修正 ＋ 測試 ＋ 文件。無模型變更、無新表、無 migration、無新設定鍵。
  • 對應項目：1.0.119 全庫盤點查出的三項落差之第一項
  • 編碼：UTF-8（繁體中文，含 BOM）

一、解決什麼

同一筆會議，從畫面刪和從 REST API 刪，結果不一樣——因為它們是兩份不同的程式：

團隊權控刪附件實體檔清孤兒成員＋標來源過時
畫面（MeetingService.DeleteAsync）❌ 落差 #2，另案✅✅
REST API（MeetingRepository.DeleteAsync）✅❌❌

從 API 刪會議會留下磁碟孤兒附件檔、孤兒成員列，而且引用它的知識來源不會被標成過時——使用者完全不會知道那個來源的內容已經失準了。這是三項落差裡唯一會造成「資料悄悄變錯而沒有人知道」的一項，所以先修它。

既有的 MeetingKnowledgeSourceStaleTests 完整釘住了 Service 那條路徑（6 條，含兩條刻意的反證），但完全沒有涵蓋 Repository 這條——這就是它能一直存在的原因。

二、順帶修掉的第二個洞

規劃時查證出：Meeting.GeneratedContentRelativePath（AI 會議紀錄的 .md）兩條路徑原本都沒刪，畫面刪也會留孤兒檔（MeetingService.DeleteAsync 只走 item.Files）。

安全性先查證過才動手：會議與影音轉錄的產生內容檔名都是 {年}/{Guid:N}.md（MeetingMinutesGenerationService.SaveMarkdownAsync／LlmGenerationService.SaveGeneratedContentFileAsync），GUID 命名不可能撞檔，刪會議只會刪到自己那份；而且兩支服務本來就有「只保留最新一筆：刪除上次的落地檔」的邏輯，刪這種檔不是新行為。

三、修法

新增 Business/Helpers/MeetingDeletionHelper.cs，與 KnowledgeSourceMaintenanceHelper 同一個形狀：靜態、不呼叫 SaveChangesAsync，交由呼叫端在既有交易中一併提交以維持原子性。

它做三件事：刪附件實體檔 → 刪 AI 會議紀錄的 .md → 呼叫既有的 KnowledgeSourceMaintenanceHelper.MarkOwningSourcesStaleAsync(..., removeOrphanItems: true)。兩條路徑都改成呼叫它。

檔案變更
Helpers/MeetingDeletionHelper.cs（新）共同處置
Services/DataAccess/MeetingService.cs「逐檔刪 → 標過時」那一段換成 helper。行為的唯一變化是多刪了 AI 會議紀錄那份檔
Repositories/MeetingRepository.cs建構式加 IOptions<SystemSettings> 與 ILogger；DeleteAsync 由 FindAsync 改為帶 .Include(x => x.Files) 的查詢，通過權限檢查後呼叫 helper

三個刻意的設計選擇

① 權限檢查留在原位，在刪檔之前。 helper 會真的刪檔，順序反了會變成「刪不掉但檔案已經沒了」——比原本的落差更糟。這一點由一條專門的反證測試釘住。

② 刪檔失敗不讓整筆刪除失敗。 檔案被其他程序佔用時只記 Warning 繼續走（沿用素材三型 TryDeleteRelative 的處置）。留下孤兒檔，比讓使用者永遠刪不掉那筆會議好。⚠️ 這與 MeetingService 原本的 TryDeleteFile（不 catch，被鎖住就整筆失敗）不同，是刻意改成較安全的那一種。

③ 沒有把 GetFullPath／TryDeleteFile 搬進 helper。 規劃時本來要搬，實作時查出那三個 private 方法還被另外三處呼叫（單檔刪除等），與本次的連帶處置無關；搬了會動到不相干的程式路徑。真正該消掉的重複——刪除的連帶處置序列——已經消掉了。

四、測試：MeetingDeleteParityTests.cs（新檔，6 條）

既有的 MeetingKnowledgeSourceStaleTests 一條都沒有改——它講的是「素材異動 → 過時」的契約，這一檔釘的是不一樣的東西：兩條刪除路徑的結果必須一致。

先寫測試看紅燈，確認測到的是真問題：

#測什麼修之前
1Repository 刪 → 孤兒成員被移除、來源 ContentStale🔴 紅
2Repository 刪 → 附件實體檔不存在🔴 紅
3Repository 刪 → AI 會議紀錄的 .md 不存在🔴 紅
4Service 刪 → AI 會議紀錄的 .md 不存在（第二節那個洞）🔴 紅
5平價：同一情境走兩條路徑，成員數／ContentStale／兩種檔案的存在與否完全一致🔴 紅
6🔴 反證：Repository 對無權限的會議 → 回 false，且檔案還在、成員還在、來源沒被標過時、會議還在綠（但先前沒人守著）

實測修之前 5 紅 1 綠，與預期完全一致——綠的那條正是反證，它本來就該綠。

第 6 條是這組裡最重要的：修完之後 helper 會刪檔，必須確認權限不足時 helper 根本沒被呼叫到。

六、順帶記錄，本版不處理

MyTaskRepository.DeleteAsync 與 ProjectRepository.DeleteAsync 有同一類的實體檔孤兒（刪 DB 列但不刪附件實體檔）。那兩支是樣板 CRUD、與知識庫無關，不在本次範圍內，記在這裡供日後決定。
