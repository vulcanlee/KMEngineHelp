變更紀錄

favicon 多尺寸重生：修正緊裁基準，分頁圖示放大 1.38 倍

變更目的

使用者回報：瀏覽器分頁上本系統的圖示，比 Facebook / LinkedIn / Blogger / TikTok 等其他分頁的圖示小很多。

根本原因：0.2.159 那次「去白邊放大」本身就沒改對

wwwroot/favicon.png（128×128）中，標誌本體只佔 74×90 px（寬 57.8%、高 70.3%），四周是透明留白。換算到分頁的 16px 顯示，標誌只有 9.2 × 11.2 px，難怪比鄰居小一截。

留白的來源是 0.2.159 的處理方式。該篇第 3 步寫「依非透明像素 bbox 緊裁（裁切後約 304×341）」—— 用的是 alpha bbox。但來源圖 wwwroot/images/app-logo.png 的白色圓角卡片外圍有一層淺灰柔邊（以下稱「幽靈環」），它既不夠透明（alpha > 32）也不夠白（min RGB < 235），四角 flood fill 會停在那裡。緊裁於是被這圈環撐大，裁到的是卡片，不是標誌。

本次在記憶體中重跑該演算法，完整重現了這個 bug：

四角 flood fill 後  alpha bbox = (92, 72, 420, 439) → 328×367，比例 0.894  ← 幽靈環（卡片）
                    墨色  bbox = (136, 105, 366, 382) → 230×277，比例 0.830  ← 標誌本體

328×367 與該篇自述的「約 304×341」（比例 0.891）是同一個東西 —— 比例對得上，而標誌本體的 0.830 對不上。該篇第 1 段「讓 logo 貼齊放大」的成果宣稱並未達成，已回頭在該篇加註勘誤。

處理方式

新增 scripts/Build-Favicons.py（納入版控，取代一次性執行）。核心是把緊裁基準從 alpha bbox 換成墨色 bbox（alpha > 128 且 (R+G+B)/3 < 200）：

  1. 讀 wwwroot/images/app-logo.png（512×512 RGBA）轉 RGBA。
  2. 四角 BFS 連通填充去背（背景判定：alpha < 32 或 min(R,G,B) >= 235）：與畫布邊緣相連的區域 alpha 設 0；內部白色（節點圓、盾牌、鑰匙孔）被深色描邊包圍、與外部不連通，完整保留 5,982 個像素（未用「全部白→透明」以免挖空內部）。
  3. 依墨色 bbox 緊裁 → 230×277。幽靈環在此框之外，因此被裁掉。
  4. 長邊縮至 round(尺寸 × 0.96)（LANCZOS）、置中貼到透明方形畫布。留 2% 安全邊距是刻意的：六邊形上下尖角的反鋸齒貼死邊緣會被切平。
  5. 落檔前驗證，未通過則非零離開、不寫任何檔案（見下節）。

輸出四個尺寸，App.razor 以 sizes 屬性升冪宣告（Chrome 依 sizes 挑最接近、Firefox 傾向取最後一個合適者，升冪且尺寸標示正確時兩種策略結果都對）：

檔案畫布標誌內容高填滿寬填滿
favicon-16.png16×1612 × 1593.8%75.0%
favicon-32.png32×3226 × 3196.9%81.2%
favicon-48.png48×4838 × 4695.8%79.2%
favicon.png128×128102 × 12396.1%79.7%
（修改前）favicon.png128×12874 × 9070.3%57.8%

相對現況放大約 1.38 倍；分頁上的標誌從 9.2 × 11.2 px 變成 12 × 15 px。

favicon.png 檔名刻意不改：既是 128 尺寸的來源，也是有人硬寫 /favicon.png 時的相容路徑。

驗證：守門已實證有效

Build-Favicons.py 的 verify() 直接釘住本次的 bug 型態。已實證：把緊裁基準改回 alpha bbox（＝0.2.159 的錯誤做法）後，驗證器回報 7 個問題、離開碼 1，第一條即點名成因：

墨色 bbox 為 328x367，預期 230x277。（若量到 328x367 表示緊裁基準被改回 alpha bbox，那是幽靈環不是標誌）
墨色 bbox 比例 0.894，預期 0.83 ± 0.005
墨色 bbox (92, 72, 420, 439) 未嚴格內縮於 alpha bbox (92, 72, 420, 439)，緊裁基準可能取錯
16px：內容寬 13，預期 12 ／ 32px：28，預期 26 ／ 48px：41，預期 38 ／ 128px：110，預期 102

其餘斷言：輸出必須是 RGBA 且四角 alpha 為 0（擋住日後偷加實心底磚）、內部白色像素不得低於 1,000（擋住挖空盾牌與鑰匙孔）、每個尺寸的內容高必須等於 round(尺寸 × 0.96) 且置中偏移差 ≤ 1px。

⚠️ 驗證器刻意不斷言「填滿率 ≥ 96%」：round(16 × 0.96) = 15、15/16 = 93.75%，16px 那檔會永遠不過。要比對的是精確值 15／31／46／123。

未變更

  • wwwroot/images/app-logo.png（登入頁 Login.razor 與 SplashView.razor 仍在用的白色圓角磚版，維持不變）。
  • 指紋化機制：@Assets[...] 寫法沿用 0.2.158 的結論，四個新舊檔案都走同一套。
  • .csproj：Razor SDK 對 wwwroot/** 自動 glob，新增 PNG 不需任何設定。
  • 測試數量：758 條不變（本次不影響任何測試）。無 migration。

刻意不做

  • 不加實心底色磚。其他分頁的圖示（Facebook / LinkedIn / Blogger / TikTok）之所以看起來「滿」，是因為它們是填滿整個方框的實心色磚。本系統維持透明背景是使用者的明確選擇，代價是六邊形為直立形（比例 0.830），寬度只能填到約 80%，視覺上仍會比滿版色磚略小一點。
  • 不加 favicon.ico / site.webmanifest / apple-touch-icon / theme-color：超出本次需求範圍。
  • 不新增守門測試：使用者選擇以實作順序與人工檢查守住，改以速查文件登記不變量。

已知風險

  • ⚠️ @Assets["不存在的 key"] 會靜默失敗：ResourceAssetCollection 的 indexer 查不到時原樣回傳 key，不編譯失敗也不拋例外，產生無指紋的 <link href="favicon-16.png"> → MapStaticAssets 不認得 → 404 → 被 UseStatusCodePagesWithReExecute("/not-found") 重導成一頁 HTML，瀏覽器拿到非圖片內容就安靜放棄。畫面上只會看到「favicon 沒變」，沒有任何錯誤訊息。因此實作順序必須是「先產圖 → 再改 App.razor → 再建置」，且四個檔案缺一不可。已登記進速查。
  • 發佈設定 FolderProfile.pubxml 是 DeleteExistingFiles=false，舊的 favicon.<舊指紋>.png 會殘留在發佈資料夾。無害（App.razor 引用的是新指紋），但可自行清理。

備註

  • favicon 是瀏覽器快取最頑固的資源之一，Chrome 另有獨立的 favicon 資料庫，Ctrl+F5 常常無效。若沒看到變化，最可靠的確認方式是開一個全新的無痕視窗，或 DevTools → Application → Storage → Clear site data。
  • 重新產生圖示：python scripts/Build-Favicons.py（先跑 --dry-run 可只驗證不落檔）。相依 Pillow。

編碼要求

  • 本次新增文件以 UTF-8（含 BOM）保存，內容為繁體中文、無亂碼。
