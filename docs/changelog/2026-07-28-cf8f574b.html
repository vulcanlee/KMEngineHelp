選單「系統監控與日誌」拆分與 flyout 溢出修正（1.0.96 → 1.0.97）

  • 日期：2026-07-28
  • 版本：1.0.96 → 1.0.97
  • 類型：UI 修正（無新表、無 migration、不動權限）

問題

側邊欄收合狀態下，滑過「系統管理 › 系統監控與日誌」彈出的第三層面板有 8 個項目，高度超過視窗，最後一項「資料表使用狀況」被切在畫面外——看得到一半但點不到。

根因

收合態的側邊欄不是 AntDesign Menu，而是 NavMenu.razor 自製的 CSS flyout。.collapsed-submenu-flyout（第三層面板）是 position: absolute; top: 0; left: 100%——對齊觸發列頂端往下長，既沒有 max-height 也沒有 overflow。「系統監控與日誌」那一列位在第二層面板偏下的位置，8 項面板的起點就低，直接掉出視窗底部。

展開態沒這問題（走 AntDesign inline Menu，包在 overflow-y: auto 的 .nav-scrollable 裡）。

⚠️ 為什麼不是「再加一層子功能表」

這是最直覺的想法，但 NavMenu.razor:71 的註解顯示前人正是為了「單一面板過長溢出」才做出現在這層巢狀——再加一層是重複同一招：

  • NavMenu.razor 的收合態標記寫死三層（item → child → grandChild），第四層要改標記與 CSS；
  • 導覽變成三次 hover，往右還可能撞到視窗右緣；
  • 而且新面板一樣沒有高度上限、一樣會溢出，根因沒解到。

改採「同層拆兩組（解眼前）＋ 第三層加高度上限（解根因）」。

變更

1. Menu.json：502 拆成兩組

「系統管理」的子分類由 3 組變 4 組：

群組id圖示項目
系統監控（沿用 502、改名）502monitor_heart統計儀表板、系統健康監控、待處理背景工作、資料表使用狀況
診斷與日誌（新增）504troubleshoot檢索診斷與調校、資料一致性巡檢、日誌等級切換、日誌下載

分法是「現在系統怎麼樣」vs「查問題／看日誌」。葉節點的 id／url／icon 一律未動，只是換掛群組。

刻意不重編 503 的 id：陣列位置決定顯示順序，id 只是識別碼，現況本來就不連號（502 底下是 513、53…）。重編是無益的擾動。

2. NavMenu.razor.css：只給第三層加高度上限

.collapsed-submenu-flyout {
    max-height: calc(100vh - 2rem);
    overflow: hidden auto;
}

⚠️ 第二層 .collapsed-menu-flyout 完全沒動，並在該處補上 guard 註解。原因是 開發慣例與限制速查.md 記載的 1.0.44 踩雷點：第二層是第三層 flyout（定位在 left:100%、於框外）的 containing block，一加 overflow 就把第三層整個裁掉，懸停子分類將看不到功能頁。

第三層可以加，是因為它底下只有葉節點連結、框外沒有任何定位元素，overflow 裁不到東西。

⚠️ overflow 明寫兩軸（hidden auto）：只寫 overflow-y: auto 會讓 overflow-x 隱含變成 auto，產生 1.0.44 那個假的水平捲軸。

3. MenuIconTests.AllowedParentIcons 補 troubleshoot

新群組圖示須在白名單內。troubleshoot 本來就在 AllowedLeafIcons（被「檢索診斷與調校」使用），與 monitor_heart／auto_awesome 同時列在兩份白名單的既有慣例一致。

4. 文件

  • 開發慣例與限制速查.md：①子分類 3 組 → 4 組與新名稱；②把「兩層 flyout 皆不可加 overflow/max-height」改寫為分層敘述。原敘述會讓後人以為第三層也不能加，而本次正好證明第三層可以且應該加——踩雷點的敘述不精確，比沒寫更危險。
  • 12 份 live 文件的導覽路徑（約 34 處）依該頁實際落在哪一組改成「系統監控」或「診斷與日誌」。其中 系統健康監控-prd.md 需改寫而非換字：/system-health、/log-settings、/log-download 三頁原本同群組，現在分屬兩組。
  • docs/changelog/* 一律未動：那是歷史紀錄，記載當時為真的事（docs/README.md:201 那筆 changelog 索引條目同理保留）。

為什麼不需要權限三處同步

權限樹（RolePermissionService）只對應最上層 8 組選單，而整個「系統管理」子樹都是 adminOnly=true、不在權限樹裡——MenuPermissionAlignmentTests.EachGroup_HasEnoughChildPermissions_ForItsSubMenu 對 adminOnly 群組直接 continue 跳過。故 MagicObjectHelper 與 RolePermissionService 皆未動，頂層順序與數量（8 組）亦未變。

已知限制

  • 本次未新增自動化測試：問題與修正都在 CSS 與選單資料層，專案沒有 UI 視覺回歸測試基礎設施；MenuIconTests／MenuPermissionAlignmentTests 只能守住「圖示在白名單」與「位置索引對齊」，守不住「面板會不會被裁掉」。
  • ⚠️ 未執行瀏覽器實測：以下需人工驗收——①收合側邊欄後第二層出現 4 個子分類；②兩個新群組的第三層面板 4 項全部可見可點；③回歸 1.0.44：滑過子分類時第三層仍能正常彈出在第二層框外（沒有被裁）；④縮小視窗高度時第三層應出現垂直捲軸、不得出現水平捲軸。
  • 第三層面板的 top 仍對齊觸發列，max-height 只保證「不超過視窗高度」，並未做視窗感知的重新定位。極矮視窗下面板起點仍可能偏低（此時會出現捲軸而非被裁掉）。純 CSS 無法可靠做到視窗感知定位，需要 JS 或 CSS anchor positioning（瀏覽器支援度不足）。
