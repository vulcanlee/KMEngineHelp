會議欄位擴充與工作／專案進度彙總（1.0.19）

  • 日期：2026/07/20
  • 版本：1.0.18 → 1.0.19
  • 類型：資料模型擴充（雙 migration）＋唯讀計算功能
  • 對應 PRD：專案協作模組強化 PRD 第三階段
  • 代辦清單：專案協作模組強化開發代辦清單

一、會議新增 10 個可空欄位

Meeting 原本只有標題／描述／摘要／與會人員／起訖時間／分類／團隊，缺少實務上最常被問到的會議形式、地點、主持人等資訊。

1.1 五個人工填寫欄位（本階段即可使用）

欄位型別說明
MeetingModestring?會議形式：實體／線上／混合
Locationstring?地點，或線上會議連結
Hoststring?主持人
Recorderstring?紀錄人
Decisionsstring?決議事項

選項常數 MeetingAdapterModel.MeetingModeOptions（比照 MyTasAdapterModel.StatusOptions 的既有慣例），並於 MeetingService.ValidateBusinessRulesAsync 驗證（允許空值，有填才檢查）。

1.2 五個階段四預留欄位（本階段不上表單、不上清單）

欄位型別說明
SourceTranscriptionIdint?來源轉錄紀錄 Id
GeneratedContentRelativePathstring?AI 產生的會議紀錄 Markdown 相對路徑
GeneratedAtDateTime?AI 產生時間
MinutesStatusstring?未產生／轉錄中／轉錄完成／產生中／已產生／失敗
PendingActionItemsJsonstring?AI 待辦草稿 JSON 陣列

一併在本階段建好，讓整個模組只需要一次雙 migration，階段四不必再動資料庫。

雙 provider migration AddMeetingFields：SQLite 20260720035447、SQL Server 20260720035519，兩份皆為 10 個 AddColumn，無 rename／drop／create table。

1.3 清單新增三欄

會議形式、主持人、地點。三欄皆不設 Sortable — Sortable 需在 MeetingService.GetAsync 的排序 if/else 鏈補對應分支，否則點欄位標題不會有反應（靜默失效）。決議事項與紀錄人只在編輯表單。

二、UpdateAsync 的兩個刻意設計（含測試守護）

MeetingService.UpdateAsync 是逐欄複製，不是整包覆寫。這帶來兩個必須明確處理的點：

1. 五個人工欄位必須補進逐欄複製。 漏了就是靜默資料遺失——使用者填了、按存檔、重開就不見了，而且不會有任何錯誤訊息。實作時是先寫測試確認會失敗，才補上複製邏輯的。

2. 五個 AI 欄位刻意「不」複製。 那五個由階段四的背景管線獨立維護；若也放進逐欄複製，使用者只是改個標題存檔，就會把 AI 產出的結果整組清空（paraObject 來自表單，那五欄一律是 null）。

兩點都有測試守護於 KnowledgeExtraction.Tests/MeetingFieldPersistenceTests.cs（5 筆），其中 UpdateAsync_ShouldNotTouchStageFourAiFields 就是把「不可複製 AI 欄位」這條約束固定下來，避免日後有人「順手補齊」而踩雷。

三、SourceTranscriptionId 採軟參照、不做硬 FK

PRD 原本寫「FK → MediaTranscription，Restrict」，實查後改為純 int? 欄位、不建立 FK，理由有三：

  1. 本專案指向 MediaTranscription 的既有做法都是軟參照 — KnowledgeSourceItem 明確註明「以 ItemType＋ItemId 指向，不做硬 FK」；MediaTranscription 自己的版本鏈（PreviousVersionId／SupersededById）也註明「軟參照無 FK」。
  2. 全域刪除政策是 Restrict — BackendDBContext.OnModelCreating 有一段迴圈把所有 FK 設成 Restrict。做成硬 FK 會導致「有會議掛著的轉錄紀錄就刪不掉」，使用者會看到不友善的錯誤。
  3. MediaTranscription 沒有 ICollection<Meeting> 導覽屬性，硬 FK 需額外的 .WithMany() 設定，徒增耦合。

代價：可能出現孤兒 Id（轉錄被刪、會議仍指著）。階段四讀取端須容忍此情況。此外，因為 MediaTranscription 有版本鏈，這個 Id 釘的是特定版本而非「最新版」，階段四若要跟隨最新版需另行解析版本鏈。

四、工作／專案進度彙總（純計算、零 migration）

MyTask 早就有父子關係與 CompletionPercentage，但從來沒有被彙總過（既有的 RecomputeParentDatesAsync 只同步日期）。

4.1 規則

  • 工作進度：有子工作 → 所有子工作 CompletionPercentage 的平均（含 0%，四捨五入取整）；無子工作 → 自身值
  • 專案進度：該專案頂層工作（ParentTaskId == null）的 CompletionPercentage 簡單平均；無工作 → 專案自身值
  • CompletionPercentage 欄位本身完全不動 — 仍是使用者手動維護的值，UpdateAsync 照樣寫入它

0% 一律計入：CompletionPercentage 是非空 int、預設 0，無法區分「未填」與「真的 0%」；未動過的子工作就是 0% 完成，計入才反映真實進度（4 個子工作只完成 1 個 → 25%，而非 100%）。

4.2 實作

新增由服務填入的 adapter 屬性 RolledUpProgress／HasChildren（工作）與 RolledUpProgress／HasTasks（專案），不落地資料庫、不需 migration，因此永遠不會出現「統計值與實際子項不同步」。

效能上完全比照既有 ChildCount 的 N+1 迴避做法：MyTasService 直接把既有的 ChildCount group-by 擴充成同時取回筆數與平均（沒有多開一次查詢）；ProjectService 原本沒有任何 post-map 補值區塊，新增一次 group-by。兩者都是每頁一次查詢，不隨列數增長。

4.3 已知界線（刻意不做）

專案進度取的是頂層工作的自身 CompletionPercentage，不是「頂層工作彙總後的進度」。要做到後者需要兩層 group-by，成本與複雜度不成比例。實務影響：若某頂層工作有子工作，專案會用它的手動值而非其子工作平均。

4.4 顯示方式

未使用 AntDesign <Progress>，沿用全站既有的文字慣例（@context.X%）——實查確認 <Progress> 在本專案從未被使用過，而顯示百分比的既有做法散見於 KnowledgeSourceView、SkillView、ImageRecognitionView、MediaTranscriptionView、DocumentExtractionView 五處，全是模板欄位渲染文字。引入新元件會造成不一致。

進度欄另以小字標示來源（「依子工作自動彙總」／「依工作項目自動彙總」／「手動值」），讓使用者知道數字從哪來。兩個進度欄皆不設 Sortable — 值是查詢後才在記憶體算出來的，資料庫端無從排序。
