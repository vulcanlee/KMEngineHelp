Graph RAG P12：全域作業狀態表 ＋ 待抽取來源（1.0.94 → 1.0.95）

  • 日期：2026-07-28
  • 版本：1.0.94 → 1.0.95
  • 類型：新增功能／維運補強（Graph RAG 第十二階段；雙庫 migration AddGraphJobState）

背景

兩個維運缺口，都是 P3／P6／P7 自陳但一直沒解的：

① 全域圖譜作業不可觀測。 社群摘要重建（P3）與 LLM 別名候選生成（P6）的狀態只活在記憶體單例（GraphCommunityBuildState／GraphAliasBuildState）。而 PipelineJobQueryService 的註解寫得很清楚——一律由 DB 狀態推導，刻意不讀佇列深度。沒有 DB 列，這兩個作業在 /pipeline-jobs 就結構上不可能顯示，自然也不能取消；服務重啟更會靜默丟失重建訊號（P7 記載：「服務重啟仍會靜默丟失重建訊號」）。

② 最需要重抽的來源反而看不到。 P7 把「抽取／重抽三元組」接到知識來源頁，但自陳限制：知識圖譜審核頁是三元組導向的，抽取失敗或抽不出東西的來源因為一條三元組都沒有，完全不會出現在審核清單裡——而那正是最需要重抽的情況。

⚠️ 為什麼要建表（而不是「顯示記憶體狀態就好」）

因為 /pipeline-jobs 的資料來源就是 DB。要讓這兩個作業出現在那裡、能被取消、重啟後能撿回，沒有 DB 列就無解——顯示記憶體旗標只能做到「看得到現在有沒有在跑」，解不掉重啟遺失與無法取消這兩個真問題。

變更

1. 新增 GraphJobState（雙庫 migration AddGraphJobState）

欄位：JobType／Status／ResultCount／ErrorMessage／TriggeredBy／TriggeredByName／StartedAt／CompletedAt／時間戳，加 Status 索引。

刻意無 Teams：與 GraphEntityAlias 一致——全域治理作業、管理員專屬，由呼叫端把關。

2. ⚠️ 刻意不進 PipelineNames

PipelineNames 是 per-record 管線的常數集，配套的是 TryCancel(pipeline, recordId)。硬塞進去會讓 recordId 在這兩個全域作業上失去意義，也會污染 /pipeline-jobs 既有的推導假設。

改以 JobType 字串識別，但仍重用 IPipelineCancellationRegistry——它的鍵本來就只是字串，並不限於 per-record。PipelineJobQueryService.LabelOf／UrlOf 與 PipelineJobCancelService 各加兩個 case。

3. 觸發 → 執行 → 終態的完整鏈路

  • 觸發點（GraphCommunityService.TriggerRebuildAsync／GraphEntityAliasService.TriggerSuggestionAsync）先建 GraphJobState 列再入列，佇列的 PipelineJob.Id 由原本的 0 佔位改為帶真正的列 Id。
  • 在飛判定改以 DB 為準（HasInFlightAsync）——記憶體旗標在服務重啟後會歸零，DB 不會。記憶體旗標保留供審核頁即時輪詢，兩者並存但終態一律以 DB 為準。
  • 背景服務出列後 TryMarkProcessingAsync → 執行 → CompleteAsync 寫終態（已完成／失敗）。

4. 取消的兩段語意（比照各 per-record 管線）

情況作法
處理中TryCancel 發取消權杖，執行中的工作停下來
等待中（或重啟後的孤兒）只改 DB 狀態為「已取消」；真正的略過發生在出列時——TryMarkProcessingAsync 回 false，背景服務直接 continue

背景服務捕捉到「非關機」的 OperationCanceledException 時刻意不覆寫狀態，因為 CancelAsync 已經寫成「已取消」了。

5. 重啟復原（GraphJobRecovery）

兩個背景服務啟動時先跑 RecoverAsync：把殘留的「處理中」改回「等待中」，再把所有未結束的作業重新入列。這才是「重啟不再靜默丟失重建訊號」的實際修法（P3 原本刻意不做復原、P7 記載未動）。

復原失敗只記 log 不拋——不得讓背景服務起不來，否則後續新觸發也跟著失效。

6. /pipeline-jobs 顯示

GetPendingJobsAsync 追加一次查詢。RecordId 放的是 GraphJobState 的列 Id、Teams 恆為 null（全域治理無團隊）、Title 帶觸發者以便判讀。GetSummaryAsync 因為重用同一條清單查詢，「卡片數字＝頁面列數」的既有不變量自動維持（已補測試釘住）。

7. 「待抽取來源」分頁（知識圖譜審核頁第四頁）

GraphTripleService.GetSourcesNeedingExtractionAsync：列出已蒸餾、且滿足下列任一的來源——

  • 該來源沒有任何三元組（抽取沒產出東西）
  • 圖譜狀態為失敗（即使已有三元組，失敗代表這次沒抽完整）

進行中（等待中／處理中）者刻意排除——已經在跑了，不需要再按一次。

leak=0：非管理員只看得到「無團隊(公開)或與角色團隊交集」的來源。重抽按鈕直接呼叫 P7 已補好完整守門的 TriggerExtractionAsync（團隊權控 → 已蒸餾 → LLM 已設定 → 非 in-flight），不在 UI 重複一份守門。

沿用既有 角色_知識圖譜審核 頁權，不新增權限常數（不需動 MagicObjectHelper／RolePermissionService／Menu.json 三處同步）。

已知限制（未來增量）

  • 記憶體旗標（IGraphCommunityBuildState／IGraphAliasBuildState）與 DB 並存：前者供審核頁即時輪詢、後者為權威。多執行個體部署下記憶體旗標只反映本行程，DB 才是全域真相。
  • 復原是整批重新入列，不會續跑到一半的社群重建——社群重建本來就是整批取代、失敗不留半成品，所以重跑是安全的。
  • 「待抽取來源」清單上限 50 筆（take 參數預設），未做分頁。
  • 取消進行中的作業依賴 GraphCommunityBuilder／GraphEntityAliasGenerator 對 CancellationToken 的響應；兩者的 LLM 呼叫之間會檢查，但單次 LLM 呼叫進行中無法立即中斷。
  • 未執行：實際重啟服務驗證復原流程（需部署環境）。單元測試已直接測 GraphJobRecovery.RecoverAsync，但端到端的「重啟後真的續跑」留給部署後驗收。
