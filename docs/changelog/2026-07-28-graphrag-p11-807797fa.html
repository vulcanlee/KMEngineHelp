Graph RAG P11：檢索熱路徑快取（1.0.93 → 1.0.94）

  • 日期：2026-07-28
  • 版本：1.0.93 → 1.0.94
  • 類型：效能改善（Graph RAG 第十一階段；無新表、無 migration、無行為變更）

背景

RetrievalService.SearchGraphAsync 每一次檢索都要跑三個全表查詢：

  1. 全部已核可別名（GraphEntityAlias）
  2. 全部錨頁節點（GraphNode，WikiPageId != 0）
  3. 全部已核可三元組（GraphTriple，且含兩次 join 回 GraphNode 取兩端名稱）

這件事 P4 的 changelog 就記載了（「檢索需載入（ACL 過濾後的）錨頁節點與已核可三元組……大圖時可再優化」），P7 只補了索引沒動作法，P8 又記一次（「P7 只補了索引，快取未做。多跳讓這件事更值得處理」）。三度記載、三度未做，本階段處理掉。

為什麼不是 ICacheService

專案已有 ICacheService（走 IDistributedCache，部署時可能是 Redis）。這裡刻意不用它：

  • 要快取的是已解析的字典與清單（別名對照表、節點列、三元組列），走 IDistributedCache 每次都得序列化往返，Redis 部署下尤其不划算。
  • 這些資料本來就只在本行程的檢索路徑使用，沒有跨行程共享的需求。

因此採行程內單例快照（IGraphRetrievalCache / GraphRetrievalCache），不耦合快取供應商。

⚠️ 紅線：只快取「未套 ACL 的原始列」

快取是全域共用的，鍵不含使用者身分。所以：

  • 快照裡的錨頁節點與三元組一律帶著 Teams 原封不動，載入時不套任何權控。
  • 權控改由 SearchGraphAsync 逐請求在記憶體施加，判定條件與原本的 BuildTeamAccessPredicate 等價（改用 TagStringHelper.IsTeamAccessible），語意不變、只是從 SQL 移到記憶體。
  • 別名表無 Teams（P5 起就是全域治理），是三者中唯一可以直接快取「建好的對照表」的。

若違反這條、把過濾後的結果存進快取，先檢索的人的可見範圍就會被後檢索的人取用。已由兩條雙向測試釘住（管理員先→受限者後、受限者先→管理員後）。

失效

新增 Invalidate()，由所有會改變「已核可別名／節點／已核可三元組」的寫入路徑呼叫：

呼叫點說明
GraphEntityAliasService 的 AddAsync／ApproveAsync／RejectAsync規則刻意訂為「任何一筆別名寫入都失效」，不逐案推敲哪些狀態轉換才影響已核可集合
GraphTripleService 的 ApproveAsync／RejectAsync／UpdateAsync同上；UpdateAsync 還會改兩端節點指向（且可能新建節點）
GraphExtractionProcessor 抽取完成後新三元組是「待審核」不進檢索，但新節點會進錨頁對照

過度失效只是多跑一次載入（這些都是低頻的管理員操作或背景抽取），漏失效卻是最長 5 分鐘的錯誤結果——所以刻意選寬鬆的規則。

另加絕對逾時 300 秒作為安全網：日後有人新增寫入路徑卻忘記呼叫 Invalidate() 時，錯誤最多存活 5 分鐘而不是永遠。

其他實作細節

  • 單飛載入：以 SemaphoreSlim 確保並行請求只有一個真的打 DB。冷啟動時若不擋，N 個並行檢索會同時跑 N 次全表查詢——正是最不該塞爆 DB 的時刻。
  • 不設筆數上限：現況本來就每次請求都在記憶體建出同樣大的物件，快取只是「建一次共用」，峰值配置與 GC 壓力都下降。
  • RetrievalService 的建構式加一個必要參數（不是可選），刻意不留「沒有快取時的第二條路徑」——那條路會沒有測試覆蓋而逐漸與正式路徑分歧。9 處測試建構點一併更新，且一律注入真實的 GraphRetrievalCache 而非 stub。

相容性

沒有任何行為變更：檢索結果、分數、權控判定全部相同，差別只在資料從哪裡來。既有 8 條圖檢索測試（含兩條多跳 leak=0）未改一行即通過。

已知限制（未來增量）

  • ⚠️ 多執行個體部署下失效只影響本行程：若水平擴充成多個 Web 執行個體，A 執行個體核可的別名不會即時反映到 B，由 300 秒絕對逾時兜底。要即時就得改走分散式失效訊號（如 Redis pub/sub），目前規模不需要。
  • 快照是全有全無地重建：核可一筆別名會讓整個快照（含三元組與節點）重載，沒有做細粒度的部分更新。以目前的寫入頻率不值得複雜化。
  • 仍未對 GraphEdge（wiki-link 邊）查詢做快取：它與 BFS 的 frontier 相依，每一跳的條件都不同，不是「全表載入一次」就能解的形狀。
  • 本次未實測大圖下的效能改善幅度（需要具規模的真實資料）。改善的論據是「三個全表查詢由每次變成每 5 分鐘一次」，屬結構性而非量測所得。
