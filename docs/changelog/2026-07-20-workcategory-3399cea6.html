新增「專案分類」（WorkCategory）主檔，與知識庫分類清單脫鉤（1.0.18）

  • 日期：2026/07/20
  • 版本：1.0.17 → 1.0.18
  • 類型：新功能（新資料表＋CRUD 頁＋REST API）＋既有資料自動回填
  • 對應 PRD：專案分類 PRD、專案協作模組強化 PRD 第二階段
  • 代辦清單：專案協作模組強化開發代辦清單

一、變更內容

1.1 新增「專案分類」主檔

專案、工作、會議的「分類」欄位原本共用 Category（分類清單），但那份清單的定位是知識庫主題標籤（8 處在用）。兩種語意混在一起，下拉選單越長越雜。

新增 WorkCategory 實體與 /work-categories 管理頁（欄位與 Category 完全相同：名稱／描述／啟用狀態／建立時間／更新時間），供專案項目、工作項目、會議記錄使用。

雙 provider migration AddWorkCategory：SQLite 20260720031350、SQL Server 20260720031235。兩份皆僅 CreateTable，無 rename／drop。

1.2 分工邊界

清單路由供哪些頁面使用
專案分類（新）/work-categories專案項目、工作項目、會議記錄
分類清單（原有）/categories知識來源、知識瀏覽、Wiki 頁、AI 技能產生器、音訊轉錄、文件萃取、圖片清單、內容清點報表

兩頁各加一行說明文字，提醒使用者用途差異。

1.3 下拉來源切換：只有 5 處

全站共 13 處以 GetAllEnabledNamesAsync() 填充分類下拉。本次只切換這 5 處：

  • Views/Projects/ProjectViewView.razor.cs（工具列篩選 ＋ 內嵌編輯表單，razor 有兩個迴圈）
  • Views/Projects/MyTasViewView.razor.cs
  • Views/Projects/MyTasEditModal.razor.cs
  • Views/Projects/MeetingViewView.razor.cs
  • Views/Projects/MeetingEditModal.razor.cs

其餘 8 處維持吃分類清單（不得誤改）：DocumentExtractionView、ImageRecognitionView、KnowledgeSourceView、KnowledgeWikiView、MediaTranscriptionView、ContentInventoryReportView、SkillView、WikiPageView。

ProjectRelatedRecordsModal 不需要改 — 它（專案清單的「工作與會議」對話窗）完全沒有注入 CategoryService，只注入 MyTasService／MeetingService／ModalService／NotificationService；分類下拉是由它掛載的 MyTasEditModal／MeetingEditModal 各自載入，已被上述兩處涵蓋。記載於此，免得日後有人白找。

1.4 既有紀錄的儲存格式完全未變更

Project／MyTask／Meeting 的 Categories 欄位仍是 TagStringHelper 的 \n 包夾字串（如 "\nA\nB\n"），AutoMapper ForMember 轉換不動，BuildContainsAnyPredicate 精確成員比對不動。本次只換了「哪一張表填充下拉選單」，沒有任何資料轉換。

1.5 既有分類值自動回填

新增 WorkCategoryBootstrapSeeder，掛在 Program.cs 既有的 migration／seeding 區塊內（Database.Migrate() 之後、與預設角色／預設帳號同一個 scope）：

掃三表 Categories（AsNoTracking + Distinct）→ TagStringHelper.ToList 攤平
→ Trim → 濾空白 → 忽略大小寫去重 → 缺的批次新增（IsEnabled = true）
→ 記錄 ScannedCount / InsertedCount
  • 每次啟動都執行（冪等），不用一次性旗標——三個單欄 SELECT DISTINCT 成本可忽略，且能持續吸收「直接改資料庫」或「還原舊備份」帶進來的新值
  • 以名稱（忽略大小寫）判斷，與服務層唯一性檢查一致，絕不會塞進 UI 會判為重複的列
  • 失敗不中斷啟動：try/catch ＋ LogError（依日誌鐵則不得靜默）
  • 採同步實作以配合該啟動區塊全程同步的既有風格，避免 sync-over-async

1.6 REST API

WorkCategoryController 完整克隆 CategoryController：search／get／post／put／delete，名稱重複回 409 Conflict，排序參數字串與分類清單 API 一致。

1.7 選單與權限

MagicObjectHelper.角色_專案分類 = "專案分類"；RolePermissionService 附加於「資料定義」群組最末端；Menu.json 資料定義 subMenu 最末端（id 65、圖示 label）。三處以位置索引對應，本次僅在既有群組尾端追加、不動頂層結構，1.0.17 新增的 MenuPermissionAlignmentTests 維持全綠。

二、已知技術債（本次不處理）

MyTask.Category（單值、Required、自由輸入文字）與多值 Categories 並存，目前供關鍵字搜尋、排序及對外 API 精確過濾使用。它是非空欄位且有對外 API 契約，改動＝migration ＋ API 破壞性變更 ＋ 回填每一列，且用途與多值標籤本就不同。若要退場應另開 PRD。

實作過程中的一個陷阱（記錄備忘）

首次產生 SQLite migration 時加了 --no-build，EF 使用了尚未包含 WorkCategory 的舊組件，產出一份 Up()／Down() 皆為空的 migration，且 BackendDBContextModelSnapshot.cs 未被更新——建置與測試都不會發現（測試 fixture 走 EnsureCreatedAsync()，依 model snapshot 建表而非跑 migration）。已 dotnet ef migrations remove 後不帶 --no-build 重新產生。日後產 migration 一律不要用 --no-build。
