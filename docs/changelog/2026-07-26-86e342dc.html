移除健康檢查的「開發預設金鑰」判定（1.0.69）

  • 日期：2026/07/26
  • 版本：1.0.68 → 1.0.69
  • 類型：功能移除（依使用者決定）
  • 影響範圍：/system-health 的「身分驗證」檢查項（權重 15）

一、起因

1.0.68 部署到正式環境後站台正常啟動（移除 StartupSafetyValidator 生效），但 /system-health 的「身分驗證」項顯示異常：

Cookie scheme：True；JWT bearer：True；Issuer：已設定；Audience：已設定；SigningKey 長度：202。
Cookie/JWT 設定不完整，或 Production 仍使用開發用 JWT key。

診斷（由畫面資訊即可推定）

原本的紅燈條件有四個，畫面顯示前三個都通過（Cookie=True、JWT=True、Issuer／Audience 已設定、長度 202 ≥ 32），所以唯一成立的只剩：

usesDevelopmentKeyInProduction = environment.IsProduction()
    && UnsafeDefaults.IsUnsafeSigningKey(jwtSettings.SigningKey);   // 金鑰以 "DevelopmentOnly-" 開頭

而 202 ≠ 倉庫預設的 94——金鑰確實被改過，但新值仍以 DevelopmentOnly- 開頭（推測是在預設值後面接了東西，而非整個換掉）。

順帶回答：為什麼本機 Development 不會警告

該判定被 environment.IsProduction() 擋住，Development 環境下恆為 false，所以永遠不會紅——這是刻意設計，開發機本來就該用開發金鑰。

另外兩邊的值其實不同：Development 顯示 SigningKey 長度：94（正好是倉庫預設值），Production 顯示 202。不過即使兩邊完全相同，Development 也一樣不會警告。

二、移除內容

項目處置
SystemHealthService.CheckAuthentication 的 usesDevelopmentKeyInProduction刪除；status 改為只看 hasCookie && hasJwt && hasRequiredJwtSettings
失敗訊息「Cookie/JWT 設定不完整，或 Production 仍使用開發用 JWT key。」→ 只保留前半句
Web/Configuration/UnsafeDefaults.cs刪除（上面那行是它唯一的生產端消費者）
Tests/UnsafeDefaultsTests.cs刪除（15 個測試）

SystemHealthService 的 environment 欄位保留——:168（環境名稱）、:177（Swagger）、:387（安全設定 productionRisk）仍在使用。using KnowledgeExtraction.Web.Configuration; 也保留（SwaggerSettings／CacheSettings 共 8 處在用）。

檢查項總數維持 24 項，只是「身分驗證」這一項的判定條件變少。

三、移除後的實際狀態

系統已經沒有任何地方會提示「Production 正在用開發預設金鑰或預設密碼」。

三道防線在三次變更中依序拆除：

版本拆除的原因
1.0.68啟動安全檢查（StartupSafetyValidator）兩度擋住正式部署（HTTP 500.30）
1.0.68緊急跨過開關正解比跨過更快，逃生口反而是容易被遺忘的後門
1.0.69健康檢查的金鑰內容判定本次

僅剩的補償方式是人工核對：部署後檢查 appsettings.Production.json／web.config 的實際值——金鑰只要不以 DevelopmentOnly- 開頭、密碼不是 support／1qaz@WSX 即可。已寫入 planning/08 backlog 與部署 SOP。

若日後想恢復偵測，建議只做提示、不要擋啟動——這正是 1.0.68／1.0.69 兩次移除的教訓。

四、驗證

項目結果
dotnet test653 通過 / 0 失敗（668 − 15）
殘留參照UnsafeDefaults 在 src/ 與 docs/（排除 changelog／archive）0 命中
Production 啟動成功，/health/ready 回 200

「身分驗證」項轉綠未經畫面目視確認——/system-health 需管理員登入，curl 只拿得到 Blazor 外殼。但推論是確定的：使用者的 Development 截圖已顯示「正常」，且該環境的 Cookie／JWT／Issuer／Audience 條件與 Production 完全相同（金鑰長度 94 亦 ≥32）。Production 唯一多出來的就是本次移除的判定，移除後兩者判定條件已完全一致。

五、文件同步

  • features/系統健康監控.md：「身分驗證」項改為只描述 Cookie/JWT scheme、Issuer/Audience、金鑰長度，並註明不檢查金鑰內容。
  • operations/全新機器部署SOP.md：移除「上線後可到 /system-health 確認」的建議，改為明確寫出沒有任何自動偵測。
  • security/認證授權與權限機制.md：移除「唯一的提示是 /system-health」，改為「系統已無任何自動提示」。
  • planning/08：補償措施改寫為人工核對，並寫明核對標準。
