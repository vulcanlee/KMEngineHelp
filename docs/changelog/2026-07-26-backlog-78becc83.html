權限常數金絲雀測試，並補回兩筆「宣稱已記入 backlog 但查無此項」的待辦（1.0.74→1.0.75）

  • 日期：2026-07-26
  • 版本：1.0.74 → 1.0.75
  • 類型：測試補強（資安守門）＋流程風險修正

需求

一、現有測試攔不住「改權限常數值」這條靜默災難路徑

MagicObjectHelper 的 29 個 角色_* 常數，它們的值會寫進每個角色的 RoleView.TabViewJson。改值以後，既有角色資料列裡存的還是舊字串，SetPermissionInput 的比對全部 miss → 除 admin 外所有角色的選單全部消失。

問題在於沒有任何機制攔得住。MenuPermissionAlignmentTests 看起來像在守護這件事，但：

  • expected 來自它自己的對照表（值取自 MagicObjectHelper 常數）
  • actual 來自 RolePermissionService.GetRoleListPermissionAllName()（也是同一批常數）

兩邊同源。 改常數值時兩邊會一起變 → 測試全綠、dotnet build 成功、/system-health 全綠，然後部署炸權限。該測試檔的註解只是「口頭」寫著不要改常數值，沒有任何可執行的守護。

這件事現在特別要緊：下一批（1.0.76）要動 55 處實體名詞字串，而 7 個 角色_XXX 識別字在文字上包含要被取代的舊名（角色_工作項目、角色_圖片清單、角色_分類清單、角色_團隊清單、角色_提示詞清單、角色_清洗設定檔、角色_知識來源管理清單）。跨檔全域取代會波及它們——那會編譯失敗（好結果），但若有人「順手改識別字讓它編過」，常數值就會一起被改掉。

二、兩筆 changelog 宣稱「已記入 backlog」，實際查無此項

出處宣稱實情
1.0.70 changelog 第 45 行實體名詞約 30 處「已記入 backlog 另批處理，理由見優化建議清單」grep -rc "實體名詞" docs/planning/ → 0 命中
1.0.56 changelog 第 57 行「已知缺口：5 支 Service 仍無預設排序分支」planning/08 內查無此項

這是流程風險，不只是文件缺漏：兩份 changelog 都寫了「已記入 backlog」，讀者（含後續盤點者）會信任那句話而不去核對，於是這兩項實際上從未進入任何待辦清單。若不修，下一次盤點會再漏掉同樣的東西。

變更

新增 Tests/PermissionConstantCanaryTests.cs

把 29 個常數的值硬編在測試檔裡，作為唯一不依賴 MagicObjectHelper 的外部參考點。三條測試：

  1. EveryPermissionConstant_KeepsItsPersistedValue —— 每個常數值必須等於硬編值。
  2. PermissionConstantSet_MatchesCanaryTable —— 常數集合不得增減而本表未同步（新增權限時必須來補一筆）。
  3. PermissionTree_UsesOnlyCanaryValues —— 權限樹用到的每個字串都必須落在本表值域內，防止有人在 RolePermissionService 直接打裸字串繞過常數。

⚠️ 硬編表包含兩個歷史遺留的尾隨空白，必須照抄不可清掉：["角色_角色管理"] = "角色管理 "、["角色_登出"] = "登出 "。這兩個值也在 DB 裡，「順手把多餘空白清掉」同樣會掉權限。表格是用腳本從原始碼萃取後寫入的（29 筆逐字，避免手動轉錄出錯），寫入後即為靜態文字、不再讀取原始碼。

測試註解明寫「這條紅了不要改測試，先確認是不是誤改了常數值；只有在確實要新增權限時才來本表補一筆」。

補回 planning/08 的兩筆待辦

新增一節「由 changelog 追蹤鏈補漏（2026-07-26，1.0.75）」，比照該檔既有的分節寫法，逐條標明出處 changelog 與行號，並記下這件事本身的流程教訓：日後 changelog 若要寫「已記入 backlog」，請同時在該檔補上條目再 commit。

其中「實體名詞」那項一併寫進下一批要用的三個陷阱（角色_XXX 前綴包含、會議紀錄（紀）99 處不可動、MeetingService.cs:626 會落地到資料列、LlmPromptDefaults.cs:59 是 LLM 提示詞），讓下一批不必重新查證。「5 支預設排序」那項標為已於 1.0.73 修正，並更正原記錄的錯誤歸因（真正的洞在內層 SortDescending == null，不是外層缺 else）。
