系統監控與健康檢查指南

說明「系統健康監控」頁與部署探針端點的用途、如何看懂燈號與各檢查項、常見紅/黃項的對策，以及同群組的「資料一致性巡檢」「日誌下載」「待處理背景工作」怎麼用——讓管理員快速判斷系統與各依賴是否正常。

  • 文件用途：說明「系統健康監控」頁與部署探針端點的用途、如何看懂燈號與各檢查項、常見紅/黃項的對策，以及同群組的「資料一致性巡檢」「日誌下載」「待處理背景工作」怎麼用——讓管理員快速判斷系統與各依賴是否正常。

  • 建立日期：2026/06/26

一、為什麼需要

系統依賴多個外部元件（資料庫、第三方工具 ffmpeg/yt-dlp/markitdown/Node、OpenAI 金鑰、檔案目錄權限…）。任何一項出問題，往往要等使用者操作到該功能才報錯。健康檢查把這些一次集中體檢，讓你在上線前或出狀況時，一眼看出哪裡紅燈。

二、系統健康監控 /system-health（僅管理員）

進入路徑：左側選單「系統管理 → 系統監控 → 系統健康監控」（三層選單，要多點一層）。畫面標題是「系統健康監控」。

頁面由三個部分組成：

  1. 整體健康：紅/黃/綠燈號 ＋ 健康分數（0–100）＋ 最後檢查時間。
  2. ≥ 90 綠：系統健康。
  3. 70–89 黃：可運作，有項目需關注。
  4. < 70 紅：健康程度不足，應立即檢查。

分數為各項加權平均（正常＝滿分、警示＝半分、異常＝0）。24 項的權重合計為 232，其中「資料庫」權重最高（25），其次是日誌與身分驗證（各 15）、向量索引涵蓋率（15）。

  1. 檢查項目（共 24 項）：畫面上是單一扁平清單（不是分成幾個區塊顯示），每項會標註它的分類與權重，並顯示紅/黃/綠、名稱、狀態文字、證據（實際檢查到的值）與失敗訊息。下面依分類整理，方便你理解每項在檢查什麼：
  2. 基礎系統（9 項）：網站/應用程式（環境/版本/運作時間）、API（Controller 數/Swagger）、資料庫（Provider/連線/待套用 migration 數）、資料庫大小與資料量（1.0.13 新增，資訊型：SQLite 檔案大小＋知識來源/知識頁/向量/聊天紀錄/Token 用量列數，恆為正常）、日誌（NLog 目錄/今日檔）、身分驗證（Cookie/JWT 設定；1.0.72 起 Production 下另檢查是否沿用開發預設金鑰／密碼，命中為警示黃燈）、檔案系統（6 個關鍵目錄存在且可寫）、主機資源（記憶體/磁碟空間）、安全設定（Production 下 Swagger/CORS/錯誤詳情）。
  3. 語音轉文字工具（5 項）：ffmpeg、yt-dlp、markitdown、Node.js、抖音助手腳本（路徑與版本；抖音助手為選用，未設為警示）。
  4. 語音轉文字設定（2 項）：OpenAI API 設定（缺 ApiKey 為異常）、轉錄儲存目錄（存在且可寫）。
  5. 知識庫 RAG（1 項）：向量索引涵蓋率——統計「已清洗來源」中已建立向量索引的比例；未設定嵌入為警示，有可索引來源但索引為空（chunk=0）為異常（AI 知識問答將一律查無依據）。
  6. 基礎設施與整合（7 項；5 項 1.0.11 新增、2 項 1.0.13 新增）：
  7. MCP Server——/mcp 端點、McpAccess policy、McpApiKey scheme 是否就緒＋啟用中金鑰數；0 把啟用金鑰為警示（外部無狀態 Agent 無法用 X-API-Key，JWT/Cookie 仍可），policy/scheme/端點缺失為異常。
  8. 分散式快取——Memory 直接正常；Redis 以寫入/回讀一筆 ping 實測連線，失敗為異常。
  9. AI 生成/嵌入 Provider——依 Cloud/Local 分流檢查生成與嵌入端點設定是否齊備（缺 ApiKey 或地端缺 BaseUrl/模型為異常）。
  10. RAG 檢索設定——權重與門檻合理性（權重和非 1 為警示、門檻越界為異常；檢查 appsettings 值）。
  11. 背景管線——八條匯入/處理背景服務（含 1.0.84 起的三元組抽取），加上 1.0.72 納入的 2 支寫入服務（用量寫入、進度寫入），是否都已註冊（缺任一為異常；僅檢查註冊，未偵測卡死或佇列積壓）。
  12. 大語言模型可用性（1.0.13 新增）——實際呼叫一次主生成模型（極小提示詞、8 秒逾時）：有回應為正常（證據含模型/耗時/回應長度）、逾時或呼叫失敗為異常、未設定端點為警示（略過實呼叫）。每次進頁會產生一次微量 LLM 呼叫，用量以作業別「健康檢查」記錄於 /token-usage，統計時可篩選排除。
  13. 嵌入端點可用性（1.0.13 新增）——實際嵌入一段探針文字（8 秒逾時）：成功回報向量維度（與設定不一致為警示）、逾時或失敗為異常、未設定為警示。與 LLM 檢查同樣以「健康檢查」作業別記錄用量。
  1. 日誌尾端：最後 100 筆 NLog 紀錄與日誌檔路徑，方便就地排查。

三、部署探針端點（給容器/負載平衡器）

供 Kubernetes、反向代理或監控系統做存活/就緒探測（不含詳細診斷，回應精簡）：

  • /health/live：liveness（程式是否活著）。
  • /health/ready：readiness（是否可服務；包含資料庫連線檢查）。

項目典型狀況對策

檔案系統某關鍵目錄不存在或不可寫確認 ExternalFileSystem.* 路徑存在且程式有寫入權限

背景管線八條背景服務或 2 支寫入服務缺任一（紅）屬程式註冊問題，非設定可解；注意此項只檢查「有沒有註冊」，不會偵測卡死或佇列積壓 —— 管線卡住時這一項仍是綠燈，要看各功能頁的狀態欄。1.0.72 起把「用量寫入」「進度寫入」兩支也納入：前者沒起來會讓 Token 用量默默不再記錄（統計報表跟著失準且無錯誤訊息）
身分驗證Production 沿用開發預設金鑰或 support 預設密碼（黃）1.0.72 新增。證據列會標出是金鑰還是密碼。這不是故障、不影響站台運作，但代表任何看得到原始碼的人都能偽造 token —— 請依《正式部署與安全檢查清單》更換後重啟。非 Production 不會亮此燈

四之二、資料一致性巡檢 /data-consistency（僅管理員）

進入路徑：系統管理 → 診斷與日誌 → 資料一致性巡檢。

與健康檢查的分工：健康檢查看的是「系統與依賴還活著嗎」；這一頁看的是「資料本身有沒有前後不一致」。兩者互補，健康檢查全綠時這頁仍可能有待處理項目。

畫面說明文字（逐字）：

本頁僅管理員可見，統計為全庫。列出「孤兒成員」（引用的素材已不存在）、「過時來源」（成員異動或素材編修後尚未重跑清洗）與「低比值來源」（清洗後內容相對彙整前明顯偏小，可能曾被模型輸出上限截斷）。

三顆按鈕：

按鈕作用停用條件
重新整理重跑巡檢—
清除所有孤兒成員移除所有失效參照，並把所屬來源標記為過時孤兒數為 0 時不可按
重新清洗所有過時來源把所有過時來源逐一排入重新清洗（背景處理）過時數為 0 時不可按

三個區塊（1.0.116 起）：

  • 孤兒成員（N）：欄位為 所屬知識來源、素材型別、素材 Id、成員列 Id。沒有時顯示「沒有孤兒成員，資料一致。」
  • 過時來源（N）：欄位為 標題、清洗狀態、更新時間、操作（單筆「重新清洗」）。沒有時顯示「沒有過時來源。」
  • 低比值來源（N）（1.0.116 新增）：欄位為 標題、比值（預設由小到大排序）、彙整量（估計）、清洗後、清洗時間、操作（單筆「重新清洗」）。沒有時顯示「沒有低比值來源。」

低比值來源是什麼、為什麼要有這一項

清洗後的內容應該與彙整前同一量級（去重會縮，但不會縮到只剩零頭）。比值明顯偏低，常見原因是內容曾被模型的輸出上限截斷。

1.0.112 起清洗被截斷會直接失敗或在清洗結果留 > 註記：；但該版之前清洗的資料完全沒有留下痕跡——狀態是「已清洗」、信心分數可能還很高。唯一看得出端倪的就是這個比值。這一項的用途就是把那些舊資料自動指認出來，取代人工逐筆稽核。

要注意說明
⚠️ 這是提示，不是判決內容本來就高度重複的素材（大量制式表單、範本化工單）合理地會有很低的比值。那是誤報
最快的處置是「重新清洗」1.0.112 起若真的被截斷，遮罩會直接失敗並說明原因——一次就知道
彙整量是估計值只讀檔案大小、不讀內容，所以「檔案只含空白字元」會被算成可用
門檻可設定SystemSettings.Cleaning.CleanedRatioWarnBelow，預設 0.30；0 或負數＝停用這項檢查。改設定需重啟
這一項的成本最高要對每一筆已清洗來源量測其成員檔案大小（每筆數次檔案查詢）。因為是「按下去才跑的巡檢」所以可接受，但來源很多時這一頁會比以前慢；未清洗的來源完全不碰

兩個確認訊息（逐字，動手前先讀懂）：

  • 清除孤兒：將移除所有『素材已不存在』的成員參照，並把其所屬知識來源標記為『內容已過時』（提醒你重跑清洗）。此動作僅移除失效參照，不影響仍存在的素材。
  • 重新清洗全部：將對所有『內容已過時』的知識來源逐一排入重新清洗（背景處理）。清洗完成後可視需要再蒸餾與建立索引。

建議處理順序：先「清除孤兒成員」（移掉指向不存在素材的死參照）→ 再「重新清洗所有過時來源」→ 視需要蒸餾與建立索引。

孤兒是怎麼來的？ 知識來源的成員是軟參照（記型別＋Id、沒有外鍵），所以素材被刪掉時成員列不會自動消失。系統在刪除素材時會主動清理，但如果曾直接改資料庫、還原舊備份，或早期版本留下的資料，就可能殘留孤兒。

四之三、日誌下載 /log-download（僅管理員）

進入路徑：系統管理 → 診斷與日誌 → 日誌下載。

健康監控頁底只看得到最後 100 筆日誌；要追一段時間的完整脈絡就用這一頁，它會把區間內的日誌逐筆過濾、依時間合併成單一 .log 再以 zip 封裝下載。

操作：

  1. （可選）從「快速區間」下拉挑一個：最近10分鐘／最近30分鐘／最近1小時／最近2小時／最近3小時。選了會以現在時間回推填入起訖，仍可手動微調。
  2. 或直接填「起始時間」「結束時間」（可選到時分秒）。進頁時預設是「最近一小時」。
  3. 按「下載」。

限制（重要）：

項目值
區間上限31 天（超過會被擋，訊息 時間區間過長，請限制在 31 天內。）
輸出大小上限200 MB（超過訊息 選取範圍的日誌量過大，請縮小時間區間。）
日誌保留期NLog 每日輪替、保留 30 天

其他錯誤訊息：未選時間 請選擇起始與結束時間。；起訖顛倒 起始時間不可晚於結束時間。；非管理員 您沒有權限下載系統日誌。；伺服器未設路徑 NLog:BasePath 未設定。

區間內沒有任何資料時，仍會下載一個空的日誌檔（不是錯誤）——這本身也是資訊：代表那段時間確實沒有符合的紀錄。

四之四、待處理背景工作 /pipeline-jobs（僅管理員，1.0.78 新增）

進入路徑：系統管理 → 系統監控 → 待處理背景工作。首頁管理者專區第五張卡也可直達。

與「背景管線」健康項的分工（兩者常被混淆）：

看什麼答得出什麼問題
/system-health 的「背景管線」項8 條管線 ＋ 2 支寫入服務有沒有註冊／實例化「管線服務是不是根本沒起來？」
本頁每條管線目前實際有幾筆在等、幾筆在跑「東西為什麼還沒好？是排在後面，還是卡住了？」

服務都註冊了（健康項綠燈）但使用者覺得慢，答案通常在本頁——前面排了一長串。

列出的內容：8 條管線「等待中／處理中」的工作（1.0.84 起新增「三元組抽取」，即知識圖譜的實體關係抽取），每 5 秒自動更新。同一筆知識來源最多出現四列（清洗／蒸餾／索引／三元組抽取是同一張表的四個階段）。

數字取自資料庫狀態，不是佇列長度。佇列是記憶體 Channel、讀取即消耗、無法列舉；而且佇列長度與實際狀態必然有落差（取出瞬間、取消之後、重啟之後都會不一致）。所以首頁卡片的數字永遠等於本頁的列數。

取消：兩種狀態都能取消。「等待中／排隊中」是把狀態改成「已取消」，背景服務之後取出該筆時會檢查狀態並跳過；「處理中／產生中」是對正在執行的工作發出取消訊號中斷它。兩者都不刪紀錄，取消後可到來源頁重新觸發。

沒有「全部取消」是刻意的：每條管線同時只處理一筆，全系統最多同時 8 筆在跑，批次能省的極少；而批次會放大「處理中」取消的競態窗口。

知識圖譜的兩項「全域單例」作業（1.0.95 起）

除了上述 8 條 per-record 管線，本頁另會列出知識圖譜的兩項全域作業：

作業誰觸發成本
社群摘要重建管理員在「知識圖譜審核」頁頂按「重建社群摘要」每個社群一次 LLM（群數上限 GraphMaxCommunities，預設 50）
LLM 別名建議管理員在「知識圖譜審核 → 實體合併」按「LLM 自動建議別名」一次 LLM（送出的實體名上限 GraphAliasNameCap，預設 300）
  • 它們不屬於 8 條管線（PipelineNames）：因為是全域的、不對應任何單一紀錄，無法掛在某筆資料的狀態欄上，所以另以獨立的作業狀態表（GraphJobState）記錄，本頁一併呈現。
  • 一樣可取消，服務重啟後未完成的作業會被撿回。
  • ⚠️ 取消不是立刻停：單次 LLM 呼叫進行中無法中斷，取消只在呼叫之間生效——按了取消卻看到它還在跑幾十秒是正常的。
  • ⚠️ 多台機器部署時，記憶體中的「正在建置」旗標只反映本機，本頁（資料庫）才是全域真相。

圖譜的抽取狀態機、成本與參數見 知識圖譜（Graph RAG）使用指南 §五。

五、建議的使用時機

  • 上線前：開 /system-health 確認整體綠燈、無紅項，再開放使用。
  • 出狀況時：先看健康頁找紅/黃項與證據 → 看頁底最後 100 筆日誌 → 不夠就到 /log-download 撈該時段完整日誌。
  • 例行巡檢：定期查看，特別是換機器、改設定、更新工具版本後；順手看一下 /data-consistency 有沒有累積孤兒/過時來源。
  • 改過素材或直接動過資料庫之後：一定要看 /data-consistency。
  • 自動化監控：用 /health/ready／/health/live 接你的監控/負載平衡器。

六、常見問題（FAQ）

問題說明
進不了 /system-health僅管理員可見；用管理員帳號登入。
全綠但某功能仍失敗健康檢查涵蓋常見依賴，仍可能有未涵蓋的執行期問題；看該功能錯誤訊息與日誌。
抖音助手紅/黃要不要理它是選用項；不轉錄抖音可不處理。
探針端點看不到細節/health/live、/health/ready 刻意精簡；詳細診斷看 /system-health。
找不到「系統健康檢查」頁名是「系統健康監控」，且在三層選單下：系統管理 → 系統監控 → 系統健康監控。
背景管線綠燈但功能卡住該項只檢查服務有沒有註冊，不偵測卡死或佇列積壓。要看實際積壓請開 /pipeline-jobs（待處理背景工作）——那頁列出 8 條管線目前等待中／處理中的每一筆；另可看各功能頁的狀態欄與 /log-download 的日誌。
RAG 檢索設定顯示的值與實際不符該項讀 appsettings.json；/rag-diagnostics 的熱套用覆寫會蓋掉生效值。以 /rag-diagnostics 顯示的為準。
健康分數被某項拉低但那項我不需要警示（黃）只扣一半權重。選用項（抖音助手、MCP 金鑰數為 0）通常是黃燈，可接受；不必為了衝分數硬補。
按了「重建社群摘要」，要去哪看進度/pipeline-jobs（待處理背景工作）。它與 8 條 per-record 管線並列，但屬全域單例作業，狀態存在獨立的作業狀態表。
取消了圖譜作業，為什麼它還在跑單次 LLM 呼叫進行中無法中斷，取消只在呼叫之間生效。社群摘要重建是「每群一次 LLM」，所以要等當前那一群跑完才會真正停。
三元組抽取一直是「處理中」先看該來源的錯誤訊息，再到 /system-health 確認「大語言模型可用性」。服務重啟時殘留的「處理中」會自動改回「等待中」重新排程，不會永久卡住。
日誌下載按了沒反應/檔案很小先確認區間有資料；區間內無紀錄會下載空的日誌檔。超過 31 天或 200MB 會被擋並顯示訊息。
