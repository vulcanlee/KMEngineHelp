一、檢索品質評測在做什麼？（為什麼需要）

一句話：它是知識庫「檢索品質」的單元測試，外加「權控合規」的回歸守門。

你準備一批「評測題庫」：每筆是一個問句，加上「這個問題理應命中哪些知識來源、（可選）理應命中哪些章節、以及要用什麼身分去問」。按「評測」時，系統用目前的混合檢索把問句打進整個知識庫，再把實際命中結果和你的期望逐項比對，算出分數（Precision@k、Recall@k、NDCG@k、MRR、出處正確率、越權洩漏、檢索延遲）並彙整成儀表板。

評測用哪些紀錄？

  • 評的是你建立的「問句樣本」（在 /rag-evaluation 新增的那些紀錄：問句＋期望命中來源／錨點＋模擬團隊／管理員）。「評測此筆」＝該筆問句；「評測全部」＝目前頁面所有問句樣本。
  • 檢索打的是「整個已索引知識庫」：把問句送進混合檢索，比對的是所有已索引內容（向量 chunk），並依該樣本模擬的團隊權限（評測團隊／模擬管理員）過濾。不是某一筆來源、也不是「未索引的知識來源加工列」——而是「全部已索引內容（在模擬權限範圍內）」。所以未經「清洗 → 蒸餾 → 索引」的來源不會被檢索到（見 §二前提）。
  • 不經 LLM 生成：評測是純檢索品質量化（找得到／找得準／不外洩／夠快），不需要 LLM 產生答案。

對系統有沒有影響？

檢索品質評測是量測／唯讀工具：它只把分數寫回該問句樣本的指標欄位，不會改變向量索引、不影響使用者實際的AI 知識問答／搜尋結果。沒有任何 檢索品質評測樣本時，AI 知識問答照常運作、結果一樣——它的價值在於把「檢索品質與權控合規」變成可量化、可回歸的數字（與清洗品質評測管上游清洗對稱）。

與「清洗品質評測」的分工（互補、不可互相取代）

清洗品質評測 /golden-samples檢索品質評測 /rag-evaluation
把關位置上游：清洗品質下游：檢索品質
量什麼遮罩召回、必保留、分類 F1、摘要涵蓋找得到/找得對、出處正確、不外洩、夠快
對應問題「內容清乾淨了嗎？」「問得到、答得準、不越權嗎？」

兩者串起來＝「清洗 → 檢索」完整品質把關鏈（設計規格 §11.2）。

為什麼一定要有它

  • 檢索品質會「悄悄」變動：換嵌入模型、調整切塊參數、調融合權重，都可能讓「找得到/找得準」變好或變差，但肉眼看不出來。評測集把它變成可比較的數字。
  • 越權洩漏是資安紅線：知識庫跨來源檢索，最怕「非授權團隊內容被檢索出來」。檢索品質評測用受限身分去問，把越權命中量化成一個必須為 0 的指標，當回歸守門。
  • 防回歸：每次調整後重跑，立刻知道有沒有變更糟，而不是上線後才發現。

二、開始前的前提（必讀）

  1. 評測打的是「真實索引」：檢索品質評測檢索的是已建立的向量索引，所以要先有「已清洗 → 已蒸餾 → 已索引」的知識來源。前置設定（尤其嵌入端點）與完整流程見 PoC 執行與驗收指南。
  2. ⚠ 未設定嵌入時，檢索退化為關鍵字比對（非正式語意檢索），分數不代表正式品質；正式評測前請先設妥嵌入。
  3. 相關性以「知識來源標題」為準：期望命中用知識來源的標題標註（不是 chunk 編號）——因為重建索引後 chunk 會變、標題不會，這樣評測樣本才穩定、可長期回歸。

三、新增一筆 檢索品質評測樣本：各欄位用途與例子

在 /rag-evaluation 按「新增」，表單欄位如下（清單型欄位每行一項）：

欄位用途（影響哪個指標）例子
標題樣本辨識名稱「員工健檢福利」「客服退款流程（人資看不到）」
問句（Query）送進混合檢索的問題本身「入職滿三年的員工可以享有哪些健康檢查福利？」
期望命中來源（ExpectedSourceTitles）相關性 ground truth；算 Precision/Recall/NDCG/MRR。每行一個知識來源標題，須與「知識來源加工」的標題完全一致員工手冊、福利制度SOP
期望錨點（ExpectedAnchors）選填；填了則出處正確率改以命中的章節/條款（AnchorRef）比對第三章 健康檢查、第 12 條
模擬團隊（EvalTeams）評測時模擬使用者所屬團隊；留空＝公開使用者。用於越權洩漏驗證人資（每行一個團隊名）
模擬管理員（EvalIsAdmin）勾選＝以管理員身分評測（不受團隊權控、看得到全部）品質樣本勾選；資安樣本不勾

四、操作步驟（頁面各功能）

進入頁面：左側選單「知識庫 → 檢索品質評測」（路由 /rag-evaluation）。需具備 RAG評測 頁面權限（於「角色管理」勾選）。

工具列：

  • 新增：建立一筆評測樣本（見第三節）。
  • 重新整理：重載清單。
  • 載入種子：一鍵帶入範本樣本。按鈕常駐顯示；若清單已有樣本，按下去不會重複載入，會回覆「已有 RAG 評測樣本，未載入種子。」
  • 評測全部：對目前頁面所有樣本逐筆評測。
  • 設為基線：把當前指標存成回歸基準。在還沒有任何「已評測」樣本前，這顆是不能按的（服務端也會擋，回覆「尚無已評測樣本，無法設為基線」）。基線只保留一份（重新設定即覆蓋），並會連同當時的 7 個檢索參數一起快照。
  • 搜尋：依標題/問句關鍵字過濾。

單筆操作（每列右側）：

  • 評測此筆：用該樣本的問句與模擬身分跑一次檢索並計分。
  • 檢視明細：看該筆最近一次評測的完整指標 JSON。
  • 修改 / 刪除：編輯或移除樣本。

儀表板（有已評測樣本時顯示）：已評測筆數、平均 Precision@k / Recall@k / NDCG@k / MRR、平均出處正確率、越權洩漏總數（>0 會以紅色醒目示警）、平均檢索延遲。

設為基線與前後比較（EVAL-1）：

  • 設為基線：在基線區塊輸入標籤（留空自動以時間命名）後按「設為基線」，會把目前的整體彙總凍結成一份基線，並一併快照產生這份基線的檢索參數與門檻（TopK／CandidateTopK／融合權重／MinScore／Reject／LowConf）。基線為單一份（再次設定即覆寫）。
  • 目前 vs 基線：設過基線後，頁面顯示逐指標的「目前值／基線值／差異」；差異以顏色標示進步（綠）／退步（紅）（越權洩漏與延遲以「越低越好」判定）。
  • 典型用法（調參—量測閉環）：評測全部 → 設為基線 → 到 /rag-diagnostics 調整查詢期檢索參數（見診斷手冊 §五）→ 回本頁重跑「評測全部」→ 看差異判斷這次調整是變好還是變差。

清單表格欄位：標題、問句、期望來源數、P@k、R@k、NDCG@k、MRR、出處正確率、越權洩漏、延遲(ms)、最近評測時間。

五、看懂指標

指標意思怎樣算好
Precision@k回傳命中中「屬於期望來源」的比例越高越好（雜訊少）
Recall@k期望來源中「有被檢索到」的比例越高越好（沒漏）
NDCG@k相關命中是否排在前面（名次加權）越高越好（好的排前面）
MRR第一個相關命中的名次倒數（第 1 名＝1、第 2 名＝0.5…）越高越好（第一筆就對）
出處正確率有填期望錨點時＝命中的 AnchorRef 對中比例；否則＝命中來源標題相關比例越高越好（引用對章節）
越權洩漏命中中「該身分不該看到」的筆數必須為 0（資安守門）
檢索延遲(ms)本次檢索耗時越低越好（在可接受範圍）

k 即該次實際回傳的命中數（受 Retrieval.TopK 限制）。⚠ TopK 的生效值可能不是 appsettings.json 裡的那個 —— 它可以在 /rag-diagnostics 熱套用覆寫。比較不同時間的評測結果前，先確認 TopK 有沒有被改過，否則分數差異可能來自參數而非知識品質。

長期趨勢看報表：本頁是「逐筆樣本的評測台」；若要看整體區間趨勢（平均分數、命中率、零命中比例、信心與分數分布），用「統計報表 → 檢索品質統計」（/reports/retrieval-quality）。那頁的資料源是真實使用者的問答稽核，不是你建的評測樣本——兩者互補：評測樣本是可控的回歸基準，報表是真實流量的體檢。

六、撰寫準則與建議（如何建立「好」的評測樣本）

1. 分兩類樣本，目的不同

  • 品質樣本：勾選模擬管理員（看得到全部），用來驗「找得到、找得對」——填期望命中來源（與可選錨點）。
  • 資安樣本：不勾管理員、設定模擬團隊為某受限團隊，期望命中只列該身分本來就看得到的來源——用來驗「越權洩漏＝0」。建議每個受控團隊至少 1 題。

2. 問句怎麼寫

  • 用真實使用者的問法、具體、單一意圖；一題一焦點，不要把多個問題塞一句。
  • 例：✅「特休假可以遞延到隔年嗎？」 ❌「請說明所有假別與請假與加班規則」。

3. 期望命中來源怎麼定

  • 先以管理員身分到 AI 知識問答 /knowledge-base-chat 提同一問題，看出處面板實際命中哪些來源，再把「理應命中」者回填。
  • 標題務必與「知識來源加工」一致。比對規則：大小寫不影響（不分大小寫），但全形/半形、空白、錯字會被判為未命中、分數異常偏低。
  • 這個欄位的畫面標籤是「期望命中來源（每行一個知識來源標題）」——一行一個標題，不要用分號或逗號分隔。

4. 期望錨點要不要填

  • 只有當你在意引用到正確章節/條款時才填；一旦填了，出處正確率就改以錨點比對（更嚴格）。一般場景可留空。

5. 覆蓋面建議

  • 核心高頻問題（最常被問的）。
  • 跨多來源問題（答案需綜合多份來源）。
  • 邊界/否定問題（知識庫其實沒有答案的，預期「查無依據」；可由人工在問答頁對照）。
  • 各受控團隊的資安樣本。

6. 數量與維護

  • 先建 5～10 題涵蓋代表場景，之後依回歸需要增補。
  • 換嵌入模型 / 調切塊 / 調融合權重後務必重跑（這正是它防回歸的價值）。
  • 知識來源改名後，記得同步更新樣本的「期望命中來源」。

7. 判讀紅線

  • 越權洩漏總數必須為 0：只要 >0，視為資安事故，立即檢查檢索層權控與該來源的團隊標籤，不要先調別的。
  • P/R/NDCG 跌破歷史基準：視為品質回歸，回頭檢討提示詞 / 檢索參數 / 切塊，而非放寬期望。

七、常見問題（FAQ）

  • 「評測全部」後分數全 0 或無命中？ 多半是該來源尚未索引，或「期望命中來源」標題與實際不一致。先確認來源已完成蒸餾（會自動索引）、標題逐字相符。
  • 沒設定嵌入也能評測嗎？ 能，但檢索退化為關鍵字比對，分數不代表正式語意檢索品質；正式評測前請設妥嵌入端點。
  • 和清洗品質評測有什麼不同？ 清洗品質評測管上游清洗品質、檢索品質評測管下游檢索品質，互補、不可互相取代（見第一節）。
  • 重新蒸餾後要不要重評？ 要。重蒸餾會產生新版頁（舊版轉 superseded、退出檢索）並連動重索引，內容/排序可能變動，請重跑相關樣本確認沒有回歸。

八、誠實評估：誰最需要它

  • 受監管 / 高風險客群（金融、醫療、法務、含大量個資）：可量化的越權洩漏＝0 與檢索品質回歸防護很可能是採購與稽核要件——能證明「不會把不該看的撈出來、品質不會悄悄退步」，是差異化與信任護城河。
  • 一般中小企業客群：多作為幕後品保即可，不必當主打；它支撐的是「AI 知識問答可被信任」這件事的證據基礎。
