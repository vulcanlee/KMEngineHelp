操作指南

手動開發新 CRUD 頁面的計畫

  • 文件版本：2.0（改藍本、補 4 項現行必做步驟、修正服務註冊位置與命名慣例）
  • 更新日期：2026/07/26
  • 對應系統版本：1.0.71
  • 編碼：UTF-8（繁體中文，含 BOM）

目標：複刻既有 CRUD 頁的「新增、查詢、更新、刪除、過濾、排序、分頁、驗證、通知」行為，並保留同等結構（Page + View + Service + AdapterModel + Entity + 註冊 + 樣式）。

動手前請先讀 開發慣例與限制速查——本文與它衝突時，以它為準。

0. 該拿哪一頁當藍本？

建議以 CategoryViewView 或 ProjectViewView 為藍本，不要用 RoleViewView。

RoleViewView 走的是 CheckIsAdmin()（管理員專用頁），既沒有 CheckAccessPage 頁面權限檢查、也沒有團隊權控。照它複刻出來的頁面會同時漏掉兩層權限 —— 這是資安問題，不是風格問題。

藍本適合什麼
CategoryViewView單純的基礎資料 CRUD（有頁面權限、無團隊欄位）
ProjectViewView帶分類／團隊標籤、需要團隊權控的業務資料
RoleViewView只有「純管理員頁」才適用；且不要照抄它的權限寫法

⚠️ 註：Components/Views/Admins/RoleViewViewSample.* 這個範例殘留檔已於 1.0.74 刪除（無 @page、全庫零引用的死碼），不必再找它。它先前被標為「全站唯一還在用已禁用的 MessageService」，但那句話是錯的——1.0.71 盤點時另外查出 6 個活著的檔案也在用（含七個頁面共用的 ContentEditDialog）。全站已於 1.0.74 清零，並由 Tests/ToastConventionTests.cs 自動守著。

1. 先做盤點（複刻前準備）

  1. 確認資料實體與欄位
  2. 目標 CRUD 的資料表實體（Entity）欄位需定義完成，至少要有 Id、主要顯示欄位、建立/更新時間欄位。
  3. 若這筆資料需要團隊權控，Entity 要有 Teams（分隔字串）欄位；需要分類篩選則加 Categories。
  1. 產生雙資料庫 migration（不可只做一套）
  2. SQLite：KnowledgeExtraction.AccessDatas
  3. SQL Server：KnowledgeExtraction.AccessDatas.SqlServerMigrations
  4. 指令與注意事項見 EFCore.md。只產一套會讓另一個資料庫的 schema 靜默落後。
  1. 確認前後端模型對應
  2. 建立 AdapterModel（ViewModel）承接畫面資料與驗證屬性。
  3. 編輯前一定要 Clone()，避免直接改到表格資料來源。
  1. 確認 AutoMapper 映射
  2. 新增 Entity <-> AdapterModel 雙向映射（Business/Models/AutoMapping.cs）。
  3. 標籤欄位不可走預設同名對應：Categories／Teams 是 Entity 的分隔字串、AdapterModel 的 List<string>，一律用 ForMember ＋ TagStringHelper.ToList／ToStored 雙向轉換。
  1. 確認 DI 註冊與路由入口
  2. 在 KnowledgeExtraction.Web/Extensions/ServiceCollectionExtensions.cs 加入 services.AddScoped<YourEntityService>();

（不是 Program.cs —— 服務註冊早已抽到這個 extension，Program.cs 只剩極少數特例。）

  • 建立 Components/Pages/<領域>/YourEntityPage.razor 並放入 <YourEntityViewView />。
  1. 同步權限三處（漏了會壞或被測試擋下）
  2. Share/Helpers/MagicObjectHelper.cs：加 角色_xxx 常數
  3. Business/Services/Other/RolePermissionService.cs：加到對應群組的正確位置
  4. Web/Datas/Menu.json：加選單項到對應位置

這三者是以陣列位置索引互相對應的，順序錯了權限就會對到別的頁。Tests/MenuPermissionAlignmentTests.cs 會擋下不一致。

注意：權限樹的字串是既存資料（寫在每個角色的 RoleView.TabViewJson），新增可以、改既有的值不行。

2. 後端服務層複刻計畫（DataAccess Service）

以 CategoryService（無團隊欄位）或 ProjectService（有團隊欄位）為模板建立 YourEntityService：

  1. GetAsync(DataRequest)：列表查詢
  2. 支援 Search 關鍵字篩選。
  3. 支援 SortField + SortDescending 排序（每個可排序欄位要明確分支）。
  4. 支援分頁 CurrentPage / PageSize。

DataRequest.Take 已廢棄、不再影響查詢結果（見 Models/Systems/DataRequest.cs 的註解），一律用 PageSize。

  • DataRequest 另有 CategoryFilters／TeamFilters／ProjectIdFilters 可用來做多選過濾。
  • 回傳 DataRequestResult<T>（Result + Count）。
  1. GetAsync(id)：單筆查詢
  2. 以 AsNoTracking 取單筆後映射成 AdapterModel。
  1. AddAsync / UpdateAsync / DeleteAsync
  2. 參照既有流程：清除追蹤（CleanTrackingHelper.Clean<T>）→ 寫入 → SaveChangesAsync()。
  3. 全部包裝 try/catch，失敗時 Logger.LogError 並回傳 VerifyRecordResult。
  1. BeforeXxxCheckAsync（新增/修改/刪除前檢查）
  2. 新增重複檢查。
  3. 修改時做「資料仍存在」與「唯一性衝突」檢查。
  4. 刪除前檢查可放關聯限制邏輯。
  1. 其他依賴資料初始化
  2. 若有 JSON 欄位/權限樹/外部依賴，集中在 OtherDependencyData 類方法處理，避免散落在 UI。

2.6 團隊權控（有 Teams 欄位就必做）

這是本專案的資安不變量：紀錄查詢／Controller／下載一律要套團隊權控 —— 非管理員只能看到「無團隊（公開）」或「與自己角色團隊有交集」的紀錄，管理員不受限。

// 建構式注入
private readonly IRecordAccessScopeProvider accessScope;

// 在 GetAsync(DataRequest) 裡，套完其他篩選之後：
var scope = await accessScope.GetAsync();
if (!scope.IsAdmin)
{
    dataSource = dataSource.Where(
        TagStringHelper.BuildTeamAccessPredicate<YourEntity>(x => x.Teams, scope.Teams));
}

單筆存取（GetAsync(id)、下載、編修）則用 TagStringHelper.IsTeamAccessible(item.Teams, scope.Teams, scope.IsAdmin) 判斷後拒絕。

參考實作：ProjectService／MeetingService／MediaTranscriptionService。漏掉這一段就是越權讀取。

3. 前端 View 元件複刻計畫（.razor + .razor.cs + .razor.css）

3.1 Razor 結構（UI 佈局）

  1. 工具列（Toolbar）
  2. 左側：新增、重新整理。
  3. 右側：搜尋輸入框、清空搜尋（有值才顯示）、搜尋按鈕。
  4. 工具列的動作鈕（新增／重新整理／搜尋／清空搜尋）一律使用 CrudActionButton（與操作欄同元件、同外觀），

不要用 emoji（➕/🔄/🔍/❌）或自訂 *-icon-button 按鈕。CrudActionButton 已內建 Tooltip，無需再包一層。 語意對應：新增=add、重新整理=refresh、搜尋=search、清空=close。 範例：<CrudActionButton Title="新增" Icon="add" OnClick="@(async () => await OnAddAsync())" />

  1. Table（RemoteDataSource=true）
  2. @bind-PageIndex、@bind-PageSize、@bind-Total。
  3. OnChange=OnTableChange 處理分頁與排序。
  4. 至少一個 ActionColumn 放修改/刪除按鈕；操作欄與列內小動作一律使用 CrudActionButton，不要使用 emoji 或裸 <button class="btn-edit">。
  5. CrudActionButton 的 Icon 必須使用 classic Google Material Icons 名稱（系統以 BlazorMaterialIcons 渲染），例如 edit、delete、description、visibility、replay、stop_circle。
  1. Modal + EditForm
  2. OnOk 統一走儲存。
  3. DataAnnotationsValidator + ValidationSummary + ValidationMessage。
  4. 使用 InputWatcher 將 EditContext 傳到 code-behind，供 Validate() 使用。
  5. 依欄位型態放對應元件（Input、Select、Checkbox...）。
  6. 多選 Select 的寫法是鐵則：必用 Mode="SelectMode.Multiple"（列舉，不是字串 "multiple"）＋ Values ＋ OnSelectedItemsChanged；不可用 @bind-Values:after（不會觸發）。範例見 Components/Views/Projects/ProjectViewView.razor。
  7. 若 Modal 內有 <InputFile>（上傳），Modal 必須設 MaskClosable="false"，否則點遮罩會中斷上傳。
  8. Modal 的樣式不能寫在 scoped .razor.css（Modal 掛在元件樹外，scoped 樣式會靜默失效），要寫在 wwwroot/app.css。

3.2 進頁權限檢查（必做樣板）

OnInitializedAsync 開頭要先擋權限，否則沒權限的人也進得來：

protected override async Task OnInitializedAsync()
{
    if (AuthenticationStateHelper.CheckAccessPage(MagicObjectHelper.角色_你的權限名) == false)
    {
        logger.LogWarning("Access denied to page. Permission={Permission}", MagicObjectHelper.角色_你的權限名);
        RoleMessage = MagicObjectHelper.你沒有權限存取此頁面;
        return;      // ← 一定要 return，不要繼續載入資料
    }

    await ReloadAsync();
}

Razor 端以 RoleMessage 決定整頁顯示：

@if (!string.IsNullOrEmpty(RoleMessage))
{
    <div class="alert alert-danger" role="alert">@RoleMessage</div>
}
else
{
    @* 正常頁面內容 *@
}

參考實作：Components/Views/Categories/CategoryViewView.razor.cs。

純管理員頁（不進權限樹）才改用 AuthenticationStateHelper.CheckIsAdmin()，例如 /system-health、/chat-logs。兩者不要混用。

3.3 Code-behind 行為（事件與狀態）

  1. 狀態欄位
  2. _pageIndex/_pageSize/_total/searchText/sortField/sortDirection。
  3. modalVisible/isNewRecordMode/CurrentRecord。
  1. ReloadAsync
  2. 統一列表資料載入入口，任何操作後都回到這裡。
  1. OnTableChange
  2. 更新頁碼。
  3. 解析目前排序欄位與方向（含 FieldName fallback 處理），再 ReloadAsync()。
  1. OnSearchAsync / OnRefreshAsync
  2. 搜尋時頁碼重設為 1。
  3. 重新整理後提供通知。
  1. OnAddAsync / OnEditAsync / OnDeleteAsync
  2. Add：建立新物件與預設值。
  3. Edit：使用 Clone() 防止雙向綁定直接污染列表項目。
  4. Delete：先 Confirm，再刪除，再通知，再 Reload。
  1. OnModalOKHandleAsync
  2. 先做 LocalEditContext.Validate()。
  3. 新增/修改分流：補齊 CreateAt/UpdateAt 或僅更新 UpdateAt。
  4. 成功後關閉 Modal 並 Reload。
  1. 鍵盤操作
  2. Enter 觸發儲存、Esc 關閉，提升可用性。

4. 手動開發步驟（建議順序）

  1. 建立 Entity（AccessDatas/Models）。
  2. 產生雙資料庫 migration（SQLite ＋ SQL Server，見 EFCore.md）。
  3. 建立 AdapterModel（Models/AdapterModel）+ DataAnnotations。
  4. 在 AutoMapping 加入雙向映射（標籤欄位用 ForMember ＋ TagStringHelper）。
  5. 建立 YourEntityService（Business/Services/DataAccess）並完成 CRUD + 查詢排序過濾分頁，並套團隊權控（§2.6）。
  6. 在 Web/Extensions/ServiceCollectionExtensions.cs 註冊 AddScoped<YourEntityService>()。
  7. 同步權限三處：MagicObjectHelper → RolePermissionService → Menu.json（位置索引要對齊）。
  8. 建立 YourEntityViewView.razor（照 CategoryViewView／ProjectViewView 版型）。
  9. 建立 YourEntityViewView.razor.cs（含 CheckAccessPage 進頁權限檢查，見 §3.2）。
  10. 建立 YourEntityViewView.razor.css（先複製同命名 class，再微調；Modal 樣式要放 wwwroot/app.css）。
  11. 建立 YourEntityPage.razor 與 @page 路由。
  12. 本機驗證（新增/查詢/修改/刪除/過濾/排序/分頁/驗證提示）＋權限與團隊可見性驗證。
  13. 跑 dotnet build、dotnet test（MenuPermissionAlignmentTests 會檢查第 7 步）。

5. 「完美複刻」的關鍵注意事項

  1. 排序欄位名稱一致性
  2. UI DataIndex 必須對應 Service SortField 比對字串（通常用 nameof(AdapterModel.Property)）。
  1. 分頁行為一致性
  2. 任何查詢條件變更（搜尋、重設）時，頁碼要回到第 1 頁。
  1. 編輯時資料隔離
  2. 使用 Clone() 後再編輯，避免列表資料提早變動造成 UI 錯亂。
  1. Validation 上下文取得
  2. 若要在 Modal 的 OnOk 觸發 Validate()，要確保 LocalEditContext 已被 InputWatcher 正確帶入。
  1. 通知與錯誤體驗一致
  2. 成功/失敗都要有明確通知，一律用 NotificationService（MessageService 自 1.0.24 起全站禁用）：
     notificationService.Open(new NotificationConfig
     {
         Message = "系統訊息",
         Description = "新增成功",
         NotificationType = NotificationType.Success,
         Placement = NotificationPlacement.BottomRight,
     });
  1. 圖示一致性（操作欄＋工具列）
  2. 全站動作鈕一律使用 CrudActionButton，不可用 emoji 或裸 <button class="btn-edit">。工具列與操作欄用同一元件、同外觀。
  3. 操作欄：修改 <CrudActionButton Title="修改" Icon="edit" OnClick="..." />；刪除 <CrudActionButton Title="刪除" Icon="delete" Danger OnClick="..." />（仍須二次確認）。
  4. 工具列：新增=add、重新整理=refresh、搜尋=search、清空搜尋=close。
  5. 下載/檢視/重試/取消等動作使用語意相符的 classic Material Icons；新增名稱前請確認不是 Material Symbols-only，並補進 CrudActionIconTests.AllowedCrudActionIcons 允許清單。
  1. 資料追蹤一致性（EF Core）
  2. Update/Delete 前先清 tracking，降低同一 DbContext 追蹤衝突。
  1. 初始化商業邏輯收斂
  2. 新增時的預設值（如權限預設）寫在 Add 流程，不要散在 UI 多處。

7. 手動測試清單（交付前必跑）

  1. 開啟頁面後資料可正確載入（含總筆數）。
  2. 搜尋關鍵字可過濾，清空搜尋可還原。
  3. 點欄位排序可切換升冪/降冪，資料順序正確。
  4. 分頁切頁後資料正確。
  5. 新增：
  6. 必填未填會顯示驗證錯誤。
  7. 儲存後出現成功通知，列表可見新資料。
  8. 修改：
  9. 開啟編輯資料正確。
  10. 儲存後資料更新且時間欄位更新。
  11. 刪除：
  12. 有二次確認。
  13. 刪除成功後列表更新。
  14. 鍵盤操作：Enter 可送出、Esc 可關閉。
  15. 例外路徑：服務拋錯時有錯誤紀錄與使用者可理解訊息。
  16. 權限：
  17. 用沒有勾該頁權限的角色登入 → 整頁顯示「你沒有權限存取此頁面」，且看不到選單項。
  18. 用有勾的角色登入 → 可正常進入。
  19. 團隊可見性（有 Teams 欄位才需要）：
  20. 建三筆資料：無團隊（公開）、團隊 A、團隊 B。
  21. 用「只屬於團隊 A」的非管理員登入 → 只看得到公開那筆與團隊 A 那筆，看不到團隊 B 的。
  22. 用管理員登入 → 三筆都看得到。

  24. 自動化：dotnet build 與 dotnet test 全綠（MenuPermissionAlignmentTests 會驗權限三處同步）。

8. 建議的實作原則（降低後續維護成本）

  1. 命名對齊：XxxPage / XxxViewView / XxxService / XxxAdapterModel。
  2. 注意 View 元件實際慣例是 XxxViewView（例如 CategoryViewView、ProjectViewView、RoleViewView），不是 XxxView。
  3. 檔案位置：Page 放 Components/Pages/<領域>/、View 放 Components/Views/<領域>/。
  4. 方法對齊：ReloadAsync / OnTableChange / OnAddAsync / OnEditAsync / OnDeleteAsync / OnModalOKHandleAsync。
  5. 單一資料入口：所有 UI 刷新都走 ReloadAsync。
  6. 商業邏輯集中：預設值、JSON 轉換、限制檢查放 Service。
  7. UI 僅做互動：按鈕事件只組裝參數與呼叫 Service。

依照此計畫，你可以在不引入額外框架的前提下，將新 CRUD 頁面以最小偏差複刻成與 RoleViewView 一致的結構與行為。
