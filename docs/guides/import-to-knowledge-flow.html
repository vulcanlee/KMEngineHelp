一、全景流程

步驟：

  1. 匯入：把素材匯入——影音轉逐字稿（逐字稿）、文件轉文字（Markdown）、圖片解讀（解讀文字），以及會議錄音（/meeting 上傳自動轉錄並產生 AI 會議紀錄，1.0.20）。加入知識來源時，會議可用第四型素材「會議紀錄」直接納入（1.0.25，索引 AI 會議紀錄非逐字稿）。
  2. 編成知識來源：在「知識來源加工」建立一筆來源，加入跨管線的成員（只會用到「已完成且有內容」者）。
  3. （可選）清洗規則設定：到「清洗規則設定」建立一組客製提示詞（去重/遮罩/分類/摘要/信心，留空＝用系統預設）。
  4. （可選）清洗品質評測校準：用題庫量測目前提示詞品質、取得建議的自動放行門檻。
  5. 清洗：按「清洗」，於對話窗選設定檔（或「預設／全域」）。背景管線：彙整成員 → 繁體化 → 去重 → 遮罩 → 分類 → 摘要 → 信心自評，產出單一 Markdown。
  6. 品質關卡：信心 ≥ 門檻（預設 0.70）→「已清洗」；否則 →「待審核」。
  7. 人工審核：待審核者由具 知識審核 權限者核准/退回。
  8. 檢視/編修清洗結果：可預覽、複製、線上編修並存回檔案（CleanedSourcePath，不存資料庫）。
  9. 蒸餾：對已清洗來源按「蒸餾」，把內容蒸餾為多個互連 Wiki 實體頁（見第五節，已實作）。

二、清洗 / 清洗規則設定 / 清洗品質評測 三者關係

角色它是什麼比喻
知識清洗真正的生產線：把彙整內容去蕪存菁、去敏、結構化、產出乾淨知識工廠產線
清洗規則設定這條產線「這一次用哪一組配方（提示詞）」產線的配方/參數設定
清洗品質評測用固定題庫量測配方品質、校準「自動放行」門檻出貨前的品管抽驗與及格線設定

操作注意事項（重要）

  1. 清洗品質評測目前用「全域」提示詞，不會套用你所選的清洗規則設定。EvaluateOneAsync 以AI 提示詞（清洗-*）或內建預設評測。要驗證某個設定檔的效果，目前需先把該組提示詞設成全域 清洗-* 再評測，或以清洗前後結果人工比較；「清洗品質評測指定設定檔」屬規劃中的後續延伸。
  2. 門檻校準是「建議值」：清洗品質評測算出的建議門檻僅供參考，實際套用要改 appsettings.json 的 SystemSettings.Cleaning.ConfidenceThreshold（預設 0.70）並重啟。注意這個清洗門檻與檢索門檻不同 —— 檢索側的 RejectThreshold／LowConfidenceThreshold 等 7 個參數可以在 /rag-diagnostics 熱套用、免重啟；清洗門檻不行，只能改設定檔。
  3. 編修清洗結果不會改狀態、也不自動重跑下游：直接覆寫清洗後檔案、更新時間，狀態維持不變。
  4. 遮罩失敗＝整筆清洗失敗（安全設計，避免漏遮外洩）；其餘步驟（去重/分類/摘要）可降級略過並記備註。
  5. 清洗結果只存檔案不存 DB：落在 CleanedSourcePath 下 {年}/{guid}.md，DB 僅存相對路徑。
  6. 未設定 LLM 金鑰：清洗只做彙整＋繁體化，跳過五段 LLM 強化（信心為空 → 走待審核或視設定）。但清洗品質評測在無金鑰時完全無法執行（會直接失敗，訊息「未設定 LLM（OpenAI ApiKey），無法評測」）——因為指標要靠 LLM 的實際輸出來比對。蒸餾同樣必須有金鑰。也就是說：無金鑰環境可以走完「匯入→聚合→清洗（降級）」，但評測與蒸餾以後的流程走不下去。

三、端到端例子 1：客服知識庫（一般敏感度）

  1. 匯入：上傳客服通話錄音（轉逐字稿）＋退款 FAQ 文件（萃取 Markdown）。
  2. 知識來源：建立「客服－退款流程」，加入上述兩個已完成成員。
  3. 清洗規則設定：建立「客服清洗規則設定」——遮罩客戶姓名/電話/Email；分類提示偏向「客服、財務」；摘要強調流程步驟。
  4. 校準（可選）：用一筆相近的黃金樣本（如種子「客服案件紀錄」：預期遮罩 陳美麗、mei@example.com；必保留 退款、計費規則）評測，確認遮罩召回率高、必保留達成，門檻訂 0.70。
  5. 清洗：按「清洗」選「客服清洗規則設定」→ 背景產出乾淨 Markdown，信心 0.82 ≥ 0.70 → 已清洗。
  6. 完成：檢視清洗結果、必要時小幅編修（複製/儲存），成為可檢索的客服知識。

四、端到端例子 2：人資／合約（高敏感、需人工把關）

  1. 匯入：上傳合約 PDF（萃取）＋員工名冊（文件/圖片）。
  2. 知識來源：建立「2026 供應商合約彙整」。
  3. 清洗規則設定：建立「高敏感遮罩設定檔」——強化遮罩身分證、金融帳號、密碼、統一編號；必保留合約關鍵條款用語。
  4. 校準：用種子「合約摘要（含機密帳號）」「新進員工資料表」評測，確認 A123456789、007-123456789012、P@ssw0rd2026 等遮罩召回率達標（這群樣本 HumanPass 多為否，提醒門檻要保守）。
  5. 清洗：產出後信心 0.6 < 門檻 0.70 → 待審核。
  6. 人工審核：具 知識審核 權限者開啟、確認個資已遮、條款完整 → 核准（或退回並填理由）。
  7. 完成：核准後成為可信任、可稽核的知識。

五、「蒸餾」現況與操作

  • 現況：已實作。 對已清洗的知識來源按「蒸餾」，背景管線會把清洗後內容用 LLM 蒸餾成多個 Wiki 實體頁（一概念一頁、以 [[wiki-links]] 互連、繼承來源 Teams/Categories 標籤），結果列於左側「知識庫 → 知識頁審核」頁。詳見 知識頁審核 PRD。
  • 操作步驟：
  • 在「知識來源加工」對一筆已清洗來源按「蒸餾」（僅該狀態可蒸餾）。
  • 背景蒸餾：讀清洗後內容 → LLM 蒸餾為多頁 → 落檔（WikiOutputPath）。蒸餾中可「取消」、失敗/取消可「重試」；來源列有「蒸餾」狀態與進度。
  • 到「知識頁審核」頁檢視產出：每頁信心 ≥ 門檻（SystemSettings.Distillation.ConfidenceThreshold，預設 0.70）→「已完成」；否則「待審核」。
  • 具 蒸餾審核 權限者可核准/退回待審核頁；任何頁可線上編修內容、刪除。
  • 注意事項：
  • 蒸餾在清洗之後、輸入為已遮罩內容，故不再重做遮罩。
  • 重蒸餾＝新版（VER-1）：重新蒸餾同一來源會保留舊版（轉「已汰換」）並建立版本鏈，不刪除既有 Wiki 頁。
  • 未設定 LLM 金鑰無法蒸餾（與清洗不同，蒸餾必須有 LLM）。
  • Wiki 頁內容只存檔案不存 DB（WikiOutputPath 下 {年}/{guid}.md）。
  • 已實作的下游：階段三知識庫（向量索引／混合檢索／跨來源問答／檢索品質評測）已完成，見 AI 知識問答使用指南 與 檢索品質評測使用指南。
  • 已上線的延伸：[[概念]] 可點擊跨頁導覽與 reader 導向知識百科頁（DIS-1/DIS-2，/knowledge-wiki）。
  • 規劃中的延伸：每來源客製蒸餾提示詞、Wiki 一致性 lint，以及能力包（SOP、問答、稽核 checklist——見 strategy/09 企業應用情境型錄）。

簡言之：清洗（去蕪存菁、去敏、結構化）、蒸餾（精煉為互連 Wiki 頁）、知識庫（向量索引／權控檢索／附出處問答）皆已可用。
