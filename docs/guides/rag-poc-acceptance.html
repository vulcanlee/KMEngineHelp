一、PoC 目標與驗收標準

目標：以最接近真實的方式，端到端驗證「已清洗、已蒸餾、已索引」的知識能否被自然語言跨來源檢索，並得到附出處、受權控的可信答案。

驗收標準（四面向，全部通過且流程可重複才算 PoC 完成）：

#面向通過判定（出自 strategy/12 §11.3、strategy/04 §階段三驗收）
1答案正確性答案依參考資料作答、與事實一致；查無依據時明確說明、不臆造
2出處可追溯每個答案附出處，可一路鑽取回知識來源 → 成員 → 原始檔下載
3權控正確非授權團隊內容不出現在答案/出處/下載；公開內容人人可見；管理員可見全部；每查詢留稽核軌跡
4遮罩無漏清洗後內容已遮敏感資訊（姓名/電話/Email/身分證/帳號/密碼等），且關鍵業務詞保留

量化輔助：四面向可分別用 清洗品質評測（上游清洗遮罩召回等）與 檢索品質評測（下游檢索 P/R/NDCG、越權洩漏=0）轉成可回歸指標，見第五節。

二、前置準備

2.1 嵌入設定（關鍵，未設妥則 PoC 無法驗證跨來源檢索）

跨來源檢索仰賴向量索引，索引需要嵌入端點。在 appsettings.json 的 OpenAISettings 擇一設定：

模式必填欄位備註
雲端ApiKey（＋ EmbeddingModel，預設 text-embedding-3-large）沿用既有 BaseUrl/ApiKey
地端LocalBaseUrl ＋ LocalEmbeddingModel（預設 bge-m3）OpenAI 相容端點；繁中多語表現佳
  • EmbeddingProvider：Cloud／Local；留空＝沿用 GenerationProvider 取向。
  • EmbeddingDimensions：固定 1024（目前系統運作約定；文件與查詢向量不可混用不同維度，請勿任意更動）。
  • 檢索參數在 SystemSettings.Retrieval：TopK(10)、CandidateTopK(50)、VectorWeight(0.7)、KeywordWeight(0.3)、MinScore(0.0)；另有兩段式信心門檻 RejectThreshold(0.15)、LowConfidenceThreshold(0.30)。
  • 切塊參數也在 SystemSettings.Retrieval：ChunkTargetChars(800)、ChunkMaxChars(1200)、ChunkOverlapChars(120)。調整後需重新建立索引才會影響既有知識。
  • 生成與改寫模型：GenerationModel(gpt-5.4)、QueryRewriteModel(gpt-5.4-mini)；查詢改寫 Retrieval.QueryRewrite：Enabled(true)、Mode(Auto)、MinQueryChars(20)、MaxHistoryMessages(6)、FallbackToOriginalOnError(true)。做 §4.1 的多輪追問判讀時要知道這組設定。

⚠ appsettings 的值不一定是當前生效值。 上面 7 個查詢期參數（TopK／CandidateTopK／VectorWeight／KeywordWeight／MinScore／RejectThreshold／LowConfidenceThreshold）都可以在「檢索診斷與調校」（/rag-diagnostics）熱套用，覆寫存在資料庫、免改設定檔也免重啟。做 PoC 前請先到那一頁確認有沒有「頁面覆蓋中」，否則你以為在測 appsettings 的值，其實測的是別人套用過的覆寫。切塊參數不在熱套用範圍（改了必須重建索引）。

  • 是否視為已設定，由 OpenAISettings.IsEmbeddingConfigured() 判定（雲端看 ApiKey；地端看 LocalBaseUrl＋LocalEmbeddingModel）。

⚠ 未設定嵌入的後果：蒸餾完成後索引管線無法建立新的向量索引；檢索服務可用關鍵字路徑降級，但此時無法驗證本 PoC 的核心語意召回能力。務必在開始前設妥嵌入端點。

2.2 資料與身分準備

  • 素材：挑 1–2 份真實手冊/SOP（例：員工手冊、客服 SOP）。最好內含可遮罩的個資（姓名/電話/Email/身分證/帳號）與須保留的條款用語，才能同時驗遮罩與答案正確性。
  • 團隊與帳號（驗權控用）：規劃至少 2 個團隊 ＋ 公開（無團隊） 的內容，並準備兩種可登入身分：
  • 管理員（不受團隊權控，應看到全部）。
  • 受限團隊成員（只屬其中一個團隊，應看不到其他團隊內容）。
  • 角色／團隊建立見 使用者安裝與操作手冊。

三、執行步驟（逐站操作）

全景：匯入 → 編成知識來源(指定團隊) → (可選)清洗規則設定/清洗品質評測校準 → 清洗 → (品質關卡) → 蒸餾 → (蒸餾審核) → [自動]索引 → 跨來源問答。前段操作細節見 從匯入到知識的操作流程，此處延伸到索引與問答。

階段路由（左側選單）操作完成判定
1. 匯入/document-extraction、/media-transcription、/image-recognition上傳手冊/SOP（文件/音訊/圖片），等背景處理。PDF 注意事項見下方狀態「已完成」且有內容
2. 編成知識來源/knowledge-sources「新增」來源 → 「管理成員」加入步驟 1 的已完成素材 → 設定 Teams（團隊）成員齊、團隊已標（團隊＝權控根）
3.（可選）清洗規則設定/cleaning-profiles建客製提示詞組（去重/遮罩/分類/摘要/信心）；高敏感資料建議強化遮罩規則—
4.（可選）清洗品質評測校準/golden-samples用標準題庫量遮罩召回/分類/摘要、取建議門檻遮罩召回 ≥0.98 等達標
5. 清洗/knowledge-sources →「清洗」選設定檔（或預設/全域）→ 背景：彙整→繁化→去重→遮罩→分類→摘要→信心信心 ≥0.70 →「已清洗」；否則「待審核」
6. 品質關卡/knowledge-sources「待審核」者由具 知識審核 權限者「核准/退回」；可「檢視清洗結果」預覽/編修來源為「已清洗」
7. 蒸餾/knowledge-sources →「蒸餾」對已清洗來源按「蒸餾」，背景蒸餾為多個互連 Wiki 頁蒸餾進度完成
8. 蒸餾審核/knowledge-distillationWiki 頁信心 ≥0.70 →「已完成」；否則由具 蒸餾審核 權限者核准Wiki 頁「已完成/已核准」
9. 索引（自動、背景）—（無需手動）蒸餾成功後自動把「清洗內容」與「已核准 Wiki 頁」切塊、嵌入、寫入向量庫稍候片刻讓背景索引完成
10. 跨來源問答/knowledge-base-chat用自然語言提問 → 串流答案 → 展開「出處面板」得到附出處答案

關於步驟 1（PDF 萃取）的重要事實：

本專案的出貨設定（MarkItDownSettings.PdfUseLlm = true、PdfLlmModel = gpt-5.4）是把整份 PDF 送給大語言模型轉 Markdown，不是純本機萃取。做 PoC 時要知道：

  • PDF 會用到金鑰、也會計入 Token 用量（作業別 文件轉文字、型別 File），成本評估別漏掉這一段。
  • 圖片與圖表會在原位以 > **[圖片]** 開頭描述，可還原成數據的圖表會另外輸出 Markdown 表格。這會影響 §4.4「與原文對比」的基準 —— 萃取結果不會是原文逐字複刻，而是 AI 的結構化重述。
  • 提示詞鍵是 文件-PDF轉Markdown（可在 /prompts 覆寫）；逾時 600 秒；只嘗試一次。
  • 失敗（含沒有金鑰）會自動降級成 MarkItDown、狀態仍是「已完成」，並在該筆的錯誤訊息欄留下 AI 解析 PDF 失敗，已自動改用 MarkItDown 轉換：{原因}。做 PoC 前務必檢查有沒有這行，否則你會以為在驗證 AI 萃取品質，其實跑的是降級路徑。
  • 若要刻意測純本機路徑，把 PdfUseLlm 設成 false（程式屬性的預設值本來就是 false）。
  • 非 PDF 格式一律走 MarkItDown，不呼叫 LLM。

關於索引（步驟 9）的重要事實：

  • 索引是蒸餾成功後自動觸發的背景作業（需嵌入已設定）；此外「知識來源加工」每列對已清洗來源提供「建立索引／重建索引」按鈕（TriggerEmbeddingIndexAsync，不需重蒸餾即可增量建立/更新向量），並有工具列的一鍵全量重建索引（RQ-8，0.3.10）。
  • 採增量重建：以 (SourceLayer, WikiPageId, ContentHash) 比對，只對新增/變更的 chunk 重新嵌入，不變者不重嵌。
  • 要重建索引不必重蒸餾：對已清洗來源按「建立索引／重建索引」即以增量 diff 更新向量；重蒸餾則產生新版頁（VER-1，0.3.14；舊版轉 superseded 保留，不刪除）並自動連動索引。
  • 嵌入未設定時索引會略過；之後補上嵌入設定，不需要重新蒸餾 —— 只要該來源的狀態是「已清洗」，直接按該列的「建立索引」即可（唯一的前置條件是狀態＝已清洗且不在索引中，與蒸餾狀態無關）。重跑蒸餾只會白花一次 LLM 費用。

四、四面向人工檢核

逐面向在指定畫面驗證；可用文末「PoC 檢核表」逐項記錄。

4.1 答案正確性（畫面：/knowledge-base-chat）

  • 針對手冊/SOP 的真實問題提問（例：「入職滿三年可享什麼健康檢查福利？」）。
  • 檢查：答案是否依參考資料、與原文事實一致、無捏造；刻意問知識庫沒有的問題，應明確回覆「查無依據」而非硬掰（知識庫-系統 提示詞精神，規格 §9.2）。

4.2 出處可追溯（畫面：/knowledge-base-chat 答案下方「出處面板」）

  • 每個 AI 回合下方應列出引用 chunk（來源標題／層別 Wiki/Cleaned／錨點／片段／相似度分數）。
  • 鑽取鏈逐層可達（規格 §10.1）：命中 chunk → 所屬 Wiki/清洗來源 → 知識來源 → 成員（KnowledgeSourceItem）→ 原始檔下載。
  • 點「下載原始檔」應能取得原始音訊/文件/圖片，且下載受同一團隊權控。

4.3 權控正確（畫面：/knowledge-base-chat，以兩種身分對照）

  • 以受限團隊成員登入，提一個會命中「其他團隊」內容的問題 → 答案/出處/下載不得出現其他團隊內容；公開內容可見。
  • 以管理員登入提同一問題 → 應可見全部團隊內容。
  • 對照兩者差異即為權控證據（規格 §8.3：每輪重新取存取範圍、越權內容由檢索層過濾，不進 context/答案/出處）。

4.4 遮罩無漏（畫面：/knowledge-sources →「檢視清洗結果」）

  • 把「清洗後 Markdown」與「原始成員內容」（在 /document-extraction 等管線頁可看原文）對比。
  • 檢查：敏感資訊（姓名/電話/Email/身分證/金融帳號/密碼/統一編號等）已遮罩，且關鍵業務詞（流程、條款用語）保留。
  • 量化：在 /golden-samples 用相近樣本量遮罩召回率（目標 ≥0.98）。

五、量化銜接（把人工檢視轉成可回歸指標）

人工判讀之外，用兩個既有評測頁把品質「數字化」，作為日後換模型/調參的回歸基準：

  • 清洗品質評測 /golden-samples（上游清洗品質）：遮罩召回、必保留、分類 F1、摘要涵蓋＋門檻掃描。對應四面向的「遮罩無漏」。
  • 檢索品質評測 /rag-evaluation（下游檢索品質）：把 PoC 的代表問題建成評測樣本——Query ＋ 期望命中來源（標題） ＋ 期望錨點 ＋ EvalTeams/EvalIsAdmin，量測 Precision@k / Recall@k / NDCG@k / MRR / 出處正確率 / 越權洩漏(必為 0) / 檢索延遲。對應「答案/出處/權控」三面向的客觀化。
  • 提醒：「載入種子」載入的是範本樣本，其「期望命中來源」務必改成本次 PoC 實際已索引的知識來源標題才有意義。
  • 品質樣本設 EvalIsAdmin=true（看全部）；資安樣本設受限 EvalTeams 並只列可見來源，由「越權洩漏總數」把關（應為 0）。

六、問題記錄與迭代

PoC 是迭代而非一次過：

  1. 記錄每個面向的缺陷（答錯/出處斷鏈/越權/漏遮）。
  2. 對症調整：
  3. 漏遮或分類差 → 調清洗提示詞/設定檔、用清洗品質評測重驗。
  4. 檢索召回差或排序不佳 → 到 /rag-diagnostics 熱套用 Retrieval 權重/TopK/MinScore（下一次檢索生效、免重啟），或調整 ChunkTargetChars/ChunkOverlapChars 後重建索引（切塊參數不能熱套用）。
  5. 地端嵌入品質存疑 → 先以雲端對照，評估 bge-m3 召回（規格 §12.3 Q1）。
  6. 重新清洗/蒸餾/（自動）索引 → 重測，直到四面向達標。
  7. 把穩定的問題集沉澱進 /rag-evaluation，未來變更後一鍵回歸。

七、常見陷阱

  • 未設嵌入端點 → 無法建立新的語意向量索引，檢索只能降級走關鍵字路徑；務必先設定（§2.1）。
  • 調切塊參數後要重建索引：ChunkTargetChars、ChunkMaxChars、ChunkOverlapChars 只在建立索引時生效，既有 VectorEmbedding 不會自動更新。
  • 換嵌入模型需全量重建索引：不同模型的向量不可混比；以 VectorEmbedding.EmbeddingModel 辨識，換模型後重新蒸餾全部來源重建。
  • 重蒸餾＝新版（VER-1，0.3.14）：保留舊版（轉 superseded、向量標非現行）並建版本鏈，不刪舊頁；重建索引的正規途徑是對來源按「建立索引／重建索引」。
  • 清洗品質評測用「全域」提示詞，不會套你選的清洗規則設定；要驗特定設定檔需先設為全域 清洗-* 或人工比對。
  • 清洗/蒸餾內容只存檔案不存 DB（CleanedSourcePath／WikiOutputPath 下 {年}/{guid}.md）。
  • 索引有手動按鈕：清單頁每列對已清洗來源提供「建立索引／重建索引」；索引本身仍是背景作業，觸發後給它一點時間完成再去問答。
