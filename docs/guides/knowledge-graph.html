一、知識圖譜在做什麼？（為什麼需要）

一句話：除了「找出最相似的段落」，再多記住一件事——實體之間有什麼關係，好回答那些「答案不在任何單一段落裡」的問題。

一般的 RAG（向量＋關鍵字混合檢索）本質是「找最像的幾頁」。它很擅長「教育訓練補助上限是多少」這種答案就寫在某一段裡的問題，但有兩類問題它結構上答不好：

問題類型例子為什麼一般檢索答不好
多跳關聯「客戶A 的 ERP 主機出問題，會影響到哪些系統？」答案要串起「ERP 主機 → 部署於 → 某台伺服器 → 也跑著 → 報表模組」，這條鏈分散在三份不同文件，沒有任何一段同時提到頭尾
全域綜觀「客戶A 的整體維運風險有哪些？」這題沒有「最相關的 5 段」——它需要看過全部內容再歸納。只取前 K 段等於隨機抽樣

知識圖譜針對這兩類問題各給一條路：多跳圖檢索（第一類）與社群摘要全域問答（第二類）。

它是加分項，不是取代品。 圖檢索是混合檢索的第三路，權重由 GraphWeight 控制；把它設成 0，系統就完全回到 1.0.82 之前的行為，向量與關鍵字兩路照常運作。

1.1 四個名詞（白話版）

名詞白話例子
實體（Entity／節點）一個名詞——人、組織、產品、系統、概念客戶A ERP系統、Windows Server 2022
關係（Relation）連接兩個實體的動詞或述語部署於、負責維護、相依於
三元組（Triple）「實體—關係—實體」一組，是圖譜的最小單位客戶A ERP系統 — 部署於 → Windows Server 2022
社群（Community）關係特別緊密的一群實體。系統會替每一群寫一份摘要，全域問答就是拿這些摘要來答「客戶A 維運相關」自成一群

⚠️ 不要和清洗流程的「關鍵實體」混淆。 清洗的「摘要」步驟會請 LLM 列出人事時地物「關鍵實體」，那是一串關鍵詞、存在清洗結果裡；本文件的「實體」是圖譜的節點，有型別、有錨定的 Wiki 頁、會參與多跳遍歷。兩者是不同機制。

二、開始前的前提

這一章的所有功能都有前置條件，沒過就一定看不到效果。建議照表逐項確認：

#前提怎麼確認不通過的後果
1已設定 Chat 大語言模型「系統管理 → 系統監控 → 系統健康監控」(/system-health) 看 LLM 可用性三元組抽取、社群摘要、別名建議、全域問答全部無法執行（抽取會被前置守門擋下並顯示應用性錯誤訊息；REST global-ask 回 503）
2知識來源已清洗「知識來源加工」清單的「清洗」欄沒有清洗內容就沒有蒸餾
3知識來源已蒸餾同上「蒸餾」欄＝已蒸餾「抽取／重抽三元組」按鈕不會出現
4Wiki 頁已核可「知識頁審核」把該來源的 Wiki 頁核可抽取會跑完但抽不到東西——抽取讀的是「已完成且現行」的 Wiki 頁。這是最常見的踩雷點
5三元組已核可本頁「三元組審核」分頁，狀態＝已完成待審核／已退回的三元組完全不影響檢索（這是刻意的治理設計）
6GraphWeight 大於 0管理員在「檢索診斷與調校」(/rag-diagnostics) 看實際生效值設 0＝圖檢索整路關閉，連查詢都不發
7權限權限樹勾「知識圖譜審核」進不了頁面。核可／退回另需「蒸餾審核」動作權；「實體合併」與「重建社群摘要」只有管理員，勾角色權限也沒用

💡 為什麼 appsettings 的值不一定是生效值：GraphWeight／GraphMaxHops／GraphHopDecay 可以在 /rag-diagnostics 線上覆寫（存在資料庫），覆寫後就以資料庫的值為準。要確認當前實際生效值，一律看那一頁，不要看 appsettings.json。

三、三元組是怎麼產生的（按下按鈕後系統做了什麼）

按下「抽取／重抽三元組」後，依序發生：

  1. 前置守門（任一不過就直接擋下，不會白花 LLM 費用）：來源存在 → 團隊權控（非管理員只能操作無團隊或與自己團隊有交集的來源）→ 蒸餾狀態＝已蒸餾 → Chat LLM 已設定 → 該來源沒有正在進行中的抽取。
  2. 排入佇列，圖譜狀態變「等待中」。背景服務取出後轉「處理中」並回報百分比。
  3. 讀取內容：取該來源「已完成且現行」的 Wiki 頁內容。這一步決定了「Wiki 頁沒核可就抽不出東西」。
  4. LLM 抽取：用提示詞 圖譜-三元組抽取 請 LLM 輸出「主詞／主詞型別／關係／受詞／受詞型別／信心」。
  5. 落地與去重：建立或重用實體節點（同名收斂），三元組以「主詞｜關係｜受詞」為鍵去重。
  6. 狀態一律是「待審核」，等人工審核。

⚠️ 重抽是安全的。 去重鍵是「主詞｜關係｜受詞」，而且絕不覆蓋你已核可或已退回的判斷——已審核過的三元組會原樣保留。所以抽壞了、來源更新了，放心重抽。

3.1 圖譜有兩種邊，來源不同

邊的種類從哪來要不要 LLM要不要人工審核
概念連結邊（GraphEdge）Wiki 頁內文的 [[標題]] 連結，直接解析成「頁↔頁」的邊❌ 不用❌ 不用（是內容本身就有的連結）
三元組邊LLM 從 Wiki 頁內容抽出的「實體—關係—實體」✅ 要✅ 要，核可後才生效

概念連結邊會在蒸餾完成、Wiki 頁核可或編修時冪等重建（重跑結果一樣，不會累積重複），不需要你操作。三元組邊才是本頁要審核的東西。

💡 為什麼要人工審核：LLM 抽關係會出錯（把「提到」當成「相依於」、把兩個不相干的名詞連起來）。如果錯的關係直接進檢索，它會把錯的內容拉到前面——比沒有圖譜更糟。所以設計成「LLM 提案、人工核可」的治理流程。

四、/knowledge-graph-review 頁面操作

進入：選單「知識庫 → 知識圖譜審核」。權限樹要勾的是 知識圖譜審核——這是全系統少數「選單顯示名＝權限名」完全一致的一項，不是漏改。

頁面說明文字寫著「審核由 AI 從蒸餾內容抽取的『實體—關係—實體』三元組；核可後才會納入檢索加分。統計為全庫（依團隊權控過濾）。」

4.1 頁頂：社群摘要狀態列

灰底橫條，顯示「社群摘要（全域問答用）」目前狀態：

顯示意思
—狀態尚未載入
建置中…正在重建，此時「重建社群摘要」鈕會禁用
目前 N 個社群，上次建立 2026/07/29 14:30正常。N 就是全域問答可取用的社群總數
（上次錯誤：…）紅字顯示上次重建失敗原因
  • 「重建社群摘要」按鈕：僅管理員可見。按下後排入全域單例作業（見 §五）。
  • 「重新整理狀態」按鈕：所有人可用，重新拉一次狀態。

⚠️ 沒重建過社群摘要 = 全域問答不能用。 這是部署後最容易漏掉的一步，已列入 正式部署與安全檢查清單。

4.2 分頁一：三元組審核

篩選列：狀態下拉（待審核／已完成／已退回／全部）、依團隊過濾（多選）、搜尋「主詞/關係/受詞」（可按 Enter）、搜尋鈕、重新整理鈕。

表格欄位：主詞（附型別標籤）、關係、受詞（附型別標籤）、信心、來源、狀態。

操作按鈕（需 canReview＝管理員或具「蒸餾審核」權限）：

按鈕出現條件作用
編修有審核權即可（任何狀態）開 Modal 可改：主詞、主詞型別、關係、受詞、受詞型別。型別可留空（提示為「如 人/組織/產品/概念」）
核可狀態＝待審核 且有審核權狀態轉「已完成」，開始納入檢索加分
退回同上開 Modal 顯示該三元組並可填「退回理由（選填）」，狀態轉「已退回」，永久不進檢索

核可／退回／編修任一動作都會立即讓檢索快取失效，不必等排程，下一次檢索就反映最新狀態。

4.3 分頁二：實體合併（僅管理員可見）

維護「別名 → 標準名」對照（頁面例子是「TSMC → 台積電」）。核可後，別名變體在社群偵測與檢索都視為同一個實體。

三個區塊：

  1. 「LLM 自動建議別名」（藍底）：顯示「待審核 N 筆，上次建議 時間 新增 M 筆」或「生成中…」或紅字錯誤。按鈕排入全域單例作業（見 §五），生成中會禁用。旁有「重新整理狀態」。
  2. 手動新增別名（淺灰底）：輸入「別名（如 TSMC）」→「標準名（如 台積電）」→ 按「送出（待審核）」。手動新增的也要審核，不會直接生效。
  3. 別名清單：狀態篩選＋搜尋「別名/標準名」；表格欄位為 別名、標準名、信心、狀態、審核者、退回理由；待審核者有「核可」「退回」（退回可填理由）。

別名怎麼傳遞：已核可的別名會做傳遞閉包收斂。也就是 A→B 與 B→C 都核可時，A、B、C 會被視為同一個實體。所以核可前要想清楚——把「同名不同物」誤併會讓兩批無關的知識黏在一起（發現誤併就把該筆別名退回）。

⚠️ 別名是全域治理：別名表沒有團隊欄位，因此只影響實體的連通性，不會放寬任何人的可見範圍。也因為是全域的，只有管理員能維護。

核可別名之後：檢索即時生效；但要讓社群也套用合併，需要再按一次頁頂的「重建社群摘要」。

4.4 分頁三：圖譜瀏覽

輸入實體名稱、選跳數（只能 1、2、3）、按「查詢」。別名會自動解析為同一實體，且只顯示你有權存取的關係。

結果呈現：

  • 一張 SVG 放射狀示意圖：查詢的實體置中（藍色大圓點），第 1 跳綠色、第 2 跳以上黃色，依跳數分層排在同心圓上，節點名稱標在圓點上方。
  • 一行統計：「共 N 個實體、M 條關係」。
  • 一張表格：主詞／關係／受詞／跳數（每頁 20 筆）。

兩種「沒結果」：

  • 查無實體時顯示警示：「查無實體「X」，或該實體目前沒有『已核可且您有權存取』的關係。」——注意這句話同時涵蓋三種情況：名字打錯、三元組還沒核可、或那些關係你沒權限看。
  • 節點數達 100 個上限時顯示：「⚠️ 鄰域節點已達上限 100 個而停止擴展，以下結果並不完整。請縮小跳數。」不會靜默截斷。

4.5 分頁四：待抽取來源

列出「已蒸餾、但圖譜還沒東西」的來源（抽取失敗或抽不出三元組者），只顯示你有權存取的來源。

💡 為什麼要獨立一個分頁：三元組審核清單是「三元組導向」的——抽取失敗或抽不出東西的來源因為一條三元組都沒有，反而完全不會出現在審核清單裡，而那正是最需要重抽的。

表格欄位：知識來源、圖譜狀態（空白時顯示「待抽取」）、三元組數、上次抽取、錯誤訊息。每列有「抽取／重抽」按鈕，按下走的是與知識來源加工頁完全相同、已完整守門的重抽流程。

沒有待抽取來源時顯示綠色訊息：「沒有待抽取的來源——所有已蒸餾的來源都已產出三元組。」

⚠️ 兩個邊界：①進行中（等待中／處理中）的來源刻意排除——它們已經在跑，不需要再按一次。②清單一次最多取 50 筆。

五、抽取與重建的背景作業（怎麼觀測、怎麼取消）

圖譜相關共四條作業，性質不同：

#作業範圍要 LLM觸發方式在哪觀測
A三元組抽取每筆來源各一✅蒸餾完成自動觸發；或手動按「抽取／重抽」知識來源清單的「圖譜」欄（含百分比）＋「待處理背景工作」
B概念連結邊重建每筆來源各一❌蒸餾完成、Wiki 頁核可／編修時自動冪等重建無需觀測（很快、不會失敗成孤兒狀態）
C社群摘要重建全域單例✅ 每群一次管理員按「重建社群摘要」「待處理背景工作」
DLLM 別名建議全域單例✅ 一次管理員按「LLM 自動建議別名」「待處理背景工作」

A 的狀態機：待抽取（初始）→ 等待中 → 處理中（含 %）→ 已抽取 ／ 失敗 ／ 已取消。服務重啟時，殘留在「處理中」的會自動改回「等待中」並重新排程，不會卡死。

⚠️ 別把兩組狀態混在一起看：來源的抽取狀態是「待抽取／等待中／處理中／已抽取／失敗／已取消」（管線跑到哪了）；三元組的審核狀態是「待審核／已完成／已退回」（人審過了沒）。來源顯示「已抽取」只代表管線跑完，裡面的三元組仍然全是「待審核」、還沒進檢索。

C 與 D：以持久化的作業狀態列記錄，因此可觀測、可取消、服務重啟後也能撿回未完成的作業。它們刻意不列入標準背景管線清單，而是以作業類型識別。

在哪看：「系統管理 → 系統監控 → 待處理背景工作」(/pipeline-jobs，僅管理員)。可看到積壓與逐筆取消。

⚠️ 取消不是立刻停。 單次 LLM 呼叫進行中無法中斷，取消只在呼叫之間生效——按了取消，會等當前那一次 LLM 回來才真正停下。所以按了取消卻看到它還在跑幾十秒，是正常的。

⚠️ 多台機器部署時：記憶體中的「正在建置」旗標只反映本機，資料庫的作業狀態列才是全域真相。要判斷「到底有沒有人在跑」，看 /pipeline-jobs。

六、全域問答（社群摘要）

6.1 在哪切換

在「AI 知識問答」(/knowledge-base-chat) 的設定區，「查詢模式」下拉有兩個選項：

  • 一般（精準檢索）：預設，走混合檢索（向量＋關鍵字＋圖）。
  • 全域（社群摘要）：走社群摘要歸納。

6.2 兩種模式怎麼選

一般（精準檢索）全域（社群摘要）
適合的問題具體事實、條款、步驟、數字綜觀、趨勢、系統性根因、「整體有哪些…」
答案依據命中的內容片段每個社群的摘要
有出處嗎✅ 有出處面板，可鑽取回原始檔❌ 沒有出處面板、沒有相似度，改為顯示取用了幾個社群
限定來源／分類／團隊篩選✅ 有效❌ 不套用這些篩選
成本一次問答一次 LLM每個你有權存取的社群各一次 LLM，再彙整一次

⚠️ 全域模式沒有出處不是壞了，是設計如此：社群摘要是「跨多筆來源歸納後的產物」，本來就沒有對應到某一段原文的位置。要追出處請改用一般模式再問一次具體問題。

6.3 怎麼問

用「整體、綜觀、系統性、趨勢、有哪些風險」這類詞。例如：

  • ✅ 適合全域：「客戶A 的整體維運風險有哪些？」「這批知識裡反覆出現的系統性問題是什麼？」
  • ❌ 不適合全域：「客戶A 的 SLA 回應時間是幾小時？」（這題請用一般模式，才有出處可核對）

若管理員從未重建過社群摘要，系統會明確告知原因（不是回一片空白）。

七、圖譜如何影響一般問答的分數

一般模式的融合分數是三路相加：

總分 = VectorWeight × 向量分 + KeywordWeight × 關鍵字分 + GraphWeight × 圖分

圖分怎麼算（白話版）：

  1. 先由向量與關鍵字兩路命中的 Wiki 頁當作種子。
  2. 從種子沿著概念連結邊與已核可的三元組做廣度優先擴展，最多 GraphMaxHops 跳。
  3. 第 h 跳的傳播強度 = 種子強度 × GraphHopDecay^(h-1)，所以第 1 跳不衰減、第 2 跳乘一次衰減，以此類推。
  4. 擴展到的鄰居頁，其現行內容片段獲得圖分加成。
  5. 累計節點數達 GraphMaxNodes 即停止擴展並記錄 log。

7.1 七個參數

參數預設作用能否線上熱調
GraphWeight0.2圖分在融合式中的權重。設 0 = 關閉整條圖檢索路徑✅ /rag-diagnostics
GraphMaxHops2擴展跳數，範圍 1～3✅ /rag-diagnostics
GraphHopDecay0.5每多一跳的衰減係數，範圍 0～1✅ /rag-diagnostics
GraphMaxNodes200單次檢索圖遍歷的節點上限（安全閥）❌ 只讀 appsettings，改了要重啟
GraphGlobalCommunityCap20全域問答一次最多取用幾個社群（直接決定成本）❌ 需重啟
GraphMaxCommunities50社群重建最多保留幾群（超出者取成員數最大的前 N 群並記 log）❌ 需重啟
GraphAliasNameCap300LLM 別名建議一次送出的實體名上限（超出者取出現次數最多者）❌ 需重啟

⚠️ 後四項沒有資料庫覆寫路徑，/rag-diagnostics 上也刻意不提供，只能改 appsettings.json 並重啟服務。填 0 或負數時系統以 1 計（不會靜默停擺）。

⚠️ GraphMaxHops 預設是 2。 多跳自 1.0.90 起生效，這會讓 1.0.89 之前建立的檢索評測基線位移（找到的東西變多）。升級後應重跑一次評測建立新基線；想完全回到單跳行為就設 1。

八、權控如何運作（資安關鍵，越權洩漏＝0）

圖譜把「關係」也當成知識來保護。權控不是只在最後過濾一次，而是四層各自套用：

層套用的權控
邊遍歷時每一條邊都檢查團隊可存取性——而且每一跳都重新檢查，不能借道無權限的節點繞過去
節點他人團隊的實體節點不會被納入
三元組只有已核可且你有權存取的三元組才參與加分
鄰居內容片段擴展到的頁面，其片段仍要通過原本的內容層權控

三個容易誤解的地方：

  1. 他隊的三元組，即使兩端頁面都是公開的，也不會替你加分。 因為「這兩個東西有關係」這件事本身就是知識，屬於抽出它的那個來源所在團隊。
  2. 社群摘要的權限比一般紀錄更嚴：採子集判定——社群涵蓋來源的團隊聯集必須是你的團隊的子集，或該社群完全是公開內容，你才能取用。理由是一份社群摘要混合了多筆來源的知識，只要其中一筆你無權看，整份摘要就不能給你。
  3. 別名表與作業狀態表沒有團隊欄位，屬全域管理員治理。別名只改變「哪些名字算同一個實體」，不改變任何人能看到什麼。

九、怎麼量「圖到底有沒有用」

到「檢索品質評測」(/rag-evaluation) 跑評測，看四個圖相關指標：

指標意思
圖召回增益（主指標）期望來源中，命中完全來自圖檢索那一路的比例。這是保守下界——圖分讓某筆排名上升而擠進 TopK 的效應不計入，所以實際貢獻只會比這個數字高
圖參與率有多少比例的查詢，圖檢索至少貢獻了一點分數
圖獨有命中向量與關鍵字兩路都是 0 分、只有圖路找到的命中數
平均取用社群數全域問答評測時，平均每題取用幾個社群

基線會記錄當時的 GraphWeight／GraphMaxHops／GraphHopDecay。若某個基線是在這些欄位加入之前建立的，會顯示「未記錄」而不是 0——因為 0 會謊稱「當時圖是關閉的」。

全域問答評測模式：評測樣本可指定走全域模式。這個模式以「關鍵詞涵蓋率」計分，Precision／NDCG／MRR 顯示「—」（那些指標需要排序後的出處清單，全域模式沒有）。

⚠️ 全域評測會呼叫 LLM，因此不是確定性的（同一份樣本兩次跑分數可能略有差異），成本＝可存取社群數次呼叫，且沒有評測專用節流。關鍵詞比對是子字串比對，不處理同義詞。

十、對外整合（MCP 與 REST）

10.1 MCP 工具（給外部 AI Agent）

工具說明
knowledge_graph_neighbors查某實體的 N 跳鄰域。純資料庫查詢、不呼叫 LLM；只回已核可三元組；節點上限 100，達上限回傳 truncated 旗標而不靜默截斷
knowledge_ask 的 mode=global走社群摘要。回傳差異：sources 恆為空、topScore 恆為 0，改回 usedCommunities；不套用分類／團隊篩選；只做 map 不做 reduce（彙整成一段答案只有 Blazor 聊天頁會做）。無法辨識的 mode 值會明確拋錯，不會靜默當成預設

詳見 MCP 服務使用說明書。

10.2 REST 端點（給一般 HTTP 呼叫端，1.0.96 起）

端點方法說明
/api/v1/KnowledgeGraph/global-askPOST圖譜全域問答（僅 map）。LLM 未設定回 503（服務依賴未備妥，刻意不是 500）
/api/v1/KnowledgeGraph/neighbors?entityName=&maxHops=GET查實體 N 跳鄰域。maxHops 超出 1～3 回 400（刻意不靜默夾住，與 MCP 的行為不同）；查無實體回 200 + found=false（查不到不是錯誤）
  • 兩支端點都需 JWT 認證，權控完全交給既有服務，與 MCP 走同一條把關程式碼。
  • 沒有寫入型端點——無法透過 REST 新增或核可三元組，這是刻意的非目標。
  • 成本受 GraphGlobalCommunityCap 控管，沒有 API 專用節流。

十一、成本與已知限制

11.1 LLM 成本從哪來

動作呼叫次數受哪個上限控管
三元組抽取每筆來源一次—
社群摘要重建每個社群一次GraphMaxCommunities（50）
全域問答（每問一次）每個可存取社群一次 ＋ 彙整一次GraphGlobalCommunityCap（20）
LLM 別名建議一次GraphAliasNameCap（300，指送出的實體名數）

成本最需要留意的是全域問答：它不是「一問一答一次 LLM」，而是社群數乘上去。20 個社群的一題全域問答，等於 21 次 LLM 呼叫。

11.2 已知限制

限制影響與怎麼繞
四個成本閥（GraphMaxNodes／GraphGlobalCommunityCap／GraphMaxCommunities／GraphAliasNameCap）不支援線上熱調改 appsettings.json 後必須重啟服務
檢索熱路徑雖有行程內快取，多台機器部署時失效只影響本行程有 300 秒絕對逾時兜底，最長 5 分鐘後一致
REST global-ask 缺 HTTP 層的越權洩漏端到端測試（服務層已有測試覆蓋）上線前建議手動以非管理員帳號驗一次
REST 端點沒有專用節流成本只靠 GraphGlobalCommunityCap 控管，對外開放時請在前端閘道加限流
「待抽取來源」清單上限 50 筆、無分頁超過 50 筆時處理完一批再重新整理
進行中的社群重建／別名生成，單次 LLM 呼叫無法立即中斷取消只在呼叫之間生效
取消抽取的動作沿用頁面層級（僅管理員）把關，未另加團隊權控僅管理員能進 /pipeline-jobs，實際上等效
每次檢索／全域問答仍會載入全部已核可別名與社群已加索引與快取；超大圖時效能仍有優化空間
REST 端點無寫入能力審核動作只能在網頁上做

十二、常見問題（FAQ）

問題說明
抽取跑完了，但一條三元組都沒有最常見原因是該來源的 Wiki 頁還沒核可——抽取讀的是「已完成且現行」的 Wiki 頁。先到「知識頁審核」核可，再重抽。
看不到「抽取／重抽三元組」按鈕該來源還不是「已蒸餾」狀態。
抽取狀態是「失敗」先看該列的錯誤訊息，再到 /system-health 確認 LLM 可用性。不要連按重抽（每次都花錢）。
核可了三元組，但檢索結果沒變化①兩端實體必須錨定到現行的 Wiki 頁；②到 /rag-diagnostics 確認 GraphWeight 沒有被覆寫成 0；③圖分是加分項，若原本排名差距很大，加 0.2 權重可能不足以改變順序。
重抽會不會蓋掉我的審核結果不會。 去重鍵是「主詞｜關係｜受詞」，已核可／已退回的判斷原樣保留。
全域問答沒有出處，是壞了嗎不是，設計如此（見 §6.2）。要出處請改用一般模式。
全域問答說「沒有可用社群」管理員需先在本頁按「重建社群摘要」。
我看不到「實體合併」分頁該分頁僅管理員可見，角色權限勾不出來。
別名核可了但沒生效檢索是即時生效的（快取會立即失效，最長 300 秒後全機一致）；但社群要再按一次「重建社群摘要」才會套用合併。
同名不同物被誤併了把該筆別名「退回」，然後重建社群摘要。
查詢延遲變高把 GraphMaxHops 調成 1，或降低 GraphMaxNodes（後者需重啟）。
想完全關掉圖譜功能/rag-diagnostics 把 GraphWeight 設 0——連圖查詢都不會發出。

maxHops=99 為什麼回 400 而不是自動改成 3REST 端點刻意明確拒絕超界參數，讓呼叫端知道自己傳錯了（MCP 工具則是靜默夾住，兩者行為不同是刻意的）。

升級後評測分數變了GraphMaxHops 預設 2（1.0.90 起多跳生效）會讓召回變多、基線位移。請重跑評測建立新基線。
