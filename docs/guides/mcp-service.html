一、這個服務在做什麼？（為什麼需要）

MCP 服務讓外部 AI Agent（如 Codex、Claude Code、Claude Desktop、Cursor、VS Code 或其他支援 MCP 的工具）能把「查詢本企業知識庫」當成內建工具直接使用，而不必為每個 Agent 客製串接。各客戶端的實際設定步驟見 §3.3。

透過本服務，Agent 可以：

  • 問答：用自然語言詢問企業知識，取回含出處的參考資料與信心判定。注意：伺服器端只做檢索、不生成答案——最終答案是由你的 AI 用戶端（Claude／Codex 等）拿這份參考資料去生成的。
  • 搜尋：取回最相關的原始內容片段，自行彙整。
  • 盤點：列出有哪些知識來源（文件、分類、團隊）。
  • 取全文：取回單一文件的完整內容。

所有查詢都會自動套用呼叫者的團隊權限——Agent 永遠看不到使用者無權存取的內容。

服務以 HTTP（Streamable HTTP） 方式對外，端點路徑為 /mcp，與系統其他 Web API 共用同一認證與安全邊界。

二、開始前的前提

項目說明
服務已部署系統管理員已在 Web 站台啟用 MCP endpoint（/mcp），並設定授權
有一個帳號你需要一組系統帳號；其所屬團隊決定你能查到哪些知識
取得憑證兩種擇一：JWT Bearer（先登入取得 JWT，帶 Authorization: Bearer，見 §3.2）；或 MCP 專用 API Key（管理員於 /mcp-api-keys 網頁建立、存資料庫、可啟用/停用，帶專用標頭 X-API-Key；見 §6.7）
端點網址例如 https://your-host.example.com/mcp（向管理員索取正式網址）

三、AI Agent 端連線設定（使用者操作）

3.1 連線共通資訊

不論哪一種客戶端，都是連到同一個 HTTP（Streamable HTTP）端點並帶授權標頭：

  • 傳輸類型：HTTP / Streamable HTTP（不是 stdio）
  • 端點 URL：https://your-host.example.com/mcp（向管理員索取正式網址）
  • 授權標頭（擇一）：JWT → Authorization: Bearer <你的 JWT>；API Key → X-API-Key: <你的金鑰>（專用標頭，不放在 Authorization）

安全提醒：多數設定檔以明碼存放 token。建議用環境變數帶入（下方各例盡量示範），並勿把含 token 的設定檔提交進版本控管。

3.2 取得 JWT

呼叫系統既有的登入端點以帳密換取 JWT（例如 POST /api/Auth/...，實際路徑向管理員確認），把回傳的 token 填入下方各客戶端設定的授權欄位。Token 到期後需重新換發。

3.3 各家 AI Agent 設定

各家格式差異大：Codex 用 TOML（config.toml）、其餘多用 JSON；VS Code 用 servers＋必填 type，Cursor／Claude 用 mcpServers。務必用對應格式。

下方各例以 JWT（Authorization: Bearer）示範。若改用 API Key，把授權標頭換成 X-API-Key: <你的金鑰>（例如 Cursor/VS Code 的 headers 改 "X-API-Key": "..."；Codex 的 http_headers 改 X-API-Key = "..."）。

3.3.1 Codex（CLI）

編輯 ~/.codex/config.toml（全域）或專案下 .codex/config.toml。直接連遠端 Streamable HTTP 需開啟 RMCP client：

experimental_use_rmcp_client = true

[mcp_servers.knowledge_extraction]
url = "https://your-host.example.com/mcp"
# 建議：以環境變數帶 token（下行擇一）
bearer_token_env_var = "KE_JWT"     # 讀環境變數 KE_JWT，送出 Authorization: Bearer <值>
# bearer_token = "<你的 JWT>"        # 或直接明碼（較不建議）

若要帶自訂標頭（例如 API Key 方案），改用 http_headers 區塊：

[mcp_servers.knowledge_extraction]
url = "https://your-host.example.com/mcp"

[mcp_servers.knowledge_extraction.http_headers]
Authorization = "Bearer <你的 JWT>"

使用前先 export KE_JWT=<你的 JWT>（Windows PowerShell：$env:KE_JWT="<你的 JWT>"）。OAuth 型伺服器才需 codex mcp login；本服務用 Bearer，不需要。

3.3.2 Codex 桌面版（Codex App / Desktop）

以圖形介面新增，不必手改設定檔：

  1. 左下角 齒輪 Settings → MCP Servers
  2. Add server → 傳輸類型選 Streamable HTTP
  3. 填 URL：https://your-host.example.com/mcp
  4. 在 Headers 加一組：Key = Authorization、Value = Bearer <你的 JWT>（或以 Authenticate 走 OAuth，本服務用 Bearer 則直接填標頭）
  5. 儲存後即可在對話中使用這六個工具（建議先呼叫 knowledge_ping 確認連線）

Codex 的 VS Code 擴充與 CLI 共用同一份 config.toml（設定同 §3.3.1）；部分版本擴充端的伺服器顯示仍有已知問題，若沒出現可改用 CLI 驗證。

3.3.3 Claude Code（CLI）

用內建指令新增 HTTP 型伺服器（選項要放在名稱之前）：

claude mcp add --transport http knowledge-extraction \
  https://your-host.example.com/mcp \
  --header "Authorization: Bearer <你的 JWT>"
  • 加 --scope user 讓所有專案可用，或 --scope project（透過 git 分享，但勿把 token 提交）。
  • 移除：claude mcp remove knowledge-extraction；列出：claude mcp list。

3.3.4 Claude Desktop

Claude Desktop 的遠端 MCP 走 Custom Connectors（自訂連接器） UI：

  1. Settings → Connectors → Add custom connector
  2. 填入遠端 MCP URL：https://your-host.example.com/mcp
  3. 非 OAuth 時，展開設定在 Request headers 加憑證（Claude 會安全保存）：JWT → Authorization = Bearer <你的 JWT>；或 API Key → X-API-Key = <你的金鑰>
  4. 儲存後啟用該連接器

註：Claude Desktop 從雲端連到你的 MCP 伺服器，故端點需可從公網（Anthropic IP）連到。若走 claude_desktop_config.json 檔案設定，需搭配 mcp-remote 橋接遠端伺服器。

3.3.5 Cursor

編輯 ~/.cursor/mcp.json（全域）或專案 .cursor/mcp.json：

{
  "mcpServers": {
    "knowledge-extraction": {
      "url": "https://your-host.example.com/mcp",
      "headers": {
        "Authorization": "Bearer ${env:KE_JWT}"
      }
    }
  }
}

Cursor 的 url／headers 支援 ${env:VAR} 變數插值；先設好環境變數 KE_JWT 再啟動 Cursor。

3.3.6 VS Code（MCP）

建立專案 .vscode/mcp.json（注意用 servers、且每個伺服器必填 type）：

{
  "inputs": [
    { "id": "ke-jwt", "type": "promptString", "description": "Knowledge Extraction JWT", "password": true }
  ],
  "servers": {
    "knowledge-extraction": {
      "type": "http",
      "url": "https://your-host.example.com/mcp",
      "headers": {
        "Authorization": "Bearer ${input:ke-jwt}"
      }
    }
  }
}

VS Code 首次使用會提示輸入 JWT 並安全保存（inputs），避免明碼寫死在檔案裡。

3.4 連線後可用的工具

連線成功後，Agent 會在工具清單看到下列工具，並依各工具說明自動判斷何時呼叫：

工具名稱用途
knowledge_askRAG 檢索：回傳含出處的參考資料 context 與信心判定（不是生成好的答案，答案由你的用戶端 LLM 產出）。1.0.91 起支援 mode=global 走知識圖譜社群摘要
knowledge_search混合檢索，回傳相關內容片段與分數
knowledge_list_sources分頁列出可存取的知識來源
knowledge_get_document依 ID 取回單一來源全文
knowledge_ping連通性診斷：回傳固定訊息確認服務可被呼叫
knowledge_graph_neighbors（1.0.91）查某實體在知識圖譜中的 N 跳鄰域關係（實體—關係—實體），供多跳關聯探索。純資料庫查詢、不呼叫 LLM

四、六個工具的用法與範例

回傳內容為示意，實際依知識庫資料而定。參數名稱與回傳欄位名以本節為準（舊版本文件的欄位名有誤，照抄會串接失敗）。

4.1 knowledge_ask（檢索參考資料）

  • 參數（共 5 個）：
參數型別說明
questionstring必填。問句
categoriesstring[]?可選。限定分類清單；null 或空＝不限
teamsstring[]?可選。限定的團隊名稱清單（只會縮小、不會擴權）；null 或空＝不限
historyChatTurn[]?可選。多輪對話歷史，依序 user/assistant 回合；每個元素為 { "role": "...", "content": "..." }
modestring?可選（1.0.91）。local（預設，精準檢索）或 global（知識圖譜社群摘要）。無法辨識的值會明確拋錯，不會靜默退回 local——否則呼叫端會誤以為自己走了 global
  • 範例呼叫：knowledge_ask({ "question": "公司差旅報銷的流程是什麼？" })
  • 預期回傳（注意出處的欄位名是 sourceTitle 而非 title）：
{
  "answerContext": "差旅報銷須於行程結束後 7 個工作天內於差旅系統提出……",
  "confidence": "Sufficient",
  "topScore": 0.82,
  "sources": [
    {
      "knowledgeSourceId": 12,
      "sourceTitle": "差旅管理辦法 v3",
      "sourceLayer": "Cleaned",
      "snippet": "差旅報銷須於行程結束後 7 個工作天內……",
      "score": 0.82
    }
  ]
}

answerContext 是「參考資料」不是「答案」。伺服器端完全不呼叫生成模型，請把它連同 sources 一起交給你的用戶端 LLM 去組答案，並要求它引用 sourceTitle。

mode=global（知識圖譜社群摘要，1.0.91）

適合「整體風險有哪些」「反覆出現的系統性問題是什麼」這類要看過全部內容才答得出的問題。一般的向量／關鍵字檢索只取最相似的前 K 段，對這類問題等於隨機抽樣。

  • 範例呼叫：knowledge_ask({ "question": "客戶A 的整體維運風險有哪些？", "mode": "global" })
  • 回傳欄位差異（照 local 的預期去解析會拿到空值）：
欄位mode=localmode=global
sources有出處清單恆為空陣列（社群摘要沒有 chunk 層出處）
topScore融合分數恆為 0
usedCommunities不回傳取用的社群清單
categories / teams 篩選生效不套用
  • ⚠️ 只做 map、不做 reduce：本工具回傳的是「每個社群的重點」，不是彙整好的一段答案。彙整（reduce）刻意留給你的用戶端 LLM 做——與 answerContext 同樣的設計哲學。（Blazor 網頁的問答頁則會做完整 map-reduce。）
  • ⚠️ 成本是社群數的倍數：每個你有權存取的社群各一次 LLM 呼叫（上限由伺服器的 Retrieval.GraphGlobalCommunityCap 控管，預設 20）。
  • ⚠️ 前置：伺服器端的管理員必須先在「知識圖譜審核」頁按過「重建社群摘要」，否則無社群可用。
  • 社群摘要的權控比一般紀錄更嚴（子集判定），見 §五。

4.2 knowledge_search（搜尋片段）

  • 參數：query（必填）、topK（可選）。這個工具沒有 categories／teams 參數——要按分類或團隊縮小範圍請改用 knowledge_ask 或 knowledge_list_sources。
  • 範例呼叫：knowledge_search({ "query": "資安事件通報 窗口 時限", "topK": 3 })
  • 預期回傳：相關片段陣列，每筆含 knowledgeSourceId、text、sourceLayer、anchorRef、score、vectorScore、keywordScore。

4.3 knowledge_list_sources（列出來源）

  • 參數：search（可選）、categories（可選）、teams（可選）、page（預設 1）、pageSize（預設 20）
  • 範例呼叫：knowledge_list_sources({ "search": "新人", "page": 1, "pageSize": 10 })
  • 預期回傳：{ "total": 2, "items": [ { "id": 12, "title": "新人到職手冊", … } ] }（這個工具的欄位名確實是 title）

4.4 knowledge_get_document（取全文）

  • 參數：sourceId（必填）
  • 範例呼叫：knowledge_get_document({ "sourceId": 12 })
  • 預期回傳：{ "sourceId": 12, "title": "新人到職手冊", "content": "# 新人到職手冊…" }
  • 若不存在、尚未清洗完成或無權存取：{ "error": "unavailable" }（統一回應，不區分以避免洩漏來源是否存在）

4.5 knowledge_ping（連通性診斷）

  • 參數：無
  • 範例呼叫：knowledge_ping({})
  • 預期回傳：固定字串 KnowledgeExtraction MCP server is alive.
  • 用途：連線設定完成後的第一個測試。它不開查詢範圍、也不寫任何紀錄或用量，所以拿它驗證「認證有沒有通、端點有沒有到」最乾淨。若這個工具都不通，先回頭檢查 §三 的連線設定與憑證。

4.6 knowledge_graph_neighbors（查實體鄰域，1.0.91）

查某個實體在知識圖譜中的鄰域關係，用來探索「A 透過什麼連到 C」這類答案不在任何單一段落裡的關聯。

  • 參數：
參數型別說明
entityNamestring必填。實體名稱，例如 台積電。別名會自動解析為同一實體（如 TSMC → 台積電，需該別名已被管理員核可）
maxHopsint?可選。擴展跳數 1～3，預設 2。超出範圍會被靜默夾住（不報錯——呼叫端是 LLM，夾住比報錯更能讓對話繼續；REST 端點的行為相反，見 §4.7）
  • 範例呼叫：knowledge_graph_neighbors({ "entityName": "台積電", "maxHops": 2 })
  • 只回傳「已核可」的三元組，且只回你有權存取的關係。查不到時回 found=false（不是錯誤）。
  • 節點數上限 100，達上限時回傳 truncated 旗標——不靜默截斷，你會知道結果不完整。
  • ⚠️ 純資料庫查詢，不呼叫 LLM，因此不計 token 用量、速度快、可安心多次呼叫。

4.7 唯讀 REST 端點（1.0.96，給不講 MCP 協定的系統）

上面兩項圖譜能力另有對等的 REST 版本，供無法或不想實作 MCP 協定的系統整合。JWT 認證，權控與 MCP 走同一條把關程式碼。

端點對應 MCP行為差異
POST /api/v1/KnowledgeGraph/global-askknowledge_ask（mode=global）LLM 未設定時回 503（伺服器組態問題，刻意不是 500）。同樣只做 map 不做 reduce
GET /api/v1/KnowledgeGraph/neighbors?entityName=&maxHops=knowledge_graph_neighborsmaxHops 超出 1～3 回 400（刻意不像 MCP 那樣靜默夾住——REST 的呼叫端是程式，明確報錯才能讓 bug 及早浮現）。查無實體回 200 + found=false
  • ⚠️ 沒有寫入型端點：無法透過 REST（或 MCP）新增或核可三元組。審核是治理動作，刻意只留在網頁上。
  • ⚠️ 沒有 API 專用節流，成本只靠伺服器的 Retrieval.GraphGlobalCommunityCap 控管。對外開放時請在前端閘道加限流。

五、權控如何運作（資安關鍵）

  • 每次查詢，系統會依你的憑證解析出身分與所屬團隊。
  • 非管理員只能看到「無團隊（公開） 或 與你的角色團隊有交集」的知識；管理員不受限。
  • 權控發生在檢索層：越權內容永遠不會被取回，Agent 無法繞過。
  • 因此，同一個問題由不同人問，可能得到不同結果——這是預期行為，不是錯誤。

範例：僅屬「行銷部」的非管理員詢問只屬「財務部」的機密薪酬政策，會得到查無依據（confidence: Insufficient、sources: []）。

知識圖譜相關的兩項額外規則：

  • 社群摘要（mode=global）的權控更嚴，採子集判定：社群涵蓋來源的團隊聯集必須是你的團隊的子集，或該社群完全公開，才取用得到。理由是一份摘要混了多筆來源的知識，其中任一筆你無權看，整份就不能給。（其餘紀錄都是「交集即可」。）
  • knowledge_graph_neighbors 的每一跳都重新驗權限：不能借道無權限的中間節點繞到有價值的節點。他人團隊的三元組即使兩端頁面都公開也不回傳——「這兩者有關係」本身就是一項知識。

六、日誌與稽核（管理員運維）

MCP 服務被呼叫時，重要動作都會寫入日誌，並依嚴重性分到不同等級，供日後除錯與分析。日誌與稽核沿用系統既有機制。

6.1 日誌寫到哪裡

  • 與全系統共用同一份每日檔案（NLog，路徑由 NLog.BasePath 決定，出貨預設為 C:\temp\Logs，檔名 *-{日期}.log），UTF-8，保留約 30 天、單檔上限 100MB 自動輪替。
  • 每筆日誌都帶：時間、TraceId（每次請求的關聯 id，可串起同一次呼叫的所有日誌）、等級、記錄器名稱，以及情境欄位 user=（帳號）／op=（操作）／id=（紀錄 Id）。
  • MCP 相關日誌的 op= 會是 McpAsk、McpSearch、McpListSources、McpGetDocument，方便過濾。knowledge_ask 的日誌另帶 mode=local|global。

6.2 各等級（Level）記什麼

等級記錄內容預設是否輸出
Trace逐工具參數細節、檢索中間值否（深度除錯才臨時開）
Debug工具進入點、參數摘要（topK、過濾條件、sourceId）、身分解析結果否（正式環境不開）
Information里程碑：工具呼叫開始、成功（含命中數/最高分/信心/耗時）是
Warning權控拒絕、找不到來源、查無依據、稽核寫入失敗、授權未過是
Error例外、檢索/DB 失敗、下游（OpenAI 嵌入）錯誤是
Critical系統幾乎無法運作（如 DB 完全失敗）是

6.3 常見日誌訊息解讀

你會看到的訊息（示意）等級意義
MCP 工具呼叫開始。tool=knowledge_ask questionLen=…Information有一次問答進來了
MCP 工具呼叫成功。tool=knowledge_ask 命中數=… 最高分=… 信心=…Information問答完成，附檢索 metrics
MCP 工具權控拒絕。tool=knowledge_get_document sourceId=…Warning有人嘗試取用越權來源（已擋下，可歸責）
MCP 問答稽核持久化失敗（不影響回答）。Warning稽核寫 DB 失敗，但回答不受影響
MCP 工具呼叫失敗。tool=…Error該次呼叫發生例外，需追 TraceId 查上下文

6.4 稽核紀錄（可歸責性）

  • MCP 問答會寫入既有 AI 知識問答稽核（KnowledgeBaseQueryAudit），與 Blazor 問答同軌。
  • 稽核只存身分與分數指標：帳號、姓名、是否管理員、團隊、查詢長度、命中數、最高分、信心、命中明細（Id/層別/分數）。
  • 不會儲存問句本文、回答內容或知識片段文字（隱私邊界不變量）。
  • 可經 /rag-diagnostics 頁面查閱近期問答稽核紀錄（管理員）。

6.5 臨時提高日誌等級切換（除錯用）

  • 到 /log-settings 頁面（管理員），把等級臨時切到 Debug 或 Trace，即可看到工具參數摘要與更細節；設定即時生效（nlog.config autoReload），除錯完請切回 Information 以免日誌暴量與洩漏過細資訊。

6.6 MCP 聊天紀錄與 Token 歸屬（1.0.8 起）

  • 聊天紀錄：knowledge_ask 每次呼叫會寫入既有 問答稽核明細（/chat-logs，管理員可查；進入路徑：系統管理 → AI 與整合 → 問答稽核明細），來源出處標示為「MCP Server 問答」（Origin=Mcp）。寫入的是問句原文與回傳的參考資料 context 全文（存於實體檔案），檔案內該段標題為「回傳給 Agent 的檢索參考資料（伺服器端未生成 AI 答案，答案由 MCP 用戶端 LLM 生成）」。隱私影響見 §七 Q2。
  • 不會出現在「完整對話紀錄」/chat-sessions：MCP 單次呼叫不帶 SessionId，不構成「一段對話」。
  • 全文 .md 內容含：呼叫來源（MCP API Key 名稱）、使用者提問、回傳給 Agent 的檢索參考資料 context、出處與信心/分數。
  • 注意：MCP 的 AI 答案是由 MCP 用戶端（如 codex/Claude）的 LLM 生成，伺服器端不生成答案，故聊天紀錄記的是「回傳的參考資料」，非 AI 回答。此紀錄比照網頁聊天紀錄會保留問句與 context 全文於檔案（僅管理員可查），與 6.4 稽核（不存本文）是兩套獨立機制。
  • knowledge_search 屬低階檢索、不寫聊天紀錄（其 token 仍歸屬，見下）。
  • Token 歸屬：knowledge_ask 與 knowledge_search 的檢索用量（嵌入 Embedding、必要時查詢改寫 QueryRewrite）會歸屬到呼叫者並標記作業 McpKnowledgeAsk／McpKnowledgeSearch，可於 /token-usage（明細）與 /reports/token-usage-report（報表）依作業與使用者切分查閱。
  • 上限說明：MCP 能計量的只有「檢索端」token；「答案生成」token 發生在 MCP 用戶端、不在本系統計量範圍。

6.7 API Key 管理（1.0.9 起：改存資料庫、網頁維護）

  • MCP 的 API Key 改由資料庫儲存，不再寫在 appsettings.json。管理員於 /mcp-api-keys（系統管理 → AI 與整合 → MCP 金鑰管理，僅管理員） 網頁 CRUD：
  • 新增：系統自動產生一把隨機金鑰（可「重新產生」），設定「名稱」（辨識用途/agent）與「對映使用者」（決定團隊權控範圍），可直接複製金鑰貼進客戶端設定。
  • 啟用/停用：可即時停用單一金鑰；停用後該金鑰立即無法連線（回 401），不需重啟服務。重新啟用即恢復。
  • 修改/刪除：刪除後使用該金鑰的 Agent 立即無法連線。
  • 認證流程：MCP 連線帶 X-API-Key → 伺服器查資料庫比對啟用中的金鑰（常數時間比對）→ 命中即以對映使用者身分套團隊權控。
  • 金鑰以明文儲存於資料庫，僅管理員可於網頁檢視；請比照密碼妥善保管、勿外流。

七、除錯與問題診斷（管理員）

症狀檢查方向
Agent 連不上 /mcp確認 endpoint 已註冊、.RequireAuthorization() 憑證正確、網路/憑證（HTTPS）可達
呼叫回 401/未授權JWT 過期或無效 → 重新換發並確認 Authorization: Bearer；或 API Key 無效 → 確認 X-API-Key 標頭與管理員設定的金鑰一致
查詢總是查無依據確認嵌入索引已建立（/rag-diagnostics 索引健康）、該使用者團隊是否真的有權存取相關來源
取全文回 unavailable來源不存在／尚未清洗完成／無權存取三者之一；若屬無權，查 Warning 日誌確認是誰、哪筆 sourceId
要追某一次呼叫的完整過程從日誌取該次 TraceId，以 TraceId 過濾即可串起開始→檢索→成功/失敗全鏈
需要更多細節/log-settings 臨時開 Debug，重現後切回

八、建議使用時機與最佳實務

  • 一般問答優先用 knowledge_ask（有出處、有信心判定）；需要 Agent 自行彙整或比對多段時再用 knowledge_search。
  • 先列來源再取全文：不確定文件 ID 時，先 knowledge_list_sources 找到 ID，再 knowledge_get_document。
  • 善用過濾：knowledge_ask 與 knowledge_list_sources 可帶 categories／teams 縮小範圍（只會縮小、不會擴權），提升相關度。knowledge_search 沒有這兩個參數（只有 query／topK）。
  • 憑證保管：JWT／API Key 視同密碼，勿寫入版本控管或公開設定；日誌本身不會記錄它們。
  • 運維巡檢：定期看 Warning（權控拒絕是否異常增加）與 Error（呼叫失敗率）。/mcp 已內建套用 api 限流政策，不需另外加。

九、常見問題（FAQ）

Q1：MCP 服務會把知識內容外流給不該看的人嗎？ 不會。權控在檢索層生效，非管理員只能取回公開或其團隊交集的內容，Agent 無法繞過。

Q2：日誌會記錄我問了什麼、回傳了什麼嗎？

會，而且是全文。 這裡要分成三個不同的東西講清楚（舊版本文件把它們混為一談、寫成「本文不落地」，那是錯的）：

機制存什麼存在哪誰能看
NLog 應用日誌不含本文。只記身分、操作、命中數、分數、長度等 metricNLog.BasePath 下的每日檔維運（可經 /log-download 打包下載）
檢索稽核（KnowledgeBaseQueryAudit）不含問句本文、不含 chunk 文字。只記長度與分數，供門檻校準資料庫管理員（/rag-diagnostics）
聊天紀錄（/chat-logs）⚠️ 問句原文與回傳的參考資料 context 全文實體檔案（ChatLogPath 下的 .md）僅管理員

也就是說：「不落地」只適用於前兩者。第三者（聊天紀錄）是刻意保留全文的稽核設計，來源出處會標示為「MCP Server 問答」。

如果你的使用情境不允許問句落地，這是必須在導入前確認的政策點——請與系統管理員討論是否要調整 ChatLogPath 的保護措施、存取控管與保存期限。不要對客戶或資安審查說「MCP 問答不留本文」。

補充：MCP 的問答不會出現在「完整對話紀錄」/chat-sessions，因為單次工具呼叫沒有「對話」概念（不帶 SessionId）。要稽核 MCP 一律到 /chat-logs，來源選「MCP Server 問答」。

Q3：為什麼同一個問題，我和同事得到的答案不同？ 因為你們所屬團隊不同，可存取的知識範圍不同。這是預期的權控行為。

Q4：JWT 過期了怎麼辦？ 重新呼叫登入端點換發，更新 MCP client 設定中的 Authorization。

Q5：我想追一次失敗的呼叫，從哪裡開始？ 從錯誤日誌取該次 TraceId，用它過濾日誌即可看到該次呼叫的完整脈絡（開始、權控、檢索、失敗原因）。

Q6：可以用 stdio（本機管道）連線嗎？ 本服務採 HTTP transport，因為 stdio 無法沿用 JWT 身分解析與團隊權控，不適合對外多租戶場景。

Q7：mode=global 回來的 sources 是空的、topScore 是 0，是壞了嗎？ 不是，這是設計。全域模式的依據是社群摘要（跨多筆來源歸納後的產物），本來就沒有對應到某一段原文的位置與相似度。改看 usedCommunities。若你需要可鑽取的出處，請用 mode=local（預設）再問一次具體問題。

Q8：mode=global 為什麼沒有直接給我一段完整答案？ 它只做 map、不做 reduce——回傳的是「每個社群的重點」，彙整刻意留給你的用戶端 LLM，與 answerContext 是「參考資料不是答案」同一套設計哲學。（Blazor 網頁的問答頁會做完整 map-reduce。）

Q9：knowledge_graph_neighbors 查得到的東西比我預期少很多？ 三個常見原因，依序檢查：①那些三元組還在「待審核」——本工具只回已核可的；②該實體的關係屬於你無權存取的團隊；③節點數達 100 上限被截斷（此時回傳會帶 truncated 旗標，請縮小 maxHops）。另外 maxHops 傳超過 3 會被靜默夾到 3（REST 端點則是回 400）。
