一、這個系統的目的與價值

一句話：把零散的素材（會議錄音、影片、PDF/Office 文件、圖片）變成「乾淨、去敏、可被自然語言問答、附出處、且受團隊權限控管」的知識資產。

它要解決的痛點：

  • 資料散在各處（錄音檔、文件、圖片、某個人的記憶裡），找不到、用不上。
  • 內容含個資／機密，不敢直接拿來用或共享。
  • 就算用 AI 問答，也不知道答案的依據在哪、能不能信。
  • 不同人不該看到不同內容，缺乏權限控管與稽核軌跡。

本系統把「匯入 → 聚合 → 清洗 → 蒸餾 → 索引 → 問答」一站一站打通，並讓品質可被量測（清洗品質評測量上游清洗、檢索品質評測量下游檢索），讓知識可被信任、可被稽核、可被權控。

3.1 選單名 ↔ 權限樹名 對照表（設定角色權限前必看）

這是全系統最容易踩的坑：「角色管理」/roleviews 的權限樹上，項目名稱刻意保留舊名，與左側選單顯示的名稱不一樣。所以你在選單看到「知識百科」，去權限樹卻要找「知識瀏覽」。

為什麼不一起改？ 因為權限樹的字串是既存資料——它被寫進每個角色的 RoleView.TabViewJson 欄位裡。一旦改字串，所有既有角色都會立刻掉權限。系統另有一條自動化測試（MenuPermissionAlignmentTests）釘住這張對照關係，確保兩邊不會各自漂移。選單名以「使用者看得懂用途」為準、可自由調整；權限名不得變更。

四、前置：安裝、啟動、第一次登入

本節為最小可動步驟；第三方工具（ffmpeg/yt-dlp/markitdown/Node 工具鏈）的逐項安裝與路徑設定，請依 使用者安裝與操作手冊 §1–§3 完成。

  1. 安裝執行時：Windows 10/11（64 位元）；安裝 .NET 10 ASP.NET Core Runtime（winget install Microsoft.DotNet.AspNetCore.10）。以 dotnet --info 確認可見 10.x 的 Microsoft.AspNetCore.App。
  2. 解壓程式：解壓到有完整讀寫權限的純英文路徑（例如 C:\KnowledgeExtraction\app）。
  3. （選配）設定金鑰與工具路徑：要用「轉錄／文件轉文字／圖片解讀／LLM 清洗」時，在 appsettings.json 填 OpenAISettings:ApiKey 與對應工具路徑（FfmpegPath/YtDlpPath/MarkItDownPath）。沒有金鑰也能登入操作，只是清洗只做「彙整＋繁體化」並標註略過 LLM 步驟（註記全文：> 註記：未設定 LLM（OpenAI ApiKey），略過去重/遮罩/分類/摘要，僅輸出彙整與繁體正規化內容。），且 PDF 萃取會降級走 MarkItDown（見 §6.2）。
  4. 啟動（本機建議只綁 HTTP）：在解壓目錄開 PowerShell 執行

六、匯入素材（三條管線）

三條管線都在左側選單的「資料匯入」群組下（1.0.17 起），操作模式一致：「清單頁 → 新增 → 背景處理」。匯入後為背景作業，清單會即時顯示狀態與進度；失敗可重試、處理中可取消。三者共通的標籤欄位：分類（多選，來自知識庫分類 /categories）、團隊（多選，決定可見範圍）。

還有第四個匯入入口：會議管理頁（/meeting）的「上傳錄音」，會自動轉錄並產生 AI 會議紀錄與待辦草稿——見 第十四章 §14.3。

多選欄位使用方式：在下拉中勾選多個分類／團隊；留空表示「公開（無團隊）」。

素材版本鏈：三條管線的每筆記錄都可按「上傳新版本」上傳改版檔案，形成版本鏈——版本欄顯示 v{n}、舊版標「（已被取代）」，可按「版本歷史」查看各版本。知識來源會沿版本鏈指向最新版本，便於文件改版後更新知識（見第十五章一條龍）。

上傳時會出現進度視窗（1.0.50 新增）：四條上傳管道（影音／文件／圖片／會議錄音）在讀取檔案時都會彈出「上傳檔案中」視窗，顯示檔名、進度條與「已上傳 X / Y」。

  • 這個 X / Y 是資料量（MB/GB），不是「第幾個檔案」——即使是批次 zip，顯示的也是那個 zip 檔的讀取進度。
  • 視窗不能用 X、點遮罩或 Esc 關閉，只能按「取消」；進度到 100% 後取消鈕會失效（因為檔案已讀完、要開始送出了）。
  • 取消是乾淨的：這個階段只是把檔案讀進記憶體，還沒送到後端，所以取消不會留下任何檔案或資料列，不需要事後清理。

6.2 文件轉文字 /document-extraction

上傳 PDF/Word/Excel/PPT 轉成 Markdown。轉換路徑依格式分兩條：

  • PDF：本專案的出貨設定（appsettings.json 的 MarkItDownSettings.PdfUseLlm = true、PdfLlmModel = gpt-5.4）是先把整份 PDF 送給大語言模型轉 Markdown，所以 PDF 會用到金鑰、也會計入 Token 用量。好處是版面、表格、圖表都判讀得比較好：圖片與圖表會在原位以 > **[圖片]** 開頭描述內容，可還原成數據的圖表還會另外輸出 Markdown 表格。逾時 600 秒、只嘗試一次。
  • 沒有金鑰（或 LLM 失敗）不會讓工作失敗，系統會自動降級改用 MarkItDown，並在該筆紀錄留下訊息 AI 解析 PDF 失敗，已自動改用 MarkItDown 轉換：{原因}，狀態仍是「已完成」。看到這行就知道這份 PDF 走的是純本機路徑、品質與 AI 路徑不同。
  • 若想關掉 AI 路徑，把 PdfUseLlm 改成 false（程式屬性的預設值本來就是 false，是本專案的設定檔把它打開的）。
  • PDF 以外的格式：一律走 markitdown（本機執行、不需金鑰、忠實萃取）。

兩條路徑之外，都可再選擇以提示詞讓 LLM 依萃取結果生成內容（需金鑰）。

  • 索引：待索引／等待中／處理中（NN%）／已索引／失敗／已取消

若素材在別的畫面被編修過，「狀態」欄會多一個橘色標籤「內容已變更，建議重新清洗→蒸餾」——看到它就代表下游的清洗結果、Wiki 與索引都還是舊內容。

7.2 管理成員

按「管理成員」把上面已匯入的素材加入此來源。素材型別下拉共四種（1.0.25 起）：影音轉逐字稿（逐字稿）／文件轉文字／圖片解讀／會議紀錄——第四型「會議紀錄」加入的是已產生的 AI 會議紀錄（只列「會議紀錄狀態＝已產生」的會議，索引 AI 會議紀錄而非逐字稿）。

  • 硬性限制：只能加入已完成的素材（會議須「已產生」）、受團隊權控（看得到才能加）、不可重複加入同一筆。
  • 挑選建議：同一主題的素材放一起；依合理順序排列（影響清洗後的閱讀順序）。
  • 挑選輔助：右側「加入素材（僅顯示已完成）」除了型別下拉與「搜尋標題」，還有「分類過濾」「團隊過濾」兩個多選、排序下拉（最近更新優先／最舊更新優先）與「上一頁／下一頁」分頁；已加入的會顯示「已加入」而非「加入」按鈕。
  • 左側「已加入成員（依順序）」每列有「上移」「下移」「移除」。

素材被編修後系統會自動偵測：四種素材型別（影音／文件／圖片／會議紀錄）只要在各自畫面編修過文字內容，系統就會把所有引用它的知識來源自動標記為「內容已過時」（清單上出現「內容已變更，建議重新清洗→蒸餾」標籤），你不必自己記得哪些來源受影響。刪除素材時還會順便清掉指向它的孤兒成員。

但有兩種情況刻意不標記（因為不影響聚合內容）：①只改素材的標題／分類／團隊等中介資料；②會議把 AI 產出的摘要／決議事項／與會人員套用到欄位（這三個欄位不進知識來源內容）。

7.3 清洗（產出乾淨知識）

  1. （選配）先到 /cleaning-profiles 準備一組客製設定檔。
  2. 在該知識來源按「清洗」，於對話窗選擇要套用的清洗規則設定（或「預設／全域」）。
  3. 系統在背景做：去重 → 遮罩 → 分類 → 摘要 → 信心自評，產出單一 Markdown。
  4. 依信心分數自動路由：≥ 門檻（預設 0.70） → 狀態「已清洗」；否則 → 「待審核」。
  5. 「待審核」者由具「知識審核」權限者開啟，核准／退回（填理由）。
  6. 隨時可「檢視清洗結果」：預覽、複製、線上編修。清洗結果只存檔案（C:\temp\KnowledgeExtraction\CleanedSource\{年}\…），不存資料庫。

清洗狀態機：草稿 → 等待中 → 處理中 → 已清洗 / 待審核 / 失敗 / 已取消（待審核經人工核准轉「已清洗」、退回轉「已退回」）。

沒有金鑰時：清洗只做「彙整＋繁體化」，跳過 LLM 去重/遮罩/分類/摘要並標註略過。遮罩失敗＝整筆清洗失敗（安全設計）。

7.4 AI 對話（單一來源問答）

每筆知識來源可開「AI 對話」（ChatGPT 風格、多輪、串流）針對該來源內容提問；可切換回答詳簡（簡潔／標準／詳細）、檢視參考資料、逐則訊息複製原始 Markdown。此為單一來源的對話；跨整庫問答見第十一章。

八、清洗品質評測 /golden-samples

用「標準答案題庫」量測上游清洗品質並校準「自動放行」的信心門檻——把它當清洗的「單元測試」。

評測用哪些紀錄？ 評的是每筆黃金樣本自己的「原始輸入文字」（你貼進去的代表性髒資料）＋你標的標準答案，完全不會讀取「知識來源加工」的任何紀錄。「評測此筆」＝該筆樣本；「評測全部」＝目前頁面所有黃金樣本。沒有任何黃金樣本時，清洗／搜尋照常運作、結果一樣（清洗品質評測只量測、不改變系統）。

⚠️ 多值欄位一律「一行一項」，不要用分號或逗號分隔。 下表四個多值欄位的畫面標籤都明寫「（每行一項）」，系統唯一認得的分隔符是換行。若你把 王小明;0912345678 填成一行，系統會把整串當成一個詞去比對，永遠不會命中 → 遮罩召回率恆為 0，你會誤判清洗壞了。

欄位（畫面標籤）意義如何輸入必填
標題樣本名稱自由文字✅
輸入文字要餵入清洗管線的原始彙整文字貼一段代表性的髒資料—
預期遮罩詞（每行一項）清洗後不該出現的敏感字串一行一個，例如第一行 王小明、第二行 0912345678—

操作：新增樣本 → 按「評測」（或「評測全部」）→ 系統用目前的清洗提示詞跑你的輸入，算出遮罩召回率、分類 F1、摘要涵蓋率等，並建議自動放行門檻。指標解讀（參考值）：遮罩召回 ≥ 0.98、F1 ≥ 0.70。

建議門檻為參考值；要實際生效需改 appsettings.json 的 SystemSettings.Cleaning.ConfidenceThreshold（預設 0.70）。

十一、AI 知識問答 /knowledge-base-chat

用自然語言跨整個知識庫提問，得到附出處、且只回你有權看的內容的答案。

  • 控制項：畫面右上有「新對話」、「我的對話」與「系統提示詞設定」（展開後按鈕文字變「收合設定」）三顆按鈕。新對話（1.0.105 新增）會清空畫面上的問答並開始新的一段對話，但設定面板的所有條件都保留；串流中此鈕停用（要中斷請按「停止」）。展開設定後可調：回答詳簡切換（簡潔／標準／詳細）、套用既有提示詞、編輯系統提示詞、限定知識來源、限定分類、限定團隊（皆留空＝全部；團隊篩選 1.0.x 起）、送出／串流中可「停止」、多輪對話。分類下拉只列你可存取知識中實際用到的分類、團隊下拉只列你可存取的團隊；篩選只在有權限範圍內再縮小、無法擴權。設定的變更套用於下一則訊息。
  • 回答動作：每則回答可「複製」原始 Markdown 或「下載 PDF」；並可按「滿意」👍／「不滿意」👎 回饋（寫入 問答稽核明細供管理員查閱；再按同一顆＝取消回饋）。回饋會匯總進統計報表的「AI 回答滿意度」與「問答使用統計」。
  • 出處面板：預設收合，標頭是「出處（N）」，可「展開／收合」。每筆出處會標示層別——藍色「蒸餾頁」代表命中的是蒸餾後的 Wiki 頁，綠色「清洗內容」代表命中的是清洗後內容；另附「相似度 0.000」（三位小數）與 160 字以內的片段。
  • 查無依據 / 信心不足的固定訊息：完全查不到依據時，系統不會呼叫 LLM，直接回「您的問題在知識庫中查無相關依據。請嘗試調整問法，或確認該主題是否已納入知識庫。」；只找到弱相關內容時，會在正常答案前加上「⚠️ 信心不足：知識庫中僅找到弱相關內容，以下回答僅供參考。」

11.0.1 我的對話與繼續對話（1.0.40 新增）

按右上「我的對話」會滑出抽屜，列出你自己在這個頁面的歷史對話（每列顯示對話標題、藍色「N 輪」標籤、時間），每頁 10 筆。

抽屜最上方有關鍵字搜尋（1.0.105 新增）：輸入後按 Enter 或「搜尋」即可篩選，比對範圍是對話標題與該段對話各輪的提問文字，不含 AI 回答，因此第 2 輪以後才問到的字詞也搜得到；按「清除」回到完整清單。同一個抽屜也用於「知識來源 AI 對話」頁。

點任一列進入詳細頁，可看整段問答與每輪當時的「設定：」摘要；上方有「← 返回清單」與「繼續對話」。按「繼續對話」會把那段對話載回主畫面接著問下去。

這個抽屜有本人限制：只讀得到自己帳號的對話，別人的讀不到。管理員要看全部人的對話請用 §13.4 完整對話紀錄。

  • 查詢改寫（QueryRewrite）：系統會即時改寫你的問句以提高檢索命中，無須手動處理。
  • 出處鑽取：每個答案附來源，可鑽取回「知識來源 → 成員 → 原始檔」，並可下載原始檔。
  • 團隊權控：每次查詢即時驗證權限，非管理員不會檢索到無權限內容（越權洩漏應為 0）。
  • 前置：對應知識來源需已「清洗 → 蒸餾 → 索引」，且嵌入端點已設定。

怎麼問得到好答案、出處面板細節見 AI 知識問答使用指南。

11.1 外部 AI Agent 整合（MCP Server）

同樣的問答與團隊權控能力，另以 MCP Server（端點 /mcp）對外提供，讓 Claude／Codex 等 AI Agent 直接查詢知識庫。

  • 六個工具：knowledge_ping（連線測試）、knowledge_ask（附出處問答；1.0.91 起支援 mode=global 走社群摘要）、knowledge_search（純檢索）、knowledge_list_sources（列可見來源）、knowledge_get_document（取單一文件內容）、knowledge_graph_neighbors（查實體的 N 跳鄰域，純資料庫查詢、不呼叫 LLM，1.0.91）。
  • 唯讀 REST 端點（1.0.96）：不講 MCP 協定的系統可改用 POST /api/v1/KnowledgeGraph/global-ask 與 GET /api/v1/KnowledgeGraph/neighbors（JWT 認證、權控與 MCP 走同一條程式碼、無寫入端點）。
  • 雙認證：JWT Bearer（登入取得）或 X-API-Key；API Key 由管理員在 MCP 金鑰管理 /mcp-api-keys 網頁建立、即時啟用/停用（存資料庫，1.0.9 起）。
  • 權控一致：MCP 呼叫套用與網頁問答相同的團隊權控——呼叫者身分決定可見範圍，非管理員不會查到無權限內容。
  • 可稽核、可計量：MCP 問答寫入 問答稽核明細 /chat-logs，token 用量歸屬呼叫者、可在 /token-usage 與統計報表查閱（1.0.8 起）。

連線設定步驟（Claude Code／Codex）、各工具參數與範例見 MCP 服務使用說明書。

11.2 全域問答（社群摘要模式，1.0.85 起）

設定面板的「查詢模式」下拉有兩個選項，用來對付兩種性質不同的問題：

一般（精準檢索）全域（社群摘要）
適合的問題具體事實、條款、步驟、數字綜觀、趨勢、系統性根因、「整體有哪些…」

問法建議、成本估算與完整限制見 知識圖譜（Graph RAG）使用指南 §六。

十二、檢索品質評測 /rag-evaluation

量測下游檢索品質與權控合規——「找得到／找得準／不外洩」。與清洗品質評測（上游清洗）併呈，形成「清洗 → 檢索」完整把關鏈。

評測用哪些紀錄？ 評的是你建立的每筆「問句樣本」（Query＋期望命中來源等）。按「評測」時，系統把該問句送進混合檢索，打的是整個已索引知識庫（所有已索引內容），並套該樣本模擬的團隊權限（評測團隊／模擬管理員）過濾——不是某一筆來源、也不是「未索引的知識來源清單列」，而是「全部已索引內容（在模擬權限範圍內）」。前提：要先完成「清洗 → 蒸餾 → 索引」。整個過程純檢索、不經 LLM 生成；結果只寫回樣本指標，不改索引或實際問答／搜尋行為。

⚠️ 同樣地，這裡的三個多值欄位也是一行一項（畫面標籤已明寫），不可用分號分隔——否則「越權洩漏＝0」這條安全驗收會被誤判成通過或失敗。

欄位（畫面標籤）意義如何輸入必填
標題樣本名稱自由文字✅
問句要送入混合檢索的問題例如「退款要幾天？」✅
期望命中來源（每行一個知識來源標題）應被檢索到的知識來源標題（相關性 ground truth）一行一個；須與實際已索引的來源標題一致。比對不分大小寫，但全形/半形、空白、錯字會判為未命中—
期望錨點（每行一項，選填；用於出處正確率）應命中的章節／條款錨點一行一個（章節/條款）—
模擬團隊（每行一項，空＝公開使用者）模擬使用者的團隊（越權洩漏測試用）一行一個—
模擬管理員是否模擬為不受權控的管理員勾選—

操作：新增樣本 → 「評測」→ 看儀表板指標：P@k／R@k／NDCG／MRR、檢索延遲（毫秒），越權洩漏以紅色標示（應為 0）。

知識圖譜相關指標（1.0.92 起）：儀表板另有四項——圖召回增益（主指標；期望來源中其命中全部來自圖檢索那一路的比例，是保守下界，圖分讓排名上升而擠進 TopK 的效應不計入）、圖參與率、圖獨有命中（向量與關鍵字皆 0 分、只有圖找到的）、平均取用社群數。基線會一併記錄當時的 GraphWeight／GraphMaxHops／GraphHopDecay；基線建立於這些欄位加入之前時顯示「未記錄」而不是 0（0 會謊稱當時圖是關閉的）。

樣本另可指定走「全域問答（社群摘要）」評測模式：以關鍵詞涵蓋率計分，P@k／NDCG／MRR 顯示「—」（全域模式沒有排序後的出處清單）。⚠️ 該模式會呼叫 LLM，因此不是確定性的（同一樣本兩次跑分數可能略有差異），成本為可存取社群數次呼叫，且關鍵詞為子字串比對、不處理同義詞。

13.4.1 /chat-logs 與 /chat-sessions 該用哪一個

你想做的事用哪頁
看實際送進 LLM 的完整提示詞/chat-logs（只有這裡有）
看信心、topScore、滿意度/chat-logs（/chat-sessions 沒有這三欄）

為什麼 /chat-sessions 看不到 MCP？ 因為 MCP 的 knowledge_ask 是單次呼叫、沒有「對話」概念，寫紀錄時不帶 SessionId，所以不會產生對話列。MCP 的問答一律到 /chat-logs 查（來源選「MCP Server 問答」）。

隱私提醒：這兩頁的全文都確實落地在實體檔案（刻意設計，僅管理員可查）。做資安說明時不要說「問句與回答不落地」——那是錯的。真正不含問句本文的是 /rag-diagnostics 用的檢索稽核（只存長度與分數）。

13.5 檢索診斷與調校 /rag-diagnostics

以「AI 知識問答稽核」為資料源，做 topScore 分佈與門檻校準：看總問答數/有命中/查無命中/查無依據/信心不足/正常回答等統計；可熱套用 RejectThreshold／LowConfidenceThreshold（免改 appsettings.json、下一則問答即生效）與查詢期檢索參數（TopK/CandidateTopK/向量權重/關鍵字權重/MinScore）；提供「試檢索」（不呼叫 LLM、不寫稽核）與索引健康、症狀自檢。

13.6 資料一致性巡檢 /data-consistency

列出「孤兒成員」（知識來源成員指向已不存在的素材）與「過時來源」（成員內容變更後尚未重清）。可一鍵「清除所有孤兒成員」「重新清洗所有過時來源」，或對單筆「重新清洗」。

13.7 日誌等級切換 /log-settings

執行期暫時切換最低日誌等級（Trace/Debug/Information/…）：立即生效、免重啟；但存檔仍以 nlog.config 為準。Trace/Debug 噪音大，診斷完請切回 Information。日誌檔在 NLog.BasePath 下（預設 C:\temp\Logs\...）。

依時間區間把系統日誌打包成 zip 下載，方便把某段時間的日誌交給支援人員排查。

  • 操作：選「起始時間」「結束時間」（預設＝最近一小時）→ 按「下載」→ 取得 zip。也可用「快速區間」下拉（最近 10/30 分鐘、1/2/3 小時；1.0.13 新增）以現在時間回推自動帶入起訖，選完仍可手動微調。
  • 限制與驗證：未選時間→「請選擇起始與結束時間。」；起始晚於結束→「起始時間不可晚於結束時間。」；區間上限 31 天；合併後未壓縮超過 200 MB →「選取範圍的日誌量過大，請縮小時間區間。」
  • 內容：來源為 NLog 應用程式日誌（每日輪替、保留 30 天）；逐筆依時間戳過濾（含端點）、例外堆疊等多行內容完整保留，依時間排序合併為單一 .log 後封裝；zip 檔名 logs_{yyyyMMddHHmm}-{yyyyMMddHHmm}.zip。區間內無資料仍會下載（空日誌檔）。
  • 權限：僅管理員；非管理員進頁顯示「您沒有權限下載系統日誌。」，API 端亦擋 403。

13.9 統計報表（共通操作）

側邊選單獨立群組「統計報表」共五頁，供管理員做管理決策；非管理員顯示「您沒有權限檢視統計報表。」

  • 進頁即查：以預設條件自動查詢——起始日／結束日預設近 30 天（今日−30～今日，含當日）。
  • 篩選：日期區間＋團隊多選（空＝全部、可搜尋）→ 按「查詢」。
  • 匯出：每頁都有「下載 PDF 報表」，把目前查詢結果匯出成 {報表前綴}_{yyyyMMddHHmmss}.pdf。

13.15 待處理背景工作 /pipeline-jobs（1.0.78 新增）

位置在「系統管理 › 系統監控」，僅管理員可見；統計為全庫（不套團隊權控）。首頁管理者專區第五張卡可直達。

列出 7 條背景管線目前「等待中／處理中」的工作，每 5 秒自動更新，可逐筆取消。

管線顯示名對應實體待處理狀態處理中狀態
影音轉逐字稿MediaTranscription等待中處理中
文件轉文字DocumentExtraction等待中處理中
圖片解讀ImageRecognition等待中處理中
知識來源清洗KnowledgeSource.Status等待中處理中
知識來源蒸餾KnowledgeSource.DistillationStatus等待中處理中
知識來源索引KnowledgeSource.EmbeddingIndexStatus等待中處理中
會議紀錄產生Meeting.MinutesStatus排隊中產生中

同一筆知識來源最多會出現三列（清洗／蒸餾／索引是同一張表的三個階段），一列＝一條管線的一筆工作。

數字為什麼取自資料庫、而不是佇列長度

佇列是記憶體中的 Channel，讀取即消耗、無法在不破壞它的前提下列舉內容。而且佇列長度與實際狀態必然有落差：工作被取出的瞬間它已離開佇列、但狀態還沒寫成「處理中」；取消後狀態已是「已取消」、但那筆仍留在佇列裡佔位；重啟後佇列歸零、但資料庫裡仍有「處理中」。所以本頁與首頁卡片都只看資料庫狀態——這也是卡片數字永遠等於本頁列數的原因。

兩種取消的差別

情況取消時實際發生什麼
等待中／排隊中把狀態改成「已取消」。背景服務之後把這筆從佇列取出時會檢查狀態並跳過它（不會真的從佇列移除，因為技術上做不到）
處理中／產生中對正在執行的工作發出取消訊號，中斷它

兩者都不會刪除紀錄。取消後可到來源頁重新觸發（欄位「前往來源頁」直接跳過去）。

沒有「全部取消」是刻意的

每條管線同時只處理一筆，所以全系統最多同時 7 筆是「處理中」，批次能省的操作極少；而「處理中」的取消在少數競態下會出現「標記成已取消但處理其實跑完了」，批次操作會把這個窗口放大。若之後有需要，安全的形狀是「只批次取消等待中」——那條路徑沒有競態。

十四、專案協作（專案／工作／會議）

左側選單「專案協作」群組的三個畫面。專案與工作屬一般協作追蹤；會議管理自 1.0.20 起已接上知識管線——上傳錄音會自動轉錄並由 AI 產生會議紀錄，所以這一組不再是「與知識管線無關」的孤島。

三頁的分類皆來自 專案分類（/work-categories，見 5.3），不是知識庫分類；團隊標籤則與全系統共用同一份團隊管理，權控規則一致。

14.1 欄位一覽

  • 專案管理 /projects：標題、說明、起訖日、狀態、優先級、完成百分比（0–100）、負責人、分類、團隊。
  • 工作任務 /Task：欄位類同專案，外加分類與所屬專案（選填、可清除）；工作可有子工作（多層）。
  • 會議管理 /meeting：標題、說明、摘要、出席者、起訖日、所屬專案（選填）、分類、團隊，另有 1.0.19 新增的 會議形式（實體／線上／混合）、地點、主持人、紀錄人、決議事項。編輯表單中的摘要與決議事項採左編輯／右 Markdown 預覽的分欄版面（1.0.22 起），兩區各有一顆複製鈕——左邊複製 Markdown 原始碼、右邊複製渲染後的純文字。清單頁精簡為 8 欄（標題／摘要／會議紀錄狀態／開始日期／所屬專案／分類／團隊／操作，1.0.21 起），其餘欄位改於編輯表單檢視；摘要過長時單行截斷，滑鼠停留可看全文。

「所屬專案」在專案管理、工作任務、會議管理三處都是選填。可以先建工作或會議、之後再掛專案，也可以清除掛載。

14.2 彙總進度（1.0.19）

完成百分比不再只靠人工維護：

  • 工作任務：若有子工作，顯示值＝所有子工作完成百分比的平均（含 0% 的子工作一起算）；沒有子工作時取自身的手動值。
  • 專案管理：若有頂層工作，顯示值＝所有頂層工作彙總進度的平均；沒有工作時取自身的手動值。

清單上會標明該筆是「依子工作自動彙總」還是「手動值」，避免誤以為手動改了沒生效。要讓專案進度自動反映實況，就把工作拆成子工作並各自更新完成度。

14.3 會議 AI 自動化（1.0.20）

在會議清單列按「上傳錄音」上傳會議錄音／錄影（格式同影音轉逐字稿，單檔 2GB），系統會：

  1. 建立一筆轉錄紀錄（繼承該會議的分類與團隊）並排入轉錄佇列。
  2. 轉錄完成後自動呼叫 LLM 產生會議紀錄 Markdown（落檔保存，可在頁內編修存回）。
  3. 同時從逐字稿抽出待辦草稿（標題／負責人／期限）。

清單的「會議紀錄狀態」欄依序顯示：轉錄中 → 轉錄完成 → 產生中 → 已產生。1.0.21 起清單每 5 秒自動更新，不必手動按重新整理；產生完成時右下角會跳出通知，告知接下來可做什麼。

待辦要人工確認才會建立：按「待辦確認」開啟草稿清單，逐筆勾選後確定，才會建立工作任務；建出來的工作繼承這場會議的專案、團隊、分類。已建立過的草稿在「建立狀態」欄標示「已建立」並整列停用，不會重複建立；尚未建立的顯示「待建立」。

勾選前可以就地修正 AI 的產出：事項標題、負責人、期限都可以直接改，另有「工作狀態」下拉（未開始／進行中／已完成／暫緩／等待），決定建出來的工作任務起始狀態（預設「未開始」）。這些編輯會一併存回草稿，重開對話窗看到的是你確認過的版本。

⚠️ 1.0.20 有個缺陷：這些欄位雖然可以輸入，但送出時會被丟棄（服務層只收索引、草稿一律從資料庫重讀）。1.0.21 已修正，就地編輯現在真的會生效。

建出來的工作可回溯來源會議（1.0.24 起）：工作任務（/Task）編輯窗有唯讀欄位「來源會議」，顯示該會議目前標題、可點擊跳回 /meeting；依 MyTask.SourceMeetingId 軟參照即時解析，會議改名即時反映，被刪或無權時顯示「（來源會議已移除或無權存取）」。

摘要欄位只填空白、不覆寫：自動產生時，只有原本空白的「摘要／決議事項／出席者」會被填入 AI 結果——自動觸發時沒有人在現場確認，不能弄丟任何人工輸入。要改用 AI 版本，按該列的「套用 AI 結果」，會跳確認視窗，確認後才覆寫這三欄。

注意：需已設定 OpenAI 金鑰；未設定時轉錄仍會完成，但不會產生 AI 會議紀錄。若 LLM 未依格式回應，系統會降級把整份回應存為會議紀錄（狀態仍為「已產生」），摘要類欄位留空由人工整理。從 /media-transcription 一般上傳的音訊不會觸發會議紀錄產生。

把會議紀錄納入知識來源（1.0.25 起）：已產生的 AI 會議紀錄可作為知識來源的第四型素材——在 /knowledge-sources「管理成員」的素材型別下拉選「會議紀錄」，只會列出「已產生」的會議；聚合器索引的是 AI 會議紀錄（非逐字稿），彙整標頭為 ## 會議紀錄：{標題}（見 7.2）。

十五、端到端完整走查範例（一條龍）

以「把每週產品會議變成可問答知識」為例，串起所有畫面：

  1. 基礎設定：/teams 建「PMO」；/categories 建「會議」；/roleviews 建「知識管理員」（勾權限＋預設團隊 PMO）；/myusers 建你自己的帳號並指派該角色。
  2. 匯入：到 /media-transcription 上傳週會錄音（標題「2026Q2-產品週會-0612」、團隊 PMO）→ 等狀態變「已完成」。
  3. 檢視/編修：打開逐字稿，把聽錯的人名、料號改正存回（錯字會一路帶到下游）。
  4. 聚合：到 /knowledge-sources 新增「2026 Q2 產品週會」（團隊 PMO）→「管理成員」加入上面的逐字稿。
  5. （選配）配方：到 /cleaning-profiles 建「會議配方」，摘要提示詞要求分「決議／待辦／負責人」三段。
  6. 清洗：在該來源按「清洗」選「會議配方」→ 信心 0.83 ≥ 0.70 → 自動「已清洗」→「檢視清洗結果」確認。
  7. （選配）評測：到 /golden-samples 放一筆含決議與人名的標準答案，按「評測」看摘要涵蓋率與建議門檻。
  8. 蒸餾：在該來源按「蒸餾」🧪 → 到 /knowledge-distillation 審核 Wiki 頁（核准）。
  9. 索引：確認 appsettings.json 已設嵌入端點 → 蒸餾後系統自動建索引，狀態變「已索引」。
  10. 問答：到 /knowledge-base-chat 問「上次週會對 X 的決議是什麼？」→ 得到附出處答案，點出處鑽取回逐字稿原文。
  11. 回歸把關：到 /rag-evaluation 放幾筆問句，建立檢索品質基準（越權＝0），日後改動可防回歸。

最終得到：一份乾淨、去敏、可被自然語言問答、附出處、受團隊權控、且品質可量測的會議知識資產。

十六、貫穿全程的重要觀念

  • 團隊權控：非管理員只看得到「公開（無團隊）」或「與自己角色預設團隊有交集」的紀錄；管理員不受限。看不到資料時，先確認角色預設團隊與紀錄團隊是否相符。
  • 標籤是精確比對的字串：分類/團隊以名稱字串比對，命名後勿隨意更名。
  • 多數產物只存檔案：逐字稿、萃取 Markdown、清洗結果、Wiki 頁都存在 C:\temp\KnowledgeExtraction\… 對應子目錄，DB 只存相對路徑。
  • 背景作業 + 重試/取消：三條匯入管線與清洗/蒸餾/索引都是背景任務，失敗可重試、處理中可取消。
  • 遮罩失敗＝整筆清洗失敗：安全優先，寧可重跑。
