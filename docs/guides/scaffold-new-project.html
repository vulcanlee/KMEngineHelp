腳手架新專案啟動流程

從本腳手架複製成新系統時的操作步驟與檢查清單，避免命名、設定、帳號與文件殘留舊專案資訊。

  • 文件用途：從本腳手架複製成新系統時的操作步驟與檢查清單，避免命名、設定、帳號與文件殘留舊專案資訊。
  • 主要讀者：開發者、技術主管
  • 文件版本：1.1（反映 1.0.70 的腳本修正；補 New-CrudModule 產出位置與搬入後必做步驟）
  • 更新日期：2026/07/26
  • 對應系統版本：1.0.71
  • 編碼：UTF-8（繁體中文，含 BOM）

本文件是建立新專案時的操作檢查清單；下列項目依每次新專案情境逐項確認，不視為 KnowledgeExtraction.AI 目前 backlog。

一、產生新專案副本

pwsh -File scripts/New-StarterProject.ps1 -ProjectName 新系統代號 -DestinationPath 目標目錄

腳本會做的事：遞迴複製（排除任何層級的 .git／bin／obj／.vs／.playwright-cli／output）、把文字檔內的 KnowledgeExtraction 換成新代號、重命名含舊名的資料夾與檔案、清洗敏感值，最後跑一次安全檢查。

1.0.70 修正了三個會咬人的問題

問題修正後
敏感值清洗永遠不命中（比對固定舊值 "SupportPassword": "support"，但實際值早就不是它）改成以鍵名為準的 regex，涵蓋 SupportPassword／SupportEmail／SigningKey；安全檢查也改成「讀回值是否等於預期佔位值」
會把 docs/ 下所有 .md 的 BOM 剝掉（PowerShell 7 的 Set-Content -Encoding UTF8 是無 BOM），新專案第一次跑 Test-DocsEncoding.ps1 就整批 FAILED逐檔保留原本的 BOM 有無
排除目錄只過濾最上層，巢狀的 src/<方案>/.vs 仍被複製；.vsidx 在 Visual Studio 開著時被鎖定 → 腳本在複製階段就崩潰改為逐檔複製並過濾任何層級的排除目錄

清洗後仍要人工確認

腳本會把這些換成佔位值，但佔位值不是安全值，部署前必須改成真正的隨機值：

設定鍵清洗後的佔位值
BootstrapSettings.SupportPasswordchange-me
BootstrapSettings.SupportEmailsupport@example.com
JwtSettings.SigningKey<新代號>-ChangeThisJwtSigningKey-AtLeast32Chars-ReplaceBeforeProduction

JwtSettings.SigningKey 有 [MinLength(32)] 驗證，替換值必須 ≥32 字元，否則新專案一啟動就設定驗證失敗。

⚠️ SupportPassword 為什麼重要：程式每次啟動都會用它重設 support 帳號的密碼雜湊（不是只有第一次），所以留著已知值等於內建一組後門帳密。

腳本結尾會列出仍需人工檢視的殘留（例如 docs 裡提到舊金鑰字串的說明文字），並固定提醒一次「請在部署前修改 SupportPassword 與 SigningKey」。

二、改名檢查清單

  • 替換 solution、project、namespace 與 assembly 名稱（腳本已做大部分，仍需複查）。
  • 檢查 src/<新代號>/<新代號>.slnx 內所有 project path 是否同步更新。
  • 更新 appsettings.json 的 SystemSettings.SystemInformation（系統名稱、描述、版本）。
  • SystemVersion 是全系統唯一的版本來源；本專案慣例是每次完成一次可建置的異動就 +1，並在 commit message 說明。
  • 更新 README、docs/ 與 CI workflow 顯示名稱。
  • 檢查 UserSecretsId、NLog 路徑（NLog.BasePath，出貨為 C:\temp\Logs）、ExternalFileSystem.* 各資料夾路徑、BootstrapSettings 與部署環境 secret。
  • 決定是否保留 tools/：目前只有 tools/douyin-audio（抖音下載助手），是本專案特有的外部工具，新系統若不需要抖音轉錄可整個移除（並清掉 OpenAISettings.DouyinHelperScript／NodePath 與健康檢查的相關期待）。
  • CLAUDE.md 與 AGENTS.md 要依新系統調整：裡面記載的是本專案的不變量（團隊權控、雙 provider migration、選單/權限位置索引、標籤字串格式…），新系統若架構不同會誤導 AI 協作。

三、API 與 DTO 檢查清單

  • Web API request/response 使用 DTO，不直接暴露 Entity。
  • 所有 API 回應統一封裝為 ApiResult<T>。
  • 新增業務模組時，同步建立 CreateUpdateDto、Dto、SearchRequestDto 與 mapping。
  • 新 API 優先使用 /api/v1/...，並保留 /api/... 相容路由直到公告移除。

用 New-CrudModule.ps1 產 CRUD 骨架

pwsh -File scripts/New-CrudModule.ps1 -Name 模組名稱

產出位置是 output/crud-modules/<Name>，是「離線骨架」，不會自動加進方案。 它會產生約 10 個檔案（Entity／Dto／CreateUpdateDto／SearchRequestDto／Repository／Controller／Service／Tests，以及一份 Menu.<Name>.json 片段）。

⚠️ 搬進方案後，骨架還缺這些本專案的必做事項（骨架裡沒有，得自己補）：

  1. 套團隊權控 —— 查詢/下載都要經 IRecordAccessScopeProvider ＋ TagStringHelper.BuildTeamAccessPredicate／IsTeamAccessible。漏了就是資安漏洞。
  2. 權限三處同步 —— Share/Helpers/MagicObjectHelper.cs、Business/Services/Other/RolePermissionService.cs、Web/Datas/Menu.json 以位置索引對應，三處要一起改（有 MenuPermissionAlignmentTests 守著）。
  3. 雙資料庫 migration —— SQLite 與 SQL Server 各一支，見 EFCore.md。
  4. 進頁權限檢查 —— AuthenticationStateHelper.CheckAccessPage(...)。
  5. 改用 CrudActionButton 取代骨架的原生按鈕（全站統一的圖示按鈕）。
  6. 改用 NotificationService —— 本專案已禁用 MessageService。

詳見 建立一個新 CRUD 操作網頁說明。

四、驗收標準

# 1) 建置與測試
dotnet build src/<新代號>/<新代號>.slnx -v:minimal --no-incremental
dotnet test  src/<新代號>/<新代號>.Tests/<新代號>.Tests.csproj -v:minimal

# 2) 文件編碼（docs/*.md 必須 UTF-8 含 BOM、無亂碼）
pwsh -File scripts/Test-DocsEncoding.ps1 -DocsPath <新專案>/docs
  • Swagger UI 可使用 Bearer token 呼叫受保護 API。
  • 新專案文件不再殘留不應公開的開發帳號、JWT key 或舊系統名稱。
  • appsettings.json 的 SystemVersion 已改成新系統的起始版號。

五、備註風險

  • 若只改 UI 顯示名稱但未改 namespace，未來套件發布、log 分類與維運追蹤會混淆。
  • 預設帳號目前仍是腳手架初始化流程的一部分，正式部署前必須處理（改 SupportPassword、建立自己的管理員帳號）。
  • JwtSettings.SigningKey 沒有任何啟動期守門：1.0.69 已移除 Production 啟動安全檢查，程式不會因為你留著開發金鑰而阻止啟動。這一項只能靠人工檢查。
